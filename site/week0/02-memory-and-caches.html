Memory and caches

For six weeks your compiler has turned programs into correct C loops. Week 7 is about making those loops fast, and its first lessons lean on one idea from this page: memory is not equally fast everywhere, so the order a loop touches memory in can change its speed several times over. By the end you can look at a loop and say whether it treats memory well.

Goal

Explain why walking a 2D array row by row is faster than column by column, and count the cache lines a loop touches.

You'll use

Memory as a row of numbered bytes, and an array as a base address plus an offset, from lesson 0.1. The nested C for loops your compiler has printed since week 3.

Warm up

Two questions from lesson 0.1, from memory. Pulling an idea back out of your head is what makes it stay.

An int array a starts at byte address 1000. Each int is 4 bytes. At what address does a[3] start?

Three ints come before a[3]. How many bytes is that?

Base plus offset: 1000 + 3 × 4 = 1012.

How many bytes do 16 ints take?

Each int is 4 bytes.

16 × 4 = 64 bytes. Keep that number in mind. It comes back on this page.

Two loops, one answer

Here are two C loops. Both add up every number in the same 2D array m, which has N rows and N columns. The first goes row by row. The second goes column by column.

for (int i = 0; i < N; i++)
  for (int j = 0; j < N; j++)
    sum += m[i][j];

Row order: finish a row, then start the next.

for (int j = 0; j < N; j++)
  for (int i = 0; i < N; i++)
    sum += m[i][j];

Column order: finish a column, then start the next.

N is 8,000, so m holds 64 million ints. Both loops do the same 64 million additions and get the same sum. How do their times compare?

In lesson 0.1 an array was a row of bytes. Which loop moves through those bytes in order?

Row order took about 20 ms and column order about 430 ms. A millisecond (ms) is a thousandth of a second. That is one run on the machine this course was built on, with gcc at -O1 and one thread. Your numbers will differ.

The processor did the same additions both times. The only thing that changed was the order in which it asked memory for the numbers. The rest of this page explains why that order matters so much, in four small steps.

A 2D array is one long row of boxes

Memory has no rows and columns. It is one long row of boxes. So C stores int m[4][4] by laying its rows end to end: all of row 0, then all of row 1, and so on. This layout is called row-major.

To find m[i][j] in that long row when each row has C columns, count the boxes before it. Here is m[1][2] with C = 4:

  1. Count the full rows. One row comes first, and it fills 4 boxes.
  2. Add the column. 2 more boxes into row 1 makes box 6. In general the box is i * C + j.
  3. Turn boxes into bytes. Each int is 4 bytes, so box 6 starts at byte 24.

The distance in memory from one read to the next is called the stride. Stepping along a row has a stride of 1 box. Stepping down a column has a stride of C boxes.

Repair the row-major index

flat_index(i, j, C) should return the box that holds m[i][j] when each row has C columns. It counts boxes, not bytes. Right now it returns i + j, which forgets how long a row is. Repair it.

The cache is a small, fast copy

A processor can add two numbers in under a nanosecond (ns), a billionth of a second. Fetching a number from main memory typically takes about 100 ns. If every read went all the way to main memory, the processor would spend nearly all its time waiting.

So a small and very fast memory sits right beside the processor. It is called the cache, and it holds copies of boxes that were used recently.

Picture a desk and a library shelf. The shelf holds every book, but each trip to it is a walk. The desk holds only a few books, and reading from it takes no time. Main memory is the shelf and the cache is the desk.

  • A hit is a read that finds its box in the cache. It is fast.
  • A miss is a read that does not. The box is fetched from main memory, which is slow, and a copy stays in the cache.
  • When the cache is full, an old copy is thrown out to make room. That copy has been evicted.

A loop reads the same 3 boxes again and again, and the cache holds 3 boxes. After the first pass, what is each read?

Is anything ever thrown out if only 3 boxes are in use?

The first pass misses 3 times and fills the cache. Nothing new arrives after that, so nothing is evicted and every later read is a hit.

Neighbors come along for free

A cache never fetches just one box. It fetches a cache line: 64 bytes that sit side by side in memory. That is the size on most processors today. One line holds 16 ints.

In the library picture, a line is a whole book. You wanted one page, but you carry the book back to the desk, so the pages next to it are already there when you want them.

Lines sit at fixed places. Line 0 is bytes 0 to 63, line 1 is bytes 64 to 127, and byte b is in line b / 64, rounded down.

An int array starts at byte 0 and nothing is in the cache. You read a[0] up to a[31] in order. How many of the 32 reads miss?

How many 64-byte lines do 32 ints fill?

2. a[0] misses and brings in a[0] to a[15]. a[16] misses and brings in the rest. The other 30 reads are hits.

To count the lines a walk touches, find the line of its first byte and the line of its last byte. Take 2 ints starting at byte 60:

  1. Find the first and last byte. 2 ints are 8 bytes, so the walk covers bytes 60 to 67.
  2. Find their lines. 60 / 64 rounds down to line 0. 67 / 64 rounds down to line 1.
  3. Count. Lines 0 and 1 make 2 lines, even though the walk is only 8 bytes long.

How many lines does a walk touch?

Write long long lines_touched(long long start, int n). You read n 4-byte ints in a row, starting at byte address start. Return how many different 64-byte cache lines those bytes fall in. n can be 0, and then the answer is 0. In C, dividing two positive whole numbers already rounds down.

Row order against column order

Now put the pieces together on a toy machine that fits on the screen. The array is int m[4][4]. A toy cache line is 16 bytes, so each row of m is exactly one line. The cache holds only 2 lines. When it is full, it evicts the line that has gone unused the longest.

Step through row order first and watch the miss count.

Row order missed 4 times, once per line. Column order reads m[0][0], m[1][0], m[2][0], m[3][0], then starts the next column. How many of its 16 reads miss?

Each read in a column is in a different row, so a different line. The cache holds 2 lines. Is row 0 still there when the second column starts?

All 16. Each column touches all 4 lines, and the cache keeps only the last 2. By the time the loop comes back to a line, that line has been evicted.

Back to the real loops

The real machine works the same way, with bigger numbers. A real line holds 16 ints.

  • Row order has a stride of 1 box. It misses once, then gets 15 hits from the same line. Every byte it paid for gets used.
  • Column order has a stride of 8,000 boxes. Every read lands on a different line and uses 1 of its 16 ints. When the loop returns for the next column, 8,000 other lines have gone by, and the array is far bigger than the cache. Most of those lines are gone again.

That is the 20 ms against 430 ms from the start of the page.

With N = 8,000, how many bytes apart are m[i][j] and m[i+1][j]?

Going down one row skips a whole row of 8,000 ints.

8,000 × 4 = 32,000 bytes. A line is 64 bytes, so each step down a column jumps 500 lines ahead.

Rule of thumb

Make the innermost loop walk the last index of the array, so it moves through memory with a stride of 1.

When everything fits, order stops mattering

Column order lost because lines were evicted before the loop came back to them. If the cache can hold every line a loop needs, nothing is evicted and both orders do equally well. On the same machine, a 64×64 array (16 KB) summed many times over took the same time in either order.

That suggests a trick for big arrays: work on a small block, called a tile, finish it while it is in the cache, then move on. Try it. Use the layout: transpose

One more piece of practice with the flat layout. To transpose a matrix is to swap its rows and columns, so the number at row i, column j moves to row j, column i. The result has cols rows and rows columns, so its rows are rows boxes long. That puts dst[j][i] in box j * rows + i.

Transpose a row-major matrix

Write void transpose(const int *src, int *dst, int rows, int cols). src is a rows x cols matrix stored row-major. Fill dst, a cols x rows row-major matrix, so that dst[j][i] == src[i][j].

Both arrays are flat, so you compute every index yourself with the formula from this lesson. The tests check 1 x 1, single rows, single columns and that transposing twice gives back the original.

Which loop order is cache friendly here?

Neither, fully. If the inner loop walks j, reads of src are stride 1 but writes to dst jump by rows. Swap the loops and the problem swaps sides. Fast transposes work on small square tiles that fit in cache, which is the tiling idea in miniature.

The examples print dst through some helper code. Only your transpose matters.

  • Explain why row order uses every byte of each line and column order wastes most of it.

Cache levels and typical sizes, for when week 7 says L1, L2 and L3

A real processor has several caches, not one. Each level is bigger and slower than the one before it. These are rough, typical numbers for a modern desktop chip, not measurements from this page:

leveltypical sizetypical latency
registera few hundred bytes0 cycles
L1 cache32 to 64 KB per core~1 ns (4 to 5 cycles)
L2 cache256 KB to 2 MB per core~4 ns
L3 cache8 to 64 MB shared~10 to 20 ns
DRAMgigabytes~80 to 100 ns

These vary by chip. Only the ratios matter here: each level is several times slower than the one above it. A cycle is one tick of the processor's clock, about 0.25 ns at 4 GHz. A register is one of a few dozen named slots inside the processor where arithmetic actually happens, and a core is one of the chip's independent processors.

A cache line is 64 bytes on x86 and most ARM chips. Apple M-series chips use 128.

Prefetchers and what else the toy leaves out, for readers who want the whole story

Prefetchers. Real processors have hardware prefetchers that spot a regular walk and fetch the next lines before the program asks. They make row order even cheaper than one miss per line suggests. They typically help much less with a stride of 32,000 bytes, which lands on a different 4 KB page of memory on every read. On a small array, column order can look much less bad than the toy suggests.

Address translation. The processor also keeps a small cache of where each page of memory really lives, called the TLB. Column order on a big array misses in that too.

The C compiler. At -O2, gcc also adds several ints with one instruction in row order, which it cannot do down a column. Measured that way here, the gap grew from about 20 times to about 30. The page quotes -O1 so that the gap is only about memory.

Powers of two. With N = 8,192 the column loop took about 820 ms here, nearly twice as long as with 8,000, though the array is only 5 percent bigger. A cache can keep each line in only a few places, chosen by the line's address. With a power of two stride, the lines of one column compete for the same places.

How the timing was done. Each loop sat in its own function, compiled with gcc 14.2 and run 5 times in turn on a desktop processor with about 30 MB of its largest cache. The array is 256 MB. The times on this page are typical of those runs. Do not trust intuition about speed. Measure, as week 7 does.

Check yourself

How many 4-byte floats fit in one 64-byte cache line?

A float is 4 bytes. Divide the line size by the element size.

64 / 4 = 16.

int m[4][4] starts at address 0. What's the byte address of m[2][3]?

Row-major: first count how many ints come before m[2][3], then turn that count into bytes.

Two full rows of 4, plus 3 more. Each int is 4 bytes.

(2 × 4 + 3) × 4 = 11 × 4 = 44.

For float a[N][N] in C, which loop nest walks memory with stride 1 in the inner loop?

Which two elements are neighbors in memory: a[i][j] and a[i][j+1], or a[i][j] and a[i+1][j]?

The inner loop should move the last index, j, because a[i][j] and a[i][j+1] are adjacent in memory.

You sum float a[1024] front to back, and a starts on a line boundary. How many distinct 64-byte cache lines do you touch?

Work out the total bytes first, then how many 64-byte lines that many bytes fill.

1024 × 4 = 4096 bytes, and 4096 / 64 = 64 lines. Each line is fetched once and fully used.

A loop reads a[0], a[16], a[32], ... from a float array (stride 16 floats). What fraction of each fetched 64-byte line does it use?

A stride of 16 floats is 64 bytes. Where does each access land relative to the previous one?

Stride 16 floats is 64 bytes, so every access lands on a new line and uses 4 of its 64 bytes.

On the toy machine above, change the cache to hold 4 lines. How many misses does column order have now?

Column order misses because rows get evicted before the next column comes back to them.

If the cache can hold every line of the matrix at once, does anything ever get evicted?

All 4 lines of m fit at once, so after the first column brings them in, nothing is evicted. 4 misses, same as row order. That's the idea behind tiling: make the working set fit.
