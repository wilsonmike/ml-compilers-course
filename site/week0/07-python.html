Make it run from any folder

The grader lives in the course folder and runs your compiler from there. Guess what that does before you read on.

You cd to a different folder and type python -m mlc hello.uir again. What happens?

Python looks for a package in the folder you are standing in. Is mlc there?

The fix is a wrapper: a tiny script that tells Python where your package is and then runs it. It sets PYTHONPATH, a list of extra folders Python searches for packages. Steps 1 and 2 are the same step for two systems. Do the one for yours.

  1. Windows: save the wrapper. Save these three lines as mlc.cmd in my-ml-compiler, next to the mlc folder. 
    @echo off

  2. macOS and Linux: save the wrapper. Save these two lines as compile in my-ml-compiler, next to the mlc folder. Then run chmod +x compile once, which lets the file run as a command. The name can't be mlc, because a file and a folder can't share a name. 
    #!/bin/sh
PYTHONPATH="$(dirname "$0")" exec python3 -m mlc "$@"
  3. Find the full path. Inside my-ml-compiler, type pwd (in the old Windows Command Prompt, cd alone). It prints the folder's full path, such as C:\Users\you\my-ml-compiler or /home/you/my-ml-compiler.

/home/you/my-ml-compiler/compile hello.uir

What each line of the wrappers does (for when one misbehaves)

Windows. @echo off stops the script from printing its own commands, which would add lines the grader does not expect. %~dp0 is the folder the .cmd file lives in, and %* passes every argument through. The exit code of the last line becomes the wrapper's exit code.

macOS and Linux. #!/bin/sh says which program runs the script. $(dirname "$0") is the folder the script lives in, "$@" passes every argument through, and exec replaces the shell with Python, so Python's exit code is the wrapper's.

Each .py file in the package is a module. Inside the package you import a sibling by its full name, such as from mlc.words import count.

A crash is not an answer

The setup is done. The rest of this page is a short list of Python behaviors that cause wrong answers in a compiler. Each one starts with a guess.

A test holds a broken program and expects REJECTED. Your compiler hits the broken line and raises a ValueError that nothing catches. What does the grader record?

The grader reads one line from your program's normal output. Where does Python print a traceback?

An uncaught exception is an error that no except handles. Python prints its traceback to stderr, the separate channel for error messages, and prints nothing to the normal output. The grader finds no line and fails the test.

So refusing a program takes three moves:

  1. Make your own exception class. For example class Rejected(Exception).
  2. Raise it wherever your compiler finds a broken program.
  3. Catch only that class at the top, and print REJECTED and the path.

Let every other exception crash loudly. Such a crash is a bug in your compiler, and you want to see its traceback.

Answer with a line, not a crash

check raises Rejected for a program with a bad line. judge should return the outcome line, but right now a bad program crashes it. Catch Rejected inside judge and return "REJECTED " plus the path. Leave check as it is.

Integers never wrap

The course's language has a 32-bit whole number type named i32. An i32 holds values from -2147483648 to 2147483647. One step past the top wraps around to the bottom, so 2147483647 + 1 is -2147483648.

What does Python print for print(2147483647 + 1)?

Python is not using 32 bits here. Just add 1.

2147483648. A Python int grows as large as it needs to, so it never wraps. That is the wrong answer for an i32, and Python gives no warning.

So your compiler wraps by hand, after every operation that makes an i32:

  1. Do the math. x = 2147483647 + 1 gives 2147483648.
  2. Keep the low 32 bits. low = x & 0xFFFFFFFF gives a number from 0 to 232 - 1. Here it is still 2147483648.
  3. Fix the sign. If low is 231 or more, it stands for a negative number, so subtract 232. Here that gives -2147483648.

Put those steps in one helper and call it everywhere: add, subtract, multiply, negate, shift left and even division. H.4 explains slowly why the bits work this way.

Wrap a Python int to 32 bits

Write wrap32(x): the signed 32-bit value with the same low 32 bits as x. It has to work for any size of int, positive or negative.

A mask and a sign fix, or the one-line version that shifts the range first.

Negative numbers and shifts, for when you write shl and shr

& on a negative int acts as if it had infinitely many sign bits, so -1 & 0xFFFFFFFF is 4294967295. Masking then fixing the sign works for every int.

>> on a negative int is an arithmetic shift (GCC and Clang do the same on signed values, though the C standard leaves that implementation-defined). << never drops bits, so 1 << 40 is a 41-bit number until you wrap it.

Division rounds down

Dividing two whole numbers often leaves a fraction, and something has to round it away. Languages disagree on which way.

What is -7 % 2 in Python? (% is the remainder.)

Python's -7 // 2 is -4. The remainder is what you add to -4 * 2 to get back to -7.

1, since -4 * 2 + 1 is -7. C answers -1 to the same question, because C's division gives -3.

Python's // floors: it rounds down, toward negative infinity. C's / on ints truncates: it rounds toward zero. They differ only when the signs differ and there is a remainder.

expressionPython (and your compiler's div, mod)C
7 / 2, 7 % 23, 13, 1
-7 / 2, -7 % 2-4, 1-3, -1
7 / -2, 7 % -2-4, -1-3, 1
-7 / -2, -7 % -23, -13, -1

The Python column uses // where the table says /. Here Python is on your side: the course's div and mod floor too. Two edges still need care. Python raises ZeroDivisionError for a zero divisor, where the course defines div x 0 as -1 and mod x 0 as x. And -2147483648 // -1 is 231, which has to wrap back to -2147483648.

The course's 32-bit division

Write div32(a, b) for i32 values, the way .uir's div works: the floor quotient, wrapped to 32 bits, and -1 when b is 0. div32(-7, 2) is -4. (Lesson 1.2 has a variant that returns mod too.)

C's rounding in Python, for week 2 when your compiler prints C

% follows //, so it takes the sign of the divisor in Python and the sign of the dividend in C.

You'll want C's rule too, from week 2. Plain / in Python always gives a float: 7 / 2 is 3.5. int(3.5) truncates toward zero, but going through a float is a habit to avoid, since floats can't hold every 64-bit int. Divide the absolute values with // and put the sign back yourself. math.fmod is C's fmod for floats, which truncates like C. And round(2.5) is 2, because Python rounds halves to even.

Floats need rounding to f32

Python's float is a 64-bit number, called a double. The course's f32, which arrives in week 2, has only 32 bits, so it holds fewer digits. This helper rounds a double to the nearest f32. It packs the number into 4 bytes with the struct module and unpacks it again:

import struct

def to_f32(x: float) -> float:
    return struct.unpack("<f", struct.pack("<f", x))[0]

What is to_f32(0.1) == 0.1?

0.1 has no exact binary form, so the 64-bit and the 32-bit versions each hold the closest value they can.

False. to_f32(0.1) is 0.10000000149011612, the closest f32 to 0.1. A value such as 0.5 fits exactly and comes back unchanged.

Round after every f32 operation, not only at the end. a + b on two f32 values is computed as a double, and the sum has to be rounded before anything else uses it. One kind of input makes to_f32 crash. Repair that in the first exercise, then use the helper in the second.

Round to f32 without crashing

C turns a number too big for an f32 into infinity. struct.pack raises OverflowError. Repair to_f32 so it returns infinity with the sign of x: math.copysign(math.inf, x).

Is it already an f32?

Write is_f32(x): True when the float x is exactly representable in single precision. NaN and the infinities count as representable.

Round it with the trick above and compare. Then check what your answer says about float('nan') and 1e39.

The format codes, and how to read an f32's bits

"<f" means one little-endian 32-bit float. struct.pack rounds to the nearest single, ties to even, exactly like C's (float) cast. "<I" reads the same 4 bytes as an unsigned int, which is how you get at an f32's bits: struct.unpack("<I", struct.pack("<f", x))[0]. NaN and the infinities themselves pack fine.

Equal values share a dict key

In week 1 your compiler keeps a dict from "what a node is" to the node, so that building the same node twice gives back the one you already have. A dict finds a key by ==, and Python calls some different values equal.

How many keys does the dict {1: "a", True: "b"} have?

Python says True == 1 is True.

One. True == 1, so the second entry lands on the first key and the dict is {1: 'b'}.

For a compiler that is three bugs waiting:

  1. A number and a bool collide. An i32 constant 1 and a bool true become one node.
  2. Two zeros collide. 0.0 == -0.0, but they are different f32 values.
  3. NaN gets lost. nan == nan is False, so a new NaN never finds the old one.

One fix covers all three: make the key the dtype plus the value's bits, not the value. struct gives you the bits.

Python also has a second kind of equality. a == b asks whether two values are equal. a is b asks whether they are the very same object. Week 1 turns on that difference, and P.4 has the details. The drill below checks that counting and sorting with a dict feel easy.

The k most common words

Write top_words(k, words). Count every word, then return the k most frequent as (word, count) tuples: higher counts first, and ties broken alphabetically (plain string order, so "A" sorts before "a"). If there are fewer than k distinct words, return them all.

Tools: a dict to count, sorted with a tuple key, and a slice to take a prefix.

The three key traps in code, and how to test for NaN and -0.0 
print({0.0: "a", -0.0: "b"})       # {0.0: 'b'}: one key, since -0.0 == 0.0
print({1: "a", True: "b"})          # {1: 'b'}: True == 1, and 1 == 1.0 too
nan = float("nan")
d = {nan: "a"}
print(d.get(nan), d.get(float("nan")))   # a None: the same NaN object is found, a new one isn't

In C, 1.0f / -0.0f is -inf, which is why the two zeros must stay apart. Test for NaN with math.isnan. Test for -0.0 with math.copysign(1.0, x) < 0, since -0.0 == 0.0.

Frozen dataclasses, == and is, for when you design your node class

A dataclass writes the boring parts of a class for you: the constructor, a readable repr and ==. frozen=True makes instances immutable, which is what a node in a graph should be: once built, it never changes.

from dataclasses import dataclass
from enum import Enum

class Suit(Enum):
    HEARTS = 1
    DIAMONDS = 2
    CLUBS = 3
    SPADES = 4

@dataclass(frozen=True)
class Card:
    rank: int        # 2 through 14, where 11 is a Jack and 14 an Ace
    suit: Suit

a = Card(14, Suit.SPADES)
b = Card(14, Suit.SPADES)
print(a == b, a is b)        # True False
print(len({a, b}))           # 1: frozen dataclasses hash by their fields
# a.rank = 2                 # dataclasses.FrozenInstanceError

An enum is a fixed set of named values. Suit.HEARTS is never equal to 1 or to a string, so a typo becomes an error instead of a silent mismatch. Use one for anything with a fixed list of choices, like a set of ops or dtypes.

For a dataclass, == compares every field, and if a field holds another node, it compares that one too, all the way down. On a big graph that can take as long as the graph is big. a is b is one pointer comparison.

Writing @dataclass(frozen=True, eq=False) keeps the fields immutable but leaves == and hash as identity, the same as is. That's the right choice for a class whose instances you guarantee are unique. For such a class, slow structural equality is the wrong choice. If you ever key a dict on id(x), keep x alive, because Python reuses the id of an object that has been freed.

Dict order, sorting and functools.cache, for when you memoize

A dict keeps keys in insertion order, which makes output reproducible. sorted takes a key function, and a tuple key sorts by its first element, then its second.

counts: dict[str, int] = {}
for word in ["kiwi", "pear", "kiwi"]:
    counts[word] = counts.get(word, 0) + 1
print(counts)                                             # {'kiwi': 2, 'pear': 1}
print(sorted(counts.items(), key=lambda wn: -wn[1]))      # most common first

functools.cache remembers a function's results by its arguments, so a second call with the same arguments returns at once. It's the quickest memo there is. It has two catches. The cache lives as long as the program, so it never forgets. And it keys only on the arguments: if the answer also depends on something else, such as which call's arguments are in effect (week 1, lesson 5), a global cache will hand back a stale answer. A plain dict that you create, pass around and drop when you're done is often the better memo.

from functools import cache

@cache
def ways(n: int) -> int:          # ways to climb n stairs, 1 or 2 at a time
    return 1 if n <= 1 else ways(n - 1) + ways(n - 2)

print(ways(90))                     # instant: each n is computed once

match has no safety net

match takes a value apart by its shape, one case per shape. Your compiler will have one case per kind of node. Here is a small one:

def points(card: str) -> int:
    match card:
        case "king":
            return 10
        case "ace":
            return 11

What does points("queen") return?

When no case matches, match does nothing and the function runs off its end.

None. No case matched, nothing was returned, and Python stayed silent. The wrong value shows up much later, far from the match that caused it.

Nothing checks that you covered every case. Add a new kind of node next month, and every match that forgot it falls through and returns None. So end each match with a catch-all that raises:

        case _:
            raise TypeError(f"not a card: {card!r}")

Now a missing case is a loud error at the right line. One more trap: a number in a pattern compares with ==, so case 0: also matches 0.0, -0.0 and False. A rule such as "x + 0 is x" has to check the dtype as well.

Class patterns, guards and sequence patterns in one example

With one small class per kind of card, each case names a class and pulls out its fields. Dataclasses support positional patterns like Number(n, _) automatically. Suit is the enum from the dataclass toggle above.

@dataclass(frozen=True)
class Number:          # 2 through 10
    n: int
    suit: Suit

@dataclass(frozen=True)
class King:
    suit: Suit

@dataclass(frozen=True)
class Ace:
    suit: Suit

def describe(card) -> str:
    match card:
        case Number(n, Suit.HEARTS) if n >= 9:    # nested pattern plus a guard
            return "a high heart"
        case Ace(Suit.SPADES):
            return "the ace of spades"
        case Number(n, _):
            return f"the number {n}"
        case King() | Ace():                       # either class, any fields
            return "a high card"
        case _:
            raise TypeError(f"not a card: {card!r}")

Cases are tried top to bottom, and the first that matches wins. Number(n, _) binds the first field to n and ignores the second. if n >= 9 is a guard: the case only matches if it's true. Sequence patterns work too: case [first, *rest]: matches a list or tuple with at least one element.

OCaml's compiler warns when a match misses a case. Python doesn't. The "x + 0 is x" rule is wrong for f32 because -0.0 + 0.0 is 0.0.

Deep graphs hit the recursion limit

A compiler walks its graph of nodes with a function that calls itself once per level. Here is the smallest function of that kind:

def depth(n: int) -> int:
    if n == 0:
        return 0
    return 1 + depth(n - 1)

What does depth(5000) do?

Python limits how many calls can be waiting on each other at once.

Python stops any recursion deeper than about 1000 calls with RecursionError. depth(5000) needs 5000.

Week 1 caps a program at 100 nodes, but from week 2 the caps are lifted, and a program can be a chain thousands of nodes long. There are two fixes. sys.setrecursionlimit(100_000) raises the limit, and it's fine for a few thousand levels. The sturdier fix is to keep your own stack in a list:

def total(tree) -> int:            # tree: None, or a tuple (left, value, right)
    stack, out = [tree], 0
    while stack:
        t = stack.pop()
        if t is not None:
            left, value, right = t
            out += value
            stack.append(left)
            stack.append(right)
    return out

The loop does what the recursion would have done, but its "call stack" is an ordinary list, limited only by memory. For a walk that must visit a node's children before the node, push the node back with a "finished" flag before its children, and emit it when it comes off the stack the second time.

Capstone: the toposort from lesson 0.3

Toposort a tiny DAG, in Python

A toposort lists the nodes of a graph so that every node comes after the nodes it uses. Lesson 0.3 steps through one. Here you write it, with the traps in view. A graph is a list of Node(name, srcs), each name appearing once, with srcs a tuple of names. Write topo(graph, root): every name reachable from root, each exactly once, in depth-first post-order. Visit a node's srcs left to right, then emit the node itself.

For (a + b) * (a + b) that's ["a", "b", "add", "mul"]. Nodes not reachable from root are left out. One hidden test is a doubling DAG (x0 to x30), so remember what you've visited. Another is a chain 5000 nodes deep.

Python hints

Build {n.name: n for n in graph} once, so looking a node up is one dict access. A set remembers what you've seen. Then either raise the recursion limit or use an explicit stack, as shown just above.
