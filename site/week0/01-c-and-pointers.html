C and pointers

From week 2 on, your compiler prints C, and a C compiler turns that C into a program that runs. You'll read that C to check your compiler did the right thing. This lesson teaches the C you need for that and no more.

Goal

Read a short C function that uses pointers, arrays, int32_t math and a struct, and say what it does.

You'll use

Numbers that wrap at 32 bits and division that rounds down, both from lesson 1.2. The slow version is H.4 Numbers that behave like C.

Your week 1 compiler works on whole numbers alone. In week 2 it gets memory, and it ends the week by printing a C function like this one:

void kernel(int32_t *restrict b0) {

  int32_t v4 = (int32_t)((uint32_t)v3 + (uint32_t)v3);
  b0[0] = v4;

By the end of this page you can read it. You won't write much C in this course: your compiler writes it, and you check it.

Read a C program

Here is a whole C program.

#include <stdio.h>
#include <stdint.h>

int32_t total(int32_t n) {
  int32_t t = 0;
  for (int32_t i = 0; i < n; i++) {
    t = t + i;
  }
  return t;
}

int main(void) {
  printf("%d\n", total(4));
  return 0;
}

Guess first. What does the program print?

The loop runs with i as 0, 1, 2 and 3. Each pass adds i to t.

6, which is 0 + 1 + 2 + 3. At i = 4 the test i < n is false and the loop stops.

  1. Every value has a type. int32_t t = 0; makes a variable t that holds a 32-bit whole number, like .uir's i32. Plain int is 32 bits too on the machines in this course.
  2. A function. int32_t total(int32_t n) { ... } takes one int32_t and gives one back with return. A function that gives nothing back starts with void.
  3. A loop. for (start; test; step) runs start once, then repeats the body while test is true, with step after each pass. i++ adds 1 to i.
  4. The start and the output. A program starts at main. printf("%d\n", v) prints the whole number v and ends the line.
  5. The includes. The #include lines bring in printf and int32_t from C's library.

A variable lives at an address

Your program's memory is one long row of small boxes called bytes. Each byte has a number, its address: its position in the row. A variable is a name for a few bytes side by side. An int32_t takes 4.

int32_t x = 5;
int32_t *p = &x;
*p = 9;
printf("%d\n", x);

No line says x = 9. What do you think this prints?

p holds the place where x lives. The third line puts 9 into that place.

9. *p = 9 wrote into the bytes at the address in p, and those bytes are x.

  1. Take the address. &x means "the address of x".
  2. Keep it in a pointer. A pointer is a variable that holds an address. int32_t *p says p holds the address of an int32_t. A pointer is 8 bytes on a 64-bit machine.
  3. Follow it. *p means "the box at the address in p". You can read it or assign to it.

Print p itself and you get a large number such as 000000B7495FF924 that changes from run to run. You only need what it leads to.

This is how the C your compiler prints hands back results: it gets a pointer to the caller's memory and writes through it.

Change the box, not the address

add_one(&x) should make x one larger. The starter changes p, the function's own copy of the address, so x stays the same. Repair the one line.

An array is a row of boxes

An array is several values of one type laid side by side. int32_t a[4] is four int32_t boxes, 16 bytes in all. Used by itself, the name a gives the address of the first box.

int32_t a[4] = {10, 20, 30, 40};
int32_t *p = a;
printf("%d\n", *(p + 2));

What does it print?

p + 2 does not mean "2 bytes on". It means "2 boxes on".

30. p is the address of a[0], and two boxes on is a[2].

C counts in boxes, not bytes: p + 2 moves 8 bytes, because each box is 4. And a[i] means *(a + i): start at a, step i boxes on, read. sizeof(int32_t) is C for the size of one box, 4.

address of a[i]  =  start  +  i * sizeof(element)

This formula is the most important line in the course. By week 5 your compiler turns a 4D tensor index into exactly this: one start address plus one offset.

Addresses are written in hexadecimal: base 16, digits 0 to 9 then a to f, marked by 0x. So 0x1004 is 4 more than 0x1000, and 0x100c is 12 more. Step through the snippet and watch the address in p.

C does not check the index

Guess first. int32_t a[4] has the boxes a[0] to a[3]. What does C do with a[4]?

a[4] is *(a + 4). Nothing in that formula mentions the length.

C does the address math and reads. You may get another variable's bytes, or a crash. The rules of C promise nothing.

So in week 2 your compiler proves that every read and write is inside its array before it prints any C.

A function can't check either. An array handed to a function arrives as a plain pointer to its first box, without its length. Inside the function, sizeof of it gives 8, the size of a pointer. The functions your compiler prints are called kernels. Now you can read the first line of the one at the top of the page:

void kernel(int32_t *restrict b0)

It returns nothing and takes b0, the address of the first box in a row of int32_t. restrict promises that no other pointer in the function reaches the same boxes. const, as in const int *p, promises not to write through p.

Sum an array with a pointer

Write int sum(const int *p, int n): add up the n ints starting at address p and return the total. Use p[i], or move p itself with p++. Both are the same address math.

When n is 0, p may be NULL, the pointer that points at nothing. Don't read through it.

More on sizeof, const and arrays that turn into pointers

sizeof gives a size in bytes, computed at compile time. sizeof(int) is 4 on every machine you'll use. For int a[4], sizeof(a) is 16. But pass a to a function and it "decays" into a plain int *, and inside that function sizeof gives 8, the size of a pointer. The array's length is gone. That's why your week 2 kernels never ask for a length: your compiler knows every size and writes it into the C as a constant.

const int *p is a pointer to ints you promise not to write through. The pointer itself can still move, so p++ is fine. The week 2 kernels don't use it, because any buffer may be written.

Indexing has no bounds check because p[2] is exactly *(p + 2): add 2 elements to the address, then read.

What happens at 2,147,483,647 + 1

The largest int32_t is 2,147,483,647. In .uir, adding 1 to it wraps to the smallest value, so "is x + 1 greater than x?" is false there. This C program asks the same question. A C comparison gives 1 for true and 0 for false.

#include <stdio.h>
#include <stdint.h>

int bigger(int32_t x) {
  int32_t y = x + 1;
  return y > x;
}

int main(void) {
  printf("%d\n", bigger(2147483647));
  return 0;
}

What does it print?

C makes no promise about a signed add that does not fit. What could a C compiler that wants fast code do with that freedom?

Built with gcc -O0 (no optimizing) it prints 0. Built with gcc -O2 (optimizing) the same file prints 1. clang does the same.

C calls a signed add that does not fit undefined behavior: the rules of C say nothing about the result, so a C compiler may assume it never happens. Without optimizing, the machine's add wraps and you get 0. The optimizer reasons that x + 1 is always greater than x and answers 1 without comparing.

uint32_t is safe. It is an unsigned 32-bit number, 0 to 4,294,967,295, and C defines its math to wrap. A cast, written (uint32_t)x, converts a value to another type. So your compiler will print a wrapping add like this:

int32_t y = (int32_t)((uint32_t)x + (uint32_t)1);
  1. Convert to unsigned. 2147483647 and 1 keep their bits.
  2. Add. The sum, 2147483648, fits in a uint32_t.
  3. Convert back. The same 32 bits read as an int32_t are -2147483648, which is .uir's answer.

With that line the program prints 0 however you build it.

Code quiz: add with wraparound, no UB

Write int32_t wrap_add(int32_t a, int32_t b) returning a + b wrapped to 32 bits, so wrap_add(2147483647, 1) is -2147483648. Don't add two signed ints directly: do the add in uint32_t, where wrapping is defined, then convert back.

The 32 bits themselves: two's complement, with a bit viewer

An int32 has 32 bits. Read as an unsigned number, it ranges from 0 to 232−1. Two's complement reads the top bit as worth −231 instead of +231. So the range is −2,147,483,648 (INT_MIN) to 2,147,483,647 (INT_MAX), and -1 is all ones, 0xffffffff.

Check that last one: with all 32 bits set, the top bit is worth −2,147,483,648 and the other 31 ones add up to +2,147,483,647. Together that's −1.

Type a number to see its bits. The top bit (the sign bit) is underlined.

If you add 1 to INT_MAX and keep only the low 32 bits, you get INT_MIN. That's called wrapping. The hardware does it, and the language you'll compile in this course defines add and mul to wrap exactly like that.

C does not promise wrapping

In C, signed overflow (INT_MAX + 1 on an int) is undefined behavior. The compiler is allowed to assume it never happens, and optimizers really do use that. Unsigned arithmetic (uint32_t) is defined to wrap. When your compiler prints C for a wrapping i32 add (i32 is the course's 32-bit integer type), it'll need to cast to unsigned, add, and cast back, or pass a flag like -fwrapv. That last cast back is "implementation-defined": the C standard lets each compiler choose what happens, and every compiler you'll use wraps. Keep this in your back pocket for week 2.

C division rounds toward zero

In the warm up, .uir's div -7 2 was -4. Your compiler has to get that answer out of C's /.

Predict the output of printf("%d", -7 / 2); in C.

The exact answer is -3.5. Which way does C round: down, or toward zero?

C truncates toward zero. −3.5 becomes −3.

C's / on whole numbers drops the part after the decimal point. That is called truncating. The remainder % is whatever makes (a / b) * b + a % b == a true.

expressionC result.uir div or mod
7 / 233
-7 / 2-3-4
-7 % 2-11
7 % -21-1

The two disagree only when the exact answer is not whole and the signs of a and b differ. Then the floor is one less than C's answer.

Code quiz: Python's // from C's /

Write int floor_div(int a, int b) that rounds down like Python: floor_div(-7, 2) == -4. Start from C's truncating a / b and fix it up. b is never 0. In week 2 your compiler's C computes the course's div this way.

The two divisions C leaves undefined, and how Python compares
expressionC resultwhy
INT_MIN / -1undefinedthe true quotient, 2147483648, doesn't fit in an int

In the main table, -7 / 2 is −3 because −3.5 rounds toward zero, not down to −4. The remainders follow from that: −3 × 2 + (−1) = −7 and −3 × −2 + 1 = 7. So C's remainder takes the sign of the left operand.

The C standard gives INT_MAX + 1 no value at all for a plain int. It does not wrap to INT_MIN and it does not stick at INT_MAX.

Python and the course disagree with C

Python's // rounds down (-7 // 2 == -4) and its % follows the right operand's sign (-7 % 2 == 1). The course's div and mod round down too, like Python, and they define a zero divisor instead of leaving it undefined: div x 0 is −1 and mod x 0 is x. From week 2 your compiler prints C, so it has to get that answer out of C's truncating /.

A struct, and a function handed to a function

In week 7 your compiler prints C that runs one loop body on many threads. That C needs three more pieces. The first is a struct: a type that groups several named values, called fields, into one block of memory.

#include <stdio.h>
#include <stdint.h>

typedef struct { int32_t *b0; int32_t r3; } ctx_t;

void body(int32_t r, void *ctx) {
  ctx_t *k = ctx;
  k->b0[r] = k->r3 + r;
}

void run(int32_t n, void (*f)(int32_t, void *), void *ctx) {
  for (int32_t r = 0; r < n; r++) {
    f(r, ctx);
  }
}

int main(void) {
  int32_t a[3] = {0, 0, 0};
  ctx_t k = { a, 10 };
  run(3, body, &k);
  printf("%d %d %d\n", a[0], a[1], a[2]);
  return 0;
}

Guess first. What three numbers does it print?

run calls body with r as 0, 1 and 2.

10 11 12. The field r3 is 10, and each call stores 10 plus its own r into box r.

  1. Make the struct. The typedef line names a struct type ctx_t with two fields. ctx_t k = { a, 10 }; fills them in order: b0 is a and r3 is 10.
  2. Hand over a function. In run(3, body, &k), body without parentheses is the function itself, not a call. The parameter void (*f)(int32_t, void *) reads "f is a function that takes an int32_t and a void * and returns nothing".
  3. Carry anything. void * is a pointer to "something". run passes &k along without knowing what is in it, and the first line of body turns it back into a ctx_t *.
  4. Read a field through a pointer. k->r3 means "the field r3 of the struct k points to". On a struct that is not behind a pointer you write a dot: k.r3.

Going from 32-bit to 64-bit machines doubled the size of pointers. Did it change int?

4 bytes, 32 bits. Pointers are 8 bytes on a 64-bit machine, but int stayed at 4.
