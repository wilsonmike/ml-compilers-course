Compilers and IRs

This page is the map of the course. You follow one small expression through every stage of a compiler: text, tree, graph, a simpler graph and C. Then you see which week builds each stage, so you always know where you are.

Warm up

Two quick questions. Pulling an idea back out of your head is what makes it stay.

What is 2 + 3 * 4?

Multiplication happens before addition.

14. You did 3 * 4 first, even though 2 + 3 is written first. The order of the work is not the order of the text. A compiler has to find that structure too.

What is %out?

%a   = add 2 3
%out = mul %a %a

add adds and mul multiplies. Work out %a first.

%a is 5, and 5 × 5 is 25. The second line uses %a twice, but the adding was done once. Keep that in mind: it comes back as "sharing".

Start with one line of text

A compiler is a program that reads a program in one language and writes a program in another language that does the same thing. To see how, follow this one expression all the way through:

(a + b) * (a + b) * 1

To the compiler this is only a string of characters. The first job is to split it into words, called tokens. The part that does this is the lexer. Spaces disappear and every token gets a label:

(lparenaname+opbname)rparen*op(lparenaname+opbname)rparen*op1number

A flat row of tokens still does not say what to do first. The next stage works that out.

Predict: when this expression is worked out, which operation is done last?

Parentheses go first. After that, a row of * is worked left to right.

Both sums come first, then the two sums are multiplied, then the result is multiplied by 1. The last operation is the one the whole answer comes out of.

The text becomes a tree

The parser is the part that works out the structure. It turns the tokens into a tree: every operation is a box, and arrows run into it from the things it uses. Inputs sit on top and the answer comes out of the bottom box, the * 1 you just picked.

The parentheses are gone, because the shape of the tree says what happens first. But look at the top two rows. a + b was written twice, so the tree holds it twice. A compiler that walks this tree would add a and b twice.

Predict: the tree has 9 boxes. If every box that is identical to another one is stored only once, how many boxes are left?

Two boxes are identical when they have the same label and the same inputs. The two * boxes have different inputs.

Six: a, b, one +, 1 and two *. The two * boxes stay separate because one multiplies the sum by itself and the other multiplies by 1.

The tree becomes a graph that shares

Store each identical box once and let both users point at it. The tree is now a graph. Its full name is a DAG, a directed acyclic graph: arrows have a direction and never loop back.

The * box takes the same + box twice, so the sum is worked out once. The trick that builds a graph this way is called hash consing: before making a box, look in a table to see if the same box already exists. You write it in lesson 1.1.

This graph is the compiler's intermediate representation, or IR: the form a compiler keeps the program in while it works on it, between reading the input and writing the output. Everything else in this course reads this graph or changes it.

Predict: one box in the graph does work that changes nothing. Which one could the compiler remove?

Which operation gives back exactly what went in?

Anything times 1 is itself, so that box can go and nothing about the answer changes.

A rewrite makes the graph simpler

A rewrite finds a pattern in the graph and replaces it with something simpler that gives the same answer. The rule here is x * 1 → x, where x stands for any box. Step through it.

Rewriting is most of what a compiler does between reading and writing. The hard part is the words "same answer". x * 0 → 0 is right for whole numbers. It is wrong for decimal numbers, which have special values such as infinity, and infinity times 0 is not 0. Lessons 1.3 and 1.4 are about which rules are safe and how to prove it.

Predict: the last stage prints C, one line for each operation box left in the graph. Inputs like a and b get no line. How many lines?

After the rewrite the graph has four boxes. Two of them are inputs.

Two: one for the + and one for the *.

The graph becomes C

There are two things to do with a finished graph. An interpreter is a program that runs another program directly, without writing a new one. That is what your week 1 compiler does with the graph. From week 2 on it also does the compiler's real job and writes a new program, in C:

int f(int a, int b) {
  int t0 = a + b;
  int t1 = t0 * t0;
  return t1;
}

Read it in two moves:

  1. One line per box. Each operation becomes a line that saves its answer in a fresh name, t0 then t1.
  2. Inputs first. C runs top to bottom, so every box is printed after the boxes it uses. An order like that is called a topological sort, or toposort.

The sum is computed once and the * 1 is gone. The C is better than the text you started with, and all of the improving happened on the graph. The part that prints the output is called a backend.

Predict: in week 8 the same compiler prints code for a GPU, a chip that runs thousands of small jobs at once. Which stage has to change the most?

Which stage is the only one that knows what the output language looks like?

The graph stays. The course adds a few new kinds of box that say which work runs side by side, and a second backend prints CUDA, the language NVIDIA GPUs run, from the same graph. That is why the IR matters so much: design it well once and every later stage reuses it.

Code quiz: how big is the tree?

e0 = a + b is a tree of 3 nodes. e(k+1) = e(k) * e(k), stored as a tree with no sharing, so both operands are full copies. Write long long tree_nodes(int k) returning the node count of e(k), for 0 <= k <= 60. The same thing as a DAG has just k + 3 nodes.

Evaluate postfix with a stack

Postfix (also called RPN, reverse Polish notation) writes each operator after its operands, so "23+4*" means (2 + 3) * 4. That's a toposort of the expression tree: every operator comes after the operands it uses. No parentheses or precedence rules are needed, because a stack does all the work. (A stack is a list you only add to, "push", and take from, "pop", at the top.)

Write int rpn(const char *s) for single digits 0 to 9 and the ops + - *. A digit pushes its value. An op pops b, then a, and pushes a op b. Return the one value left at the end. Inputs are always valid and at most 64 characters.

A C string is an array of characters that ends with a zero byte, so for (int i = 0; s[i] != '\0'; i++) visits every character.

How the printer picks an order, step by step (toposort)

C runs top to bottom, so to print C from a DAG you need an order where every node comes after the nodes it uses. That order is a topological sort. A depth-first walk gives you one: visit a node's inputs first, then emit the node, and skip anything you've already emitted.

Each emitted node becomes one line of C that assigns a fresh temporary. Leaves (inputs and constants) don't need a line of their own.

You'll write this toposort yourself at the end of lesson 0.7, in Pythonlesson 0.6, in OCaml, once you've seen the traps of your language.

Why sharing is a big deal, and how a table builds it

You build a DAG by keeping a table of every node you've made, keyed by "what op, which operands" (a hash table, which is a dictionary: give it a key and it quickly gives back the stored value). Before you build a node, you look it up. If it's already there, you reuse it. Two nodes with the same op and the same inputs are not just equal, they're the same object.

Sharing compounds

Sharing isn't a small saving. Take x1 = x0 + x0, x2 = x1 + x1, and so on up to x30. As a DAG that's 31 nodes. As a tree it's over a billion. Any code that walks your IR without remembering what it already visited will treat the DAG like a tree, and it'll never finish. The week 1 tests include a deeper version of this case (94 levels).

Hard ideas, slowly takes sharing, walking a graph in order and rewriting one at a time, with code in your language.

More on rewrites: a second example, fixpoints and the float traps

"Means the same thing" hides real questions. Is x * 0 → 0 safe? For integers, yes. For floats, no, because inf * 0 and nan * 0 are both nan, and -3.0 * 0.0 is -0.0, not 0.0. Those are special float values that integers don't have: inf is infinity, nan ("not a number") is the result of something undefined, and -0.0 is a negative zero that compares equal to 0.0 but is a different value. Floats arrive in week 2, and lesson 2.1 covers them. Week 1 is all about rules like this, on integers: which ones are safe, how to apply them until nothing changes, and how to prove the rules you wrote didn't break anything.

Integers have a trap of their own. In .uir a 32-bit add or mul that overflows wraps around, while in C a signed overflow is undefined. So the C backend cannot print a plain a + b for every add, and the short C on this page is a sketch. Lesson 2.4 shows what to print.

What makes a good IR, for readers who have built a compiler before
  • Small. Every op you add is one more case for every rewrite and every backend (the part of the compiler that prints C or GPU code). The course's IR has a few dozen ops by the end, and that's enough to train an LLM.
  • Uniform. Every node is the same shape: an op, a tuple of source nodes, and an argument (extra data that isn't a node, like the number inside a constant). One rewrite engine handles all of it.
  • Shared. Hash consing means equal things are the same object, so "are these equal?" is a pointer comparison.
