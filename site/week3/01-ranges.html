Ranges and ends

Every program so far did a fixed number of steps: one line of .uir, one piece of work. Week 3 adds loops, so a short program can work through a thousand numbers. This lesson gives you the two ops that make a loop: range, a counter, and end, which says what gets repeated.

Warm up

Two questions from week 2, from memory. Pulling an idea back out of your head is what makes it stay.

What does %b1 hold?

%b  = buffer 3 [5 6 7] dtype=i32 slot=0
%e  = shrink %b 2 []
%s  = store %e 1
%b1 = after %b %s

The store writes into box 2. after names the buffer once that write has happened.

Box 2 gets the 1 and the other boxes keep their values: 5, 6, 1.

A buffer has 4 elements. shrink %b %k [] passes the bounds check only if the interval of %k fits inside which range?

Boxes are numbered from 0.

Four boxes are numbered 0, 1, 2 and 3. Any value of %k outside [0, 3] would miss the buffer, so the program is rejected.

A sum that does not scale

Here is a week 2 program that adds up the four numbers in %b. %s3 is the total, 9:

%b   = buffer 4 [3 1 4 1] dtype=i32 slot=0
%v0  = shrink %b 0 []
%x0  = load %v0
%v1  = shrink %b 1 []
%x1  = load %v1
%v2  = shrink %b 2 []
%x2  = load %v2
%v3  = shrink %b 3 []
%x3  = load %v3
%s1  = add %x0 %x1
%s2  = add %s1 %x2
%s3  = add %s2 %x3

Each element costs a view, a load and an add. What does this program look like for a buffer of 1,000 numbers?

Count the lines that mention element 2.

Three lines per element, so about 3,000 lines. A real model works on millions of numbers.

In PythonOCaml you would write a loop: one copy of the work and a counter that says which element it is on. Week 3 gives .uir the same thing.

A sum also needs a running total kept in memory. That is lesson 3.2. This lesson builds the loop on a smaller job: put i * i into box i.

A counter that is a value

The loop you already know:

b = [0, 0, 0, 0]
for i in range(4):
    b[i] = i * i
let b = Array.make 4 0 in
for i = 0 to 3 do
  b.(i) <- i * i
done

In .uir every line is a value, so the counter is a value too. %i = range 4 is an i32 that takes the values 0, 1, 2 and 3, one after the other. Anything computed from %i is computed once for each of those values.

With %i = range 4, what values does %t = add %i 10 take, in order?

%i starts at 0 and stops before 4.

%i is 0, 1, 2, 3, so %t is 10, 11, 12, 13. A range counts from 0 up to one less than its bound.

Now the body of the loop, built from the counter:

%b  = buffer 4 dtype=i32 slot=0
%i  = range 4
%sq = mul %i %i
%v  = shrink %b %i []
%s  = store %v %sq
  1. Make the counter. %i = range 4.
  2. Compute with it. %sq is i * i, once for each i.
  3. Aim with it. %v is a window onto box i. The window moves with the counter.
  4. Write. %s stores i * i into box i.

Close the loop with end

Those lines are not a loop yet. Python marks the body of a loop by indenting it.OCaml marks the body of a loop with do and done. A graph has no such marks, only nodes that point at their sources.

You add %b1 = after %b %s to the five lines. What is wrong?

after %b %s means "%b, once %s has happened". Which %s?

%s still depends on the counter, so it is not one write. The program is REJECTED. Something has to say "do this for every value of %i".

That something is end. %e = end %s %i means: run the store %s once for every value of %i, in increasing order. An end is an effect, a thing that happens to memory, the same as a store. So after can sequence it:

%e  = end %s %i             # repeat %s for i = 0, 1, 2, 3
%b1 = after %b %e           # the buffer after the whole loop

A range on its own loops nothing. The loop exists only where an end closes it. Step through the loop as it runs:

Square every element

Slot 0 holds six i32s. Write out[i] = in[i] * in[i] into slot 1 for every i from 0 to 5. The starter handles only i = 0. Turn it into a loop.

The grader sets both buffers' data for each test and checks slot 1's final contents.

The counter has bounds

Week 2 checks every view before the program runs. In a loop one view lands on many boxes, so the check has to cover all of them at once.

A buffer has 4 elements, and %v = shrink %b %i [] with %i = range 5. What outcome does ./compile print for the file?

What's the interval of %i?

%i is in [0, 4], so the view could start at element 4 of a four-element buffer. The bounds check fails, so the program is rejected before it runs: REJECTED.

A range n has the interval [0, n-1], and the week 2 bounds check uses it like any other interval. Arithmetic on the counter moves the interval with it: for %i = range 4, add %i 1 is in [1, 4], which also misses a four-element buffer.

Reverse into a second buffer

Copy slot 0 (five i32s) into slot 1 backwards: out[i] = in[4 - i]. There's no subtract op, and the view has to pass the bounds check.

What is inside the loop

When your compiler prints C for a loop, it has to decide which lines go between the braces.

In the squares program, which of these has to be computed again for every i?

Which one changes when %i changes?

%sq is built from %i, so it has a new value each time around. The buffer exists once, and %b1 comes after the loop.

Your compiler tracks this with one property. Every node has a set of open ranges: the ranges it depends on that no end has closed yet.

  1. A range opens itself. The set of %i is {i}.
  2. Other ops take the union. A node's set is everything open in any of its operands.
  3. An end removes its range. end %s %i has the set of %s, minus i.

A value with {i} open is computed inside the i loop. A value with nothing open is computed once, outside every loop. Loads get one more rule in lesson 3.2.

Fix the open ranges

A toy graph has four kinds of node: Range name, Lit n, Add (a, b) and End (effect, name), which closes the range called name. opens n should return the sorted names of the ranges still open at n. The Lit and Add cases are right. The Range and End cases are wrong. Fix those two.

Two loops, one inside the other

A grid needs two counters: one for the row and one for the column. Lesson 0.4 put row i, column j of a 3-column grid at i*3 + j. This store depends on %i and %j, so it needs two ends:

%b  = buffer 6 dtype=i32 slot=0
%i  = range 2
%j  = range 3
%i3 = mul %i 3
%o  = add %i3 %j            # row-major offset i*3 + j
%v  = shrink %b %o []
%s  = store %v %o
%ej = end %s %j             # inner loop: j
%ei = end %ej %i            # outer loop: i
%b1 = after %b %ei

How many times does the store run?

For each of the 2 values of %i, %j takes all 3 of its values.

2 × 3 = 6 times, once for each box of the grid.

The order of the ends decides which loop is inside. %ej closes %j around the store, so j is the inner loop. %ei then repeats that whole inner loop for every %i.

loop i (end %ei)
%i3 = mul %i 3
loop j (end %ej)
%o = add %i3 %j
%s = store ...
for (int32_t r3 = 0; r3 < 2; r3++) {
  int32_t v4 = r3 * 3;      /* i*3: outside the j loop */
  for (int32_t r5 = 0; r5 < 3; r5++) {
    int32_t v6 = v4 + r5;
    b0[v6] = v6;
  }
}

The C is the oracle's rendering, with the wraparound casts trimmed for reading.

The open set of %i3 is {i}, so it's computed in the i loop, not the j loop. Swap the two ends and you get the same answers with the loops the other way round. Lesson 3.3 shows why that choice matters.

Add a row to every row

Slot 0 holds a grid of 2 rows and 3 columns, stored row-major in six i32s. Slot 1 holds one row of three i32s. Write the grid with that row added to each of its rows into slot 2: out[i*3 + j] = grid[i*3 + j] + row[j]. The starter has only the three buffers.

Open ranges on a toy graph

Here's a five-constructor toy version of the graph. Write opens: the sorted, duplicate-free names of the ranges a node depends on that no End has closed. This is the property your compiler computes for every UOp.

Loops your compiler must refuse

You have met two loops the checker rejects: one that no end closes, and one whose counter runs past the buffer. Two more:

  • Closing a range the effect doesn't use. end %s %j when %s doesn't depend on %j is an error.
  • An assert with an open range. An assert gives one answer for the whole program, so it must sit outside every loop.

You want a triangle: for each i, the inner loop runs i times. So you write %j = range %i. What happens in week 3?

The bound has to be known before the loop starts. Is %i one fixed number?

The bound of a range must have no open ranges, and %i is open in itself. So every loop nest in week 3 is a rectangle: each loop runs the same number of times whatever the other counters are.

Every rule that makes a loop invalid, for when you write the checker

The oracle checks these statically. Each one is a mistake that would otherwise produce C that means something different from your graph:

  • Closing a range the effect doesn't use. end %s %j when %s doesn't depend on %j is an error, not a pointless loop.
  • A bound that depends on a range. %j = range %i is rejected in week 3.
  • An open range where none is allowed. assert, call and a range's bound must have nothing open. An assert inside a loop would have to pass once per iteration, which the format doesn't say how to report.
  • A loop nobody closes. Every range a store depends on must be closed by an end before an after uses it.
  • Closing a range twice. Each range has exactly one end, so each range is exactly one loop.
  • Out of bounds. A range's interval is [0, n-1], and week 2's bounds check uses it. shrink %b %i [] with %i = range 5 on a four-element buffer is invalid. When the bound isn't a constant, the interval is [0, hi(n) - 1], where hi(n) is the top of the bound's own interval, so range %c with %c in [0, 4] is [0, 3]. If hi(n) ≤ 0 the loop never runs, and the interval is [0, 0].

Two more from the spec. The last operand of an end must be a range, and every operand before it must be an effect: a store or another end. And an after that sequences a loop must name the version the loop stores into, as it must for a single store.

Range bounds that are computed, zero or negative, for when you run a loop in your interpreter

The bound can be any i32 expression that doesn't depend on another range. range 0 (or anything 0 or below) runs zero times. A computed or loaded bound is fine too, like range %c with %c = mod %k 5 for a loaded %k. Because the bound can't depend on another range, every loop nest in week 3 is a rectangle: no triangular loops yet.

One end with several effects, and loops that ignore an outer range, for when a test uses them

The full form is end x1 ... xk r: one or more effects, then the range. It runs all of the effects once for every value of r, and at least one of them must depend on r. This loop fills two buffers:

%a  = buffer 3 dtype=i32 slot=0
%b  = buffer 3 dtype=i32 slot=1
%i  = range 3
%va = shrink %a %i []
%vb = shrink %b %i []
%sq = mul %i %i
%sa = store %va %i
%sb = store %vb %sq
%e  = end %sa %sb %i
%a1 = after %a %e
%b1 = after %b %e

Ranges nest the way the ends do. If an effect is inside end ... r1, and that end is inside end ... r2, then r2 is the outer loop. A loop body may ignore an outer range. It then repeats, doing the same thing each time.

An after may also sit inside a loop. Only an after with no open ranges counts as a buffer's output version. Lesson 3.2 covers that case.

Check yourself

After the squares program on this page runs, what does %b1 hold?

The loop runs the store four times: b[0] = 0, b[1] = 1, b[2] = 4, b[3] = 9. The oracle agrees.

In the loop-nest example, which loop computes %i3 = mul %i 3?

Where a value lives depends on what it depends on, not on who uses it.

%i3 has open ranges {i}, so it's computed once per value of i, in the i loop, outside the j loop. Its user %o has {i, j} open and lives in the j loop.

%s stores into shrink %b %i [], with %i = range 4 and %j = range 2. What does %e = end %s %j do?

Does %s depend on %j?

%s doesn't use %j, and closing a range the effect doesn't use is an error: "end closes a range its effects don't use". Repeating a store that doesn't change is almost always a bug in the graph, so the format refuses it.

The bound of a range is add 0 0. What happens to a buffer that loop stores into?

The spec says what n ≤ 0 does.

A range with bound 0 or below runs zero times, so the store never happens and the buffer's final version holds its initial data. The program is valid, and an assert on that data gives MATCH.

Why must an assert have no open ranges?

How many answers would an assert that runs four times give?

An assert gives one answer for the program: MATCH or MISMATCH. Inside a loop it would give one per iteration. To check something about every iteration, store it into a buffer inside the loop and assert on the buffer after the loop.
