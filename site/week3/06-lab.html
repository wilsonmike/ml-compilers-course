Lab: loops

In this lab your compiler learns loops. It reads range and end, refuses loops that make no sense, runs an accumulator the right way and prints nested for loops in C. You build it in the order the week taught it, and every step ends with something you can run.

Goal

Pass all 94 week 3 tests with your own compiler, and write 10 tests of your own.

You'll use

Your compiler from the week 2 lab, and this week's lessons: ranges and ends (3.1), memory in loops (3.2), matrix multiply (3.3), convolution (3.4) and rendering loops (3.5).

Warm up

Two questions from this week. Pulling an idea back out of your head is what makes it stay.

A loop adds in[k] to a total that starts at 0, and in holds 5 6 7. A broken compiler loads the total once, before the loop. What does the total hold after the loop?

Lesson 3.2: every pass adds to the same starting value. What does the last pass store?

7. Every pass stores 0 + in[k], and the last store wins. A load that runs inside the loop gives 18.

A store depends on %i and %j. Which loop is the outer one?

%ei = end %s %i
%ej = end %ei %j

Lesson 3.5: %ei repeats the store for every i. What does %ej repeat?

j. %ej repeats the whole i loop once for each j, so the i loop is inside it.

What you are building

The same three commands as last week. What changes is which programs they take.

  • compile FILE judges programs with range and end. A loop that breaks a rule is REJECTED. A valid one is run, with memory carried from one pass to the next.
  • compile render FILE prints nested for loops for a program with a range, and refuses an invalid one as before.
  • compile simplify FILE does not change.

The suite has 57 run tests and 37 render tests. Render tests are graded as in week 2.

How a render test is graded, step by step, for when a kernel fails

Exactly as in week 2, with one change to the loop check. For each # render test the grader:

  1. Runs your.exe render FILE and fails the test on a nonzero exit.
  2. Parses the program with the oracle and checks whether it contains a range. It then strips comments and string literals from your C and fails the test if it finds while, do or goto, or, when the program has no range, for.
  3. Writes its own main: one array per buffer, filled with its starting data (f32 from exact bits), a call to kernel in slot order, then one line per element.
  4. Compiles both files with clang -std=c11 -O2 -ffp-contract=off -fsanitize=undefined -fsanitize-trap=undefined ... -lm.
  5. Runs it and compares every element with the oracle: i32 and bool exactly, f32 bit for bit, any NaN matching any NaN.

Two new ways to fail. A loop bound or offset that overflows int32_t in your C is undefined behavior, so keep loop counters int32_t and do index arithmetic through the same uint32_t wrap as every other add and mul. And an accumulator loaded once outside its loop gives the wrong sum, not a crash: it shows up as a wrong value in the buffer.

Read range and end

YOURS is the path to your compiler in quotes, as in the week 1 lab. From the root of the course repo, run the new suite with your compiler as it is:

python tools/test.py --compiler YOURS --week 3

The last line should read 23 / 94 passed. Four of those tests have no loop. The other 19 are rejected_ tests, and they pass by luck: your compiler rejects any file with an op it can't read.

  1. Parse them. range n takes one operand. end x1 ... xk r takes one or more effects, then a range.
  2. Type them. The bound is an i32 scalar, and so is the counter. An effect is a store or an end, with dtype void. Only end and after may take one, so after now accepts an end.
  3. Keep ranges apart. Every range line is its own loop. Hash consing must never merge two of them, even with the same bound.
  4. Bound the counter. In your interval analysis a range is [0, hi - 1], where hi is the top of its bound's interval. When hi is 0 or less, use [0, 0].
  5. Stop there. A valid program with a range can't run yet. Let it fail with a message of your own.

Refuse bad loops

Every rule in this step reads one fact about a node: its open ranges, the loops it depends on that are not closed yet.

%s is a store that depends on %i and %k. Which ranges are open in %e = end %s %k?

Lesson 3.1: what does an end do to the range it names?

Only i. An end has its effects' open ranges, minus the one it closes.

  1. Compute open ranges. One pass that remembers its answers. A range is open in itself. An end removes its range. Every other node takes the union of its sources.
  2. Check each end. Its effects must depend on the range it closes.
  3. Check what must sit outside loops. An assert, a call, a call body, a range bound and a buffer or alloc size have nothing open.
  4. Count the ends. No range is closed by two ends. Every range a store depends on is closed by one.
  5. Check each after. Week 2's rules still hold through a loop: every store is sequenced, and the loop in after m e stores into m, or into a version built on m inside the loop.

Give every node its loops

Before anything runs, each node needs a path: the list of loops it sits inside, outermost first.

In the convolution the k loop is inside the i loop. The load of w[k] depends only on %k. What is its path?

Lesson 3.5: a value goes inside every loop around its deepest range.

i, then k. The k loop lives inside the i loop, so anything in it is inside both, even when it never uses %i.

  1. Order the loops. Look at each end. The ranges still open after it closes its own are the loops around it.
  2. Set each path. Take the node's deepest open range. The path is the loops around that range, then the range. A node with nothing open has an empty path.

To check it, print every node with its path for tests/week3/render/r_loop_invariant_value.uir. Then ask the oracle where it puts each line:

Move the accumulator load

An accumulator's load depends on no range, so its path is empty, and there it would read the starting value once. That is the bug from the warm up.

  1. Find every use of the load. Count every use in the program, asserts too.
  2. Find the innermost loop that holds them all. A use is inside a loop only if its own path puts it there, or it is a load this rule moved there.
  3. Move the load into that loop if it is deeper than the load's path and it stores into the version the load reads. Otherwise leave the load where it is.
  4. Work on the graph as written. If your builder folds mul %i 0 to 0 first, two different views become one and loads change places.

Print the paths for tests/week3/render/r_loop_carried_load.uir, and run the oracle's render on it.

Run the loops

Now the evaluator. First write the smallest loop yourself.

Your first loop

Slot 0 is x (4 f32), slot 1 is y (4 f32). Make the final contents of slot 1 equal 2 * x[i] for every i in 0..3, using one range. The starter does only i = 0, with no loop.

  1. Build blocks. A block holds the nodes that share one path, and the loops directly inside it. Order each block as in week 2: sources first, and loads of a version before the store or loop that overwrites it.
  2. Use one array per buffer and alloc. A store changes it in place. Week 2's copy per version can't carry a total from one pass to the next.
  3. Walk the blocks. For a loop, set its counter to 0, then 1, up to n - 1, and run its block each time. A bound of 0 or less runs it zero times.

Render the loops

The renderer walks the same blocks and prints where the evaluator computed. It needs clang or gcc on your PATH, as in week 2. Start with r_loop_invariant_value, the kernel you read when you set the paths.

Write your 10 tests

Same deal as before: 10 tests in <your compiler repo>/tests/week3/, each aimed at a rule someone will get wrong. This one catches an accumulator load left outside its loop, which would give 12:

Good targets for your tests

Good targets: an accumulator whose load has to run inside the loop, a reset store indexed by the outer ranges, and a range bound of 0 (the loop runs zero times). Rejected cases make good targets too (give the file a rejected_ name), such as an end that closes a range its effect doesn't use, or a range closed by two ends. Also try one end with two effects writing two buffers, and a padded convolution whose raw index is rejected but whose masked index matches.

Your matmul render test fails with a wrong value: every output equals just the last product. What's the most likely cause?

Which value should change from one k iteration to the next?

If the load of the accumulator runs once before the loop, each iteration computes start + product and stores it, and the last store wins. The placement rule puts that load inside the loop. Overflow would trap, and the flags are the grader's, not yours.
