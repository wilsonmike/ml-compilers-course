Rendering loops

Your render command prints one flat list of C lines. A program with ranges needs for loops, and the graph never says which line goes inside which loop. In this lesson you work that out: every value gets a depth, and the depths become nested blocks of C.

Goal

Decide which loops each node's C line sits inside, then print the loop nest.

You'll use

Open ranges and end from lesson 3.1, the accumulator from lesson 3.2, the convolution from lesson 3.4 and the week 2 renderer from lesson 2.4.

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

Which ranges are open in %a?

%i = range 4
%j = range 3
%a = mul %i 5
%b = add %a %j

A value's open ranges are the ranges it is built from. Follow the sources of %a.

Only i. %a is built from %i and a constant. %b uses %j too, so it has both open.

Two loads read buffer version %b, and one store overwrites it. In the C from lesson 2.4, where does the store go?

C has one array. What is left of the old version once the store has run?

The store changes the array in place, so every load of the old version has to run first.

Which lines go inside the for?

This program multiplies every element of x by g[0] squared and writes the results to y.

%x  = buffer 4 dtype=i32 slot=0
%g  = buffer 1 dtype=i32 slot=1
%y  = buffer 4 dtype=i32 slot=2
%i  = range 4
%gv = shrink %g 0 []
%k  = load %gv
%k2 = mul %k %k
%xv = shrink %x %i []
%xe = load %xv
%p  = mul %xe %k2
%yv = shrink %y %i []
%s  = store %yv %p
%e  = end %s %i
%y1 = after %y %e

Here it is as a graph, with views drawn as their offsets. The end will become a for loop, and two loads, two multiplies and a store each become one line of C. Nothing in the graph says which of those five lines go inside the braces.

Where should the C line for %k2 = mul %k %k go?

Would its value be different on the second trip through the loop?

Before the loop. Nothing it is built from changes with i, so one computation is enough. Inside the loop it would give the same answer four times.

The reference compiler prints this:

void kernel(int32_t *restrict b0, int32_t *restrict b1, int32_t *restrict b2) {
  int32_t v6 = b1[0];
  int32_t v7 = (int32_t)((uint32_t)v6 * (uint32_t)v6);
  for (int32_t r8 = 0; r8 < 4; r8++) {
    int32_t v11 = b0[r8];
    int32_t v12 = (int32_t)((uint32_t)v11 * (uint32_t)v7);
    b2[r8] = v12;
  }
}

Two lines come before the for: the load of g[0] and its square. Three go inside, because they depend on %i. The renderer sorted them with one question: which ranges does this value depend on?

Every value has a depth

The depth of a value is the number of loops its C line sits inside. Depth 0 means before every loop. The rule that sets it:

A value is computed inside every loop whose range it depends on, and no deeper.

You already know what a value depends on: its open ranges from lesson 3.1. This program fills a 2 by 3 table with i*10 + j.

%y  = buffer 6 dtype=i32 slot=0
%i  = range 2
%j  = range 3
%r  = mul %i 3
%o  = add %r %j
%t  = mul %i 10
%v  = add %t %j
%yv = shrink %y %o []
%s  = store %yv %v
%ej = end %s %j
%ei = end %ej %i
%y1 = after %y %ei
  1. Number the loops. i is the outer loop, depth 1. j is inside it, depth 2.
  2. List the open ranges. %r and %t have {i}. %o, %v and the store have {i, j}.
  3. Take the deepest one. %r and %t get depth 1. The other three get depth 2.
void kernel(int32_t *restrict b0) {
  for (int32_t r4 = 0; r4 < 2; r4++) {
    int32_t v5 = (int32_t)((uint32_t)r4 * (uint32_t)3);
    int32_t v6 = (int32_t)((uint32_t)r4 * (uint32_t)10);
    for (int32_t r7 = 0; r7 < 3; r7++) {
      int32_t v8 = (int32_t)((uint32_t)v5 + (uint32_t)r7);
      int32_t v10 = (int32_t)((uint32_t)v6 + (uint32_t)r7);
      b0[v8] = v10;
    }
  }
}

v5 and v6 run twice, not six times. Moving work out of a loop is called hoisting. Here it needs no extra code: it is what "and no deeper" means.

Loops nest i (outermost), then j, then k. A value is add %i %k. Where is it computed?

A value lives at the depth of its deepest open range.

It depends on k, the innermost range, so it's computed every k iteration, even though it doesn't use j.

Find the loop order first

The last section took i as the outer loop. No line of the program says that. Change only the two end lines:

%ei = end %s %i
%ej = end %ei %j
%y1 = after %y %ej

The store still depends on i and j. With these ends, which loop is the outer one?

%ei repeats the store for every i. What does %ej repeat?

j. %ej repeats the whole i loop once for each j, so the i loop is inside it.

Now mul %i 3 sits at depth 2 and runs six times:

void kernel(int32_t *restrict b0) {
  for (int32_t r4 = 0; r4 < 3; r4++) {
    for (int32_t r5 = 0; r5 < 2; r5++) {
      int32_t v6 = (int32_t)((uint32_t)r5 * (uint32_t)3);
      int32_t v7 = (int32_t)((uint32_t)v6 + (uint32_t)r4);
      int32_t v9 = (int32_t)((uint32_t)r5 * (uint32_t)10);
      int32_t v10 = (int32_t)((uint32_t)v9 + (uint32_t)r4);
      b0[v7] = v10;
    }
  }
}

The same node got a different depth. So depths mean nothing until the loops are in order, and the order comes from the ends:

  1. Look at an end. %ei = end %s %i closes i.
  2. Read what is still open. Its effect also depends on j, so %ei has {j} open.
  3. Those are the loops around it. The i loop sits inside the j loop.

A value then goes inside every loop around its deepest range, even one it does not use. In the convolution, w[k] depends only on k, but the k loop is inside the i loop, so the load is inside both.

This is why a loop program needs reshaping before it can be printed. The syllabus calls it ordering the ranges, and suggests a rewrite engine like week 1's: rules that push each node into the loop it belongs to and pull everything else out. You can also compute the order and the depths directly. Either way, make it a pass of its own, separate from printing. Week 4 creates ranges for you and reuses it.

One load has to move

There is one case where the depth rule alone prints a wrong program. It is the accumulator from lesson 3.2, here as the inner loop of the convolution:

%cur = load %yv0
%sum = add %cur %p
%s   = store %yv0 %sum
%ek  = end %s %k

%yv0 is the view of y[i], and %p is this tap's product, which depends on k.

In the convolution, the accumulator load %cur = load %yv0 depends on i but not on k. Its only use is inside the k loop, and the k loop stores into the version it reads. Where does it run?

This is the one placement rule that isn't about open ranges.

A load runs in the innermost loop holding all its uses, and because that loop stores into the version it reads, it reloads every iteration and sees the running sum. Anywhere else, every iteration would add to the same starting value.

By its ranges, %cur has depth 1: before the k loop. There it would be read once, and every trip would add its product to the same starting value. So loads get one more rule:

  1. Place the load by its ranges. %cur: the i loop.
  2. Find the innermost loop that holds every use. Its only use is %sum, in the k loop.
  3. Move it if that loop is deeper and writes what the load reads. The k loop stores into y[i], so the load moves in and runs on every trip.

Only loads ever move.

When a load must not move: split uses, for when a lab test surprises you

"Every use" means every use in the program, including an assert. A use counts as inside a loop only if it is placed there itself: because it depends on the loop's range, or because it is a load that this same rule moved there.

If a load has one use inside the loop and one outside, the innermost loop holding all its uses is the outer block. The load runs once, before the loop, and every use sees the contents from before the loop. In tests/week3/run/pinned_load_outside.uir the load's use add %x 1 depends on no range, so the reference prints both before the loop:

void kernel(int32_t *restrict b0) {
  int32_t v4 = b0[0];
  int32_t v6 = (int32_t)((uint32_t)v4 + (uint32_t)1);
  for (int32_t r7 = 0; r7 < 3; r7++) {
    int32_t v8 = (int32_t)((uint32_t)r7 * (uint32_t)0);
    b0[v8] = v6;
  }
}

Place loads on the graph as written. If your builder folds mul %k 0 to 0 first, lesson 3.2's two views of one element merge into one and the loads change places.

The shape of the C

With an order and a depth for every node, printing is week 2's renderer run once per block. A block is the list of lines between one pair of braces.

  • Depth 0 is the function body. Buffers are parameters.
  • An end is a loop. It prints for (int32_t rN = 0; rN < bound; rN++) { in the block of the loops around it, then a new block, then }. The range becomes the counter rN.
  • The new block holds every node whose deepest loop is the one that end closes.
  • Inside a block, week 2's order holds. Sources first, and loads of a version before the store that overwrites it.

What the grader allows now

The render grader still removes comments and strings, then looks for loops. For a program that contains a range, for is allowed and while, do and goto are not. For a program with no ranges (every week 2 test), any loop at all fails the test.

What you can do now

  • Give every value a depth: its deepest open range, in the order the loops nest.
  • Read the loop order off the ends before placing anything.
  • Move an accumulator load into the loop that writes what it reads.
  • Print each end as a for with its own block.

The placement rules in the spec's words, for when you write the pass
  • A value is computed inside every loop whose range it depends on, and no deeper. Its depth is the deepest of its open ranges. A constant, or anything built only from constants and buffers, lives outside every loop.
  • A load is placed the same way, with one exception. First place it by its own open ranges. Then find the innermost loop holding every use of it. If that loop is deeper, and it stores into the version the load reads, the load moves into it and sees the current contents on every iteration. A use counts as inside a loop only if it's placed there itself. That's the accumulator from lesson 3.2.
  • An end is a loop. It sits in the block around its loop, and its loop body is a new block holding everything whose deepest range is the one it closes.

The ranges an end still has open after closing its own are exactly the loops around it. Each range is closed by exactly one end, so the nesting is always well defined. If a value depends on two loops that are not nested in each other, the program is invalid.

A bigger example: the four loops of the 2D convolution, for checking your output

This is the reference's C for the 2D convolution program in lesson 3.4. The loops are oy, ox, ky and kx, outermost first.

void kernel(float *restrict b0, float *restrict b1, float *restrict b2) {
  for (int32_t r7 = 0; r7 < 3; r7++) {
    int32_t v8 = (int32_t)((uint32_t)r7 * (uint32_t)3);
    for (int32_t r9 = 0; r9 < 3; r9++) {
      int32_t v10 = (int32_t)((uint32_t)v8 + (uint32_t)r9);
      b2[v10] = 0x0.0p+0f;
      for (int32_t r15 = 0; r15 < 2; r15++) {
        int32_t v16 = (int32_t)((uint32_t)r7 + (uint32_t)r15);
        int32_t v17 = (int32_t)((uint32_t)v16 * (uint32_t)4);
        int32_t v18 = (int32_t)((uint32_t)r15 * (uint32_t)2);
        for (int32_t r19 = 0; r19 < 2; r19++) {
          float v20 = b2[v10];
          int32_t v21 = (int32_t)((uint32_t)r9 + (uint32_t)r19);
          int32_t v22 = (int32_t)((uint32_t)v17 + (uint32_t)v21);
          float v24 = b0[v22];
          int32_t v25 = (int32_t)((uint32_t)v18 + (uint32_t)r19);
          float v27 = b1[v25];
          float v28 = (v24 * v27);
          float v29 = (v20 + v28);
          b2[v10] = v29;
        }
      }
    }
  }
}
  • v8 is oy*3. It depends on the outermost range only, so it is computed once per oy, not once per tap.
  • v10 and the reset store depend on oy and ox.
  • v17 is (oy + ky)*4 and v18 is ky*2. Neither uses kx, so both stay out of the innermost loop.
  • v20 is the accumulator load, placed by its use.

A C compiler would hoist these too, at -O2. You still want to do it yourself: it's free once you have depths, it makes the C readable, and from week 6 your kernels get timed with your own code doing the work.

Check yourself

In an i, j, k nest, where is mul %i 3 computed?

What's the deepest range it depends on?

Its only range is i, so it's hoisted out of j and k. Ordinary values stay at the depth of their ranges. Only a load whose uses sit in a deeper loop that writes the version it reads moves toward those uses.

What outcome should ./compile print for this file?

%b  = buffer 4 dtype=i32 slot=0
%i  = range 4
%j  = range 2
%v  = shrink %b %i []
%s  = store %v 7
%e  = end %s %j
%b1 = after %b %e
%x  = load %b1
%t  = assert %x [7 7 7 7]

Which range does the store depend on, and which one does the end close?

REJECTED. The store depends on i, but the end closes j, which its effect doesn't use. The oracle rejects it: "end closes a range its effects don't use".

One range %i is closed by two different ends, one around a store into slot 0 and one around a store into slot 1. Is that a valid program?

A range is the loop. How many loops can one loop be?

A range names one loop, so it gets one end. To write two buffers in the same loop, give that end both effects. The oracle accepts end %s0 %s1 %i and rejects the two-end version.

After this program, what's in c[2]?

One loop runs both stores. What does the second store write at i = 2?

4: the loop writes i*i into c[i], so c = [0 1 4]. Both afters take the same end, one per buffer it wrote.
