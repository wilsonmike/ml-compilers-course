A GEMM by hand

Neural networks spend most of their time multiplying matrices. In this lesson you write a matrix multiply in .uir, called a GEMM (general matrix multiply). It is the first program in this course that matters in machine learning, and it is what three weeks of ops, memory and loops were for.

Goal

Write a matrix multiply in .uir with three ranges and one running total per output cell.

You'll use

Dot products and the triple loop from lesson 0.5. Views (shrink) from lesson 2.1, load, store and after from lesson 2.2, and the bounds proof from lesson 2.3. range and end from lesson 3.1, and the accumulator and its reset from lesson 3.2.

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

Lesson 0.5: a dot product multiplies the matching pairs of two vectors, then adds the products. What is [1, 2, 3] · [4, 5, 6]?

Three products, then one sum: 1*4, 2*5, 3*6.

4 + 10 + 18 = 32.

An i loop wraps a j loop. A reset, store %o 0, writes through %o = shrink %out %i []. How often does the reset run?

A store runs inside every loop whose range it depends on, and no deeper.

The view depends on %i and not on %j. So the store sits inside the i loop and outside the j loop. That is how lesson 3.2 reset a total once per row.

The cell of C at row i, column j is row i of A dotted with column j of B. Here is row 0, column 0:

  1. Pick the row. Row 0 of A is [1 2].
  2. Pick the column. Column 0 of B, read downward, is [5 7].
  3. Dot them. 1*5 + 2*7 = 19.

What goes in row 1, column 0 of C?

Row 1 of A is [3 4]. The column is the same one as before.

[3 4] dotted with [5 7] is 15 + 28 = 43. The whole answer is C = [[19 22] [43 50]].

That is all a matrix multiply is: one dot product per output cell. Make this one program fast and a whole neural network is fast. First you have to write it.

The dark cell is row 1, column 0. At which index of the buffer does it sit?

Row 0 comes first and takes up three boxes: 0, 1 and 2.

Index 3. You skip one whole row of 3 boxes, then take 0 steps along the row.

Lesson 0.4's rule: in a matrix with cols columns, row r, column c sits at index r*cols + c. Skip r whole rows, then step c boxes along. Every index in a GEMM is built this way, so practice it twice before you use it.

A matrix has 4 columns. At which index is row 2, column 1?

r*cols + c with r = 2, cols = 4, c = 1.

2*4 + 1 = 9. Two whole rows are 8 boxes, then one step along.

B has 3 rows and 2 columns. Which index holds row k, column j?

Multiply the row number by the number of columns, not by the number of rows.

Each row is 2 boxes wide, so skipping k rows skips k*2 boxes. Then step j along: k*2 + j.

One dot product, one loop

You will build the GEMM in three small moves. The first is one cell of C: one dot product. Lesson 3.2's dot product kept its total in an alloc. A GEMM needs one total per cell, so this one keeps it in the output element, which the loop loads and stores on every turn.

The output element starts out holding junk, say 100. A loop adds 1*4, then 2*5, then 3*6 into it. What does it hold at the end?

The three products add up to 32. What were they added to?

100 + 32 = 132, not 32. An output buffer can start with anything in it, so the program has to store a 0 first.

So the program is a reset, then lesson 3.2's loop. Here it is for two vectors of three:

%a    = buffer 3 dtype=i32 slot=0
%b    = buffer 3 dtype=i32 slot=1
%out  = buffer 1 dtype=i32 slot=2
%o    = shrink %out 0 []
%z    = store %o 0
%out1 = after %out %z
%k    = range 3
%av   = shrink %a %k []
%x    = load %av
%bv   = shrink %b %k []
%y    = load %bv
%p    = mul %x %y
%o1   = shrink %out1 0 []
%cur  = load %o1
%sum  = add %cur %p
%s    = store %o1 %sum
%e    = end %s %k
%out2 = after %out1 %e
  1. Reset the total. Store 0 into out[0]. %out1 names the buffer after the reset.
  2. Count. %k takes the values 0, 1 and 2.
  3. Read one pair. Load a[k] and b[k] and multiply them.
  4. Add it in. Load the total from %out1, add the product and store it back. The loop stores into the version %cur reads, so %cur sees the newest total on every turn.
  5. Close the loop. end repeats the store for every %k. %out2 is the buffer after the loop.

Dot product

Lesson 3.2's dot product again, now with the total in the output. Put the dot product of slots 0 and 1 (four i32s each) into slot 2's only element. The starter resets the output and stops. Add the loop.

All the columns

The second move: dot one vector v with every column of B. That gives one whole row of C. B has 3 rows and 2 columns, so there are two totals, out[0] and out[1].

v is [1 2 3]. B is [[7 8] [9 10] [11 12]], so its columns are [7 9 11] and [8 10 12]. A program loops over j and k, but reads B at index k*2. What does out hold?

Index k*2 is row k, column 0, whatever j is.

Without + j both turns of the j loop read column 0, and 7 + 18 + 33 = 58 both times. The right answer is [58 64].

Four things change from the dot product:

  1. Add a range. %j = range 2 counts the columns.
  2. Read column j. B's offset becomes k*2 + j.
  3. Give each column its own total. The output view is shrink %out %j []. The reset stores through it, so the reset depends on %j and runs once per column.
  4. Close two loops. The inner loop first: k, then j.
%j    = range 2
%ov   = shrink %out %j []
%z    = store %ov 0
%out0 = after %out %z
%k    = range 3
...
%k2   = mul %k 2
%kj   = add %k2 %j
%bv   = shrink %B %kj []
...
%ek   = end %s %k
%ej   = end %ek %j
%out1 = after %out %ej

The last line builds on %out, not on %out0. The reset now runs inside the j loop, so %out0 only exists inside one turn of that loop (lesson 3.2).

Repair: one row times a matrix

Slot 0 is v, three i32s. Slot 1 is B, 3 rows and 2 columns, row-major. Slot 2 gets the two dot products: out[j] is v dotted with column j of B. The starter has the bug from the quiz above. Fix B's offset.

All the rows

The third move does that for every row of A, and that is the whole GEMM. A has 2 rows and 3 columns, B has 3 rows and 2 columns, and C has 2 rows and 2 columns. A third range, %i, counts the rows of A. Two indexes start using it:

C[i*2 + j] = sum over k of  A[i*3 + k] * B[k*2 + j]

Step through what each turn reads and writes. The matrices are the ones from lesson 0.5.

The innermost line does one multiply and one add. How many times does it run for this GEMM?

C has 4 cells. Each cell is a dot product of 3 pairs.

2 * 2 * 3 = 12. Three nested ranges run their body once for every combination of i, j and k.

Write the GEMM

Slot 0 is A (2 rows, 3 columns), slot 1 is B (3 rows, 2 columns) and slot 2 is C (2 rows, 2 columns), all i32 and row-major. The starter is the program from the last section: it only multiplies row 0 of A. Add %i = range 2, read A at i*3 + k, keep each total at i*2 + j of C, and close the third loop.

Read the finished program

Here is the same GEMM on floats, a few lines at a time. The running total is C itself. The reset's offset, i*2 + j, depends on two ranges, so the reset runs once per output cell.

The order of the ends picks the loop order: k is closed first, so it is the innermost loop. Swap the j and i ends and C comes out the same. Only the order the cells are filled in changes, and with it the speed.

The C your renderer should produce for this GEMM, for lesson 3.5 and the lab

With M rows of A, K columns of A and N columns of B, the general form is C[i*N + j] = sum over k of A[i*K + k] * B[k*N + j]. Here M = 2, K = 3 and N = 2.

The whole program checks out with the oracle, and its C, run on real arrays, prints 58 64 139 154. Here's the rendered kernel, with the wraparound casts trimmed for reading:

for (int32_t r6 = 0; r6 < 2; r6++) {             /* i */
  int32_t v7 = r6 * 2;                           /* i*N */
  int32_t v8 = r6 * 3;                           /* i*K */
  for (int32_t r9 = 0; r9 < 2; r9++) {           /* j */
    int32_t v10 = v7 + r9;                       /* i*N + j */
    b2[v10] = 0x0.0p+0f;                         /* reset C[i][j] */
    for (int32_t r15 = 0; r15 < 3; r15++) {      /* k */
      float v16 = b2[v10];                       /* loop-carried load */
      int32_t v17 = v8 + r15;
      float v19 = b0[v17];                       /* A[i][k] */
      int32_t v20 = r15 * 2;
      int32_t v21 = v20 + r9;
      float v23 = b1[v21];                       /* B[k][j] */
      float v24 = v19 * v23;                     /* two statements, as the oracle prints them: */
      float v25 = v16 + v24;                     /* a*b + c on one line invites an FMA (lesson 2.4) */
      b2[v10] = v25;
    }
  }
}

Every index computation sits in the loop of its deepest range: i*K outside the j loop, i*N + j outside the k loop. You get that hoisting for free from open ranges. 0x0.0p+0f is how the oracle prints zero: the same value as lesson 2.4's 0x0p+0f.

Same answer, different speed: why loop order matters, for week 7

The order of the ends picks the loop order. Here's a 2-by-3 fill written two ways. Both store i*3 + j into element i*3 + j, and both leave the buffer holding 0 to 5:

%ej = end %s %j      # j inner
%ei = end %ej %i     # i outer

for (i ...)
  for (j ...)
    b[i*3 + j] = ...   /* 0 1 2 3 4 5 */
%ei = end %s %i      # i inner
%ej = end %ei %j     # j outer

for (j ...)
  for (i ...)
    b[i*3 + j] = ...   /* 0 3 1 4 2 5 */

The left version walks memory in order: addresses 0, 1, 2, 3, 4, 5. The right one jumps by 3 each step. Lesson 0.2 showed what that costs: in-order access uses every byte of each cache line it loads, and strided access can miss on nearly every step once the arrays are bigger than the cache. In this GEMM, the inner k loop walks A along a row (stride 1) but B down a column (stride N). Reordering the loops so the innermost index is the one each array is contiguous in is one of the first speedups in week 7. For now, the grader only checks correctness.

Every index is proven in bounds

Lesson 2.3 said a view is only allowed when the compiler can prove its offset fits inside the parent. Loops do not change that. A range n has bounds [0, n-1]. Take A's view, shrink %A %ik []:

  1. Bound the counters. %i = range 2 is in [0, 1]. %k = range 3 is in [0, 2].
  2. Bound the offset. i*3 is in [0, 3]. Adding k gives [0, 5].
  3. Compare. A has 6 elements and the view is 1 wide, so the last allowed start is 5. The highest offset is 5. Proven.

Make A five elements long and the same program is rejected: "can't prove the view is in bounds: offset in [0, 5], 1 element(s), parent has 5".

C's offset is i*2 + j, with %i = range 2 and %j = range 2. What is the highest value it can take?

Use the highest i and the highest j. Both are 1.

1*2 + 1 = 3. C has 4 elements, so the last allowed start is 3 and the view is proven.

The proof only says an index lands inside the buffer, not that it is the right one. In this exercise the wrong index and the right one both pass the bounds check.

C = A @ B transposed

A and B are both 2-by-3 i32 matrices, row-major, in slots 0 and 1. Compute C = A @ B^T (2-by-2) into slot 2: C[i*2 + j] is the dot product of row i of A and row j of B. The starter is the plain GEMM from this page, which indexes B as if it were 3-by-2.

Check yourself

With %i = range 2 and %k = range 3, what interval does the bounds check give i*3 + k? (low and high)

A range's interval is [0, n-1]. Multiply, then add, end by end.

i is in [0, 1], so i*3 is in [0, 3]. Adding k in [0, 2] gives [0, 5], which fits a six-element buffer exactly.

For the 2-by-3 A and 3-by-2 B in the stepper on this page, what does C[1*2 + 1] end up holding?

Row 1 of A is [4 5 6]. Column 1 of B is [8 10 12].

4*8 + 5*10 + 6*12 = 32 + 50 + 72 = 154, the same answer as the stepper in lesson 0.5.

Suppose the accumulator is a one-element alloc that's never reset, and each (i, j) copies it into C after its k loop. The right C is [58 64 139 154]. What does C hold?

The alloc starts at 0 once, not once per output element.

The sum carries over from one output element to the next: 58, then 58 + 64 = 122, then 122 + 139 = 261, then 261 + 154 = 415. That's why the reset has to depend on i and j.

Change A to five elements, leaving the rest of the GEMM alone. What outcome does ./compile print?

The interval of i*3 + k doesn't change.

The offset is still in [0, 5], and a five-element buffer can't hold a view at 5, so the bounds check fails and the program is rejected before it runs: REJECTED.

How many multiply-adds does an M-by-K times K-by-N GEMM do?

How many output elements are there, and how many multiply-adds does each one take?

There are M*N outputs, and each is a sum of K products, so the innermost body runs M*N*K times. That's the trip count of the three nested ranges.

Swapping the order of the j and i ends in the GEMM changes...

Each element is written exactly once in both versions.

Each element gets the same value either way, so the result is identical and the bounds don't change. What changes is the loop nest the renderer emits, and so the access pattern. That decides cache behavior, which week 7 starts measuring.
