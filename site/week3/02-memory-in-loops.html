Week 3 · Lesson 2

Memory in loops

By the end of this lesson you can write a loop that keeps a running total in memory, and say what every load in it sees. A loop runs the same store many times, so "which version does this load read?" needs a clear answer. Every sum your compiler handles works this way, including the matrix multiply in the next lesson.

Goal

Write a loop that adds into one box of memory, and say for any load which loop it runs in and which contents it reads.

You'll use

range, end and open ranges from lesson 3.1. load, store, after and versions from lesson 2.2. alloc from lesson 2.1. The fact that two identical lines make one node, from lesson 1.1.

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

From lesson 2.2. What does %x hold?

%b  = buffer 2 [5 6] dtype=i32 slot=0
%e  = shrink %b 0 []
%s  = store %e 7
%b1 = after %b %s
%x  = load %e

A load reads the version its view was cut from. Which version is %e cut from?

%e is a view of %b, the version before the store, so the load reads 5. The 7 is in %b1, the version that after names.

From lesson 3.1. How many times does the store run?

%b  = buffer 3 dtype=i32 slot=0
%i  = range 3
%v  = shrink %b %i []
%s  = store %v 7
%e  = end %s %i
%b1 = after %b %e

end %s %i repeats the store for every value of %i.

%i takes the values 0, 1 and 2, and end runs the store once for each. A value that does not depend on %i has no open range, so it is computed once, outside the loop.

A total that comes out wrong

This program should add up four numbers and put the total in out[0]. The running total lives in %acc, an alloc with one box. An alloc is scratch memory that starts as 0.

%in   = buffer 4 [1 2 3 4] dtype=i32 slot=0
%out  = buffer 1 dtype=i32 slot=1
%acc  = alloc 1 dtype=i32
%a    = shrink %acc 0 []
%k    = range 4
%cur  = load %a
%iv   = shrink %in %k []
%x    = load %iv
%sum  = add %cur %x
%s    = store %a %sum
%e    = end %s %k
%acc1 = after %acc %e
%tot  = load %a
%o    = shrink %out 0 []
%so   = store %o %tot
%out1 = after %out %so

It looks right: load the total, add in[k], store it back, four times. What does out[0] hold at the end?

Look at %tot = load %a. Which version of the accumulator is %a cut from?

It holds 0, not 10. %tot loads through %a, and %a is a view of %acc. That is the memory before the loop, and it holds 0.

This is the warm up again, with a loop where the single store was. end wraps the repeated store into one effect, %e. Then %acc1 = after %acc %e names the memory once the whole loop has finished. (after and end are the only ops that take an effect.) The total is in %acc1, so the final load needs a view cut from %acc1.

Read the total from the right version

This is the program above. Slot 0 holds four i32s, and their sum should end up in slot 1. Change the last load so it reads the accumulator after the loop. You need one new view.

An accumulator, pass by pass

An accumulator is a piece of memory that a loop reads, changes and writes back on every pass. Here it is one box. Each pass through the loop body is called an iteration, and each one does four things:

  1. Load the total so far. %cur = load %a reads the box.
  2. Load this pass's number. %x is in[k].
  3. Add. %sum = add %cur %x.
  4. Store it back. store %a %sum writes into the same box, ready for the next pass.

Step through the repaired program:

At the start of the iteration k = 3, what does %cur read?

It reads what the iteration k = 2 stored.

The first three passes added 1, 2 and 3, so the box holds 6. This pass adds 4 and stores 10.

Where a load runs

%cur = load %a does not depend on %k. Lesson 3.1 said a value with no open range is computed once, outside every loop.

Suppose your compiler placed %cur by that rule alone: one load, before the loop. With in = 1 2 3 4, what would the accumulator hold after the loop?

%cur would be 0 on every pass. What does the last pass store?

Every pass would store 0 + in[k]. The last pass stores 0 + 4, so the box ends at 4 instead of 10.

So a load gets one extra rule. It answers "which loop does this load belong to?"

Where a load runs

First place the load like any value: inside every loop whose range it depends on, and no deeper. Then find the innermost loop that holds every use of the load. If that loop is deeper, and it stores into the version the load reads, the load moves into that loop. It runs on every iteration and sees the current contents: the previous iteration's store, or the contents before the loop on the first iteration.

Apply it to %cur:

  1. Place it by open ranges. Nothing is open, so it starts outside the loop.
  2. Find every use. Its only use is %sum. That depends on %k, so it sits inside the k loop.
  3. Check the loop's stores. The k loop stores through %a into %acc, the version %cur reads. So %cur moves into the loop. Such a load is called loop-carried.

%tot reads %acc1 and its use is outside the loop, so it runs once, after the loop. Here's the C the oracle renders, trimmed of the wraparound casts:

int32_t a4[1] = {0};
for (int32_t r7 = 0; r7 < 4; r7++) {
  int32_t v8 = a4[0];        /* %cur: inside the loop */
  int32_t v10 = b0[r7];      /* in[k] */
  int32_t v11 = v8 + v10;
  a4[0] = v11;
}
int32_t v15 = a4[0];         /* %tot: after the loop */
b1[0] = v15;

Dot product

Slots 0 and 1 each hold four i32s. Put their dot product from lesson 0.5, a[0]*b[0] + ... + a[3]*b[3], into slot 2's only element. Only the buffers are declared. Write the accumulator loop yourself: a one-box alloc, a range, the four steps, end and after. Then load the total from the version after the loop and store it into out.

One load, used inside and outside

The broken program says load %a on two lines. Two identical lines are one node, so there is one load with two uses: %sum inside the loop and the store into %out outside it. No loop holds both uses, so the load stays outside. It runs once, before the loop, and every use sees the contents from before the loop. That loop was broken too: every pass added to the same 0.

Here is the same shape in a buffer you can see:

%b   = buffer 2 [5 0] dtype=i32 slot=0
%acc = shrink %b 0 []
%cur = load %acc            # used inside AND outside the loop
%k   = range 3
%one = add %k 1
%sum = add %cur %one        # use 1: inside the loop
%s   = store %acc %sum
%e   = end %s %k
%b1  = after %b %e
%dst = shrink %b1 1 []
%s2  = store %dst %cur      # use 2: after the loop
%b2  = after %b1 %s2

What are the final contents of the buffer?

Where does %cur run when one of its uses is outside the loop?

%cur runs once, before the loop, and reads 5. Each iteration stores 5 + (k + 1), so the last leaves 8. b[1] gets the pre-loop 5: [8 5].

A use that doesn't depend on the range pins the load

A use counts as inside a loop only if it is placed there itself: because it depends on that loop's range, or because it is a load this same rule moved there. %y = add %cur 1 depends on no range, so it sits outside the loop and keeps its load outside too. The accumulator then stops accumulating, with no error.

A pinned load, worked through

This loop is meant to add 1 to b[0] three times, starting from 10. It writes 11:

%b  = buffer 1 [10] dtype=i32 slot=0
%i  = range 3
%z  = mul %i 0
%v  = shrink %b %z []         # the store's view depends on %i
%v0 = shrink %b 0 []          # the load's view doesn't
%x  = load %v0
%y  = add %x 1                # depends on no range
%s  = store %v %y
%e  = end %s %i
%b1 = after %b %e

%y depends on no range, so it's placed outside the loop, and so is its load: both run once, and every iteration stores the same 11. Load through the store's own view (%x = load %v) and the load depends on %i, runs every iteration, and the result is 13.

When you need both the starting value and the running value

The same node can't be both. Because UOps are hash consed, "the load of b[0]" is one node. You can't have it be loop-carried for one use and pre-loop for another. And writing load %acc a second time doesn't help: two identical loads are the same node. If you need both the running value and the starting value, load through two different view nodes of the same element. Load the starting value through the view at offset 0, as before. Load the running value through a view at offset mul %k 0: it's still element 0, but the graph sees a different node, and it depends on %k, so it runs inside the loop. With that change, the program above gives b[0] = 11 (loop-carried) and b[1] = 5 (the starting value).

Don't fold the trick away. mul %k 0 only helps while it is still a node. If your graph builder applies week 1's mul(x, 0) → 0 as it builds, the running view becomes shrink %b 0 [], the same node as %acc, and the two loads merge back into one. Place loads on the graph exactly as written, and run any simplifier rules afterwards or not at all.

Start the total before the loop

An alloc starts as 0, which suits a sum. But an output buffer starts with junk, and a running maximum needs a start that no input can beat. In both cases you store a starting value before the loop. That store makes a new version, and the loop works on it:

%o    = shrink %out 0 []
%z    = store %o 0
%out0 = after %out %z
%o0   = shrink %out0 0 []
%k    = range 5
%v    = shrink %in %k []
%x    = load %v
%cur  = load %o0
%sum  = add %cur %x
%s    = store %o0 %sum
%e    = end %s %k

The loop loads and stores through %o0, a view of %out0. Which line names the buffer after the loop?

In week 2, each after built on the version its store wrote into.

The loop stores into %out0, so its after builds on %out0. With after %out %e two versions would both build on %out, and the buffer would have two possible outputs. The oracle rejects it: "the loop must store into the version after names, not an older one".

A buffer's versions stay one chain, as in week 2. A whole loop is one link in that chain.

The largest of five

Slot 0 holds five f32s. Put their maximum into slot 1's only element. Slot 1 starts with junk, so start the running max from something no input can beat.

Reset inside an outer loop

Now sum each row of a matrix into its own out[i]. Every row needs its total reset to 0 first. Where does the reset store go?

A program has an i loop around a j loop. It also has store %o 0 with %o = shrink %acc 0 []. How often does that store run?

What are the store's open ranges?

The store depends on no range, so it has nothing open and runs once, outside both loops. To reset once per row, the store has to depend on %i, for example by storing into shrink %out %i [].

So the reset stores into a view that uses %i. Then the j loop accumulates into the version after the reset:

%i    = range 3
%o    = shrink %out %i []
%z    = store %o 0              # reset out[i]: runs once per i
%out0 = after %out %z           # a version that lives inside the i loop
%j    = range 4
...
%o0   = shrink %out0 %i []
%cur  = load %o0                # loop-carried in the j loop
%s    = store %o0 %sum
%ej   = end %s %j
%ei   = end %ej %i
%out1 = after %out %ei          # the output: no open ranges

%out0 has {i} open, so it is local to one iteration of the i loop: this row's box, freshly reset. Only an after with nothing open counts as the buffer's output. That is why the last line builds on %out, the version before the loops, and not on %out0.

Row sums

Slot 0 is a 3-by-4 i32 matrix, row-major. Write each row's sum into slot 1: out[i] = A[i*4+0] + ... + A[i*4+3]. Slot 1 starts with junk, so every out[i] has to be reset before its row is summed. The starter forgets.

Every rule for memory inside loops, for when you write the lab
  • Load placement. The rule in "Where a load runs" is the whole rule. "Every use" means every use in the program, including an assert. render emits no code for asserts, but it still counts them when it decides whether a load is pinned outside a loop, so render and ./compile agree.
  • Split uses. If some uses are inside the loop and some outside, the load runs outside the loop and every use sees the contents from before the loop.
  • Afters inside loops. An after may sit inside loops. Only an after with no open ranges counts as a buffer's output version. Every range a store or after depends on must be closed by an end before any top-level output.
  • The loop's after. If the after's effect is an end, the loop must store into the exact version the after names, or into a version built on it inside the loop. In the row-sum program the reset is inside the i loop, so %out0 is built inside it and after %out %ei is right. Now move the reset outside every loop, so that its after, say %r = after %out %z, has nothing open. The loop then stores into %r, so the loop's after must build on that version: after %r %ei. Writing after %out %ei there is invalid, because the buffer's versions would fork.
  • Inside one iteration. The week 2 rules hold: one store per version, and loads of a version run before the store that overwrites it.
  • Bounds. A range's interval is [0, n-1], so i*K + k is provably inside an M*K buffer when i < M and k < K.

What you can do now

  • Keep a running total in one box of memory and read it from the version after the loop.

  • Spot a load that is stuck outside its loop because of a second use.
  • Start an accumulator before a loop, or reset it inside an outer loop, and build the after on the right version.

Check yourself

The split-use program above, without the second store. What's the final b[0]?

%b   = buffer 2 [5 0] dtype=i32 slot=0
%acc = shrink %b 0 []
%cur = load %acc
%k   = range 3
%one = add %k 1
%sum = add %cur %one
%s   = store %acc %sum
%e   = end %s %k
%b1  = after %b %e

Is %cur used anywhere outside the loop now?

Its only use is inside the k loop, which stores into the version it reads, so it's loop-carried: 5 + 1 + 2 + 3 = 11.

In the repaired accumulator program, the final load is %tot = load %a1, with %a1 a view of %acc1. Where does it run?

Which version does it read, and where is its use?

%tot reads %acc1, the version after the loop, and its use (the store into %out) is outside every loop. So it runs once, after the loop's closing brace.

Which ops may consume an effect (a store or an end)?

Effects are void.

Effects have dtype void, and only after (to name the memory after it) and end (to repeat it) take them.

Why does %out1 = after %out %ei build on %out and not on %out0, the version after the reset?

What are %out0's open ranges?

%out0 depends on the reset store, which depends on %i. A version with an open range exists once per iteration, so it can't be what the buffer holds after the loop. The output is the after with nothing open, built on the version before the loops.
