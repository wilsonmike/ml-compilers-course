Flash attention

Attention is the step a language model spends most of its time in. Done the obvious way, it fills a table of scores far too big for a GPU's fast memory. You'll learn the one trick that lets a kernel get the same answer without ever storing that table.

Goal

Compute a softmax in one pass, and explain how that lets an attention kernel skip the table of scores.

You'll use

Softmax from lesson 6.2, shared memory from lesson 8.3 and per-thread memory in registers from lesson 9.1.

In the exercises: a for loop over a list of pairs (P.3).

In the exercises: List.fold_left with a tuple as the running state (O.3).

Softmax turns a row of scores into shares. What do the shares add up to?

Each share is one score's exp divided by the sum of all of them.

1. Every share is a piece of the same total, so together they make the whole.

An alloc is only ever used at t·16 + e, inside a local loop over t, with e from 0 to 15. Where can the CUDA compiler keep it?

Lesson 9.1 had a name for memory of this shape.

It's per-thread memory. No thread reads another thread's slice, so each thread can hold its 16 elements in registers, the fastest memory there is.

What attention does

A language model reads text as a row of words. (Real models cut text into tokens, which are words or pieces of words. We'll say words.) To understand one word, the model needs the others. In "big dogs bark", who is barking?

Attention is the step that lets each word look at every word and decide how much each one matters. The amounts are called weights. They're shares that add up to 1. Models like the one behind ChatGPT are stacks of attention steps, and attention is where they spend most of their time. So it's a kernel worth making fast.

Work one row by hand

Each word carries three rows of numbers. Its query says what it's looking for. Its key says what it offers. Its value is what it hands over when a word looks at it. The score of one word looking at another is high when the first word's query matches the second word's key.

Here's the row for "bark". Its scores for the three words are 1, 2 and 0. A real value is a row of D numbers. To keep the arithmetic small, each value here is one number: 10, 20 and 30.

  1. Subtract the largest score. The largest is 2, so the scores become -1, 0 and -2. Week 6 did this to keep exp from overflowing. It doesn't change the answer.
  2. Take exp of each. 0.368, 1 and 0.135.
  3. Add them up. 1.503.
  4. Divide each by the sum. The weights are 0.245, 0.665 and 0.090. Steps 1 to 4 are softmax.
  5. Average the values by weight. 0.245·10 + 0.665·20 + 0.090·30 = 18.45.

The output for "bark" is 18.45. It's mostly the 20 from "dogs", pulled a little toward the other two.

Suppose all three scores were equal. With values 10, 20 and 30, what would the output be?

Equal scores give equal weights, one third each.

20. Equal weights make a plain average. Scores only matter by how far apart they are.

The full formula with Q, K and V, for when you read the kernel

A head of attention has three S×D matrices: queries Q, keys K and values V, one row per token. For query row i:

s_j = (q_i · k_j) / sqrt(D)          for every key j: a score
p_j = exp(s_j - m) / l               m = the largest s_j, l = the sum of exp(s_j - m): softmax
o_i = sum over j of p_j · v_j        the output row

Subtracting the largest score m changes nothing mathematically and keeps exp from overflowing. A model runs many heads at once: the speed test uses 16.

The problem: a table of scores

A row of S words has S scores for every word, so S × S in all. The obvious way uses three kernels. The first writes every score into a table. The second runs softmax over each row of it. The third multiplies the weights by the values. Each score is an f32, which takes 4 bytes.

Guess first. A model reads 8,192 words at once. How many MB is its table of scores? (8,192 is 213, and 1 MB is 220 bytes.)

8192 · 8192 · 4 bytes is 213 · 213 · 22.

228 bytes, which is 256 MB, for one table. A model runs several attentions side by side, each called a head, and every head has its own table.

A block's shared memory holds tens of kilobytes. A thread's registers hold about 1 KB. So 256 MB fits in neither, and the table has to live in global memory, the slow one.

Even at 1,024 words, one head's scores are 4 MB. They're written, read for the max, read for the sum, read again to normalize into another 4 MB, and read for the product. The arithmetic is cheap next to all that traffic. Measured on the 4060 Ti, 4 heads of 1,024 tokens with D = 32:

kernel (4 heads, 1,024 tokens, D = 32)time
three kernels through an S×S score matrix in global memory2.97 ms
flash attention: one kernel, nothing S×S stored0.33 ms

The second row is flash attention. It gets the same outputs and never writes the table. The rest of this lesson builds it.

Is that comparison fair? A note on the slow kernel

Our three-kernel version is simple in other ways too: its softmax pass gives each row to one thread. A tuned version would close some of the gap, but not the traffic, which grows with S².

Softmax without keeping the scores

To skip the table, a thread has to finish a row while its scores go by one at a time, keeping none of them. Softmax seems to forbid that. Its first step subtracts the largest score, and the largest isn't known until every score has been seen.

Scores arrive one at a time. So far you've seen only the score 1, so the largest is m = 1 and the sum is l = exp(1 - 1) = 1. Now a 2 arrives, a new largest. The old sum was built against the wrong max. Can you fix it without the old scores?

exp(a)·exp(b) = exp(a + b). What is exp(s - 1)·exp(1 - 2)?

It's exp(s - 2), exactly what the term should have been. One multiply fixes every old term at once, because they all sit inside the sum.

So keep two numbers, a running max m and a running sum l. This is a running softmax. When a new score s arrives:

m_new = max(m, s)
c     = exp(m - m_new)              the correction: 1 if the max didn't change
l     = l · c + exp(s - m_new)
m     = m_new

Start with m = -inf and l = 0. exp(-inf) is 0, so the first score needs no special case.

Try it on the scores for "bark", 1, 2 and 0, arriving in two pieces: first the 1, later the 2 and the 0.

  1. First piece, score 1. m_new = 1 and c = exp(-inf) = 0, so l = 0·0 + exp(0) = 1.
  2. Second piece, score 2. A new max. c = exp(1 - 2) = 0.368, so l = 1·0.368 + exp(0) = 1.368.
  3. Score 0. The max stays 2, so c = 1 and l = 1.368 + exp(-2) = 1.503.
  4. Check. By hand, with every score in view, the sum was 1.503. Same answer, and no score was kept.

online scores returns (m, l) after one pass. The starter updates the max but forgets to rescale the sum, so it's only right when the max never rises. Repair it.

Carry the output along too

The sum l is only the bottom of the division. The top is the weighted sum of the values. Keep it the same way, in a running acc that is rescaled by the same c:

acc = acc · c + exp(s - m_new) · v

At the end, the output is acc / l. Here is "bark" again, with values 10, 20 and 30:

  1. Score 1, value 10. acc = 0·0 + 1·10 = 10.
  2. Score 2, value 20. acc = 10·0.3679 + 1·20 = 23.679.
  3. Score 0, value 30. acc = 23.679·1 + 0.1353·30 = 27.739.
  4. Divide. 27.739 / 1.5032 = 18.45, the output you got by hand.

That's a whole row of attention from three numbers of state. When a value is a row of D numbers, acc is a row of D numbers too.

Attention for one row, in one pass

Write attend pairs. Each pair is (score, value) for one key. Return the output for the row: the average of the values, weighted by the softmax of the scores. Go through the pairs once and keep only three numbers: m, l and acc. Do not build a list of scores. The starter returns 0.

The same update with value rows of two numbers

Here it is on two keys with D = 2. Say their scores come out 1 and 2, with v_1 = [1, 0] and v_2 = [0, 1]. Start from m = -inf, l = 0, acc = [0, 0]:

key 1, s = 1:  m_new = 1, c = exp(-inf) = 0
               l = 0·0 + exp(0) = 1
               acc = [0, 0]·0 + 1·[1, 0] = [1, 0]
key 2, s = 2:  m_new = 2, c = exp(1 - 2) = 0.368
               l = 1·0.368 + exp(0) = 1.368
               acc = [1, 0]·0.368 + 1·[0, 1] = [0.368, 1]
end:           o = [0.368, 1] / 1.368 = [0.269, 0.731]

That's exactly the softmax of [1, 2], [0.269, 0.731], weighting the two value rows. Key 1's terms were computed against a max of 1 and fixed up by c once the max became 2.

The kernel: one tile of keys at a time

Now a kernel can skip the table. s_cuda_flash_attention gives each block 64 query rows of one head, one row per thread. The keys and values go past in tiles of 64:

  • Phase 0: thread t loads its query row into qr[t·D + d], and sets its running max mx[t] to -inf. Its running sum l[t] starts at 0, as every alloc does.
  • Then a loop over tiles of keys. Phase 1 copies the tile's keys and values into shared memory. Phase 2 has each thread fold the tile's keys into its row, one at a time, with the update above.
  • Phase 3: O[row] = acc / l.

A score exists for a moment inside one thread, and then it's gone. Nothing S×S is ever stored.

Tiling the keys is what saves global memory traffic. Each tile of keys and values is read from global memory once per block, then used from shared memory by all 64 of the block's query rows, so the block reads K and V once instead of 64 times.

Everything a thread keeps across keys, qr, acc, mx and l, is at t·S + e: per-thread memory, so it lives in registers, with e a literal from the upcast loops.

In s_cuda_flash_attention, D = 32: a query row has 32 numbers, and so does acc. How many floats does one thread keep across keys, counting qr, acc, mx and l?

Two rows of 32 and two single numbers.

32 + 32 + 1 + 1 = 66 floats a thread, all in registers. In shared memory instead, the same kernel takes 1.39 ms for 16 heads, against 0.82 ms in registers, and s_cuda_flash_attention asks for at least 0.8 of the reference's speed.

One thing to know before the lab. Flash attention computes the same softmax as the three-kernel version, but not the same bits: it rescales its sums as it goes, so it rounds at different points. That's fine in .uir, where a program means exactly its own operations. The tests check the flash program's bits against the interpreter running the flash program.

Phase 2's update in .uir, for when you debug the kernel in the lab

The small version of the kernel, c_flash_attention, uses 32 query rows a block and tiles of 32 keys. Here's phase 2's update from it (head size 8), after the scaled dot product %s:

%mnew = max %v112 %s                # %v112 = mx[t]
%v114 = sub %v112 %mnew
%corr = exp %v114
%v115 = sub %s %mnew
%pj = exp %v115
%v116 = mul %v113 %corr             # %v113 = l[t]
%v117 = add %v116 %pj
%v118 = store %v110 %mnew           # mx[t] = mnew
%v119 = store %v111 %v117           # l[t] = l * corr + pj
%d2 = range 8 axis=upcast           # then acc[t*8 + d] = acc[t*8 + d] * corr + pj * V[j][d]
What exact bits cost, and what real kernels do differently

The bits do cost speed. .uir's exp is defined by a fixed, fully specified recipe (week 6): a range reduction, a polynomial and some bit tricks, dozens of operations, and the kernel calls it twice per key. Real kernels use the GPU's fast, approximate exponential instead, and do the two matrix products on tensor cores in 16-bit floats. Neither gives bits a grader can check.

This kernel rescales after every key. The FlashAttention paper rescales once per tile: it computes a whole tile's scores, takes their max, and corrects l and acc once.

The running max is 2 and the running sum is 3. The next score is 4. What happens to the sum before exp(4 - 4) is added?

The old terms are exp(s - 2). What should they be?

They should be exp(s - 4), and exp(s - 2)·exp(2 - 4) = exp(s - 4). The new sum is 3·exp(-2) + 1, about 1.41.

Is float addition associative?

Rescaling as you go changes which roundings happen. Both are softmax to within rounding, but bit for bit they differ, and each test checks a program against itself.

In s_cuda_flash_attention (head size 32), why does the flash kernel keep acc at acc[t·32 + d] with d an upcast loop?

Lesson 9.1.

t·32 + d keeps every thread in its own 32 elements, and the upcast makes each d a literal, so the CUDA compiler can put all 32 in registers. That's the difference between 1.39 and 0.82 ms.
