Week 9 · Lesson 5

Flash attention

Attention is the core of every transformer, and its obvious implementation writes a table of scores that grows with the square of the sequence length. Flash attention never writes it. It streams keys through shared memory and keeps a running softmax in each thread's registers. This lesson derives the trick and walks through the kernel in the tests.

Attention

A head of attention has three S×D matrices: queries Q, keys K and values V, one row per token. For query row i:

s_j = (q_i · k_j) / sqrt(D)          for every key j: a score
p_j = exp(s_j - m) / l               m = the largest s_j, l = the sum of exp(s_j - m): softmax
o_i = sum over j of p_j · v_j        the output row

Subtracting the largest score m changes nothing mathematically and keeps exp from overflowing. A model runs many heads at once: the speed test uses 16.

The obvious way, and its cost

The obvious kernel computes every score into an S×S matrix in global memory, then a softmax pass over each row, then a product with V. At 1,024 tokens one head's scores are 4 MB. They're written, read for the max, read for the sum, read again to normalize into another 4 MB, and read for the product. At 8,192 tokens one head's scores are 256 MB. The arithmetic is cheap next to all that traffic. Measured on the 4060 Ti, 4 heads of 1,024 tokens with D = 32:

kernel (4 heads, 1,024 tokens, D = 32)time
three kernels through an S×S score matrix in global memory2.97 ms
flash attention: one kernel, nothing S×S stored0.33 ms

Our three-kernel version is simple in other ways too: its softmax pass gives each row to one thread. A tuned version would close some of the gap, but not the traffic, which grows with S².

Softmax in one pass

The trouble is the softmax: it needs the largest score before it can add anything up, and the largest isn't known until every score has been seen. The fix is to keep a running max m and a running sum l, relative to the max so far, and correct the sum when the max changes. When a new score s arrives:

m_new = max(m, s)
c     = exp(m - m_new)              the correction: 1 if the max didn't change
l     = l · c + exp(s - m_new)
m     = m_new

Every term already in l was exp(s_old - m). Multiplying by exp(m - m_new) turns it into exp(s_old - m_new), as if the new max had been known all along. Start with m = -inf and l = 0: exp(-inf) is 0, so the first score needs no special case.

The output row works the same way. Keep a running acc, the sum of exp(s_j - m)·v_j, and rescale it by the same c. At the end, o_i = acc / l.

Here it is on two keys with D = 2. Say their scores come out 1 and 2, with v_1 = [1, 0] and v_2 = [0, 1]. Start from m = -inf, l = 0, acc = [0, 0]:

key 1, s = 1:  m_new = 1, c = exp(-inf) = 0
               l = 0·0 + exp(0) = 1
               acc = [0, 0]·0 + 1·[1, 0] = [1, 0]
key 2, s = 2:  m_new = 2, c = exp(1 - 2) = 0.368
               l = 1·0.368 + exp(0) = 1.368
               acc = [1, 0]·0.368 + 1·[0, 1] = [0.368, 1]
end:           o = [0.368, 1] / 1.368 = [0.269, 0.731]

That's exactly the softmax of [1, 2], [0.269, 0.731], weighting the two value rows. Key 1's terms were computed against a max of 1 and fixed up by c once the max became 2.

The kernel in the tests

s_cuda_flash_attention gives each block 64 query rows of one head, one row per thread, and tiles of 64 keys. Its small version, c_flash_attention, uses 32 of each:

  • Phase 0: thread t loads its query row into qr[t·D + d], and sets its running max mx[t] to -inf. Its running sum l[t] starts at 0, as every alloc does.
  • Then a loop over tiles of keys. Phase 1 copies the tile's keys and values into shared memory. Phase 2 has each thread fold the tile's keys into its row, one at a time, with the update above.
  • Phase 3: O[row] = acc / l.

Tiling the keys is what saves global memory traffic. Each tile of keys and values is read from global memory once per block, then used from shared memory by all 64 of the block's query rows, so the block reads K and V once instead of 64 times. This kernel rescales after every key. The FlashAttention paper rescales once per tile: it computes a whole tile's scores, takes their max, and corrects l and acc once.

Here's phase 2's update in .uir, from c_flash_attention (head size 8), after the scaled dot product %s:

%mnew = max %v112 %s                # %v112 = mx[t]
%v114 = sub %v112 %mnew
%corr = exp %v114
%v115 = sub %s %mnew
%pj = exp %v115
%v116 = mul %v113 %corr             # %v113 = l[t]
%v117 = add %v116 %pj
%v118 = store %v110 %mnew           # mx[t] = mnew
%v119 = store %v111 %v117           # l[t] = l * corr + pj
%d2 = range 8 axis=upcast           # then acc[t*8 + d] = acc[t*8 + d] * corr + pj * V[j][d]

Everything a thread keeps across keys, qr, acc, mx and l, is at t·S + e: per-thread memory, so registers, with e a literal from the upcast loops. In s_cuda_flash_attention, with D = 32, that's 66 floats a thread. In shared memory instead, the same kernel takes 1.39 ms for 16 heads, against 0.82 ms in registers, and s_cuda_flash_attention asks for at least 0.8 of the reference's speed.

Same math, different bits

Flash attention computes the same softmax as the three-kernel version, but not the same bits: it rescales its sums as it goes, so it rounds at different points. That's fine in .uir, where a program means exactly its own operations. The tests check the flash program's bits against the interpreter running the flash program.

The bits do cost speed. .uir's exp is defined by a fixed, fully specified recipe (week 6): a range reduction, a polynomial and some bit tricks, dozens of operations, and the kernel calls it twice per key. Real kernels use the GPU's fast, approximate exponential instead, and do the two matrix products on tensor cores in 16-bit floats. Neither gives bits a grader can check.

Check yourself

How many MB is one head's S×S score matrix of f32 at 4,096 tokens? (1 MB = 220 bytes.)

4096 · 4096 · 4 bytes.

4096² · 4 = 226 bytes, 64 MB, per head, before the softmax writes another. Flash attention stores none of it.

The running max is 2 and the running sum is 3. The next score is 4. What happens to the sum before exp(4 - 4) is added?

The old terms are exp(s - 2). What should they be?

They should be exp(s - 4), and exp(s - 2)·exp(2 - 4) = exp(s - 4). The new sum is 3·exp(-2) + 1, about 1.41.

Does flash attention give the same bits as the three-kernel version?

Is float addition associative?

Rescaling as you go changes which roundings happen. Both are softmax to within rounding, but bit for bit they differ, and each test checks a program against itself.

In s_cuda_flash_attention (head size 32), why does the flash kernel keep acc at acc[t·32 + d] with d an upcast loop?

Lesson 9.1.

t·32 + d keeps every thread in its own 32 elements, and the upcast makes each d a literal, so the CUDA compiler can put all 32 in registers. That's the difference between 1.39 and 0.82 ms.
