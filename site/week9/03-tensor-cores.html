Week 9 · Lesson 3

Tensor cores

Since 2017, NVIDIA GPUs have had a second kind of arithmetic unit, built for one job: multiply two small matrices and add the result to a third. A warp asks for a whole 16×16 tile product at once, thousands of multiply-adds, where an ordinary instruction does 32. This lesson adds them to .uir, with an int8 type so the bits still match exactly.

What a tensor core does

Every SM of the 4060 Ti has four tensor cores next to its ordinary float units. The instruction they run is a matrix multiply-accumulate, mma: C = C + A·B, with A, B and C small tiles. It's a warp instruction. The tile is spread across the registers of the warp's 32 threads, called a fragment, and all 32 threads issue it together. In CUDA's wmma interface the tiles we use are 16×16×16, and one mma_sync is 16·16·16 = 4,096 multiply-adds.

The inputs are narrow: 16-bit floats, 8-bit floats, 8-bit integers. Narrow inputs are what make the units small enough to put four per SM, and it's why ML models are so often run in 16 or 8 bits.

Why int8

A float tensor core doesn't round like the interpreter. It multiplies the inputs exactly, but how it adds sixteen products together, how many bits it keeps along the way and how it rounds, is not IEEE arithmetic step by step, and it differs from one GPU generation to the next. A grader that compares bits can't use it.

Integers have no rounding. The product of two 8-bit integers fits in 16 bits, and a sum of them in 32-bit integers is exact as long as it doesn't overflow, in any order. So the tensor cores give exactly the interpreter's answer. That's why .uir's tensor-core op takes i8 inputs and an i32 accumulator. It's also real: int8 matrix multiplies are how many models are served after quantization.

In .uir

Three additions, all in the week 9 spec:

  • i8, a dtype for memory. Buffers and allocs hold it, load and store move it, and cast converts it. To compute, cast to i32. Casting an i32 to i8 keeps the low 8 bits, so 200 becomes -56.
  • mma C A B lda=.. ldb=.. ldc=.., an effect like store. Each operand is memory or a scalar view where a 16×16 tile starts, and lda, ldb, ldc are the tiles' row strides ("ld" is short for leading dimension, the usual name in matrix libraries). It adds A·B into C, in i32, wrapping on overflow like add.
  • axis=warp, a phase run by whole warps: warp w runs iteration w, so a warp loop of 4 makes a block of 128 threads. Inside a kernel, an mma must be in a warp loop, and a store can't be.

Here's a 32×32 product, two blocks of two warps, each warp making one 16×16 tile of C from two tiles of k. The whole program is the test c_mma_from_global:

%g = range 2 axis=global            # block g: rows 16g .. 16g+15 of C
%w = range 2 axis=warp              # warp w: columns 16w .. 16w+15
%ki = range 2                       # two tiles of k
...                                 # C at g*512 + w*16, A at g*512 + ki*256, B at ki*512 + w*256
%m = mma %v4 %v8 %v12 lda=16 ldb=16 ldc=32
%v13 = end %m %ki
%v14 = end %v13 %w
%v15 = end %v14 %g
%C1 = after %C %v15

The race rule of lesson 8.2 holds for warps too, with one extra: an mma writes a whole tile, so its offset gets two more digits, the tile's rows (ldc, up to 15) and its columns (1, up to 15). Here warp w's tile starts at 16w and its rows add up to 15·32: digits 32, 16 and 1, and 32 > 16 + 15, so the two warps' tiles never touch.

Alignment and tile-major order

The tensor cores load a tile from an address that's a multiple of 32 bytes. So the spec requires every term of A's and B's offsets to be a multiple of 32 elements (they're bytes), and every term of C's a multiple of 8 (32 bytes of i32). That rules out the obvious layout. In a row-major int8 matrix, the tile in columns 16 to 31 starts 16 bytes in.

The fix is to store the matrix tile-major: tile after tile, each tile's 256 bytes together. Every tile then starts at a multiple of 256. The example above reads A and B stored that way. The GEMM kernels in the tests read ordinary row-major matrices and rearrange each slice into tile-major order as they copy it into shared memory.

The mma rules

All of these are checked statically, and breaking one exits 2. One example each:

  • Row strides are multiples of 16. lda, ldb and ldc are positive literals: 16, 32, 48 and so on. lda=8 exits 2 (err_mma_lda_not_16).
  • Every tile is in bounds. A tile reaches 15·ld + 16 elements past its offset, so offset + 15·ld + 16 must be at most the memory's size. With lda=32, a tile at offset 0 reaches 496 elements, too many for a 256-element A (err_mma_out_of_bounds).
  • Every offset term is a provable multiple. Of 32 for A and B, of 8 for C. A term is a provable multiple of k when it's a literal divisible by k, an add of two provable multiples, or a mul with at least one factor a provable multiple. Nothing smarter: mul (mul k 2) 16 is a multiple of 32 in fact, but neither factor is, so it exits 2. Write mul k 32. An A offset of 32k + j fails because j isn't one (err_mma_offset_not_provable).
  • The tile is part of the offset expression. Week 8's one-offset-expression rule compares layouts, not just offsets. An mma tile and a plain load or store of the same memory differ even at the same offset, and so do two tiles with different row strides. Two mmas into the same C tile in one kernel, one with ldc=16 and one with ldc=32, exit 2.
  • In a week 7 thread loop, an mma follows the slice rule like a store, with size the whole tile, 15·ld + 16 elements. That covers its C, and its A or B when the loop also writes that memory. With %r = range 2 axis=thread and C at 256r, ldc=16 fills each 256-element slice exactly, and ldc=32 reaches 496 elements and exits 2.

The CUDA

render-cuda turns a warp loop into { int32_t w = threadIdx.x / 32; ... } and a barrier, and an mma into the wmma calls. Here's the example's:

{ wmma::fragment<wmma::matrix_a, 16, 16, 16, signed char, wmma::row_major> fa_; wmma::load_matrix_sync(fa_, b0 + v16, 16);
  wmma::fragment<wmma::matrix_b, 16, 16, 16, signed char, wmma::row_major> fb_; wmma::load_matrix_sync(fb_, b1 + v19, 16);
  wmma::fragment<wmma::accumulator, 16, 16, 16, int> fc_; wmma::load_matrix_sync(fc_, b2 + v11, 32, wmma::mem_row_major);
  wmma::mma_sync(fc_, fa_, fb_, fc_); wmma::store_matrix_sync(b2 + v11, fc_, 32, wmma::mem_row_major); __syncwarp(); }

Load three fragments, multiply, store C. The __syncwarp() makes the warp's stores visible to all its threads before a later iteration loads the same C tile again. The harness includes <mma.h>, and the build passes -arch=native, since int8 tensor cores need an sm_72 or newer GPU. The emulator runs wmma on the CPU: every thread of the warp computes the whole tile, and lane 0 stores it. A lane is a thread's index within its warp, 0 to 31.

How fast?

The test s_cuda_mma_gemm is a 1024×1024 int8 GEMM. A block makes a 64×64 tile of C with 8 warps, and each 32-wide slice of k is copied into shared memory tile-major. On the 4060 Ti:

kernel (1024×1024 int8 GEMM)timespeed
the same kernel, each mma as plain loops split across the warp1.05 ms2.0 TOP/s
the reference, on tensor cores0.34 ms6.3 TOP/s

Three times faster, and still far from what the tensor cores can do. Most of the time goes to moving tiles: every mma loads C from shared memory and stores it back, and the copy phase moves one byte per thread per step. A faster kernel keeps the C fragments in registers for the whole loop over k, and loads 16 bytes per thread at a time. A compiler can spot the first of those: the same C tile, loaded and stored around every iteration of a loop, can be loaded once before it and stored once after. The test asks for half the reference's speed. Without tensor cores you get about a third.

Check yourself

How many multiply-adds does one 16×16×16 mma do?

Each of the 256 elements of C is a dot product of length 16.

16·16·16 = 4096. An ordinary instruction for the same warp does 32.

Why does .uir's mma take i8 inputs, not 16-bit floats?

What has every test since week 1 compared?

How a float tensor core adds its products isn't IEEE arithmetic step by step, and it varies by GPU. Products of i8 values summed in i32 are exact integers, so the GPU gives exactly the interpreter's answer.

A is a row-major 32×32 i8 matrix. Why can't an mma read the tile at rows 0 to 15, columns 16 to 31, straight from it?

Where does that tile's first element sit?

Its first element is element 16. The tensor cores load from 32-byte boundaries, so the spec rejects it. Stored tile-major, every tile starts at a multiple of 256.

Warp w writes the C tile at w·128 with ldc=16, for w in 0..1. Valid?

The digits are 128, 16 and 1. Does 128 beat what the smaller ones add up to?

The tile's rows add up to 15·16 = 240 and its columns 15, so 128 must be more than 255. It isn't: warp 0's rows 8 to 15 are warp 1's rows 0 to 7. That's the test err_warp_tiles_overlap.
