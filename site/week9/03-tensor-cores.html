Week 9 · Lesson 3

Tensor cores

A tensor core is a part of the GPU that multiplies two small 16×16 matrices in a single step. It was built because machine learning is mostly matrix multiply. By the end of this lesson you can write .uir that uses one, with the three things the language needs for it: a small integer type, an op for a whole tile and a loop run by warps.

Goal

Write a .uir program that multiplies 16×16 tiles with mma, and read the CUDA and the C it turns into.

You'll use

Warps of 32 threads from lesson 8.1, the place-value rule from lesson 8.2, phases from lesson 8.3 and the GEMM (matrix multiply) of lesson 9.2.

Warm up

Two questions from week 8, from memory. Pulling an idea back out of your head is what makes it stay.

A block has 96 threads. How many warps is that?

How many threads are in one warp?

A warp is 32 threads that take every step together, and 96 / 32 is 3.

Thread t of block b writes element c·b + t, and t runs from 0 to 15. Which c keeps the blocks from writing the same element?

Place value: the block digit must be worth more than the most t can add.

16 is more than 15, the most t reaches. With 15, block 1 thread 0 and block 0 thread 15 collide.

One step, thousands of multiply-adds

So far, every multiply-add in your kernels was done by one thread, one at a time. A warp of 32 threads gets 32 of them done per step.

A tensor core is a second kind of arithmetic unit, on NVIDIA GPUs since 2017. It takes two 16×16 matrices A and B and a third one C, and computes C = C + A·B in one step. As in week 7, a small piece of a matrix is a tile. In the product, each element of C gets one row of A times one column of B: 16 pairs of numbers, multiplied and added up.

Guess first. C has 16×16 elements, and each one takes 16 multiply-adds. How many multiply-adds is one tile product?

16 · 16 elements, 16 multiply-adds each.

16·16·16 = 4,096, from one instruction.

The instruction is called a matrix multiply-accumulate, or mma. Every SM of the 4060 Ti has four tensor cores. They fit because their inputs are narrow: 16-bit floats, 8-bit floats or 8-bit integers.

To use them, .uir needs three new things.

A small integer type: i8

The tensor cores in this course work on 8-bit integers, so .uir needs a type for them. An i8 is an integer stored in 8 bits. Eight bits make 256 patterns, and an i8 uses them for the numbers -128 to 127.

An i32 holds 200. cast turns it into an i8 by keeping only its low 8 bits. What is the i8?

It wraps around like i32 does, only sooner. One step past 127 is -128.

200 does not fit, so it wraps: 200 - 256 = -56.

i8 is a type for memory. A buffer or alloc can hold it with dtype=i8, load and store move it, and cast converts it. There is no i8 arithmetic: to compute with one, cast it to i32 first. Your compiler's cast needs the wrap from the quiz, so write it now.

Keep the low 8 bits

to_i8(x)to_i8 x should return what an i8 holds after x is cast to it. The starter keeps the low 8 bits with & 255land 255, which gives a number from 0 to 255. Repair it so the answer is always from -128 to 127: 200 becomes -56 and 128 becomes -128.

Why integers: the bits still match

Every test since week 1 compares bits with the interpreter. A float tensor core cannot pass that: how it rounds while adding its 16 products differs from one GPU generation to the next. An integer one also adds in an order you do not control. Does that matter?

Three i32 values are added with wraparound, once as (a + b) + c and once as a + (b + c). Are the two results always the same?

Integers have no rounding. Wrapping only throws away bits above bit 31.

Integer addition is exact, and wrapping drops the same high bits whatever the order. Float addition rounds at each step, so there the order matters.

So mma takes i8 inputs and adds into i32. The products are exact and the sum comes out the same in any order, so the tensor core gives the interpreter's answer, bit for bit. Real models are served this way too: shrinking a model's numbers to 8-bit integers is called quantization.

mma: add a tile product into C

The second new thing is the op itself:

%m = mma %C %A %B lda=16 ldb=16 ldc=16

A and B are i8 memory and C is i32 memory. The ld attributes come in the next section. mma is an effect, like store: it changes memory. For every row i and column j from 0 to 15, it adds row i of A times column j of B into C[i][j]. Here is one element by hand. Row 0 of A starts 2 -1 3, column 0 of B starts 4 5 -2, the other 13 entries of each are 0, and C[0][0] holds 10.

  1. Pair them up. 2·4, -1·5, 3·-2, then 13 pairs with a zero.
  2. Multiply. 8, -5, -6, then zeros.
  3. Add into C. 10 + 8 - 5 - 6 = 7. The old 10 is kept and added to.

Row 3 of A starts 1 2 3 and column 5 of B starts 3 2 1. The rest are zeros. C[3][5] holds -4. What does it hold after the mma?

Three products, then add what C already holds.

1·3 + 2·2 + 3·1 = 10, and -4 + 10 = 6.

A 16×16 tile is 256 elements of memory, row after row. As with a store, after %C %m names the new version of C.

A tile inside a wider matrix

Real matrices are bigger than one tile. Say C has 16 rows and 32 columns, and you want the product in its right half. Step through where that tile sits in memory.

An mma needs two facts for each tile. Where it starts: the operand can be a scalar view such as shrink %C 16 [], and its offset is the tile's first element. And its row stride: how many elements lie between the start of one row of the tile and the start of the next. That is the width of the matrix the tile sits in. lda, ldb and ldc are the row strides of the three tiles. "ld" is short for leading dimension.

A is 64 columns wide. A tile starts at element 32 with lda=64. At which element does row 2 of the tile start?

Row i of the tile starts i · lda elements after the tile's first element.

32 + 2·64 = 160.

Aim a tile at the right half of C

C has 16 rows and 32 columns. A and B are 16×16. The program should add A·B into columns 16 to 31 of C and leave columns 0 to 15 alone. It starts at the right element, but one attribute is wrong. Repair it.

A warp runs it together

In a kernel, a store is run by one thread. An mma cannot be: the 32 threads of a warp hold each tile together in their registers and issue the instruction together. So .uir needs a loop whose iterations are warps, the third new thing:

%w = range 4 axis=warp

Iteration w is run by warp w: the 32 threads whose threadIdx.x / 32 is w.

Guess first. A kernel has the warp loop above. How many threads are in each of its blocks?

Four warps, and you know the size of a warp.

4 · 32 = 128. A warp loop of n makes the block 32n threads.

A warp loop is a phase, like a local loop: it sits inside a global loop and ends with a barrier. Inside a kernel an mma must be in a warp loop, and a store must not be, since there all 32 threads would run it. Here two warps each make one tile of C:

%A  = buffer 512 dtype=i8 slot=0
%B  = buffer 256 dtype=i8 slot=1
%C  = buffer 512 dtype=i32 slot=2
%g  = range 1 axis=global
%w  = range 2 axis=warp
%go = mul %g 512
%wo = mul %w 256
%co = add %go %wo
%cv = shrink %C %co []
%av = shrink %A %wo []
%m  = mma %cv %av %B lda=16 ldb=16 ldc=16
%ew = end %m %w
%eg = end %ew %g
%C1 = after %C %eg

Do the two warps ever write the same element? Use the place-value rule. An mma writes a whole tile, so its offset has two extra digits.

  1. List the digits. w is worth 256 and reaches 1. The tile's row is worth ldc, 16, and reaches 15. Its column is worth 1 and reaches 15.
  2. Check each one. 16 is more than 15. 256 is more than 15·16 + 15 = 255.
  3. Conclude. The tiles sit a whole tile apart, so the program is valid.

What your compiler emits

This is the kernel render-cuda writes for that program:

__global__ void k0(int8_t *__restrict__ b0, int8_t *__restrict__ b1, int32_t *__restrict__ b2) {
  int32_t r7 = blockIdx.x;
  int32_t v8 = (int32_t)((uint32_t)r7 * (uint32_t)512);
  {
    int32_t r9 = threadIdx.x / 32;
    int32_t v10 = (int32_t)((uint32_t)r9 * (uint32_t)256);
    int32_t v11 = (int32_t)((uint32_t)v8 + (uint32_t)v10);
    { wmma::fragment<wmma::matrix_a, 16, 16, 16, signed char, wmma::row_major> fa_; wmma::load_matrix_sync(fa_, b0 + v10, 16);
      wmma::fragment<wmma::matrix_b, 16, 16, 16, signed char, wmma::row_major> fb_; wmma::load_matrix_sync(fb_, b1 + 0, 16);
      wmma::fragment<wmma::accumulator, 16, 16, 16, int> fc_; wmma::load_matrix_sync(fc_, b2 + v11, 16, wmma::mem_row_major);
      wmma::mma_sync(fc_, fa_, fb_, fc_); wmma::store_matrix_sync(b2 + v11, fc_, 16, wmma::mem_row_major); __syncwarp(); }
  }
  __syncthreads();
}

The warp loop became a block that works out its warp number, r9, then a barrier. The mma became calls to wmma, CUDA's interface to the tensor cores. A fragment is a tile held in the warp's registers: load three, multiply, store C. For the CPU, render writes plain loops:

  for (int32_t r9 = 0; r9 < 2; r9++) {
    int32_t v10 = (int32_t)((uint32_t)r9 * (uint32_t)256);
    int32_t v11 = (int32_t)((uint32_t)v8 + (uint32_t)v10);
    for (int32_t i_ = 0; i_ < 16; i_++) for (int32_t j_ = 0; j_ < 16; j_++) {
      uint32_t s_ = (uint32_t)b2[v11 + i_ * 16 + j_];
      for (int32_t k_ = 0; k_ < 16; k_++) s_ += (uint32_t)((int32_t)b0[v10 + i_ * 16 + k_] * (int32_t)b1[0 + k_ * 16 + j_]);
      b2[v11 + i_ * 16 + j_] = (int32_t)s_;
    }
  }

The sum is kept in a uint32_t so that it wraps like add.

In the C above, how many times does the line with s_ += run?

Multiply the four loop bounds.

2 · 16 · 16 · 16 = 8,192. On the GPU that is two mma_sync calls. On a 1024×1024 GEMM the tensor cores make the kernel three times faster.

Now write one yourself. Outside a kernel an mma may sit in a plain loop, as it does here.

Two tiles on the tensor cores

The starter multiplies a 32×16 matrix A by a 16×16 matrix B with three loops, one multiply-add at a time. Replace the triple loop with mma, one tile of C per iteration of a loop of 2.

Where a tile may start

A tensor core loads a tile from an address that is a multiple of 32 bytes. So .uir only accepts an mma when the compiler can prove each tile starts on such a boundary. The exact rules are in the reference section below.

This rules out the obvious layout. In a row-major i8 matrix 32 wide, the tile in columns 16 to 31 starts at byte 16. The fix is to store the matrix tile-major: tile after tile, each tile's 256 bytes together. Step through it.

Where does an element go, tile-major?

A matrix with cols columns is cut into 16×16 tiles. The tiles are stored one after another, left to right and then down, and each tile is row-major inside. Write tile_major row col cols: the offset of element (row, col).

Reference for the lab

You do not need these to finish the page. Open them when you add tensor cores to your own compiler. All of it is in the week 9 spec.

Every i8 rule, for when you add the dtype
  • i8 is 8-bit two's complement, -128 to 127. buffer and alloc take dtype=i8. A literal in a data list is an integer from -128 to 127, and a url= file has one byte per element.
  • load of i8 memory gives an i8 value, and store takes one.
  • cast X dtype=i8 takes an i32 (or an i8, unchanged) and keeps its low 8 bits, so 200 becomes -56. A cast from i8 to i32, f32 or bool is exact. A cast to i8 from f32 or bool is rejected.
  • There are no i8 literals, and arithmetic and comparisons do not take i8: cast to i32 to compute or to assert. Ops that only move values (where, stack, index and the shape ops) take it like any dtype.
  • Only buffer, alloc and cast accept dtype=i8. Any other op given it is rejected, param and bitcast included.
  • For bounds analysis, an i8 load or cast has bounds [-128, 127].
Every mma rule and the test that checks it, for when your compiler must reject a program

C is i32 memory, A and B are i8 memory. Each is a buffer or alloc version, or a scalar view (shrink ... []) whose offset is where the tile starts. The sums are in i32, wrapping on overflow like add. end repeats an mma as it does a store. Like a load, the mma reads the versions of A, B and C it names, so a later store into one of them waits for it.

All of these are checked statically, and breaking one makes the program REJECTED (and makes render and render-cuda exit 2). One example each:

  • Row strides are multiples of 16. lda, ldb and ldc are positive literals: 16, 32, 48 and so on. lda=8 is rejected (rejected_mma_lda_not_16).
  • Every tile is in bounds. A tile reaches 15·ld + 16 elements past its offset, so offset + 15·ld + 16 must be at most the memory's size. With lda=32, a tile at offset 0 reaches 496 elements, too many for a 256-element A (rejected_mma_out_of_bounds).
  • The tile is part of the offset expression. Week 8's one-offset-expression rule compares layouts, not just offsets. An mma tile and a plain load or store of the same memory differ even at the same offset, and so do two tiles with different row strides. Two mmas into the same C tile in one kernel, one with ldc=16 and one with ldc=32, are rejected.
  • In a week 7 thread loop, an mma follows the slice rule like a store, with size the whole tile, 15·ld + 16 elements. That covers its C, and its A or B when the loop also writes that memory. With %r = range 2 axis=thread and C at 256r, ldc=16 fills each 256-element slice exactly, and ldc=32 reaches 496 elements and is rejected.
Alignment and provable multiples: the exact rule for where a tile may start, for when a valid-looking offset is rejected

The tensor cores load a tile from an address that's a multiple of 32 bytes. So the spec requires every term of A's and B's offsets to be a multiple of 32 elements (an i8 element is one byte), and every term of C's a multiple of 8 (32 bytes of i32). In a row-major int8 matrix, the tile in columns 16 to 31 starts 16 bytes in, so it is rejected.

Every offset term is a provable multiple. Of 32 for A and B, of 8 for C. A term is a provable multiple of k when it's a literal divisible by k, an add of two provable multiples, or a mul with at least one factor a provable multiple. Nothing smarter: mul (mul k 2) 16 is a multiple of 32 in fact, but neither factor is, so it's rejected. Write mul k 32. An A offset of 32k + j fails because j isn't one (rejected_mma_offset_not_provable).

Stored tile-major, every tile starts at a multiple of 256. The GEMM kernels in the tests read ordinary row-major matrices and rearrange each slice into tile-major order as they copy it into shared memory.

Every warp rule and a larger example, for when you check kernels with warp loops
  • A warp loop's bound is a literal from 1 to 32. A warp loop of n makes the block 32n threads, and every local and warp loop of one kernel must agree on the block size.
  • A warp loop is inside a global loop. Phases don't nest: no warp or local loop inside a local or warp loop, in either order.
  • Inside a global loop, an mma must be inside a warp loop, and a store must be inside a local loop, not a warp loop.
  • The week 8 rules apply with w as the parallel index. An mma adds two digits to its C offset: ldc with largest value 15 (the row), and 1 with largest value 15 (the column). The same two digits (with lda or ldb) apply to an A or B tile when the same code also writes that memory.
  • ./compile executes a warp loop as an ordinary loop, as always.

Here's a 32×32 product, two blocks of two warps, each warp making one 16×16 tile of C from two tiles of k. The whole program is the test c_mma_from_global:

%g = range 2 axis=global            # block g: rows 16g .. 16g+15 of C
%w = range 2 axis=warp              # warp w: columns 16w .. 16w+15
%ki = range 2                       # two tiles of k
...                                 # C at g*512 + w*16, A at g*512 + ki*256, B at ki*512 + w*256
%m = mma %v4 %v8 %v12 lda=16 ldb=16 ldc=32
%v13 = end %m %ki
%v14 = end %v13 %w
%v15 = end %v14 %g
%C1 = after %C %v15

Here warp w's tile starts at 16w and its rows add up to 15·32: digits 32, 16 and 1, and 32 > 16 + 15, so the two warps' tiles never touch. A and B are stored tile-major.

The CUDA details: headers, barriers and the emulator, for when you write render-cuda

render-cuda turns a warp loop into { int32_t w = threadIdx.x / 32; ... } followed by __syncthreads(), and an mma into the wmma calls. matrix_a and matrix_b fragments are signed char, row_major. The accumulator is int, loaded and stored with mem_row_major. The __syncwarp() makes the warp's stores visible to all its threads before a later iteration loads the same C tile again.

The harness includes <mma.h> and says using namespace nvcuda;, so don't include it yourself. The build passes -arch=native, since int8 tensor cores need an sm_72 or newer GPU. Declare shared memory __shared__ __align__(32), so tiles in it are aligned.

The emulator runs wmma on the CPU: every thread of the warp computes the whole tile, and lane 0 stores it, between two warp barriers. A lane is a thread's index within its warp, 0 to 31. For the CPU, an i8 is an int8_t.

How fast: measured times on the 4060 Ti, for when you tune the lab's GEMM

The test s_cuda_mma_gemm is a 1024×1024 int8 GEMM. A block makes a 64×64 tile of C with 8 warps, and each 32-wide slice of k is copied into shared memory tile-major. On the 4060 Ti:

kernel (1024×1024 int8 GEMM)timespeed
the same kernel, each mma as plain loops split across the warp1.05 ms2.0 TOP/s
the reference, on tensor cores0.34 ms6.3 TOP/s

Three times faster, and still far from what the tensor cores can do. Most of the time goes to moving tiles: every mma loads C from shared memory and stores it back, and the copy phase moves one byte per thread per step. A faster kernel keeps the C fragments in registers for the whole loop over k, and loads 16 bytes per thread at a time. A compiler can spot the first of those: the same C tile, loaded and stored around every iteration of a loop, can be loaded once before it and stored once after. The test asks for half the reference's speed. Without tensor cores you get about a third.

Check yourself

How many multiply-adds does one 16×16×16 mma do?

Each of the 256 elements of C is a dot product of length 16.

16·16·16 = 4096. An ordinary instruction for the same warp does 32.

Why does .uir's mma take i8 inputs, not 16-bit floats?

What has every test since week 1 compared?

How a float tensor core adds its products isn't IEEE arithmetic step by step, and it varies by GPU. Products of i8 values summed in i32 are exact integers, so the GPU gives exactly the interpreter's answer.

A is a row-major 32×32 i8 matrix. Why can't an mma read the tile at rows 0 to 15, columns 16 to 31, straight from it?

Where does that tile's first element sit?

Its first element is element 16. The tensor cores load from 32-byte boundaries, so the spec rejects it. Stored tile-major, every tile starts at a multiple of 256.

Warp w writes the C tile at w·128 with ldc=16, for w in 0..1. Valid?

The digits are 128, 16 and 1. Does 128 beat what the smaller ones add up to?

The tile's rows add up to 15·16 = 240 and its columns 15, so 128 must be more than 255. It isn't: warp 0's rows 8 to 15 are warp 1's rows 0 to 7. That's the test rejected_warp_tiles_overlap.
