Lab: fast GPU kernels

In this lab your compiler learns to make GPU kernels fast. It keeps each thread's sums in registers, reads i8 memory and turns mma and warp loops into tensor-core CUDA. You need no GPU: the emulator runs every kernel and checks every bit.

Goal

Pass all 52 week 9 tests with your own compiler, in the emulator or on a GPU, and write 10 tests of your own.

You'll use

Your compiler from the week 8 lab, and lessons 9.1, 9.2, 9.3, 9.4 and 9.5.

Warm up

Pulling an idea back out of your head is what makes it stay.

A block has 4 threads. Phase 1 stores acc[t·4 + e]. Phase 2 loads acc[((u + 1) mod 4)·4 + e]. May render-cuda give each thread its own private acc?

Lesson 9.1: which elements does thread 0 load in phase 2, and who stored them?

Thread 0 loads elements 4 and 5, which thread 1 stored.

Two warps each run an mma with ldc=16 into one C. Warp w's tile starts at k·w. What is the smallest k your compiler accepts?

Lesson 9.3: the row digit is worth 16 and reaches 15. The column digit is worth 1 and reaches 15.

The smaller digits add up to at most 15·16 + 15 = 255, and k must be more than that.

What you are building

  • compile FILE reads dtype=i8, runs mma, and runs axis=warp as an ordinary loop. It rejects a program that breaks lesson 9.3's rules.
  • compile render FILE prints a warp loop as a plain loop and an mma as loops.
  • compile render-cuda FILE prints an mma as wmma calls, and per-thread memory as a private array in each thread.

The suite has 52 tests: 34 run tests, of which 22 are named rejected_, 2 CPU render tests (r_), 12 CUDA tests (c_) and 4 speed tests (s_cuda_). The contract is spec/uir-week9.md. If this page and the spec disagree, the spec wins.

As in week 8, no rejected_ test has an assert, so printing REJECTED proves nothing. The grader also runs your render on each one and wants exit code 2 and an invalid: line. So run every rule in render too.

How each kind of test is graded this week
  • Run tests check the semantics of i8, mma and warp loops, and every rule. Each rejected_ test breaks exactly one rule, and its first line says which. mma_wraps checks that the sums wrap like add, and per_thread_read_neighbor checks that an alloc read across threads still means shared memory.
  • Render tests (r_) compare your C's buffers with the interpreter. r_mma_reads_before_overwrite checks that your schedule runs an mma before a store that overwrites its A.
  • CUDA tests (c_) run your render-cuda on a GPU or in the emulator and compare every buffer, bit for bit: an int8 GEMM, a register-tiled f32 GEMM, a convolution, flash attention and smaller ones for each rule. c_shared_not_per_thread fails if you put memory in registers that a later phase reads across threads. c_err_mma_outside_kernel is a valid program that is not in kernel form, and render-cuda must exit 2.
  • Speed tests time your CUDA against the reference's on the GPU: s_cuda_gemm_registers (0.8 of its speed or more), s_cuda_mma_gemm (0.5 or more), s_cuda_flash_attention (0.8 or more) and s_cuda_conv3x3 (0.5 or more). The first and third need per-thread memory in registers, and the second needs tensor cores. Without a GPU they only check that your CUDA builds. On a GPU their expected bits come from the reference's C, since the inputs are too big to interpret.

Keep per-thread memory in each thread

This step changes only render-cuda, and only for speed.

  1. Find the candidates. Start from each kernel's shared allocs.
  2. Check every access. Each load and store must be inside a local loop, at t·S + e, with t that loop's range and S one positive literal. Your week 7 slice check must prove 0 ≤ e and e + size ≤ S.
  3. Declare it. For an alloc that passes, print T a[S] = {0}; at the top of the kernel, with no __shared__.
  4. Index by e. Print the offset minus t·S, in uint32_t.
  5. Leave the rest shared. One access outside the pattern keeps the alloc in shared memory.

Add the i8 dtype

i8 is a type for memory: 8 bits, from -128 to 127.

  1. Parse it. Only buffer, alloc and cast take dtype=i8. On any other op it is rejected.
  2. Check the data. A literal in an i8 data list is from -128 to 127.
  3. Cast. A cast to i8 keeps the low 8 bits of an i32, so 200 becomes -56. From f32 or bool it is rejected. A cast from i8 is exact.
  4. Refuse arithmetic. Arithmetic and comparisons reject i8. Ops that only move values, such as where and stack, take it.
  5. Render it. In C and in CUDA an i8 is an int8_t.
Checkpoint 
-k i8    6 / 6 passed
-k run/  26 or more of 34

Stuck? Open the toggle "Every i8 rule" in the reference section of lesson 9.3.

Make mma run

%e = mma %C %A %B lda=16 ldb=16 ldc=16 is an effect, like store.

  1. Parse it. All three strides are required. after and end treat an mma as they treat a store.
  2. Check the operands. C is i32 memory, and A and B are i8 memory. Each is a buffer, an alloc or a scalar view. Each stride is a positive literal multiple of 16.
  3. Check bounds. A tile reaches 15·ld + 16 elements past its offset, all inside the memory.
  4. Check alignment. Every term of the A and B offsets is a provable multiple of 32, and of the C offset a provable multiple of 8.
  5. Execute it. Add 16 products into each C[i][j], in i32 that wraps.
  6. Order it. Wherever your compiler orders memory, an mma is a load of A, B and C and a store into C.
Checkpoint 
-k run/mma_      6 / 6 passed
-k rejected_mma  9 or more of 11
-k run/          30 or more of 34

Three mma rules that are easy to miss, for when a hidden case surprises you
  • Inside a week 7 thread loop, an mma follows the slice rule like a store, with size the whole tile: 15·ld + 16 elements. That covers its C, and its A or B when the loop also writes that memory.
  • Week 8's one-offset-expression rule counts the tile as part of the expression. An mma tile and a plain load or store of the same memory are different layouts even at the same offset, and so are two tiles with different row strides.
  • For bounds analysis, an i8 load or cast has bounds [-128, 127].

Add warp loops

compile FILE runs a warp loop as an ordinary loop. The work is the rules, in render too.

  1. Parse it. range takes axis=warp, with a literal bound from 1 to 32.
  2. Place it. A warp loop is inside a global loop. No warp or local loop sits inside a warp or local loop.
  3. One block size. A warp loop of n means 32n threads. Every local and warp loop of a kernel must agree.
  4. Who runs what. Inside a global loop, an mma must be in a warp loop and a store in a local loop.
  5. Keep warps apart. Run week 8's mixed-radix rule with w as the parallel index. An mma adds two digits to its C offset: ldc reaching 15 and 1 reaching 15.

Render for the CPU

Run -k render/r_. Both tests fail until your C emitter can print an mma.

  1. Print a warp loop. It is a plain for loop, as a local loop is.
  2. Print an mma. Three loops of 16. Read C[i][j] into a uint32_t, add the 16 products to it, then store it back. The uint32_t makes the sum wrap like add.
  3. Schedule it. In r_mma_reads_before_overwrite a store into A comes first in the text, but the mma reads the version before it. Your C must run the mma first.
Checkpoint 
-k render/r_  2 / 2 passed

Print tensor-core CUDA

Start with the smallest test: c_one_warp has one warp loop of 1 and one mma.

  1. Print a warp phase. Like a local phase, with the counter set to threadIdx.x / 32.
  2. Size the block. A warp loop of n launches 32n threads in each block.
  3. Print an mma. Load three wmma fragments, call mma_sync and store_matrix_sync, then __syncwarp();. Do not include <mma.h>: the harness does.
  4. Align shared arrays. Declare each one __shared__ __align__(32).
  5. Keep tiles shared. An alloc that is an mma operand, or is accessed in a warp loop, is never per-thread.
  6. Refuse a stray mma. An mma outside every global loop is not in kernel form, so render-cuda exits 2.

Write your 10 tests

Put 10 tests in <your compiler repo>/tests/week9/, each aimed at a rule someone will get wrong. The first toggle below holds a whole one, rejected_warp_tiles_one_row_close.uir. Its two warps start their C tiles 240 elements apart, so warp 1's tile starts in row 15 of warp 0's. It ends in an assert, so only the rule can make it REJECTED.

Check your tests against the oracle:

python tools/test.py --check-tests <your compiler repo>/tests/week9 --week 9

With only that file there, it prints 1 / 1 tests agree with the oracle.

The sample test, to copy into your tests folder 
%A  = buffer 512 dtype=i8 slot=0
%B  = buffer 256 dtype=i8 slot=1
%C  = buffer 512 dtype=i32 slot=2
%g  = range 1 axis=global
%w  = range 2 axis=warp
%go = mul %g 512
%ao = mul %w 256
%wo = mul %w 240
%co = add %go %wo
%cv = shrink %C %co []
%av = shrink %A %ao []
%m  = mma %cv %av %B lda=16 ldb=16 ldc=16
%ew = end %m %w
%eg = end %ew %g
%C1 = after %C %eg
%z  = shrink %C1 0 []
%l  = load %z
%a  = assert %l 0

Change 240 to 256 and drop rejected_ from the name, and you have its partner, which must MATCH.

Good targets for your tests

Good targets: an mma whose C tile is offset inside a bigger matrix, and the same with an offset one element off alignment. A per-thread alloc with a vector access that just fits its slice. A cast to i8 of a value past 255. A kernel with a local phase, a warp phase and a local phase, sharing one block size.

Check yourself

Your compiler passes every week 9 test in the emulator, but on a GPU s_cuda_gemm_registers and s_cuda_flash_attention fail as too slow. What's the likely cause?

Which two tests need registers?

Both keep each thread's sums in per-thread memory. Correct bits and a slow kernel point at where those sums live. A missing barrier would give wrong bits.

c_shared_not_per_thread fails, and every other test passes. What did your compiler do?

Lesson 9.1, "When an alloc does not qualify".

The rule needs every access, loads included, at t·S + e with e inside the slice. A read of (t + 1)·S + e needs memory the block shares, so the alloc must stay in shared memory.
