Week 9 · Lesson 6

The week 9 lab

Teach your compiler registers and tensor cores. It reads i8, runs mma and warp loops, checks their rules, renders them for the CPU and as wmma calls, and keeps per-thread memory in registers. You're done when every week 9 test passes, in the emulator or on a GPU, weeks 1 to 8 still pass, and you've written 10 tests of your own.

The command-line contract

commandweek 9 changes
your.exe run FILEThe i8 dtype for buffers, allocs and casts, mma as an effect, and axis=warp as a plain loop. New static errors (exit 2): i8 data out of range, i8 literals or arithmetic, dtype=i8 on any op but buffer, alloc and cast (so param and bitcast too), a cast to i8 from f32 or bool, an mma with a bad dtype, stride, alignment or bounds, a warp bound that isn't a literal from 1 to 32, a warp loop outside a global loop, a warp or local loop inside a phase, an mma outside a warp loop or a store inside one in a kernel, block sizes that disagree, and warps whose C tiles overlap.
your.exe render FILEA warp loop is a plain loop. An mma is 256 dot products of length 16, in uint32_t so it wraps. i8 is int8_t.
your.exe render-cuda FILEA warp loop is a phase on threadIdx.x / 32, an mma is wmma calls and __syncwarp(), shared arrays are __align__(32), and per-thread memory is a plain array in each thread.

How the tests are graded

  • Run tests check the semantics of i8, mma and warp loops, and every rule. Each err_ test breaks exactly one rule. mma_wraps checks the sums wrap like add, and per_thread_read_neighbor checks that an alloc read across threads still means shared memory.
  • Render tests (r_) compare your C's buffers with the interpreter. r_mma_reads_before_overwrite checks your schedule runs an mma before a store that overwrites its A.
  • CUDA tests (c_) run your render-cuda on a GPU or in the emulator and compare every buffer, bit for bit: an int8 GEMM, a register-tiled f32 GEMM, a convolution, flash attention, and smaller ones for each rule. c_shared_not_per_thread fails if you put memory in registers that a later phase reads across threads.
  • Speed tests time your CUDA against the reference's on the GPU: s_cuda_gemm_registers (0.8 of its speed), s_cuda_mma_gemm (0.5), s_cuda_flash_attention (0.8) and s_cuda_conv3x3 (0.5). The first and third need per-thread memory in registers, the second needs tensor cores. Without a GPU they only check that your CUDA builds. On a GPU their expected bits come from the reference's C, since the inputs are too big to interpret.

Running the suite

Stuck on a failing test? The week 9 test guide says what each test checks and which bugs make it fail, and the week 9 study guide has a cheat sheet and a step-by-step way out.

python tools/test.py --compiler "C:/path/to/your.exe" --week 9                     # nvcc if it's on PATH, else the emulator
python tools/test.py --compiler "C:/path/to/your.exe" --week 9 --cuda-docker nvidia/cuda:12.6.3-devel-ubuntu22.04
python tools/test.py --compiler "C:/path/to/your.exe" --week 9 -k mma -v           # one group, with details
python _reference/uirc.py render-cuda tests/week9/render/c_mma_from_global.uir      # the reference's CUDA, to compare

Then run weeks 1 to 8 again, one --week at a time. The register GEMM reads the 768×768 matrices of week 7 from data/. The other speed tests fill their inputs in a kernel of their own, so they need no files. Real tensor cores need an sm_72 or newer GPU: an RTX 20-series or newer, or a T4 or better on a notebook or a rented machine. On Kaggle, choose the T4, not the P100. Lesson 8.5 covers where to get one.

Write your 10 tests

Ten tests in path/to/your-repo/tests/week9/, checked with python tools/test.py --check-tests path/to/your-repo/tests/week9. Good targets: an mma whose C tile is offset inside a bigger matrix, and the same with an offset one element off alignment. Two warps whose tiles are exactly a tile apart, and one row closer. A per-thread alloc with a vector access that just fits its slice. A cast to i8 of a value past 255. A kernel with a local phase, a warp phase and a local phase, sharing one block size.

A build order that works

  1. i8

    Parse dtype=i8 on buffers, allocs and casts, check data ranges, wrap on cast, and reject everything else.

    Checkpoint: i8_cast_wraps, i8_to_f32 and the err_i8_* tests pass, and c_i8_kernel passes in the emulator.

  2. mma in run

    Parse it, check dtypes, strides, bounds and alignment, and execute it. Treat it as a load of A, B and C and a store into C everywhere your compiler orders memory: one effect per version, and loads before overwriting stores.

    Checkpoint: the mma_* run tests and err_mma_* pass.

  3. Warp loops

    Accept axis=warp, check where it may be, the block size, and that kernels put mma in warp loops and stores in local loops. Add the tile's two digits to the mixed-radix rule.

    Checkpoint: every run test passes.

  4. Render for the CPU

    Warp loops as plain loops, mma as loops in uint32_t.

    Checkpoint: the r_ tests pass.

  5. render-cuda: tensor cores

    Warp phases on threadIdx.x / 32, mma as wmma, aligned shared arrays.

    Checkpoint: c_mma_from_global, c_one_warp, c_32_warps and c_mma_gemm pass in the emulator.

  6. render-cuda: registers

    Find the per-thread allocs with your week 7 slice check, declare them in each thread, and index them by the offset minus t·S.

    Checkpoint: every c_ test passes in the emulator, including c_shared_not_per_thread.

  7. On a GPU

    Run the suite with nvcc or --cuda-docker. If a speed test fails, compare your CUDA with the reference's: are the sums in a plain array, and is every index into it a literal after unrolling?

    Checkpoint: everything passes on the GPU, including the four speed tests.

Checklist

The AI policy, still

An AI assistant may explain concepts, draw diagrams, and help you debug by asking questions, but must never write or rewrite compiler code. "Why would my flash kernel be slower with the same bits?" is a fine question. "Write my wmma emitter" is not.

Check yourself

Your compiler passes every week 9 test in the emulator, but on a GPU s_cuda_gemm_registers and s_cuda_flash_attention fail as too slow. What's the likely cause?

Which two tests need registers?

Both keep each thread's sums in per-thread memory. Correct bits and a slow kernel point at where those sums live. A missing barrier would give wrong bits.

c_shared_not_per_thread fails, and every other test passes. What did your compiler do?

Lesson 9.1, "When it isn't per-thread".

The rule needs every access, loads included, at t·S + e with e inside the slice. A read of (t + 1)·S + e needs memory the block shares, so the alloc must stay in shared memory.

What does the emulator do with wmma?

The emulator runs wmma on the CPU, so every tensor-core test checks your bits without a GPU. Only timing needs real hardware, and lesson 8.5 shows how to rent some for about a dollar.
