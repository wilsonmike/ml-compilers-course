Week 9 · Lesson 1

Registers and register tiles

Week 8's tiled GEMM multiplies two 768×768 matrices at 1.8 TFLOP/s, on a GPU that peaks near 22. Its threads spend their time reading shared memory, two loads for every multiply-add. This lesson gives each thread a small tile of outputs of its own, keeps their sums in registers, and more than triples the speed. In .uir that takes one new rule and no new syntax.

Where the time goes

In week 8's kernel, each thread owns one element of C. For every step of k it loads one value of A's tile and one of B's tile from shared memory, multiplies them, and adds the product to its sum. Shared memory is fast, but a load still costs more than a multiply-add, and every multiply-add needs two. The arithmetic units wait on the loads.

The fix is reuse. Give each thread a 4×4 piece of C instead of one element. For one step of k, the thread loads 4 values from a column of A's tile and 4 from a row of B's tile, then does all 16 products: every A value meets every B value. That's 16 multiply-adds for 8 loads, four times the work per load.

Where the 16 sums live

The thread now has 16 running sums, so the program needs memory for them: an alloc of 16 per thread, 4096 for a block of 256 threads. Thread t keeps its sums at acc[t·16 + i·4 + j].

By week 8's rule, an alloc used inside one global loop is the block's shared memory. That works, and the bits are right. But each sum is read and written once per step, so the loads we just saved come back as shared-memory traffic for the sums.

The sums belong in registers: each thread has its own, hundreds of them, and using one costs nothing beyond the instruction itself. A register has no address, though, so the CUDA compiler can only keep an array in registers if it knows, when it compiles, which element every access touches.

Per-thread memory

Look at how acc is used. Every access is t·16 + e, where t is the thread and e is between 0 and 15. Thread 3 only ever touches elements 48 to 63. No other thread ever reads or writes them, in any phase. Week 7 had a name for this shape, the thread slice rule r·S + e (lesson 7.4).

So week 9 adds a rule. An alloc of a kernel is per-thread when every load and store of it is inside a local loop, at t·S + e with t that loop's range, one S for all of them, and 0 ≤ e, e + size ≤ S provable. No access may be in a warp loop or be an operand of an mma. Lesson 9.3 adds both: a warp loop is a phase run by whole warps of 32 threads, and an mma is a tensor-core instruction those 32 threads issue together. A warp's threads share those accesses, so they can't be split into per-thread slices. A per-thread alloc means the same as before: it's still shared memory, zero at the start of every block. But since no thread can see another's slice, render-cuda may give each thread its own S elements instead:

  int32_t r14 = blockIdx.x;
  __shared__ __align__(32) float a15[1024];        /* the A tile: shared */
  ...
  float a17[16] = {0};                              /* thread t's 16 sums: per-thread */
  ...
    {
      int32_t r114 = threadIdx.x;
      ...
      for (int32_t r120 = 0; r120 < 16; r120++) {
        ...
        float v132 = a17[(int32_t)((uint32_t)(v130) - (uint32_t)r114 * 16u)];   /* v130 = r114*16 + 0: a17[0] */

Two details make it registers rather than an array in memory. The offset minus t·S is e, and computing it in uint32_t lets the CUDA compiler cancel the t·S terms exactly. And e must be a literal in each copy, which an upcast loop does: i and j are unrolled, so the 16 accesses are a17[0] to a17[15]. With a plain loop index in e, the array still works but lives in slower local memory. That's CUDA's name for memory private to one thread that actually sits in the GPU's DRAM, behind the caches. It has nothing to do with axis=local.

When it isn't per-thread

A later phase may read anything an earlier phase wrote to shared memory. If phase 2 reads acc[(t + 1)·16 + e], thread t reads its neighbor's sums, and that only works if they're in memory the whole block shares. The access isn't t·S + e, so the rule says no, and the alloc stays shared. The test c_shared_not_per_thread is exactly that case: a compiler that keeps it in registers gets wrong bits.

Check yourself

A thread computes a 4×4 tile of C. Per step of k it does 16 multiply-adds. How many multiply-adds is that per shared-memory load?

How many values does it load per step?

It loads 4 values of A and 4 of B, 8 loads, for 16 multiply-adds: 2 per load. One output per thread gives half a multiply-add per load.

Phase 1 stores acc[t·8 + e] for e in 0..7, and phase 2 loads acc[t·8 + 7 - e] for e in 0..7. Is acc per-thread?

The rule is about whose slice, not which element of it.

7 - e is between 0 and 7, so every access is inside thread t's elements 8t to 8t + 7. Reversing within your own slice is fine. Upcast loops decide whether it becomes registers, not whether it's per-thread.

Does the rule change what the program means?

Per-thread memory means exactly what shared memory means. Keeping it shared is correct, just slow, and only a GPU can tell. It's one of the bugs planted in the reference, and only the speed tests catch it.

The 16 sums are per-thread, but the loops over i and j are plain loops, not upcast. Where does the CUDA compiler put the array?

Can you index a register with a variable?

Registers are named by the instruction, not computed. A loop the compiler fully unrolls can still end up in registers, but an upcast loop makes it certain, and that's why the reference's kernels unroll the loops over a thread's own tile.
