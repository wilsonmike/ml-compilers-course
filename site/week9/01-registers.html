Week 9 · Lesson 1

Registers and register tiles

Your GPU kernels from week 8 give the right bits. Week 9, the last week, makes them fast, with two ideas: registers, which keep a thread's working numbers inside the thread, and tensor cores, units that multiply small matrices in one step. This lesson is the first: each thread makes a small patch of outputs and keeps their sums in registers.

Goal

Count the shared-memory reads a kernel makes, and decide which allocs are per-thread memory that render-cuda may keep in registers.

You'll use

Registers and upcast loops from lesson 7.3, the slice rule from lesson 7.4, shared memory and phases from lesson 8.3 and rendered CUDA from lesson 8.4.

Warm up

Two questions from weeks 7 and 8, from memory. Pulling an idea back out of your head is what makes it stay.

On the CPU, the C compiler could keep the sums acc[0] to acc[3] in registers only after the loop was unrolled with upcast (lesson 7.3). Why not before?

Is there a machine instruction for "register number r7"?

An instruction names its registers outright. After unrolling, every index is a literal, so each element can get a register of its own.

Every load and store of an alloc is inside one global loop (lesson 8.3). What is that alloc, and who can read it?

Phase 2 of the reverse read slots that other threads had written.

Any thread of the block may read any element of it. This lesson has to rule that out before memory can move into registers.

Count the reads in week 8's kernel

On the 768×768 GEMM from week 7, week 8's kernel reaches 1.8 TFLOP/s (trillion float operations a second), on a GPU that peaks near 22. Count what it does.

A block copies a tile of A and a tile of B into shared memory. Each thread owns one element of C. For every step of k, the thread reads one value of A's tile and one of B's tile, multiplies them and adds the product to its sum. One multiply and one add together are a multiply-add.

How many shared-memory reads does that thread make for each multiply-add?

Which numbers does one multiply need?

One value of A and one of B, for every multiply-add in the kernel.

A shared-memory read costs more than the multiply-add it feeds, so the arithmetic units wait on the reads. And the thread next door reads the very same A value, to multiply it by a different B value. Every number is read again for each use.

Let one thread make a 4×4 patch

The fix is reuse. Give each thread a 4×4 patch of C, 16 outputs, where it had one. For one step of k, those 16 outputs need only 4 values of A, one for each row of the patch, and 4 values of B, one for each column.

The thread reads those 4 A values and 4 B values, then multiplies every A value by every B value. In how many multiply-adds is each number it read used?

Pick one A value. How many B values does it meet?

Each A value meets all 4 B values, and each B value all 4 A values. In week 8's kernel every number was used once.

One step of k for the patch:

  1. Read. 4 values of A and 4 of B: 8 reads from shared memory.
  2. Multiply. Every A value times every B value: 16 products.
  3. Add. Each product goes into its own running sum: 16 multiply-adds.

That is half a read for each multiply-add. Week 8's kernel needed 2, four times as many. Such a patch is called a register tile. Step through it.

Where the 16 sums go

The thread now has 16 running sums, and the program needs memory for them: an alloc of 16 for each thread, 4096 for a block of 256 threads. Thread t keeps sum (i, j) at acc[t·16 + i·4 + j].

By week 8's rule, an alloc used inside one global loop is the block's shared memory.

Every multiply-add loads its sum from acc, adds the product and stores the sum back. With acc in shared memory, how many shared-memory accesses does each multiply-add make for its sum alone?

Count the load and the store.

One load and one store. The patch cut the reads of A and B to half a read for each multiply-add, and the sums put two accesses back.

The traffic we saved came back. The sums belong in registers, as in lesson 7.3. A GPU thread has up to 255 of its own, and using one costs nothing beyond the instruction itself.

But any thread of a block may read any element of shared memory. Before acc can leave it, the compiler must know that no thread ever looks at another thread's sums.

Per-thread memory

Here are two allocs. Both are shared memory by week 8's rule.

  • sh, from lesson 8.3's reverse: phase 1 stores sh[t], and phase 2 loads sh[7 - u].
  • acc, the sums: every load and store, in every phase, is at acc[t·16 + e] with e from 0 to 15.

Which alloc could be swapped for a small private array inside each thread, with no thread able to tell?

Does a thread ever read an element that another thread wrote?

In sh, thread 0 reads slot 7, which thread 7 wrote. In acc, thread 3 only ever touches elements 48 to 63, and no other thread does.

Lesson 7.4's slice rule named this shape: t·S picks slice t, and e picks a place inside it. Week 9 builds one new rule on it. An alloc of a kernel is per-thread when every load and store of it passes three checks:

  1. It is inside a local loop. t is that loop's range, the thread number.
  2. Its offset is t·S + e. S is a positive literal, the same one for every access.
  3. It stays in the slice. 0 ≤ e and e + size ≤ S can be proved, where size is how many elements the access touches.

Then thread t only ever touches elements t·S to t·S + S - 1, in every phase. The program means what it meant before: the alloc is still shared memory, zero at the start of every block. The rule is a permission. render-cuda may give each thread its own array of S elements.

Does the access stay in its slice?

Thread t owns elements t·s to t·s + s - 1. owns s t off size should say whether an access that starts at element off and touches size elements stays inside them. The starter forgets how far the access reaches. Repair it.

The whole rule, with warp loops and mma, for when you write the check in the lab

An alloc of a kernel is per-thread when every load and store of it is inside a local loop, at t·S + e with t that loop's range, one S for all of them, and 0 ≤ e, e + size ≤ S provable. As in week 7, a bare t counts as S = 1.

No access may be in a warp loop or be an operand of an mma. Lesson 9.3 adds both: a warp loop is a phase run by whole warps of 32 threads, and an mma is a tensor-core instruction those 32 threads issue together. A warp's threads share those accesses, so they can't be split into per-thread slices.

In render-cuda, per-thread memory may be a plain array in each thread, T a[S] = {0}; at the top of the kernel, indexed by e.

When an alloc does not qualify

One access outside the pattern loses the permission. Recall lesson 8.3: a later phase may read anything an earlier phase wrote to shared memory.

A block has 4 threads. Phase 1 stores acc[t·4 + e]. Phase 2 loads acc[((u + 1) mod 4)·4 + e]. In both, e is 0 or 1. Is acc per-thread?

Thread 0 is in phase 2. Which elements does it load, and who stored them?

Thread 0 loads elements 4 and 5, which thread 1 stored. The offset is not u·S + e, so the alloc stays in shared memory. Unused room in a slice is fine.

That program is the test c_shared_not_per_thread. A private array there gives wrong bits. So the check has to see every access before it says yes. Write it.

Can it live in registers?

Each access to one alloc is (s, lo, hi, size): its offset is t·S + e with e in [lo, hi], and it touches size elements. s is Some S, or None when the offset lacks that form. Write per_thread accesses: S when every access has the same positive S and stays in its slice, otherwise 0. An empty list gives 0. The starter trusts the first access.

What render-cuda prints

Here is a small kernel: 2 blocks of 4 threads, where each thread keeps 2 sums at acc[t·2 + e]. This is what the reference compiler's render-cuda prints for the top of the kernel, up to the first load of a sum:

__global__ void k0(int32_t *__restrict__ b0, int32_t *__restrict__ b1) {
  int32_t r5 = blockIdx.x;
  int32_t a6[2] = {0};
  int32_t v7 = (int32_t)((uint32_t)r5 * (uint32_t)8);
  {
    int32_t r8 = threadIdx.x;
    int32_t v9 = (int32_t)((uint32_t)r8 * (uint32_t)2);
    int32_t v10 = (int32_t)((uint32_t)v9 + (uint32_t)0);
    int32_t v12 = a6[(int32_t)((uint32_t)(v10) - (uint32_t)r8 * 2u)];
    ...
  1. The array. int32_t a6[2] = {0}; is a plain array of S = 2 elements, zeroed at the top of the kernel. It has no __shared__, so every thread gets its own.
  2. The index. The program's offset is t·2 + e, but the private array is indexed by e alone. So the renderer prints the offset minus t·2.

v10 is r8·2 + 0. For thread 3, which element of a6 does a6[v10 - r8·2] touch?

r8 is the thread number, 3. Work out v10 first.

6 - 6 = 0, for every thread. The subtraction is done in uint32_t, where the two r8·2 terms cancel exactly, so the CUDA compiler can see the literal 0. The copy for e = 1 gives a6[1].

Change phase 2 so that it reads the next thread's slice, and the rule says no. The same renderer then prints week 8's form, __shared__ __align__(32) int32_t a7[8];, and indexes it with the full offset: a7[v11].

Literal indexes make it registers

A private array is not yet a register. In the kernel above, e comes from an upcast loop. Each copy of the body has a literal e, so the indexes work out to a6[0] and a6[1], and the CUDA compiler keeps those two elements in registers.

Here is the start of the same phase with a plain loop for e:

    for (int32_t r10 = 0; r10 < 2; r10++) {
      int32_t v11 = (int32_t)((uint32_t)v9 + (uint32_t)r10);
      int32_t v13 = a6[(int32_t)((uint32_t)(v11) - (uint32_t)r8 * 2u)];
      ...

The index now works out to r10, the loop counter. What can the CUDA compiler count on doing with a6?

It is the first warm up question again, on a GPU.

The bits are still right, but the array may sit in memory. An upcast loop does not leave it to chance.

That private memory is called local memory: CUDA's name for memory that belongs to one thread but sits in the GPU's DRAM, behind the caches. It is far slower than a register, and it has nothing to do with axis=local.

The fast GEMM needs both pieces. The per-thread rule makes the 16 sums private, and upcast loops over i and j of the 4×4 patch make their indexes the literals 0 to 15. Here is what that bought on the 768×768 GEMM from week 7, measured on the RTX 4060 Ti this course was written on:

The second row also grows the block's tile, which lesson 9.2 explains. The third row changes only where the sums live, and it is about 1.5 times faster.

The last kernel is the reference for the speed test s_cuda_gemm_registers, which asks for at least 0.8 of its speed. Sums in shared memory give about 0.67, so the test fails without this lesson's rule.

The tests for per-thread memory, for when you do the lab
  • c_per_thread_fresh_each_block: per-thread memory starts at zero in every block, in registers or not.
  • c_per_thread_plain_loop: a per-thread alloc indexed by a plain loop. It may not fit in registers, but the bits are the same.
  • c_shared_not_per_thread: phase 2 reads the next thread's slice, so the alloc must stay shared.
  • c_regtile_gemm: a small GEMM with 4×4 register tiles, checked for bits.
  • s_cuda_gemm_registers: the 768×768 speed test. Without a GPU it only checks that your CUDA builds.

Check yourself

A thread computes a 4×4 tile of C. Per step of k it does 16 multiply-adds. How many multiply-adds is that per shared-memory load?

How many values does it load per step?

It loads 4 values of A and 4 of B, 8 loads, for 16 multiply-adds: 2 per load. One output per thread gives half a multiply-add per load.

Phase 1 stores acc[t·8 + e] for e in 0..7, and phase 2 loads acc[t·8 + 7 - e] for e in 0..7. Is acc per-thread?

The rule is about whose slice, not which element of it.

7 - e is between 0 and 7, so every access is inside thread t's elements 8t to 8t + 7. Reversing within your own slice is fine. Upcast loops decide whether it becomes registers, not whether it's per-thread.

Your render-cuda keeps a per-thread alloc in shared memory, as week 8 did. What happens?

Does the rule change what the program means?

Per-thread memory means exactly what shared memory means. Keeping it shared is correct, just slow, and only a GPU can tell. It's one of the bugs planted in the reference, and only the speed tests catch it.

The 16 sums are per-thread, but the loops over i and j are plain loops, not upcast. Where does the CUDA compiler put the array?

Can you index a register with a variable?

Registers are named by the instruction, not computed. A loop the compiler fully unrolls can still end up in registers, but an upcast loop makes it certain, and that's why the reference's kernels unroll the loops over a thread's own tile.
