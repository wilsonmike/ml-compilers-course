Convolutions

You spent two weeks making matrix multiply fast. A convolution is the other operation image models spend their time in. This lesson shows that a convolution is a matrix multiply in disguise, so your fast GEMM already covers it, and then how real kernels avoid the one cost of that disguise.

Goal

Turn a convolution into a matrix multiply, count what that costs in memory, and say how implicit GEMM and a direct kernel avoid the cost.

You'll use

The window sum from lesson 3.4 and its movement op form from lesson 5.4. Shared memory tiles and sums in registers from lesson 9.1 and lesson 9.2, and tensor cores from lesson 9.3.

Warm up

Two ideas from earlier lessons that this one joins together. Pulling an idea back out of your head is what makes it stay.

From lesson 3.4: x = [2 2 2 8 8 8] and the kernel is w = [-1 0 1]. What is y[2] = x[2]*w[0] + x[3]*w[1] + x[4]*w[2]?

The window is x[2], x[3], x[4], which is 2, 8, 8.

2*(-1) + 8*0 + 8*1 = 6. One window, times the kernel, summed.

In a matrix multiply, each output is one row times one column, summed. What is row [1 2 3] times column [4 5 6]?

Multiply the pairs in order, then add the three products.

1*4 + 2*5 + 3*6 = 32. A GEMM is nothing but sums like this one.

Do you have to start over?

Your GEMM kernel now copies tiles into shared memory, keeps its sums in registers and can run on tensor cores. A convolution looks like a different loop nest: a window sliding over an image.

Guess first. To make a convolution fast on the GPU, how much of weeks 8 and 9 do you have to redo?

Look at the two warm up answers. Both are a list of numbers times a list of weights, summed.

Each output of a convolution is a window times the kernel, summed. Each output of a matrix multiply is a row times a column, summed. Make every window a row and they are the same thing.

So the answer is no. The rest of this lesson is three ideas: the rewrite, what the rewrite costs and how fast kernels keep the rewrite but skip the cost.

Lay each window out as a row

Take the warm up's x = [2 2 2 8 8 8] and w = [-1 0 1].

  1. Cut out the windows. Six numbers hold four windows of three: [2 2 2], [2 2 8], [2 8 8] and [8 8 8].
  2. Stack them as rows. That gives a matrix M with 4 rows and 3 columns.
  3. Multiply by the kernel. Row i of M times w is exactly y[i]. So M·w = [0 6 6 0], the whole convolution.

Laying each window out as a row of a matrix is called im2col, short for image to columns. Step through it:

A row of 10 numbers and a 3-tap kernel. How many rows does the im2col matrix have?

One row per window. The last window starts at x[7].

10 - 3 + 1 = 8 windows, starting at x[0] through x[7]. Each is a row of 3.

Lay the windows out as rows

im2col x k should return one row per window of x: row i holds the k numbers starting at x.(i). The code is nearly right, but every row comes out the same. Fix the one index that is wrong.

The same rewrite on an image

A real convolution has more of everything. The input is an image with C channels, X[c][y][x]. A filter is a 3×3 window of weights for every input channel, and there are K filters, W[k][c][dy][dx]. Output channel k at pixel (y, x) is the sum, over all channels and the 3×3 window, of input times weight:

Y[k][y][x] = sum over c, dy, dx of  X[c][y + dy][x + dx] · W[k][c][dy][dx]

Near the edge the window hangs over, so the input gets a border of zeros, one pixel wide. The tests' inputs come already padded: an H×W output reads an (H+2)×(W+2) input.

The rewrite is the same three steps:

  1. Cut out the windows. One per output pixel: its 9 input values from every channel, C·9 numbers.
  2. Stack them as rows. All H·W pixels give an (H·W) × (C·9) matrix, the patch matrix.
  3. Multiply by the filters. Lay the filters out as a (C·9) × K matrix, one column per filter. The product is an (H·W) × K matrix whose row (y, x) holds every output channel at that pixel.

That product is a GEMM, so block tiles, register tiles and tensor cores all apply. The speed test has 32 input channels, 64 output channels and an image of H = 256 rows by W = 64 columns. That is K·H·W·C·9 multiply-adds, 302 million.

The letters

The letters here are the convolution's own. C counts channels, not the GEMM's output matrix. K counts filters, not attention's keys or a GEMM's k loop. W is both the weights and the image's width.

The speed test has 32 input channels and 3×3 filters. How long is each row of its patch matrix?

One row is one pixel's whole window: 9 values from each channel.

32·9 = 288. With 256·64 = 16,384 output pixels, the patch matrix is 16,384 × 288 and the filter matrix is 288 × 64.

The cost: every number, many times

Here is a 3×3 image, values 1 to 9, padded with zeros. It has 9 output pixels, so its patch matrix has 9 rows. Before you step through, count.

The value 5 sits in the center of the image. How many of the 9 windows contain it, so how many times does im2col copy it?

A 3×3 window centered on any of the 9 pixels reaches the center.

All 9. Windows overlap, so im2col stores a value once for each window that covers it, up to 9 times for a 3×3 filter. A corner value such as 1 is in 4 windows.

At full size this adds up. The speed test's padded input X is 544,896 floats. Its patch matrix would be 16,384 × 288 = 4,718,592 floats, almost 9 times as much. Lesson 9.2 showed that a kernel is limited by its arithmetic or by its memory traffic. Writing the patch matrix out and reading it back is traffic the convolution itself never needed.

Compute the address, skip the copy

A fast GEMM never reads its input matrix whole. It copies one tile at a time into shared memory. So the patch matrix never has to exist: when the kernel wants element (row, col) of it, compute where that number lives in the image and read it from there. That is implicit GEMM. Many library convolutions work this way, on tensor cores.

For one channel and outputs W wide:

  1. Split the row into a pixel. y = row div W and x = row mod W.
  2. Split the column into a tap. dy = col div 3 and dx = col mod 3.
  3. Add them. The number is input (y + dy, x + dx), at offset (y + dy)·(W + 2) + x + dx in the padded image.

Where does a patch element live?

A one-channel image has outputs w pixels wide, so its padded input is w + 2 wide and stored row-major. Write patch_addr row col w: the offset in the padded input of element (row, col) of the patch matrix. Row y*w + x is output pixel (y, x), and column dy*3 + dx is tap (dy, dx) of the 3×3 window.

The address with channels, and where the name im2col comes from

With C channels a column is c·9 + dy·3 + dx, so first c = col div 9, then split the remainder into dy and dx. A channel of the padded image is (H+2)·(W+2) elements, so the offset gains a term c·(H+2)·(W+2).

The first im2col routines stacked each window as a column, not a row, which is where "image to columns" comes from. Rows or columns, it is the same matrix turned on its side.

The kernel in the tests

c_conv3x3 and s_cuda_conv3x3 use a simpler direct kernel. It has no patch matrix at all, stored or implicit, and keeps the same two ideas from the GEMM: stage inputs in shared memory, keep sums in registers.

  • A block makes one output row y for 8 output channels. Thread x makes those 8 outputs at pixel (y, x).
  • The block copies the input rows it needs, from every channel, and its 8 filters into shared memory.
  • Each thread then adds into 8 sums of its own, which live in registers.

The overlap that made im2col expensive now pays off. Each input value in shared memory is read by up to 3 threads (the window's 3 columns), and each read serves all 8 output channels. Each weight is read by every thread of the block.

A block makes output row y with 3×3 windows. How many rows of each input channel must it copy into shared memory?

The window reads rows y + dy for every dy.

Three: padded rows y to y + 2. In the speed test that is 32·3·66 = 6,336 floats of input per block.

The kernel's three phases, for when you read the test in the lab
  • Phase 1 copies the three input rows the block needs, y to y + 2 of every channel, and the 8 filters into shared memory. Every thread copies a few elements, chosen so neighboring threads read neighboring addresses.
  • Phase 2 loops over the channels, and for each channel over the 3×3 window and the 8 output channels, with the last three loops upcast. Each thread adds into its 8 sums at acc[x·8 + o], a per-thread alloc, so they live in registers.
  • Phase 3 writes the 8 outputs.

In s_cuda_conv3x3 there are 2,048 blocks of 64 threads: 8 groups of output channels times 256 rows. The shared allocs are 6,336 floats of input rows and 8·288 = 2,304 floats of filters, and acc is 64·8 = 512.

Not every kernel is limited by the same thing

On the 4060 Ti the speed test's convolution takes 0.41 ms, 1.5 TFLOP/s. That is with its 8 sums in registers. In lesson 9.1, moving the GEMM's sums from shared memory into registers made it 1.5 times faster.

Guess first. Put the convolution's 8 sums back in shared memory. How long does it take now?

Registers only help a kernel that is waiting on its sums.

0.42 ms against 0.41 ms. Unlike the GEMM, this kernel isn't waiting on its sums.

Its blocks are small (64 threads), and its copy phase computes a div and a mod per element it moves, the same kind of address arithmetic you just wrote. Before you optimize a kernel, find out what it's waiting for. Making the wrong part faster changes nothing. The speed test asks for half the reference's speed.

The convolution as a GEMM multiplies the im2col matrix by the filter matrix. What shape is the result?

Rows come from the first matrix, columns from the second.

The im2col matrix is (H·W) × (C·9) and the filters (C·9) × K, so the product is (H·W) × K: every output channel at every pixel.

Why do fast libraries avoid writing the im2col matrix to memory?

How many windows cover one input pixel?

With 3×3 windows, an input pixel is in up to 9 of them, so im2col is up to 9 times the size of the image. Implicit GEMM computes those addresses while loading tiles instead.
