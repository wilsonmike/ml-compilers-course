Convolutions

A convolution slides a small filter over an image. Image models from LeNet to ResNet are mostly convolutions, and on a GPU they're computed the same way as a GEMM: tiles in shared memory, sums in registers. This lesson shows why a convolution is a GEMM in disguise, and walks through the kernel in the tests.

What a convolution computes

The input is an image with C channels, X[c][y][x]. A filter is a 3×3 window of weights for every input channel, and there are K filters, W[k][c][dy][dx]. Output channel k at pixel (y, x) is the sum, over all channels and the 3×3 window, of input times weight:

Y[k][y][x] = sum over c, dy, dx of  X[c][y + dy][x + dx] · W[k][c][dy][dx]

Near the edge the window hangs over, so the input gets a border of zeros, one pixel wide. The tests' inputs come already padded: an H×W output reads an (H+2)×(W+2) input. That's K·H·W·C·9 multiply-adds: for the speed test's 32 input channels, 64 output channels and an image of H = 256 rows by W = 64 columns, 302 million.

The letters here are the convolution's own. C counts channels, not the GEMM's output matrix, K counts filters, not attention's keys or a GEMM's k loop, and W is both the weights and the image's width.

A GEMM in disguise

Write each output pixel's window out as a row: its 9 input values from every channel, C·9 numbers. Stack the rows of all H·W pixels into a matrix. That's called im2col, image to columns. Lay the filters out as a C·9 × K matrix. Then the convolution is exactly their product, an (H·W) × K matrix whose row (y, x) holds every output channel at that pixel.

So everything about fast GEMMs applies. The catch is that im2col copies every input value up to 9 times, once into each window that covers it. Writing that matrix out to memory costs more than the convolution saves. The fast way is implicit GEMM: run a GEMM kernel, but when it copies a tile of the patch matrix into shared memory, compute where each element comes from in the image, and never store the big matrix at all. Many library convolutions work this way, on tensor cores.

The kernel in the tests

c_conv3x3 and s_cuda_conv3x3 use a simpler direct kernel, with the same ideas:

  • A block makes one output row y for 8 output channels. Thread x makes those 8 outputs at pixel (y, x).
  • Phase 1 copies the three input rows the block needs, y to y + 2 of every channel, and the 8 filters into shared memory. Every thread copies a few elements, chosen so neighboring threads read neighboring addresses.
  • Phase 2 loops over the channels, and for each channel over the 3×3 window and the 8 output channels, the last three loops upcast. Each thread adds into its 8 sums at acc[x·8 + o], a per-thread alloc, so they're registers.
  • Phase 3 writes the 8 outputs.

Each input value in shared memory is read by up to 3 threads (the window's 3 columns), and each read serves all 8 output channels. Each weight is read by every thread of the block.

Not every kernel is limited by the same thing

On the 4060 Ti the speed test's convolution takes 0.41 ms, 1.5 TFLOP/s. Keeping the 8 sums in shared memory instead of registers makes almost no difference: 0.42 ms. Unlike the GEMM, this kernel isn't waiting on its sums. Its blocks are small (64 threads), and its copy phase computes a div and a mod per element it moves. Before you optimize a kernel, find out what it's waiting for. Making the wrong part faster changes nothing. The speed test asks for half the reference's speed.

Check yourself

An image has 2 channels, and the filters are 3×3. How long is each row of the im2col matrix?

One row is one output pixel's whole window, across all channels.

2·9 = 18: the 9 values of the window in each of the 2 channels.

The convolution as a GEMM multiplies the im2col matrix by the filter matrix. What shape is the result?

Rows come from the first matrix, columns from the second.

The im2col matrix is (H·W) × (C·9) and the filters (C·9) × K, so the product is (H·W) × K: every output channel at every pixel.

Why do fast libraries avoid writing the im2col matrix to memory?

How many windows cover one input pixel?

With 3×3 windows, an input pixel is in up to 9 of them, so im2col is up to 9 times the size of the image. Implicit GEMM computes those addresses while loading tiles instead.

Moving the convolution's sums from shared memory to registers barely changes its speed, but for the GEMM it was 1.5 times. Why?

"Not every kernel is limited by the same thing".

Speeding up a part that isn't the bottleneck doesn't speed up the kernel. Measure first, then optimize what it's actually waiting on.
