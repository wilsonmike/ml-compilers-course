Week 9 · Lesson 2

Fast GEMMs

A GEMM is the kernel every ML compiler is judged by, and the fast ones all follow one plan: move each value as few times as possible through each level of memory. This lesson is that plan as numbers you can check, and the handful of GPU details that decide how close a kernel gets to the hardware's peak.

A ladder of memories

A multiply-add needs its two inputs in registers. They start in global memory. On the way they can stop in two places: the L2 cache, which the whole GPU shares (32 MB on the 4060 Ti), and a block's shared memory. Each step up the ladder is faster and smaller:

Reuse, as a number

Take a block tile of BM×BN outputs. For each slice of k it loads a BM×BK tile of A and a BK×BN tile of B, and does BM·BN·BK multiply-adds with them. So it does BM·BN / (BM + BN) multiply-adds for every value it loads. The same count works one level down, for a thread's TM×TN tile reading shared memory.

The roofline

A kernel can't be faster than its arithmetic alone, or than its memory traffic alone. That bound is called the roofline: time is at least the larger of the two. A 768×768 GEMM is 2·768³, about 0.9 billion float operations, which takes at least 41 µs at 22 TFLOP/s. Reading A and B once is 4.7 MB, at least 16 µs at 288 GB/s. So this GEMM is limited by arithmetic, if the kernel reads each value only a few times.

Week 8's 16×16 tiles read A and B 48 times over, 226 MB in all. Straight from global memory that alone would take 0.8 ms, longer than the kernel's measured 0.51 ms. It's faster because A and B fit in the L2 cache, so most of those reads never reach global memory. With 64×64 tiles the traffic drops to 57 MB. Big tiles matter even when the L2 catches everything: L2 has a bandwidth limit of its own, and every load is an instruction the SM has to issue.

Coalescing

A warp's 32 loads go to memory together. When neighboring threads read neighboring addresses, the hardware combines them into a few wide transactions of 32 bytes each. When they read addresses far apart, every thread costs its own transaction, most of whose bytes are thrown away.

That's why the copy phase of the register-tiled GEMM picks its element as q·256 + t, where q from 0 to 3 counts the copies each of the 256 threads makes, and maps it to row q·16 + t / 16, column t mod 16: 16 neighboring threads read 16 neighboring floats of one row of A. Had thread t copied row t instead, a warp would touch 32 different rows.

Occupancy

A load from global memory takes hundreds of cycles. An SM hides that by keeping many warps on hand and running whichever is ready. How many it can hold depends on what each block uses. An SM has 65,536 registers: at 64 registers a thread, that's 1,024 threads, four blocks of 256. A thread that uses 128 registers halves it. Bigger thread tiles mean more reuse and more registers, so fewer warps to hide latency with. Fast kernels balance the two, and tuning that balance is most of what libraries like cuBLAS do.

What else fast kernels do

  • Vector loads: one float4 load moves 16 bytes in one instruction instead of four.
  • Double buffering: load the next tile into a second shared buffer while computing on this one, so the arithmetic never waits.
  • No bank conflicts: shared memory has 32 banks, and two threads of a warp reading different addresses in one bank take turns. Padding a tile's rows by one element usually fixes it.
  • Tensor cores: the next lesson.

None of these changes a bit of the result, so a .uir compiler may do all of them. The speed tests only ask for a fraction of the reference's speed. Beating it is a fine challenge.

Check yourself

A block makes a 64×64 tile of C. How many multiply-adds does it do for each value it loads from global memory?

BM·BN / (BM + BN).

64·64 / 128 = 32. Each value of A's tile is used by all 64 columns of the block's tile, and each value of B's by all 64 rows.

Thread t of a warp loads A[t·768], the first element of row t. What's wrong?

Which addresses do neighboring threads read?

32 neighboring floats are 128 bytes, four 32-byte transactions. 32 floats in 32 different rows are 32 transactions, each mostly wasted. Read along rows across the threads of a warp.

A kernel uses blocks of 256 threads and 128 registers per thread. An SM has 65,536 registers. At most how many of its blocks fit on one SM, by registers alone?

Registers per block first.

A block needs 256·128 = 32,768 registers, so two fit in 65,536. At 64 registers a thread, four would.

The first block to read a tile brings it into L2, and later blocks reading the same tile find it there. For matrices too big for L2, the block tile size decides the traffic to global memory directly.
