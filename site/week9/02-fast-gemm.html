Week 9 · Lesson 2

Fast GEMMs

A GEMM, a matrix multiply, is the kernel every ML compiler is judged by. By the end of this lesson you can count how many times a tiled GPU kernel reads each number, and name the three limits that decide how close it gets to the GPU's peak. Your compiler's speed tests in the lab depend on every one of them.

Goal

Given a GEMM kernel's tile sizes, say how much memory traffic it causes and what limits its speed on a GPU.

You'll use

The roofline from lesson 7.1, tiling from lesson 7.2, SMs and warps from lesson 8.1, shared memory from lesson 8.3 and register tiles from lesson 9.1. Every hardware number and measured speed here is for the RTX 4060 Ti this course was tested on.

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

A machine has a peak of 100 GFLOP/s and 20 GB/s of bandwidth. What is the best speed, in GFLOP/s, for a kernel with 2 FLOPs per byte?

Memory can feed bandwidth · intensity. Compare that with the peak and take the smaller.

20 · 2 = 40 GFLOP/s, under the peak of 100.

In lesson 9.1 a thread makes a 4×4 patch of C. For one step of k it loads 4 values of A and 4 of B. How many multiply-adds does it get from those 8 loads?

Every A value meets every B value.

4 · 4 = 16 multiply-adds for 8 loads, 2 per load.

A ladder of memories

A multiply-add needs its two inputs in registers. They start in global memory, the GPU's main memory (DRAM). On the way up they can stop in a block's shared memory, from week 8, and in the L2 cache, a cache that the whole GPU shares. Each rung of the ladder is smaller and faster than the one below it:

A and B are 768×768 f32 matrices, 4.7 MB together. Which is the smallest level of the ladder that holds both of them whole?

Compare 4.7 MB with each size in the table.

4.7 MB is far over 48 KB and well under 32 MB. So shared memory can hold only a tile at a time, and once A and B have been read, a copy of them sits in the L2 cache.

Every fast GEMM follows one plan: once a value has climbed a rung, use it as many times as you can.

How many times is each number read?

In week 8's kernel, each block makes a 16×16 tile of C. For that it needs 16 rows of A and 16 columns of B, and it copies them from global memory into its shared memory, a slice of k at a time.

C is 768 columns wide, so 48 blocks sit side by side in one row of tiles. All 48 need the same 16 rows of A. How many times is each element of those rows read from global memory?

A block cannot see another block's shared memory.

48 times. Each block has its own shared memory, so each of the 48 blocks makes its own copy.

The same goes for B. Here is the total:

  1. Count the blocks. 768 / 16 = 48 tiles each way, so 48 · 48 = 2,304 blocks.
  2. Count one block's reads. 16 rows of A and 16 columns of B, each 768 long: 2 · 16 · 768 = 24,576 floats.
  3. Multiply. 2,304 · 24,576 floats at 4 bytes each is 226 MB.

A and B are 4.7 MB. The kernel reads them 48 times over.

Lesson 9.1's kernel gives each block a 64×64 tile of C. Now how many times is each element of A read?

How many 64-wide tiles fit across 768 columns?

768 / 64 = 12. Twelve blocks share each row of A, so the traffic is 12 times 4.7 MB, about 57 MB. Bigger block tiles mean fewer copies of every number.

Reuse as one number

Here is the same fact from inside one block that makes BM×BN outputs, BK steps of k at a time.

  1. Count the loads. A BM×BK tile of A and a BK×BN tile of B: (BM + BN) · BK values.
  2. Count the work. BM · BN · BK multiply-adds.
  3. Divide. BM·BN / (BM + BN) multiply-adds per value loaded.

A block makes a 32×32 tile of C. How many multiply-adds does it do for each value it loads from global memory?

BM·BN / (BM + BN) with both equal to 32.

32 · 32 / 64 = 16. For a square tile the answer is half the tile's width, so doubling the tile doubles the reuse.

The roofline, for this GEMM

A kernel can be no faster than its arithmetic alone, and no faster than its memory traffic alone. This GPU's peak is 22 TFLOP/s (1 TFLOP/s is 1,000 GFLOP/s). Its global memory delivers 288 GB/s.

The 768×768 GEMM is about 906 million FLOPs. At 22 TFLOP/s, what is the least time it can take, in microseconds?

22 TFLOP/s is 22 million FLOPs every microsecond.

906 / 22 is about 41 µs.

Memory needs less: 4.7 MB at 288 GB/s is 16 µs. The larger of the two is 41 µs, so the GEMM is compute-bound, if each value travels once. Week 8's kernel reads 226 MB. Straight from global memory, that alone would take 0.8 ms. Yet the kernel measured 0.51 ms.

The L2 cache is the reason. A and B fit in it, so the first block to read a tile brings it into L2, and most later reads never reach global memory. Big tiles still matter when L2 catches everything. L2 has a bandwidth limit of its own, and every load is an instruction the SM has to issue. With 64×64 block tiles and 4×4 thread tiles the measured time is 0.145 ms, which is 6.2 TFLOP/s. That is still well under 22.

What limits a block's size?

Bigger block tiles mean less traffic. Why not make C one tile?

A block makes a 128×128 tile of C, and each of its threads makes a 2×2 patch. How many threads does the block need?

128 / 2 patches each way.

64 · 64 = 4,096 threads. A CUDA block can have from 1 to 1,024 threads, so this block cannot exist.

Two limits cap a block:

  • Threads. A block has 1 to 1,024 threads, and it needs (BM / TM) · (BN / TN) of them. A 64×64 tile with 4×4 patches needs 16 · 16 = 256.
  • Shared memory. The block's A tile and B tile must fit in 48 KB, unless the kernel asks for more. For a square tile that is 2 · BM · BK floats. With BM = 64 and BK = 16 it is 2,048 floats, 8 KB.

So a bigger block tile needs a bigger thread tile to stay under 1,024 threads. A bigger thread tile needs more registers, and those run out too, as the occupancy screen shows.

Neighbors read neighbors: coalescing

A warp's 32 threads send their loads to memory together. Memory answers in transactions: one trip that brings back 32 bytes in a row.

Each of a warp's 32 threads reads one f32, and thread t reads float t of an array. How many 32-byte transactions cover all 32 floats?

32 floats in a row are how many bytes?

32 floats are 128 bytes, which is four transactions, and every byte that moves is used. If thread t read float 768 · t instead, the 32 floats would sit in 32 different places and need 32 transactions.

Coalescing is the hardware combining a warp's loads into as few transactions as it can, which works when neighboring threads read neighboring addresses. When the addresses are far apart, every thread costs its own transaction, most of it wasted. Step through both cases:

So in the register-tiled GEMM's copy phase, 16 neighboring threads copy 16 neighboring floats of one row of A.

The exact index the copy phase uses, for when you read the reference kernel

The copy phase of the register-tiled GEMM picks its element as q·256 + t, where q from 0 to 3 counts the copies each of the 256 threads makes. It maps that to row q·16 + t / 16, column t mod 16. So threads 0 to 15 read columns 0 to 15 of one row, threads 16 to 31 the next row, and so on.

Too many registers: occupancy

A load from global memory takes hundreds of cycles. An SM hides that wait by holding many warps and running whichever one is ready (lesson 8.1). How many it can hold depends on what each block uses up.

An SM has 65,536 registers. A kernel's blocks have 256 threads, and each thread uses 64 registers. How many blocks fit on the SM, by registers alone?

Registers per block first: 256 · 64.

A block needs 256 · 64 = 16,384 registers, and 65,536 / 16,384 = 4.

Occupancy is the share of an SM's thread slots that a kernel's blocks fill. An SM on this GPU has 1,536 slots, so four blocks of 256 is 67 percent. A thread that uses 128 registers halves it: two blocks, 512 threads. With fewer warps, the SM more often has nothing ready to run while loads are on their way. The kernel gets slower even though each thread does more per load.

A bigger thread tile means more reuse and more registers, so fewer warps to hide the waiting with. Tuning that balance is most of what libraries like cuBLAS do.

Four more things fast kernels do, for when you try to beat the reference
  • Vector loads: one float4 load moves 16 bytes in one instruction instead of four.
  • Double buffering: load the next tile into a second shared buffer while computing on this one, so the arithmetic never waits.
  • No bank conflicts: shared memory has 32 banks, and two threads of a warp reading different addresses in one bank take turns. Padding a tile's rows by one element usually fixes it.
  • Tensor cores: the next lesson. Float tensor cores round differently from f32, so .uir exposes them through exact i8 to i32 matrix multiply-add ops instead.

The first three never change a bit of the f32 result, so a .uir compiler may do all of them on any kernel. The speed tests only ask for a fraction of the reference's speed. Beating it is a fine challenge.

Check yourself

A block makes a 64×64 tile of C. How many multiply-adds does it do for each value it loads from global memory?

BM·BN / (BM + BN).

64·64 / 128 = 32. Each value of A's tile is used by all 64 columns of the block's tile, and each value of B's by all 64 rows.

Thread t of a warp loads A[t·768], the first element of row t. What's wrong?

Which addresses do neighboring threads read?

32 neighboring floats are 128 bytes, four 32-byte transactions. 32 floats in 32 different rows are 32 transactions, each mostly wasted. Read along rows across the threads of a warp.

A kernel uses blocks of 256 threads and 128 registers per thread. An SM has 65,536 registers. At most how many of its blocks fit on one SM, by registers alone?

Registers per block first.

A block needs 256·128 = 32,768 registers, so two fit in 65,536. At 64 registers a thread, four would.

On this 768×768 GEMM, week 8's kernel reads 226 MB of tiles, which would take 0.8 ms from global memory at 288 GB/s, but it runs in 0.51 ms. How?

The ladder has a step between global memory and shared memory.

The first block to read a tile brings it into L2, and later blocks reading the same tile find it there. For matrices too big for L2, the block tile size decides the traffic to global memory directly.
