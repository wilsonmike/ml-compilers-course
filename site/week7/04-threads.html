Threads: iterations at the same time

Your machine has several processor cores, and so far your compiled code has used one of them. In this lesson a loop hands its iterations to all of them with axis=thread. You also learn the rule that stops two iterations from writing the same memory, because a compiler that lets them do it is broken.

Goal

Decide whether a thread loop is safe: every iteration writes only its own slice of memory.

Two threads, one counter

A core is one unit inside the processor that runs instructions, one after another. A laptop or desktop has several, often 4, 8 or more. A thread is one sequence of instructions in progress, and a program with several threads can keep several cores busy at once.

Everything you have compiled so far is one thread. One core works and the rest sit idle. A loop of 192 iterations could give 24 to each of 8 cores and finish much sooner. First, a prediction.

A counter starts at 0. Two threads each run counter = counter + 1 1,000 times, at the same time. What is the counter at the end?

counter = counter + 1 is three steps: load the counter, add 1, store it back. The other thread can run between any two of them.

Sometimes it is 2,000. Often it is less, and a different number each run. Additions get lost, and the lines below show how.

The line counter = counter + 1 is three steps: load, add, store. Here threads A and B take them at the same moment, with the counter at 5:

A loads 5            B loads 5
A adds 1, has 6      B adds 1, has 6
A stores 6           B stores 6

Two additions ran, and the counter went from 5 to 6. Whether this happens depends on timing, so the total differs from run to run. This is a race: two threads use the same memory at the same time, and at least one of them writes to it.

Lose an update yourself

In the exercise, schedule lists which thread takes the next step. Each thread has its own register, reg[t]reg.(t), and takes its three steps in turn: load the counter into its register, add 1 to the register, store the register back.

Run two threads by hand

run plays a schedule and returns the counter. The load step is written. Fill in the add step and the store step. Then compare the two sample tests: when thread 0 finishes before thread 1 starts, the answer is 2. When they take turns, it is 1.

Your code was the same in both tests. Only the order of the steps changed. That makes a race the worst kind of bug for a compiler: the program is right on most runs, so tests pass, and the wrong answer shows up later on someone else's machine.

So .uir does not look for races while the program runs. It rejects, before anything runs, every program that could have one.

A loop that asks for threads

A range can ask for its iterations to be spread over threads:

%r = range 192 axis=thread

The iterations of a thread loop may run in any order, at the same time. As with upcast, the result must not change. ./compile still runs them in order, one after another. So the program has to be written so that the order cannot matter. Which loops are like that?

A loop over r runs all its iterations at once. Which body always gives the same result as running them in order?

One of them is the counter again.

In the first body, iteration r writes element r and no other iteration touches it. The second is the shared counter: every iteration loads and stores o[0].

Two things made the first loop safe, and they become the rule:

  • Reads are free. A race needs a write. Memory the loop never stores into, like x, may be read anywhere by every iteration.
  • Writes stay apart. Each iteration stores only into elements that no other iteration loads or stores.

Each iteration owns a slice

To keep writes apart, the spec cuts every buffer the loop stores into equal slices, one per iteration. With a slice size of S, iteration r owns elements r·S to r·S + S - 1. Every store in the loop, and every load of memory the loop also stores into, must be at an offset of this form:

r * S + e        S is a literal
                 e is the rest of the offset, proven inside [0, S)

r * S picks the slice. e picks a place inside it and must never reach the next one. A bare r counts as S = 1. Step through three offsets for a loop over r in 0..3, with j in 0..3. Each cell shows which iterations write it.

A thread loop over r stores into o and only reads x. Inside it, c runs from 0 to 7. Which access breaks the rule?

For each store, what is the largest e? The slice size is 8.

In 8r + c + 1, e = c + 1 reaches 8, the first element of the next iteration's slice. In 8r + c, e stops at 7. The load of x[c] is free, because the loop never stores into x.

The same proof as lesson 2.3

In lesson 2.3 you proved a view inside its buffer: find the offset's bounds [lo, hi], then check lo ≥ 0 and hi + k ≤ n. The slice rule is that proof again, with the slice in place of the buffer: e has bounds [lo, hi], and the access passes when lo ≥ 0 and hi + size ≤ S. size is how many elements the access touches: 1 for a [] view, k for a [k] view.

Take a 4×8 matrix whose rows run on threads. The store is at add (mul %r 8) %c, with %c = range 8:

  1. Find the r term. It is mul %r 8, so S is 8.
  2. Collect the rest. e is %c.
  3. Bound e. A range of 8 has bounds [0, 7].
  4. Compare. 0 ≥ 0 holds, and 7 + 1 ≤ 8 holds. The store is proven.

Step 1 reads the offset as it is written. It looks for one term that is r, mul r S or mul S r. An offset written (r·2)·4 + c has the same value as r·8 + c, but it has no term of that shape, so the program is rejected.

Write the offset the checker can read

The row loop of this 4×8 scaling is a thread loop, but its store offset is written (r·2)·4 + c, which the slice rule rejects. Write it so the rule can see each row's slice.

Write the check

Often e is a sum of several terms. It is not one node in the program, so bound each term on its own, then add the low ends and add the high ends.

Take the offset r·32 + i·8 + c, with i in 0..3 and c in 0..7. The term i·8 has bounds [0, 24] and c has [0, 7]. So e has bounds [0, 31], and 31 + 1 ≤ 32. The access stays in its slice. Your compiler runs this check on every such access.

Check one access against the slice rule

Write slice_ok. It takes the slice size s, the bounds (lo, hi) of each term of e, and the access size. It returns true when the access is proven to stay inside the slice. An empty list of terms means the offset is r·S alone, so e is 0.

Private memory

A loop often needs scratch memory, such as an alloc that holds a running sum. Here acc is an alloc of one element, used only inside a loop over r in 0..3. Each iteration does acc[0] = acc[0] + r and then copies acc[0] to o[r].

As a plain loop, with no axis, what is o at the end? Write the four numbers with spaces between them.

In a plain loop an alloc keeps its contents from one iteration to the next.

0 1 3 6, the running sums. Each iteration starts from what the one before it left in acc.

As a thread loop, that would be the shared counter again: every iteration loads and stores acc[0]. But scratch memory is not meant to be shared, so the spec makes it private. An alloc whose every load and store is inside one thread loop gets a fresh copy, all zeros, at the start of every iteration. The tiled GEMM's 32 running sums are a private alloc.

This is the one place where an axis changes what a program means, and ./compile follows it too: it sets a private alloc back to zeros at the start of each iteration.

Any other alloc, such as one that is loaded after the loop, is shared. It follows the slice rule exactly as a buffer does.

Splitting the work

When the C runs, a small library called the harness hands out the iterations. Each thread gets one chunk of neighboring iterations: with 192 iterations on 8 threads, thread 0 runs 0 to 23, thread 1 runs 24 to 47, and so on. Neighboring iterations own neighboring slices, so each thread writes one solid block of memory.

Thread the outermost loop the slice rule allows, so each thread gets plenty of work. Starting a thread costs tens of microseconds, and a thread loop around a tiny body is slower than a plain loop. A thread loop inside another thread loop is invalid. On the 768×768 GEMM with 24 hardware threads, threading the 192 row blocks made it about 8 times faster.

One chunk per thread

Write chunks n t: one contiguous range of iterations per thread, covering all n exactly once. Each range is (lo, hi) and stops just before hi. Use m = min t n threads, but at least 1, and give thread k the range from n·k / m to n·(k+1) / m, with whole-number division.

Every thread-loop rule and the tests that check it, for when you write validation in the lab
  • No nesting. A thread loop can't be inside another thread loop. It may be inside a plain loop.
  • The form. Every store in the loop body, and every load of memory the body also stores into, is at a flat offset r * S + e. r is the thread range and appears in exactly one term of the offset's sum, as r itself (S = 1) or as mul r S or mul S r with S a positive literal.
  • The rest. e is the sum of the other terms. None of them depends on r. 0 ≤ e and e + size ≤ S must be provable from bounds, where size is 1, or k for a [k] view. Bound each term on its own and add the results.
  • One S per buffer. Every access to one buffer in the loop uses the same S.
  • Read-only memory is free. Loads of memory the body never stores into may be anywhere.
  • Private allocs. An alloc whose every load and store is inside one thread loop starts every iteration as zeros. In C it is an array declared inside the thread's function. Any other alloc is shared and follows the same rules as a buffer.

A program that breaks a rule is REJECTED. The tests loop_alloc_carries_over and thread_private_alloc_fresh run the same program as a plain loop and as a thread loop and get different answers, 0 1 3 6 and 0 1 2 3. In rejected_thread_alloc_shared every iteration stores to element 0 of a shared alloc. In thread_alloc_indexed_by_r iteration r stores to element r of a shared alloc, which is fine.

The tiled GEMM's offset written in the form, for when you thread it in the lab

Write offsets expanded. In the GEMM, C's offset (4ib + wi)·N + 8jb + wj is written as ib·(4N) + wi·N + jb·8 + wj, with e = wi·N + jb·8 + wj. For N = 768 the terms are in [0, 2304], [0, 760] and [0, 7], so e is in [0, 3071], and 3071 + 1 ≤ 3072 = S. Each row block writes only its own 3072 elements. A and B are only read, so they may be read anywhere.

The check works on shape because a shape is easy to state and to prove. Your simplifier could fold (r·2)·4 into r·8, but the spec checks the program as written.

Why 24 threads do not give 24 times the speed, and what the speed tests ask for

Threading the GEMM's row blocks took it from 98 ms to 12 ms with clang, and about 15 to 30× together with upcast. It's not 24×, because threads share the memory bus and the L3 cache, and some cores are slower than others. The speed tests with thread loops ask for half the reference's speed. A renderer that runs thread loops one iteration at a time lands around 0.13 and fails.

Contiguous chunks also mean two threads rarely touch the same cache line. When they do, the line bounces between cores, which is slow even without a race. That's called false sharing.

Your machine has 24 hardware threads. Why doesn't threading make the GEMM 24× faster?

What do all the cores have in common?

Cores share the path to memory and the last-level cache. As cores are added, those shared parts become the limit, along with the fixed cost of starting threads.

A 4-element alloc is stored inside a thread loop over r and loaded after the loop. Each iteration stores to element r. What does the spec say?

Is every load and store inside the thread loop?

The load after the loop makes the alloc shared, so it follows the slice rule like a buffer. The offset is r itself, so S = 1 and each iteration owns its own element. That's the test thread_alloc_indexed_by_r.
