Threads: iterations at the same time

A desktop processor has several cores, each able to run its own loop. If the iterations of a loop don't depend on each other, they can run on different cores at once. The hard part isn't starting threads, it's proving that no two iterations step on each other's memory.

axis=thread

%ib = range 192 axis=thread

Iterations of a thread loop may run in any order, at the same time. run still executes them in order, one after another. The program must be written so that the order doesn't matter, and the spec checks that statically.

What goes wrong: a race

Suppose two iterations both do o[0] = o[0] + 1 at the same time. Each loads o[0], say 5, adds 1, and stores 6. One increment is lost, and which one depends on timing. This is a race. Its result can change from run to run, and the bit-exact grader would catch it only sometimes. So the spec forbids it outright.

The slice rule

Each iteration r gets its own slice of memory: elements r·S to r·S + S - 1. Every store in the loop, and every load of memory the loop also stores into, must be at a flat offset of the form

r * S + e        S a literal (a bare r means S = 1), r in exactly one term,
                 e doesn't depend on r, and 0 <= e, e + size <= S

size is how many elements the access touches: 1 for a scalar load or store. Your week 1 bounds analysis proves the part about e: bound each of its terms on its own, then add up the lows and the highs. Every access to one buffer in the loop uses the same S. Memory the loop only reads, like the A and B of a GEMM, may be read anywhere: two threads reading the same float is no problem.

The check looks at the shape of the offset, not its value. (r·2)·4 equals r·8 but isn't in the form, so it's rejected. Write offsets expanded: in the GEMM, C's offset (4ib + wi)·N + 8jb + wj is written as ib·(4N) + wi·N + jb·8 + wj, with e = wi·N + jb·8 + wj. For N = 768 the terms are in [0, 2304], [0, 760] and [0, 7], so e is in [0, 3071], and 3071 + 1 <= 3072 = S. Each row block writes only its own 3072 elements.

Write the offset the checker can read

The row loop of this 4×8 scaling is a thread loop, but its store offset is written (r·2)·4 + c, which the slice rule rejects. Write it so the rule can see each row's slice.

Private allocs

The GEMM's 32 accumulators are an alloc used only inside the thread loop. Shared between threads, they'd race. So the spec makes them private: an alloc whose every load and store is inside one thread loop gets a fresh copy, all zeros, at the start of every iteration. In C that's simply an array declared inside the thread's function.

That's a real semantic difference, and run implements it too. In a plain loop an alloc keeps its contents from one iteration to the next, so an accumulator keeps a running total. In a thread loop each iteration starts from zero. The tests loop_alloc_carries_over and thread_private_alloc_fresh run the same program both ways and get different answers.

Any other alloc, say one that is also loaded after the loop, is shared, and the slice rule applies to it exactly as to a buffer. Every iteration storing to element 0 is rejected (err_thread_alloc_shared), and iteration r storing to element r is fine (thread_alloc_indexed_by_r).

How the iterations are split

The harness gives each hardware thread one contiguous chunk of iterations: with 192 iterations on 8 threads, thread 0 runs 0 to 23, thread 1 runs 24 to 47, and so on. Contiguous chunks mean each thread writes one block of memory, so two threads rarely touch the same cache line. When they do, the line bounces between cores, which is slow even without a race. That's called false sharing.

One chunk per thread

Write chunks n t: one contiguous range of iterations per thread, covering all n exactly once.

What to thread, and what it's worth

Thread the outermost loop that the slice rule allows: each thread then gets plenty of work per iteration. Starting threads costs tens of microseconds, so a thread loop around a tiny body is slower than a plain loop. Only one level may be threaded. A thread loop inside another is invalid, but a thread loop inside a plain loop is fine.

On the 768×768 GEMM with 24 hardware threads, threading the 192 row blocks gave about 8× on its own (98 ms to 12 ms with clang), and about 15 to 30× together with upcast. It's not 24×, because threads share the memory bus and the L3 cache, and some cores are slower than others. The speed tests with thread loops ask for half the reference's speed. A renderer that runs thread loops one iteration at a time lands around 0.13 and fails.

In a thread loop over r in 0..3, which store is valid?

Each iteration's slice is r·S to r·S + S - 1.

With S = 4, e = j is in [0, 3], inside the slice. 2r + j reaches 2r + 3, which is iteration r + 1's slice. o[j] has every iteration write the same four elements.

A thread loop reads x[anything], and never stores to x. Is that allowed?

Which accesses can race?

A race needs at least one write. Memory the loop never stores into can be read anywhere, by every iteration.

An alloc acc is used only inside a thread loop over r in 0..3. Each iteration does acc[0] = acc[0] + r, then writes acc[0] to o[r]. What is o?

A private alloc starts at zero in every iteration.

Each iteration sees a fresh zero: o = [0 1 2 3]. As a plain loop the alloc carries over, giving running sums [0 1 3 6].

A shape-based check is easy to state and to prove. The program spells the offset out in the form the rule recognizes. Your simplifier could fold it, but the spec checks the program as written.

Your machine has 24 hardware threads. Why doesn't threading make the GEMM 24× faster?

What do all the cores have in common?

Cores share the path to memory and the last-level cache. As cores are added, those shared parts become the limit, along with the fixed cost of starting threads.

A 4-element alloc is stored inside a thread loop over r and loaded after the loop. Each iteration stores to element r. What does the spec say?

Is every load and store inside the thread loop?

The load after the loop makes the alloc shared, so it follows the slice rule like a buffer. The offset is r itself, so S = 1 and each iteration owns its own element. That's the test thread_alloc_indexed_by_r.
