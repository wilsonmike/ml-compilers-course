The week 7 lab

Teach your compiler the three loop axes. It checks the thread rules, runs private allocs fresh in each iteration, unrolls upcast loops, and outlines thread loops for uir_parallel_for. You're done when every week 7 test passes, including three speed tests on a 768×768 GEMM, and weeks 1 to 6 still pass, and you've written 10 tests of your own.

The command-line contract

commandweek 7 changes
your.exe run FILErange takes axis=loop|upcast|thread. Every axis runs as an ordinary loop, except that a private alloc starts at zero in every iteration of its thread loop. New static errors (exit 2): an unknown axis, an upcast bound that isn't a literal from 1 to 32, a thread loop inside a thread loop, and a store (or a load of memory the loop stores into) that isn't at r·S + e with 0 ≤ e, e + size ≤ S, one S per buffer.
your.exe render FILEUnroll upcast loops. Outline thread loops into a function and call uir_parallel_for, declared in your C. Private allocs are declared inside the outlined function.

How the tests are graded

  • Run tests check the rules and the private-alloc semantics. Several come in pairs that differ only in the axis, like loop_alloc_carries_over and thread_private_alloc_fresh.
  • Render tests compare your C's buffers with the interpreter's, bit for bit, as always. The harness links in its pthreads uir_parallel_for when your C calls it. Upcast tests raise the size limit with # max_bytes:.
  • Speed tests (# speed: X) build your kernel and the reference kernel the same way at -O2, run each three times alternately, and require the reference's exact bits and at least X times its speed. s_gemm_768_threads and s_gemm_768_threads_and_upcast need 0.5. s_gemm_768_upcast (one thread) needs 0.65. On a machine with fewer than 4 hardware threads, the thread tests check bits only.

Write your 10 tests

Ten tests in path/to/your-repo/tests/week7/, checked with python tools/test.py --check-tests path/to/your-repo/tests/week7. Good targets: a store at r·S + e where e just fits and one where it's one over, a vector store whose size pushes it out of its slice, a load of a neighbor's element, a private alloc read before it's written, a thread loop inside a plain loop that captures the outer counter, and an upcast loop of 32.

A build order that works

  1. Parse axis=

    Store the axis on the range. Validate it, and check upcast bounds. Treat every axis as a plain loop everywhere else.

    Checkpoint: weeks 1 to 6 pass, and every week 7 run test passes except the thread-rule and private-alloc ones.

  2. The thread rules

    After linearizing, walk each thread loop's body. Reject nesting. For each store, and each load of memory the body stores into, split the flat offset into a sum of terms, find the one term with r, and bound the rest with your week 1 bounds.

    Checkpoint: every err_thread_* test exits 2, and the valid ones run.

  3. Private allocs

    An alloc whose every load and store is inside one thread loop is private. Re-zero it at the start of each iteration in run.

    Checkpoint: thread_private_alloc_fresh and loop_alloc_carries_over both pass.

  4. Render upcast

    In the emitter, emit an upcast loop's body once per value, with the range as a literal.

    Checkpoint: r_upcast_sum_order and the r_gemm_tiled_* tests pass, bit for bit.

  5. Render thread loops

    Emit the body into its own list of lines, collect its free names and their C types, and write a struct, a static function and the uir_parallel_for call. Declare private allocs inside the function.

    Checkpoint: every render test passes.

  6. Speed

    Run the speed tests with -v. If one is slow, compare your C with python _reference/uirc.py render. Look for an upcast loop left as a loop, missing restrict, or a private alloc that ended up shared.

    Checkpoint: all three speed tests pass.

The AI policy, still

An AI assistant may explain concepts, draw diagrams, and help you debug by asking questions, but must never write or rewrite compiler code. "Why is my upcast tile slower than the reference's?" is a fine question. "Write my outlining pass" is not.

Your machine has 2 hardware threads. What do the thread speed tests check?

The spec's grading section.

With 2 threads, even a perfect threaded kernel is at most 2× faster than a sequential one, which is too close to the 0.5 target to separate right from wrong. So those tests check correctness only.
