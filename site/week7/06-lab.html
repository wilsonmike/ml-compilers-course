Lab: fast kernels

In this lab your compiler learns to obey a program's schedule. It unrolls upcast loops, checks that thread loops are safe, and moves each thread loop into its own function. At the end, the C it writes for a 768×768 matrix multiply keeps pace with the reference compiler's, and for the first time tests grade that speed.

What you are building

The same two commands take one new attribute on range.

  • compile FILE runs every axis as an ordinary loop. It rejects a thread loop that breaks the rules of lesson 7.4, and it gives a private alloc fresh zeros in every iteration.
  • compile render FILE prints an upcast loop as copies of its body, and a thread loop as a function that the harness runs on many threads.

The suite has 27 run tests and 14 render tests. Three of the render tests are speed tests. Each multiplies two 768×768 matrices. The language contract is spec/uir-week7.md. If this page and the spec disagree, the spec wins.

How run and render tests are graded this week
  • Run tests check the rules and the private-alloc semantics. Several come in pairs that differ only in the axis, like loop_alloc_carries_over and thread_private_alloc_fresh. For each rejected_ test the grader also runs your render on the file and expects it to refuse.
  • Render tests compare your C's buffers with the interpreter's, bit for bit, as always. The harness links in its pthreads uir_parallel_for when your C calls it. Upcast tests raise the size limit with # max_bytes:.
  • Speed tests (# speed: X) are the next section. s_gemm_768_threads and s_gemm_768_threads_and_upcast use 0.5. s_gemm_768_upcast (one thread) uses 0.65. They read data/a768.f32 and data/b768.f32 next to them, 2.4 MB each.

How a speed test is graded

A speed test starts with a line such as # speed: 0.5. The grader then does four things.

  1. Render twice. It renders the program with your compiler and with the reference compiler.
  2. Build both the same way. Same C compiler, same -O2, on your machine.
  3. Take turns. It runs your kernel, then the reference kernel, three times each, and keeps the best time of each.
  4. Compare. Your bits must equal the reference's. Then your best time must be at most the reference's best time divided by the number. With 0.5 you may take twice as long.

So a slow computer is not a problem. The reference kernel runs on the same computer and is slowed just as much.

A busy computer is different. Each kernel runs for a few thousandths of a second. If a browser, a video call or another test grabs the cores during your turns, you get too slow through no fault of your code. Run the speed tests again on their own:

python tools/test.py --compiler YOURS --week 7 -k s_gemm -v --jobs 1

--jobs 1 runs one test at a time, so tests do not fight each other for cores. Close heavy programs first. A failure that goes away was noise. A failure that comes back every time is a real bug.

On a machine with fewer than 4 hardware threads, the two thread tests check bits only.

A thread speed test says too slow during a full run. You rerun it twice with --jobs 1 and it passes both times. What do you do?

A real bug fails every time.

A renderer that ignores an axis is slow on every run.

Check the thread rules

Your compiler must prove that no two iterations touch the same memory.

  1. Reject nesting. A thread loop inside a thread loop is rejected. Inside a plain loop it is fine.
  2. Pick the accesses. Check every store in the body, and every load of memory the body also stores into. Loads of memory it only reads are free.
  3. Split the offset. Write the flat offset as a sum of terms. Exactly one term holds r: r itself (S is 1), mul r S or mul S r, with S a positive literal. No other term may depend on r.
  4. Bound the rest. Bound each other term with your week 1 bounds and add them up. The low end must be 0 or more, and the high end plus the access size must be S or less.
  5. One S per buffer. Every access to one buffer in the loop uses the same S.

Run the check for render too. An alloc that is used outside the loop is checked the same way as a buffer.

Give each iteration fresh scratch memory

Three run tests still fail. All three expect a private alloc.

  1. Find the private allocs. An alloc is private when every load and every store of it is inside one thread loop.
  2. Zero it per iteration. When compile FILE runs the loop, set each private alloc back to all zeros at the start of every iteration.
  3. Leave plain loops alone. There an alloc keeps its contents from one iteration to the next.

--skip s_gemm  37 or more of 38

Outline thread loops

  1. Declare the harness function. Print the prototype of uir_parallel_for from section 3 of the spec near the top of your C.
  2. Emit the body apart. Render the loop body into its own list of lines.
  3. Collect the free names. They are the names the body uses but does not declare, without the loop counter: buffer pointers, values computed before the loop, and counters of enclosing loops. Note each one's C type.
  4. Write the struct and the function. One field per free name. The function takes the counter and a void *, unpacks the fields into locals, then holds the body.
  5. Declare private allocs inside. Each call then starts from zeros.
  6. Replace the loop with the call. Fill the struct and call uir_parallel_for with the trip count, the function and the struct's address.

--skip s_gemm       38 / 38 passed

Write your 10 tests

Put 10 tests in <your compiler repo>/tests/week7/, each aimed at a rule someone will get wrong. This one catches a slice check that is off by one:

%o  = buffer 16 dtype=i32 slot=0
%r  = range 2 axis=thread
%j  = range 5
%m  = mul %r 4
%f  = add %m %j
%v  = shrink %o %f []
%s  = store %v 1
%ej = end %s %j
%e  = end %ej %r
%o1 = after %o %e
%w  = shrink %o1 0 []
%x  = load %w
%t  = assert %x 1

With range 4 it would print MATCH. Save it with a name that starts with rejected_, then check your tests against the oracle:

python tools/test.py --check-tests <your compiler repo>/tests/week7 --week 7

With only that file there, it prints 1 / 1 tests agree with the oracle.

Good targets for your tests

Good targets: a store at r·S + e where e just fits and one where it's one over, a vector store whose size pushes it out of its slice, a load of a neighbor's element, a private alloc read before it's written, a thread loop inside a plain loop that captures the outer counter, and an upcast loop of 32.
