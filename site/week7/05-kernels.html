Kernels and outlining: rendering a thread loop

Lesson 7.4 proved that a thread loop's iterations can run at the same time. C has no way to say that about a for loop. Here you turn the loop's body into a function that any core can call, and you hand that function everything it needs.

Goal

Render a thread loop as its own C function, a struct of the values it needs and one call to uir_parallel_for.

You'll use

C pointers, structs and -> from lesson 0.1. Thread loops and private allocs from lesson 7.4.

Closures, from "Functions that make functions" in P.5.

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

An alloc is used only inside a thread loop. What does each iteration find in it when it starts?

Lesson 7.4 called this kind of alloc private.

A private alloc is fresh and zeroed for every iteration, so no two threads share it. Today you see what that looks like in C.

After int x = 7; int *p = &x;, what does p hold?

&x reads as "the address of x".

A pointer holds an address, so a function that receives p can reach memory it does not own. Today one pointer carries a whole bundle of values into a function.

A for loop stays on one core

Here is the C your render prints today for a small program. Three times over, it adds r + k to every element of a 64-element buffer. The program wants the inner loop, the one over r4, spread across cores.

void kernel(int32_t *restrict b0) {
  for (int32_t r3 = 0; r3 < 3; r3++) {
    for (int32_t r4 = 0; r4 < 64; r4++) {
      int32_t v6 = b0[r4];
      int32_t v7 = (int32_t)((uint32_t)r4 + (uint32_t)r3);
      int32_t v8 = (int32_t)((uint32_t)v6 + (uint32_t)v7);
      b0[r4] = v8;
    }
  }
}

The casts are week 2's wrapping add. Read v7 as r4 + r3.

You want a second core to run iteration r4 = 3 while the first core runs r4 = 0. What has to change in this C?

A thread library has one basic move: "run this function". What can you give it?

A for loop is one core walking through the iterations in order, and C has no words for "run this iteration somewhere else". Threads come from a library, and a library can only be handed things C can name. A loop body has no name. A function does.

Moving a block of code into its own function is called outlining. It is the reverse of inlining, where a call is replaced by the function's body. Once the body is a function, iteration 3 is one call with 3 as its argument, and any core can make that call.

The body uses names it does not own

Cut the four body lines out of the loop. Paste them into a new function whose one argument is the counter r4.

      int32_t v6 = b0[r4];
      int32_t v7 = (int32_t)((uint32_t)r4 + (uint32_t)r3);
      int32_t v8 = (int32_t)((uint32_t)v6 + (uint32_t)v7);
      b0[r4] = v8;

The C compiler now reads that function alone. Every name in it has to be an argument or be declared inside it.

Which names does the new function still need handed in from outside?

For each name, find where it is declared: in these four lines, or above them?

The four lines declare v6, v7 and v8 themselves, and r4 is the argument. b0 is a parameter of kernel and r3 is the outer loop's counter. Both live in kernel, which the new function can't see.

Names a block uses but does not define are called its free variables. The outlined function needs each of them handed in.

You have met this before. In P.5, make_counter returned next_number, and that inner function kept using count from the function around it. Python bundled count with the function for you. The bundle is called a closure.

You have met this before. In O.2, add 10 gave back a function that still held the 10. OCaml bundled that value with the function for you. The bundle is called a closure.

C bundles nothing. Your compiler has to build the bundle by hand and pass it to the function. That job is called closure conversion.

Pack the free variables in a struct

The harness will call your function with exactly two arguments: the counter and one pointer. So every free variable has to travel behind that one pointer. A struct is a C type that groups several named values, called fields, into one block of memory. Pack the free variables into a struct and pass its address.

  1. List the uses. b0, r4, r3, v6, v7, v8.
  2. Cross off what the body declares. v6, v7 and v8 go.
  3. Cross off the loop counter. r4 arrives as the argument.
  4. Pack the rest. b0 and r3 become the fields.

This is what the reference compiler prints when the inner loop says axis=thread:

typedef struct { int32_t *b0; int32_t r3; } thread0_ctx;
static void thread0(int32_t r4, void *ctx) {
  thread0_ctx *k_ = ctx;
  int32_t *restrict b0 = k_->b0;
  int32_t r3 = k_->r3;
  int32_t v6 = b0[r4];
  int32_t v7 = (int32_t)((uint32_t)r4 + (uint32_t)r3);
  int32_t v8 = (int32_t)((uint32_t)v6 + (uint32_t)v7);
  b0[r4] = v8;
}

void kernel(int32_t *restrict b0) {
  for (int32_t r3 = 0; r3 < 3; r3++) {
    { thread0_ctx k_ = { b0, r3 }; uir_parallel_for(64, thread0, &k_); }
  }
}

The typedef line names the struct type thread0_ctx. Inside thread0, k_->r3 reads the field r3 through the pointer k_. The first three lines unpack the struct into locals with their old names, so the four body lines are the same text as before.

What the thread body needs

A body is a list of (name, uses) statements. The starter returns every name the body uses. Repair it so it returns only the names the body uses but doesn't define, leaving out its loop variable: the fields of the context struct.

What goes in and what stays out

Try the four moves on a bigger kernel. The loop over r10 is about to become a thread loop.

void kernel(float *restrict b0, float *restrict b1, float *restrict b2) {
  float v7 = b1[0];
  for (int32_t r8 = 0; r8 < 2; r8++) {
    float v9 = ((float)r8);
    for (int32_t r10 = 0; r10 < 64; r10++) {
      int32_t v11 = (int32_t)((uint32_t)r10 * (uint32_t)2);
      int32_t v12 = (int32_t)((uint32_t)v11 + (uint32_t)r8);
      float v15 = b0[r10];
      float v16 = (v15 * v7);
      float v17 = (v16 + v9);
      b2[v12] = v17;
    }
  }
}

How many fields does the context struct for the r10 loop have?

List every name the six body lines use. Cross off the ones they declare, then r10.

Five: b0, b2, r8, v7 and v9. The reference prints typedef struct { float *b0; float *b2; int32_t r8; float v7; float v9; } thread0_ctx;. The body never touches b1, so it stays out.

So three kinds of name go in: buffer pointers, values computed before the loop, and counters of enclosing loops. A buffer the body doesn't use stays out.

One more thing stays out: a private alloc. It is declared inside the function, as in this line from the test r_thread_private_alloc:

  int32_t a5[1] = {0};

A variable declared inside a function is made new on every call. So each iteration gets its own zeros, which is what lesson 7.4 promised.

The harness runs the function

Your C never starts a thread itself. The harness, the C file your kernel is linked with, provides one function for that:

void uir_parallel_for(int32_t n, void (*body)(int32_t, void *), void *ctx);

Its arguments are a trip count n, a function body that takes a counter and a pointer, and a pointer ctx. It calls body(r, ctx) once for every r from 0 to n - 1, spread across threads. void * means "a pointer to something", so the harness can carry your struct without knowing what is in it. Print this prototype line in your C. The harness defines the function.

The thread loop in kernel becomes one line:

    { thread0_ctx k_ = { b0, r3 }; uir_parallel_for(64, thread0, &k_); }
  1. Fill the struct. Give the current values, in the order of the fields.
  2. Call the harness. Pass the trip count, the function's name and the struct's address.
  3. Wait. The call returns only when every iteration is done, so the next line may read what the loop wrote.

The struct is filled again at every pass of the r3 loop. That is how each pass hands the body its own r3.

In the kernel with thread0_ctx k_ = { b0, r3 }, how many times does thread0 run in total?

Each pass of the outer loop makes one call to uir_parallel_for. How many times does each call run the body?

The outer loop makes 3 calls to uir_parallel_for, and each call runs thread0 64 times: 192. The threads are also started 3 times, which is why lesson 7.4 said to thread the outermost loop the slice rule allows.

Write the call that starts the threads

Write call_site id n fields. It returns the one line of C that replaces a thread loop in the kernel: fill a context struct with the values named in fields, then call uir_parallel_for with the trip count n, the function thread<id> and the struct's address. For call_site 0 64 ["b0"; "r3"] the answer is exactly { thread0_ctx k_ = { b0, r3 }; uir_parallel_for(64, thread0, &k_); }.

Kernels and restrict

A kernel is a loop nest that runs as one unit: the code between one materialization and the next. Week 4's rangeify already produces them. Each stage, each store of a whole value, becomes its own loop nest at the top of the C function. Fusing ops puts more work in one kernel. Materializing splits it.

On a CPU, kernels run one after another, and threads split one kernel's outer loop across cores. On a GPU, which the course reaches next week, each kernel is a separate launch. The thread loop you render this week is the same idea at a smaller scale: hand one loop's iterations to many workers.

Every listing above declares its buffer pointers restrict. Buffers never overlap in .uir, but C doesn't know that. When a kernel writes through one pointer and reads through another, the C compiler has to assume the write might change what the read sees, so it loads the value again after every store. restrict promises the pointers don't overlap. The compiler can then keep loaded values in registers across stores, and that matters in tight loops.

The outlined function gets its buffers from the struct, not from parameters. Where does the reference put restrict there?

Look at the first lines of thread0 in the listing with the struct.

The fields are plain pointers. The promise is made again on the locals, so a hot loop inside the thread function gets the same benefit as a loop in kernel.

A second full example: the threaded row sum, with a loop inside the thread body

Here is the reference compiler's C for the test r_thread_rowsum, out[r] = sum of row r:

void uir_parallel_for(int32_t n, void (*body)(int32_t, void *), void *ctx);

typedef struct { int32_t *b0; int32_t *b1; } thread0_ctx;
static void thread0(int32_t r5, void *ctx) {
  thread0_ctx *k_ = ctx;
  int32_t *restrict b0 = k_->b0;
  int32_t *restrict b1 = k_->b1;
  b1[r5] = 0;
  int32_t v10 = (int32_t)((uint32_t)r5 * (uint32_t)3);
  for (int32_t r11 = 0; r11 < 3; r11++) {
    int32_t v12 = b1[r5];
    int32_t v13 = (int32_t)((uint32_t)v10 + (uint32_t)r11);
    int32_t v15 = b0[v13];
    int32_t v16 = (int32_t)((uint32_t)v12 + (uint32_t)v15);
    b1[r5] = v16;
  }
}

void kernel(int32_t *restrict b0, int32_t *restrict b1) {
  { thread0_ctx k_ = { b0, b1 }; uir_parallel_for(4, thread0, &k_); }
}

The loop variable r5 is the function's argument. The two buffers it uses travel in thread0_ctx. Everything the body defines (v10 to v16, the inner loop and its counter r11) stays inside. In the GEMM, the struct holds just the three buffers: the tile's accumulators are a private alloc, declared in the function.

Why the harness's prototype for kernel doesn't say restrict

The harness declares kernel with plain pointers, and your C defines it with restrict ones. That's fine: qualifiers on parameters don't change a function's type, so the two declarations match.

Which names does the body use without defining?

Values from before the loop (and buffer pointers, and enclosing loop counters) come from outside. Private allocs are declared inside the function so each call gets fresh zeros.

A thread loop sits inside a plain loop over p, and its body uses p. How does the body get p?

The function's argument is the thread loop's own counter.

The outer counter is a free variable of the body. The struct is filled just before each uir_parallel_for call, so every pass of the outer loop passes its own p. The test r_thread_captures_values does exactly this.

What does restrict on the kernel's buffer pointers let the C compiler do?

What must the compiler assume about two pointers without it?

Without it, any store might alias any load, so the compiler reloads values after every store. .uir buffers never overlap, so the promise is true.

Starting threads costs tens of microseconds. Which loop should you thread?

How many times would an inner thread loop start its threads?

A thread loop inside other loops starts its threads once per outer iteration. Threading the outermost allowed loop pays that cost once, for the most work.
