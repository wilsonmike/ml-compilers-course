Week 7 · Lesson 1

Measuring speed: FLOPs, bytes and the roofline

For six weeks the only question was: is the answer right? From this week the answer must stay exactly the same, bit for bit, and the new question is: how fast? By the end of this lesson you can measure a kernel's speed and say what is holding it back, which is what your compiler needs to know before it tries to make anything faster.

Goal

Given a kernel, say whether arithmetic or memory limits its speed.

You'll use

Cache lines and stride from lesson 0.2, and tools/bench.py from the week 6 lab. The code on this page is one division and one comparison.

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

An f32 array has 1,000 elements. How many bytes is that?

The 32 in f32 counts bits. There are 8 bits in a byte.

Each f32 is 4 bytes, so 1,000 of them take 4,000 bytes.

A matrix is stored row after row. Which walk gets a new cache line on almost every step?

Which two elements sit next to each other in memory: left and right neighbors, or up and down neighbors?

Row neighbors are 4 bytes apart, so 16 of them share one 64-byte line. Column neighbors are a whole row apart, so each step lands on a different line.

Same answer, different speed

Here are two ways to multiply two 768×768 matrices in C. Each one computes every C[i][j] as the same sum, in the same order of k. The outputs match bit for bit. Only the order of the loops differs.

for (int i = 0; i < N; i++)
  for (int j = 0; j < N; j++) {
    float s = 0.0f;
    for (int k = 0; k < N; k++)
      s += A[i*N + k] * B[k*N + j];
    C[i*N + j] = s;
  }

Loop A: k is the inner loop.

for (int i = 0; i < N; i++) {
  for (int j = 0; j < N; j++) C[i*N + j] = 0.0f;
  for (int k = 0; k < N; k++)
    for (int j = 0; j < N; j++)
      C[i*N + j] += A[i*N + k] * B[k*N + j];
}

Loop B: j is the inner loop.

Both loops do the same 0.9 billion multiplies and adds. How do their times compare?

Look at B[k*N + j]. In each loop, how far does the inner loop jump through B on every step?

Loop A took 89 ms and loop B took 30 ms. That is one measurement, on the machine this course was built on, with gcc at -O2 and one thread. Your numbers will differ.

In loop A the inner loop walks B down a column, so almost every load is a new cache line. In loop B the inner loop walks B and C along a row. Walking in order also lets the C compiler do several floats with one instruction, which lesson 7.3 covers.

So the second half of this course is about a number the first half ignored. Two counts describe any kernel: how much arithmetic it does, and how many bytes it moves.

Count the work: FLOPs

A FLOP is one floating-point operation: one add or one multiply. FLOPs count the work a kernel does, whatever order it does it in. Divide the FLOPs by the seconds the kernel took and you have its speed. The usual unit is GFLOP/s, billions of FLOPs per second.

Here is loop A's speed:

  1. Count the FLOPs. Each of the 768 × 768 outputs is a sum of 768 terms, and each term costs one multiply and one add. That is 2 · 768³ = 905,969,664, about 0.9 GFLOP.
  2. Time the kernel. 89 ms is 0.089 seconds.
  3. Divide. 0.906 / 0.089 is about 10 GFLOP/s.

tools/bench.py does all three steps for any program. On the same machine, the same matrix multiply reached over 200 GFLOP/s with this week's schedule, the program's choice of how each loop runs, and it still computed the identical bits.

Loop B does the same 0.906 GFLOP in 30 ms. What is its speed in GFLOP/s?

30 ms is 0.030 seconds. Divide the GFLOPs by the seconds.

0.906 / 0.030 is about 30 GFLOP/s. Same work, a third of the time, three times the speed.

Count the bytes: bandwidth

Now a simpler kernel: add two arrays of 16 million floats, z[i] = x[i] + y[i]. It walks memory in perfect order.

Loop B ran at 30 GFLOP/s. How fast does this add run on the same machine?

Each array is 64 MB, far too big for any cache. Where does every number have to come from?

It measured 2.2 GFLOP/s, on the same machine with the same compiler. The processor spends most of its time waiting for numbers to arrive.

Memory can only deliver so many bytes per second. That rate is its bandwidth, and on this machine it measured about 25 GB/s. Each add reads 8 bytes and writes 4, so it moves 12 bytes for 1 FLOP. 25 billion bytes per second, at 12 bytes per add, is about 2 billion adds per second. No faster processor would change that.

The matrix multiply is different. Its three matrices are small, and it uses each number 768 times. The number that tells these kernels apart is arithmetic intensity: FLOPs per byte moved between memory and the processor. The add has 1/12, about 0.08.

Summing an f32 array does one add per 4-byte element. With 25 GB/s of bandwidth, what is the most GFLOP/s memory can feed it?

The intensity is 1 FLOP per 4 bytes. Multiply the bandwidth by the intensity.

25 · (1/4) = 6.25 GFLOP/s. A sum has three times the add's intensity, so memory can feed it three times as many FLOPs.

Two limits, one picture

Put both limits on one chart. Intensity runs across and speed runs up.

  1. The arithmetic ceiling. A processor can do only so many FLOPs per second. That is its peak. For a desktop with every core (each of its independent processors) working it is a few hundred GFLOP/s, and this page uses 200. It is a flat line, the same for every kernel.
  2. The memory slope. Memory can feed at most bandwidth · intensity FLOPs per second. At 25 GB/s, a kernel with 1 FLOP per byte gets 25 GFLOP/s and a kernel with 2 gets 50. It is a rising line.

A kernel has to stay under both lines, so its best possible speed is the smaller of the two. Pick a kernel and see which line it meets first.

A machine with a peak of 200 GFLOP/s and 25 GB/s of bandwidth

The thick line is a slope that meets a flat top, like a roof. That is why this chart is called the roofline. A kernel under the slope is memory-bound. A kernel under the flat part is compute-bound. The lines meet at 200 / 25 = 8 FLOPs per byte.

On this machine, what is the best speed in GFLOP/s for a kernel with 4 FLOPs per byte?

Work out the memory slope at 4 FLOPs per byte, then compare it with the ceiling of 200.

Memory can feed 25 · 4 = 100 GFLOP/s. That is under the ceiling of 200, so 100 is the best it can do, and it is memory-bound.

Which limit is a kernel hitting?

Every kernel gets the same five steps. Here they are for the 768×768 matrix multiply:

  1. Count the FLOPs. 2N³, about 906 million.
  2. Count the bytes. It reads two matrices and writes one. Each is 4N² bytes, so 12N² in all, about 7 million.
  3. Divide. The intensity is 2N³ / 12N² = N / 6, which is 128 FLOPs per byte.
  4. Find the memory slope. 25 · 128 = 3,200 GFLOP/s.
  5. Take the smaller. The ceiling is 200. This kernel is compute-bound.

So the roofline says loop A, at 10 GFLOP/s, could run 20 times faster. Step 2 assumed each number travels from memory once. Loop A fetches the same numbers again and again, and lesson 7.2 fixes that.

The roofline

Write attainable: the best GFLOP/s a kernel can reach, given the machine's peak and bandwidth and the kernel's FLOPs and bytes.

Measure honestly

Timing is noisy. Other programs run, the processor changes its clock speed, the first run warms the caches. Three habits make numbers trustworthy:

  • Time the kernel alone. Not the compiler, not loading the data. The harness reads a monotonic clock, one that only ever counts forward, just before and just after the kernel call.
  • Take the best of several runs. Noise almost always makes a run slower, so the minimum is the closest to the truth.
  • Compare on the same machine, at the same time. A number from your laptop and one from a server mean nothing side by side. The speed tests run your kernel and the reference kernel alternately, three times each, and compare the bests.

Three runs of one kernel take 31 ms, 30 ms and 44 ms. Which time, in ms, do you report?

Something else was running during the 44 ms run. Did that make the kernel itself slower?

30 ms, the best. The average, 35 ms, mostly measures whatever interrupted the third run.

How week 7 grades speed

A test with # speed: 0.5 requires your kernel to run at least half as fast as the reference compiler's kernel for the same program, built the same way, on your machine. It must also give exactly the reference's bits. Half is generous on purpose: the tests aren't measuring clever tricks, they're checking that your compiler does what the program's schedule says. Lessons 7.3 and 7.4 show that a renderer that ignores the schedule lands 2 to 8 times too slow.

A test says # speed: 0.5. The reference kernel's best time is 20 ms. What is the longest best time, in ms, that still passes?

Half the speed means twice the time.

20 / 0.5 = 40 ms. The rule is: your best time is at most the reference's best time divided by the number after speed:.

Bits first, then speed

Nothing this week changes what a program computes. Unrolling and threads must keep every add in its original order, so a fast kernel's output is identical to a slow one's. The C is compiled with -ffp-contract=off, which stops the C compiler from fusing a multiply and an add into one instruction. That fused instruction rounds once instead of twice, so it would change the bits.

What you can do now

  • Count a kernel's FLOPs and turn a time into GFLOP/s.
  • Count the bytes a kernel moves and work out its arithmetic intensity.
  • Draw the roofline from a machine's peak and bandwidth, and say whether a kernel is memory-bound or compute-bound.
  • Time a kernel so the number means something: alone, best of several, same machine.

How tools/bench.py counts FLOPs, for when your numbers differ slightly from this page

It counts one FLOP per element of each elementwise op, and size - result size per reduce, times the trip count of any hand-written loops around them. Movement ops and loads count zero. A matmul written as a multiply and a reduce is therefore N³ multiplies plus N³ - N² adds, slightly under the 2N³ used above, because a sum of 768 terms needs 767 adds.

What this simple model leaves out, for readers who know hardware

Caches. The bytes that count are the ones that travel from main memory. A kernel whose data fits in a cache is not held to the memory slope at all, which is why a small matrix multiply does not behave as memory-bound whatever its N / 6 says.

Writes cost more than 4 bytes. Before it writes to a cache line, a processor normally reads that line in. So the add really moves closer to 16 bytes per element than 12. The 25 GB/s on this page was computed with 12, from one thread.

Both limits depend on the core count. One core has a lower peak than all of them together, and several cores can pull more bytes per second than one. A careful roofline uses a peak and a bandwidth measured with the same number of threads.

Peak depends on the instructions used. A core that works on 8 floats per instruction has 8 times the peak of the same core working on one at a time.

Why does the grader take the best of three runs, not the average?

Can noise make a kernel faster than it really is?

Almost never. Interference slows a run down, and the rare speedups (a clock boost, a cache already warm) are small and also hit the reference. The minimum filters it out better than an average, which a single slow run would drag up.

Your renderer uses an instruction that does a·b + c with one rounding. What happens on the tests?

The spec says mul, then add, each rounded.

A fused multiply-add skips the rounding after the multiply. The result is often more accurate, and sometimes different in the last bit, which the bit-exact tests catch. That's why the harness passes -ffp-contract=off.
