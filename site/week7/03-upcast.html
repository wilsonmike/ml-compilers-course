Upcast: unrolling loops into registers

By the end of this lesson you can mark a small loop so that it is printed as straight-line C with no loop at all. That lets the C compiler keep a tile's running sums inside the processor and stop sending them to memory and back on every step. The answer stays the same, bit for bit. Only the speed changes.

Goal

Turn a loop with a small fixed bound into copies of its body, and say why that is faster and why it cannot change the result.

You'll use

Ranges and allocs that hold running sums (lesson 3.1 and 3.2), loops rendered as C (3.5) and tiling (7.2). The last exercise uses lists and strings (P.3).

Warm up

Two questions from the last two lessons, from memory. Pulling an idea back out of your head is what makes it stay.

A large matrix multiply does over 100 FLOPs for every byte it moves (lesson 7.1). What holds it back?

Many FLOPs per byte means the kernel needs few bytes for a lot of math.

It is limited by the arithmetic. Once tiling keeps the data close, memory is no longer the excuse. The arithmetic itself has to get faster, and that is this lesson.

Tiling works on a 4×8 block of outputs side by side (lesson 7.2). What happens to the order of the adds inside any one output's sum?

Tiling changed which sums run next to each other, not what happens inside one sum.

The order inside each sum is untouched, so every result keeps its exact bits. The same promise has to hold for everything in this lesson.

What a tiled loop still wastes

Here is a small loop with the same shape as a tile's inner loops. It keeps 4 running sums. The outer loop runs 3 times, and each time the inner loop adds one number from x to each sum, so sum i ends up as x[i] + x[4 + i] + x[8 + i]. This is the kernel the reference compiler prints for it with python _reference/uirc.py render:

void kernel(float *restrict b0, float *restrict b1) {
  float a3[4] = {0};
  for (int32_t r5 = 0; r5 < 3; r5++) {
    int32_t v6 = (int32_t)((uint32_t)r5 * (uint32_t)4);
    for (int32_t r7 = 0; r7 < 4; r7++) {
      float v9 = a3[r7];
      int32_t v10 = (int32_t)((uint32_t)v6 + (uint32_t)r7);
      float v12 = b0[v10];
      float v13 = (v9 + v12);
      a3[r7] = v13;
    }
  }
  for (int32_t r16 = 0; r16 < 4; r16++) {
    float v19 = a3[r16];
    b1[r16] = v19;
  }
}

a3 is the alloc that holds the 4 sums, and b0 is x. Read the inner loop. Its first line loads a sum from memory, and its last line stores the sum back. The add in between is the only real work. So every add drags along one load and one store whose only job is to remember a total.

The processor has a better place for a total. A register is one of a few dozen slots inside the processor that each hold one number, and reading or writing one causes no memory traffic at all. If the 4 sums lived in 4 registers, that load and that store would disappear.

Guess first. A machine instruction names its registers outright, the way you name a variable. There is no instruction for "register number r7". What can the C compiler do with a3[r7] when it cannot work out which values r7 takes?

A register cannot be indexed. An array in memory can.

It has to leave the array in memory, because only memory can be indexed by a number that changes. The compiler can swap an array element for a register only when it knows, while compiling, exactly which element each line touches.

Sometimes the C compiler works that out on its own. For this toy loop, gcc -O2 does. For the real tiled GEMM, with 32 sums inside three more loops, it does not get all the way, and the kernel runs several times slower than it could. Your compiler should not hope. It can print C where nothing is left to work out.

Upcast prints the loop as copies

A range can now say how its loop runs. That setting is called its axis:

%i = range 4 axis=upcast

An upcast loop is printed with no for. The renderer prints the body once for each value of the counter, with the counter replaced by that number. Writing a loop out as copies is called unrolling. Here is how the inner loop above gets unrolled:

  1. Read the bound. It is the literal 4, so there will be 4 copies.
  2. Copy the body. Print its lines 4 times, one copy after another.
  3. Replace the counter. In the first copy every r7 becomes 0, in the next 1, then 2, then 3.
  4. Drop the loop. No for line and no r7 are left.

Add axis=upcast to the inner range, render again, and the outer loop becomes:

  for (int32_t r5 = 0; r5 < 3; r5++) {
    int32_t v6 = (int32_t)((uint32_t)r5 * (uint32_t)4);
    float v8 = a3[0];
    int32_t v9 = (int32_t)((uint32_t)v6 + (uint32_t)0);
    float v11 = b0[v9];
    float v12 = (v8 + v11);
    a3[0] = v12;
    float v15 = a3[1];
    int32_t v16 = (int32_t)((uint32_t)v6 + (uint32_t)1);
    float v18 = b0[v16];
    float v19 = (v15 + v18);
    a3[1] = v19;
    float v22 = a3[2];
    int32_t v23 = (int32_t)((uint32_t)v6 + (uint32_t)2);
    float v25 = b0[v23];
    float v26 = (v22 + v25);
    a3[2] = v26;
    float v29 = a3[3];
    int32_t v30 = (int32_t)((uint32_t)v6 + (uint32_t)3);
    float v32 = b0[v30];
    float v33 = (v29 + v32);
    a3[3] = v33;
  }

Every index into a3 is now a plain number. a3[2] is always the same slot, so the C compiler can treat it as an ordinary variable and keep it in a register for the whole outer loop. The loads and stores of the sums are still written in the C, but the machine no longer has to perform them.

The bound of an upcast range must be a literal from 1 to 32, because the body is copied that many times.

A loop has range 8 axis=upcast and its body renders as 5 lines of C. How many lines does the unrolled loop print?

One full copy of the body for each value of the counter.

8 copies of 5 lines is 40 lines. Unrolled code is long. That is why render tests with upcast loops raise the C size limit with # max_bytes:.

Every rule for axis=, for when you write the parser and checker
  • range takes an optional axis= attribute: loop (the default, an ordinary loop as in week 3), upcast or thread (lesson 7.4). Any other name is rejected (rejected_axis_unknown).
  • An upcast bound is a literal from 1 to 32. The rule is about the program as written, not about what a simplifier could fold. The tests are rejected_upcast_not_literal, rejected_upcast_too_big and rejected_upcast_zero.
  • ./compile executes an upcast loop exactly like an ordinary loop, in order.
  • In render, emit the body once per value of the range, with the range a literal in each copy. Nested upcast loops multiply: a 4 loop around an 8 loop prints 32 copies.
  • Buffers never alias, so a kernel may declare its parameters restrict.

An axis never changes the result

This is the rule that makes axes safe to use: an axis changes how a loop runs, never what it computes. ./compile treats an upcast loop exactly like a plain loop. The rendered copies come in the same order the loop would have run, so every sum does the same adds in the same order and gets the same bits.

Check it on the example. With x holding the numbers 1 to 12 and plain loops, the four sums come out as [15 18 21 24].

Now the inner range is range 4 axis=upcast, and x is still 1 to 12. What is the first sum, x[0] + x[4] + x[8]?

Does the axis change which numbers are added, or in what order?

Still 1 + 5 + 9 = 15. The reference compiler gives [15 18 21 24] both ways. If an axis ever changes an answer, the compiler has a bug.

Now try it on a real program. The order of adds matters for floats, and the second test below is built to show it: 1e8 + 1 - 1e8 loses the 1 when added in that order. If upcast reordered anything, that test would catch it.

Write the unroller

In your compiler, unrolling belongs in the renderer, at the moment a loop is printed. The graph and the linearizer still see an ordinary loop, so every rule from earlier weeks keeps working untouched.

The printing itself is two loops: one over the counter's values, and inside it one over the lines of the body. Practice that on plain strings first.

Unroll a loop body

Write unroll n body. body is a list of C lines, where @ stands for the loop counter. Return the list of lines for the unrolled loop: the whole body with @ replaced by 0, then the whole body with 1, up to n - 1. Keep the lines of each copy in their original order.

Why unrolling does not disturb the accumulator rule, for when you build the lab

Week 3's rule for loads still decides where things run. In the tiled GEMM, the load of acc[ki*8 + kj] sits inside the k loop, because the k loop stores into the version it reads. Unrolling doesn't change that: it happens after linearizing, when you print C. Unroll in the renderer, not in the graph, and the rules from earlier weeks keep working untouched.

What it is worth, and when to stop

Measured on the 768×768 GEMM, on one thread, against the same loops without axes:

C compilerplain loopsupcast tilespeedup
clang 1998 ms23 ms4.2×
gcc 14148 ms82 ms1.8×

The two compilers differ a lot. Both get faster, and neither changes a bit of the result. The speed test for upcast alone, s_gemm_768_upcast, asks for at least 0.65 of the reference's speed. A renderer that prints upcast loops as plain for loops lands around 0.25 with clang and 0.55 with gcc, and fails.

Part of the gain is SIMD: one instruction that does 4 or 8 multiplies (or adds) on floats that sit next to each other. The eight B values for one row of a tile are neighbors in memory, so once the code is straight-line the compiler can use it. Each of those floats belongs to a different output with its own sum, so no sum's order changes.

Unrolling everything is not faster

Registers run out. An x86-64 processor has 16 vector registers, and at the grader's plain -O2 each holds 4 floats. Sums that do not fit spill back to memory. Code size grows too: the C for the full schedule is about 30 KB.

With 16 vector registers that hold 4 floats each, how many running sums can stay in registers at once, at most?

Registers times floats per register.

16 × 4 = 64. A 4×8 tile needs 32 sums, which take 8 registers and leave room for the loaded values. A 16×16 tile needs 256 sums, 64 registers' worth, so it spills and runs slower than a smaller tile.

The tiled GEMM's innermost loop before and after, for when you read your own rendered C

Here is the innermost loop of the tiled GEMM before and after, in the C your compiler emits (simplified):

/* plain loops: acc[] is indexed by variables, so it stays in memory */
for (int32_t ki = 0; ki < 4; ki++)
  for (int32_t kj = 0; kj < 8; kj++)
    acc[ki * 8 + kj] = acc[ki * 8 + kj] + A[(4*ib + ki) * K + k] * B[k * N + 8*jb + kj];

/* upcast: every index is a literal */
float a0 = A[(4*ib + 0) * K + k];   /* one A value per tile row: a0 .. a3 */
acc[0] = acc[0] + a0 * B[k * N + 8*jb + 0];
acc[1] = acc[1] + a0 * B[k * N + 8*jb + 1];
...
acc[31] = acc[31] + a3 * B[k * N + 8*jb + 7];

With constant indices and an array that never escapes, the C compiler replaces acc[0] to acc[31] with 32 variables, and those go in registers.

Check yourself

What does ./compile do differently for an upcast loop?

Do axes change results?

No axis changes what a program computes. Upcast is an instruction to the renderer: copy the body instead of looping.

Why can the C compiler keep acc[0..31] in registers after unrolling, but not before?

Can you write register[k] in machine code?

There's no "register number k" instruction. An array indexed by a loop variable needs an address in memory. With constant indices, the compiler treats each element as its own variable.

Is %r = range %n axis=upcast valid, with %n = add 4 4?

The spec says "a literal from 1 to 32".

The rule is about the program as written, not about what a simplifier could fold. The test rejected_upcast_not_literal checks it.

SIMD multiplies 8 adjacent floats in one instruction. Does that change any result's bits?

Which outputs share an instruction?

The 8 lanes are 8 different C[i][j]. Each lane's add rounds like the scalar add would. What would change bits is fusing a multiply and an add, which -ffp-contract=off forbids.
