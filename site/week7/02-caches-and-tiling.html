Week 7 · Lesson 2

Caches and tiling: reuse what you've loaded

You'll be able to say why plain matrix multiply loops are slow, and how tiling fixes it: do all the work you can with a number while it is close. Your compiler needs this because week 7's test programs are tiled, and it must run them fast without changing one bit of any result.

Goal

Count the loads a matrix multiply does, cut them down with tiles, and tell a safe reordering from one that changes a float result.

You'll use

Cache lines from lesson 0.2, the triple loop from lesson 0.5, the roofline from lesson 7.1 and the fact that f32 adds round, from lesson 4.2.

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

A cache line is 64 bytes. How many f32 values is that?

An f32 is 4 bytes.

64 / 4 = 16. Read one and the other 15 come along.

A kernel does very few FLOPs for each byte it moves. What holds it back?

Lesson 7.1: memory can feed bandwidth · intensity FLOP/s.

Low intensity means the processor waits for bytes. Keep this in mind: a kernel that moves the same bytes many times lowers its own intensity.

A puzzle from lesson 7.1

A 768×768 matrix multiply does over 100 FLOPs for each byte it needs, so the roofline says memory should not hold it back. Yet plain loops ran at 10 GFLOP/s and a good schedule at over 200, with the same arithmetic and the same bits.

The roofline counted every byte once. Plain loops don't move every byte once. They load the same numbers again and again, often from far away.

Recall the desk and the library shelf from lesson 0.2. The cache is the desk, main memory is the shelf, and a book is a cache line: you never carry one float, you carry 16. Suppose you fetch a book, read one page, put it back and come back later for the next page. You spend the day walking.

A real processor has several desks, each bigger and slower than the last:

levelsizetime to read
registersa few hundred bytesfree, as part of an instruction
L1 cache32 to 64 KB per coreabout 1 ns
L2 cache256 KB to 2 MB per coreabout 4 ns
L3 cache8 to 64 MB, shared10 to 20 ns
main memorygigabytesabout 100 ns

About how many times longer does a read from main memory take than a read from L1?

Divide the two times in the table.

100 ns / 1 ns = 100. The exact numbers vary by machine, but the ratios don't. So two habits make a kernel fast: use all 16 floats of every line you load, and use each number many times while it is still close.

Count the loads in plain loops

Here is the plain multiply, C = A · B, for N×N matrices. A load is one read of a number from memory. Every multiply-add needs two.

for i in 0 .. N-1:
  for j in 0 .. N-1:
    for k in 0 .. N-1:
      C[i][j] += A[i][k] * B[k][j]

Take N = 4. Over the whole run, how many times is the single element B[2][1] loaded?

Which outputs C[i][j] use B[2][1]? It needs k = 2 and j = 1.

4 times: once each for C[0][1], C[1][1], C[2][1] and C[3][1]. In general, N times.

Now look at how long the number waits between uses:

  1. Find who needs it. B[2][1] is used by every output in column 1, one per row i.
  2. Find the gap. After C[0][1] uses it, the loops finish row 0 and reach C[1][1]. That is N · N = 16 multiply-adds later.
  3. See what went by. Those 16 multiply-adds loaded every element of B once. The whole of B passed over the desk before B[2][1] was wanted again.

Now make N 768. Each element of B is loaded 768 times, and between two loads all of B goes by: 2.4 MB, more than L1 holds. So the number has left the near cache and comes back from 10 to 100 times farther away. Walking down a column of B also jumps 768 floats per step, so each load opens a new cache line and uses 1 of its 16 floats.

A is treated better. With N = 4, how many multiply-adds pass between two loads of A[0][2]?

A[0][2] is used by C[0][0], then C[0][1]. How long is one k loop?

4, one k loop. Row i of A is reused right away for the next j, so it stays on the desk. It is still a load every time, though: two loads for every multiply-add.

Tiling: do more with each trip

Tiling means working on a small block of outputs, a tile, at the same time. Take a tile of 4 rows by 8 columns of C. For one value of k:

  1. Load from A. 4 numbers, one per row of the tile.
  2. Load from B. 8 numbers, one per column. They sit side by side, in one or two cache lines.
  3. Use every pair. 4 · 8 = 32 multiply-adds, one for each output in the tile.

That is 12 loads for 32 multiply-adds. One output at a time needs 64. Each number is used several times while it is on the desk, and the tile's 32 running sums are small enough to stay there too.

N = 768 and tiles are 4 rows tall. How many times is one element of B loaded now?

One load serves all 4 rows of a tile.

768 / 4 = 192 loads in place of 768, and each one feeds 4 multiply-adds.

The loop order, tile by tile

Tiling is only a new loop order. Two outer loops pick a tile. Then k runs, and for each k two short loops visit every output in the tile:

for ib in 0 .. N/4 - 1:
  for jb in 0 .. N/8 - 1:
    for k in 0 .. N-1:
      for i in the 4 rows of tile ib:
        for j in the 8 columns of tile jb:
          C[i][j] += A[i][k] * B[k][j]

The innermost line is the same as before. Here C is 8×16, cut into four tiles, and k runs from 0 to 5. As you step, watch one output and ask in what order its terms arrive.

The rule: every sum keeps its order

Each output is a sum of N terms, and f32 adds round. Does it matter how the adds are grouped? Predict first.

One output's four terms are 100000000, 1, -100000000, 1. An f32 keeps about 7 digits, so 100000000 + 1 rounds back to 100000000. Added in order, left to right, the result is 1. Someone adds the first two terms, adds the last two terms, then adds the two halves. What do they get?

Work out each half first. Both halves round.

The halves are 100000000 and -100000000: each 1 is rounded away. They add to 0. In order, the big numbers cancel first and the last 1 survives.

The graders compare bits, so week 7 follows one rule:

The rule

You may change which sums take their turn first. You may not change the order of the adds inside any one sum. Then every result is bit for bit the same.

Tiling passes. Each C[i][j] still adds A[i][0]·B[0][j] first, then the k = 1 term, and so on. Only the turns of different outputs are interleaved.

A tiling that cuts k into blocks, sums each block alone and then adds the block sums does not pass. That is the two halves from the quiz: it regroups the adds, so the bits can change. The spec doesn't allow it.

Blocks that keep the order

dot adds its products in order. dot_blocks walks the same products in blocks of block, but it sums each block alone and then adds the block sums, so its bits can differ. Repair dot_blocks so it still walks block by block and always returns exactly what dot returns.

Add with a loop and +, not sum(). From Python 3.12, sum() of floats keeps extra precision as it goes, so its answer can differ from adding one float at a time, which is what the hardware and your compiler do.

A tiled GEMM in .uir

The week 7 tests write the tile out explicitly. Ranges ib and jb pick the tile, and three pairs of ranges (4 and 8) index inside it, one pair per step: ri, rj for the first product, ki, kj for the sums, and wi, wj for writing the tile out. A 32-element alloc holds the tile's sums:

%acc = alloc 32 dtype=f32
%ib  = range 192            # tile row: rows 4ib .. 4ib+3
%jb  = range 96             # tile column: columns 8jb .. 8jb+7
# start each sum from its first product, A[i][0]·B[0][j]
%ri  = range 4
%rj  = range 8
...
# then for k = 1 .. 767: for each (ki, kj) in the tile, acc[ki*8 + kj] += A[i][k]·B[k][j]
%k0  = range 767
%k   = add %k0 1
%ki  = range 4
%kj  = range 8
...
# finally write the tile to C
%wi  = range 4
%wj  = range 8
...

The lines left out are the index arithmetic, loads and stores. The exercise "Schedule a GEMM" in lesson 7.6 has the whole program, on an 8×5 by 5×16 GEMM with the same 4×8 tile.

Each tile's sums start from the tile's own first product, not from zero, for two reasons. First, it's the same order reduce folds in, so the result equals the matmul sugar's bit for bit. Second, there's a placement rule from week 3: a store that doesn't depend on jb runs outside the jb loop. A reset to 0.0 would run once for the whole program instead of once per tile. The first product depends on the tile's indices, so it lands inside the loop where it belongs.

How many tiles does this program compute?

One tile for each pair of ib and jb.

192 · 96 = 18432 tiles of 32 outputs each, which is all 768 · 768 outputs.

Loop order is the program's

Your compiler doesn't choose this order this week: the program spells it out, and your job is to render it faithfully and fast. Choosing tile sizes automatically is a scheduling problem the course comes back to. For now, notice that the order is a choice, and that a good one costs nothing in correctness.

What you can do now

  • Explain why plain loops are slow on a big matrix: each number of B is loaded N times, with all of B going by in between.
  • Count loads and multiply-adds for a tile, and write the tiled loop order.
  • State the rule: reorder which sums go first, never the adds inside a sum.
  • Spot a reordering that changes f32 bits, and repair it.

Writing a tile as loops is only a start. The big win comes next, in lesson 7.3, when the loops inside the tile are unrolled and the 32 sums become registers.

Cutting k into blocks safely, and what BLAS does (for the curious)

When a matrix is far larger than the cache, libraries also cut the k loop into blocks so that the part of A and B in use stays close. That can keep the bits, as your repaired dot_blocks shows: carry each running sum from one block of k into the next, and every sum still adds its terms in the order k = 0, 1, 2, ....

What changes the bits is giving each block its own fresh sum and adding the block sums at the end, or adding several terms at once in separate lanes. Libraries like BLAS do both for speed, which is one reason their results differ in the last bits from a simple loop's. This course keeps the order fixed, and the week 7 test programs tile only the outputs.

The C compiler follows the same rule. At -O2 it will not regroup float adds on its own, and the harness passes -ffp-contract=off so that a multiply and an add are never fused into one rounding.

A tile's sums are reset with store acc 0.0, a store that depends only on the in-tile ranges. What goes wrong?

Week 3: where does a store run?

A value or store runs inside every loop whose range it depends on, and no deeper. Starting from the first product A[i][0]·B[0][j] depends on the tile indices, so it runs once per tile.

Why not also split the k sum into blocks and add the blocks up at the end?

Is f32 addition associative?

No. (a + b) + c and a + (b + c) can round differently. Libraries like BLAS do reorder sums, which is one reason their results differ in the last bits from a simple loop's. This course keeps the order fixed.
