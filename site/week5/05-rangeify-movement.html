Rangeify movement ops

A movement op computes nothing. In this lesson you teach rangeify what to do with one: change the index, then ask the source. Once it can, your compiler turns lesson 5.4's matmul into two plain loops, and the big cube of products is never built.

Goal

Give the element at any index of a permute, expand, shrink, reshape and pad as index arithmetic on its source.

You'll use

The question "what is your element at i?" (lesson 4.3), row-major order and strides (5.1) and the movement ops themselves (5.2, 5.3).

In the exercises: a list comprehension with zip (P.3) and match on your own classes (P.4).

In the exercises: list functions like List.map2 (O.3) and match on your own types (O.4).

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

From lesson 4.3: what is the element at i of expand 2.0 [4]?

Every element of a broadcast is the same scalar.

The index is thrown away. No copy is built, and nothing is computed.

From lesson 5.1: a buffer of 12 numbers is read as shape [3 4], row-major. Which flat position holds element [2][1]?

Each row is 4 numbers, so row 2 starts at position 8.

2·4 + 1 = 9. The strides of [3 4] are 4 and 1: one step along axis 0 skips 4 elements.

A transpose computes nothing

Hand your compiler the matmul from lesson 5.4 and it stops at the first permute. It has no rule for it. Lesson 4.3 gave you the question to ask: what is your element at index i? A value now has several axes, so the index is a list with one entry per axis, like (i, j). Ask a transpose:

%m = reshape %v [2 3]
%t = permute %m [1 0]

%v holds 10 20 30 40 50 60. So %m is [[10 20 30] [40 50 60]], and %t has shape (3, 2).

The element of %t at (2, 1) is which element of %m?

A transpose turns rows into columns. %m has no row 2.

A transpose's element at (i, j) is the source's element at (j, i). Here that is %m at (1, 2), which is 60.

No add or multiply happened. The permute swapped the two index entries and passed the question on to its source, the value it was applied to.

A movement op only changes the question

Asked for its element at one index, a movement op asks its source for the element at another index. It computes no value and uses no memory. Each rule in this lesson says how to get the other index.

The general rule for permute %x [p0 p1 ...]: entry k of the index goes to axis p_k of the source. With order [2 0 1], index (1, 0, 2) asks the source at (0, 2, 1). It is a reordering, with no arithmetic at all.

expand drops an index, shrink adds an offset

%c has shape (3, 1) and holds 7 8 9, one number per row. %e = expand %c [3 4] repeats each row's number across 4 columns.

The element of %e at (2, 3) is %c at (2, ?). What is the missing entry?

How many elements does %c have along axis 1?

0. Axis 1 of %c has one element, at position 0. The 3 is thrown away, and the answer is %c at (2, 0), which is 9.

That is the rule for expand: every size-1 axis of the source is asked at 0, and the other entries pass through. Lesson 4.3's expand of a scalar is the same rule with every entry dropped.

shrink cuts a window that starts at an offset, so its rule adds the offset back. For %w = shrink %p 2 [5] on a 7-element %p:

  1. Take the index. Say %w is asked for element 4.
  2. Add the offset. 4 + 2 = 6.
  3. Ask the source. The answer is %p at 6.

With several axes, each entry gets its own axis's offset.

The source index of a movement op

src op idx answers one question: when a movement op is asked for its element at index idx, which index does it ask its source for? The Permute case is written. Fix the other two, which pass the index on unchanged. Expand shape carries the shape of the source, the value being expanded, so you can see which axes have size 1. Shrink offsets carries one offset per axis.

reshape flattens, then splits

Take the same %m = [[10 20 30] [40 50 60]], shape (2, 3), and reshape it: %r = reshape %m [3 2].

The element of %r at (1, 0) is which element of %m?

Reshape never moves a number. Write %r out in rows of 2.

%r is [[10 20] [30 40] [50 60]], so (1, 0) is 30. Swapping the entries would give 20, which is the transpose's answer, not the reshape's.

A reshape keeps every element at the same row-major position (lesson 5.2). So the position is the one thing both shapes agree on, and the rule goes through it:

  1. Flatten in the new shape. Shape [3 2] has strides 2 and 1, so (1, 0) is at position f = 1·2 + 0·1 = 2.
  2. Split in the old shape. Shape [2 3] has strides 3 and 1. The entry for an axis is (f div stride) mod size: the row is (2 div 3) mod 2 = 0 and the column is (2 div 1) mod 3 = 2.
  3. Ask the source. The answer is %m at (0, 2).

These are the first movement rules that cost anything: a few integer ops on the index. Here they are for index (2, 1). Guess each value, then change the 2 and the 1 on the first two lines to try another index.

Flatten, then split

Write the two halves of the reshape rule. flatten shape idx is the row-major position of index idx in shape. unflatten shape f goes the other way: the index, one entry per axis, of position f. reshape_src is written and joins them: flatten in the new shape, unflatten in the old one.

pad needs a mask and a clamp

pad %x [1 2] on a 3-element x = 1 2 3 gives 6 elements: 0 1 2 3 0 0. One zero went in front, so element i of the result lines up with x at i - 1.

At i = 5 that is x at 4, and x has no element 4. The result there must be 0. What should the loop do on that trip?

In C, is it safe to read past the end of a buffer if you never use the value?

Reading outside a buffer is undefined behavior in C, even when the value is thrown away. So the read itself has to stay inside.

So the pad rule has two parts. For l zeros on the left of an n-element source:

  • The mask picks the value. valid is true when l ≤ i < l + n, and the element is where(valid, the read, 0).
  • The clamp keeps the read legal. To clamp a number is to pull it back into a range: the read is at i - l clamped into [0, n - 1].

Step through all six trips. In the rendered C the counter is r9, x is b0 and the result is b1.

The mask doesn't make the read safe

The where throws the loaded value away outside the real elements, so it's tempting to drop the clamp and read b0[r9 - 1]. But the load still runs on every trip: at r9 = 0 it reads b0[-1], and at r9 = 5 it reads b0[4] of a 3-element buffer. The grader can't see this, because the bad value never reaches an output. Clamp first, then mask.

Pad: clamp and mask

Write the two halves of a padded read. For a pad with l zeros on the left of an n-element x: pad_valid(i, l, n) is 1 when position i lands on a real element and 0 otherwise, and pad_src(i, l, n) is the index to read, i - l clamped into [0, n-1]. Positions may be anywhere, including negative.

The oracle's C for this pad, for when you compare your renderer's output

Here is the oracle's C for pad %x [1 2] on a 3-element x, stored into a 6-element buffer:

for (int32_t r9 = 0; r9 < 6; r9++) {
  bool v11 = (0 < r9);
  bool v12 = (r9 < 4);
  bool v13 = (v11 ? v12 : false);                 /* valid: 1 <= r9 < 4 */
  int32_t v14 = (int32_t)((uint32_t)r9 + (uint32_t)-1);
  int32_t v15 = (v14 > 0 ? v14 : 0);             /* clamp below */
  int32_t v16 = (int32_t)((uint32_t)v15 * (uint32_t)-1);
  int32_t v17 = (v16 > -2 ? v16 : -2);
  int32_t v18 = (int32_t)((uint32_t)v17 * (uint32_t)-1);   /* clamp above: min(v15, 2) */
  float v20 = b0[v18];
  float v21 = (v13 ? v20 : 0x0.0p+0f);
  b1[r9] = v21;
}

There's no min op, so the upper clamp is written as -max(-x, -(n-1)).

Follow one question to the load

Movement ops stack up, and each one passes the question to the next. The asking ends at a load of a buffer, which answers with one scalar load, as in lesson 4.3. Ask the transpose from the start of the lesson for its element at (2, 1):

  1. Ask the permute. %t swaps the entries and asks %m for (1, 2).
  2. Ask the reshape. %m flattens (1, 2) in [2 3]: f = 1·3 + 2 = 5. Splitting 5 in %v's shape (6,) leaves 5.
  3. Ask the load. %v is a load, so the answer is a scalar load of buffer element 5, the 60.

Two ops, one load, and the only arithmetic was on the index.

Every rule needed a shape: strides for the reshape, sizes for the clamp, and the loop's bound for the store. So before rangeify asks anything, it works out the shape of every value in the chain.

The shape after a chain of movement ops

Given a starting shape and a list of movement ops, compute the final shape. Reshape and Expand give the new shape directly, Permute reorders axes, Pad adds a left and right amount per axis, and Reduce mReduce(m) drops the first m axes. The inputs are always valid.

Every index rule in one table, with stack, index and reduce, for when you write the lab

Week 5 asks week 4's question with an index tuple (i0, i1, ...), one entry per axis. A movement op answers by rewriting the tuple and passing the question to its operand:

opelement at (i0, ..., ik) becomes
reshapeflatten the index in the new shape (f = i0·stride0 + i1·stride1 + ..., row-major strides), then unflatten f in the old shape: axis k is (f div stride_k) mod size_k
permute [p0 p1 ...]the operand at the index whose axis p_k is i_k: just a reordering, no arithmetic
pad [l r ...]the operand at the clamped index clamp(i - l, 0, n - 1), then where(valid, that, 0), with valid = l ≤ i < l + n
shrinkthe operand at (i0 + o0, ...)
expandthe operand with every size-1 axis read at 0
stackitem i0 at the rest of the index: a chain of wheres on i0, or a plain C array index when the items are scalars
index x j0 ...the operand at (j0, ..., i0, ...): the js become its leading coordinates. On a stack of vectors that coordinate goes through the where chain, so with two items a j that isn't a constant renders as (j < 1 ? a0 : a1). The oracle renders a constant j the same way, with a constant condition like (1 < 1) that constant folding (lesson 1.3) could remove
reduce pop=mone accumulator loop over all m leading axes together: a flat counter t, unflattened into the m indices with div and mod

Eventually every question reaches a load of a rank-1 buffer, which answers with a scalar load at offset + i. Everything above it was index arithmetic.

A reduce over two axes, in the oracle's C, for when your pop=2 output differs

Here is reduce op=add pop=2 on a (2, 2, 3) value (a 12-element buffer, reshaped), stored into a 3-element buffer. The two popped axes make 4 combinations per output. The accumulator is seeded with the first, element (0, 0, n), and one loop folds in the other 3 in row-major order:

float a3[1] = {0};
for (int32_t r9 = 0; r9 < 3; r9++) {
  int32_t v11 = (r9 % 12);
  float v13 = b0[v11];
  a3[0] = v13;
  for (int32_t r17 = 0; r17 < 3; r17++) {
    float v18 = a3[0];
    int32_t v19 = (int32_t)((uint32_t)r17 + (uint32_t)1);
    int32_t v20 = (v19 / 2);
    int32_t v21 = (v20 % 2);
    int32_t v22 = (int32_t)((uint32_t)v21 * (uint32_t)2);
    int32_t v23 = (v19 % 2);
    int32_t v24 = (int32_t)((uint32_t)v22 + (uint32_t)v23);
    int32_t v25 = (int32_t)((uint32_t)v24 * (uint32_t)3);
    int32_t v26 = (int32_t)((uint32_t)v25 + (uint32_t)r9);
    int32_t v27 = (v26 % 12);
    float v29 = b0[v27];
    float v30 = (v18 + v29);
    a3[0] = v30;
  }
  float v34 = a3[0];
  b1[r9] = v34;
}

The flat counter t = r17 + 1 (v19) is unflattened in shape [2 2]: v21 = (t div 2) mod 2 on axis 0 and v23 = t mod 2 on axis 1. Then v26 = (i0·2 + i1)·3 + n flattens the full index in (2, 2, 3). For output n = 0 with the buffer holding 0..11: the seed is element 0, then t = 1, 2, 3 unflatten to (0, 1), (1, 0) and (1, 1) and read elements 3, 6 and 9, for a sum of 18.

The cube was never there

The syllabus matmul from lesson 5.4 (A stored transposed), with K = 2, M = 2 and N = 3, multiplies two values expanded to a (2, 2, 3) cube, then reduces over k. Rangeify makes this of it, names tidied up:

for (r = 0; r < 6; r++) {
  m = r / 3;
  n = r % 3;
  acc = a[0*2 + m] * b[0*3 + n];
  for (k = 1; k < 2; k++)
    acc = acc + a[k*2 + m] * b[k*3 + n];
  c[r] = acc;
}

Every line comes from a rule you know:

  • The store of the 6 results is one loop, and splitting r into (m, n) is the reshape rule.
  • The reduce is lesson 4.3's accumulator: seeded at k = 0, then a loop over the rest.
  • The mul asks both sides at (k, m, n). The expands drop n for a and m for b, and the reshapes flatten what is left to k·2 + m and k·3 + n.

The cube has 12 elements. How many of them does this C store in memory?

Look for an array of 12 floats in the code.

None. Each cube element is one multiply of two loads, done when the reduce asks for it and added straight into acc.

The oracle's exact C for this matmul, and why it prints C's / and %

The syllabus GEMM from lesson 5.4 (K = 2, M = 2, N = 3), after rangeify. The store of the [2 3] result became one loop over its 6 elements, and the reduce pop=1 became a seeded accumulator and a loop over the remaining K - 1 = 1 values of k:

float a4[1] = {0};
for (int32_t r11 = 0; r11 < 6; r11++) {          /* output element: (m, n) = (r11 / 3, r11 % 3) */
  int32_t v13 = (r11 / 3);
  int32_t v14 = (v13 % 2);
  int32_t v15 = (v14 % 4);
  float v17 = b0[v15];                          /* a at k = 0 */
  int32_t v18 = (r11 % 3);
  int32_t v19 = (v18 % 6);
  float v21 = b1[v19];                          /* b at k = 0 */
  float v22 = (v17 * v21);
  a4[0] = v22;                                  /* seed with the k = 0 product */
  for (int32_t r26 = 0; r26 < 1; r26++) {       /* k = 1 */
    float v27 = a4[0];
    int32_t v28 = (int32_t)((uint32_t)r26 + (uint32_t)1);
    int32_t v29 = (v28 % 2);
    int32_t v30 = (int32_t)((uint32_t)v29 * (uint32_t)2);
    int32_t v31 = (int32_t)((uint32_t)v30 + (uint32_t)v14);
    int32_t v32 = (v31 % 4);
    float v34 = b0[v32];
    int32_t v35 = (int32_t)((uint32_t)v29 * (uint32_t)3);
    int32_t v36 = (int32_t)((uint32_t)v35 + (uint32_t)v18);
    int32_t v37 = (v36 % 6);
    float v39 = b1[v37];
    float v40 = (v34 * v39);
    float v41 = (v27 + v40);
    a4[0] = v41;
  }
  float v45 = a4[0];
  b2[r11] = v45;
}

Inside the k loop, v28 = r26 + 1 is k, and v29 = v28 % 2 is its coordinate on the k axis of size 2. A's flat index is k·2 + m (v31, reusing v14 = m from the outer loop), and B's is k·3 + n (v36, reusing v18 = n). The two loads are multiplied and added into the accumulator.

The / and % here are .uir's div and mod. Those floor, while C's operators truncate, but the two only differ when an operand is negative. Every left operand here is provably non-negative and every divisor is a positive constant, so the oracle prints C's operators bare. Anywhere else it calls helpers that floor (the oracle names them i32_div and i32_mod), like the uir_div and uir_mod you wrote in lesson 2.4.

The [K M N] cube from lesson 5.4 is gone. Every element of it was a multiply of two loads, and rangeify only ever asked for the elements the reduce needed, one k at a time.

Cleaning up the index math: the leftover % 4 and % 6, for when you want smaller output

Above, look at v15 = (v14 % 4). v14 is (r11 / 3) % 2, which is always 0 or 1, so the % 4 does nothing. The same goes for v19 = (v18 % 6). These are the same leftovers as the % 4 line in lesson 4.3's reduce loop, and week 1 already gave you the tool to remove them: bounds analysis (lesson 1.4) proves v14 is in [0, 1], and the rule mod(x, c) → x when 0 ≤ x < c deletes the op. Constant folding (lesson 1.3) handles any arithmetic on constants that's left. The output is correct either way. Cleaner index math is smaller and, from week 7, faster.

Check yourself

A [6] value is reshaped to [2 3]. Element [1][2] of the result reads which flat position of the original?

Row-major strides for [2 3] are 3 and 1.

1·3 + 2·1 = 5.

A flat index f is unflattened in shape [2 3 4]. What is the coordinate on axis 1?

Axis 1's stride is the product of the sizes after it.

The stride of axis 1 is 4, so divide by 4, then take the coordinate mod its size, 3. For f = 23: (23 div 4) mod 3 = 2, and element 23 of a [2 3 4] is [1][2][3].

In the rendered pad loop above, which index of b0 does iteration r9 = 5 read?

5 - 1 = 4, then clamp into [0, 2].

2, the last real element. The mask then replaces it with 0, because position 5 is past the end of x.

Why does a rendered pad clamp the index when the mask already zeroes the value outside x?

Does where stop the load from happening?

No: both branches are evaluated, as in week 1. Without the clamp the loop reads b0[-1] and past the end, which is undefined behavior even if the value is thrown away.

In the rendered syllabus GEMM with K = 2, how many times does the inner accumulator loop run per output element?

The accumulator is seeded with the k = 0 product.

Once: r26 < 1. The reduce folds K values. The first seeds the accumulator, and the loop folds the remaining K - 1.

How does rangeify answer "your element at (k, m, n)" for expand %b3 [K M N], where %b3 has shape [K 1 N]?

Which axis of %b3 has size 1?

The size-1 axis is read at 0, so m is ignored. No memory is involved: expand is pure index rewriting.
