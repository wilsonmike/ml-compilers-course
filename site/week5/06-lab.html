Lab: movement ops

In this lab your compiler learns grids. It takes values of any rank, runs reshape, permute, pad and shrink, and turns each of them into index arithmetic when it renders C. You build it in the order the week taught it, and every step ends with something you can run.

What you are building

The same three commands as last week. What changes is which programs they take.

  • compile FILE judges programs whose values have any rank. Four ops are new: reshape, permute, pad and shrink on a value. expand, stack, index and reduce now work at any rank. Memory stays flat: buffers, views and params are still rank 0 or 1.
  • compile render FILE prints loops for those programs, in at most 20,000 bytes of C.
  • compile simplify FILE does not change.

The suite has 82 run tests and 34 render tests. The language contract is spec/uir-week5.md. If this page and the spec disagree, the spec wins.

A program loads 4 floats, reshapes them to [2 2], reshapes back to [4] and stores them. May its C have a for loop?

Last week a reduce or an expand allowed loops. Movement ops join that list.

Yes. Any movement op or value of rank 2 or more allows loops. The oracle prints one loop of 4 trips here.

The command-line contract for week 5, with every reason to print REJECTED

Nothing is new on the command line. What changes is which programs the commands accept, and when render may print loops.

commandweek 5 changes
your.exe FILE...Values may have any rank. reshape, permute, pad and value shrink are new, and expand, stack, index and reduce pop=m work at any rank. A program is rejected (print REJECTED FILE) for any of these: a reshape that changes the element count, a permute order that isn't a permutation, a pad list of the wrong length, a shrink offset that can't be proven in range, an expand that grows an axis that isn't size 1, a reduce popping more axes than the value has, storing a value whose shape isn't the view's (buffers stay rank 1), a param of rank 2 or more, a negative pad, more indices than axes, and stacking values of different shapes. An index that the bounds can't prove in range is rejected too, as in week 1: nothing fails at run time.
your.exe render FILEStill at most 20,000 bytes, bit-exact. for loops are allowed when the program has a range, any shape op (reduce, expand, stage, reshape, permute, pad, value shrink), an elementwise op on a shaped value, a value of rank 2 or more, or a rank-1 value with more than 32 elements. Otherwise it stays loopless, as in week 2.

Bounds analysis does not look inside the new ops. The result of a reshape, a permute, a pad, a value shrink, an expand or a reduce gets the full range of its dtype. A shape size is 1 or more, so reshape %v [6 0] is rejected.

How a render test is graded, step by step, and three things that bite this week

The same five steps as week 4. For each # render test the grader:

  1. Runs your.exe render FILE and fails the test on a nonzero exit.
  2. Fails the test if your output is over 20,000 bytes.
  3. Decides with the oracle whether loops are allowed (the rule above), strips comments and strings from your C, and fails the test on while, do, goto, or a disallowed for.
  4. Compiles your C with its own main: clang -std=c11 -O2 -ffp-contract=off -fsanitize=undefined -fsanitize-trap=undefined ... -lm.
  5. Runs it and compares every buffer with the oracle: i32 and bool exactly, f32 bit for bit, any NaN matching any NaN.

Three things bite this week. First, a reduce over several axes must fold them in row-major order, the same order the oracle uses, or f32 bits drift. Second, a padded read must clamp its index: an out-of-bounds read is undefined behavior even when the mask throws the value away. The sanitizer won't always catch it: clamp because the C must be correct. Last, a store into the buffer its own value reads, like r_inplace_transpose, must go through a temp ("Storing into the memory you read" in lesson 4.4). A fused transpose overwrites elements it still has to read.

Give a value any rank

YOURS is the path to your compiler in quotes. From the root of the course repo, run the new suite with your compiler as it is:

The last line should read 18 / 116 passed. Those are the rejected_ tests, and they pass by luck: your compiler rejects every grid.

  1. Lift the limit. A shape is a list of sizes of any length. ALU ops, where, cast and assert take operands of one shared shape. A store still needs the view's shape.
  2. Add reshape. reshape x [d0 d1 ...] has the shape in the list. The element counts must match. [] turns one element into a scalar.
  3. Keep one flat list. In your evaluator, a value is a shape and a flat row-major list. An elementwise op works position by position. A reshape keeps the list and swaps the shape.
  4. Stack any shape. stack takes items of one shape and adds an axis in front. The literal [[1 2] [3 4]] is a stack of stacks, and most tests assert against one.
  5. Take axes off the front. index takes up to one index per axis and drops that many leading axes. reduce gets pop=m, from 1 to the rank, 1 when left out. It folds the first m axes away, in row-major order, starting from the first element.

Run permute

First use a permute yourself.

Row sums with permute

Slot 0 holds a 2x3 i32 matrix, row-major. Store its two row sums into slot 1. The starter reduces the first axis directly, which gives column sums.

  1. Type it. permute x [p0 p1 ...] needs one entry per axis of x, and the entries must be every axis number exactly once. Size k of the result is x's size on axis p_k.
  2. Find the source index. For each index of the result, entry k goes to axis p_k of x.
  3. Tabulate. Walk every index of the result shape in row-major order, and copy the element at its source index into a new flat list.

Step 3 is the pattern for every movement op in the evaluator.

Run pad, shrink and expand

Three more rules, run the same way.

  1. Pad. pad x [l0 r0 l1 r1 ...] needs two amounts per axis, none negative. Each axis grows by its pair. The element at i is x[i - l] when every axis lands inside x, and zero anywhere else: 0, 0.0 or false.
  2. Shrink a value. shrink x o0 ... [s0 ...] with a value as its first operand takes one i32 scalar offset per axis. The element at i is x[i + o]. Use your week 1 bounds on each offset: its low end must be 0 or more, and its high end plus the window size must fit in the axis. A 3-wide window of 4 elements is accepted with an offset bounded 0 to 1, and rejected with 0 to 2.
  3. Expand at any rank. expand x [d0 ...] takes a scalar, or a value of the same rank as the list. Only size-1 axes may grow, and each one is read at 0.

Ask for an element with a list of indexes

Now render. In week 4, rangeify asked each vector for its element at i. Now the question carries a list, one scalar per axis.

  1. Change the question. "The element at" takes a list. A load of a view still takes one index, and an elementwise op passes the same list to each operand. The store loop from week 4 stays, because a stored value is rank 1.
  2. Write flatten and split once. Flatten takes an index list and a shape and builds the position with mul and add nodes. Split takes a position and a shape and builds each entry as (position div stride) mod size.
  3. Reshape. Flatten the list in the reshape's own shape. Split that position in the source's shape, and ask the source.
  4. Permute, expand and shrink. A permute sends entry k to axis p_k. An expand asks every size-1 axis of its source at 0. A shrink adds each offset to its entry.

Pad with a mask and a clamp

The rule for pad has two parts, and the grader can only see one of them.

  1. Build the mask. For each axis with l zeros before n real elements, the entry i is inside when l ≤ i and i < l + n. The mask is true when every axis is inside.
  2. Clamp the read. Each entry asks the source at i - l, clamped into 0 to n - 1. With l = 1, entry 0 reads at 0, not at -1.
  3. Select. The element is a where of the mask, the source's element and a zero of the dtype.

No test fails if you drop the clamp, because the bad value never reaches an output. Keep it: a read past a buffer is undefined behavior in C.

Fold several axes in one loop

The last piece. A reduce now folds the first m axes, and the rest of the index picks which fold you get.

%t has shape (3, 4, 5). How many trips does the loop for one element of reduce %t op=max pop=2 make?

The two popped axes hold 3 * 4 elements for each output. The first one is the seed.

11. Twelve elements are folded for each output. The first seeds the accumulator and the loop folds in the other 11.

  1. Seed. Asked at a list rest, store the operand's element at (0, ..., 0, rest) into a one-element alloc.
  2. Fold with one counter. Let T be the product of the popped sizes. Open a range T-1. Split the counter plus 1 in the popped shape, put those entries in front of rest, and fold that element in. Row-major order comes from the split.
  3. Read. Load the accumulator after the end.
  4. Finish the week 4 ops. An index puts its operands in front of the list. A stack asks each operand with the rest of the list and picks one by the first entry. A stage fills a flat temp with every element, and answers with a load at the flattened list.

Write your 10 tests

Put 10 tests in <your compiler repo>/tests/week5/, each aimed at a rule someone will get wrong. This one catches a transpose written as a reshape:

%x = stack 1 2 3 4 5 6
%m = reshape %x [2 3]
%t = permute %m [1 0]
%a = assert %t [[1 4] [2 5] [3 6]]

With six equal numbers the wrong compiler would pass too. Check your tests against the oracle:

python tools/test.py --check-tests <your compiler repo>/tests/week5 --week 5

Good targets: a transpose tested with distinct values (constant data hides every bug), a reshape after a permute versus before it, and a pad on the right only. What shape is a whole-buffer view?

The view has shape (4,) and the value (2, 2). The oracle prints REJECTED: "the value must match the view's dtype and shape".

Which of these makes the program REJECTED?

Count the elements before and after.

3 elements can't become 4. The oracle: "reshape keeps the element count: 3 != 4".

What is reduce %m op=add pop=3 on a value of shape (2, 2)?

pop counts leading axes, between 1 and the rank.

A rank-2 value has two axes to pop. The oracle rejects pop=3.

In the row sums exercise, why does reducing the (2, 3) matrix directly give column sums?

Which index varies along axis 0 of a row-major matrix?

Folding axis 0 combines m[0][j] with m[1][j]: one sum per column. Transposing first puts each row on axis 0.
