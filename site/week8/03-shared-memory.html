Shared memory and barriers

So far every thread did its work alone. In this lesson the threads of one block work together: each puts a value in the block's shared memory, they all wait, and then each reads what the others put there. Every fast GPU kernel your compiler writes will use this pattern, because it is how a block loads a tile once and reuses it.

Goal

Split a block's work into phases, say where the barrier goes, and tell which allocs are a block's shared memory.

Blocks, threads and shared memory from lesson 8.1, global and local loops and the same-expression rule from lesson 8.2, and load, store and after from lesson 2.2.

Warm up

Two questions from lessons 8.1 and 8.2, from memory. Pulling an idea back out of your head is what makes it stay.

Who can read and write a block's shared memory?

Global memory, shared memory, registers. Shared is the middle one.

Shared memory belongs to one block. All of that block's threads see it, and no other block does.

A kernel has 4 blocks b of 4 threads t. Which store offset gives every thread its own element?

The largest t is 3. The coefficient of b has to beat that.

4 is more than 3, the most t can add, so 4b + t is a different number for every block and thread. With b + t, block 0 thread 1 and block 1 thread 0 both write element 1.

A job one thread cannot do alone

In lesson 8.1 a block reversed 8 numbers in two moves, through shared memory, with a barrier between them. Here you see why it needs both, starting from a plan with neither. A block of 4 threads owns 4 elements of a buffer x, which hold [1 2 3 4]. The job is to reverse them in place: x itself should end as [4 3 2 1].

The obvious plan gives every thread one small job. Thread t reads its mirror element x[3 - t] and writes that value into its own element x[t]. All four threads run at the same time.

Suppose the threads happen to run in the order 0, 1, 2, 3, each one finishing before the next starts. What is x afterward?

Thread 2 reads x[1]. Which thread has already written x[1] by then?

Thread 0 writes 4 into x[0] and thread 1 writes 3 into x[1]. Then thread 2 reads x[1], which is now 3 and no longer 2. Thread 3 reads x[0], which is now 4. The 1 and the 2 were overwritten before anyone read them.

Two of the threads read a value that another thread had already overwritten. On a GPU it is worse, because nobody chooses the order. The answer depends on which thread gets there first, and it can change from one run to the next. That is a race, the same trouble as the lost update in lesson 7.4.

Lesson 8.2's rule already refuses this plan. One piece of code stores to x[t] and loads x[3 - t], and those are two different offset expressions for one buffer. So the threads have to work together.

Two phases with a wait between them

The fix is lesson 8.1's two moves. The block uses its shared memory as a scratch area. Call it sh. The work splits into two phases: steps that every thread of the block does, one phase after the other.

  1. Copy out. Thread t copies x[t] into sh[t]. Each thread touches only its own slot.
  2. Wait. No thread goes on until all four have finished their copy.
  3. Copy back, mirrored. Thread t reads sh[3 - t] and writes it into x[t].

The wait is the barrier from lesson 8.1, written __syncthreads() in CUDA: no thread of the block passes it until every thread has reached it.

In the last step a thread reads a slot that another thread wrote. Inside one phase that would be a race. After the barrier it is safe, because every slot was filled before any thread got past.

x starts as [1 2 3 4]. In the second phase, what number does thread 1 write into x[1]?

Thread 1 reads sh[3 - 1]. What did the first phase put in that slot?

The first phase copied the old x[2], which is 3, into sh[2]. Thread 1 reads it there. It no longer matters who has overwritten x[2], because nobody reads x in the second phase.

Step through the whole thing and check your answer against the last step.

Take the barrier away

Now delete step 2, the wait. Each thread does its copy out and goes straight on to its copy back. Some threads are faster than others.

Shared memory starts as all zeros. With no barrier, thread 0 finishes its copy out and starts its copy back while thread 3 has not copied anything yet. What does thread 0 write into x[0]?

Thread 0 reads sh[3]. Whose job was it to fill that slot?

Thread 3 fills sh[3], and it has not done so yet. Thread 0 reads the 0 that was there and writes it into x[0]. With the barrier, the answer was 4.

The hard part is that a missing barrier gives a wrong answer only sometimes. An SM runs a block's threads in warps of 32 (lesson 8.1). The threads of one warp usually run together, though nothing promises it. So a small block of one or two warps often gets lucky, and the test passes on your machine.

That is why the lab's suite includes a block of 1024 threads, c_reverse_shared_1024. Its 32 warps really do run at different times. The emulator runs every thread of a block as a real operating system thread with a real barrier, so a missing barrier shows up there too.

Phases in .uir

In .uir you never write a barrier. Consecutive local loops inside one global loop are the phases, and the gap between two of them is the barrier. Run as plain loops, the wait is automatic: the first loop ends before the second starts. On a GPU every thread runs both phases one after the other, so your compiler puts __syncthreads() in the gap. Lesson 8.4 does that.

Here is the reverse for 4 blocks of 8 threads, with the loop bodies left out:

%sh = alloc 8 dtype=f32
%b = range 4 axis=global
%t = range 8 axis=local
...
%e1 = end %s1 %t
%sh1 = after %sh %e1
%u = range 8 axis=local
...
%e2 = end %s2 %u
%eb = end %e1 %e2 %b
  1. The shared memory. %sh is an alloc that is used only inside the global loop.
  2. Phase 1. The loop %t. Thread t copies x[8b + t] into sh[t].
  3. The barrier. Nothing to write. %sh1 is the shared memory after all of phase 1.
  4. Phase 2. The loop %u. Thread u reads sh[7 - u] from %sh1 and writes o[8b + u].
  5. The block. Its end lists both phases.

Lesson 8.2's rule is checked one phase at a time. Phase 2 only reads sh, and memory that a phase only reads may be read anywhere. So a later phase may read anything an earlier phase wrote to shared memory.

One thing differs from the picture: this program writes its answer to a second buffer o and not back into x. The toggle below says why.

Reverse through shared memory

Phase 2 reads sh[u], so the program copies each block unchanged. Make it read the mirror slot.

Why the answer goes to o and not back into x

Buffers are different from shared memory. Other blocks run at the same time, and no barrier waits for them. So the kernel check, which proves blocks don't collide, covers all of a block's phases at once: every access to a buffer in the kernel uses the same offset expression. Loading x[8b + t] in phase 1 and storing x[8b + u] in phase 2 are two expressions, because %t and %u are two different loops, so .uir rejects the in-place version. Hand-written CUDA can reverse in place this way. The .uir rule is stricter than it has to be, in exchange for being simple to check.

With a second buffer, phase 2 could also read x[8b + 7 - u] directly, since x is only read. The exercise goes through sh because that is the shape of every tiled kernel: load a piece into fast shared memory once, wait, then let every thread read any part of it.

Write a second phase yourself

Now a phase from nothing, for a slightly different job: rotate each block of 4 left by one, so [1 2 3 4] becomes [2 3 4 1]. Thread u outputs the element of the thread to its right, and the last thread wraps around to the first. So thread u reads sh[(u + 1) mod 4].

Phase 1 is the same as before and is already written. Phase 2 needs four things:

  1. A loop. %u = range 4 axis=local. The bound matches phase 1, because a kernel has one block size.
  2. A load from shared memory. Through %sh1, at slot (u + 1) mod 4.
  3. A store to the output. At o[4b + u]. The starter's %m is already 4b.
  4. The ends. End the phase on %u, list both phases in the block's end, and finish with %o1 = after %o %eb.

Write the second phase

The starter has phase 1 only, so o is never written. Add phase 2 so that each block of 4 comes out rotated left by one: o[4b + u] gets sh[(u + 1) mod 4].

What counts as shared memory

One question is still open: what is in sh when a block starts?

An alloc sh of 1 element is used only inside a global loop of 3 blocks. In each block, phase 1 copies sh[0] to o[b], and phase 2 stores 9 into sh[0]. What is o at the end?

Can one block ever see what another block left in shared memory?

Every block starts with its own sh, all zeros. The 9 that a block stores is gone when that block ends. If blocks could see each other's leftovers, the answer would depend on the order they ran in, and .uir never allows that.

The rule: an alloc whose every load and store is inside one global loop is that block's shared memory. Each block gets its own copy, and each copy starts as all zeros. Block 0's sh[0] and block 1's sh[0] are different memory, so the check that keeps blocks apart skips shared memory.

./compile runs the blocks as a plain loop, so it sets the alloc back to zeros at the start of every block, just as week 7 did for a thread loop's private alloc.

An alloc that is used in two global loops, or anywhere outside one, is not shared memory. It is never set back to zero. ./compile and render treat it like a buffer, and render-cuda refuses the program with exit code 2, because that memory has nowhere to live on a GPU.

A real GPU does not hand a block clean memory. Shared memory may hold an earlier block's leftovers. So the kernel your compiler renders clears it first: every thread zeroes part of it, then comes a barrier, then phase 1.

Is this alloc shared memory?

Your compiler has to decide which allocs are shared memory. uses has one entry for each load or store of one alloc: Some g when it is inside global loop number g, or None when it is outside every global loop. The list is never empty. Write shared uses: true when every use is inside the same global loop. The starter says yes to everything.

The tests that check zeroing, for when you do the lab

For ./compile, the test block_shared_starts_at_zero checks that each block starts from zeros. plain_loop_alloc_carries_over runs the same program with plain loops, where the alloc keeps its contents from one iteration to the next.

For render-cuda, the rendered kernel has to zero its shared arrays, with every thread clearing part of them, and then a barrier. Skip that and, on a real GPU, a test like c_shared_dirty_then_fresh reads another block's leftovers. In the emulator, c_block_shared_fresh is the test that catches it.

Phases inside a loop, and why the last phase ends with a barrier too

A tiled GEMM puts its phases in a plain loop over tiles of k: load a tile of A and B into shared memory, multiply it in, then load the next. That needs a barrier at the end of the last phase too. Otherwise a fast thread starts loading tile k + 1 while a slow one is still multiplying tile k. That's why the CUDA renderer puts a barrier after every phase, including the last.

Check yourself

Phase 1 stores sh[t]. Phase 2, the next local loop, loads sh[7 - u]. Is that allowed?

What's between the two phases?

The barrier between phases guarantees every slot was written before any thread reads. The rule is checked within each phase, and phase 2 only loads sh, so it may load anywhere.

An alloc sh of 1 element is used only inside a global loop over b in 0..3. In each block, one phase adds 5 + 0·b to sh[0] (with one thread), and the next writes sh[0] to o[b]. What is o?

What does each block's shared memory start with?

Each block starts from zero: o = [5 5 5 5]. As plain loops, the alloc carries over and o would be [5 10 15 20].

Your CUDA forgets the barrier between two phases, and a test with a block of 32 threads passes on your GPU. Why?

How does an SM run a block's threads?

A race that doesn't show is still a race. The 1024-thread test and the emulator both catch it, and newer GPUs don't even promise lockstep within a warp.

Why does the rendered kernel zero its shared arrays before the first phase?

What does a GPU's shared memory hold when a new block starts on an SM?

The spec gives each block a fresh, zeroed copy. The GPU gives no such promise, so the kernel clears it, and a barrier makes sure the clearing is done before anyone reads.
