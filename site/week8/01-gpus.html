How a GPU runs code

You'll be able to picture how a GPU runs a loop: as thousands of threads, grouped into blocks, with three kinds of memory. Your compiler needs this picture because this week it starts to write programs for a GPU, and every rule in the next lessons comes from it.

Goal

Say which thread handles which element, what the threads of a block can share, and what each of a GPU's three memories is for.

Warm up

Two questions from week 7, from memory. Pulling an idea back out of your head is what makes it stay.

A thread loop has 192 iterations and the machine uses 8 threads, each with an equal chunk. How many iterations does one thread run?

Divide the iterations by the threads.

192 / 8 = 24. On a CPU, a few threads each do a lot of work. Today that turns around.

Two threads use the same memory at the same time. When is that a race?

Lesson 7.4: reads are free.

A race needs a write. Any number of threads may read the same memory. That rule holds on a GPU too.

What a GPU is

In week 7 a CPU ran the 768×768 matrix multiply on 24 threads. This week the same job runs on a GPU. Guess the scale first.

A CPU works on the matrix multiply with 24 threads at once. About how many does a GPU work on at once?

The matrix has 768 · 768 = 589,824 outputs. A GPU can give every output a thread of its own.

Tens of thousands. The week 8 kernel starts one thread per output, 589,824 in all, and the GPU keeps tens of thousands of them going at any moment. That count is approximate and depends on the program.

A GPU (graphics processing unit) is a chip with thousands of small workers that all run the same short program at once, each on its own piece of data. A CPU core is the opposite: there are few of them, and each is fast and can run anything.

GPUs were built to color millions of pixels with one formula. That is a loop whose iterations do not need each other, which is the kind of loop this course has been writing all along. It is also why almost all machine learning runs on GPUs, and why your compiler learns to write code for one.

One program, many threads

A GPU worker is called a thread, as on a CPU. The program they all run is a kernel: one function, run by every thread at the same time.

Nobody hands a thread its work. Each thread is given one thing, its own number t, and uses it to pick its share. Here is a kernel that doubles 8 numbers, run by 8 threads:

o[t] = x[t] * 2

All 8 threads run that line at the same time. Is there a race?

Do any two threads have the same t?

Every thread has a different number, so every thread writes a different element. This is the safe loop from lesson 7.4, with one thread per iteration.

That is the whole idea of a GPU kernel. The loop is gone. What used to be the loop index is now the thread's number.

A block: threads that share and wait

Some jobs need threads to work together. Take reversing 8 numbers in two moves. First, thread t copies x[t] into slot t of a small memory that all 8 threads can see. Then thread t reads slot 7 - t, which another thread filled, and writes it to o[t].

All 8 threads run both moves at their own pace. What can go wrong?

Thread 0 is quick and thread 7 is slow. What does thread 0 find in slot 7?

A fast thread reaches its second move while a slow one is still on its first, and reads an empty slot. The threads need a way to wait for each other.

A GPU gives threads both things, inside a group called a block. A block is up to 1024 threads that get:

  • Shared memory: a small, fast memory that only the threads of this block can see.
  • A barrier: a line in the kernel that no thread passes until every thread of the block has reached it. In CUDA, the language for NVIDIA GPUs, it is written __syncthreads().

With a barrier between the two moves, every slot is filled before any thread reads one.

A grid of blocks

One block holds at most 1024 threads, and the matrix multiply wants 589,824. So a kernel is started as a grid: many blocks, all the same size, all running the same kernel.

Now a thread knows two numbers: its block, written blockIdx.x in CUDA, and its place inside the block, threadIdx.x. Call them b and t. With blocks of 32 threads, thread t of block b handles element 32b + t. For thread 3 of block 1:

  1. Find where the block starts. Block 0 covers elements 0 to 31, so block 1 starts at 32 · 1 = 32.
  2. Add the thread's place. 32 + 3 = 35.

Blocks are kept apart on purpose. They run in whatever order the hardware likes, many at once. A block cannot see another block's shared memory, and no barrier waits for another block. So a block must never depend on another block.

In the exercise, two loops stand in for the grid: one pass of the inner body is one thread. A real GPU runs all the passes at the same time.

Give every thread its own element

launch runs a doubling kernel on a grid of blocks blocks of size threads. It is nearly right, but every block doubles the same first elements. Fix the one line that picks a thread's element.

Which thread owns an element

You can run the formula backward. Element 77, with blocks of 32 threads:

  1. Count the full blocks before it. 77 divided by 32 is 2, in whole numbers. The element is in block 2.
  2. Take what is left. Block 2 starts at 64, and 77 - 64 = 13. That remainder is the thread.

So division gives the block and the remainder gives the thread. The next lesson uses the same pair of operations to read one thread number as a row and a column.

Find the thread for an element

Write owner. It takes the block size size and an element i, and returns the pair (block, thread) that handles element i.

Warps: how the hardware runs a block

Blocks and threads are the model you program against. Underneath, the chip is made of units called streaming multiprocessors (SMs). The RTX 4060 Ti this course was tested on has 34 of them. A block runs on one SM from start to finish, and an SM runs a block's threads 32 at a time.

A block has 256 threads, and its SM runs them in groups of 32. How many groups is that?

Divide 256 by 32.

256 / 32 = 8. A full block of 1024 threads is 32 groups.

Each group of 32 is a warp. A warp's threads usually take every step together. An SM holds many warps and switches between them: when one warp is waiting for memory, it runs another. So a GPU is fast only when its SMs have plenty of warps with work to do.

Warps explain one trap. Different warps of a block run at different times, so a kernel that forgets its barrier may pass with a small block and fail with a large one.

Three kinds of memory

The data of a kernel lives in the GPU's main memory, called global memory. It is large, and far away: one read takes hundreds of cycles, where a cycle is one tick of the chip's clock.

The 256 threads of a block each need the same small group of numbers from global memory, many times over. Which plan is faster?

Week 7 had a trick for using a number many times while it is close.

One slow trip, then many fast reads. This is week 7's tiling, with the tile kept in a block's shared memory.

A thread can keep data in three places:

memorywho sees itsize and speedwhat it is for
globalevery thread of every block, and the host copies data in and outgigabytes, hundreds of cycles awaythe kernel's inputs and outputs
sharedthe threads of one blocktens of kilobytes per block, far faster than global memory but slower than registers (tens of cycles)a tile the whole block reads many times
registersone threadup to 255 registers (about 1 KB) per thread, the fastestthe values one thread is computing with

The host is the CPU program that starts the kernel. Shared memory is what makes a GPU kernel fast: load a tile from global memory once, wait at a barrier, then let every thread of the block read it many times.

The same bits as the CPU

The grader compares your GPU results with the interpreter, bit for bit, as it has every week. That works because each thread does the same operations in the same order as the CPU would. Two GPU habits would change bits, and the build turns both off.

  • Fused multiply-add computes a·b + c in one step and rounds once. The flag -fmad=false turns it off.
  • Fast division is quicker and less exact. The flag -prec-div=true, already the default, keeps it off.

Why does the course build CUDA with -fmad=false?

How many roundings does a·b + c have?

a·b + c as two operations rounds the product, then the sum. A fused one rounds only at the end. That's more accurate, but different, and the grader wants the interpreter's exact bits.

You don't need a GPU for this week. The grader has an emulator that runs your CUDA on the CPU, and lesson 8.5 shows the free and cheap ways to get a real one.

How each memory appears in .uir, for when you read the next lessons
  • Global memory holds the program's buffers.
  • Shared memory is an alloc used inside one global loop. Lesson 8.2 introduces global loops.
  • Registers hold values. The syllabus calls this address space ALU.
How fast the test GPU is and three measured kernels, for when you tune speed in the lab

The 4060 Ti does about 22 trillion float operations a second at its peak, and moves 288 GB a second from its global memory. Compare a CPU core: around a hundred billion, with SIMD. The catch is that all those threads need work and data at once. On a 512×512 GEMM, the tests measured:

kernel (512×512 GEMM, RTX 4060 Ti)timespeed
one thread per output, straight from global memory0.34 ms0.8 TFLOP/s
a block per row strip, a shared accumulator0.39 ms0.7 TFLOP/s
a 16×16 tile per block, loaded into shared memory0.17 ms1.6 TFLOP/s

The row-strip kernel is slower than the naive one even though it uses shared memory: each of its 512 blocks has only a few threads, so the SMs have too few warps to keep busy while they wait for memory. The tiled kernel is the one the speed test uses as its reference. All three are far from 22 TFLOP/s. Week 9's register tiling gets much closer while keeping the exact same bits, and pushing all the way to cuBLAS speeds takes tricks like fused multiply-add or float tensor cores that change rounding and can't keep these exact bits. A real CUDA library would allow both fused multiply-add and fast division and run a bit faster.

Check yourself

A kernel runs as blocks of 32 threads, and thread t of block b handles element 32b + t. Which element does thread 5 of block 2 handle?

Block 2 starts at element 64.

32·2 + 5 = 69. Blocks 0 and 1 cover elements 0 to 63.

Which threads can read a block's shared memory?

Shared memory lives on the SM running the block.

Each block gets its own copy of shared memory, on its SM, for as long as it runs. Other blocks can't see it. Data that must go from one block to another goes through global memory, in a later kernel.

Block 3 needs a value block 7 computes, in the same kernel. What's the problem?

What does __syncthreads() wait for?

A barrier waits for the threads of one block. Nothing in a kernel waits for another block, so block 7's results are only safe to read in a later kernel.

A thread keeps a running sum that no other thread needs. Where should it live?

Which memory belongs to one thread, and is the fastest?

Registers are private to one thread and the fastest of the three. Week 9 uses this to more than triple the speed of the week 8 kernel.
