Global and local loops

On a GPU, thousands of threads run the same code at once, and each one must pick its own piece of the work. In this lesson you write that in .uir with two new kinds of loop: one for the blocks and one for the threads of a block. You also learn the rule your compiler uses to prove that no two threads write the same element.

Goal

Write a kernel as a global loop around a local loop, and decide whether an offset gives every thread its own element.

Blocks and threads from lesson 8.1. Races and the slice rule from lesson 7.4. Loop axes from lesson 7.3.

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

In lesson 7.4, iteration r of a thread loop owns a slice of S elements that starts at r·S. With S = 4, at which element does iteration 2's slice start?

Iterations 0 and 1 own elements 0 to 7.

2·4 = 8. Iteration 2 owns elements 8 to 11 and nobody else touches them. Today you need the same promise for two indexes at once.

On a GPU, which threads can wait for each other?

Think of what a barrier, __syncthreads(), waits for.

A barrier waits for the threads of one block. Blocks run in any order, at the same time, and never wait for each other. So no block may write an element another block writes.

Which element is mine?

A kernel is the one function every GPU thread runs. Each thread knows two numbers: its block, b, and its place inside the block, t. From those two numbers it must work out which element to handle.

Take a tiny job: double 8 numbers with 2 blocks of 4 threads. That is 8 threads for 8 elements, so each thread should take exactly one.

Thread t (0 to 3) of block b (0 or 1) picks an element from 0 to 7. Which formula gives every element to exactly one thread?

Try block 1, thread 0 and block 0, thread 1 in each formula.

4b + t. Block 0 takes elements 0 to 3 and block 1 takes 4 to 7. With b + t, block 1 thread 0 and block 0 thread 1 both pick element 1.

Step through the three formulas below. Each box is one element and shows who writes it: 13 means block 1, thread 3.

With b + t two things go wrong at once. Elements 1, 2 and 3 each have two writers. That is a race, as in lesson 7.4: two threads write the same memory at the same time, so the result depends on timing. And elements 5, 6 and 7 have no writer, so those numbers are never doubled.

Two new axes

In .uir a kernel is still just loops. An axis says how a loop runs, and two new ones say which loop is which:

  • A global loop is the grid. Each iteration is one block. Blocks may run in any order, at the same time.
  • A local loop is the threads of a block. Each iteration is one thread, and they run at the same time. Its bound is the block size, a literal from 1 to 1024.

Here is the tiny job. The offset %i is 4b + t:

%b = range 2 axis=global
%t = range 4 axis=local
%m = mul %b 4
%i = add %m %t
...
%et = end %s %t
%eb = end %et %b

The local loop sits inside the global loop, and every store sits inside the local loop. Like week 7's axes, these two never change a single bit. Run as plain loops, the program means what it always did, so ./compile works as before.

Every rule on where global and local loops may go, for when you write the checker
  • A local loop sits inside a global loop, possibly inside plain loops in its body, and never inside another local loop.
  • Every local loop of one global loop has the same bound, because a kernel has one block size.
  • A global loop's body holds no thread loop, no other global loop and no local loop other than its own.
  • Every store inside a global loop is inside a local loop. A store outside one would run once on every thread.

Try other offsets

Real kernels use more creative offsets than 4b + t, and your compiler must accept the safe ones and reject the rest. Here is a bigger grid: 4 blocks of 4 threads writing 16 elements. Predict two offsets, then step through the figure to check.

4 blocks of 4 threads, offset 3b + t. What happens?

Block 0 writes elements 0 to 3. Where does block 1 start?

Fail. Block 1 starts at element 3, which thread 3 of block 0 also writes. Each block overlaps the next by one element.

Same grid, offset b + 4t: the two parts swapped. What happens?

Thread 0 of the four blocks writes elements 0, 1, 2 and 3. Where does thread 1 of block 0 write?

Pass. Each block's threads land 4 apart and the other blocks fill the gaps. The block does not have to be the big part.

An offset is a number with digits

Why do 4b + t and b + 4t pass when 3b + t fails? You learned the reason in grade school. It is place value.

Look at the number 37. The 7 is the ones digit, and a ones digit reaches at most 9. The 3 is the tens digit, and a ten is worth 10. Since 10 is more than 9, nothing in the ones place can ever add up to a ten. That is why two different pairs of digits never make the same number.

Now suppose a ten were only worth 9. Then the digits 1, 0 make 9, and the digits 0, 9 also make 9. Two different pairs, one number.

The offset 4b + t is a two-digit number. The ones digit is t, which reaches at most 3. The digit b is worth 4, which is more than 3. So different pairs of block and thread always land on different elements. In 3b + t, b is worth only 3, and t can reach 3 alone.

The digits do not all need the same size. In a time, a minute is worth 60 seconds and an hour is worth 3600. A number like that is called mixed-radix.

Threads t run from 0 to 15. In the offset c·b + t, what is the smallest c that keeps the blocks apart?

The most t can reach is 15. The block digit must be worth more than that.

16. With 15, block 1 thread 0 and block 0 thread 15 would both write element 15.

The rule for any number of digits

Write the offset as a sum of terms. A digit is a loop index times a positive literal, its coefficient. A loop of n iterations has largest value n - 1, so the most a digit can add is its coefficient times its largest value.

The rule: sort the digits by coefficient. Each coefficient must be greater than the most all the smaller digits can add up to. Then every combination of index values gives a different offset, so no two threads, of the same block or of different blocks, write the same element.

Try it on 20b + 4t + j, with 3 blocks, 5 threads, and a plain loop j of 4 iterations inside each thread. A loop inside a thread is a digit too, since one thread runs all its iterations.

  1. List the digits. b has coefficient 20 and largest value 2. t has coefficient 4 and largest value 4. j has coefficient 1 and largest value 3.
  2. Sort by coefficient. 20, then 4, then 1.
  3. Check each one. 4 is more than 3, the most j adds. 20 is more than 4·4 + 3 = 19. The offset passes.

With 16 in place of 20 it fails, because 16 is not more than 19. First repair the check for one coefficient, then write the whole rule.

Is this coefficient big enough?

fits c digits answers one question of the rule: is the coefficient c greater than the most the smaller digits can add up to? Each digit is a pair (coefficient, largest value). The function is nearly written, and it is wrong in two places. It adds up the coefficients and forgets the largest values. And it says yes when c only equals the total. Fix both.

Can two threads collide?

Write unique digits: true when the digits, sorted by coefficient from largest to smallest, form a mixed-radix number. Each digit is a pair (coefficient, largest value). A digit whose largest value is 0 is always 0, so skip it.

One index, two digits

Week 7's slice rule gave each iteration one unbroken slice. Real kernels need more. The 512×512 GEMM in the speed test has one global loop g of 1024 blocks, read as a 32×32 grid of tiles. g div 32 is a tile's row, by, and g mod 32 is its column, bx. The 256 threads of a block are read as 16×16 the same way, as ty and tx. Thread t of block g writes element

(16·by + ty)·512 + 16·bx + tx

So a block owns a 16×16 square, spread across 16 rows. The rule still works, because an index's div or mod by a literal k is a digit too. For a loop of n, the largest value is (n - 1) div k for a div, and k - 1 for a mod (or n - 1, if that is smaller).

A global loop has 100 blocks. What is the largest value of the digit g div 8?

The largest g is 99. Division rounds down.

99 div 8 = 12. And g mod 8 reaches at most 7.

Multiplied out, the GEMM's offset has four digits:

digitcoefficientlargest valuethe most it adds
by = g div 32819231253952
ty = t div 16512157680
bx = g mod 321631496
tx = t mod 1611515

8192 is more than 7680 + 496 + 15 = 8191. 512 is more than 511. 16 is more than 15. It passes.

One catch. The offset must pin down the index: it holds the index itself, or both its div k and its mod k by the same k. A lone t mod 4 with 8 threads passes the coefficient check, yet threads 0 and 4 write the same element.

The same expression, every time

One more rule. Within the code being checked, every access to one buffer must use the same offset expression: the same terms once the adds are flattened, in any order.

Equal digits are not enough. sh[t] and sh[t + 1] have the same digit, but if thread t stores to sh[t] and loads sh[t + 1], it reads its neighbor's slot while the neighbor may be writing it. Requiring the identical expression rules that out with no arithmetic. Your hash consing from lesson 1.1 makes each term a pointer, so the check compares two sorted lists of node ids.

A kernel loads o[t + 4*g] and then stores o[4*g + t]. Does that pass the same-expression rule?

The rule flattens the adds into a list of terms and ignores their order.

Both are the terms t and 4*g. Each thread reads and writes only its own element, which is safe.

The full rule with every special case, for when you write the checker in the lab

The rule is checked twice, on two pieces of code. Once per local loop, with t as the parallel index and the block fixed: do the block's threads collide? And once over the whole global loop body, with g as the parallel index: do the blocks collide? Loops inside the piece being checked count as digits too, since one thread runs all their iterations.

Five more parts complete the rule:

  • Terms that don't involve a loop of the code being checked are the same for every thread, so they're ignored: a constant, a loop outside the kernel, and for one phase (one local loop, lesson 8.3) also the block index and plain loops around the phase.
  • A vector access of k elements is a digit too: coefficient 1, largest value k - 1.
  • A term that involves an inner loop but isn't a digit, like i * j, counts as a digit of coefficient 1 whose largest value is its largest minus its smallest value, which your bounds analysis from lesson 2.3 computes. If such a term involves the parallel index, the access is invalid.
  • Coefficients are positive. 7 - t walks backwards through memory, which is perfectly safe, but the rule doesn't try to prove it.
  • The offset has to pin down the parallel index, unless its loop has one iteration: the index itself, its div 1, or both its div k and its mod k by the same k. o[0] written by every block is the plainest race there is. A lone t mod 4 is a quieter one: with 8 threads the digits pass, yet threads 0 and 4 write the same element. (A mod k with k larger than the index's largest value is the index itself, so it counts.)

The rule applies to every store, and to every load of memory the same code also stores into. Memory that's only read can be read anywhere: the GEMM's A and B are read by many blocks at once, which is fine. The same-expression rule also requires the same vector size on every access.

Check yourself

Blocks b in 0..7, threads t in 0..15. Which store offset is valid?

The largest t is 15. What must the coefficient of b beat?

The coefficient of b must be greater than 1·15. With 8, block 0 thread 8 and block 1 thread 0 both write element 8.

Is b + 4t valid, with b in 0..3 and t in 0..7?

The rule sorts the digits. It doesn't care which one is the block.

The threads of each block are spread out with stride 4 and the blocks fill the gaps between them. That's still a unique number. On a real GPU this layout is often slower, since neighboring threads write elements 4 apart (16 bytes for f32).

Blocks b in 0..1, threads t in 0..7. A store goes to o[8b + (t mod 4)]. Is it valid?

Which threads have the same t mod 4?

The coefficients pass, but the offset only sees t mod 4. Threads 0 and 4, 1 and 5, and so on write the same element. Adding the digit t div 4, as in 8b + 4·(t div 4) + (t mod 4), pins t down.

A local loop has 64 threads, and the offset uses t div 4. What is that digit's largest value?

The largest t is 63.

63 div 4 = 15. And t mod 4 has largest value 3.

In one local loop, thread t stores sh[t] and loads sh[t + 1]. Why is it rejected, when both offsets have the digit t?

Who writes sh[t + 1]?

Thread t + 1 stores into sh[t + 1] in the same phase, at the same time. The load would see the old or the new value depending on timing.
