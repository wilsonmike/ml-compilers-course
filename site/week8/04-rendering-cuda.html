Rendering CUDA

Your compiler can check and run block and thread programs, and it can print C for a CPU. It has never printed code for a GPU. Here you learn the four small changes that turn the C you already print into CUDA, the language NVIDIA GPUs run.

Goal

Read a program made of global and local loops and say, line by line, the CUDA your compiler prints for it.

You'll use

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

In lesson 7.5, what did render print for a thread loop?

Threads run functions, so the body had to become one.

The body moved into a function, thread0, and the harness ran it once per iteration. Today's kernel is the same move with different words.

A program has %b = range 2 axis=global and, inside it, %t = range 4 axis=local. How many threads does the GPU start in total?

A global loop counts blocks. A local loop counts the threads in each block.

2 blocks of 4 threads: 8 threads.

The same program, printed for a GPU

This program adds 1 to each of 8 numbers, with 2 blocks of 4 threads:

%x = buffer 8 dtype=i32 slot=0
%o = buffer 8 dtype=i32 slot=1
%b = range 2 axis=global
%m = mul %b 4
%t = range 4 axis=local
%i = add %m %t
%xv = shrink %x %i []
%xe = load %xv
%y = add %xe 1
%ov = shrink %o %i []
%s = store %ov %y
%e = end %s %t
%eb = end %e %b
%o1 = after %o %eb

python _reference/uirc.py --week=8 render-cuda FILE prints this for it (helper functions and one comment left out). One line is hidden:

__global__ void k0(int32_t *__restrict__ b0, int32_t *__restrict__ b1) {
  int32_t r5 = ________;
  int32_t v6 = (int32_t)((uint32_t)r5 * (uint32_t)4);
  {
    int32_t r7 = threadIdx.x;
    int32_t v8 = (int32_t)((uint32_t)v6 + (uint32_t)r7);
    int32_t v11 = b0[v8];
    int32_t v12 = (int32_t)((uint32_t)v11 + (uint32_t)1);
    b1[v8] = v12;
  }
  __syncthreads();
}

void kernel(int32_t *b0, int32_t *b1) {
  UIR_LAUNCH(k0, 2, 4, b0, b1);
}

r5 is the block counter %b. The thread counter r7 is read from threadIdx.x. What is hidden?

There is no for anywhere in the function. Each thread has to be told which block it is in.

The line is int32_t r5 = blockIdx.x;. The GPU starts every block and every thread itself, and tells each one its numbers.

CUDA is NVIDIA's language for its GPUs: C++ plus a few extra words. This page uses six of them: __global__, blockIdx.x, threadIdx.x, blockDim.x, __shared__ and __syncthreads(). Every other line is C your week 7 renderer already prints.

A global loop becomes a function and a launch

For the CPU, render treats a global loop like week 7's thread loop. For the program above it prints:

static void thread0(int32_t r5, void *ctx) {
  ...
  { thread0_ctx k_ = { b0, b1 }; uir_parallel_for(2, thread0, &k_); }

render-cuda makes the same two pieces:

__global__ void k0(int32_t *__restrict__ b0, int32_t *__restrict__ b1) {
  int32_t r5 = blockIdx.x;
  ...
  UIR_LAUNCH(k0, 2, 4, b0, b1);
  1. Mark the function. __global__ marks a function the CPU starts and the GPU runs, once on every thread. Such a function is called a kernel. Name them k0, k1 and so on.
  2. Pass the buffers. There is no struct. The buffers the loop uses are plain parameters. Find them the way you found free variables in 7.5.
  3. Read the counter. The counter is not a parameter. It is blockIdx.x, the number of the block this thread is in.
  4. Launch. In the host function kernel, which runs on the CPU, print UIR_LAUNCH(name, blocks, threads, buffers...).

A second global loop has 4 blocks of 2 threads and uses only buffer b1. What is its launch line?

Blocks come before threads, and a kernel takes only the buffers it uses.

Name, blocks, threads, then the buffers. The reference prints exactly this line for such a loop.

Open a kernel and launch it

kernel_open k counter params returns the first two lines of kernel number k, and launch k blocks threads bufs returns the line that starts it. Both are nearly written, but three places still print CPU code. Fix them so that kernel_open 0 "r5" [("int32_t", "b0"); ("int32_t", "b1")] gives the first two lines of the listing above and launch 0 2 4 ["b0"; "b1"] gives its launch line.

A local loop becomes a block of code

For the CPU, the local loop in the program is a plain loop:

  for (int32_t r7 = 0; r7 < 4; r7++) {
    ...
    b1[v8] = v12;
  }

On the GPU, each block already has 4 threads, and every one of them runs the kernel function from top to bottom.

What should that for line become in CUDA?

If all 4 threads ran all 4 iterations, how many times would each element be stored?

The threads are the iterations. A loop here would do the work 4 times over, with every thread writing every element.

So the reference prints a pair of braces and a barrier:

  {
    int32_t r7 = threadIdx.x;
    ...
    b1[v8] = v12;
  }
  __syncthreads();
  1. Open braces. They keep one phase's names apart from the next phase's.
  2. Read the counter. threadIdx.x is this thread's number inside its block.
  3. Print the body. The same lines as in the CPU loop.
  4. Wait. __syncthreads() is the barrier from lesson 8.3: no thread goes on until every thread of the block has arrived. Print it after every local loop, the last one too.

Lines outside a local loop, like v6, run on every thread. That is safe because they only compute values. It is also why lesson 8.2 forbade a store there: all 4 threads would do it.

Fuse phases into one thread body

Write fuse_phases: each phase becomes a block that reads its index from threadIdx.x, followed by a barrier. The starter prints each phase as a CPU loop. Change it.

Shared memory becomes a __shared__ array

Lesson 8.3 reversed each block through an alloc sh, its shared memory. In CPU C that alloc is one line inside the outlined function:

  int32_t a7[4] = {0};

Each call of the function is one block, so each block gets its own zeroed array.

A kernel function runs once on every thread. If it kept that line as it is, what would go wrong?

A variable declared inside a function is made new for each call. Who makes the calls now?

An ordinary array in a kernel belongs to one thread. The array has to be one per block, seen by all of its threads.

CUDA's word for one per block is __shared__. Here is what the reference prints at the top of the reverse kernel, right after the block counter:

  __shared__ int32_t a7[4];
  for (int32_t z_ = threadIdx.x; z_ < 4; z_ += blockDim.x) a7[z_] = 0;
  __syncthreads();
  1. Declare. __shared__, the element type, the name and the size.
  2. Clear your share. A __shared__ array starts with leftovers, not zeros. Each thread starts at its own number and steps by blockDim.x, the number of threads in a block. With 4 threads and 10 elements, thread 1 would clear elements 1, 5 and 9.
  3. Wait. A barrier, so nobody reads before every element is zero.

After that, loads and stores of sh are plain array accesses: a7[r9] = v13;.

Declare and clear shared memory

Write shared_lines ty name n. It returns the three lines that open a kernel's shared memory: the __shared__ array of n elements of C type ty, the loop in which each thread clears its share, and the barrier. shared_lines "int32_t" "a7" 4 gives exactly the three lines above.

Kernel form: what render-cuda accepts

Not every valid program can be printed this way.

Two global loops, one after the other, both store into the same alloc. ./compile runs the program fine. What does render-cuda do?

A __shared__ array belongs to one block of one kernel, and it is gone when the block ends.

The second kernel could never see what the first one stored. The alloc has nowhere to live on the GPU, so the program is refused.

A program is in kernel form when both of these hold:

  1. All work is inside kernels. Every computation sits inside a global loop, and every global loop is at the top level. A value computed outside would live on the CPU, where the GPU can't see it.
  2. Each kernel is self-contained. It uses only buffers, literals, its own ranges and its own shared memory.

For anything else, render-cuda prints one line to stderr and exits 2. For the program in the quiz, the reference prints:

invalid: render-cuda: an alloc used outside a single global loop has nowhere to live on the GPU

The program itself is still valid. ./compile runs it and render prints CPU C for it. Only render-cuda says no.

The same file runs with no GPU

Real CUDA launches a kernel with k0<<<2, 4>>>(b0, b1). Your output never prints that. It prints UIR_LAUNCH, and the harness says what that means. That one choice lets the same file run in two places:

  • With a GPU. The harness defines UIR_LAUNCH as the <<< >>> launch and builds your file with nvcc, NVIDIA's compiler. It copies the buffers to the GPU, calls your kernel and copies them back.
  • Without one. An emulator is a program that stands in for hardware you don't have. The harness builds your file as plain C++ and defines the CUDA words itself. UIR_LAUNCH is a loop over blocks, one after another. Each block's threads are real threads, a __shared__ array is one array they all see, and __syncthreads() is a real barrier.

So a missing barrier is a real race in the emulator too, and you can do the whole week on a laptop.

The emulator runs UIR_LAUNCH(k0, 2, 4, b0, b1). What is the largest number of kernel threads running at the same moment?

The emulator runs blocks one after another.

4: one block's threads. Block 1 starts only after block 0 has finished. A real GPU may run both blocks at once, which is why lesson 8.2 proved that blocks never touch the same element.

The whole reverse kernel, line by line, for when you write the lab

An i32 version of the reverse from lesson 8.3, 2 blocks of 4 threads. This is what the reference prints for it, without the helper functions at the top and one comment:

__global__ void k0(int32_t *__restrict__ b0, int32_t *__restrict__ b1) {
  int32_t r6 = blockIdx.x;
  __shared__ int32_t a7[4];
  for (int32_t z_ = threadIdx.x; z_ < 4; z_ += blockDim.x) a7[z_] = 0;
  __syncthreads();
  int32_t v8 = (int32_t)((uint32_t)r6 * (uint32_t)4);
  {
    int32_t r9 = threadIdx.x;
    int32_t v11 = (int32_t)((uint32_t)v8 + (uint32_t)r9);
    int32_t v13 = b0[v11];
    a7[r9] = v13;
  }
  __syncthreads();
  {
    int32_t r16 = threadIdx.x;
    int32_t v17 = (int32_t)((uint32_t)v8 + (uint32_t)r16);
    int32_t v19 = (int32_t)((uint32_t)r16 * (uint32_t)-1);
    int32_t v20 = (int32_t)((uint32_t)3 + (uint32_t)v19);
    int32_t v22 = a7[v20];
    b1[v17] = v22;
  }
  __syncthreads();
}

void kernel(int32_t *b0, int32_t *b1) {
  UIR_LAUNCH(k0, 2, 4, b0, b1);
}
  • __global__ marks a function the CPU launches and the GPU runs, once per thread. Its parameters are the buffers the kernel uses, which you find the same way as week 7's free names.
  • The global loop's index is blockIdx.x. There's no loop: the GPU starts every block.
  • The shared alloc is a __shared__ array. The threads clear it together, each taking every blockDim.x-th element, and wait.
  • Code in the global loop but outside a local loop, like v8, runs on every thread. That's fine, since it only computes values. Stores outside local loops are forbidden for exactly this reason.
  • Each local loop becomes a block of code where the index is threadIdx.x, followed by a barrier. The braces keep one phase's names apart from the next.
  • The host function kernel takes the program's buffers, which are already on the GPU, and launches each kernel in program order with UIR_LAUNCH(name, blocks, threads, args...).

Helpers like f32_max get __device__, so GPU code can call them. Everything between the braces is the C your week 7 renderer already writes for a loop body.

A program with several global loops: several kernels, launched in order

A program with several global loops launches several kernels, one after another. Each kernel takes only the buffers it uses. Here is the end of the reference's output, one comment left out, for a program with two global loops, the second of 4 blocks of 2 threads using only b1:

void kernel(float *b0, float *b1) {
  UIR_LAUNCH(k0, 2, 4, b0, b1);
  UIR_LAUNCH(k1, 4, 2, b1);
}

Each launch finishes before the next starts, so a later kernel may read anything an earlier one wrote. That's the barrier between blocks that lesson 8.1 said a kernel doesn't have. c_two_kernels checks it.

What render prints for the CPU, and the tests that check it

render still has to accept these programs. A global loop renders like week 7's thread loop: an outlined function run by uir_parallel_for, with the shared memory declared inside it so each block gets its own, zeroed. Local loops are plain loops, so phases are consecutive loops and need no barrier. The tests r_reverse_shared_cpu and r_gemm_tile_per_block_cpu check that.

Why the GPU's results match the CPU's bit for bit

Every thread does the same operations, in the same order, as the interpreter does for that iteration. The C you emit is unchanged. Two compiler flags keep the GPU's arithmetic exact: -fmad=false stops nvcc from fusing a multiply and an add, and -prec-div=true keeps division correctly rounded. The math helpers from week 6 are written with +, *, / and comparisons, so they come out the same too.

Check yourself

In CUDA, what replaces the for loop over a local range t?

How many threads does a block of 4 start?

The GPU starts one thread per iteration. Each one runs the body with its own threadIdx.x. The only loop left is the one clearing shared memory, where each thread clears every blockDim.x-th element.

Why doesn't your CUDA write k0<<<2, 4>>>(b0, b1) directly?

Who defines UIR_LAUNCH?

A C++ compiler can't read <<<>>>. Leaving the launch to a macro from the harness lets your output run on a GPU when there is one and on threads when there isn't.

A program computes %s = load %x0 at the top level and uses %s inside a global loop. What does render-cuda do?

Where would %s be computed, and can a kernel see it there?

Kernel form keeps the contract simple: everything is computed inside kernels. A real compiler would split the program into host and device parts. Ours leaves that for later.

How does the CPU render handle a global loop?

Blocks may run at the same time.

A block is an independent iteration with private memory, which is exactly a thread loop with a private alloc. The local loops inside stay plain loops, run by one CPU thread.
