Lab: GPU kernels

In this lab your compiler learns blocks and threads. It reads global and local loops, proves that no two threads write the same element, and prints CUDA with a new command, render-cuda. You need no GPU: the grader can run your CUDA in an emulator.

Goal

Pass all 42 week 8 tests with your own compiler, in the emulator or on a GPU, and write 10 tests of your own.

You'll use

Your compiler from the week 7 lab, and lessons 8.1, 8.2, 8.3, 8.4 and 8.5.

What you are building

Two commands learn two new axes, and one command is new.

  • compile FILE runs axis=global and axis=local as ordinary loops. It rejects a program that breaks the rules of lesson 8.2, and it gives each block fresh shared memory.
  • compile render FILE prints a global loop the way week 7 printed a thread loop.
  • compile render-cuda FILE prints CUDA: one kernel for each global loop.

The suite has 42 tests. 24 are run tests, and 16 of those are named rejected_. 3 are CPU render tests. 14 are CUDA tests, named c_. The last one, s_cuda_gemm_512, is a speed test. The language contract is spec/uir-week8.md. If this page and the spec disagree, the spec wins.

rejected_digits_exactly_touch.uir stores at o[2b + t] and has no assert. A compiler with none of the week 8 rules runs it. What does it print?

Week 1: what must a test end with?

A program with no assert is rejected whatever else is in it. None of the 16 rejected_ tests has an assert, so seeing REJECTED proves nothing this week.

What checks your rules is a second step. For each rejected_ test the grader also runs your render on the file, and passes the test only if it exits with code 2 and prints an invalid: line. So judge these tests by the grader's count, and run every rule in render too.

The command-line contract for week 8, with every new reason to print REJECTED
commandweek 8 changes
your.exe FILE...axis=global and axis=local run as plain loops, except that a block's shared memory starts at zero for every value of the global index. New REJECTED cases: a local bound that isn't a literal from 1 to 1024, a local loop outside a global loop or inside another local loop, local loops of different sizes in one global loop, another parallel loop inside a global loop, a store outside a local loop and an offset that breaks the mixed-radix rule.

your.exe render-cuda FILENew. Prints CUDA: a __global__ function per global loop, __shared__ arrays zeroed by the threads, each phase as a block on threadIdx.x followed by __syncthreads() and a host kernel that calls UIR_LAUNCH. Exits 2 if the program isn't in kernel form.
How each kind of test is graded this week
  • Run tests check the rules and the shared-memory semantics. Each rejected_ test is built around one rule, and its first line says which. digits_just_apart and rejected_digits_exactly_touch differ by one in a coefficient.
  • Render tests (r_ and local_bound_1024) compare your C's buffers with the interpreter, bit for bit, as in week 7.
  • CUDA tests (c_, header # cuda) run your render-cuda output on a GPU or in the emulator and compare every buffer with the interpreter, bit for bit. Four c_err_ tests (header # cuda: invalid) are valid programs that aren't in kernel form, and render-cuda must exit 2.
  • The speed test s_cuda_gemm_512 runs your CUDA and the reference's for the same 512×512 tiled GEMM on the GPU, three times each, alternating, timed with CUDA events. It needs the reference's bits and at least half its speed. Without a GPU it only checks that your CUDA builds.

Read the two axes

YOURS is the path to your compiler in quotes. Run the run tests with your compiler as it is:

python tools/test.py --compiler YOURS --week 8 -k run/

The last line should read 17 / 24 passed.

  1. Parse the words. range now also takes axis=global and axis=local.
  2. Check local bounds. The bound of a local range is a literal from 1 to 1024. A name, a 0 or a 1025 is rejected, in render too.
  3. Keep it on the range. Store the axis on the node. Everywhere else, treat both as plain loops for now.
Checkpoint

Check where the loops sit

These rules look only at how loops are nested. Check them in compile FILE and in render.

  1. Local needs global. A local loop is inside a global loop, directly or inside plain loops in its body. It is never inside another local loop.
  2. One block size. Every local loop of one global loop has the same bound.
  3. No other parallel loop. A global loop's body holds no thread loop, no global loop and no local loop other than its own.
  4. Stores stay inside. Every store inside a global loop is inside a local loop.
Checkpoint 
-k rejected_local          5 / 5 passed
-k rejected_thread_in      1 / 1 passed
-k rejected_store_outside  1 / 1 passed
-k run/                    14 or more of 24

Stuck? Open the toggle under "Two new axes" in lesson 8.2.

Keep threads and blocks apart

This is the mixed-radix rule, the largest step of the lab.

  1. Find the shared allocs. An alloc is shared memory when every load and store of it is inside one global loop.
  2. Pick the accesses. Check every store, and every load of memory the same code also stores into.
  3. Find the digits. Write the flat offset as a sum of terms. A digit is a loop index, or its div or mod by a positive literal, times a positive literal.
  4. Sort and compare. Each coefficient must be greater than the most all the smaller digits can add up to.
  5. Pin down the index. The offset holds the parallel index itself, or both its div k and its mod k.
  6. One expression per buffer. Every access to one buffer uses the same terms.
  7. Check twice. Once for each local loop, with its index as the parallel one. Once for each global loop's whole body, with the global index as the parallel one, skipping shared allocs.
Checkpoint 
-k rejected_  16 / 16 passed
-k run/       23 or more of 24

If -k run/ is below 23, your check rejects a valid program.

Stuck? Reread "The rule for any number of digits" and "One index, two digits" in lesson 8.2. Its last toggle lists every special case.

Give each block fresh shared memory

With -v, the last failing run test, block_shared_starts_at_zero, says expected MATCH, got MISMATCH. Its alloc carries one block's values into the next.

  1. Zero it per block. When compile FILE runs a global loop, set each of its shared allocs back to zeros at the start of every iteration, as week 7 did for a private alloc.
  2. Leave other allocs alone. An alloc used in two global loops, or outside one, keeps its contents.
Checkpoint 
-k run/  24 / 24 passed

Stuck? Reread "What counts as shared memory" in lesson 8.3.

Render for the CPU

Run -k render/r_. r_gemm_tile_per_block_cpu fails, because your C keeps one shared array for all the blocks and never clears it.

  1. Treat global as thread. Give a global loop to your week 7 outliner: a function, a struct and a call to uir_parallel_for.
  2. Treat shared as private. Declare each shared alloc inside the outlined function, so every block starts from zeros.
  3. Keep local loops plain. Two phases are two for loops in a row, so the barrier is automatic.

Print a kernel and its launch

Start from a copy of your C emitter and the smallest test: c_scale has one global loop, one local loop and no shared memory.

  1. Add the command. compile render-cuda FILE runs the same checks as render.
  2. Mark the helpers. Put __device__ on helper functions such as f32_max.
  3. Print a kernel. Each top-level global loop becomes __global__ void k0(...), then k1. Its parameters are the buffers it uses. Its counter is blockIdx.x.
  4. Print each local loop. An open brace, the counter set to threadIdx.x, the body, a close brace, then __syncthreads();.
  5. Print the host function. void kernel(...) takes the program's buffers and launches each kernel in program order with UIR_LAUNCH(name, blocks, threads, buffers...).
Checkpoint 
-k c_scale -v  1 / 1 passed
-k render/c_   4 or more of 14

Stuck? Reread "A global loop becomes a function and a launch" and "A local loop becomes a block of code" in lesson 8.4.

Add shared arrays

  1. Declare. Right after the block counter, print each shared alloc as a __shared__ array.
  2. Clear. A __shared__ array starts with leftovers. Print the loop in which each thread zeroes its share: it starts at threadIdx.x and steps by blockDim.x.
  3. Wait. Print __syncthreads(); after the clearing, before the first phase.

Two tests reverse each block through shared memory: c_reverse_shared with 2 blocks of 64 threads and c_reverse_shared_1024 with 3 blocks of 1024.

Checkpoint 
-k c_reverse       2 / 2 passed
-k c_block_shared  1 / 1 passed
-k render/c_       10 or more of 14

Stuck? Reread "Shared memory becomes a __shared__ array" in lesson 8.4.

Refuse what is not in kernel form

The four tests left are valid programs that no GPU could run as written. For them render-cuda must print an invalid: line to stderr and exit with code 2.

  1. All work is in kernels. Every computation is inside a global loop, and every global loop is at the top level. A thread loop is not a kernel.
  2. Each kernel stands alone. It uses only buffers, literals, its own ranges and its own shared memory. An alloc used by two kernels fails this.
Checkpoint 
-k c_err   4 / 4 passed
-k s_cuda  1 / 1 passed

Write your 10 tests

Put 10 tests in <your compiler repo>/tests/week8/, each aimed at a rule someone will get wrong. This one catches a coefficient that is one too small:

%o  = buffer 10 dtype=i32 slot=0
%b  = range 2 axis=global
%t  = range 5 axis=local
%m  = mul %b 4
%i  = add %m %t
%v  = shrink %o %i []
%s  = store %v 1
%et = end %s %t
%eb = end %et %b
%o1 = after %o %eb
%l  = load %o1
%w  = stack 1 1 1 1 1 1 1 1 1 0
%a  = assert %l %w

Thread 4 of block 0 and thread 0 of block 1 both write o[4]. This file ends in an assert, so only the rule can make it REJECTED. Give it a name that starts with rejected_, then check your tests against the oracle:

python tools/test.py --check-tests <your compiler repo>/tests/week8 --week 8

With only that file there, it prints 1 / 1 tests agree with the oracle.

Good targets for your tests

Good targets: an offset with div and mod digits that just fits, and one where a coefficient is one too small. A vector store whose size pushes it into a neighbor's slot. A later phase reading another thread's slot, and the same read in the same phase. Shared memory read before any phase writes it. A CUDA test with two kernels where the second reads what the first wrote.

Check yourself

Your render-cuda launches every kernel with 1 thread per block, and each thread loops over the whole local range. Which tests fail?

Do the bits change if one thread does every iteration in order?

One thread running the phases in order is exactly the plain loops, so every bit matches. Only the speed test sees it, and that's why there is one. This is one of the bugs planted in the reference to prove the suite catches it.

c_reverse_shared passes on your GPU but c_reverse_shared_1024 fails. What's the likely bug?

Lesson 8.3, "Take the barrier away".

The tests differ in block count, 2 against 3, and in block size, 64 threads against 1024. The block size is what matters here. A block of 1024 has 32 warps that run at different times, so a phase can start reading before another warp has finished writing.
