Getting a GPU, or not needing one

You do not need a GPU to finish this course. Every correctness test in weeks 8 and 9 runs in an emulator on any computer. A real NVIDIA GPU adds one thing, the speed tests. This lesson helps you pick a path and set it up.

Goal

Pick the way you will run your compiler's CUDA, set it up and see one week 8 test pass.

No GPU? You are not shut out

The grader comes with an emulator, a program that runs your CUDA on an ordinary processor. It is free, it works on Windows, Mac and Linux, and it checks every answer bit for bit. Without a GPU, a speed test only checks that your CUDA builds. You can finish the whole course this way.

No GPU: the emulator

The grader picks the emulator by itself when it finds no CUDA compiler. All you need is a C++ compiler, which you likely installed in week 0.

  1. Check your C++ compiler. Run these. At least one should print a version number. 
    clang++ --version
g++ --version
  2. Run one CUDA test. From the course folder, try the smallest one with the course's reference compiler. Running the reference is fine. Reading its source spoils the course. 
    python tools/test.py --compiler "python _reference/uirc.py --week=8" --week 8 -k c_scale -v
  3. Read the result. You should see: 
    1 / 1 passed
  4. Later, use your own compiler. In the lab, put your compiler's path after --compiler. Nothing else changes.

If you see no C++ compiler (clang++ or g++) for the CUDA emulator, and no nvcc, go back to step 1.

What is the one thing the emulator cannot tell you?

A processor taking turns is nothing like a graphics card.

Wrong bits, missing barriers and unzeroed shared memory all fail in the emulator. Speed cannot be measured, since a processor running 1024 threads per block is nothing like a GPU.

How the emulator works, for when a test fails only there

With no nvcc on your PATH and no --cuda-docker, the grader compiles your CUDA as C++ with clang++ or g++. Blocks run one after another. Each block's threads are real threads, __shared__ arrays are shared by them and __syncthreads() is a real barrier. A missing barrier is a real race in both the emulator and on a GPU.

Failure messages from the emulator say so: "your CUDA doesn't compile (as C++, in the emulator)", or "the emulated kernel didn't finish", which usually means a thread waits at a __syncthreads() the others never reach.

A gaming PC with an NVIDIA card

Your card can run every test, speed included. You need two things: the NVIDIA driver, the software that lets your computer talk to the card, and nvcc, NVIDIA's compiler for CUDA.

On Linux:

  1. Install the driver and the CUDA toolkit from NVIDIA's site. Use CUDA 11.8 or newer, 12.x preferred.
  2. Check both. nvidia-smi should list your GPU and nvcc --version should print a version.
  3. Run the grader as usual. It finds nvcc on its own.

On Windows, use Docker, a tool that runs a ready-made Linux setup in a box. It is simpler than a native build, and it is how this course was tested.

  1. Install a recent NVIDIA driver and Docker Desktop with the WSL 2 backend.
  2. Check that Docker sees the GPU. This should print a table with your card's name: 
    docker run --rm --gpus all nvidia/cuda:12.6.3-base-ubuntu22.04 nvidia-smi
  3. Give the grader a CUDA image. The first run downloads about 11 GB, one time. 
    python tools/test.py --compiler "C:/path/to/your.exe" --week 8 --cuda-docker nvidia/cuda:12.6.3-devel-ubuntu22.04

Your own compiler still runs on Windows. Only the CUDA build and run happen in the container.

On Windows with an NVIDIA GPU, what does --cuda-docker run inside the container?

Where does your compiler run?

Your compiler runs on Windows and writes the CUDA. The grader then builds and runs it in the CUDA image, with --gpus all giving the container your GPU.

Old toolkits, native Windows builds and the environment variable, for when setup fights you

Ubuntu's own nvidia-cuda-toolkit package is often too old to build for RTX 40-series cards, so install from NVIDIA's site.

Building CUDA natively on Windows needs Visual Studio's compiler, which is why Docker is the simpler route.

Setting the environment variable UIR_CUDA_DOCKER to the image name does the same as the --cuda-docker flag. If nvcc is on your PATH, the grader uses it and ignores the image.

A free notebook

A notebook is a web page that runs your commands on someone else's computer. Two services lend out a GPU for free, with limits.

  • Google Colab: choose Runtime, then Change runtime type, then a GPU. It is usually an NVIDIA T4. Free GPUs aren't guaranteed, and sessions end when idle.
  • Kaggle: about 30 GPU hours a week. In the notebook's settings turn on the GPU accelerator and internet access. Pick the T4, since the P100 lacks the tensor cores week 9 needs. Turning on internet access asks you to verify a phone number once.

Both need an account, and each service sets its own age rules. If you are a minor, ask an adult before you sign up.

  1. Check the GPU and get the course. A line starting with ! runs in a shell. 
    !nvidia-smi
!nvcc --version
!git clone https://github.com/wilsonmike/ml-compilers-course
    You should see a table with the GPU's name, then a version number.
  2. Upload your compiler's source and build it there.
  3. Run the grader with !python tools/test.py and your usual options, from the course folder.

A Python compiler runs as is.

An OCaml compiler needs opam installed in the notebook, which takes a while every session. For OCaml a rented machine is less hassle.

In a notebook, !nvidia-smi prints a GPU table but !nvcc --version says the command is not found. What does the grader do?

The grader looks for nvcc, not for a card.

A GPU without nvcc cannot build your CUDA. The grader then uses the emulator, the same as on a computer with no GPU. Pick a notebook image that has the CUDA toolkit.

Renting: read this before you pay

Some sites rent you a whole computer with a GPU by the hour. You control it from your own computer with SSH, a tool that opens a command line on a far away machine. Two such sites are Vast.ai, where independent hosts list their machines, and RunPod.

As of November 2026, an RTX 3090 or 4090 costs roughly $0.15 to $0.40 an hour on Vast.ai and about $0.35 to $0.70 on RunPod. These numbers are approximate and prices change weekly, so check before you start. This week needs an hour or two, so about a dollar.

Renting costs real money

If you are a minor, ask a parent or another adult first. It is their card and their choice. You never need to rent: the emulator is enough to finish the course.

Three rules that keep you safe
  1. Cap the cost. Add a small amount of credit and turn automatic top-up off. That limits what a forgotten machine can cost.
  2. Bring no secrets. A rented machine is someone else's computer, and the host can see what is on it. Bring only the course repo and your compiler. Never copy your private SSH key, a GitHub token, a password or an API key there.
  3. Shut it down. A running machine bills by the hour whether you use it or not. Stop it when you finish for the day. A stopped one usually still bills a little for its disk, so destroy it when the week is over.

Your compiler is all the machine needs. A token or a private key lets a stranger act as you. Clone public repos over HTTPS and copy results back with scp.

Renting: the steps

The steps are the same on both sites.

  1. Make an SSH key on your computer, if you don't have one: ssh-keygen -t ed25519. Accept the defaults. The public half is ~/.ssh/id_ed25519.pub.
  2. Make an account and add credit, a small amount with automatic top-up off.
  3. Add your public key in the account's SSH keys settings. Paste the contents of the .pub file, never the private one.
  4. Start a machine with any recent NVIDIA GPU and an image that has nvcc: a CUDA -devel image such as nvidia/cuda:12.6.3-devel-ubuntu22.04, or the provider's PyTorch template.
  5. Connect with the SSH command the provider shows. It looks like ssh -p 41234 root@203.0.113.7. Then run nvidia-smi and nvcc --version. You should see the GPU's name and a version number.
  6. Copy your work in. Clone the course with git clone. Copy your compiler from your computer with scp -P 41234 -r my-compiler root@203.0.113.7:~/. Install Python or OCaml as in week 0.
  7. Run the grader as on your own computer. It finds nvcc by itself.
  8. Stop or destroy the machine. Closing the SSH window does not stop the bill. Then check the site's dashboard to see that nothing is still running.

Which file do you paste into a GPU provider's SSH key settings?

Which one is safe to give away?

The public key lets the machine recognize you. The private key proves you're you, and it never leaves your computer.

Install commands and a RunPod setting, for when a step above fails

If the image lacks git, run apt update && apt install -y git first. Python is apt install -y python3 and OCaml starts with apt install -y opam.

On RunPod, pick a pod with a public IP and TCP port 22 exposed. Its default proxied SSH doesn't support scp or VS Code. RunPod's price depends on whether you pick its community or its secure cloud.

Editing on the rented machine with VS Code, and two settings to turn off first

To edit on the rented machine as if it were local, VS Code's Remote-SSH extension works well. Add the machine to ~/.ssh/config:

Host gpu
  HostName 203.0.113.7
  Port 41234
  User root
  ForwardAgent no

Then ssh gpu connects, and in VS Code "Remote-SSH: Connect to Host" lists gpu. Before connecting to a machine you don't own, turn off two VS Code settings that are on by default, remote.SSH.enableAgentForwarding and git.terminalAuthentication. Otherwise anyone with root there can use your SSH key and your Git login while you're connected.
