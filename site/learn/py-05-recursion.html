Recursion and functions as values

At the end of the last lesson, evaluate called itself to work out a tree. This lesson explains how that works, from the very start: what happens when a function calls itself, how Python keeps track, what goes wrong, and how to fix it. Then it shows that a function is a value like any other, which you can store, pass around, and build inside other functions.

A function that calls itself

A function is recursive when it calls itself. That sounds like it should go on forever, and it would, unless each call works on a smaller problem and there's a problem small enough to answer straight away. Here's a countdown:

def countdown(n):
    if n == 0:
        print("liftoff")
        return
    print(n)
    countdown(n - 1)
>>> countdown(3)
3
2
1
liftoff

Every recursive function has two parts:

  • The base case answers the smallest problem without calling itself. Here, n == 0 prints liftoff and stops.
  • The recursive step does a little work and calls itself on a smaller problem. Here, it prints n and counts down from n - 1.

Each call moves one step closer to the base case, so the calls must end. Here is every call that countdown(3) makes:

callnbase case?printsthen calls
13no3countdown(2)
22no2countdown(1)
31no1countdown(0)
40yesliftoffnothing, it returns

A loop could do the same countdown. Recursion earns its keep on problems that contain smaller copies of themselves, like trees, where a loop gets awkward. You'll get there in two sections.

Factorial and the call stack

The factorial of n, written n!, is 1 * 2 * 3 * ... * n. So 3! is 6, and 0! is 1 by agreement. The key fact is that n! is n times (n − 1)!. That's a smaller copy of the same problem, so it turns straight into code:

def factorial(n):
    if n == 0:
        return 1
    return n * factorial(n - 1)
>>> factorial(3)
6
>>> factorial(10)
3628800

This time each call needs an answer back before it can finish. factorial(3) can't multiply by 3 until factorial(2) has returned. So how does Python keep track of all the calls that are waiting?

Every call gets its own frame: a small record holding that call's variables (its own n) and the place to carry on from when the call it's waiting for returns. The frames sit on the call stack. A call adds a frame on the end, and a return removes it. Only the newest frame is running, and every frame above it is waiting. Step through it:

There are four n variables during this run, one per frame, each holding a different number. They don't clash, because each lives in its own frame. Here's the same run as a table, read top to bottom for the calls and bottom to top for the returns:

How to write one without tracing it

Tracing every call is good for learning, and tiring for real work. When you write a recursive function, trust that the call on the smaller problem returns the right answer, and ask only: "given that, is my answer right?" If factorial(n - 1) really is (n − 1)!, then n * factorial(n - 1) really is n!. Check the base case on its own, and you're done.

Recursion on a tree

Here are the expression classes from lesson 4 again. An Add holds two smaller expressions, and each of those may hold smaller ones still. A tree is made of smaller trees, so recursion fits it exactly.

from dataclasses import dataclass

@dataclass(frozen=True)
class Num:
    value: int

@dataclass(frozen=True)
class Add:
    left: "Expr"
    right: "Expr"

@dataclass(frozen=True)
class Mul:
    left: "Expr"
    right: "Expr"

Expr = Num | Add | Mul

e = Add(Num(2), Mul(Num(3), Num(4)))

To count the nodes in a tree: a Num is one node. An Add or a Mul is one node, plus all the nodes on its left, plus all the nodes on its right. The base case is the leaf, and the recursive step is the two children:

def count_nodes(e):
    match e:
        case Num(_):
            return 1
        case Add(left, right) | Mul(left, right):
            return 1 + count_nodes(left) + count_nodes(right)
        case _:
            raise TypeError(f"not an expression: {e!r}")
>>> count_nodes(e)
5
>>> count_nodes(Num(7))
1

Add(left, right) | Mul(left, right) is an or-pattern: it matches either class, and both sides name their fields the same way, so one case covers both. Here's the trace for e, with the calls listed in the order they finish:

callnodeleft givesright givesreturns
count_nodes(Num(2))leaf1
count_nodes(Num(3))leaf1
count_nodes(Num(4))leaf1
count_nodes(Mul(...))Mul111 + 1 + 1 = 3
count_nodes(Add(...))Add131 + 1 + 3 = 5

Change one line and the same walk answers a different question. To add up every number in the leaves, a Num gives its value instead of 1, and a parent adds its children's sums without the extra 1:

def leaf_sum(e):
    match e:
        case Num(v):
            return v
        case Add(left, right) | Mul(left, right):
            return leaf_sum(left) + leaf_sum(right)
        case _:
            raise TypeError(f"not an expression: {e!r}")
>>> leaf_sum(e)
9

Most tree functions you'll ever write have this shape: a case for the leaves, a case that calls itself on the children and combines the results, and a case _: that raises. evaluate from lesson 4 is one more of them. In week 1 your compiler walks its graph of nodes the same way, calling itself on each node's sources.

How deep is the tree?

Write depth(e): the number of nodes on the longest path from the top node down to a leaf. A lone Num has depth 1. Add(Num(2), Mul(Num(3), Num(4))) has depth 3: Add, then Mul, then a Num. The starter has the classes. Keep them as they are.

A node is one level, plus the deeper of its two children. max(a, b) gives the larger of two numbers.

Flatten nested lists

A list can hold other lists, which can hold lists too. That's a tree as well. Write flatten(items), which returns one flat list of all the non-list values, in order. flatten([1, [2, [3, 4]], 5]) is [1, 2, 3, 4, 5].

Go through items. isinstance(x, list) tells you whether an item is a list, which you flatten with a recursive call and add with extend: a.extend(b) adds every item of the list b to the end of a. Anything else is a leaf you append.

When recursion goes wrong

Forget the base case, and the calls never stop. Here's a countdown that never checks for zero:

def countdown(n):
    print(n)
    countdown(n - 1)

countdown(3) prints 3, 2, 1, 0, −1, −2, and on for about a thousand lines, and then Python stops it:

Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
  File "<stdin>", line 3, in countdown
  File "<stdin>", line 3, in countdown
  File "<stdin>", line 3, in countdown
  [Previous line repeated 993 more times]
  File "<stdin>", line 2, in countdown
RecursionError: maximum recursion depth exceeded while calling a Python object

That is Python 3.11. Other versions may show a slightly different count, or end the last line after "exceeded". Every call adds a frame, and frames take memory. To stop a runaway function from eating it all, Python limits how many frames can be on the stack at once. The recursion limit is 1000 by default:

>>> import sys
>>> sys.getrecursionlimit()
1000

When you see RecursionError, the first suspect is a missing or unreachable base case. Check that every call really gets closer to it. factorial(-1), for example, counts down −2, −3, and never hits 0.

The second cause is sneakier: the function is correct, and the input is deep. Here is a tree that is a long chain, 1 + (1 + (1 + ...)), 5000 levels deep:

chain = Num(1)
for i in range(5000):
    chain = Add(Num(1), chain)
>>> leaf_sum(chain)
Traceback (most recent call last):
  ...
RecursionError: maximum recursion depth exceeded

(The middle of the traceback, the repeated leaf_sum lines, is left out here.) leaf_sum is right. It needs about 5000 frames, one per level, and Python allows 1000. Programs that compilers read can be this deep, and one of the course's later tests is over two thousand lines long. There are two fixes.

Fix 1: raise the limit. sys.setrecursionlimit(10_000) allows 10,000 frames (the _ in a number only makes it easier to read), and then leaf_sum(chain) returns 5001. It's one line, and it's fine for a few thousand levels. But the limit was protecting something: set it very high, feed in a deep enough tree, and Python itself can crash, with no traceback to tell you why.

Fix 2: keep your own stack. The call stack holds "things still to do". You can hold them yourself, in an ordinary list, which is limited only by your computer's memory. Take a node off the list, deal with it, and put its children on the list to deal with later:

def leaf_sum(e):
    stack = [e]
    total = 0
    while stack:
        node = stack.pop()
        match node:
            case Num(v):
                total += v
            case Add(left, right) | Mul(left, right):
                stack.append(left)
                stack.append(right)
            case _:
                raise TypeError(f"not an expression: {node!r}")
    return total
>>> leaf_sum(e)
9
>>> leaf_sum(chain)
5001

stack.pop() removes and returns the last item, so the list works like the call stack: the newest thing added is the first one handled. while stack: keeps going until the list is empty. Here's the run on e = Add(Num(2), Mul(Num(3), Num(4))):

The leaves are visited in a different order than in the recursive version, and for a sum the order doesn't matter. When it does matter, as when a node must be handled after its children, it takes more care. Lesson 0.7 shows how.

Functions are values

In Python a function is a value, like a number or a string. def makes a function and stores it in a variable named after it. You can store it in another variable too, and call it through that name:

>>> def shout(s):
...     return s.upper() + "!"
...
>>> yell = shout
>>> yell("hi")
'HI!'

Without parentheses, shout is the function itself. With them, shout("hi") calls it. That means you can pass a function to another function, which calls it for you:

>>> def apply_twice(f, x):
...     return f(f(x))
...
>>> apply_twice(shout, "hi")
'HI!!'
>>> apply_twice(factorial, 3)
720

apply_twice(factorial, 3) works out factorial(factorial(3)), which is factorial(6), which is 720. apply_twice doesn't care which function it gets, as long as it can be called with one argument.

You've seen this before: sorted takes a key= function. It calls the function on every item and sorts by what comes back.

>>> words = ["pear", "fig", "banana"]
>>> sorted(words)
['banana', 'fig', 'pear']
>>> sorted(words, key=len)
['fig', 'pear', 'banana']

Often the key you need is a one-off, too small to deserve a def and a name. A lambda is a small function written in place: lambda w: -len(w) is a function that takes w and returns -len(w). Its body is one expression, and its value is returned without a return.

>>> sorted(words, key=lambda w: -len(w))
['banana', 'pear', 'fig']
>>> sorted(words, key=lambda w: w[-1])
['banana', 'fig', 'pear']

The first sorts longest first, since a bigger length gives a smaller key. The second sorts by last letter: a, g, r.

Pass the function, don't call it

sorted(words, key=len()) calls len with no arguments right away, before sorted ever runs, and fails with TypeError: len() takes exactly one argument (0 given). Write key=len, without parentheses, so sorted gets the function and calls it itself.

Functions that make functions

A function can define another function inside itself and return it. The inner function can still see the outer function's variables, even after the outer one has returned. Here's a function that makes counters:

def make_counter():
    count = 0
    def next_number():
        nonlocal count
        count += 1
        return count
    return next_number
>>> c = make_counter()
>>> c()
1
>>> c()
2
>>> d = make_counter()
>>> d()
1
>>> c()
3

Slowly: each call to make_counter() runs its body once. It makes a fresh count set to 0, defines next_number, and returns it without calling it. The returned function keeps hold of that count. Calling c() adds one to it. d came from a second call, so it has a count of its own, and counting with d doesn't move c.

A function bundled with the outer variables it uses is called a closure. nonlocal count says "the count I change here is the outer one". Without it, count += 1 would make Python treat count as a new variable belonging to next_number, and the first call would fail with UnboundLocalError: cannot access local variable 'count' where it is not associated with a value. You only need nonlocal to assign to an outer variable. Reading it, or changing a dict it names, works without.

This shape is worth knowing: lesson 1.1 asks you to write a function that returns a node-making function with its own private dict inside.

Remembering answers with a cache

The Fibonacci numbers start 0, 1, and each one after is the sum of the two before: 0, 1, 1, 2, 3, 5, 8, 13. That's a recursive definition with two base cases. To see how much work it does, this version counts its calls in a variable outside the function (global calls lets it change that variable, as nonlocal did above):

>>> calls = 0
>>> def fib(n):
...     global calls
...     calls += 1
...     if n < 2:
...         return n
...     return fib(n - 1) + fib(n - 2)
...
>>> fib(20)
6765
>>> calls
21891

21,891 calls to find one number. fib(20) calls fib(19) and fib(18). But fib(19) calls fib(18) again, and each of those calls fib(17), and so on. The same small answers are worked out over and over. The fix is to remember each answer the first time. functools.cache is a decorator that does this: it keeps a dict from arguments to results, and a repeated call returns the stored result without running the function.

>>> from functools import cache
>>> calls = 0
>>> @cache
... def fib(n):
...     global calls
...     calls += 1
...     if n < 2:
...         return n
...     return fib(n - 1) + fib(n - 2)
...
>>> fib(20)
6765
>>> calls
21
nfib(n)calls without cachecalls with cache
55156
105517711
20676521,89121
2575025242,78526

With the cache, each n from 0 to 20 runs once, so 21 calls. Without it, the count grows by about 1.6 times for each step of n. The arguments become dict keys, so they must be hashable: a frozen dataclass works, a list doesn't. Remembering results like this is called memoization, and you'll use it in week 1 to avoid walking the same part of a graph twice. Lesson 0.7 explains when a plain dict you manage yourself is the better memo.
