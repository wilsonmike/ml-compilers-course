Lists and pattern matching

A list holds many values of one type, in order. Pattern matching takes a value apart by its shape. Together with recursion they are the heart of everyday OCaml, and the same three ideas will walk the trees in your compiler.

Lists

A list is written with square brackets, and the elements are separated by semicolons:

# [1; 2; 3];;
- : int list = [1; 2; 3]
# ["milk"; "eggs"; "bread"];;
- : string list = ["milk"; "eggs"; "bread"]
# [];;
- : 'a list = []

Read int list as "a list of ints". The empty list [] has type 'a list, a list of anything, because there is nothing in it yet to say which type.

Every element of a list must have the same type. A list of ints can't hold a string:

# [1; "two"];;
Line 1, characters 4-9:
1 | [1; "two"];;
        ^^^^^
Error: This expression has type "string" but an expression was expected of type
         "int"

Why so strict? Because then any code that takes an int list knows that every element is an int, and OCaml can check that code once, for all lists. You never have to ask "but what if this one is a string?". When you really do need a mix of kinds, you define a type that lists the kinds (lesson O.4), and the list holds that type.

Semicolons, not commas

Most languages write [1, 2]. In OCaml that is a list with one element, a pair. The comma makes a tuple (more on those below), so OCaml quietly builds something else, and you find out later from a type error somewhere else.

# [1, 2];;
- : (int * int) list = [(1, 2)]
# [1, 2, 3];;
- : (int * int * int) list = [(1, 2, 3)]

Read the type: (int * int) list, a list of pairs. If you meant three ints, the type tells you right away. Make a habit of reading the type of every list you type in utop.

How a list is built: ::

Under the square brackets, a list is a chain of small cells. Each cell holds one element and points at the rest of the list. The last cell points at the empty list []. The operator :: (say "cons", short for "construct") makes one new cell in front of an existing list:

# 1 :: [2; 3];;
- : int list = [1; 2; 3]
# 1 :: 2 :: 3 :: [];;
- : int list = [1; 2; 3]

[1; 2; 3] is only a nicer way to write 1 :: 2 :: 3 :: [], which is 1 :: (2 :: (3 :: [])). In memory it looks like this:

[1; 2; 3]

 +---+---+    +---+---+    +---+---+
 | 1 | o-+--->| 2 | o-+--->| 3 | o-+---> []
 +---+---+    +---+---+    +---+---+
  head  rest

Each box is one cell. The left half is the head, the element. The right half points to the rest of the list (also called the tail). To reach the third element, you follow two arrows. That is why a list is good for going through elements one by one from the front, and slow for "give me element number 5000".

Lists are immutable: once made, a cell never changes. So adding to the front doesn't touch the old list. It makes one new cell that points at it:

# let a = [2; 3];;
val a : int list = [2; 3]
# let b = 1 :: a;;
val b : int list = [1; 2; 3]
# a;;
- : int list = [2; 3]
b ---> +---+---+
       | 1 | o-+--+
       +---+---+  |
                  v
a ------------> +---+---+    +---+---+
                | 2 | o-+--->| 3 | o-+---> []
                +---+---+    +---+---+

b and a share the cells for 2 and 3. That is safe only because nobody can change them, and it makes :: fast: one new cell, however long the list is. You'll see this idea again in week 1, where many parts of a compiler's graph share the same nodes.

Tuples

A tuple groups a fixed number of values, which may have different types. You write it with commas, usually in parentheses:

# (3, "apples");;
- : int * string = (3, "apples")
# ("Ada", 36, true);;
- : string * int * bool = ("Ada", 36, true)

The type int * string reads "an int and a string". The * here means "and", not multiplication. A list and a tuple differ in two ways: a list can have any length but one type, and a tuple has a fixed length but each position can have its own type. A shopping list is a list. One line on it, a quantity and an item, is a tuple.

To get the parts out, fst and snd work on pairs. More often you name the parts with a pattern:

# let pair = (3, "apples");;
val pair : int * string = (3, "apples")
# fst pair;;
- : int = 3
# let (n, fruit) = pair;;
val n : int = 3
val fruit : string = "apples"

let (n, fruit) = pair says "pair has the shape of two things, call them n and fruit". That is your first pattern: a shape with names in it. The next section does the same thing for lists.

Pattern matching

A list has exactly two possible shapes. Either it is empty, [], or it is a first cell, x :: rest, with some element x in front of the rest. match checks which shape a value has and names the parts:

let describe l =
  match l with
  | [] -> "empty"
  | x :: rest -> "starts with " ^ string_of_int x
# describe [];;
- : string = "empty"
# describe [7; 8];;
- : string = "starts with 7"

Each line starting with | is a case: a pattern, an arrow, and the result for that shape. OCaml tries the cases from top to bottom and uses the first one that fits. For [7; 8], the pattern x :: rest fits with x = 7 and rest = [8], and those names exist only on the right of that arrow. Like if, a match is an expression, so every case must give the same type.

Now the best part. Leave a shape out:

# let first l = match l with x :: rest -> x;;
Line 1, characters 14-41:
1 | let first l = match l with x :: rest -> x;;
                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^
Warning 8 [partial-match]: this pattern-matching is not exhaustive.
Here is an example of a case that is not matched:
[]

val first : 'a list -> 'a = <fun>

OCaml checked every shape a list can have and found one you didn't handle. It even gives you an example: []. "Exhaustive" means "covers everything". If you ignore the warning and later call first [], the program stops with a Match_failure error.

This warning is a gift. In most languages, forgetting the empty case is a crash you find when a user hits it. In OCaml you find it the moment you write the function. It gets even better with your own types in lesson O.4: add a new kind of value to a type, and OCaml lists every match in your program that forgot about it. In a compiler with dozens of operations, that is how you keep hundreds of functions in step.

Unused names

In x :: rest -> x, the name rest is never used. Write _ instead, as in x :: _ -> x. _ is a pattern that matches anything and names nothing. In a dune project an unused name is a warning that stops the build, so _ is a habit worth starting now.

Recursion on lists

Pattern matching and recursion fit lists perfectly. A list is either empty, or an element followed by a smaller list. So a function on lists says what to do with the empty list, and what to do with x given the answer for rest:

let rec length l =
  match l with
  | [] -> 0
  | _ :: rest -> 1 + length rest

let rec sum l =
  match l with
  | [] -> 0
  | x :: rest -> x + sum rest
# length [5; 6; 7];;
- : int = 3
# sum [1; 2; 3];;
- : int = 6

Read sum aloud: "the sum of an empty list is 0. The sum of x followed by rest is x plus the sum of rest." Each call works on a shorter list, so the calls always reach []. Step through it. Each step replaces one call by what its matching case says.

The same shape builds new lists. map applies a function to every element. The answer for x :: rest is f x in front of the mapped rest:

let rec map f l =
  match l with
  | [] -> []
  | x :: rest -> f x :: map f rest
# map (fun x -> x * 10) [1; 2; 3];;
- : int list = [10; 20; 30]

Trace it the same way: map f [1; 2; 3] is f 1 :: map f [2; 3], which is 10 :: 20 :: 30 :: []. Its type is ('a -> 'b) -> 'a list -> 'b list: given a function from 'a to 'b and a list of 'a, you get a list of 'b.

Your own map

Write my_map f l yourself, without looking at the code above if you can. my_map (fun x -> x + 1) [1; 2; 3] is [2; 3; 4]. The starter walks the list but builds nothing.

The List library

You'll write match on lists often, but for the common jobs the List module already has a function. Each one is the recursion above, written once so you don't have to repeat it.

map and filter

# List.map (fun x -> x * 10) [1; 2; 3];;
- : int list = [10; 20; 30]
# List.map String.length ["hi"; "there"];;
- : int list = [2; 5]
# List.filter (fun x -> x mod 2 = 0) [1; 2; 3; 4; 5; 6];;
- : int list = [2; 4; 6]

List.map f l makes a new list with f applied to each element. List.filter keep l makes a new list with only the elements where keep says true. Neither changes l. They can't: lists are immutable.

fold_left: combine everything into one value

List.fold_left f start l walks the list from the left, carrying one value along, called the accumulator. It starts as start. For each element x, the new accumulator is f acc x. At the end, the accumulator is the answer.

When you write a fold, ask two questions: what does acc mean (a total, a count, the best so far), and what should it be before any element has been seen?

Count the positives with fold_left

Write count_positive l: how many elements of l are greater than 0. count_positive [3; -1; 0; 5] is 2. Use List.fold_left. The starter's function never changes the count.

iter, rev, length and @

# List.iter print_endline ["milk"; "eggs"];;
milk
eggs
- : unit = ()
# List.rev [1; 2; 3];;
- : int list = [3; 2; 1]
# List.length [1; 2; 3];;
- : int = 3
# [1; 2] @ [3; 4];;
- : int list = [1; 2; 3; 4]

List.iter calls a function on each element for what it does (here, printing), and gives back (). List.rev reverses. List.length counts, by walking the whole list, so don't call it inside a loop over the same list. @ joins two lists.

Adding to the end is slow

a @ b can't change the last cell of a to point at b, because cells never change. So it copies every cell of a. On a list of 10,000 elements, adding one element at the end copies 10,000 cells. Do that in a loop and the work grows with the square of the length. The usual fix: build the list backwards with :: (one cell each), then call List.rev once at the end.

Maybe a value: option

Some questions don't always have an answer. "Find the first number over 10" has none if every number is small. OCaml's answer to this is the option type:

# List.find_opt (fun x -> x > 10) [3; 12; 40];;
- : int option = Some 12
# List.find_opt (fun x -> x > 100) [3; 12; 40];;
- : int option = None

An int option is either Some n, holding an int, or None, holding nothing. It is not an int. You can't add 1 to it. To use the int inside, you match on both shapes, and OCaml checks that you handled both:

let first_big l =
  match List.find_opt (fun x -> x > 10) l with
  | Some x -> "found " ^ string_of_int x
  | None -> "none"
# first_big [3; 12];;
- : string = "found 12"
# first_big [3];;
- : string = "none"

Why not return a special "nothing" value, the way many languages use null? Because null pretends to be a normal value. Code that forgets to check for it compiles fine and crashes later, often far from the cause. In OCaml, "maybe nothing" has its own type. An int is always a real int, and when something might be missing, the type says option and the exhaustiveness check makes you deal with None.

Some library functions skip the option and raise an error instead. List.find raises Not_found when nothing matches, and List.hd (the first element) fails on an empty list:

# List.find (fun x -> x > 100) [3; 12; 40];;
Exception: Not_found.
# List.hd [];;
Exception: Failure "hd".

Prefer the _opt versions while you are learning, so the type reminds you. Exceptions, and when they are the better choice, are in lesson O.4.

The last element, as an option

Write last l: Some of the last element, or None for the empty list. last [1; 2; 3] is Some 3. The starter returns the first element.

Tail recursion

Look again at sum: x + sum rest. The addition can't happen until sum rest comes back. So each call has to wait, and remember its x, while the next call runs. The computer keeps those waiting calls in a region of memory called the call stack, one frame per waiting call. For a list of n elements, n frames pile up before the first addition happens:

sum [1; 2; 3]

  | sum []            returns 0          |   <- top: running now
  | 3 + sum []        waiting, holds 3   |
  | 2 + sum [3]       waiting, holds 2   |
  | 1 + sum [2; 3]    waiting, holds 1   |
  +--------------------------------------+   one frame per element

The stack has a size limit. OCaml 5 gives it a lot of room (up to about a gigabyte), so you need very deep recursion to reach it, but you can. Here is sum_to from lesson O.2 with a hundred million calls:

# let rec sum_to n = if n = 0 then 0 else n + sum_to (n - 1);;
val sum_to : int -> int = <fun>
# sum_to 100_000_000;;
Stack overflow during evaluation (looping recursion?).

(The underscores in 100_000_000 are only for reading. OCaml ignores them.) A list sum with a hundred million elements would fail in the same way. Older OCaml versions, and many other languages, hit the limit much sooner. Python, for example, stops at about a thousand nested calls.

The fix is to make the recursive call the very last thing the function does, with nothing left to do after it comes back. Then the current frame has nothing left to remember, and OCaml reuses it for the next call instead of piling up a new one. Such a call is a tail call, and a function whose recursive calls are all tail calls is tail recursive. To get there, you carry the running total down as an extra argument, an accumulator, the same idea as in fold_left:

let rec sum_acc acc l =
  match l with
  | [] -> acc
  | x :: rest -> sum_acc (acc + x) rest
CallacclNext
10[1; 2; 3]sum_acc 1 [2; 3]
21[2; 3]sum_acc 3 [3]
33[3]sum_acc 6 []
46[]returns 6

No call waits for anything. Each one hands over the whole job, and the addition happens before the call, not after it. The stack holds one frame the whole time, and the hundred-million version finishes:

# let rec sum_to_acc acc n = if n = 0 then acc else sum_to_acc (acc + n) (n - 1);;
val sum_to_acc : int -> int -> int = <fun>
# sum_to_acc 0 100_000_000;;
- : int = 5000000050000000

You call it with the starting accumulator, sum_acc 0 l. List.fold_left is tail recursive for the same reason, which is one more reason to use it. Don't rewrite every function this way. The plain version is easier to read and fine for the lists and trees in this course. Reach for an accumulator when the input can be very long.

A tail-recursive sum

Write sum_from acc l: acc plus the sum of l, tail recursively. sum_from 0 [1; 2; 3] is 6 and sum_from 10 [] is 10. One test uses a list of a million elements. The recursive case in the starter is already right.

What you can do now

  • Write lists with semicolons, and spot [1, 2] by its type.
  • Build lists with ::, and picture them as chains of shared, unchanging cells.
  • Group values of different types in tuples, and take them apart with let (a, b) = ....
  • Take a list apart with match on [] and x :: rest, and read the exhaustiveness warning.
  • Write recursive functions on lists and trace them step by step.
  • Use List.map, List.filter, List.fold_left, List.iter, List.rev and @, and know why @ at the end is slow.
  • Handle a maybe-missing value with option, Some and None.
  • Explain the call stack, and turn a recursion into a tail-recursive one with an accumulator.
