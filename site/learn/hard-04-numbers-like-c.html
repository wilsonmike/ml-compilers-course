Numbers that behave like C

The programs your compiler runs use 32-bit integers that wrap around, a division with its own exact rules, and, from week 2, 32-bit floats. Python and OCaml do none of these by default. This page builds each one up from a picture, so you can make your language compute exactly what the course's ops and C would.

Before you start

You need whole numbers and floats in your language (P.1O.1). Lesson 0.1 shows the same ideas from C's side, and has a bit viewer you can play with.

A fixed number of digits

A car's odometer has a fixed number of wheels. Four wheels count from 0000 to 9999, and one more mile shows 0000 again: the carry has nowhere to go, so it falls off. Nothing breaks. The count wraps around.

A computer stores whole numbers the same way, with a fixed number of bits. A bit is a single binary digit, 0 or 1. With 4 bits, each place is worth twice the one to its right: 8, 4, 2, 1. So 1011 is 8 + 2 + 1 = 11. Four bits count from 0 to 15, and then wrap. Step through a 4-bit odometer.

The machines you'll compile for use 32 bits for an i32. Read as plain counts, 32 bits go from 0 to 232 − 1, which is 4,294,967,295, and one more wraps to 0, exactly like the 4-bit wheel. Hex digits are a short way to write bits: each hex digit is 4 bits, so 32 bits are 8 hex digits, and 0xffffffff is all 32 bits set.

Negative numbers on a wheel

Where do negative numbers go? Bend the odometer into a circle. Going one step back from 0000 lands on 1111. So call 1111 "−1". One more step back, 1110, is "−2". Do that for the whole bottom half of the circle and you get two's complement, the way every modern machine stores signed integers.

The rule in one line: the top bit is worth minus its usual value. In 4 bits the top bit is worth −8 instead of 8. So 1011 is −8 + 2 + 1 = −5, and 0111 is still 7. Step around the wheel.

Two things fall out of the wheel. A number is negative exactly when its top bit is 1. And a signed value and a plain count with the same bits differ by exactly 16, the size of the wheel: 11 and −5, 15 and −1.

For 32 bits the top bit is worth −231. The smallest i32 is −2,147,483,648 (called INT_MIN), the largest is 2,147,483,647 (INT_MAX), and −1 is all ones, 0xffffffff. The two readings now differ by 232.

Overflow wraps

Add 1 to the largest i32 and the wheel turns past the top: 2147483647 + 1 is -2147483648. This is called overflow. The language your compiler runs defines add and mul to wrap exactly like this. (C itself makes signed overflow undefined, which lesson 0.1 explains. Your compiler's own arithmetic must still wrap.)

Neither of your languages wraps at 32 bits.

>>> 2147483647 + 1
2147483648
>>> 2 ** 100
1267650600228229401496703205376

A Python int grows as large as it needs to. It never overflows, so you wrap by hand: keep the low 32 bits, then read the top bit as the sign. x & 0xFFFFFFFF keeps the low 32 bits as a plain count, even for a negative x. A count of 231 or more has its top bit set, so it stands for a negative number: subtract 232.

>>> def wrap32(x):
...     x = x & 0xFFFFFFFF
...     return x - 2**32 if x >= 2**31 else x
...
>>> wrap32(2147483647 + 1)
-2147483648
>>> wrap32(-1)
-1
>>> wrap32(2**32 + 5)
5

OCaml's int has 63 bits on a 64-bit machine (one bit is used to tell numbers from pointers). It does wrap, but at 63 bits, far past where an i32 wraps. The Int32 module has true 32-bit integers, with literals ending in l, and Int32.of_int keeps the low 32 bits of an int:

# Int32.add 2147483647l 1l;;
- : int32 = -2147483648l
# let wrap32 x = Int32.to_int (Int32.of_int x);;
val wrap32 : int -> int = <fun>
# wrap32 2147483648;;
- : int = -2147483648
# wrap32 (4294967296 + 5);;
- : int = 5

You can also wrap a plain int with bit operations: x land 0xFFFFFFFF keeps the low 32 bits as a count, and a count of 0x80000000 or more stands for a negative number, so subtract 0x100000000.

Wrap after every operation

Wrapping once at the end is not enough, because later operations can depend on an intermediate value. Make one helper and call it every time an i32 is produced: add, subtract, multiply, negate, shift left, and even division (one quotient overflows, see below). Python is the risky one here: a missed wrap gives a correct-looking big number, not an error.In OCaml, doing the arithmetic in Int32 makes a missed wrap impossible, at the cost of converting at the edges.

The 32 bits as hex

Write hex32 x: the 8 lowercase hex digits of the low 32 bits of the int x, with leading zeros. hex32 255 is "000000ff", hex32 (-1) is "ffffffff", and hex32 (-2147483648) is "80000000", the same as hex32 2147483648.

Printf.sprintf "%08x" prints an int in hex with at least 8 digits. What does it print for a negative number, and how do you keep only 32 bits first?

Division: toward zero, or down?

Divide 7 by 2 and the true answer is 3.5. A whole-number division has to pick 3 or 4. For positive numbers everyone picks 3. The trouble is −7 / 2 = −3.5. There are two reasonable rules:

  • Truncate: round toward zero, so −3.5 becomes −3. C does this, and so does OCaml's /.
  • Floor: round down, toward minus infinity, so −3.5 becomes −4. Python's // does this, and so does the course's div.

The remainder follows the quotient, so that a = b × q + r always holds. With truncation the remainder has the sign of a. With flooring it has the sign of b. Step through the four sign cases on a number line.

Check a row with a = b × q + r. Truncating −7 by 2: 2 × −3 + −1 = −7. Flooring: 2 × −4 + 1 = −7. Both are correct. They're different conventions. They only disagree when the signs differ and the division isn't exact.

>>> -7 // 2
-4
>>> -7 % 2
1
>>> int(-7 / 2)
-3
# (-7) / 2;;
- : int = -3
# (-7) mod 2;;
- : int = -1
# 7 mod (-2);;
- : int = 1

Python's // and % already floor, the same as the course's div and mod. You still need C's rule from week 2 on, because the C your compiler prints truncates. int(-7 / 2) truncates, but it goes through a float, and a float can't hold every large integer exactly. For C-style division, divide the absolute values with //, then make the quotient negative when exactly one of a and b is negative. The remainder is then a - b * q.

OCaml's / and mod truncate, like C. That's the trap: the course's div and mod floor. Fix up the truncated result: when the remainder isn't zero and its sign differs from b's, subtract 1 from the quotient and add b to the remainder. Keep C's rule in mind too, because from week 2 your compiler prints C, and C's / truncates.

One quotient doesn't fit

INT_MIN / -1 should be 2,147,483,648, which is one more than INT_MAX. It wraps back to INT_MIN. That's why division needs the wrap too. Dividing by zero has no true answer, so the course defines one: div x 0 is −1 and mod x 0 is x. Python raises an errorOCaml raises Division_by_zero there, and C leaves it undefined, so both need a check first. Lesson 0.7 and lesson 0.6 each have an exercise on this.

Both kinds of division

Write divs a b, returning four numbers: the truncated quotient and remainder, then the floored quotient and remainder. divs (-7) 2 is (-3, -1, -4, 1). b is never 0. The numbers are plain ints, with no 32-bit wrapping.

/ and mod give you the first two. Get the floored pair from them with the fix-up described above.

Floats: f64 and f32

Week 1 has only integers and booleans. Floats arrive in week 2, and this part is ready for them. A float is a number in scientific notation, written in binary. In decimal, 6.02 × 1023 has a sign, some digits (6.02) and an exponent (23). A float stores the same three parts as bits: a sign bit, an exponent, and a fraction that holds the digits. A fixed number of bits for the fraction means a fixed number of significant digits, so most numbers get rounded to the nearest one that fits.

typebits: sign, exponent, fractionabout this many decimal digitswho uses it
f64 (double)1, 11, 5215 to 17Python's float, OCaml's float
f32 (single)1, 8, 236 to 9the course's f32 (from week 2), C's float, most ML models

Your language gives you f64. To compute like f32, you round to f32 after every operation: take the f64 result and replace it with the nearest value that fits in 32 bits. The standard way is to convert to the 32-bit form and back.

>>> import struct
>>> def to_f32(x):
...     return struct.unpack("<f", struct.pack("<f", x))[0]
...
>>> to_f32(0.1)
0.10000000149011612
>>> to_f32(16777217.0)
16777216.0
# Int32.float_of_bits (Int32.bits_of_float 0.1);;
- : float = 0.100000001490116119
# Int32.float_of_bits (Int32.bits_of_float 16777217.0);;
- : float = 16777216.

struct.pack("<f", x) stores x as the 4 bytes of an f32, rounding to the nearest, and struct.unpack reads those bytes back as a Python float, exactly. One catch: for a value too big for f32, like 1e39, struct.pack raises OverflowError where C would give infinity. Lesson 0.7 shows the fix.

Int32.bits_of_float x rounds x to the nearest f32 and gives its 32 bits. Int32.float_of_bits reads those bits back as an OCaml float holding exactly that f32 value. Too-big values become infinity, as in C.

16,777,217 is 224 + 1. An f32 has 24 bits of precision, so it can't hold 16,777,217. That value sits exactly halfway between 16,777,216 and 16,777,218, and a tie rounds to the neighbor whose last bit is 0.

Why 0.1 + 0.2 is not 0.3

In decimal, 1/3 never ends: 0.3333... If you only keep four digits, 1/3 is 0.3333, and three of them add to 0.9999, not 1. Nothing went wrong in the adding. The numbers were rounded before you started.

stepexactwith 4 decimal digits
1/30.3333...0.3333
1/3 + 1/30.6666...0.6666
1/3 + 1/3 + 1/310.9999

Binary has the same problem with tenths. 1/10 in binary is 0.000110011001100... forever, so 0.1 is stored as the nearest f64, which is a tiny bit off. So is 0.2, and so is 0.3, and the errors don't cancel:

>>> 0.1 + 0.2
0.30000000000000004
>>> 0.1 + 0.2 == 0.3
False
# 0.1 +. 0.2;;
- : float = 0.300000000000000044
# 0.1 +. 0.2 = 0.3;;
- : bool = false

The lesson isn't "floats are random". Float arithmetic is exact and repeatable: the same operations in the same order on the same values give the same bits every time. That's why your interpreter and the C your compiler prints can agree to the last bit, as long as both round at the same moments. What you can't do is expect a float to equal the decimal you typed.

Looking at a float's bits

Decimal printing can hide the difference between two floats. The bits never do. Here are the 32 bits of a few f32 values, split into the three parts. Step through them.

# Printf.sprintf "%08lx" (Int32.bits_of_float 0.1);;
- : string = "3dcccccd"

float.hexThe %h format writes the f64 in hex scientific notation: 0x1.999...ap-4 means 1.999...a (in hex) times 2−4. The second line gives the 32 bits of the f32 in hex. "<I" reads the same 4 bytes as an unsigned 32-bit int. Leading zeros are left off, so a value with zeros at the front prints fewer than 8 digits.%lx prints an int32 in hex. When two floats look the same in decimal but your tests disagree, print the bits.

Two odd values: nan and −0.0

nan ("not a number") is the result of an undefined operation, like 0 / 0 or infinity minus infinity. It compares unequal to everything, itself included. So x == xx = x is false exactly when x is nan, and you test for it with a function, not with equality.

−0.0 is zero with the sign bit set. It compares equal to 0.0, but it's a different value: dividing by it gives minus infinity, and its bits are 80000000 instead of 00000000.

>>> import math
>>> nan = float("nan")
>>> nan == nan
False
>>> math.isnan(nan)
True
>>> -0.0 == 0.0
True
>>> math.copysign(1.0, -0.0)
-1.0
>>> 1.0 / -0.0
Traceback (most recent call last):
  ...
ZeroDivisionError: float division by zero

- : bool = false
# Float.is_nan nan;;

# -0.0 = 0.0;;
- : bool = true
# Float.sign_bit (-0.0);;

Python refuses to divide a float by zero, where C gives an infinity. Your interpreter has to produce C's answer, so it checks for a zero divisor and returns the right infinity (or nan, for 0 / 0) itself.

OCaml's float division follows IEEE, like C, so 1.0 /. (-0.0) is already minus infinity.

Where these two bite

In a lookup table they break keys (H.1: key floats by their bits). In rewrite rules they break "obvious" laws: x * 0 → 0 is wrong when x is nan, infinity or negative (a negative x gives −0.0), and x + 0.0 → x is wrong when x is −0.0 (H.3, lesson 0.3). Week 2 has the full table of special values.

An f32's bits

Write f32_bits x: round the float x to f32 and return its 32 bits as a non-negative int (from 0 to 232 − 1). The tests print it as 8 hex digits: f32_bits 1.0 shows as 3f800000, and f32_bits (-0.0) as 80000000.

Int32.bits_of_float gives the bits, but as a signed int32. Turn it into an int and keep the low 32 bits, so the sign bit counts as 231.

Where this shows up in the course

  • Lesson 1.2: your interpreter computes i32 exactly: wrap, and div and mod that floor, with −1 and x for a zero divisor, and shl by y mod 32.
  • Lesson 1.3: constant folding must give the interpreter's answer, wrap included.
  • Week 2: f32 arrives, rounded to f32 after every operation, with the special values.
  • Lesson 2.4: the C you print must wrap and floor without undefined behavior, even though C's / truncates, and float constants are written exactly, from their bits.
  • Lesson 2.5: results come back from C as hex bits, and you compare bits.

What you can do now

  • Read 4-bit and 32-bit values in two's complement, and say why the top bit decides the sign.
  • Wrap any integer to 32 bits in your language, and know to do it after every operation.
  • Tell truncating division from flooring, for all four sign cases, know the course floors, and check a result with a = b × q + r.
  • Round an f64 to f32, and explain why 0.1 + 0.2 isn't 0.3.
  • Print a float's bits in hex, and test for nan and −0.0 correctly.

Check yourself

What is the 4-bit two's complement value of 1101?

The top bit is worth −8. The others are worth 4, 2 and 1 as usual.

−8 + 4 + 1.

−8 + 4 + 1 = −3. As a plain count the same bits are 13, and 13 − 16 = −3.

As an i32 that wraps, what is 2147483647 + 1?

2147483647 is the top of the wheel. What is one step past the top?

The wheel turns past INT_MAX to INT_MIN, −2,147,483,648. In bits, 0x7fffffff + 1 is 0x80000000, whose top bit is now set.

In C (truncating division), what is -9 % 4?

First the quotient: −9 / 4 is −2.25. Which way does C round it?

The quotient is −2. Now solve −9 = 4 × (−2) + r.

The quotient truncates to −2, and −9 − 4 × (−2) = −1. The remainder has the sign of a. Python's -9 % 4 is 3, because its quotient floors to −3.

In the course's .uir, what is div -7 2?

The exact answer is −3.5. Does the course's div truncate like C, or floor like Python?

.uir's div floors, so −3.5 rounds down to −4. C and OCaml's / would give −3. The matching mod -7 2 is 1.

In the course's .uir, what is div 5 0?

Nothing in the course fails at run time, so a zero divisor needs a defined answer.

The course defines div x 0 as −1, and mod x 0 as x. Python and OCaml would raise, and in C it's undefined, so your code checks for 0 first.

Why is 0.1 + 0.2 == 0.3 false with f64 floats?

Is 1/10 a finite fraction in binary?

0.1, 0.2 and 0.3 are each rounded to the nearest f64. The sum of the first two rounds to a different f64 than 0.3 does. The arithmetic itself is exact and repeatable.

What are the 32 bits of the f32 value -0.0, as 8 hex digits?

−0.0 is zero with only the sign bit set. The sign bit is the top bit.

80000000: the top bit is the sign, and every other bit is 0. 0.0 is 00000000. Equal by ===, different bits.
