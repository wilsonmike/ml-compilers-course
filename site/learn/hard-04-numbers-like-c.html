Whole numbers: one more than the biggest

Whole numbers in the course's language are of a kind called i32. An i32 is stored in 32 bits. A bit is one switch that is 0 or 1. Thirty-two switches can't hold every number, so there is a biggest i32: 2,147,483,647.

Predict. What does add 2147483647 1 give?

There is no bigger i32 to move to, and nothing in the course's language fails while running.

It gives −2,147,483,648, the smallest i32. The count went past the top and came back in at the bottom. The next two sections show why.

Start with a car's odometer, the counter that shows miles driven. It has a fixed number of wheels. Four wheels count from 0000 to 9999, and one more mile shows 0000. The carry has nowhere to go, so it falls off. Nothing breaks. The count wraps around.

A machine's counter has bits where the odometer has wheels. Each place is worth twice the one to its right: 8, 4, 2, 1. So 1011 is 8 + 2 + 1 = 11. Step through a counter with 4 bits and watch it wrap.

Four bits wrap after 15. Thirty-two bits wrap the same way, after 4,294,967,295.

Whole numbers: where the negatives live

An odometer has no negative numbers. A machine gets them by bending the counter into a circle. One step back from 0000 is 1111, so 1111 is called −1. One more step back, 1110, is −2. Half the circle goes to the negative numbers. This layout is called two's complement, and every modern machine uses it.

The rule in one line: the top bit is worth minus its usual value. In 4 bits the top bit is worth −8, so 1011 is −8 + 2 + 1 = −5. Step around the wheel.

On the 4-bit wheel, what is 7 + 2?

Adding 1 is one step clockwise. Start at 7 and take two steps.

One step past 7 is −8, and one more is −7. School math says 9, and 9 − 16 is −7. The wheel has 16 positions, so a wrapped answer is always off by 16.

An i32 is the same wheel with 232 positions, which is 4,294,967,296. The biggest value is 2,147,483,647, called INT_MAX. One step past it is the smallest, −2,147,483,648, called INT_MIN. That is the answer you predicted a moment ago.

A number is negative exactly when its top bit is 1. A signed value and a plain count with the same bits differ by exactly 16, the size of the wheel: 11 and −5, 15 and −1. For 32 bits the top bit is worth −231, −1 is all ones, and the two readings differ by 232.

C itself makes signed overflow undefined, which lesson 0.1 explains. The course's add, mul and shl are defined to wrap, so your compiler's own arithmetic must wrap.

Whole numbers: wrap by hand

Your language does not wrap at 32 bits:

>>> 2147483647 + 1
2147483648
# 2147483647 + 1;;
- : int = 2147483648

A Python int grows as large as it needs to and never wraps.An OCaml int has 63 bits, so it wraps far too late. So your interpreter wraps by hand. Take 1,500,000,000 + 1,500,000,000:

  1. Do the math with no limit. The sum is 3,000,000,000.
  2. Check the range. That is past INT_MAX.
  3. Come around. Subtract the size of the wheel, 4,294,967,296. The result is −1,294,967,296. (Subtract again if the number is still too big. A number below INT_MIN gets the wheel size added.)

Code does it in two moves. First find where the number lands on the wheel, as a count from 0. x % 2**32 does that: it is the remainder after dividing by the wheel size.x land 0xFFFFFFFF does that: it keeps the lowest 32 bits of x and clears the rest. Then read the top half of the wheel as negative: a count of 231 (2,147,483,648) or more has the wheel size subtracted.

Finish the wrap

wrap32 x should turn any whole number into the i32 it wraps to. The first move is written: count is where x lands on the wheel, as a count from 0 to 232 − 1. The second move is missing, so the positions that stand for negative numbers come out as large positive counts. Add it.

Lesson 1.2 writes the same two moves in one line:

def wrap(x):
    return (x + 2**31) % 2**32 - 2**31
let wrap x = Int32.to_int (Int32.of_int x)
Wrap after every operation

Wrapping once at the end is not enough, because a later op can depend on a wrapped value. Call the helper every time an i32 is produced. A missed wrap in Python gives a correct-looking big number, not an error.A missed wrap in OCaml gives a correct-looking big number, not an error.

Whole numbers: see the 32 bits

Writing 32 ones and zeros is slow, so people write bits in hex. One hex digit stands for 4 bits. The digits are 0 to 9, then a to f for 10 to 15. Eight hex digits show all 32 bits, and 0x in front marks a number as hex.

When a test fails on a number near either end of the range, print the bits. In Python, x & 0xFFFFFFFF keeps the lowest 32 bits of x as a count from 0, the same as x % 2**32.x land 0xFFFFFFFF from the last section gives the count to print.

The 32 bits as hex

Write hex32 x: the 8 lowercase hex digits of the low 32 bits of the int x, with leading zeros. hex32 255 is "000000ff", hex32 (-1) is "ffffffff", and hex32 (-2147483648) is "80000000", the same as hex32 2147483648.

Whole numbers: two kinds of division

Divide 7 by 2 and the exact answer is 3.5. An i32 can't hold 3.5, so a whole-number division has to pick 3 or 4, and everyone picks 3. Now try a negative number. The exact answer to −7 ÷ 2 is −3.5.

Predict. What does the course's div -7 2 give?

The course's div always moves the same direction on the number line, for positive and negative answers.

It gives −4. The course's div always rounds down, toward the more negative number. C would say −3. Both rules are in use, and you need to tell them apart.

  • Truncate: drop the fraction, which moves toward zero. −3.5 becomes −3. C does this, and so does OCaml's /.
  • Floor: round down, toward the more negative number. −3.5 becomes −4. Python's // does this, and so does the course's div.

Step through the four sign cases on a number line.

The remainder is what is left over. Call the quotient q and the remainder r. Then r = a − b × q, so a different q gives a different r. Flooring −7 by 2: −7 − 2 × (−4) = 1. Truncating: −7 − 2 × (−3) = −1.

a, bexact a ÷ btruncate: q, rfloor: q, r
7, 23.53, 13, 1
−7, 2−3.5−3, −1−4, 1
7, −2−3.5−3, 1−4, −1
−7, −23.53, −13, −1

The two rules disagree only when the signs differ and the division isn't exact. A floored remainder has the sign of b. A truncated one has the sign of a.

Whole numbers: divide both ways in your language

Your language picked one rule. You will need both: the course's div and mod floor, and the C your compiler prints from week 2 on truncates.

>>> -7 // 2
-4
>>> -7 % 2
1
# (-7) / 2;;
- : int = -3
# (-7) mod 2;;
- : int = -1

Python's // and % floor, the same as the course's div and mod. To get C's rule from them:

  1. Divide the sizes. abs(a) // abs(b) is the quotient without its sign. For −7 and 2 that is 3.
  2. Put the sign back. Make it negative when exactly one of a and b is negative: −3.
  3. Find what is left. r = a - b * q, here −7 − 2 × (−3) = −1.

OCaml's / and mod truncate, like C. That is the trap, because the course floors. To get the floored pair from them:

  1. Divide the usual way. For −7 and 2, / gives −3 and mod gives −1.
  2. Check the remainder. If it is not 0 and its sign differs from b's, the quotient was rounded the wrong way. Here −1 and 2 differ in sign.
  3. Fix both. Subtract 1 from the quotient and add b to the remainder: −4 and 1.

Both kinds of division

Write divs a b, returning four numbers: the truncated quotient and remainder, then the floored quotient and remainder. divs (-7) 2 is (-3, -1, -4, 1). b is never 0. The numbers are plain ints, with no 32-bit wrapping.

/ and mod give you the first two. Get the floored pair from them with the fix-up described above.

Two divisions with no natural answer

Dividing by zero has no exact answer, so the course defines one: div x 0 is −1 and mod x 0 is x. Python raises an error thereOCaml raises Division_by_zero there, so check for 0 first. And div INT_MIN -1 should be 2,147,483,648, which is one past INT_MAX. It wraps back to INT_MIN, so division needs the wrap too.

Why not divide with floats, and what C does in the two odd cases

int(-7 / 2) truncates and gives −3, but it goes through a float, and a float can't hold every large integer exactly. Stay in whole numbers.

In C, dividing by zero and INT_MIN / -1 are both undefined, which means a C compiler may do anything at all. The C your compiler prints has to check for both. Lesson 0.7 and lesson 0.6 each have an exercise on this, and lesson 2.4 prints the C.

Floats (week 2): a fixed number of digits

Come back in week 2

Week 1 has only whole numbers and booleans. Read on from here when lesson 2.1 sends you.

A float is how a machine stores a number with a decimal point. Picture a calculator that keeps only 3 digits, plus a note of where the decimal point goes. It can hold 123, and 1.23, and 1,230,000. It can't hold 1,234. The fourth digit has no place to go, so the calculator stores the nearest number it can hold, 1,230.

Ask that calculator for 1,230 + 1. The exact answer is 1,231, and it stores 1,230. The 1 is gone.

The course's float is called f32. It works the same way in binary: it keeps 24 binary digits and the place of the point. That is enough for every whole number up to 224, which is 16,777,216.

Predict. In f32, what is 16,777,216 + 1?

16,777,217 needs 25 binary digits. Think of the calculator at 1,230 + 1.

The 1 disappears. An f32 can't hold 16,777,217, so the answer moves to a nearby number it can hold.

Past 16,777,216 an f32 can hold only every second whole number. A filled box is a number f32 can hold:

Whole numbers near 16,777,216

16777215
16777216
16777217

16777219
16777220

So every f32 operation takes these moves:

  1. Compute exactly. 16,777,216 + 1 is 16,777,217.
  2. Find the neighbors. The nearest numbers f32 can hold are 16,777,216 and 16,777,218.
  3. Pick the nearest. Both are 1 away. A tie goes to the neighbor whose last kept bit is 0, here 16,777,216. This rule is called ties to even.

Floats (week 2): round after every operation

Python's floatOCaml's float is a bigger kind called f64. It keeps 53 binary digits where f32 keeps 24, so it holds 16,777,217 with no trouble. To compute like an f32 machine, do the operation in your own floats, then round to f32: replace the result with the nearest value an f32 can hold. This helper does the rounding:

>>> import struct
>>> def to_f32(x):
...     return struct.unpack("<f", struct.pack("<f", x))[0]
...
>>> to_f32(16777217.0)
16777216.0
# let to_f32 x = Int32.float_of_bits (Int32.bits_of_float x);;
val to_f32 : float -> float = <fun>
# to_f32 16777217.0;;
- : float = 16777216.

struct.pack("<f", x) stores x in the 4 bytes of an f32, rounding to the nearest. struct.unpack reads those bytes back as a Python float.

Int32.bits_of_float x rounds x to the nearest f32 and gives its 32 bits. Int32.float_of_bits reads those bits back as an OCaml float.

Round after every operation, not once at the end. Take 16,777,216 + 1 + 1:

  1. Add and round. 16,777,216 + 1 is 16,777,217, which rounds to 16,777,216.
  2. Add and round again. 16,777,216 + 1 rounds to 16,777,216 again.

An f32 machine ends at 16,777,216. Rounding once at the end gives 16,777,218, a different answer.

Round after every add

sum3 a b c should add three f32 values the way an f32 machine does: a + b first, then + c, rounding to f32 after each addition. to_f32 is written. The starter rounds only once, at the end, so sum3 16777216.0 1.0 1.0 gives 16777218 where an f32 machine gives 16777216. Repair it.

Floats (week 2): why 0.1 is not exactly 0.1

In decimal, 1/3 never ends: 0.3333... Keep only four digits and 1/3 is 0.3333. Three of them add to 0.9999, not 1. Nothing went wrong in the adding. The numbers were rounded before you started.

Binary has the same trouble with tenths. 1/10 in binary goes on forever, so 0.1 is stored as the nearest float, which is a tiny bit off. As an f32 it is 0.10000000149011612. Your own f64 floats show the effect:

>>> 0.1 + 0.2
0.30000000000000004
>>> 0.1 + 0.2 == 0.3
False
# 0.1 +. 0.2;;
- : float = 0.300000000000000044
# 0.1 +. 0.2 = 0.3;;
- : bool = false

Why is 0.1 + 0.2 == 0.3 false with f64 floats?

Is 1/10 a finite fraction in binary?

0.1, 0.2 and 0.3 are each rounded to the nearest f64. The sum of the first two rounds to a different f64 than 0.3 does. The arithmetic itself is exact and repeatable.

Floats are not random. The same operations in the same order on the same values give the same bits every time. That is why your interpreter and the C your compiler prints can agree to the last bit, as long as both round at the same moments. In f32, the rounded sum of 0.1 and 0.2 happens to land exactly on the rounded 0.3. You can't guess that. You round and look.

Floats (week 2): read a float's bits

Decimal printing can hide the difference between two floats. The bits never do. An f32 has three parts: a sign bit, an exponent that says where the point goes, and a fraction that holds the digits. Step through a few values. Three of them are special: inf is infinity, a result too big for f32. nan, "not a number", is the result of something like 0 ÷ 0. And -0.0 is zero with the sign bit set.

Here is how to print the 32 bits of an f32 as hex:

>>> hex(struct.unpack("<I", struct.pack("<f", 0.1))[0])
'0x3dcccccd'
# Printf.sprintf "%08lx" (Int32.bits_of_float 0.1);;
- : string = "3dcccccd"

"<I" reads the same 4 bytes as a whole number from 0 to 232 − 1.%lx prints an int32 in hex. When two floats look the same in decimal but your tests disagree, print the bits.

Two of the special values break ordinary comparing. nan is unequal to everything, itself included, so you test for it with math.isnanFloat.is_nan. And -0.0 compares equal to 0.0, but its bits are 80000000, not 00000000.

An f32's bits

Write f32_bits x: round the float x to f32 and return its 32 bits as a non-negative int (from 0 to 232 − 1). The tests print it as 8 hex digits: f32_bits 1.0 shows as 3f800000, and f32_bits (-0.0) as 80000000.

Int32.bits_of_float gives the bits, but as a signed int32. Turn it into an int and keep the low 32 bits, so the sign bit counts as 231.

Check yourself

What is the 4-bit two's complement value of 1101?

The top bit is worth −8. The others are worth 4, 2 and 1 as usual.

−8 + 4 + 1.

−8 + 4 + 1 = −3. As a plain count the same bits are 13, and 13 − 16 = −3.

As an i32 that wraps, what is 2147483647 + 1?

2147483647 is the top of the wheel. What is one step past the top?

The wheel turns past INT_MAX to INT_MIN, −2,147,483,648. In bits, 0x7fffffff + 1 is 0x80000000, whose top bit is now set.

In C (truncating division), what is -9 % 4?

First the quotient: −9 / 4 is −2.25. Which way does C round it?

The quotient is −2. Now solve −9 = 4 × (−2) + r.

The quotient truncates to −2, and −9 − 4 × (−2) = −1. The remainder has the sign of a. Python's -9 % 4 is 3, because its quotient floors to −3.

In the course's .uir, what is div -7 2?

The exact answer is −3.5. Does the course's div truncate like C, or floor like Python?

.uir's div floors, so −3.5 rounds down to −4. C and OCaml's / would give −3. The matching mod -7 2 is 1.

In the course's .uir, what is div 5 0?
