Sharing nodes

When the same piece of a program shows up twice, a compiler can draw it twice, or draw it once and point at it from two places. This page takes the second way slowly. You will see why it matters so much, and how one lookup table makes it happen without anyone hunting for repeats.

Goal

Explain how a table makes sure the same box is never built twice, and say what goes in the table's key.

One recipe, used twice

Picture a cookbook. The pizza needs tomato sauce, and so does the pasta. The writer could print the sauce recipe twice, once inside each dish. Or the writer could print it once, on page 12, and have both dishes say "see page 12". The second book is shorter. Fix a mistake in the sauce and it is fixed for both dishes.

A program has the same choice. Take (2 + 3) × (2 + 3). The sum 2 + 3 is the sauce: it is needed twice. Each box in the picture is called a node, and a number is a node too.

One way to draw it gives every use its own copy. That takes 7 boxes: one mul, two add, two 2 and two 3. A drawing like that is called a tree.

Guess first. Now draw each thing only once and let two arrows leave a box that is used twice, like "see page 12". How many boxes does (2 + 3) × (2 + 3) need?

List the different things: the number 2, the number 3, the sum and the product.

Four: 2, 3, one add and one mul. Both arrows into mul come from the one add.

Press Next to see both drawings.

The drawing with sharing is called a DAG (lesson 1.1 says what the letters stand for). Both drawings give 25. The DAG works out 2 + 3 once, not twice.

How fast a tree grows

One shared box saved three boxes. That sounds small. It is not, because sharing can stack. In this program every line uses the line above it twice:

%x0 = 1
%x1 = add %x0 %x0
%x2 = add %x1 %x1
%x3 = add %x2 %x2

With sharing, each line adds one box. As a tree, each line needs two full copies of the tree above it and one new add on top. Count the tree by hand:

  1. Start. x0 is one box.
  2. Double and add one. x1 is two copies of x0 and an add: 2 × 1 + 1 = 3 boxes.
  3. Do it again. x2 is two copies of x1 and an add: 2 × 3 + 1 = 7 boxes.

Guess first. How many boxes is x3 as a tree?

Two copies of x2, which has 7 boxes, and one new add.

2 × 7 + 1 = 15. With sharing, x3 is 4 boxes. Step through the figure and watch the left side double.

This function only counts. It doesn't build anything:

>>> def tree_size(k):

Building the shared version in code costs nothing special. You make the new value from the same value twice, and that one value is shared:

>>> s = "x"
>>> for i in range(30):
...     s = ("+", s, s)
...
>>> s[1] is s[2]

# type e = X | Add of e * e;;

That code made 30 new values, not two billion. The danger comes later: any code that walks this value as if it were a tree takes two billion steps. H.2 is about walking it once.

Printing a shared value prints the tree. print(s)A to_string function that turns both sides of chain 30 into text writes out every copy, because text has no way to say "see page 12". Print the size or a few levels of a big shared value, never all of it.

Equal, or the very same one?

Before the table, one small idea it depends on. Start with two things you can hold.

Guess first. You and a friend each buy a copy of the same book. You write your name on page 1 of yours. What is on page 1 of your friend's copy?

How many books are there?

Nothing new. The two copies had the same words, but they are two objects. Now picture one book with two bookmarks in it. Open it at either bookmark and your name is there, because it is one object reached two ways.

Programs ask both questions about values:

  • Equal asks "do these have the same contents?" To answer, you read both books side by side to the last page. A longer book takes longer.
  • The very same one asks "is this one object?" To answer, you look at what is in your hands. That is one step, however long the book is. The usual word for it is identity.

Here a and b are two copies, and c is a second bookmark in a:

Why care? Checking two separately built copies of x30 for "equal" reads two billion boxes. Suppose you could promise that equal nodes are always the very same node. Then the one-step check would answer the slow question too. The table in the next part keeps that promise.

So don't use == on values you wrote out by hand. Values built while the program runs, like your compiler's nodes, are only the same when your code makes them the same.

A coat check that remembers

Picture the coat desk at a theater that lends coats to its actors. You don't hand over a coat. You hand over a slip that describes the one you need, like "red, size M". The attendant keeps a notebook with one line for every slip seen so far.

  1. Look the slip up. The attendant searches the notebook for "red, size M".
  2. Found: hand back the old ticket. That coat already hangs on a hook. You get its ticket number, and nothing new is made.
  3. Not found: make one. A new coat goes on the next free hook. The notebook gets a new line, and you get the new ticket number. Tickets count 0, 1, 2 and so on.

Guess first. The notebook is empty. Three slips arrive in this order: "red, M", then "blue, S", then "red, M". What ticket number does the third slip get?

The first slip got ticket 0 and the second got ticket 1. Is the third slip in the notebook?

Ticket 0. "red, M" is already in the notebook, so the attendant hands back the ticket it got the first time. Two actors now hold ticket 0, and it leads both of them to the very same coat.

Nobody at the desk has to notice that two actors want the same coat. Every request goes through the notebook, so the same slip always comes back with the same ticket.

Here is that desk in code, nearly right. The notebook is a dict from slip to ticket.The notebook is a Hashtbl from slip to ticket.

Repair the coat check

coat_check slips takes a list of slips, each a (color, size) pair, and returns the ticket number each slip gets. Tickets start at 0, and a new coat gets the next number. Two places are wrong.

The slip. It only writes down the color, so a red M and a red L count as the same coat. It should hold the color and the size.

The hit. When the slip is already in the notebook, it hands out a new number. It should hand back the ticket stored there.

Nodes go through the same desk

Now swap coats for nodes. Hash consing is the name for running every new node through a coat check. Each part of the desk gets a new name:

at the deskin the compiler
a coat on a hooka node
the ticket numberthe node's id, written n0, n1 and so on
the slipthe key: the op, the ids of the sources in order and the arg
the notebookthe table, also called the cache

The sources of a node are the boxes its arrows come from. The arg is its extra data, such as the 2 in the node for the number 2 (lesson 1.1 names that op const). So the number 2 has the key (const, [], 2). If 2 gets id n0 and 3 gets id n1, then add 2 3 has the key (add, [n0, n1]).

%a   = add 2 3
%b   = add 2 3
%out = mul %a %b

Building this program sends 7 requests to the desk: a 2, a 3 and an add for line 1, the same three again for line 2, then the mul.

Guess first. Out of those 7 requests, how many make a new node?

A request makes a node only when its key is not in the table yet. Which requests repeat an earlier one?

Four: 2, 3, add and mul. The three requests for line 2 are all found in the table. Step through and watch each one.

Line 2 made no new box, and %b names the very same node as %a. That is the promise from the last part: equal nodes are now always the same node, so the one-step check is enough.

The table compares keys, not meanings. add 3 2 has the key (add, [n1, n0]), with the sources in the other order, so it becomes a new node even though it is also 5. Making those two meet is a job for rewrite rules (H.3).

The lookup by hand in your language, and where the name comes from

The table already holds the first three nodes. The key is a tuplepair of the op and a list of ids, and the stored value here is the id:

>>> table = {("const", 2): 0, ("const", 3): 1, ("add", 0, 1): 2}
>>> ("add", 0, 1) in table
True

>>> ("add", 1, 0) in table

The name comes from Lisp, where cons builds a pair and "hash" is the table. In your real compiler each node also carries a dtype and a shape, and they are part of the key (lesson 1.1).

Why the key holds ids, not whole boxes

Back at the desk, an actor needs a full outfit: a coat and a hat. There are two ways to fill in the slip. One describes the coat and the hat again in full. The other says "the coat on hook 0 and the hat on hook 1". The second slip is short, and it stays short however fancy the coat is.

Nodes work the same way. Take x30 = add x29 x29 from the doubling chain, where x29 has the id n29.

Guess first. To look a key up, a table has to read the whole key. Which key for x30 can it read in a few steps?

Written out as a tree, x29 is about a billion boxes.

The key with ids is three small things. The other key is two billion boxes, and the table would read all of them on every lookup.

The ids are enough because every source already went through the table. Each source is the only node of its kind, so its id stands for everything under it. Two keys with the same op and the same ids describe the same node, all the way down.

  1. Get the ids. Both sources of x30 are x29, with id n29.
  2. Write the key. (add, [n29, n29]).
  3. Look it up. The table reads three small things. It never looks inside x29.

So building a node costs the same few steps whether there are 3 boxes under it or 3 billion.

How your language can do the slow thing without telling you, for when you write your real node type

To find a key, a hash table first computes a number from it (its hash) and then checks the candidates with equality. If the key held the whole source, checking for a match would look inside the source, and inside its sources, all the way down, and so would computing the hash.

A frozen dataclass with the default eq=True compares and hashes by every field, recursively. Used as a dict key, or with ==, a node then walks its whole subtree. Python and OCaml, deeper shows the fix (eq=False, so a node compares by identity).The generic Hashtbl and = are structural. A table keyed on the nodes themselves compares subtrees on every lookup. Python and OCaml, deeper shows the fix (key on ids with Hashtbl.Make).

A trap for later: a decimal number in the key

Week 1 has only whole numbers, so you can leave this part until week 2. A number node keeps its number in the key. Decimal numbers, called floats, have two odd values:

  • -0.0, a negative zero. It is equal to 0.0, but it is a different value: in C, 1.0 / -0.0 is minus infinity.
  • nan, "not a number", the result of 0.0 / 0.0. It is not equal to anything, not even itself.

A table keys float nodes on the plain float. A program has the constants 0.0 and -0.0. What happens?

Is 0.0 equal to -0.0? What does the table use to decide that two keys match?

They compare equal, so the table finds the first one and hands it back. But they are different values (in C, dividing 1.0 by them gives infinities of opposite sign), so merging them is a bug. Keying on the bits keeps them apart.

The fix is to put the float's bits in the key, not the float. Every float is stored as 64 bits (H.4 shows them). The two zeros have different bits, and a nan has the same bits as another nan made the same way.

>>> import struct
>>> struct.pack(">d", 0.0).hex()
'0000000000000000'
>>> struct.pack(">d", -0.0).hex()
'8000000000000000'
# Int64.bits_of_float 0.0;;
- : int64 = 0L
# Int64.bits_of_float (-0.0);;
- : int64 = -9223372036854775808L

struct.pack(">d", x) gives the 8 bytes of the float x, and .hex() writes them out as digits. The bytes themselves make a fine key.Int64.bits_of_float gives the 64 bits as an int64. The top bit is the sign, which is why -0.0 shows as the most negative int64.

A key for a float

Write float_key x: a value to use as a table key in place of the float x. Two keys must be equal exactly when the two floats have the same bits. So float_key 0.0 and float_key (-0.0) differ, and float_key nan = float_key nan.

One call from the standard library gives you the bits as an int64.

What a real table does with the two zeros and with nan, and one more trap of the same kind

A table that compares keys with equality turns the two zeros into one key, and a nan key may never be found again:. (A nan key does work in OCaml's Hashtbl, because it matches keys with compare, which treats nan as equal to itself. nan = nan is still false.)

>>> d = {0.0: "plus zero"}
>>> d[-0.0] = "minus zero"
>>> d
{0.0: 'minus zero'}
>>> nan = float("nan")
>>> nan == nan
False
>>> print({nan: 1}.get(float("nan")))
None
>>> struct.pack(">d", float("nan")).hex()
'7ff8000000000000'
# let h = Hashtbl.create 8;;
val h : ('_weak1, '_weak2) Hashtbl.t = <abstr>
# Hashtbl.replace h 0.0 "plus zero";;
- : unit = ()
# Hashtbl.replace h (-0.0) "minus zero";;
- : unit = ()
# Hashtbl.length h;;

# nan = nan;;
- : bool = false
# Int64.bits_of_float nan = Int64.bits_of_float nan;;

The second store overwrote the first, so a program that has both zeros would get one node for both, and a wrong answer. Bits compare like plain whole numbers, so a table keyed on them behaves.

There's one more Python trap of the same kind, and it matters in week 1: 1 == True, so {1: "a", True: "b"} has one key. Put the type in the key too. Lesson 0.7Lesson 0.6 showed the same trap for the course's own constants.
