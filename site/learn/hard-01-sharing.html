Sharing nodes

A compiler stores a program as a picture of boxes and arrows. When the same piece appears twice, you can draw it twice or draw it once and point at it from two places. This page is about the second way: why it matters so much, and how a lookup table makes it happen by itself.

Before you start

You should be comfortable with your own types and with tables of key and value: P.3 (dicts) and P.4 (classes and dataclasses)O.4 (variants and records) and O.5 (Hashtbl). Code on this page follows your Language setting in the sidebar. The ideas are the same in both languages.

One recipe, used twice

Picture a cookbook. The pizza needs tomato sauce, and so does the pasta. The writer could print the sauce recipe twice, once inside each dish. Or the writer could print it once, on page 12, and have both dishes say "see page 12". The second book is shorter, and if you fix a mistake in the sauce, you fix it in one place.

Expressions have the same choice. Take (a + b) * (a + b). Each box in the drawing below is a node. The arrows go from a node to the node that uses it. A node that another node reads from is that node's child, and the node reading it is its parent. The nodes with no children (a and b) are leaves.

A tree gives every use its own copy, so a + b appears twice. A DAG lets two arrows leave the same node, so a + b appears once and * points at it twice. DAG stands for directed acyclic graph: the arrows have a direction, and following them never brings you back where you started. Step through it.

Sources sit on top and results flow down, the same way as every graph in the course. Both drawings compute the same number. The DAG computes a + b once instead of twice.

How fast a tree grows

One shared node saves one copy. That sounds small. It isn't, because sharing can stack. Start with a leaf x0. Then let x1 = x0 + x0, x2 = x1 + x1, and keep going. Each level uses the level below it twice.

As a DAG, each level adds one node. As a tree, each level holds two full copies of the level below, plus one new + on top. So the tree size doubles, plus one, at every level. Step through the first few levels and watch the left side.

Equal, or the same one?

Two copies of the same book on a shelf are equal: same words, same pages. One book with two bookmarks in it is the same book, reached two ways. Programs make this distinction too.

  • Equality asks "do these two values look the same, all the way down?" It compares contents.
  • Identity asks "are these the very same value in memory?" It compares where they live. That's one step, however big the value is.
>>> a = [1, 2]
>>> b = [1, 2]
>>> a == b
True
>>> a is b
False
>>> c = a
>>> c is a
True

# let c = a;;

# c == a;;
- : bool = true

a and b were built separately, so they are equal but not the same. c = alet c = a doesn't copy anything. It gives the same list a second name.

That result is from utop, where each line is built on its own. A compiled program may store two identical constant lists only once, and then a == b is true. So don't use == on values you wrote out by hand. Values built while the program runs, like your compiler's nodes, are only the same when your code makes them the same.

The symbols swap between the languages

Python's == is equality and OCaml's == is identity. When you read code in the other language, check which one you're looking at. And use identity only on values you built, like nodes. For numbers and strings, is gives answers that depend on how Python stores them, so compare those with ==.For floats and strings, == gives answers that depend on how OCaml stores them, so compare those with =.

Why care? Comparing two separately built copies of x30 with equality walks both trees, two billion steps. If you could promise that equal nodes are always the same node, the cheap identity check would answer the equality question too. That promise is the next idea.

Hash consing: a coat check for nodes

At a theater coat check, you hand over a coat and get a ticket with a number. Now imagine a coat check that also remembers every coat it has seen. You hand over a coat. The attendant looks it up first. If an identical coat is already on the rack, you get that ticket back, and nothing new goes on the rack. Only a coat it has never seen gets a new hook and the next number.

Hash consing is that coat check, for nodes. You keep one table. Before you make a node, you build its key, a small description of it:

  • the op, like "+",
  • the ids of its children, in order.

Then you look the key up. If it's there, you hand back the node that's already stored. If it isn't, you make the node, give it the next id (0, 1, 2, and so on), and store it under the key. The name comes from Lisp, where cons builds a pair and "hash" is the table. Step through building (a + b) * (a + b), reading it left to right.

Seven requests, four nodes. The second a + b came back as node 2, the same node as the first, so the * points at one node twice. Nobody had to notice the repeat. The table did it.

Here is the lookup part by hand, with the table already holding the first three nodes. The key is a tuplepair of the op and a list of ids (the pictures write ("+", 0, 1), OCaml writes ("+", [0; 1])), and the stored value is the id:

>>> table = {("leaf", "a"): 0, ("leaf", "b"): 1, ("+", 0, 1): 2}
>>> ("+", 0, 1) in table
True
>>> table[("+", 0, 1)]
2
>>> ("+", 1, 0) in table
False
# let table = Hashtbl.create 16;;
val table : ('_weak1, '_weak2) Hashtbl.t = <abstr>
# Hashtbl.add table ("+", [0; 1]) 2;;
- : unit = ()
# Hashtbl.find_opt table ("+", [0; 1]);;
- : int option = Some 2
# Hashtbl.find_opt table ("+", [1; 0]);;
- : int option = None

The last lookup misses on purpose. b + a has its children in the other order, so its key is different, and it becomes a new node. Hash consing compares structure, not meaning. Making a + b and b + a meet is a job for rewrite rules (H.3).

What you get

Once every node goes through the table, two nodes with the same op and the same children are always the same node. So "are these two expressions equal?" becomes "are they the same node?", which is one identity check. In lesson 1.1 you write the full constructor, a function that does the lookup and the storing, for your own compiler.

Why the key holds ids, not whole children

You might ask: why put the children's ids in the key? Why not the children themselves?

Because of what a table does with a key. To find a key, a hash table first computes a number from it (its hash) and then checks the candidates with equality. If the key held the whole child, checking for a match would look inside the child, and inside its children, all the way down, and so would computing the hash. For x30, one lookup would walk two billion nodes.

The ids avoid that. A child that went through the table is unique, so its id stands for its entire subgraph. The key for x30 is ("+", 29, 29): three small values, whatever lies underneath. Every lookup costs the same few steps.

The float trap in a key

Leaves often hold a number, and the number goes in the key. For whole numbers that's fine. Floats have two values that break a table's idea of "the same key":

  • -0.0, a negative zero. It is equal to 0.0 but it is a different value: in C, 1.0 / -0.0 is minus infinity.
  • nan, "not a number", the result of something undefined like 0.0 / 0.0. It is not equal to anything, not even itself.

A table that compares keys with equality gets these wrong. The two zeros turn into one key, and a nan key may never be found again:. (A nan key does work in OCaml's Hashtbl, because it matches keys with compare, which treats nan as equal to itself. nan = nan is still false.)

>>> d = {0.0: "plus zero"}
>>> d[-0.0] = "minus zero"
>>> d
{0.0: 'minus zero'}
>>> nan = float("nan")
>>> nan == nan
False
>>> print({nan: 1}.get(float("nan")))
None
# let h = Hashtbl.create 8;;
val h : ('_weak1, '_weak2) Hashtbl.t = <abstr>
# Hashtbl.replace h 0.0 "plus zero";;
- : unit = ()
# Hashtbl.replace h (-0.0) "minus zero";;
- : unit = ()
# Hashtbl.length h;;
- : int = 1
# nan = nan;;
- : bool = false

The second store overwrote the first, so a program that has both zeros would get one node for both, and a wrong answer. The fix is to put the float's bits in the key instead of the float. Every float is stored as 64 bits (H.4 shows them). The two zeros have different bits, and a nan has the same bits as another nan made the same way. Bits compare like plain whole numbers, so the table behaves.

>>> import struct
>>> struct.pack(">d", 0.0).hex()
'0000000000000000'
>>> struct.pack(">d", -0.0).hex()
'8000000000000000'
>>> struct.pack(">d", float("nan")).hex()
'7ff8000000000000'
# Int64.bits_of_float 0.0;;
- : int64 = 0L
# Int64.bits_of_float (-0.0);;
- : int64 = -9223372036854775808L
# Int64.bits_of_float nan = Int64.bits_of_float nan;;
- : bool = true

struct.pack(">d", x) gives the 8 bytes of the float x, and .hex() writes them as hex digits. The bytes themselves make a fine key.Int64.bits_of_float gives the 64 bits as an int64. The top bit is the sign, which is why -0.0 shows as the most negative int64. There's one more Python trap of the same kind: 1 == True, so {1: "a", True: "b"} has one key. Put the type in the key too. A key for a float

Write float_key x: a value to use as a table key in place of the float x. Two keys must be equal exactly when the two floats have the same bits. So float_key 0.0 and float_key (-0.0) differ, and float_key nan = float_key nan.

One call from the standard library gives you the bits as an int64.
