Rewriting until nothing changes

A compiler makes a program smaller with one small move, repeated: find a shape it knows and replace it with something simpler. This page is the slow version of that idea from lesson 1.3. You'll do it by hand on plain arithmetic first, and then in code.

Goal

Apply a few small rules to an expression, inside first, until no rule fits, and say why that stops.

You'll use

Arithmetic with parentheses for the first half. For the code, match with class patterns (P.4) and a function that calls itself (P.5).

Arithmetic with parentheses for the first half. For the code, match on variants and option (O.3 and O.4).

Warm up

Two questions from school arithmetic, from memory. Pulling an idea back out of your head is what makes it stay.

What is (6 + 0) * 1?

What does adding 0 do to a number? What does multiplying by 1 do?

6. Adding zero changes nothing, and neither does multiplying by one. This whole page grows out of those two facts.

You work out 2 * (3 + 4) by hand. Which part do you do first?

Look at the parentheses.

The inside of the parentheses has to become a number before the outside can use it. That order comes back later on this page.

Tidy one expression by hand

Here is an expression. x is a number you don't know yet.

(x + 0) * 1

Guess first. What is the shortest thing you can write that has the same value for every x?

Start inside the parentheses. What is x + 0?

Just x. Adding 0 changes nothing, so the inside is x. Then x * 1 is x too.

You never needed to know x. You also did not have one big insight. You made two tiny moves, and each one looked at a single spot:

  1. Drop the plus zero. x + 0 became x. That left x * 1.
  2. Drop the times one. x * 1 became x.

A compiler does this to programs. Programs that are built by other programs are full of pointless steps like + 0, and every step it removes is work the computer never has to do. But a compiler can't glance at an expression and see the answer the way you did. So we write your tiny moves down, one at a time, as rules it can follow.

A rule says: if it looks like this, replace it with that

A rewrite rule is one tiny move, written down. It has two halves with an arrow between them:

x + 0  →  x
x * 1  →  x

Read the arrow as "if it looks like the left side, replace it with the right side". The left half is the pattern, the shape to look for. The right half is the replacement. In a pattern, a letter like x stands for anything at all: a number, a name or a whole expression in parentheses. 0 and 1 stand only for those exact numbers. When the pattern fits, we say the rule fires.

Does x + 0 → x fire on y + (2 * 0)?

A pattern compares shapes. Does it do any arithmetic?

A rule looks at what is written, and it works nothing out. 2 * 0 is worth zero, but it is not the number 0 until something turns it into one.

expressiondoes x + 0 fit?x stands forresult
y + 0yesyy
(a * b) + 0yesa * ba * b
0 + yno, the 0 is on the wrong sideunchanged
y * 0no, this is a *unchanged
y + (2 * 0)no, the right side is not the number 0 (yet)unchanged

So we need a rule that turns 2 * 0 into a number. When both sides are plain numbers, do the math now:

number + number  →  their sum
number * number  →  their product

Doing the math early like this is called constant folding. One thing is true of every rule: both sides have the same value whatever x is. That is what makes a rule safe to apply without thinking.

A rule in code

In code, an expression is a small tree. Const(5) is a number, Var("x") is a name, and Add(a, b) and Mul(a, b) each hold two smaller expressions, called their children. So (x + 0) * 1 is Mul(Add(Var("x"), Const(0)), Const(1)).Const 5 is a number, Var "x" is a name, and Add (a, b) and Mul (a, b) each hold two smaller expressions, called their children. So (x + 0) * 1 is Mul (Add (Var "x", Const 0), Const 1). Each piece of the tree is called a node. Lesson 1.3 uses the same names.

Here are those four kinds of node, so you can paste the code on this page and run it:

from dataclasses import dataclass

@dataclass(frozen=True)
class Add:
    a: object
    b: object

    b: object

All the rules live in one function. Here it is with one rule:

def rule(e):
    match e:
        case Add(x, Const(0)):
            return x
    return None
let rule e =
  match e with
  | Add (x, Const 0) -> Some x
  | _ -> None

Each casebranch is one rule: the pattern, then the replacement. rule looks at one node and its children, and never deeper. It answers with the replacementSome replacement when a rule fires, and with None when no rule fits.

None means "no rule fits"

Don't hand back the same node to say that no rule fired. The code that calls rule could not tell "nothing fits" from "a rule built this", and later it would not know when to stop.

Teach it three more rules

rule knows x + 0 → x. Add x * 1 → x and the two folding rules, one for Add of two numbers and one for Mul of two numbers.

The tests print the result with parentheses, or no rule when the answer is None.

Fix the inside first

rule handles one spot. An expression has many. Where do you start? Try x + (2 * 0). It has two spots a rule could fit: the + on the outside and the * inside the parentheses.

You visit each spot once, outside first: the +, then the *. What are you left with?

When you look at the +, what is on its right side at that moment?

At the +, the right side was still 2 * 0, so x + 0 → x did not fit. Then the * folded to 0. That made x + 0, but you had already left the + behind. You missed one.

Now go the other way. Fold the inside first: x + 0. Then visit the +, and the rule fits: x. Same rules, same two visits, better answer.

It is the order you use for arithmetic by hand, for the same reason: a spot can only be dealt with once the parts inside it are done. In the tree, the inside parts are a node's children, so the order is children first (many books say bottom up). Lesson 1.3 calls a node's children its sources and says sources first. Each node takes two moves:

  1. Simplify the children. Do this whole job on each child first.
  2. Rebuild and ask. Make the node again from its simplified children, and offer that to rule.

Step through a bigger one. Before each Next, decide which node comes next and what happens to it.

A rewrite can uncover another

One more rule. 0 + x is as pointless as x + 0, but the pattern wants the 0 on the right. You could write every rule twice, once for each side. It is cheaper to add one tidy-up rule that moves a number to the right, so the other rules only ever look there:

number + x  →  x + number      when x is not a number

You go children first and offer each node to rule once. rule gets 0 + y, and the tidy-up rule fires. What is left?

The replacement is a brand new node. Has any rule looked at it yet?

The rule built y + 0. That node did not exist a moment ago, so no rule has seen it. Offer it to rule and x + 0 → x fires.

So going inside first is not enough by itself. A rewrite can create a new chance for another rewrite, at the very spot you just finished. That adds a third move:

  1. Try again. When a rule fires, offer the result to rule too. Keep going until rule says no rule fits.

Watch all three moves work together. Again, guess before each Next.

Stop when nothing changes

"Keep going" needs a stopping point. Here it is: stop when one more try changes nothing. Sanding a table works this way. You sand, run your hand over it, and sand again until your hand finds nothing left to fix.

The thing you end on has a name. It is a fixed point (lesson 1.3 writes fixpoint): do the step to it again and you get the same thing back. For the simplifier, "nothing changes" means rule says no rule fits.

Start at 20. Keep halving, dropping any remainder, until halving changes nothing: 20, 10, 5, 2 and so on. What number do you stop on?

After 2 comes 1. What is half of 1 with the remainder dropped? And half of that?

20, 10, 5, 2, 1, 0, and half of 0 is 0 again. So 0 is the fixed point of halving. It took five changes to get there.

Repeat until nothing changes

Write fixpoint f x. Apply f to x, then to the result, and so on, until applying it gives back an equal value. Return that value and the number of times f changed something, as a pair. Halving 100 with fun n -> n / 2 goes 50, 25, 12, 6, 3, 1, 0, and then 0 / 2 is still 0, so fixpoint (fun n -> n / 2) 100 is (0, 7).

The whole simplifier

Now put the three moves into one function. It is short:

def simplify(e):
    match e:
        case Add(a, b):
            e = Add(simplify(a), simplify(b))
        case Mul(a, b):
            e = Mul(simplify(a), simplify(b))
    while True:
        new = rule(e)
        if new is None:
            return e
        e = new
let rec simplify e =
  let e =
    match e with
    | Add (a, b) -> Add (simplify a, simplify b)
    | Mul (a, b) -> Mul (simplify a, simplify b)
    | Const _ | Var _ -> e
  in
  let rec again e =
    match rule e with Some r -> again r | None -> e
  in
  again e
  1. Simplify the children. The calls to simplify on a and b.
  2. Rebuild and ask. A new Add or Mul is made from the results and handed to rule.
  3. Try again. The while loopagain keeps offering the newest result until rule answers None.

A number or a name has no children and no rule fits it, so it comes back as it went in. Now repair a simplifier that forgets two of the three moves. It works on true and false in place of numbers, and the moves are the same.

Simplify true and false

The starter has expressions over T (true), F (false), names, Not, And and Or, and a finished rule function with the usual laws (x and T is x, not (not x) is x, and so on). Its simplify makes one pass from the top down, so it misses chances: And (Not (Not T), Var "p") comes out as (T and p) instead of p.

Rewrite simplify so it reaches the fixed point. Leave rule as it is.

Bottom-up: simplify the children, rebuild the node, then apply rule until it returns None. Or keep the pass and add the loop from this page around it. Either works.

What would make it never stop

"Until nothing changes" only ends if things do stop changing. Suppose a teammate likes numbers on the left and adds a rule that is the mirror image of your tidy-up rule:

yours:   number + x  →  x + number      when x is not a number
theirs:  x + number  →  number + x      when x is not a number

Start with 2 + y and let a rule fire twice. What do you have?

Write down what your rule makes of 2 + y. Which rule fits that?

Your rule makes y + 2. Their rule fits that and makes 2 + y again. Every try changes something, so "until nothing changes" never comes.

Each rule is fine alone. As a pair they undo each other, and the compiler hangs. One rule can even do it to itself: x + y → y + x, with no condition, fits its own result.

The cure is a habit. For every rule, name something that the rule makes smaller. A count can't drop below zero, so rules that all shrink something must run out.

rulewhat gets smaller
x + 0 → x, x * 1 → xthe number of nodes, by two
folding two numbersthe number of nodes, by two
number + x → x + number, when x is not a numberthe count of + nodes with a number on the left, by one
the teammate's rulenothing. It puts back what the rule above removed.

When you add a rule, check its result against every other rule's pattern. While you develop, give the loop a limit, say 1000 tries, and raise an error past it. Then a loop shows up as a message and not as a hang.

What you can do now

  • Read a rule as "if it looks like this, replace it with that", and say what x stands for.
  • Write a function that tries every rule on one node and says when none fits.
  • Simplify children before their parent, and say what goes wrong the other way.
  • Try again after a rule fires, and stop when nothing changes.
  • Spot a rule, or a pair of rules, that would never stop.

Whole passes: a second way to reach the fixed point, for when you read other simplifiers

This page tries again at each node. Another design offers each node to rule once, and repeats the whole walk until a walk changes nothing. One walk is called a pass.

def rewrite_once(e):
    match e:
        case Add(a, b):
            e = Add(rewrite_once(a), rewrite_once(b))
        case Mul(a, b):
            e = Mul(rewrite_once(a), rewrite_once(b))
    new = rule(e)
    return e if new is None else new

def simplify(e):
    while True:
        new = rewrite_once(e)
        if new == e:
            return e
        e = new
let rec rewrite_once e =
  let e =
    match e with
    | Add (a, b) -> Add (rewrite_once a, rewrite_once b)
    | Mul (a, b) -> Mul (rewrite_once a, rewrite_once b)
    | Const _ | Var _ -> e
  in
  match rule e with Some r -> r | None -> e

let rec simplify e =
  let e' = rewrite_once e in
  if e' = e then e else simplify e'

On (0 + x) * (3 + -2) it needs three passes, because pass 1 creates x + 0 after it has gone past that spot:

2x + 0x + 0xyes
3xnonexno, so stop

Both designs reach the same fixed point here. Trying again at each node saves whole passes. Lesson 1.3 does both: it tries again at each node, and its lab simplifier also repeats passes until one changes nothing.

The comparison new == ee' = e is equality, which walks both trees. That is fine for small examples. In your compiler, nodes are hash consed, so "did anything change?" is the identity check new is ee' == e, one step.

Shared graphs: what changes when a node has two parents, for when you write the lab simplifier

So far the expressions were trees. Your compiler's graphs are shared DAGs (H.1). A tree-style walk treats a DAG like a tree: a shared node is rewritten once for every path to it, and each time it builds a new copy of the result. The sharing is gone, and on the doubling chain the work explodes. Step through what goes wrong and how to fix it.

The fix has two parts, both from earlier pages:

  • A memo from old node to new node (H.2), keyed by identity. A shared node is rewritten once. Every parent that reaches it again gets the answer from the memo.
  • Build every result through the hash-consing table (H.1), including the nodes that rules make. If a rewrite produces a node that already exists, you get the existing one back, so two parts that become equal become the same node.

With both, a pass costs one step per distinct node, and the result is as shared as it can be. Lesson 1.3 has the course's version of this loop, walking the graph in topological order.

Rule order, floats and where rewriting shows up in the course

Rule order. Cases are tried top to bottom, and the first match wins. The tidy-up rule Add(Const(m), x)Add (Const m, x) would also match 2 + 3. Put the folding rule above it, and the swap only ever fires when the right side is not a number. A rule that only puts things into one fixed order like this is called canonicalization, and it is how a compiler makes 3 + x and x + 3 meet.

Floats. x + 0 → x is safe for whole numbers. For floats it isn't: -0.0 + 0 is 0.0, not -0.0. H.4 explains -0.0.
