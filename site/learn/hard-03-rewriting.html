Rewriting until nothing changes

Most of what a compiler does to make a program smaller is one small move, repeated: find a shape it recognizes and replace it with something simpler. This page builds that move slowly, from one rule on one node to a loop that runs until no rule fits anywhere.

Before you start

You need pattern matching: match with class patterns, from P.4match on variants, from O.3 and O.4. H.1 and H.2 help with the last section.

A rule is a pattern and a replacement

Think of tidying a sentence. "Find do not, write don't." That instruction has two halves: what to look for, and what to put in its place. A rewrite rule is the same thing for expressions:

x + 0      →  x
x * 1      →  x
m + n      →  the number m + n       when m and n are both numbers
m * n      →  the number m * n       when m and n are both numbers

The left side is the pattern. The right side is the replacement. In a pattern, a letter like x is a pattern variable: it matches anything, a single number, a name, or a whole sub-expression, and it remembers what it matched so the replacement can use it. 0 and 1 match only those exact numbers. The last two rules, which compute a result from two known numbers, are called constant folding.

Every rule must keep the meaning. x + 0 has the same value as x for every whole number x, so the rule is safe for integers. (For floats it isn't: -0.0 + 0 is 0.0, not -0.0. H.4 explains -0.0.)

Matching one node

A rule matches a node when the node has the pattern's shape. Matching looks at one node and, at most, the children named in the pattern. It doesn't search the whole expression. That's the walk's job, in the next section.

y + 0yesyy
(a * b) + 0yesa * ba * b
0 + yno, the 0 is on the wrong sideunchanged
y * 0no, the op is *unchanged
y + (1 - 1)no, the right side is not the number 0 (yet)unchanged

The last row matters: a rule sees structure, not value. 1 - 1 is zero, but it isn't the number 0 until something folds it. In code, one function tries every rule on one node. It returns the replacement when a rule fires, and "nothing" when none does. Here are the four rules above, plus one more that the next sections need: move a number from the left of a + to the right.

from dataclasses import dataclass

@dataclass(frozen=True)
class Num:
    n: int

@dataclass(frozen=True)
class Var:
    name: str

@dataclass(frozen=True)
class Add:
    a: object
    b: object

@dataclass(frozen=True)
class Mul:
    a: object
    b: object

def rule(e):
    match e:
        case Add(x, Num(0)):
            return x
        case Mul(x, Num(1)):
            return x
        case Add(Num(m), Num(n)):
            return Num(m + n)
        case Mul(Num(m), Num(n)):
            return Num(m * n)
        case Add(Num(m), x):
            return Add(x, Num(m))
    return None
type e = Num of int | Var of string | Add of e * e | Mul of e * e

let rule e =
  match e with
  | Add (x, Num 0) -> Some x
  | Mul (x, Num 1) -> Some x
  | Add (Num m, Num n) -> Some (Num (m + n))
  | Mul (Num m, Num n) -> Some (Num (m * n))
  | Add (Num m, x) -> Some (Add (x, Num m))
  | _ -> None
>>> rule(Add(Var("y"), Num(0)))
Var(name='y')
>>> print(rule(Mul(Var("y"), Num(2))))
None
# rule (Add (Var "y", Num 0));;
- : e option = Some (Var "y")
# rule (Mul (Var "y", Num 2));;
- : e option = None

Cases are tried top to bottom, and the first match wins. That order is doing real work in the last rule. Add(Num(m), x) would also match 2 + 3, but the folding rule above it catches that first, so the swap only ever fires when the right side is not a number. Keep that in mind for the section on stopping.

A rule returns "nothing" when it doesn't fire

Don't return the node unchanged to mean "no rule fired". Then the code that calls rule can't tell "nothing happened" from "a rule produced this", and the loop below has no way to stop. Return None.Return None, and Some r when a rule fires.

Bottom-up through a tree

A rule works on one node. To simplify a whole expression, you walk it and offer each node to rule. The order matters. Go bottom-up: rewrite a node's children first, then the node. That way, when the walk reaches a node, its children are already as simple as they'll get in this pass, and a rule like x + 0 can see a 0 that folding a child has produced. Step through (x + 1 * 0) * (0 + 1).

def rewrite_once(e):
    match e:
        case Add(a, b):
            e = Add(rewrite_once(a), rewrite_once(b))
        case Mul(a, b):
            e = Mul(rewrite_once(a), rewrite_once(b))
    new = rule(e)
    return e if new is None else new
let rec rewrite_once e =
  let e =
    match e with
    | Add (a, b) -> Add (rewrite_once a, rewrite_once b)
    | Mul (a, b) -> Mul (rewrite_once a, rewrite_once b)
    | Num _ | Var _ -> e
  in
  match rule e with Some r -> r | None -> e

rewrite_once rebuilds the node from its rewritten children, then tries the rules on the rebuilt node, once. A leaf (a number or a name) has no children and no rule matches it, so it comes back as it went in.

Why one pass isn't enough

Sometimes a rule's result is itself something a rule could simplify, but the pass has already moved past that spot. Take (0 + x) * (3 + -2):

passexpression at the startrules that firedexpression at the endchanged?
1(0 + x) * (3 + -2)number to the right, fold, x * 1x + 0yes
2x + 0x + 0xyes
3xnonexno, so stop

In pass 1, moving the 0 to the right created x + 0, and the x * 1 rule then lifted that x + 0 up to the top. No node in pass 1 was offered x + 0 after it existed. Rewrites create new chances for other rewrites, so you can't know in advance how many passes you'll need.

# rewrite_once e;;
- : e = Add (Var "x", Num 0)

The fixed-point loop

So repeat the pass until a pass changes nothing. Sanding a table works this way: you sand, run your hand over it, and sand again until your hand finds nothing left to fix. The expression where one more pass changes nothing is a fixed point (also written fixpoint) of the pass.

def simplify(e):
    while True:
        new = rewrite_once(e)
        if new == e:
            return e
        e = new
let rec simplify e =
  let e' = rewrite_once e in
  if e' = e then e else simplify e'
>>> simplify(e)
Var(name='x')
# simplify e;;
- : e = Var "x"

The comparison new == ee' = e is equality, which walks both trees. That is fine for these small examples. In your compiler, nodes are hash consed, so "did anything change?" is the identity check new is ee' == e, one step (lesson 1.3).

A pass can also repeat at one node: after a rule fires, try the rules again on the result before moving up. Lesson 1.3 does that, and it saves whole passes. Both reach the same fixed point here.

Repeat until nothing changes

Write fixpoint f x. Apply f to x, then to the result, and so on, until applying it gives back an equal value. Return that value and the number of times f changed something, as a pair. Halving 100 with fun n -> n / 2 goes 50, 25, 12, 6, 3, 1, 0, and then 0 / 2 is still 0, so fixpoint (fun n -> n / 2) 100 is (0, 7).

Will it stop?

"Repeat until nothing changes" only ends if things eventually stop changing. Here is a rule that sounds harmless, "addition doesn't care about order, so swap":

x + y  →  y + x

The output matches the pattern again, every time. The loop never reaches a fixed point, and your compiler hangs. The cure is to make every rule make progress: name something that each rule makes strictly smaller, so it can't go on forever.

rulewhat gets smaller
x + 0 → x, x * 1 → xthe number of nodes, by two
m + n → number, m * n → numberthe number of nodes, by two
m + x → x + m, only when x is not a numberthe number of + nodes with a number on the left, by one
x + y → y + x, alwaysnothing. It loops.

The guarded swap is safe because its output has the number on the right, where the swap no longer matches. A rule that only puts things into one fixed order like this is called canonicalization, and it's how a compiler makes 3 + x and x + 3 meet.

Two rules can loop together

Each rule can be fine alone and still loop as a pair. "Move numbers to the right" plus a rule elsewhere that "moves numbers to the left" in some case will undo each other forever. When you add a rule, check its output against every other rule's pattern. While developing, give the loop a pass limit, say 1000, and raise an error past it, so a loop shows up as a message instead of a hang.

Simplify true and false

The starter has expressions over T (true), F (false), names, Not, And and Or, and a finished rule function with the usual laws (x and T is x, not (not x) is x, and so on). Its simplify makes one pass from the top down, so it misses chances: And (Not (Not T), Var "p") comes out as (T and p) instead of p.

Rewrite simplify so it reaches the fixed point. Leave rule as it is.

Bottom-up: simplify the children, rebuild the node, then apply rule until it returns None. Or keep the pass and add the loop from this page around it. Either works.

Keeping the result shared

So far the expressions were trees. Your compiler's graphs are shared DAGs (H.1). rewrite_once as written walks a DAG like a tree: a shared node is rewritten once for every path to it, and each time it builds a new copy of the result. The sharing is gone, and on the doubling chain the work explodes. Step through what goes wrong and how to fix it.

The fix has two parts, both from earlier pages:

  • A memo from old node to new node (H.2), keyed by identity. A shared node is rewritten once. Every parent that reaches it again gets the answer from the memo.
  • Build every result through the hash-consing table (H.1), including the nodes that rules make. If a rewrite produces a node that already exists, you get the existing one back, so two parts that become equal become the same node.

With both, a pass costs one step per distinct node, and the result is as shared as it can be. Lesson 1.3 has the course's version of this loop, walking the graph in topological order.
