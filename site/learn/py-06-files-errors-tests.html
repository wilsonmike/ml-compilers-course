Learn Python · Lesson 6

Files, errors and testing

A compiler is a real program: it's split across several files, it reads its input from a file named on the command line, it reports what happened in a way other programs can read, and it needs tests so you know it still works after every change. This lesson covers each of those, and how to find a bug when something goes wrong.

Modules and imports

Once a program grows past a page or two, you split it into several files. Each .py file is a module, and one module can use the functions of another by importing it. Make a folder with two files. The first, words.py, holds some tools for working with text:

def count_words(text):
    return len(text.split())

def longest_word(text):
    return max(text.split(), key=len)

if __name__ == "__main__":
    print(count_words("the cat sat on the mat"))

The second, main.py, uses them:

from words import count_words, longest_word

text = "a rose is a rose is a rose"
print(count_words(text), "words")
print("longest:", longest_word(text))
$ python main.py
8 words
longest: rose

($ stands for your terminal's prompt. Type what follows it, and the lines after are what the program prints.)

from words import count_words, longest_word tells Python: find words.py, run it, and bring those two names into this file. Python looks for it in the folder of the program you ran, which is why both files go in one folder. There's a second way to write it:

import words

print(words.count_words("a rose is a rose"))

import words brings in the whole module under one name, and you reach inside it with a dot. Both are fine. The dotted form makes it obvious where a name came from, which helps once you have many modules. The modules that come with Python, like sys, math and dataclasses, are imported the same way.

Now the last two lines of words.py. Every module has a variable called __name__. When you run a file directly, as in python words.py, Python sets it to "__main__". When the file is imported, it's set to the module's name, "words". So the code under if __name__ == "__main__": only runs when you run the file itself:

$ python words.py
6

When main.py imports words, the 6 isn't printed. Without the if, it would be, every time anything imported the module. Use this to keep a quick check, or a module's command-line entry point, in the same file as its functions.

Don't name a file after a module you use

Call your own file random.py, and import random anywhere in that folder finds your file instead of Python's. The errors that follow are baffling, like AttributeError: module 'random' has no attribute 'randint'. Pick names that aren't already taken.

Reading and writing files

To write a text file, open it for writing with "w", and write strings to it:

>>> with open("shopping.txt", "w", encoding="utf-8") as f:
...     f.write("milk\neggs\nbread\n")
...
16

Piece by piece:

  • open(name, "w", ...) opens the file for writing. "w" creates the file, or empties it if it already exists. Leave the mode out and you get "r", for reading.
  • encoding="utf-8" says how characters are stored as bytes. Always write it. Without it, Python uses whatever your computer's default is, which on Windows is often not UTF-8, so a file with an é in it can read back wrong or fail on another machine.
  • with ... as f: names the open file f for the indented block, and closes it when the block ends, even if an error happens inside. A file that isn't closed may not have all its text saved yet.
  • f.write(...) returns how many characters it wrote, and the REPL shows that 16. write doesn't add a newline for you, so the string has its own \ns.

Reading it back works the same way, with f.read(), which returns the whole file as one string:

>>> with open("shopping.txt", encoding="utf-8") as f:
...     text = f.read()
...
>>> text
'milk\neggs\nbread\n'
>>> text.splitlines()
['milk', 'eggs', 'bread']
>>> text.split("\n")
['milk', 'eggs', 'bread', '']

splitlines() cuts the text into lines and drops the line endings. Compare it with split("\n"), which sees the final \n as the start of one more, empty, line. Text files almost always end with a newline, so splitlines() is the one you want. It also handles Windows line endings (\r\n). With split("\n"), every line would keep a \r at its end.

Opening a file that doesn't exist raises an error:

>>> open("nope.txt", encoding="utf-8")
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
FileNotFoundError: [Errno 2] No such file or directory: 'nope.txt'

A plain file name like "shopping.txt" is looked up in the current directory: the folder your terminal was in when you started Python, which isn't always the folder the program is in. If a file you can see "isn't there", check where you ran the program from.

Exceptions: raising and catching

When Python can't carry out an operation, it raises an exception: an object that describes what went wrong. If nothing deals with it, the program stops and prints a traceback, ending with the exception's type and message. You've seen a few:

>>> int("seven")
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
ValueError: invalid literal for int() with base 10: 'seven'
>>> {"a": 1}["b"]
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
KeyError: 'b'
>>> 10 / 0
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
ZeroDivisionError: division by zero

The type (ValueError, KeyError, ZeroDivisionError) says what kind of problem it is. The message after the colon says which value caused it. To handle an exception yourself, put the risky code in a try block and say what to do in an except block:

def to_number(s):
    try:
        return int(s)
    except ValueError:
        return None
>>> to_number("42")
42
>>> print(to_number("seven"))
None

Python runs the try block. If it finishes, the except block is skipped. If a ValueError is raised partway, Python jumps straight to the except ValueError: block and carries on from there. Any other kind of exception isn't caught here, and keeps going up as if the try weren't there.

That last part matters. Always name the exception you expect. Here's what happens without a name:

def to_number(s):
    try:
        return int(text)
    except:
        return None
>>> print(to_number("42"))
None
A bare except hides your bugs

The function above has a typo: text instead of s. That raises NameError, which a bare except: catches along with everything else, so every call quietly returns None and nothing tells you why. With except ValueError:, the NameError would have stopped the program on the first call and pointed at the line. Catch the specific error you expect, and let the rest be loud.

Division that doesn't crash

Write safe_div(a, b): a / b, or None when b is zero. Use try and except. Any other problem, like dividing a string, must still raise its error.

Which exception does 1 / 0 raise? Catch that one, by name, and nothing else.

Your own functions can raise exceptions too, with raise. Do it when you're given something you can't sensibly work with:

def withdraw(balance, amount):
    if amount > balance:
        raise ValueError(f"cannot take {amount} from {balance}")
    return balance - amount
>>> withdraw(10, 3)
7
>>> withdraw(10, 30)
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
  File "<stdin>", line 3, in withdraw
ValueError: cannot take 30 from 10

raise stops the function at once, the same way an error from Python would. The caller decides what to do: catch it, or let it stop the program. Put the bad value in the message. "cannot take 30 from 10" is far more helpful than "invalid amount".

For errors that belong to your program, make your own exception class. It's a class that names Exception in parentheses, which makes it a kind of exception. It usually needs no body, and pass is Python's way of writing an empty block:

class ParseError(Exception):
    pass

def parse_age(s):
    if not s.isdigit():
        raise ParseError(f"not an age: {s!r}")
    return int(s)
>>> try:
...     parse_age("ten")
... except ParseError as err:
...     print("bad input:", err)
...
bad input: not an age: 'ten'

except ParseError as err: catches only your own errors, and names the exception err so you can print its message. Errors from anywhere else, including real bugs, still get through. That's the point of having your own class. In the course, your compiler raises one when it reads a program that isn't valid, catches it in one place, and reports it. Lesson 0.7 shows how.

Parse key=value lines

Write parse_pairs(text), which turns lines like name = Ann into a dict of strings, {'name': 'Ann'}. Remove spaces around each key and each value. Skip blank lines. A value may contain =: x=1=2 gives {'x': '1=2'}. A non-blank line with no =, or with nothing before the =, is an error: raise ValueError(f"bad line {n}: {line!r}"), where n counts lines from 1, blank ones included.

line.partition("=") splits at the first = only, and returns three strings: before, the = itself (or "" if there was none), and after. enumerate(lines, 1) counts from 1. s.strip() removes the spaces from both ends of s.

Talking to the shell: arguments and exit codes

A program run from a terminal gets its command-line arguments in sys.argv, a list of strings. python count.py shopping.txt gives ["count.py", "shopping.txt"]: the program's name first, then the arguments, so sys.argv[1:] is the arguments alone.

When a program ends, it hands the shell a whole number called its exit code (or exit status). 0 means it worked. Anything else means it failed, and different numbers can mean different failures. sys.exit(n) ends the program with code n. Here's a program that counts the lines in a file, using everything so far:

import sys

def main(argv):
    if len(argv) != 1:
        print("usage: python count.py FILE", file=sys.stderr)
        return 2
    try:
        with open(argv[0], encoding="utf-8") as f:
            text = f.read()
    except FileNotFoundError:
        print(f"count.py: no such file: {argv[0]}", file=sys.stderr)
        return 1
    print(len(text.splitlines()), "lines")
    return 0

if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))
$ python count.py shopping.txt
3 lines
$ echo $?
0
$ python count.py
usage: python count.py FILE
$ echo $?
2
$ python count.py nope.txt
count.py: no such file: nope.txt
$ echo $?
1

echo $? prints the last program's exit code in bash and zsh, the usual shells on Linux and macOS. In PowerShell it's echo $LASTEXITCODE, and in the old Windows cmd it's echo %ERRORLEVEL%. print(..., file=sys.stderr) sends a message to stderr, a second output meant for errors, so it doesn't get mixed into the program's real output. By habit, 2 means "you called me wrong".

Notice the shape. All the work happens in main(argv), which returns the exit code, and only the last line calls sys.exit. You can call main(["shopping.txt"]) from a test or the REPL and check what it returns, without the program ending under you.

If a program stops with an exception nobody caught, Python prints the traceback and exits with code 1. The course's grader runs your compiler on each test program and reads the one line it prints, such as MATCH case.uir or REJECTED case.uir. A crash prints a traceback instead of that line, so it fails the test, even one where the right answer was REJECTED. Lesson 0.7 gives the exact rules.

An adder that never crashes

Write main(argv) for a tiny command add A B. argv is the arguments without the program name. If there are exactly two and both are whole numbers, print their sum and return 0. Otherwise print a short message to sys.stderr and return 2. It must never raise.

Check len(argv) first. Then int() raises ValueError on something like "x", which you can catch. The tests check what main returns.

Reading a long traceback

Real errors happen deep inside a program, several calls down. Here's a small report that adds up scores, with one bad line of data:

def parse_score(line):
    name, score = line.split(",")
    return int(score)

def total(lines):
    result = 0
    for line in lines:
        result += parse_score(line)
    return result

def main():
    lines = ["ann,7", "bob,12", "cat,nine"]
    print(total(lines))

main()
$ python report.py
Traceback (most recent call last):
  File "C:\Users\you\report.py", line 15, in <module>
    main()
  File "C:\Users\you\report.py", line 13, in main
    print(total(lines))
          ^^^^^^^^^^^^
  File "C:\Users\you\report.py", line 8, in total
    result += parse_score(line)
              ^^^^^^^^^^^^^^^^^
  File "C:\Users\you\report.py", line 3, in parse_score
    return int(score)
           ^^^^^^^^^^
ValueError: invalid literal for int() with base 10: 'nine'

(The path shows where report.py is on your computer, so yours will differ.) A traceback is the call stack from lesson P.5, printed at the moment of the error. Each File ... line ... in ... entry is one frame, with the line it was running under it. ^^^^ marks the part of the line that was running. "Most recent call last" means the newest frame is at the bottom. Read it twice.

Bottom up, to see what and where. The last line is the error: a ValueError, because int was given 'nine'. The entry right above it is where it happened: line 3, in parse_score, at int(score). Often that's enough.

Top down, to see how you got there. The module called main() on line 15. main called total on line 13. total called parse_score on line 8. The bug is rarely in Python's own code, and not always in the bottom frame either. Here, parse_score did the right thing with bad input. The question is where 'nine' came from, and the frames above lead you back to the list in main.

Frames you didn't write

Sometimes the bottom frames are inside Python's own library, with paths like ...\Lib\json\decoder.py. Read upward until you reach the first frame in one of your files. That's the line of yours that passed something bad in.

Finding a bug

Here's a program with a bug that doesn't crash. It's meant to print the best score, 12, and it prints 9:

def parse_scores(text):
    scores = []
    for line in text.splitlines():
        name, score = line.split(",")
        scores.append(score)
    return scores

def best(text):
    scores = parse_scores(text)
    return max(scores)

print(best("ann,7\nbob,12\ncat,9"))

The simplest tool is print, used well. Print the inputs and outputs of the function you suspect, not "got here". Write {name=} inside an f-string to print a variable's name next to its value, with quotes around strings:

>>> scores = parse_scores("ann,7\nbob,12\ncat,9")
>>> print(f"{scores=}")
scores=['7', '12', '9']

The quotes give it away: the scores are strings, and strings compare letter by letter, so '9' beats '12' because 9 comes after 1. The fix is scores.append(int(score)).

In a bigger program, you don't know which function to suspect. Then bisect: print the data at a point roughly halfway through. If it's already wrong there, the bug is in the first half, and otherwise it's in the second half. Then split that half again. Each print halves the code you have to read, so even a big program takes only a handful of steps.

The other tool is a debugger, which pauses your program and lets you look around. Put breakpoint() on a line of its own, here as the first line of best, and run the program. It stops there and shows a (Pdb) prompt (pdb is Python's debugger). Here's a session. After each (Pdb) is what was typed:

Testing your code

An assert statement checks that something is true. If it is, nothing happens. If it isn't, it raises AssertionError, with the message after the comma if you gave one. Here's a first try at counting words, and two asserts that check it:

>>> def count_words(text):
...     return len(text.split(" "))
...
>>> assert count_words("the cat sat") == 3
>>> assert count_words("") == 0, f"got {count_words('')}"
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
AssertionError: got 1

"".split(" ") is [''], a list holding one empty string, so the empty text counts as one word. split() with no argument splits on any run of spaces and ignores spaces at the ends, and "".split() is []. That's what words.py uses.

A test is a function that calls your code and asserts on what comes back. Collect them in their own file, test_words.py, next to words.py:

from words import count_words

def test_simple():
    assert count_words("the cat sat") == 3

def test_empty():
    assert count_words("") == 0

def test_extra_spaces():
    assert count_words("  two   words ") == 2

for name, f in list(globals().items()):
    if name.startswith("test_"):
        f()
        print("ok", name)
$ python test_words.py
ok test_simple
ok test_empty
ok test_extra_spaces

The loop at the bottom uses an idea from lesson P.5: functions are values. globals() is a dict of every name defined in the file, so the loop finds each function whose name starts with test_ and calls it. If an assert fails, the program stops with a traceback that points at the failing line. Run the tests after every change. When they pass, you know the old behavior still works.

Which inputs should a test try? The ones where bugs hide, called edge cases. Most bugs live at the edges of what a function accepts, not in the middle:

input is atrybugs it catches
list or stringempty, one item, all items the samemax([]) crashing, dividing by len of nothing, an off-by-one
numberzero, one, negativedividing by zero, a loop that never runs, % and // on negatives
numberhuge, like 2**64going through a float, which loses digits past about 2**53
textspaces only, a missing separator, characters like ésplit surprises, a forgotten encoding="utf-8"

Write the test for an edge case before you fix it, and watch it fail. Then you know the test can catch the bug, and that your fix is what made it pass. The course's own tests work this way, in bulk: a folder of small programs, each with the answer it should give, run against your compiler after every change.

What you can do now

  • Split a program into modules, import between them, and use if __name__ == "__main__":.
  • Read and write text files with with open(..., encoding="utf-8"), and split them with splitlines().
  • Raise exceptions, catch the specific one you expect, and define your own exception class.
  • Read sys.argv, and report success or failure with an exit code.
  • Read a traceback bottom up and then top down.
  • Find a bug with good prints, bisecting, or breakpoint() and pdb.
  • Write small tests with assert, and pick edge cases for them.

You test average(xs), which returns sum(xs) / len(xs), on [2, 4], [1, 2, 3] and [10]. All pass. Which edge case is still untested and would crash?

What's len([])?

An empty list has length 0, so average([]) raises ZeroDivisionError. Negative and long lists work fine. "Empty" is the first edge case to try for any list.
