Files, errors and testing

So far your code has run in boxes on these pages. Your compiler will run on your own computer. It reads a program from a file, refuses a bad one without crashing, and gets checked by a test runner. This lesson covers the skills between "I can write a function" and "I can run a program on my computer and know whether it works".

Goal

Read a file, handle bad input without a crash, report the result with an exit code, and check your own code with a small test.

Read a file's text

Your compiler's input is a file of text. So the first skill is getting the text of a file into a Python value. This part is on your machine.

  1. Make a text file. In VS Code, in your learn-python folder, save a file named shopping.txt with three lines: milk, eggs and bread. Press Enter after bread.
  2. Write the program. Save this next to it as read.py:

Guess before you run it. What kind of value does f.read() put in text?

The name is read, not read_lines. It hands back everything in one piece.

One string. The end of each line is stored in it as a newline character, written \n in code. repr shows a string the way you would type it, so you can see them.

Most programs want the lines one by one. text.splitlines() gives the list ['milk', 'eggs', 'bread']. The look-alike text.split("\n"), which cuts at every \n, gives one item too many.

Lines without the stray empty one

Writing a file, missing files and where Python looks (for when a file "isn't there")

To write a text file, open it with "w" and write strings to it:

with open("shopping.txt", "w", encoding="utf-8") as f:
    f.write("milk\neggs\nbread\n")
  • "w" creates the file, or empties it if it already exists. Leave the mode out and you get "r", for reading.
  • f.write(...) returns how many characters it wrote, 16 here. It doesn't add a newline for you, so the string has its own \ns.
  • Without encoding="utf-8", Python uses your computer's default, which on Windows is often not UTF-8. A file with an é in it can then read back wrong or fail on another machine.
  • with closes the file even if an error happens inside the block. A file that isn't closed may not have all its text saved yet.

"a\nb\n".split("\n") is ['a', 'b', ''], because split sees the final \n as the start of one more, empty, line. Text files almost always end with a newline, so splitlines() is the one you want. It also handles Windows line endings (\r\n). With split("\n"), every line would keep a \r at its end.

A plain file name like "shopping.txt" is looked up in the current directory: the folder your terminal was in when you started Python, which isn't always the folder the program is in. If a file you can see "isn't there", check where you ran the program from with pwd.

When Python cannot do what a line asks, it raises an exception: a value that says what went wrong. If nothing deals with it, the program stops right there and Python prints a traceback, as in P.1. Its last line gives the kind of problem, FileNotFoundError, and then the details.

A crash is the right result for a bug in your code, because it points at the line. A missing file or a mistyped number is different. That is bad input, and a good program says so in its own words. The next part shows how.

Catch the problem and say so

int("42") turns text into the number 42. int("seven") raises a ValueError. To handle an exception yourself, put the risky lines in a try block and say what to do in an except block:

def to_number(s):
    try:
        n = int(s)
        print("converted")
    except ValueError:
        print("not a number")
        return None
    return n
  1. Try. Python runs the lines under try.
  2. Jump. If one of them raises a ValueError, Python skips the rest of the try block and jumps to the lines under except ValueError:.
  3. Carry on. If nothing was raised, the except block is skipped. Either way the program keeps going.

You call to_number("seven"). The line n = int(s) raises ValueError. Which line runs next?

The rest of the try block is skipped. Where does Python jump to?

Python jumps straight into the except ValueError: block. It prints not a number and returns None. print("converted") and return n never run for this call.

Division that doesn't crash

Write safe_div(a, b): a / b, or None when b is zero. Use try and except. Any other problem, like dividing a string, must still raise its error.

Which exception does 1 / 0 raise? Catch that one, by name, and nothing else.

A bare except hides your bugs

You can write except: with no name, and it catches everything. That includes the NameError from a misspelled variable, so a typo quietly turns into None and nothing tells you why. Name the one exception you expect, and let the rest be loud.

Raise an error yourself

Your own functions can refuse bad input the same way Python does, with the raise you met in P.4:

def check_age(age):
    if age < 0:
        raise ValueError(f"age cannot be negative: {age}")
    return age

print(check_age(12))
print(check_age(-3))
print("done")

What does this program print?

The first call is fine. Nothing in this program catches the error from the second call.

The first call returns 12. The second reaches raise, which leaves the function at once. No try catches the error, so the program stops and done never prints.

The caller decides what happens next: catch the error with try, or let it stop the program. Put the bad value in the message. "age cannot be negative: -3" helps far more than "bad age".

Refuse a bad withdrawal

withdraw(balance, amount) returns what is left after taking amount out. Right now it lets you take more than there is. When amount is larger than balance, raise ValueError with the message cannot take 30 from 10, using the real numbers.

Parse key=value lines

Write parse_pairs(text), which turns lines like name = Ann into a dict of strings, {'name': 'Ann'}. Remove spaces around each key and each value. Skip blank lines. A value may contain =: x=1=2 gives {'x': '1=2'}. A non-blank line with no =, or with nothing before the =, is an error: raise ValueError(f"bad line {n}: {line!r}"), where n counts lines from 1, blank ones included.

line.partition("=") splits at the first = only, and returns three strings: before, the = itself (or "" if there was none), and after. enumerate(lines, 1) counts from 1. s.strip() removes the spaces from both ends of s. {line!r} puts the line in quotes, as repr does.

Give your error its own name

There is a catch with except ValueError:. Python raises ValueError for its own reasons too, so you may catch an error that came from a real bug. The fix is an exception class of your own. It is a class that names Exception in parentheses. pass means the class has nothing else in it.

class ParseError(Exception):
    pass

def parse_age(s):
    if not s.isdigit():
        raise ParseError(f"not an age: {s!r}")
    return int(s)

try:
    print(parse_age("12"))
    print(parse_age("ten"))
    print("after")
except ParseError as err:
    print("bad input:", err)
print("still running")

s.isdigit() is true when every character of s is a digit, and not flips true and false. as err names the caught exception, so you can print its message.

How many lines does this program print?

Follow the jump. Which line of the try block gets skipped, and what comes after the except block?

parse_age("ten") raises, so print("after") is skipped. The except block prints the message. Then the program carries on to the last line. It did not crash.

This is the pattern your compiler uses in week 1. It raises its own exception when the program it reads is not valid, catches that one class in one place, and prints REJECTED. Every other exception is a bug in the compiler, and it stays loud.

Arguments in, exit code out

A program run from a terminal talks to the outside in two more ways. The words you type after its name are its arguments. Python puts them in the list sys.argv. When the program ends, it hands back one whole number, its exit code. 0 means "it worked". Anything else means "it failed".

A grader is a program that runs your program and checks the result. It cannot look at the screen and judge. It reads what your program printed and, often, its exit code. On your machine, save this as count.py:

import sys

def main(argv):
    if len(argv) != 1:
        print("usage: python count.py FILE", file=sys.stderr)
        return 2
    try:
        with open(argv[0], encoding="utf-8") as f:
            text = f.read()
    except FileNotFoundError:
        print(f"count.py: no such file: {argv[0]}", file=sys.stderr)
        return 1
    print(len(text.splitlines()), "lines")
    return 0

if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))
  1. Get the tools. import sys brings in sys, a set of tools that comes with Python.
  2. Do the work in main. It gets the arguments and returns the exit code. sys.argv[0] is the program's own name, so sys.argv[1:] is the arguments alone.
  3. Report problems apart from answers. file=sys.stderr sends a message to stderr, a second output meant for errors. It still shows in your terminal, but a grader reading the answer does not mix the two up.
  4. Hand back the code. sys.exit(n) ends the program with exit code n. The if above it is true only when you run this file itself. If another file imports count.py, say to test main, __name__ is "count" there and the program does not start.

Now run it three ways. After each run, ask the terminal for the exit code: echo $LASTEXITCODE in PowerShell, echo $? on macOS and Linux.

You type python count.py a.txt b.txt. What is the exit code?

How long is argv inside main? Check the first if.

argv has two items, so len(argv) != 1 is true. main prints the usage line and returns 2. By habit, 2 means "you called me wrong".

A program that stops with an uncaught exception, like crash.py, prints its traceback to stderr and exits with code 1. So to a grader a crash is always a failure, even when refusing the input was the right answer.

An adder that never crashes

Write main(argv) for a tiny command add A B. argv is the arguments without the program name. If there are exactly two and both are whole numbers, print their sum and return 0. Otherwise print a short message to sys.stderr and return 2. It must never raise.

Check len(argv) first. Then int() raises ValueError on something like "x", which you can catch. The tests check what main returns.

Splitting a program across files: modules and import (lesson 0.7 builds on this)

Lesson 0.7 sets your compiler up as a folder of files that the grader can run. Here is the idea underneath it. Each .py file is a module, and one module can use the functions of another by importing it. Make a folder with two files. The first, words.py, holds some tools for working with text:

def count_words(text):
    return len(text.split())

def longest_word(text):
    return max(text.split(), key=len)

if __name__ == "__main__":
    print(count_words("the cat sat on the mat"))

The second, main.py, uses them:

from words import count_words, longest_word

text = "a rose is a rose is a rose"
print(count_words(text), "words")
print("longest:", longest_word(text))
$ python main.py
8 words
longest: rose

($ stands for your terminal's prompt. Type what follows it, and the lines after are what the program prints.)

from words import count_words, longest_word tells Python: find words.py, run it, and bring those two names into this file. Python looks for it in the folder of the program you ran, which is why both files go in one folder. There's a second way to write it:

import words

print(words.count_words("a rose is a rose"))

import words brings in the whole module under one name, and you reach inside it with a dot. Both are fine. The dotted form makes it obvious where a name came from, which helps once you have many modules. The modules that come with Python, like sys, math and dataclasses, are imported the same way.

Now the last two lines of words.py. Every module has a variable called __name__. When you run a file directly, as in python words.py, Python sets it to "__main__". When the file is imported, it's set to the module's name, "words". So the code under if __name__ == "__main__": only runs when you run the file itself:

$ python words.py
6

When main.py imports words, the 6 isn't printed. Without the if, it would be, every time anything imported the module. Use this to keep a quick check, or a module's command-line entry point, in the same file as its functions.

Don't name a file after a module you use

Call your own file random.py, and import random anywhere in that folder finds your file instead of Python's. The errors that follow are baffling, like AttributeError: module 'random' has no attribute 'randint'. Pick names that aren't already taken.

Exit codes in other shells, and what the course's grader reads

In the old Windows cmd window, the exit code is echo %ERRORLEVEL%. In bash and zsh, the usual shells on Linux and macOS, it is echo $?.

Notice the shape of count.py. All the work happens in main(argv), which returns the exit code, and only the last line calls sys.exit. You can call main(["shopping.txt"]) from a test or the REPL and check what it returns, without the program ending under you.

The course's grader runs your compiler on each test program and reads the one line it prints, such as MATCH case.uir or REJECTED case.uir. A crash prints a traceback instead of that line, so it fails the test, even one where the right answer was REJECTED. Lesson 0.7 gives the exact rules.

Write a test by hand

How do you know a function works? Here is a word counter. text.split(" ") cuts a string at each space and returns the list of pieces.

def count_words(text):
    return len(text.split(" "))

You try count_words("the cat sat") and get 3. It looks right.

Take a guess. What does count_words("") return for the empty string?

It should be 0. It isn't.

"".split(" ") is [''], a list that holds one empty string.

1. Cutting an empty string at spaces leaves one empty piece, and len counts it as a word. You could not see that by reading the code, and one lucky check did not show it.

A test is a check you write down so you can run it again and again. It has two moves:

  1. Call the function on an input you chose.
  2. Compare the result with the answer you worked out by hand.

Try the awkward inputs first: the empty one, a single item, extra spaces. Bugs live there. The fix here is text.split() with no argument, which cuts at any run of spaces and gives [] for an empty string.

Count the failing cases

failures(f, cases) tests the function f. Each case is a pair: an input, and the answer you expect. It should return how many cases fail. The loop is written. Finish its body: call f on the input, compare with the expected answer and count each one that differs.

Python has a short way to write "compare, and stop loudly if it is wrong". assert does nothing when the check after it is true, and raises AssertionError when it is false. On your machine, save the two-line count_words above as words.py, bug and all. Save this next to it as test_words.py:

from words import count_words

assert count_words("the cat sat") == 3
assert count_words("") == 0
assert count_words("  two   words ") == 2
print("all tests passed")

The first line fetches count_words from words.py. Run python test_words.py. You should see a traceback that points at line 4 and ends with AssertionError. Now change split(" ") to split() in words.py and run the test again. You should see all tests passed. Run your tests after every change, so you know the old behavior still works.

Which inputs to test, and a test file that finds its own tests

An assert can carry a message after a comma, shown when it fails: assert count_words("") == 0, f"got {count_words('')}" ends with AssertionError: got 1.

The inputs where bugs hide are called edge cases. Most bugs live at the edges of what a function accepts, not in the middle:

Write the test for an edge case before you fix it, and watch it fail. Then you know the test can catch the bug, and that your fix is what made it pass. The course's own tests work this way, in bulk: a folder of small programs, each with the answer it should give, run against your compiler after every change.

Once you have many tests, give each one a name by making it a function, and let the file call them all:

from words import count_words

def test_simple():
    assert count_words("the cat sat") == 3

def test_empty():
    assert count_words("") == 0

def test_extra_spaces():
    assert count_words("  two   words ") == 2

for name, f in list(globals().items()):
    if name.startswith("test_"):
        f()
        print("ok", name)
$ python test_words.py
ok test_simple
ok test_empty
ok test_extra_spaces

The loop at the bottom uses an idea from P.5: functions are values. globals() is a dict of every name defined in the file, so the loop finds each function whose name starts with test_ and calls it. If an assert fails, the program stops with a traceback that points at the failing line.

Read a long traceback

When a test fails or a program crashes, the traceback is your first clue. Real errors happen several calls deep. This report adds up scores, and one line of its data is bad:

def parse_score(line):
    name, score = line.split(",")
    return int(score)

def total(lines):
    result = 0
    for line in lines:
        result += parse_score(line)
    return result

def main():
    lines = ["ann,7", "bob,12", "cat,nine"]
    print(total(lines))

main()

A traceback is the call stack from P.5, printed at the moment of the error. Each File ... line ... in ... entry is one waiting call, with the line it was running under it. The newest call is at the bottom. Read it in two passes:

  1. Bottom up, for what and where. The last line is the error: int was given 'nine'. The entry right above it is where it happened.
  2. Top down, for how you got there. main called total, which called parse_score. The bad value 'nine' came from the list in main, so that is what to fix.

Which line number of report.py was running when the error happened?

Find the last File entry, right above the ValueError line.

Line 3, return int(score), inside parse_score. The ^^^^ marks show which part of the line was running. Newer versions of Python may draw them a little differently.

Frames you didn't write

Sometimes the bottom entries are inside Python's own files, with paths like ...\Lib\json\decoder.py. Read upward until you reach the first entry in one of your files. That's the line of yours that passed something bad in.

Step through a program to find a bug

Some bugs do not crash. This program is meant to print the best score. max returns the largest item of a list.

def parse_scores(text):
    scores = []
    for line in text.splitlines():
        name, score = line.split(",")
        scores.append(score)
    return scores

def best(text):
    scores = parse_scores(text)
    return max(scores)

print(best("ann,7\nbob,12\ncat,9"))

The best score is 12. What does the program print?

Look at what append adds to the list. Is score a number, or a piece of text?

It prints 9. split returns strings, so the list is ['7', '12', '9']. Strings compare character by character, and '9' comes after '1'. The fix is scores.append(int(score)).

You found that by reading. When reading is not enough, look at the values while the program runs. There are two calm ways to do it.

Print the value you suspect. Add print(f"{scores=}") before the return in best. It prints scores=['7', '12', '9']: the name, then the value. The quotes give the bug away.

Pause the program and look around. On your machine, save the program as grades.py and add a line breakpoint() as the first line of best. Run python grades.py. It stops and waits at a (Pdb) prompt. Pdb is Python's debugger, a tool that runs a program one line at a time. Type three commands, pressing Enter after each:

-> scores = parse_scores(text)
(Pdb) n
-> return max(scores)
(Pdb) p scores
['7', '12', '9']
(Pdb) c
9

The line after -> is the one about to run. n (next) runs it. p scores prints a value. c (continue) lets the program finish. You will also see a line with the file name before each ->. On Python 3.13 and newer the first stop is on the breakpoint() line itself, so type n one more time. Delete the breakpoint() line when you are done.

Then bisect: print the data at a point roughly halfway through. If it's already wrong there, the bug is in the first half, and otherwise it's in the second half. Then split that half again. Each print halves the code you have to read, so even a big program takes only a handful of steps.

What you can do now

  • Read a text file with with open(..., encoding="utf-8"), and split it with splitlines().
