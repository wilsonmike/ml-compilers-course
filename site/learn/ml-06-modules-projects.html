Modules, maps and projects

The last step from snippets in utop to a real program. You'll group code into modules, use OCaml's maps and sets, set up a project with dune, read a file, and find out what went wrong when your program crashes.

A module groups names

You've been writing String.length since lesson O.1 and List.map since lesson O.3. The part before the dot is a module: a named group of types and functions that belong together. List holds everything about lists, String everything about strings, Hashtbl everything about hash tables.

# String.length "hello";;
- : int = 5
# String.uppercase_ascii "loud";;
- : string = "LOUD"
# List.map;;
- : ('a -> 'b) -> 'a list -> 'b list = <fun>

Why bother? Because both lists and arrays need a map, and both strings and lists need a length. Modules let each one keep the short, obvious name without the names colliding: List.length and String.length are two different functions. When you want to know what a module offers, look up its page in the OCaml manual, or type the module name and a dot in your editor and read the list it suggests.

Writing your own module

You make a module with module Name = struct ... end. Everything between struct and end is ordinary OCaml. Here is a stack, a pile where you only add to the top ("push") and take from the top ("pop"), like a stack of plates:

# module Stack = struct
    type t = int list
    let empty = []
    let push x s = x :: s
    let pop s = match s with [] -> None | x :: rest -> Some (x, rest)
  end;;
module Stack :
  sig
    type t = int list
    val empty : 'a list
    val push : 'a -> 'a list -> 'a list
    val pop : 'a list -> ('a * 'a list) option
  end
# let s = Stack.push 2 (Stack.push 1 Stack.empty);;
val s : int list = [2; 1]
# Stack.pop s;;
- : (int * int list) option = Some (2, [1])

Outside the module, you reach its names with a dot, exactly like List.map. utop answers with the module's signature: the list of everything inside it and the type of each. pop returns an option because an empty stack has nothing to pop. When there is a top, it returns the top and the rest of the stack as a pair.

A stack never changes here. push returns a new, taller stack, the same no-change style as { r with ... } in lesson O.4. OCaml's library has its own Stack module, a mutable one. Defining yours with the same name hides that one for the rest of the session, which is fine for practice.

Add peek to the Stack module

Inside the starter's Stack module, finish peek : t -> int option. It returns the top element without removing it, or None for an empty stack. The tests call it from outside as Stack.peek.

Inside the module, a stack is a plain list. Where is the top of the list?

Every file is a module, and an interface hides the details

In a project you don't usually write module ... = struct. Instead, each .ml file is a module on its own, named after the file with a capital first letter. Put the four lines from inside the struct into a file called stack.ml, and the rest of the program can call Stack.push.

Next to stack.ml you can put a file stack.mli, an interface. It lists what other files are allowed to see. Anything not listed is private to the module.

type t
val empty : t
val push : int -> t -> t
val pop : t -> (int * t) option

The first line says there is a type t but doesn't say what it is. A type like that is called abstract. Code outside the module can hold stacks and pass them to Stack's functions, but it can't see that a stack is a list. You can try the same idea in utop by writing the interface between sig and end:

# module Stack : sig
    type t
    val empty : t
    val push : int -> t -> t
    val pop : t -> (int * t) option
  end = struct
    type t = int list
    let empty = []
    let push x s = x :: s
    let pop s = match s with [] -> None | x :: rest -> Some (x, rest)
  end;;
module Stack :
  sig
    type t
    val empty : t
    val push : int -> t -> t
    val pop : t -> (int * t) option
  end
# let s = Stack.push 2 (Stack.push 1 Stack.empty);;
val s : Stack.t = <abstr>
# List.length s;;
Line 1, characters 12-13:
1 | List.length s;;
                ^
Error: This expression has type "Stack.t"
       but an expression was expected of type "'a list"

Now s prints as <abstr>, and treating it as a list is an error. Why want that? Because it means you can change how a stack works inside, say to an array, and no other file can break, since no other file was allowed to depend on the list. It is the same reason Hashtbl.t and Buffer.t print as <abstr>. For your first projects, interfaces are optional. Skip them until a module gets big enough that you want to separate what it offers from how it works.

Maps and sets: modules made by a functor

In lesson O.5 you used Hashtbl to look things up by key. OCaml has a second tool for that, the map, which never changes, like a list or a record. To get one, you write a line that looks odd at first:

module StringMap = Map.Make (String)

Map.Make is a functor: a module that builds a module from another module. A map keeps its keys in sorted order, so it needs to know how to compare two keys. The String module has a compare function for strings. Map.Make (String) takes it and builds a whole new module, which you name StringMap, full of map functions for string keys. Want ints as keys? Map.Make (Int). The pattern is always the same, so you can treat that line as a recipe.

If you type it into utop, it prints the new module's signature, about fifty lines long. It starts like this:

module StringMap :
  sig
    type key = String.t
    type 'a t = 'a Map.Make(String).t
    val empty : 'a t
    val add : key -> 'a -> 'a t -> 'a t

'a t is a map whose values have type 'a, so int StringMap.t is a map from strings to ints. Here are the functions you'll use most:

# let m0 = StringMap.empty;;
val m0 : 'a StringMap.t = <abstr>
# let m1 = StringMap.add "kiwi" 3 m0;;
val m1 : int StringMap.t = <abstr>
# let m2 = StringMap.add "pear" 5 m1;;
val m2 : int StringMap.t = <abstr>
# StringMap.find_opt "kiwi" m2;;
- : int option = Some 3
# StringMap.bindings m2;;
- : (StringMap.key * int) list = [("kiwi", 3); ("pear", 5)]
# StringMap.fold (fun word n acc -> acc + n) m2 0;;
- : int = 8

find_opt looks up a key and returns an option, like Hashtbl.find_opt. bindings lists every key and value, already in sorted key order. fold visits every pair, in key order, and builds up a result. Here it adds up all the values: 3 + 5 = 8.

add returns a new map

This is the big difference from Hashtbl. StringMap.add "pear" 5 m1 does not change m1. It returns a new map with one more key, and m1 is still the map it was:

# StringMap.cardinal m1;;
- : int = 1
# StringMap.cardinal m2;;
- : int = 2
# StringMap.find_opt "kiwi" m0;;
- : 'a option = None
# let m3 = StringMap.add "kiwi" 4 m2;;
val m3 : int StringMap.t = <abstr>
# StringMap.bindings m3;;
- : (StringMap.key * int) list = [("kiwi", 4); ("pear", 5)]
# StringMap.bindings m2;;
- : (StringMap.key * int) list = [("kiwi", 3); ("pear", 5)]

cardinal is the number of keys. Adding an existing key, as in m3, replaces its value in the new map only. This doesn't mean every add copies the whole map. Inside, the new map reuses almost all of the old one, so add stays fast even for big maps.

Throwing away the new map

Coming from Hashtbl, it's natural to write List.iter (fun w -> ignore (StringMap.add w 1 m)) words. ignore throws away the value it is given. So this builds a new map for each word and throws it away, and m stays empty. With a map you have to keep the result. The usual way is List.fold_left with the map as the accumulator: each step receives the map so far and returns the next one.

Word counts in a StringMap

Write count_words : string list -> int StringMap.t, a map from each word to how many times it appears. The starter has the throw-away bug from the box above. The tests print StringMap.bindings of your map.

List.fold_left, starting from StringMap.empty. Each step looks up the old count with find_opt and returns StringMap.add w (n + 1) m.

Sets

A set is a collection where each element appears once, and order doesn't matter on the way in. Set.Make is the same kind of functor. utop prints its long signature again, which is left out here:

# module StringSet = Set.Make (String);;
# let s = StringSet.of_list ["b"; "a"; "b"; "c"];;
val s : StringSet.t = <abstr>
# StringSet.elements s;;
- : StringSet.elt list = ["a"; "b"; "c"]
# StringSet.cardinal s;;
- : int = 3
# StringSet.mem "a" s;;
- : bool = true

of_list builds a set from a list, dropping duplicates. elements gives them back as a sorted list. mem asks whether something is in the set. Like maps, sets never change: StringSet.add returns a new set.

The distinct words, in order

Write unique_words : string list -> string list, which returns each distinct word once, in sorted order. unique_words ["b"; "a"; "b"] is ["a"; "b"].

Map or Hashtbl?

Both look things up by key. They differ in whether they change, and that decides which one fits.

A dune project from scratch

utop is great for trying things, but a program you run again and again lives in files, and dune, OCaml's build tool, turns those files into a program. Lesson 0.6 creates a project with one command, dune init project. Here you'll write the same kind of project by hand, three small files, so that you know what each one is for.

counter/
  dune-project
  bin/
    dune
    main.ml

dune-project marks the top folder of the project. It holds one line, which says which version of dune's rules the project is written for:

(lang dune 3.0)

bin/dune says what to build in the bin folder: one program, made from main.ml.

(executable
 (name main))

bin/main.ml is the program itself. This one prints how many characters a file has:

let () =
  if Array.length Sys.argv <> 2 then begin
    Printf.eprintf "usage: main FILE\n";
    exit 1
  end;
  let path = Sys.argv.(1) in
  let text = In_channel.with_open_text path In_channel.input_all in
  Printf.printf "%s has %d characters\n" path (String.length text);
  exit 0

Line by line:

  • let () = ... is the code that runs when the program starts. () is the unit value from lesson O.1, so this says "run this, and it returns nothing".
  • Sys.argv is an array of the words typed on the command line. Sys.argv.(0) is the program's own name, and Sys.argv.(1) is the first word after it. Checking the length first means you never read past the end of the array.
  • begin ... end groups steps, like parentheses. Without it, only the first step would belong to the if.
  • In_channel.with_open_text path f opens the file, calls f on it, and closes it again, even if f fails. In_channel.input_all reads everything into one string. Both need OCaml 4.14 or newer.
  • exit 0 ends the program with exit code 0, which means success. Any other number means failure. Other programs, such as the course's test runner, read this number to find out how things went.

First make a file called notes.txt in the counter folder and type a line of text into it. Then build the project and run it from the counter folder. The number you see is the length of your own file, so it may not be 20. dune build prints nothing when everything compiles. Everything after -- is passed to your program instead of to dune.

$ dune build
$ dune exec ./bin/main.exe -- notes.txt
notes.txt has 20 characters
$ echo $?
0
$ dune exec ./bin/main.exe
usage: main FILE
$ echo $?
1
$ dune exec ./bin/main.exe -- nope.txt
Fatal error: exception Sys_error("nope.txt: No such file or directory")
$ echo $?
2

echo $? shows the exit code of the last command in a Unix shell. In PowerShell, use echo $LASTEXITCODE. The finished program also sits at _build/default/bin/main.exe, and you can run that file directly.

The last run shows what happens to an exception nobody catches: the program prints Fatal error: exception and the exception, and exits with code 2. Two things go to stderr, the error stream, which is separate from normal output: the Fatal error message, and the usage line, because it was printed with Printf.eprintf. If you send normal output to a file with >, those messages still appear on screen.

Build and run from the project folder

dune looks for dune-project in the current folder and the folders above it. Run it from counter/bin and it finds the project, but ./bin/main.exe now points at the wrong place: Error: Program './bin/main.exe' not found!. Run it from a folder outside any project and you get Error: I cannot find the root of the current workspace/project. Either way, go to the folder that holds dune-project. And keep the ./ and the .exe in dune exec ./bin/main.exe, on every system: that's dune's name for the program, not a Windows file name.

When something goes wrong

Print to stderr

The oldest debugging tool is a print. Use Printf.eprintf, which works like printf but writes to stderr. That keeps your debug lines out of the program's real output, which a test may be checking. Add %! at the end of the format to make sure the line appears right away, even if the program crashes on the next line:

Printf.eprintf "looking up %s\n%!" fruit

Ask for a backtrace

Here's a program with a bug. List.assoc k l finds the value for key k in a list of pairs, and raises Not_found if it isn't there. There is no price for "plum":

let prices = [ ("kiwi", 3); ("pear", 5) ]

let price_of fruit = List.assoc fruit prices

let total basket = List.fold_left (fun acc fruit -> acc + price_of fruit) 0 basket

let () = Printf.printf "%d\n" (total [ "kiwi"; "plum" ])
$ dune exec ./bin/main.exe
Fatal error: exception Not_found

That says what went wrong, but not where. In a big program there may be fifty lookups that could raise Not_found. Set the environment variable OCAMLRUNPARAM to b (for backtrace) and run it again:

$ OCAMLRUNPARAM=b dune exec ./bin/main.exe
Fatal error: exception Not_found
Raised at Stdlib__List.assoc in file "list.ml", line 199, characters 10-25
Called from Dune__exe__Main.price_of in file "bin/main.ml" (inlined), line 3, characters 21-44
Called from Dune__exe__Main.total.(fun) in file "bin/main.ml", line 5, characters 58-72
Called from Stdlib__List.fold_left in file "list.ml", line 123, characters 24-34
Called from Dune__exe__Main in file "bin/main.ml", line 7, characters 30-56

A backtrace is the chain of calls that led to the crash, innermost first. Read it from the top and stop at the first line in a file you wrote:

  • The exception was raised inside List.assoc, in OCaml's own list.ml. Library code is rarely the culprit, so keep reading.
  • That was called from price_of, on line 3 of bin/main.ml. This is your code: the lookup that failed. (inlined) means the compiler copied price_of into the function that uses it to save a call. The line number is still right.
  • Further down: price_of was called by the fun inside total on line 5, which was run by List.fold_left, which was started on line 7.

In PowerShell, set the variable once with $env:OCAMLRUNPARAM = "b" and then run the program as usual. dune's normal build keeps the information a backtrace needs, so there's nothing else to switch on. The line numbers inside list.ml may differ with your OCaml version.

Watch a function's calls with #trace

In utop, #trace makes a function report every call and every return. It is a quick way to see a recursive function at work:

# let rec fact n = if n <= 1 then 1 else n * fact (n - 1);;
val fact : int -> int = <fun>
# #trace fact;;
fact is now traced.
# fact 3;;
fact <-- 3
fact <-- 2
fact <-- 1
fact --> 1
fact --> 2
fact --> 6
- : int = 6

<-- is a call going in, with its argument, and --> is a result coming out. The calls nest: fact 3 calls fact 2, which calls fact 1. fact 1 returns first, and then each waiting call finishes in turn, 2 × 1 = 2, then 3 × 2 = 6. Type #untrace fact;; to turn it off. The # at the start is part of the command, which is why the line above shows two: the prompt and the one you type.

What you can do now

  • Explain what a module is, write one with struct ... end, and know that each file is a module.
  • Read a simple .mli interface and say what an abstract type hides.
  • Make a map or set module with Map.Make or Set.Make, and use add, find_opt, bindings and fold, keeping the new map each time.
  • Choose between a map and a hash table.
  • Set up a dune project by hand, read a file, use Sys.argv, and exit with a meaningful code.
  • Debug with Printf.eprintf, a backtrace from OCAMLRUNPARAM=b, and #trace.
