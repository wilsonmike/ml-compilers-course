Modules, maps and projects

You can write a function. This last Learn OCaml lesson covers what sits between that and a real program: keeping functions in named groups, building a program on your own computer, running it and finding out why it is wrong. Your compiler will be a program like that.

Goal

Build a tiny program from three files, run it with an argument and track down a bug in it.

You'll use

List.fold_left and option (O.3), exceptions (O.4), arrays and Hashtbl (O.5).

The quizzes and exercises run in this page. The parts marked On your machine need a terminal and the OCaml tools from O.1.

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

The name before the dot

You have written String.length since O.1 and List.map since O.3. Look closely at the part before the dot.

String.length "hello" is 5 and List.length [1; 2; 3] is 3. What does List.length "hello" give?

Are String.length and List.length one function or two?

A type error. They are two different functions that share the short name length. The one in List takes a list, and "hello" is a string.

The word before the dot is a module: a named box of functions that belong together. List holds the functions for lists, String the ones for strings and Hashtbl the ones for hash tables. A function's full name is the box, a dot, then the short name.

Boxes let lists and strings both have a length, and lists and arrays both a map. The names never clash, and the full name tells you what the function works on.

# List.length "hello";;
Line 1, characters 12-19:
1 | List.length "hello";;
                ^^^^^^^
Error: This expression has type "string" but an expression was expected of type
         "'a list"

To see what a box holds, read the module's page in the OCaml manual.

Make your own module

Your compiler will have dozens of functions. Loose in one pile, they are hard to find. So you make boxes of your own. Here is one for a stack: a pile where you add to the top ("push") and take from the top ("pop"), like a pile of plates.

module Stack = struct
  type t = int list
  let empty = []
  let push x s = x :: s
  let pop s = match s with [] -> None | x :: rest -> Some (x, rest)
end

let s = Stack.push 2 (Stack.push 1 Stack.empty)
  1. Open the box. module Stack = struct starts a module named Stack. A module name starts with a capital letter.
  2. Fill it. Everything up to end is ordinary OCaml. t is the usual name for a module's main type, so Stack.t reads "a stack". Here a stack is a list with the top at the front.
  3. Use it from outside. After end, every name needs the box in front: Stack.push, Stack.empty. s is [2; 1].

Below the module, you type push 3 s with no Stack. in front. What happens?

Where does the name push live?

"Unbound" means OCaml knows no value by that name. push lives inside the box, so outside it the name is Stack.push. When you see this error, check for a missing module name first.

Add peek to the Stack module

Inside the starter's Stack module, finish peek : t -> int option. It returns the top element without removing it, or None for an empty stack. The tests call it from outside as Stack.peek.

Inside the module, a stack is a plain list. Where is the top of the list?

A file is a module

In a real project you rarely write struct. Every .ml file is already a module, named after the file with its first letter made a capital. So a project can look like this:

filewhat is in it
stack.mllet empty = []
let push x s = x :: s
main.mllet s = Stack.push 1 Stack.empty

Nothing in stack.ml says "module". The file name does that job. Any other file in the project reaches its contents as Stack. and a name. This is how your compiler will be laid out: one file for reading text, one for running programs and a main file that names them.

A file named price_list.ml holds let total = .... What does another file in the project call it?

Only the first letter changes.

Price_list.total. The first letter becomes a capital and the rest of the file name stays as it is, underscore included.

The editor in this page holds one file, so its exercises write module ... = struct ... end, which behaves the same way. You'll make a real second file later in this lesson.

Use a module from outside

Below the Stack module, write push_all xs s. It pushes every item of the list xs onto the stack s, first item first, and returns the new stack. push_all [1; 2; 3] Stack.empty is [3; 2; 1].

You are outside the box now. Carry the stack along the list with List.fold_left.

Interface files (.mli) and hidden types, for when a module gets big

Next to stack.ml you can put a file stack.mli, an interface. It lists what other files are allowed to see. Anything not listed is private to the module.

type t
val empty : t
val push : int -> t -> t
val pop : t -> (int * t) option

The first line says there is a type t but doesn't say what it is. A type like that is called abstract. Code outside the module can hold stacks and pass them to Stack's functions, but it can't see that a stack is a list. You can try the same idea in utop by writing the interface between sig and end:

# module Stack : sig
    type t
    val empty : t
    val push : int -> t -> t
    val pop : t -> (int * t) option
  end = struct
    type t = int list
    let empty = []
    let push x s = x :: s
    let pop s = match s with [] -> None | x :: rest -> Some (x, rest)
  end;;
module Stack :
  sig
    type t
    val empty : t
    val push : int -> t -> t
    val pop : t -> (int * t) option
  end
# let s = Stack.push 2 (Stack.push 1 Stack.empty);;
val s : Stack.t = <abstr>
# List.length s;;
Line 1, characters 12-13:
1 | List.length s;;
                ^
Error: This expression has type "Stack.t"
       but an expression was expected of type "'a list"

Now s prints as <abstr>, and treating it as a list is an error. Why want that? Because it means you can change how a stack works inside, say to an array, and no other file can break, since no other file was allowed to depend on the list. It is the same reason Hashtbl.t and Buffer.t print as <abstr>. For your first projects, interfaces are optional. Skip them until a module gets big enough that you want to separate what it offers from how it works.

When you type a module into utop, it answers with the module's signature: the list of everything inside it and the type of each. OCaml's library also has its own Stack module, a mutable one. Defining yours with the same name hides that one for the rest of the session, which is fine for practice.

A table that never changes

In the warm up, Hashtbl.replace wiped out the old value. Sometimes you need the old table too. A compiler, for example, wants to know which names were defined at each line, not only at the end. For that, OCaml has the map: a lookup table that never changes. Adding a key gives you back a new map.

You get a map module with one line. Treat it as a recipe:

module StringMap = Map.Make (String)

Map.Make is a functor: a module that builds a new module from another one. Give it String and it builds a box of map functions for string keys, which you name StringMap. Now use it:

let m0 = StringMap.empty
let m1 = StringMap.add "kiwi" 3 m0
let m2 = StringMap.add "pear" 5 m1

After all three lines have run, how many keys does m1 hold?

Did the third line change m1, or make something new?

1. The third line made a new map, m2, with two keys. m1 is still the map it was, with only "kiwi".

Step through the picture. Then read the same thing in utop, where each reply shows what you got back:

# StringMap.cardinal m1;;
- : int = 1
# StringMap.find_opt "kiwi" m2;;
- : int option = Some 3
# StringMap.find_opt "plum" m2;;
- : int option = None
# let m3 = StringMap.add "kiwi" 4 m2;;
val m3 : int StringMap.t = <abstr>
# StringMap.bindings m3;;
- : (StringMap.key * int) list = [("kiwi", 4); ("pear", 5)]

cardinal counts the keys. find_opt looks a key up and returns an option, like Hashtbl.find_opt. bindings lists every key with its value, sorted by key. Adding a key that is already there, as in m3, gives a new map with the new value. The type int StringMap.t reads "a map from strings to ints".

More about Map.Make: other key types, fold, and why add is not slow

A map keeps its keys in sorted order, so it needs to know how to compare two keys. The String module has a compare function for strings. Map.Make (String) takes it and builds the new module. Want ints as keys? Map.Make (Int). The pattern is always the same.

If you type the recipe into utop, it prints the new module's signature, about fifty lines long. It starts like this:

module StringMap :
  sig
    type key = String.t
    type 'a t = 'a Map.Make(String).t
    val empty : 'a t
    val add : key -> 'a -> 'a t -> 'a t

'a t is a map whose values have type 'a. StringMap.fold visits every pair in key order and builds up a result. This one adds up all the values, 3 + 5 = 8:

# StringMap.fold (fun word n acc -> acc + n) m2 0;;
- : int = 8

A new map for every add doesn't mean every add copies the whole map. Inside, the new map reuses almost all of the old one, so add stays fast even for big maps.

Keep the new map

Since add changes nothing, you must hold on to what it returns. The usual way is List.fold_left with the map as the running answer. This function maps each word to its length:

let lengths words =
  List.fold_left
    (fun m w -> StringMap.add w (String.length w) m)
    StringMap.empty words
  1. Start empty. The fold begins with StringMap.empty.
  2. Take the map so far. Each step receives m, the map built from the words before this one.
  3. Return the next map. The step's answer is StringMap.add ... m, a new map. The fold hands it to the next step.

StringMap.bindings (lengths ["pear"; "fig"]) is [("fig", 3); ("pear", 4)].

Throwing away the new map

Coming from Hashtbl, it's natural to write List.iter (fun w -> ignore (StringMap.add w 1 m)) words. ignore throws away the value it is given. So this builds a new map for each word and throws it away, and m stays empty.

Word counts in a StringMap

Write count_words : string list -> int StringMap.t, a map from each word to how many times it appears. The starter has the throw-away bug from the box above. The tests print StringMap.bindings of your map.

List.fold_left, starting from StringMap.empty. Each step looks up the old count with find_opt and returns StringMap.add w (n + 1) m.

A set holds each thing once

Sometimes you only need to know whether something is in a collection, with no value attached: "have I seen this name before?" That is a set. Each element is in it once, however many times you add it. Set.Make is the same kind of recipe as Map.Make:

# module StringSet = Set.Make (String);;
# let s = StringSet.of_list ["b"; "a"; "b"; "c"];;
val s : StringSet.t = <abstr>
# StringSet.elements s;;
- : StringSet.elt list = ["a"; "b"; "c"]
# StringSet.mem "a" s;;
- : bool = true

of_list builds a set from a list and drops the repeats. elements gives the set back as a sorted list. mem asks whether something is in the set. cardinal counts the elements, as it does for a map.

The set s above has 3 elements. After let s2 = StringSet.add "z" s, what is StringSet.cardinal s?

A set behaves like a map here, not like a hash table.

Still 3. Like a map, a set never changes. add returned a new set, s2, with 4 elements.

The distinct words, in order

Write unique_words : string list -> string list, which returns each distinct word once, in sorted order. unique_words ["b"; "a"; "b"] is ["a"; "b"].

What a build tool does

So far your OCaml lived in the toplevel or in one exercise box. A real program is many files, and some use others, the way main.ml used Stack. Something has to work out which file comes first, check every one and join them into a single program you can run. That something is a build tool. OCaml's is called dune.

dune needs to be told two things: where the project starts and what to build. So the smallest project is three files.

greet/
  dune-project
  bin/
    dune
    main.ml

A project has 40 .ml files. You edit one and run dune build again. What does dune redo?

A build tool keeps track of which file uses which.

dune remembers what it built and which file uses which. It redoes only what your edit could have changed, so rebuilding after a small edit stays quick even in a big project.

Build and run a project

On your machine

This part happens in a terminal, not in this page. Type dune --version. If you see a number, you are ready. If not, the install steps are in lesson 0.6. You can also read on now and do these steps when you get there.

Make this practice project somewhere outside the course folder.

  1. Make the folders. 
    mkdir greet
cd greet
mkdir bin
  2. Mark the top. In greet, make a file named dune-project with one line. It says which version of dune's rules the project uses. 
    (lang dune 3.0)
  3. Say what to build. In bin, make a file named dune. It says: build one program, starting from main.ml. 
    (executable
 (name main))
  4. Write the program. In bin, make main.ml. print_endline prints a string and ends the line. let () = in front means "run this when the program starts". Printing gives back (), the unit value from O.5, so the two sides fit. 
    let () = print_endline "hello from my own program"
  5. Build it and run it. Both commands are typed in greet, the folder that holds dune-project. 
    dune build
dune exec ./bin/main.exe
Checkpoint

dune build prints nothing when everything is fine. dune exec builds if needed, then runs the program, and you should see:

hello from my own program

The finished program is the file _build/default/bin/main.exe. dune uses the ending .exe on every system, not only on Windows.

Suppose you had saved the program as bin/mian.ml by mistake. dune build now fails. Which file does its error point at?

Which file mentions the name main?

bin/dune asks for (name main), and no file gives it a module by that name. The error is Module "Main" doesn't exist, with the file and line of the request. Notice that dune calls the file a module.

If dune can't find the project or the program, or stops on an unused variable

dune looks for dune-project in the current folder and the folders above it. Run it from greet/bin and it finds the project, but ./bin/main.exe now points at the wrong place: Error: Program './bin/main.exe' not found!. Run it from a folder outside any project and you get Error: I cannot find the root of the current workspace/project. Either way, go to the folder that holds dune-project. And keep the ./ and the .exe in dune exec ./bin/main.exe, on every system: that's dune's name for the program, not a Windows file name.

dune is stricter than utop. A name you define with let ... in and never use stops the build with Error (warning 26 [unused-var]): unused variable x. Use the name, delete it or start it with _ to say it is unused on purpose.

A program that reads its arguments

Your compiler will be run as compile FILE, with a different file each time. So a program needs the words typed after its name. They are called arguments, and OCaml puts them in an array of strings named Sys.argv. Slot 0 holds the program's own name. The first argument is in slot 1.

You run a program with one argument, Ada. What is Array.length Sys.argv?

Slot 0 is taken before any argument is counted.

2: the program's name in slot 0 and "Ada" in slot 1. Forgetting slot 0 is the usual mistake.

Read the right argument

greeting argv gets an array shaped like Sys.argv and returns the line to print. With exactly one argument it should return "hello, " and that argument. With any other count it should return "usage: ", the program's name and " NAME". The starter reads the wrong slot and never checks the length. Repair it.

On your machine

Give greet a second file and an argument. Make bin/greeting.ml with this one line:

let make name = "hello, " ^ name

Change bin/main.ml to this:

let () = print_endline (Greeting.make Sys.argv.(1))

Then run it. Everything after -- goes to your program, not to dune.

dune exec ./bin/main.exe -- Ada

You should see hello, Ada. The file greeting.ml became the module Greeting, and dune worked out that it must be built before main.ml.

Exit codes: how a program says how it went

Now you run it with no name: dune exec ./bin/main.exe. What happens?

How long is Sys.argv now, and which slot does the program read?

The array has only slot 0, so reading slot 1 raises an exception. The program prints Fatal error: exception Invalid_argument("index out of bounds") and stops.

When a program ends, it hands one number back to whoever started it. That number is its exit code. 0 means "it went fine". Any other number means "something went wrong". An exception that nobody catches ends an OCaml program with exit code 2.

You can pick the number yourself. Here is bin/main.ml with the missing check:

let () =
  if Array.length Sys.argv = 2 then
    print_endline (Greeting.make Sys.argv.(1))
  else (
    prerr_endline "usage: main NAME";
    exit 1)
  1. Check first. Slot 1 is read only when the array has two slots.
  2. Complain on the error stream. prerr_endline prints a line to stderr, a second output meant for messages to a person. The program's real answer goes to normal output, called stdout.
  3. Leave with a code. exit 1 ends the program with exit code 1. Reaching the end without trouble gives 0.
On your machine

Right after a command, echo $? shows its exit code. In PowerShell, type echo $LASTEXITCODE.

$ dune exec ./bin/main.exe -- Ada
hello, Ada
$ echo $?
0
$ dune exec ./bin/main.exe
usage: main NAME
$ echo $?
1

Why care? The course's grader is a program too. It runs your compiler on hundreds of tests. It reads what your compiler prints on stdout, and for some commands the exit code. A compiler that crashes prints no answer line, so that test fails. Lesson 0.6 connects your program to the grader.

Reading a whole file, for when your program gets a file name

This main.ml prints how many characters a file has:

let () =
  if Array.length Sys.argv <> 2 then begin
    Printf.eprintf "usage: main FILE\n";
    exit 1
  end;
  let path = Sys.argv.(1) in
  let text = In_channel.with_open_text path In_channel.input_all in
  Printf.printf "%s has %d characters\n" path (String.length text);
  exit 0
  • begin ... end groups steps, like parentheses. Without it, only the first step would belong to the if.
  • In_channel.with_open_text path f opens the file, calls f on it, and closes it again, even if f fails. In_channel.input_all reads everything into one string. Both need OCaml 4.14 or newer.
  • Printf.eprintf works like Printf.printf but writes to stderr.

Make a file called notes.txt in the project folder and type a line of text into it. The number you see is the length of your own file, so it may not be 20.

$ dune build
$ dune exec ./bin/main.exe -- notes.txt
notes.txt has 20 characters
$ echo $?
0
$ dune exec ./bin/main.exe
usage: main FILE
$ echo $?
1
$ dune exec ./bin/main.exe -- nope.txt
Fatal error: exception Sys_error("nope.txt: No such file or directory")
$ echo $?

The last run is an exception nobody caught, so the exit code is 2. If you send normal output to a file with >, the messages on stderr still appear on screen.

Find a bug calmly

Every program you write will be wrong at first. That is normal, and there is a routine for it. This program adds up the prices of the fruit in a basket. List.assoc k l finds the value stored with key k in a list of pairs.

let prices = [ ("kiwi", 3); ("pear", 5) ]

let price_of fruit = List.assoc fruit prices

let total basket = List.fold_left (fun acc fruit -> acc + price_of fruit) 0 basket

let () = print_endline (string_of_int (total [ "kiwi"; "pear"; "plum"; "kiwi" ]))
$ dune exec ./bin/main.exe
Fatal error: exception Not_found
  1. Read the error. All of it, slowly. Not_found is the exception a lookup raises when the key is missing. So some lookup failed. The message does not say which.
  2. Print a value. Make the program show what it is working on. Put one line at the start of price_of and run again: 
    let price_of fruit =
  prerr_endline ("looking up " ^ fruit);
  List.assoc fruit prices
  3. Shrink the input. Cut the input down until you have the smallest one that still fails. Here that is total [ "plum" ]. With one item there is nothing else left to suspect.

With the print from step 2 added, which line appears last, right before Fatal error?

The program stops at the first lookup that fails. Which fruit has no price?

The program prints kiwi, pear and plum, then stops. The last value printed before a crash is the one that caused it. There is no price for plum. Printing to stderr keeps these lines apart from the program's real answer.

Read the error, then repair it

average xs should return the whole-number average of a list, and 0 for an empty list. Press Run before you change anything, and read what the failing test says. Then repair the function.

The error names what went wrong. Ask which input is the smallest one that causes it.

A backtrace: ask OCaml where the exception came from

Fatal error: exception Not_found says what went wrong, but not where. In a big program there may be fifty lookups that could raise Not_found. Set the environment variable OCAMLRUNPARAM to b (for backtrace) and run the first version of the fruit program again:

$ OCAMLRUNPARAM=b dune exec ./bin/main.exe
Fatal error: exception Not_found
Raised at Stdlib__List.assoc in file "list.ml", line 199, characters 10-25
Called from Dune__exe__Main.price_of in file "bin/main.ml" (inlined), line 3, characters 21-44
Called from Dune__exe__Main.total.(fun) in file "bin/main.ml", line 5, characters 58-72
Called from Stdlib__List.fold_left in file "list.ml", line 123, characters 24-34
Called from Dune__exe__Main in file "bin/main.ml", line 7, characters 38-80

A backtrace is the chain of calls that led to the crash, innermost first. Read it from the top and stop at the first line in a file you wrote:

  • The exception was raised inside List.assoc, in OCaml's own list.ml. Library code is rarely the culprit, so keep reading.
  • That was called from price_of, on line 3 of bin/main.ml. This is your code: the lookup that failed. (inlined) means the compiler copied price_of into the function that uses it to save a call. The line number is still right.
  • Further down: price_of was called by the fun inside total on line 5, which was run by List.fold_left, which was started on line 7.

In PowerShell, set the variable once with $env:OCAMLRUNPARAM = "b" and then run the program as usual. dune's normal build keeps the information a backtrace needs, so there's nothing else to switch on. The line numbers inside list.ml may differ with your OCaml version.

Printing with Printf.eprintf, and watching a function's calls with #trace

Printf.eprintf works like printf but writes to stderr, so you can print numbers too. Add %! at the end of the format to make sure the line appears right away, even if the program crashes on the next line:

Printf.eprintf "looking up %s\n%!" fruit

In utop, #trace makes a function report every call and every return. It is a quick way to see a recursive function at work:

# let rec fact n = if n <= 1 then 1 else n * fact (n - 1);;
val fact : int -> int = <fun>
# #trace fact;;
fact is now traced.
# fact 3;;
fact <-- 3
fact <-- 2
fact <-- 1
fact --> 1
fact --> 2
fact --> 6
- : int = 6

<-- is a call going in, with its argument, and --> is a result coming out. The calls nest: fact 3 calls fact 2, which calls fact 1. fact 1 returns first, and then each waiting call finishes in turn, 2 × 1 = 2, then 3 × 2 = 6. Type #untrace fact;; to turn it off. The # at the start is part of the command, which is why the line above shows two: the prompt and the one you type.
