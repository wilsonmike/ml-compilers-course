Walking a graph once

A shared graph is small, but a careless walk over it treats it like the huge tree it stands for. This page shows the three tools that keep a walk small (a memo table, a visited set, and a topological order) and what to do when the graph is too deep for recursion.

Before you start

Read H.1 first, for trees, DAGs and identity. You should also be able to read a recursive function: P.5O.3 covers it.

Asking the same question twice

Say you want the value of x3 from H.1, where x0 is 1 and each level adds the level below to itself. The natural code is recursive: the value of a + node is the value of its left child plus the value of its right child. It gives the right answer. The problem is how often it asks.

x3 asks x2 twice, because both of its arrows come from x2. Each of those asks x1 twice. Each of those asks x0 twice. Nobody remembers an answer, so the same question gets asked again and again. Step through the calls and watch the counts next to each node.

Fifteen calls for four nodes. That's the tree size of x3 from H.1, and it's no accident: a walk that never remembers anything visits every path to a node, so it walks the tree. You can count the calls in code. A counter is a variable that the function adds 1 to each time it runs:

calls = 0

def value(e):
    global calls
    calls += 1
    if e[0] == "num":
        return e[1]
    return value(e[1]) + value(e[2])

x = ("num", 1)
for i in range(20):
    x = ("+", x, x)
print(value(x), calls)
type e = Num of int | Add of e * e

let calls = ref 0

let rec value e =
  incr calls;
  match e with
  | Num n -> n
  | Add (a, b) -> value a + value b

let rec chain k = if k = 0 then Num 1 else let s = chain (k - 1) in Add (s, s)

let () =
  let v = value (chain 20) in
  Printf.printf "%d %d\n" v !calls

This prints 1048576 2097151. The answer is 220, and it took 221 − 1 calls for 21 distinct nodes. Every extra level doubles the work. At 60 levels it would never finish.

global for the counter

Without global calls, the line calls += 1 makes Python treat calls as a new local variable, and the first call fails with UnboundLocalError. For a real program, a counter passed in or kept on an object is cleaner. Here it keeps the example short.

Arguments are evaluated right to left

Writing Printf.printf "%d %d\n" (value x) !calls prints 1048576 0. OCaml is allowed to evaluate a function's arguments in any order, and in practice it goes right to left, so !calls is read before value x runs. That's why the code above names the result with let v = ... first.

Memoization: write the answer down

The fix is what you'd do on paper: when you work something out, write the answer in a margin, and before you work anything out, look in the margin first. In code the margin is a table. This is called memoization, and the table is a memo.

The key must be the node's identity, not its contents (H.1 says why: comparing contents walks the tree again). In Python, id(e) is a number unique to each object that is still alive.In OCaml, the course's nodes carry an id number for this. The small example below has no ids, so it keeps an association list and looks up with List.assq, which compares keys with ==.

def value_memo(e, memo):
    key = id(e)
    if key in memo:
        return memo[key]
    if e[0] == "num":
        result = e[1]
    else:
        result = value_memo(e[1], memo) + value_memo(e[2], memo)
    memo[key] = result
    return result
let value_memo e =
  let memo = ref [] in
  let rec go e =
    match List.assq_opt e !memo with
    | Some v -> v
    | None ->
      let v = match e with Num n -> n | Add (a, b) -> go a + go b in
      memo := (e, v) :: !memo;
      v
  in
  go e

One memo per question

Create the memo for one walk and drop it afterward. A memo that lives forever keeps every node alive and can hand back an answer that belonged to a different question. Python reuses the id of an object that has been freed, so a long-lived table keyed by id can even match the wrong node. Keep the nodes alive while the memo is in use.A table at the top level of a module is shared by every call, which is wrong as soon as an answer depends on more than the node. Lesson 1.5 has the course's case of this.

How big would the tree be?

Write tree_size e: how many nodes e would have if it were written out as a tree, with no sharing. That's also the number of calls the naive walk makes. tree_size (chain 3) is 15, and tree_size (chain 60) must finish.

The tree size of a node is 1 plus the tree sizes of its children. Write each node's answer down, keyed by identity, with List.assq_opt.

A visited set: when you only need "seen it"

Sometimes a walk doesn't produce a value per node. It only needs to do something once per node: count it, print it, or add it to a list. Then the memo shrinks to a visited set: a set of the things you have already handled.

An everyday graph: a recipe. A pizza needs dough and sauce. Dough needs flour, water and salt. Sauce needs tomatoes and salt. Salt is shared. Your shopping list should name it once, not once per recipe that uses it.

needs = {
    "pizza": ["dough", "sauce"],
    "dough": ["flour", "water", "salt"],
    "sauce": ["tomatoes", "salt"],
}

def shopping(item, seen):
    for part in needs.get(item, []):
        if part not in seen:
            seen.add(part)
            shopping(part, seen)
    return seen
let needs = [
  ("pizza", ["dough"; "sauce"]);
  ("dough", ["flour"; "water"; "salt"]);
  ("sauce", ["tomatoes"; "salt"]);
]

let parts item = Option.value (List.assoc_opt item needs) ~default:[]

let shopping item =
  let seen = Hashtbl.create 16 in
  let rec go item =
    List.iter
      (fun p -> if not (Hashtbl.mem seen p) then begin Hashtbl.add seen p (); go p end)
      (parts item)
  in
  go item;
  seen

Items that aren't keys of needs, like flour, need nothing, so they are leaves. Here the names are strings, and two equal strings are the same item, so a plain set of names works. For nodes, you'd store ids.

The check comes before the walk goes deeper. When sauce reaches salt, salt is already in seen, so the walk doesn't go into it again. On a recipe that saves one step. On the doubling chain it is the difference between 61 steps and forever.

Children before parents: topological order

Now you want to cook. You can't make the dough before you have the flour, and you can't assemble the pizza before the dough and the sauce exist. You need an order where every item comes after everything it needs. That's a topological order. A compiler needs one every time it turns a graph into lines of code, because a line can only use values computed by earlier lines.

A post-order walk produces one. For each item: first walk each of its parts, left to right, then write the item itself down. Writing it down last is what "post" means. Add a visited set so a shared item is written once. Step through it.

def cooking_order(dish):
    done = set()
    order = []

    def visit(item):
        if item in done:
            return
        done.add(item)
        for part in needs.get(item, []):
            visit(part)
        order.append(item)

    visit(dish)
    return order
let cooking_order dish =
  let done_ = Hashtbl.create 16 in
  let order = ref [] in
  let rec visit item =
    if not (Hashtbl.mem done_ item) then begin
      Hashtbl.add done_ item ();
      List.iter visit (parts item);
      order := item :: !order
    end
  in
  visit dish;
  List.rev !order

For "pizza" this returns flour, water, salt, dough, tomatoes, sauce, pizza. Read it as a cooking plan and every step has what it needs. The list is built backwards with ::, which is cheap, and reversed once at the end. done is a keyword in OCaml, so the table is called done_.

Writing the item down first gives the wrong order

If you write the item down when you enter it (pre-order), pizza comes first, before anything it needs. That order is right for some jobs, like printing a table of contents, but it is backwards for computing. Post-order writes an item on the way out, after all its parts.

When the graph is too deep

Every recursive call waits for the calls it made. While it waits, its local variables sit on the call stack, a region of memory with one frame per unfinished call. A chain of nodes 100,000 long, each using the one below, means 100,000 unfinished calls at the deepest point. The two languages react differently.

Python refuses to go deeper than a fixed limit, 1000 calls by default:

>>> import sys
>>> sys.getrecursionlimit()
1000
>>> def depth(n):
...     return 0 if n == 0 else 1 + depth(n - 1)
...
>>> depth(900)
900
>>> depth(5000)
Traceback (most recent call last):
  ...
RecursionError: maximum recursion depth exceeded

sys.setrecursionlimit(100_000) raises the limit, and a few thousand levels are fine. Much higher, and the real stack underneath can run out, and then the program dies with no Python error message at all. Later weeks' .uir tests run to thousands of lines, so the sturdy fix is the next section.

OCaml 5 grows the stack as it needs to, up to a limit of 1 GB by default. A depth of ten million works in the toplevel:

# let rec depth n = if n = 0 then 0 else 1 + depth (n - 1);;
val depth : int -> int = <fun>
# depth 10_000_000;;
- : int = 10000000

Past the limit, the program raises the exception Stack_overflow, and the toplevel prints Stack overflow during evaluation (looping recursion?). Recursion that never stops ends there too. So in OCaml, recursion is usually fine for the course's graphs. Older OCaml versions (4.14 and before) used a much smaller system stack, so you may see advice that says otherwise. The explicit stack below still matters in OCaml when you want to control the order of work yourself, and it is how you'd write the same walk in C.

Your own stack

A recursive walk keeps its "what to do next" on the call stack. You can keep it in an ordinary list instead, and then the depth is limited only by memory. A list used this way is a stack: you push onto the end and pop from the end, so the last thing pushed is the first thing taken.

The one trick is post-order. When you first meet a node, you can't write it down yet, because its children come first. So you push it back with a note that says "ready: its children are done", and then push its children on top. The children pop first. When the node pops again with its note, you write it down. The example writes an arithmetic tree in postfix, where each operator comes after its two operands: (2 + 3) * 4 becomes 2 3 + 4 *.

def postfix(e):
    out = []
    stack = [(e, False)]
    while stack:
        node, ready = stack.pop()
        if node[0] == "num":
            out.append(str(node[1]))
        elif ready:
            out.append(node[0])
        else:
            stack.append((node, True))
            stack.append((node[2], False))
            stack.append((node[1], False))
    return " ".join(out)
type t = N of int | Op of string * t * t

let postfix e =
  let out = ref [] in
  let stack = ref [ (e, false) ] in
  while !stack <> [] do
    let node, ready = List.hd !stack in
    stack := List.tl !stack;
    match node with
    | N n -> out := string_of_int n :: !out
    | Op (name, _, _) when ready -> out := name :: !out
    | Op (_, a, b) -> stack := (a, false) :: (b, false) :: (node, true) :: !stack
  done;
  String.concat " " (List.rev !out)

The node format is ("num", 2) for a number and ("+", left, right) for an operator. The right child is pushed before the left, so the left one is on top and pops first.The stack is a list whose head is the top. Putting a first means the left child pops first, then the right child, then the node again with ready set. Here is the trace, with the top of the stack on the right and a check mark for "ready":

The same code handles an expression 100,000 levels deep, because the list grows instead of the call stack. For a DAG you add a visited set, exactly as in the recursive version: when a node pops without its note and is already in the set, skip it.

Two common slips

Pushing the children in reading order makes the last child pop first, so the output comes out mirrored. And forgetting the "ready" note makes the loop expand the same node forever, or write it before its children.

A cooking order without recursion

Write topo g root. g is a Hashtbl from an item to the list of items it needs (the starter's graph builds one from a list of pairs). An item that isn't a key needs nothing. Return every item reachable from root, each exactly once, in post-order: an item's parts left to right, then the item. Items not reachable from root are left out.

Use your own stack, not recursion. One test is a chain 100,000 items deep.

A stack of (item, ready) pairs and a table of items you have started. Mark an item when it pops without its note, and skip it if it is already marked.
