Walking a graph once

A program kept as boxes and arrows can be small and still take forever to walk, if the walk goes back inside a box every time an arrow leads there. This page goes slowly through the cure: a notebook of the boxes you have already visited. Your compiler needs it every time it counts, runs or prints a graph.

Goal

Walk a shared graph so that every box is visited exactly once, in an order where each box comes after the boxes it reads.

You'll use

The picture of boxes and arrows from Run your first program, and the run loop and env from Build the thing that runs it.

In OCaml: let rec (O.2), lists and match (O.3) and a ref (O.5).

Warm up

Two questions from the start steps, from memory. Pulling an idea back out of your head is what makes it stay.

Two. The value is used twice, so one box has two arrows going out. A box like that is shared.

Walk it with no notebook

A compiler keeps the boxes, not the lines. To do anything with them it starts at the last box and follows the arrows back to its sources. That is called a walk. The value function of lesson 1.1 is a walk: to get a box's number it asks each source for its number, then applies the op. It keeps no notes. Try it on this program, where each line adds the line above to itself:

%x0 = 1
%x1 = add %x0 %x0
%x2 = add %x1 %x1

Guess first. To get %x2, how many times does the walk visit the box %x0?

%x2 has two arrows coming in, both from %x1. The walk follows each one, and each time %x1 asks %x0 twice.

2 × 2 is 4. With one visit to %x2 and two to %x1, that is 7 visits for 3 boxes.

Now add one more line, %x3 = add %x2 %x2. Press Next and watch the count beside each box. In the pictures + stands for add.

Fifteen visits for four boxes, and eight of them land on x0. The walk follows every path to a box, and a shared graph has many paths to the same box. Each extra line doubles the work. With 60 adds there are 61 boxes and about two billion billion visits, so the walk never finishes.

Count the calls in code, for when you want to watch the doubling on your own machine

A counter is a variable that the function adds 1 to each time it runs:

calls = 0

def value(e):
    global calls
    calls += 1
    if e[0] == "num":
        return e[1]
    return value(e[1]) + value(e[2])

x = ("num", 1)
for i in range(20):
    x = ("+", x, x)
print(value(x), calls)
type e = Num of int | Add of e * e

let calls = ref 0

let rec value e =
  incr calls;
  match e with
  | Num n -> n
  | Add (a, b) -> value a + value b

let rec chain k = if k = 0 then Num 1 else let s = chain (k - 1) in Add (s, s)

let () =
  let v = value (chain 20) in
  Printf.printf "%d %d\n" v !calls

This prints 1048576 2097151. The answer is 220, and it took 221 − 1 calls for 21 distinct nodes.

global for the counter

Without global calls, the line calls += 1 makes Python treat calls as a new local variable, and the first call fails with UnboundLocalError. For a real program, a counter passed in or kept on an object is cleaner. Here it keeps the example short.

Arguments are evaluated right to left

Writing Printf.printf "%d %d\n" (value x) !calls prints 1048576 0. OCaml is allowed to evaluate a function's arguments in any order, and in practice it goes right to left, so !calls is read before value x runs. That's why the code above names the result with let v = ... first.

Add a notebook of boxes you have seen

The cure is what you would do on paper: keep a notebook, and tick off each box as you reach it. Every time the walk arrives at a box it does three things:

  1. Look in the notebook. If the box is there, turn back. Everything under it is already done.
  2. Write the box in.
  3. Go on to its sources.

Programmers call this notebook a visited set, and in code it is often named seen.

Guess first. With the notebook, how many times does the walk on x3 get past step 1 and go inside a box?

A box can be entered only while it is missing from the notebook. How many boxes are there?

Four, once per box. The walk still arrives seven times, once for the start and once for each of the six arrows, but three of those arrivals turn back at step 1.

Each new line now adds two arrivals. It no longer doubles anything. With 60 adds the walk goes inside 61 boxes and stops.

The notebook must record which box, not what the box looks like. Two boxes can look the same and still be two boxes. And comparing looks means reading everything under both boxes, which is the long walk all over again. In Python, id(n) is a number that belongs to one object and no other, so the notebook is a set of ids.In OCaml, == asks "is this the very same object?", and List.memq searches a list with it. H.1 has more on "the same one" and "an equal one".

The same idea on a graph of names: a shopping list

A pizza needs dough and sauce. Dough needs flour, water and salt. Sauce needs tomatoes and salt. Salt is shared. Your shopping list should name it once, not once per recipe that uses it.

needs = {
    "pizza": ["dough", "sauce"],
    "dough": ["flour", "water", "salt"],
    "sauce": ["tomatoes", "salt"],
}

def shopping(item, seen):
    for part in needs.get(item, []):
        if part not in seen:
            seen.add(part)
            shopping(part, seen)
    return seen
let needs = [
  ("pizza", ["dough"; "sauce"]);
  ("dough", ["flour"; "water"; "salt"]);
  ("sauce", ["tomatoes"; "salt"]);
]

let parts item = Option.value (List.assoc_opt item needs) ~default:[]

let shopping item =
  let seen = Hashtbl.create 16 in
  let rec go item =
    List.iter
      (fun p -> if not (Hashtbl.mem seen p) then begin Hashtbl.add seen p (); go p end)
      (parts item)
  in
  go item;
  seen

Items that aren't keys of needs, like flour, need nothing, so they are leaves. Here the names are strings, and two equal strings are the same item, so a plain set of names works. For nodes, you'd store ids.

The check comes before the walk goes deeper. When sauce reaches salt, salt is already in seen, so the walk doesn't go into it again. On a recipe that saves one step. On the doubling chain it is the difference between 61 steps and forever.

Keep the answer in the notebook

Counting boxes only needs "seen it". The value walk needs more. When it turns back from a box it has seen, it still needs that box's number. So next to each box, the notebook keeps the answer. That is what env did for names in your run loop.

A notebook of answers is called a memo, and using one is memoization. The three steps change a little:

  1. Look the box up. If its answer is in the memo, return it. This is a hit.
  2. Work it out. Ask each source, then apply the op.
  3. Write the answer down. Then return it.

Step through it, and watch the memo fill up beside the graph.

Here are the three steps as code, on a toy node type that is either a number or an add of two nodes. Call it with an empty dict: value(e, {}).List.assq_opt looks a node up with ==.

def value(e, memo):
    if id(e) in memo:
        return memo[id(e)]
    match e:
        case Num(n):
            v = n
        case Add(a, b):
            v = value(a, memo) + value(b, memo)
    memo[id(e)] = v
    return v
let value e =
  let memo = ref [] in
  let rec go e =
    match List.assq_opt e !memo with
    | Some v -> v
    | None ->
      let v = match e with Num n -> n | Add (a, b) -> go a + go b in
      memo := (e, v) :: !memo;
      v
  in
  go e

On a chain of 60 adds this works out 61 values and returns 260 at once.

Write a memo yourself

Now the same three steps from a nearly empty function. The question changes, the notebook does not: look the node up, work it out, write it down.

How big would the tree be?

Write tree_size e: how many nodes e would have if it were written out as a tree, with no sharing. That's also the number of calls the naive walk makes. tree_size (chain 3) is 15, and tree_size (chain 60) must finish.

The tree size of a node is 1 plus the tree sizes of its children. Write each node's answer down, keyed by identity, with List.assq_opt.

One memo per question

Create the memo for one walk and drop it afterward. A memo that lives forever keeps every node alive and can hand back an answer that belonged to a different question. Python reuses the id of an object that has been freed, so a long-lived table keyed by id can even match the wrong node. Keep the nodes alive while the memo is in use.A table at the top level of a module is shared by every call, which is wrong as soon as an answer depends on more than the node. Lesson 1.5 has the course's case of this.

Why the order matters

Your run loop went down the lines from top to bottom. That worked for a reason you may not have noticed. Here is a program with its two lines swapped:

%out = mul %a 4
%a   = add 2 3

Guess first. What does your run loop do on the first line?

Line 1 looks a up in env. Which line puts it there?

It fails. Nothing above line 1 made a. In .uir this is a rule: a name must be defined above its first use, so your compiler rejects this file.

So a box can be worked out only after every box it reads. An order like that, with sources before their users, is called a topological order. A correct .uir file is always in one.

But your compiler holds a graph, and a graph has no top or bottom. Whenever it needs lines again it has to find such an order itself. It needs one to run the boxes one at a time, and in week 2 it needs one to print a line of C for each box. The next part shows that a walk hands you this order for free.

A walk gives you the order

Take an everyday graph. A pizza needs dough and sauce. Dough needs flour, water and salt. Sauce needs tomatoes and salt. To cook, you need an order where every item comes after everything it needs.

The walk with a notebook already does it, if you write each item on your list at the right moment: on the way out, after its parts.

  1. Look in the notebook. If the item is there, turn back.
  2. Write it in the notebook.
  3. Visit each part, left to right.
  4. Add the item to the end of the list.

This is called a post-order walk. "Post" means the item is written after its parts.

Guess first. The walk starts at pizza. Which item is the first one added to the list?

An item is added only after all of its parts. Which item is reached first that has no parts?

flour. The walk enters pizza, then dough, then flour, and flour is the first one with nothing left to visit.

The list comes out as flour, water, salt, dough, tomatoes, sauce, pizza. Every step has what it needs. In your compiler the same walk starts at the program's last box, and the list it returns is an order your run loop could follow.

Repair the cooking order

cooking_order should return the list from the picture. Two things are wrong.

The moment. It adds an item to the list on the way in, so pizza comes first. Add it after the parts have been visited.

The notebook. It writes in done and never looks, so salt is listed twice. Look first, and turn back if the item is there.

done is a keyword in OCaml, so the table is called done_.

Going deeper: a graph too deep for recursion

This part and the next are optional. A week 1 file holds fewer than 100 boxes, so the walks above are all you need there. Come back when a walk fails on a long program.

Every walk so far calls itself. Each call waits for the calls it made, and while it waits its variables sit on the call stack, a piece of memory with one slot for each unfinished call. A chain of boxes 100,000 long, each reading the one before, means 100,000 unfinished calls at the deepest point.

Python refuses to go deeper than a fixed limit, which is 1000 calls unless you change it.

OCaml 5 grows its stack as needed, up to 1 GB unless you change it.

The default limit is 1000, so the walk stops with RecursionError: maximum recursion depth exceeded. Use your own stack, or raise the limit for moderate depths.

How large can OCaml 5's stack grow by default?

OCaml 5 grows the stack up to 1 GB, and ten million frames of a small function fit. 100,000 is no problem. Older OCaml versions had a much smaller stack.

sys.setrecursionlimit(100_000) raises the limit, and a few thousand levels are fine. Much higher, and the real stack underneath can run out, and then the program dies with no Python error message at all. Later weeks' .uir tests run to thousands of lines, so the sturdy fix is the next section.

Ten million calls deep in the OCaml toplevel, and what happens past the limit 
# let rec depth n = if n = 0 then 0 else 1 + depth (n - 1);;
val depth : int -> int = <fun>
# depth 10_000_000;;
- : int = 10000000

Past the limit, the program raises the exception Stack_overflow, and the toplevel prints Stack overflow during evaluation (looping recursion?). Recursion that never stops ends there too. So in OCaml, recursion is usually fine for the course's graphs. Older OCaml versions (4.14 and before) used a much smaller system stack, so you may see advice that says otherwise. The explicit stack below still matters in OCaml when you want to control the order of work yourself, and it is how you'd write the same walk in C.

Going deeper: your own stack

A recursive walk keeps its "what to do next" on the call stack. You can keep it in an ordinary list, and then only memory limits the depth. A list used this way is a stack: you add to one end and take from the same end, so the last thing added is the first thing taken. Adding is called a push and taking is called a pop.

Post-order needs one trick. When you first pop a box you can't write it down, because its sources come first. So you push it back with a note that says "ready", and push its sources on top. The sources pop first. When the box pops again with its note, you write it.

The picture does this for (2 + 3) × 4. The output is postfix, where each operator comes after its two operands: 2 3 + 4 *.

For a shared graph you add the notebook, as before: when a box pops without its note and is already in the notebook, skip it.

The postfix walk as code, with its trace and two common slips 
def postfix(e):
    out = []
    stack = [(e, False)]
    while stack:
        node, ready = stack.pop()
        if node[0] == "num":
            out.append(str(node[1]))
        elif ready:
            out.append(node[0])
        else:
            stack.append((node, True))
            stack.append((node[2], False))
            stack.append((node[1], False))
    return " ".join(out)
type t = N of int | Op of string * t * t

let postfix e =
  let out = ref [] in
  let stack = ref [ (e, false) ] in
  while !stack <> [] do
    let node, ready = List.hd !stack in
    stack := List.tl !stack;
    match node with
    | N n -> out := string_of_int n :: !out
    | Op (name, _, _) when ready -> out := name :: !out
    | Op (_, a, b) -> stack := (a, false) :: (b, false) :: (node, true) :: !stack
  done;
  String.concat " " (List.rev !out)

The node format is ("num", 2) for a number and ("+", left, right) for an operator. The right child is pushed before the left, so the left one is on top and pops first.The stack is a list whose head is the top. Putting a first means the left child pops first, then the right child, then the node again with ready set. Here is the trace, with the top of the stack on the right and a check mark for "ready":

The same code handles an expression 100,000 levels deep, because the list grows instead of the call stack.

Two common slips

Pushing the children in reading order makes the last child pop first, so the output comes out mirrored. And forgetting the "ready" note makes the loop expand the same node forever, or write it before its children.

A cooking order without recursion

Write topo g root. g is a Hashtbl from an item to the list of items it needs (the starter's graph builds one from a list of pairs). An item that isn't a key needs nothing. Return every item reachable from root, each exactly once, in post-order: an item's parts left to right, then the item. Items not reachable from root are left out.

Use your own stack, not recursion. One test is a chain 100,000 items deep.

A stack of (item, ready) pairs and a table of items you have started. Mark an item when it pops without its note, and skip it if it is already marked.

Why must the memo key be the node's identity, not its contents?

What does a table do with a key on every lookup? How much of a node's contents is there, counted as a tree?

A content key makes every lookup read the whole subtree, so the walk is slow again. An identity key is one small number. (In a hash-consed graph, equal contents means the same node anyway.)

a needs b and c, and b needs c. Write the post-order from a, parts left to right, each item once. Separate the names with commas.

Start at a and go to its first part, b. What does b need, and when is b written down?

c is written inside the walk of b. When a later reaches c, it's already done.

c, b, a. The walk of b writes c first, then b. Back in a, its second part c is already done, so it is skipped, and a comes last.

In the explicit-stack walk, why does a node get pushed back with a "ready" note before its children?

A stack gives back the last thing pushed first. Which of the node and its children is pushed last?

The children go on top, so they pop and finish first. Then the node pops again with its note, and post-order says that's when it is written.
