Learn Python · Lesson 4

Your own types

So far every value you've used came with Python: numbers, strings, lists, dicts. This lesson shows you how to make new kinds of values, like a book, a point, or a piece of an arithmetic expression. By the end you'll build the expression 2 + 3 * 4 as a tree of small objects and write a function that works out its value. That tree is the same shape as the graph your compiler builds in week 1.

Why make your own type

Say you want to keep track of a book. You know three things about it: the title, the author, and the year. With what you have so far, you might put them in a tuple:

>>> book = ("Dune", "Frank Herbert", 1965)
>>> book[2]
1965

That works, but book[2] doesn't say what it means. You have to remember that position 2 is the year. Mix up the order once, and your program quietly uses the author as the title. With ten kinds of things and five fields each, nobody can keep the positions in their head.

A type is a kind of value: int, str and list are types. Making your own type lets you bundle related values together under one name and give each one a name of its own. Then you write book.year instead of book[2]. Each named value inside is called a field (or an attribute).

A class, one line at a time

A class is the recipe for a new type. Each value you make from it is an object (also called an instance of the class). Here is a class for books:

class Book:
    def __init__(self, title, author, year):
        self.title = title
        self.author = author
        self.year = year

Read it slowly:

  • class Book: starts the recipe. Class names start with a capital letter by habit, so you can tell them apart from functions.
  • def __init__(...) is a function that lives inside the class. Its name has two underscores on each side, and Python calls it automatically every time you make a new Book. Its job is to fill in the fields. "init" is short for initialize.
  • self is the new object being filled in. Python passes it as the first argument without you writing it.
  • self.title = title creates a field called title on the object and stores the argument in it.

To make a book, call the class like a function:

>>> b = Book("Dune", "Frank Herbert", 1965)
>>> b.title
'Dune'
>>> b.year
1965

Here's what happens when Python runs Book("Dune", "Frank Herbert", 1965):

stepwhat Python doesthe object afterwards
1makes a new, empty Book objectno fields yet
2calls __init__(self=that object, title="Dune", author="Frank Herbert", year=1965)no fields yet
3runs self.title = titletitle='Dune'
4runs self.author = authortitle='Dune', author='Frank Herbert'
5runs self.year = yearall three fields
6hands the object back, and b now names itall three fields

You passed three arguments, and __init__ has four parameters. The extra one is self, which Python fills in. Every function inside a class takes self first for this reason.

Forgetting self

Leave out self and write def __init__(title, author, year):. Python still passes the new object first, so now there's one argument too many: TypeError: Book.__init__() takes 3 positional arguments but 4 were given. When an error counts one more argument than you wrote, look for a missing self.

Methods and printing

A method is a function that lives inside a class and works on one object. You've used methods already: text.lower() and words.append("x") are method calls. Here's a book with a method that works out how old the book is:

class Book:
    def __init__(self, title, author, year):
        self.title = title
        self.author = author
        self.year = year

    def age(self, now):
        return now - self.year
>>> b = Book("Dune", "Frank Herbert", 1965)
>>> b.age(2026)
61

b.age(2026) is a short way of writing Book.age(b, 2026). The object before the dot becomes self, and 2026 becomes now. Inside the method, self.year is this book's year.

Now try printing a book:

>>> print(b)
<__main__.Book object at 0x000001E6C3A5F290>

Python doesn't know how you'd like a book to look, so it prints the class name and the object's address in memory (the hex number, which is different every run). To choose the text yourself, add a method called __repr__. It takes only self and returns a string. "repr" is short for representation.

class Book:
    def __init__(self, title, author, year):
        self.title = title
        self.author = author
        self.year = year

    def __repr__(self):
        return f"Book({self.title!r}, {self.author!r}, {self.year})"
>>> b = Book("Dune", "Frank Herbert", 1965)
>>> print(b)
Book('Dune', 'Frank Herbert', 1965)
>>> [b, b]
[Book('Dune', 'Frank Herbert', 1965), Book('Dune', 'Frank Herbert', 1965)]

The !r inside the f-string means "show this value the way the REPL would", so strings keep their quotes. A good __repr__ looks like the code that would build the object. That makes error messages and debugging prints much easier to read.

Dataclasses: the short way

Writing __init__ and __repr__ by hand gets boring, and it's easy to forget a field. A dataclass writes them for you. You list the fields with their types, and put @dataclass on the line above the class:

from dataclasses import dataclass

@dataclass
class Book:
    title: str
    author: str
    year: int

    def age(self, now):
        return now - self.year
>>> b = Book("Dune", "Frank Herbert", 1965)
>>> b
Book(title='Dune', author='Frank Herbert', year=1965)
>>> b.age(2026)
61

The first line, from dataclasses import dataclass, loads dataclass from a module that comes with Python. Lesson 6 explains imports. For now, copy the line as it is.

A line that starts with @ is a decorator: it takes the class (or function) below it and changes it. @dataclass reads the field list and adds an __init__, a __repr__, and an == that compares fields. You can still add your own methods, like age.

The : str and : int parts are type hints. Python doesn't check them when it runs, so Book("Dune", "Frank Herbert", "long ago") won't fail. Your editor reads them, though, and can warn you (in VS Code, once you turn on type checking as lesson 2 describes).

You can change a field after the object is built: b.year = 1966 works. Often you don't want that. A value that never changes is easier to reason about, since nothing far away can alter it behind your back. Add frozen=True and the fields become read-only:

@dataclass(frozen=True)
class Point:
    x: int
    y: int
>>> p = Point(1, 2)
>>> p.x = 5
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
  File "<string>", line 4, in __setattr__
dataclasses.FrozenInstanceError: cannot assign to field 'x'

A value that can't change is immutable. Ints, strings and tuples are immutable too. To "move" a frozen point, you build a new one: Point(p.x + 1, p.y). The nodes of your compiler's graph will be frozen dataclasses, for reasons the next two sections explain.

A frozen point with a distance

The starter has a Point dataclass with fields x and y. Make it frozen, and write the method distance(self, other): the straight-line distance between the two points, √((x₁ − x₂)² + (y₁ − y₂)²). Point(0, 0).distance(Point(3, 4)) is 5.0.

math.sqrt takes a square root. One hidden test puts two equal points in a set, which only works for a frozen dataclass.

Equal, or the same object?

A dataclass's == compares the fields one by one. Two points with the same x and the same y are equal, even though you built them separately. Python has a second question you can ask: a is b means "are these the very same object in memory?"

>>> a = Point(1, 2)
>>> b = Point(1, 2)
>>> c = a
>>> a == b
True
>>> a is b
False
>>> a is c
True

A variable is a name that points at an object. c = a doesn't copy anything. It makes c a second name for the object a already names. Step through the picture: each box is an object, and each line joins a name to the object it names.

Think of two copies of the same printed book. They're equal: same words on every page. They aren't the same book: write in one, and the other stays clean. == asks "same words?" and is asks "same book?"

For plain classes you write yourself (without @dataclass), == falls back to is: two separate objects are never equal unless you write an __eq__ method. That's one more thing a dataclass does for you.

Why the course cares

Comparing with == on a big tree of dataclasses compares every field of every node inside, all the way down. is compares two addresses, which takes almost no time. In week 1 you'll arrange things so that equal nodes are always the same object, and then is is all you need.

Hashable values: what can be a key

You've used dicts and sets. They find things fast because they don't search. Each key is turned into a number called its hash, and the hash says which drawer the key is filed in. To look a key up, Python computes its hash, opens that one drawer, and checks with ==. A value that can be hashed is hashable.

Here's the catch. Suppose you filed a list as a key, then appended to the list. Its hash would change, but it would still sit in the old drawer. Looking it up would open the new drawer and find nothing. To stop that from happening, Python's built-in types that can change, like lists, dicts and sets, refuse to be dict keys or set members, and so does a dataclass that isn't frozen:

>>> {(1, 2): "a"}
{(1, 2): 'a'}
>>> {[1, 2]: "a"}
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
TypeError: unhashable type: 'list'

A frozen dataclass is immutable, so it's hashable. Its hash comes from its fields, so equal points land in the same drawer, and a set keeps only one of them:

>>> hash(Point(1, 2)) == hash(Point(1, 2))
True
>>> len({Point(1, 2), Point(1, 2), Point(3, 4)})
2
>>> seen = {Point(0, 0): "start"}
>>> seen[Point(0, 0)]
'start'

A dataclass that isn't frozen can change, so Python refuses to hash it:

>>> {Book("Dune", "Frank Herbert", 1965)}
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
TypeError: unhashable type: 'Book'
Frozen only goes one level deep

A frozen dataclass with a list field can still be changed through the list, and hashing it fails with unhashable type: 'list'. If a frozen class needs a sequence, use a tuple: srcs: tuple rather than srcs: list. Your compiler's nodes keep their inputs in a tuple for this reason.

Enums, isinstance and match

Some values come from a short, fixed list of choices: the colors of a traffic light, the suits of a deck, the operations of a calculator. An enum (short for enumeration) gives each choice a name:

from enum import Enum

class Light(Enum):
    RED = 1
    YELLOW = 2
    GREEN = 3
>>> Light.RED
<Light.RED: 1>
>>> print(Light.RED)
Light.RED
>>> Light.RED.name, Light.RED.value
('RED', 1)
>>> Light.RED == 1
False
>>> list(Light)
[<Light.RED: 1>, <Light.YELLOW: 2>, <Light.GREEN: 3>]

Why not the strings "red", "yellow" and "green"? Because a typo like "gren" is still a perfectly good string, and your program carries on with it. Light.GREN is an AttributeError the moment it runs. And Light.RED == 1 is False: an enum member is only ever equal to itself, so it can't be confused with a number by accident. The numbers 1, 2, 3 only need to be different from each other.

The next traffic light

Write next_light(light) for the Light enum above. A red light turns green, green turns yellow, and yellow turns red.

Three if tests with == work. So does a dict from each light to the next one, since enum members are hashable.

When a value can be one of several classes, you often need to ask which one it is. isinstance(x, C) answers "is x an object of class C?" Here are two shapes:

import math
from dataclasses import dataclass

@dataclass(frozen=True)
class Circle:
    radius: float

@dataclass(frozen=True)
class Rect:
    width: float
    height: float
>>> isinstance(Circle(1.0), Circle)
True
>>> isinstance(Circle(1.0), Rect)
False

To work out an area, you could write if isinstance(shape, Circle): ... elif isinstance(shape, Rect): ... and then read the fields. match does both in one go. It is new, so here it is first with plain values. It compares one value with each case in turn, from the top, and runs the first one that fits:

>>> def describe(n):
...     match n:
...         case 0:
...             return "zero"
...         case 1:
...             return "one"
...         case _:
...             return "many"
...
>>> describe(1)
'one'
>>> describe(7)
'many'

case _: fits any value, so it catches whatever the cases above missed. A case can also hold a class pattern:

def area(shape):
    match shape:
        case Circle(r):
            return math.pi * r * r
        case Rect(w, h):
            return w * h
        case _:
            raise TypeError(f"not a shape: {shape!r}")
>>> area(Rect(2, 3))
6
>>> area(Circle(1))
3.141592653589793
>>> area("square")
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
  File "<stdin>", line 8, in area
TypeError: not a shape: 'square'

case Circle(r): reads as "if shape is a Circle, call its first field r and run this case". case Rect(w, h): names both fields of a Rect, in the order the class lists them. The cases are tried from the top, and the first one that matches wins. Ending with a case _: that raises an error means a forgotten case is loud instead of silently returning None. raise TypeError("...") stops the function right there with an error of your choosing, the same kind of error Python itself shows. Lesson 6 covers errors properly.

Parentheses after the class name

case Circle: without parentheses doesn't test the class. A bare name in a pattern is a capture: it matches anything and stores it in a variable called Circle. Python notices when cases follow it and stops with SyntaxError: name capture 'Circle' makes remaining patterns unreachable. To match a class without naming its fields, write case Circle():.

A tree of arithmetic

Now put it all together. How would a program hold the expression 2 + 3 * 4? Not as a string: a string is only characters, and nothing in it says that the * happens first. Instead, use one small class for each kind of piece:

from dataclasses import dataclass

@dataclass(frozen=True)
class Num:
    value: int

@dataclass(frozen=True)
class Add:
    left: "Expr"
    right: "Expr"

@dataclass(frozen=True)
class Mul:
    left: "Expr"
    right: "Expr"

Expr = Num | Add | Mul

A Num holds a number. An Add holds two smaller expressions, the things on its left and right, and so does a Mul. The last line names the idea "any of these three", so the hints can say Expr. The hints are in quotes because Expr doesn't exist yet when Python reads those lines.

Since * happens before +, 2 + 3 * 4 means 2 + (3 * 4): an Add whose right side is a Mul.

>>> e = Add(Num(2), Mul(Num(3), Num(4)))
>>> e
Add(left=Num(value=2), right=Mul(left=Num(value=3), right=Num(value=4)))
>>> e.right.left
Num(value=3)

Each object is a node, and the objects it holds are its children. A node with no children, like a Num, is a leaf. Drawn as a picture, it's a tree. The course draws trees with the leaves at the top and the result at the bottom, because values flow down from the numbers to the answer:

To work out the value of a tree, look at the node you have. A Num is worth its number. An Add is worth the value of its left side plus the value of its right side. A Mul is the same, with times instead of plus. That's a sentence per case, so it's a match with a case per class:

def evaluate(e):
    match e:
        case Num(v):
            return v
        case Add(left, right):
            return evaluate(left) + evaluate(right)
        case Mul(left, right):
            return evaluate(left) * evaluate(right)
        case _:
            raise TypeError(f"not an expression: {e!r}")
>>> evaluate(Add(Num(2), Mul(Num(3), Num(4))))
14
>>> evaluate(Mul(Add(Num(2), Num(3)), Num(4)))
20

evaluate calls itself on the children. That's called recursion, and it works because each call gets a smaller tree, until it reaches a Num, which needs no further calls. The next lesson is all about how that works. For now, step through the picture above to watch the values arrive.

Look at the second example. (2 + 3) * 4 needs parentheses as text, and the tree needs none. The grouping is the shape of the tree: the Add is inside the Mul. Turning text into a tree like this is called parsing, and walking the tree to get an answer is interpreting it. Week 1 of the course does both, with nodes that are frozen dataclasses much like these.
