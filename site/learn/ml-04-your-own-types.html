Learn OCaml · Lesson 4

Your own types

So far every value had a type OCaml gave you: int, string, lists of them. This lesson shows you how to make your own. A record bundles named values together. A variant says "one of these choices". Put a variant inside itself and you get a tree, which is the shape of every program your compiler will read.

Records: a bundle of named values

Say you want to store a point on a grid. It has two numbers, an x and a y. You could use a pair (3, 4), but then you have to remember which number is which. A record gives each part a name. First you describe the shape with type, then you build values of that shape.

# type point = { x : int; y : int };;
type point = { x : int; y : int; }
# let p = { x = 3; y = 4 };;
val p : point = {x = 3; y = 4}
# p.x;;
- : int = 3

Read the first line as "a point has a field called x holding an int, and a field called y holding an int". A field is one named part of a record. Inside the type you write : and a type, and when you build a value you write = and a value. You read a field with a dot: p.x is 3.

Notice that you never told OCaml that p is a point. It saw the field names x and y and worked it out, the same way it works out that 3 is an int.

Changing one field means making a copy

Record fields can't be changed after you build the record. To get a point that is the same as p but with a different x, you build a new one with with:

# let q = { p with x = 10 };;
val q : point = {x = 10; y = 4}
# p;;
- : point = {x = 3; y = 4}

{ p with x = 10 } means "a new record, copying every field from p except x, which is 10". The old p is still there, unchanged. This is a big idea in OCaml, and you'll see it again with maps in lesson O.6: instead of changing a value, you make a new one and keep the old one too. Nobody else who holds p gets a surprise.

Every field, every time

When you build a record from scratch you must give every field. { x = 1 } fails with Error: Some record fields are undefined: "y". If you want most fields to stay the same, start from an existing record with with.

Variants: one of these choices

A record says "this AND this AND this". Sometimes you need "this OR this OR this" instead. A playing card's suit is hearts, or diamonds, or clubs, or spades. Never two at once, never something else. That is a variant type.

# type suit = Hearts | Diamonds | Clubs | Spades;;
type suit = Hearts | Diamonds | Clubs | Spades
# let colour s = match s with Hearts | Diamonds -> "red" | Clubs | Spades -> "black";;
val colour : suit -> string = <fun>
# colour Clubs;;
- : string = "black"

Each name between the bars is a constructor: a way to make a value of the type. Hearts is a value of type suit, and so is Clubs. Constructors always start with a capital letter. That is how OCaml tells them apart from ordinary names like colour.

You take a variant apart with match, the same tool you used on lists in lesson O.3. Hearts | Diamonds -> "red" is one case that covers two constructors. Why is this better than using the strings "hearts" and "clubs"? Because a typo like "heats" is still a string, and nothing would warn you. Heats is not a constructor, so OCaml refuses it at once.

Variants that carry data

A constructor can carry values with it. Here is a shape: either a circle, which needs a radius, or a rectangle, which needs a width and a height.

# type shape = Circle of float | Rect of float * float;;
type shape = Circle of float | Rect of float * float
# let area s = match s with Circle r -> 3.14159 *. r *. r | Rect (w, h) -> w *. h;;
val area : shape -> float = <fun>
# area (Rect (2.0, 3.0));;
- : float = 6.
# area (Circle 1.0);;
- : float = 3.14159

Circle of float means "the Circle constructor carries one float". Rect of float * float means "Rect carries two floats". The * here is not multiplication. In a type, * means "and", so float * float is a pair of floats.

Look at what match does now. The case Circle r checks that the shape is a circle and gives the name r to the radius inside it, ready to use on the right of the arrow. Rect (w, h) does the same for both numbers. Checking which kind of value you have and pulling out its parts happen in one step. OCaml prints 6. for the float six. The dot is how it shows you this is a float, not an int.

A constructor needs its data

Circle on its own is not a shape. OCaml says Error: The constructor "Circle" expects 1 argument(s), but is applied here to 0 argument(s). Write Circle 1.0. And for two values, the parentheses and the comma are required: Rect (2.0, 3.0), not Rect 2.0 3.0.

Perimeter of a shape

The starter adds a third shape, Square of float (the length of one side). Write perimeter : shape -> float, the distance around the shape. A circle's is 2 × π × r, a rectangle's is 2 × (w + h), and a square's is 4 × side. Use Float.pi for π.

One match case per constructor. Keep the type exactly as the starter has it, because the tests build shapes with it.

A type that contains itself: expression trees

Here is the most important type in this lesson. Think about the arithmetic 2 + 3 * 4. Multiplication goes first, so this means "2, plus the result of 3 times 4". You can draw that as a tree: the + at the bottom takes two inputs, the number 2 and the result of a *, and that * takes 3 and 4.

An expression is a piece of arithmetic like this. Each expression is one of three things: a plain number, an addition of two smaller expressions, or a multiplication of two smaller expressions. Written in OCaml, that sentence becomes a type:

# type expr = Num of int | Add of expr * expr | Mul of expr * expr;;
type expr = Num of int | Add of expr * expr | Mul of expr * expr
# let e = Add (Num 2, Mul (Num 3, Num 4));;
val e : expr = Add (Num 2, Mul (Num 3, Num 4))

The new thing is that expr appears inside its own definition. Add of expr * expr says an addition carries two expressions, and each of those can be another Add, a Mul, or a Num. A type that refers to itself like this is called recursive. It can describe arithmetic of any size, and it doesn't go on forever, because sooner or later every branch ends in a Num, which carries a plain int and nothing else.

The value e is the tree for 2 + 3 * 4. Notice there are no precedence rules in it. The tree's shape already says the Mul happens inside the Add. Here it is drawn out, with the numbers on top and the final result at the bottom:

Why this matters for the course

Your compiler's whole job is to read programs as trees like this one, look at them, and rewrite them. In week 1 the nodes are called UOps and they have more kinds than three, but every function you write on them looks like the eval below: match on the kind of node, handle its parts.

Evaluating the tree

To evaluate an expression means to work out its number. A recursive type calls for a recursive function, with one case per constructor:

# let rec eval e =
    match e with
    | Num n -> n
    | Add (a, b) -> eval a + eval b
    | Mul (a, b) -> eval a * eval b;;
val eval : expr -> int = <fun>
# eval e;;
- : int = 14

Read each case out loud. "A number is worth itself." "An addition is worth the value of its left side plus the value of its right side." "A multiplication is the same with times." That is the whole definition of arithmetic, and it fits in five lines. eval calls itself on the smaller parts, and the Num case is where the calls stop. Step through it on the tree:

Which side goes first?

The trace does the left side first because it reads more easily. OCaml doesn't promise an order for the two sides of eval a + eval b, and in practice it often does the right one first. For a function like eval, which only computes a value and changes nothing, the order can't change the answer.

The safety net: exhaustive matching

Programs grow. Say you want negative numbers too, like -(5). You add a fourth constructor, Neg of expr, and leave eval as it was:

# type expr = Num of int | Add of expr * expr | Mul of expr * expr | Neg of expr;;
type expr =
    Num of int
  | Add of expr * expr
  | Mul of expr * expr
  | Neg of expr
# let rec eval e =
  match e with
  | Num n -> n
  | Add (a, b) -> eval a + eval b
  | Mul (a, b) -> eval a * eval b;;
Lines 2-5, characters 2-33:
2 | ..match e with
3 |   | Num n -> n
4 |   | Add (a, b) -> eval a + eval b
5 |   | Mul (a, b) -> eval a * eval b..
Warning 8 [partial-match]: this pattern-matching is not exhaustive.
Here is an example of a case that is not matched:
Neg _

val eval : expr -> int = <fun>

OCaml checked every match against the type and noticed that this one forgot a case. A match that covers every constructor is called exhaustive. The warning tells you three things: where the match is (lines 2 to 5), what is wrong (not exhaustive), and an example value it can't handle (Neg _, where _ means "with anything inside").

It is only a warning, so eval still gets defined. If you ignore it and call eval (Neg (Num 5)) anyway, the program stops with Exception: Match_failure ("//toplevel//", 2, 2). In a dune project, which you'll set up in lesson O.6, this warning is treated as an error, so the program won't even build until you fix it.

That is the safety net. In a big program you might have twenty functions that match on expr. Add a constructor and the compiler hands you a list of every one that needs a new case. You don't have to remember them.

The catch-all _ cuts the net

A case | _ -> ... matches anything. It is tempting to end a match with | _ -> 0 to make a warning go away. Do that in eval and the warning disappears, and so does the help. eval (Neg (Num 5)) now quietly returns 0, and so will every constructor you add next month. A wrong answer with no warning is the hardest kind of bug to find. Use _ only when you really mean "every other case, including future ones, behaves the same".

Evaluate an expression tree

The starter's expr has five constructors: Num, Add, Sub (subtraction, left minus right), Mul, and Neg (minus one expression). Its eval ends in a catch-all, so it answers 0 for most trees. Finish eval so every tree gets its real value. For example eval (Neg (Sub (Num 2, Num 9))) is 7.

Delete the | _ -> 0 line first and read the warning. Keep the type exactly as it is: the tests build trees with it.

When there might be no answer: option and result

You met option in lesson O.3. A value of type int option is either Some of an int or None. Now you can see what it really is: a variant with two constructors, one carrying data and one not. OCaml's library defines it the same way you defined shape.

# List.find_opt (fun x -> x > 10) [3; 12; 7];;
- : int option = Some 12
# List.find_opt (fun x -> x > 100) [3; 12; 7];;
- : int option = None
# int_of_string_opt "42";;
- : int option = Some 42
# int_of_string_opt "forty";;
- : int option = None

Option is right when "no answer" needs no explanation. If you look for something and it isn't there, None says it all. But sometimes the caller needs to know why it failed. For that OCaml has result, another variant with two constructors: Ok carries the answer, and Error carries a description of what went wrong.

Here is a function that reads an age typed by a person. Two things can go wrong, and the message says which:

# let parse_age s =
    match int_of_string_opt s with
    | None -> Error "not a number"
    | Some n -> if n < 0 then Error "negative age" else Ok n;;
val parse_age : string -> (int, string) result = <fun>
# parse_age "31";;
- : (int, string) result = Ok 31
# parse_age "abc";;
- : (int, string) result = Error "not a number"
# parse_age "-4";;
- : (int, string) result = Error "negative age"

Read the type (int, string) result as "either Ok with an int, or Error with a string". The caller takes it apart with match, and because the match must be exhaustive, the caller can't forget the error case:

# let describe s =
    match parse_age s with
    | Ok n -> "age " ^ string_of_int n
    | Error msg -> "bad input: " ^ msg;;
val describe : string -> string = <fun>
# describe "abc";;
- : string = "bad input: not a number"

Division that reports its error

Dividing by zero in OCaml stops the program. Write safe_div : int -> int -> (int, string) result that returns Ok (a / b) normally, and Error "division by zero" when b is 0.

Check b before you divide. The error message must be exactly "division by zero".

Exceptions: errors you don't expect

The third way to report a problem is an exception. An exception doesn't return a value at all. It stops the current function, and the one that called it, and so on, until some code catches it. If nothing catches it, the whole program stops. You have already seen a few:

# 1 / 0;;
Exception: Division_by_zero.
# List.find (fun x -> x > 100) [3; 12; 7];;
Exception: Not_found.
# int_of_string "forty";;
Exception: Failure "int_of_string".

You can raise your own. failwith "message" raises the Failure exception with your message. raise Not_found raises the standard "I looked and it isn't there" exception. Both have any type you like, so they fit in any branch:

# failwith "boom";;
Exception: Failure "boom".
# let get_first l = match l with x :: _ -> x | [] -> raise Not_found;;
val get_first : 'a list -> 'a = <fun>
# get_first [];;
Exception: Not_found.

To catch an exception, wrap the risky code in try ... with. The part after with is written like the cases of a match, but it matches exceptions:

# let first_big l = try List.find (fun x -> x > 100) l with Not_found -> 0;;
val first_big : int list -> int = <fun>
# first_big [3; 500; 7];;
- : int = 500
# first_big [3; 12];;
- : int = 0

If the code inside try finishes normally, its value is the answer. If it raises Not_found, the Not_found -> 0 case runs instead. Any other exception passes straight through and keeps going up.

Notice what the type of List.find doesn't tell you: that it can fail. find_opt puts the failure in the type, as an option, and the compiler makes the caller deal with it. find leaves it out, and you only find out when it happens. That difference is the whole reason to choose between them.

When to use which

ToolUse it whenExample
option"Not there" is a normal answer and needs no explanation.Looking up a word in a dictionary.
resultFailure is expected and the caller needs to know why, to tell a person or decide what to do.Reading a number someone typed. Checking a program for mistakes.
exceptionIt "can't happen" unless there's a bug, or it is so rare that checking at every step would bury the real code.An index that your own logic says is always valid. A file the program can't run without.
An exception nobody catches ends the program

If you use List.find or Hashtbl.find on something that might be missing, and nothing catches Not_found, the program stops with Exception: Not_found and no hint of which lookup failed. When the missing case is normal, reach for the _opt version and match on it.

What you can do now

  • Define a record type, build a record, read its fields, and copy it with one field changed using { r with ... }.
  • Define a variant type, with or without data on each constructor, and take it apart with match.
  • Write a recursive type for a tree, like expr, and a recursive function over it with one case per constructor.
  • Read an exhaustiveness warning and know why a catch-all _ can hide bugs.
  • Choose between option, result and exceptions, and raise and catch an exception.

Check yourself

p is { x = 3; y = 4 } and let r = { p with y = 0 }. What is r.x?

Which fields does with copy from p?

Only y is given a new value. Every other field comes from p.

{ p with y = 0 } copies every field of p except y. So r.x is p.x, which is 3, and r is {x = 3; y = 0}.

With type shape = Circle of float | Rect of float * float, which of these is a value of type shape?

Each constructor needs the data its type says it carries.

Rect carries float * float, a pair. How do you write a pair?

A pair is written with parentheses and a comma, so Rect (2.0, 3.0) is right. Circle alone is missing its radius, and Rect 2.0 3.0 passes two separate values instead of one pair. Both are errors.

What is eval (Mul (Add (Num 1, Num 2), Num 5))?

Draw the tree. What is at the bottom, and what are its two inputs?

The Mul needs the value of Add (Num 1, Num 2) first.

The inner Add is 1 + 2 = 3, then the Mul is 3 * 5 = 15. This tree is (1 + 2) * 5. Trees don't need parentheses because their shape already says what goes first.

You add | Neg of expr to expr. Your eval ends with | _ -> 0. What happens?

Does the _ case match a Neg?

If a match already has a case for everything, is it exhaustive?

_ matches every value, including Neg, so the match is exhaustive and the compiler has nothing to warn about. You get a wrong answer, 0 instead of -5, with no sign that anything is off. That's the catch-all trap.

A program reads a date that a person typed. It can be malformed in several ways, and you want to show the person what was wrong. Which return type fits best?

Is bad input expected here, or a bug?

Does the caller need to know why it failed?

People mistype dates all the time, so failure is expected, and the message has to say what was wrong. result carries that message in Error, and the type forces the caller to handle it. An option would lose the reason, and an exception hides the possibility of failure from the type.

What does int_of_string_opt "7x" return?

Is "7x" a whole number?

The _opt version never raises. It returns an option.

None. The text isn't a valid int, and the _opt version reports that with None. int_of_string "7x", without _opt, would raise Failure "int_of_string" instead.
