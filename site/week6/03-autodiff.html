Automatic differentiation

By the end of this lesson you can say how far a program's output moves when one input moves a little, and work that number out for every input in one pass. The number is called the gradient. Training a model means asking for gradients over and over, so your compiler has to produce them.

Goal

Find every gradient of a small graph by walking it backward once, then ask your compiler for the same numbers with gradient.

You'll use

A list you fill in with a loop (P.3) and sugar from lesson 6.2. You need no calculus.

An array you change in place (O.5) and sugar from lesson 6.2. You need no calculus.

Nudge the input, watch the output

This lesson asks one question: if I nudge an input up a little, how far does the output move? Start with y = 3 × x. At x = 2, y is 6.

Nudge x up from 2 to 3. By how much does y go up?

Work out y for x = 3, then take away the old y.

y goes from 6 to 9, so it moves 3. Each 1 you add to x adds 3 to y, wherever x starts.

Now y = x × x at x = 3, where y is 9. This time the size of the nudge matters:

The last column settles on 6. That number is the gradient of y with respect to x at x = 3: how many times farther the output moves than the input, when the nudge is very small. Math class calls it the derivative.

For 3 × x the gradient is 3 everywhere. For x × x it depends on x: at x = 5 it is 10. A negative gradient means the output goes down when the input goes up.

Why a model needs gradients

A model is a program with many adjustable numbers in it, called weights. One more number, the loss, says how wrong the model's answers are. Training means changing the weights so the loss goes down.

A model has one weight, w = 3, and its loss is w × w. The gradient of the loss with respect to w is 6. Which change makes the loss smaller?

A gradient of 6 says: when w goes up a little, the loss goes up about 6 times as far.

The gradient is positive, so raising w raises the loss. Step the other way. At w = 2.9 the loss is 8.41, down from 9.

So the sign of a gradient tells you which way to step a weight. Training is one move, repeated: step every weight a little against its gradient.

You could find each gradient by nudging. That costs one more run of the program per weight, and this week's lab model has 7,840 weights. Nudging also only gets close (6.01, not 6). The rest of this lesson gets every gradient exactly, for about the work of two runs.

One rule for add, one for mul

A program is a graph of small ops. For one op you can find the gradient once and keep it as a rule. Find two rules by nudging.

add. u = a + b with a = 3 and b = 5 is 8. Nudge a to 4 and u is 9. It moved 1, the same as the nudge. So does nudging b.

mul. u = a × b with a = 3 and b = 5 is 15. Nudge a up to 4. By how much does u go up?

The new u is 4 × 5.

u goes from 15 to 20, so it moves 5. That is b: one more a means one more copy of b. In the same way, nudging b by 1 moves u by 3, which is a.

An operand is one of an op's inputs. Read the mul row as: each operand's gradient is the other operand's value. So mul %a 7.0 has gradient 7 with respect to %a. Both rules are exact, so small nudges are no longer needed.

Follow a nudge through two ops

Real programs chain ops. Here the input x is the 3. Step through the program first.

Nudge x from 3 to 4. By how much does %y move? Predict, then press Edit in the figure, change the 3 to a 4 and look.

First find how far %a moves. Then use the mul rule on that move.

%a moves 1, by the add rule. The mul turns each 1 of %a into 4 of %y, because its other operand is 4. So %y moves 1 × 4 = 4, from 16 to 20.

A nudge travels from the input to the output, and each op on the way multiplies it by its rule:

  1. Find the path. x, then %a, then %y.
  2. Write each op's rule. The add gives 1. The mul gives its other operand, 4.
  3. Multiply along the path. 1 × 4 = 4.

This is called the chain rule: the gradient of a chain is the rules of its ops multiplied together.

Walk backward once

The chain rule follows one input forward. A model has thousands of inputs, and doing that for each one repeats the same work. Turn it around: start at the output and walk backward.

Each node holds a gradient: how far the output moves when that node is nudged. It passes a share to each operand, which is its own gradient times the rule for that operand. A node that is used in two places gets two shares and adds them up.

Here is the warm up program with x = 3 and w = 5. Predict each number.

One walk gave both gradients. Check x by nudging: x = 4 gives 4 × 5 + 4 = 24, up 6 from 18. Walking backward like this is called reverse mode, or backpropagation. It costs about as much as one more run of the program, whether there are two inputs or 7,840.

It also explains the first table. In x × x both operands are x. Each gets the other's value, 3, and x adds its two shares: 3 + 3 = 6.

Do the walk in code

In the next two exercises a program is a list called a tape. Each entry is an input, a constant, or an add or mul of two earlier entries, named by position. Here is the warm up program:

[('x', 3.0), ('x', 5.0), ('mul', 0, 1), ('add', 2, 0)]
[X 3.0; X 5.0; Mul (0, 1); Add (2, 0)]

The walk takes three moves:

  1. Run forward. Work out the value of every entry, first to last.
  2. Seed the end. The last entry's gradient is 1.
  3. Walk backward. From the last entry to the first, send each entry's shares to its operands, adding each one to what is already there.

Last to first works because an entry is only used by later entries. When the walk reaches it, all of its shares have arrived.

Repair the backward walk

backward gets a tape and every entry's value, so move 1 is done. It returns the last entry's gradient with respect to every entry. Moves 2 and 3 have two mistakes.

The mul rule. A mul sends each operand the gradient times the other operand's value. This one uses the operand's own value.

Adding up. A share is added to what the entry already holds. This code overwrites it.

Backpropagation on a tape

Now all three moves, from a nearly empty function. Write grads tape: the gradient of the last entry with respect to every entry. Forward for values, backward for gradients.

Ask the compiler: gradient

In .uir you ask for the walk, output first and input second:

%t = mul %x %w
%l = add %t %x
%g = gradient %l %x

%l must be a single f32 number. Whole numbers have no small nudges, so only f32 values carry gradients.

Your compiler handles gradient while it builds the program, before anything runs. It does not know x or w yet. What can %g be?

6 was the answer for x = 3 and w = 5 only.

The compiler writes each share as an op instead of working it out.

For the program above, the walk builds this:

%s = mul 1.0 %w
%g = add 1.0 %s

%s is the share from %t, and the other 1.0 is the share the add sent to x. With w = 5 this is 1 + 5 = 6. Because %g is ordinary adds and muls, everything your compiler already does with a graph works on it.

Ask for a gradient

The starter returns t = x × w. Add the loss %l = mul %t %t, then make %out the gradient of %l with respect to %w. Predict the first test before you run it: x = 3 and w = 5.

f'(x) for five x at once

Slot 0 holds five values of x. For f(x) = x³ - 2x, store the gradient of f for each x into slot 1, using gradient. The starter stores f(x).

gradient starts from one number, so add the five f values up first with reduce op=add. Each x only moves its own term of the sum.

detach: send nothing back

Sometimes the walk should treat a value as a plain number. detach x has the same value as x and passes no share back to it.

x is 3. Without the detach this is x + x, and the gradient is 2. What is %g here?

%d = detach %x
%y = add %x %d
%g = gradient %y %x

The add sends 1 to each operand. Which operand passes it on to x?

1. One share goes straight to x. The other goes to the detach, which drops it. The value of %y is still 6.

What you can do now

  • Say what a gradient is: how far the output moves per unit of a small nudge to one input.
  • Tell from a gradient's sign which way to step a weight.
  • Use the two rules: add passes a gradient on unchanged, and mul multiplies it by the other operand's value.
  • Walk a graph backward once, adding up shares, to get every input's gradient.
  • Write gradient and detach in .uir.

Reference for the lab

The exact definition, for readers who know calculus

For a scalar y and a value x of any shape, gradient y x has x's shape, and element i is ∂y/∂x[i]: how fast y changes when you wiggle x[i] alone. If y = x · x and x is 3, the gradient is 6.

Your compiler computes this while building the program, not while running it. The result is an ordinary graph of muls and adds, so everything else (run, render, hash consing, staging) works on it unchanged. You can even take the gradient of a gradient.

Every op knows its local derivatives. For u = mul a b, ∂u/∂a = b and ∂u/∂b = a. The chain rule says that if you already know g = ∂y/∂u, then u sends g · b to a and g · a to b. Those are a and b's shares of the gradient.

The rule for every elementwise op, for when you write the gradient pass

The spec lists a share for every op. These are the ones from calculus, written as ops (u is the op's own result):

detach x is how you stop a gradient on purpose. Lesson 6.5 uses it on the max subtracted for a stable softmax, whose gradient cancels out in exact math. In f32 the canceling terms round, so the bits can differ without the detach.

Comparisons and integer ops have no rule because they don't need one: their results aren't f32, and only f32 nodes carry gradients. A path that leaves f32 is a dead end. That's why floor (a cast to i32 and back) has gradient 0 for |x| < 2^23, which is also the true derivative almost everywhere.

y = cast (cast x dtype=i32) dtype=f32. What is gradient y x?

Which dtype is the middle node?

The i32 node never receives a share, so nothing reaches x and the gradient is 0. That matches the math: rounding to an integer is flat almost everywhere.

The exact order of the walk and of adding shares, for when your bits differ from the tests

Start at y with g = 1.0 (∂y/∂y), and walk the graph from y back toward x. At each node, add up the shares it has received, then pass on its own shares to its operands. When the walk reaches x, the sum there is the answer.

A node has to receive all of its shares before it passes anything on. The spec orders the walk to guarantee that: take the post-order of y's graph (depth first, operands left to right, each node once) and visit it in reverse. Every node comes before the nodes it uses. H.2 walks through post-order slowly.

In (x · x) · x, x receives three shares. In exact arithmetic the order doesn't matter, but in f32 it does: (a + b) + c and a + (b + c) can round differently. So the spec fixes it. Shares are added in the order they arrive during the reverse walk, as a left fold: add c1 c2, then add that and c3. Because the walk runs backward, arrival order is often the reverse of the order the statements appear in the file. The test grad_accumulation_order has three shares whose sum depends on the order, and mismatch_grad_accumulation_other_order checks that the program-order sum is not what you get.

The walk visits nodes in reverse post-order. Why that order?

What would go wrong if a node passed its gradient on before receiving its last share?

Its operands would get a partial gradient. Reverse post-order is a reverse topological order, so users always come first. And because f32 addition isn't associative, a fixed walk also fixes the bits.

The graph gradient builds, node by node, for when you debug your output

Here is the program from the figure in the toggle above:

%t = mul %x %x
%y = mul %t %x
%g = gradient %y %x

The post-order of y's graph is x, t, y (t's operands come first, then t, then y), so the walk visits y, then t, and stops at x. y sends mul 1.0 %x to t and mul 1.0 %t to x. Call t's share %gt. t sends mul %gt %x to each operand, and both of them are x. So %g is this graph:

%gt = mul 1.0 %x
%c1 = mul 1.0 %t
%c2 = mul %gt %x
%s  = add %c1 %c2
%g  = add %s %c2

t's two shares are one node, %c2, because hash consing merges equal nodes, but x still adds it twice, once per share. Nothing is simplified: mul 1.0 %x stays in the graph. Here x is a scalar, so every literal is too. When an op's result has a shape, each literal in its rule (the -1.0 in recip's share, say) is first expanded to that shape, because ALU ops don't broadcast. The seed 1.0 is always a scalar, like y.

Which nodes take part and when gradient is invalid, for when a test is rejected

Only nodes on a path from x to y take part. A node that doesn't depend on x can't pass anything back to x, so the walk skips it. Skipping isn't just faster. A node off the path may be an op with no rule (a reduce op=mul of some unrelated data, say), and that's fine as long as x doesn't reach it. The walk also stops at x: x's own operands don't matter, because x is what you're differentiating with respect to.

What can be on the path is limited. Gradients don't go through call, load, store or loops, so a gradient whose path contains one is invalid. That's the syllabus's rule: autodiff works on pure graphs. x itself may be a load, though. The weights of a model are.

gradient is invalid when:

  • The loss isn't an f32 scalar, or x isn't an f32 value (a buffer, an i32).
  • x is a literal. gradient %y 2.0 would mean every 2.0 in the program, because equal literals are one hash-consed node.
  • The loss or x depends on an open range: no gradients inside hand-written loops.
  • A call, load or store lies on a path from x to y, or an op with no rule does (reduce op=mul).

If y doesn't depend on x at all, that's not an error. The gradient is zeros of x's shape.

gradient %y 2.0: why is it invalid?

How many nodes do add %a 2.0 and mul %b 2.0 make for the literal?

One. A gradient with respect to it would mix every use of 2.0 together, which is never what anyone means. If you want a variable, load it or stage it.

y uses x, and also reduce %d op=mul of some data %d that x doesn't touch. Is gradient y x valid?

Which nodes receive shares?

Only nodes that depend on x. The reduce's value is used, but it never needs a rule. The test grad_reduce_mul_off_path checks exactly this.

Forward mode and reverse mode, for the curious

Walking backward from the loss is reverse mode. One backward walk gives the gradient with respect to every weight at once, which is why it's what trains networks: one loss, millions of weights.

The other direction is forward mode: give one input a wiggle and push its derivative forward through the program, alongside the values. One forward pass gives the derivative of every output with respect to that one input, so a gradient over a million weights would take a million passes.

Check yourself

What is gradient of y = (x · x) · x at x = 2?

Call the inner mul c, so c is 4. The outer mul sends a share to c and one to x. Then c sends two more to x.

x receives three shares: 4 from the outer mul (g · c with c = 4), then 4 and 4 from the inner mul (2 · x each). 4 + 4 + 4 = 12 = 3 · 2².

Why reverse mode and not forward mode for training?

Forward mode follows one input's nudge forward through the program, like the chain rule.

Forward mode needs one pass per input. With a million weights that's a million passes. Reverse mode needs one pass per output, and a loss is one number.

What is gradient (mul x (detach x)) x at x = 3?

The detached x is a constant with value 3.

The mul sends x the other operand's value, 3. The detach drops the second share, which would make 6.
