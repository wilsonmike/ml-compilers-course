Lab: train MNIST

In this lab your compiler learns enough to train a model. It gains the math ops, the sugar, gradient and buffers read from files. At the end, C that your compiler wrote reads handwritten digits it has never seen, and you see how many it gets right.

Goal

Pass all 169 week 6 tests with your own compiler, including the one that must read 850 or more of 1,000 digits right, and write 10 tests of your own.

You'll use

Your compiler from the week 5 lab, and lessons 6.1, 6.2, 6.3, 6.4 and 6.5.

How the tests are graded: three new headers and the one-ulp pairs

Run tests (outcome in the file name) and # render tests work as before. Three headers are new:

  • # render check: slot S >= V: the grader reads element 0 of slot S after your kernel runs and needs it to be at least V. The MNIST test uses it for accuracy, and r_url_check uses it on a small example. Nothing else is compared.
  • # time: T: your compiler's render, the C compile and the kernel each get T seconds instead of 10. MNIST gets 120.
  • # max_bytes: B: the size limit on your C, raised for MNIST's 50 written-out steps.

The run tests check exact bits: the math ops against their definitions, each gradient against the rules and the share order, every sugar against its expansion. Several tests come in pairs: mismatch_*_one_ulp_off asserts one value one ulp (one unit in the last place) away from the right one, so the right outcome is MISMATCH. A compiler that is only close prints MATCH for it, so the test catches it.

Plan it first

First decide the order.

The spec defines exp2 as a program of ops. Which two of them does your compiler lack?

Lesson 6.1: exp2 rounds x to a whole number n, then builds 2 to the n straight from bits.

floor rounds and bitcast turns bits into a float. So bitcast is the smallest first step, and floor comes just before exp2.

Lesson 6.2, "Why the next lesson gets easier".

The gradient pass only meets core ops and the four math ops. sub, fdiv and matmul get their gradients for free.

So the route is the week's own order, then render, then MNIST.

Read a float's bits

--skip mnist leaves out the slow test. The last line should read 38 / 168 passed. Of those, 37 are rejected_ tests that pass by luck: your compiler rejects every new op.

  1. Let names hold digits. An op name may have digits after its first letter, so exp2 parses. log10 is still not an op.
  2. Add bitcast. With dtype=i32 or dtype=f32, it keeps the shape and the 32 bits and changes the type. bitcast 1.0 dtype=i32 is 1065353216. A bool on either side is rejected.

Build floor, then exp2

exp2 rounds with floor, so floor comes first.

  1. Build floor. It is sugar. Your parser replaces floor x with the 12 lines in section 3 of the spec.
  2. Type exp2 in. Copy the spec's body line by line, constants included. It takes f32 of any shape, one element at a time. An i32 or bool operand is rejected.
  3. Keep it one node. Do not expand exp2 in the parser. Your evaluator runs the body when it meets the node. The gradient pass has a rule for exp2 itself.

Expand the rest of the sugar

  1. Rewrite in the parser. neg, sub, fdiv, relu, exp, log, cmpeq and matmul each become their expansion from section 3 of the spec.
  2. Match the shape. When the operand is not a scalar, expand the constant to the operand's shape first: neg of four floats multiplies by expand -1.0 [4].
  3. Check the types. fdiv, exp and log take f32 only. cmpeq takes two i32 or two bool. The parser itself must reject f32 there: the expansion would type check. relu takes no bool. matmul takes two rank 2 values whose inner sizes agree.

Build gradient and detach

Start with paths from x to y that have no shape ops.

  1. Add detach. It has the same value as its operand. Memory is rejected.
  2. Check the request. In gradient y x, y is an f32 scalar and x an f32 value. x is not a literal or memory, and neither depends on an open range. A call or a load between x and y is rejected. x itself may be a load.
  3. Mark the path. Find the nodes of y's graph that depend on x. Only those take part.
  4. Walk backward. Seed y with 1.0. Visit the nodes in reverse post-order. At each one, add its shares in the order they arrived, then send each f32 operand on the path its share from the spec's table. A detach sends nothing.

Every share is new ops in the graph, never a number. If y does not depend on x, the answer is zeros in x's shape.

Send gradients through shapes

Each shape op sends its gradient back through a partner.

  1. Undo the moves. A reshape reshapes back and a permute uses the inverse order. A pad sends a shrink, and a shrink a pad.
  2. Sum the copies. An expand sums its gradient over the axes it grew. A reduce op=add copies its gradient to every element it added.
  3. Pay the winners. A reduce op=max sends its gradient to the largest element, split evenly on a tie. reduce op=mul on the path is rejected.
  4. Finish the list. A stack sends each item an index, an index sends a pad, and a stage sends a stage. A shrink or an index on the path needs literal offsets.

matmul needs no rule, because it was sugar.

Stuck? Reread "Every shape op has a partner" in lesson 6.4. Its reference has the exact ops.

Fill a buffer from a file

  1. Parse the two attributes. A buffer may carry url= and sha256=. They come together, and they replace the data list.
  2. Find the file. Resolve a relative path against the folder of the .uir file. Reject any path with .. in it.
  3. Check it. The SHA-256 of the bytes must equal the 64 hex digits. The size must be exactly 4 bytes per f32 or i32, or 1 per bool. A missing file or a failed check is REJECTED.
  4. Decode. Read the elements little-endian. A bool byte is 0 or 1.

hashlib.sha256 is in the standard library.

OCaml's standard library has no SHA-256. Write one in about 60 lines, or run sha256sum.

Checkpoint 
-k run/url_  6 / 6 passed
-k run/      153 / 153 passed

Stuck? Open every rule for file buffers in lesson 6.5.

Render the new ops

Sugar and gradients are ordinary ops by the time render sees them. Four things are left.

  1. Lower the math ops. Each becomes its body, inline or as one C function that does exactly the same steps.
  2. Render bitcast. Copy the 4 bytes with memcpy, never with a pointer cast. Any NaN still becomes 0x7fc00000.
  3. Leave files to the harness. It fills each url= buffer before it calls your kernel.
  4. Stage in-place updates. A training step stores W - g into the buffer W came from, and g reads all of W. Fill a temp first, then copy it in.

Train the model

First take one training step yourself.

One step of gradient descent

Slots 0 to 2 hold X (4x2), y (4 targets) and w (2 weights). With the loss 0.25 times the sum of (X @ w - y)², update w in place to w minus 0.1 times gradient loss w. The starter steps the wrong way.

The MNIST test is that step 50 times, on 7,840 weights that start at zero. Run it:

python tools/test.py --compiler YOURS --week 6 -k mnist -v

With the oracle as the compiler this takes 29 seconds. Your render, the C compile and the kernel each get 120 seconds. With a slower compiler, add --skip mnist to your other runs.

Timing your kernel with bench.py, for when you want to know how fast it trains 
python tools/bench.py --compiler "C:/path/to/your.exe" tests/week6/render/mnist_train.uir

This renders the program with your compiler, builds it at -O2 without the sanitizers, runs it, and prints the render time, the compile time, the kernel's time, and the useful work in FLOPs (floating-point operations): one per element of every elementwise op and size - result size per reduce. Divide the FLOPs by the kernel's time and you have your speed in FLOP/s. The oracle does the MNIST program's 0.17 GFLOP (a GFLOP is a billion FLOPs) in about 0.05 s. Week 6 grades only correctness and the time limits, but from here on these numbers are the scoreboard.

Write your 10 tests

Put 10 tests in <your compiler repo>/tests/week6/, each aimed at a rule someone will get wrong. This one catches an fdiv that divides:

%q = fdiv 5.0 3.0
%a = assert %q 1.6666667

The true quotient rounds to 1.6666666. Check your tests against the oracle:

python tools/test.py --check-tests <your compiler repo>/tests/week6 --week 6

With only that file there, it prints 1 / 1 tests agree with the oracle.

Good targets for your tests

Good targets: an exp2 result in the subnormal range, log2 on both sides of the 1.414 fold, sin of a negative number of turns, and a bitcast of a NaN made by arithmetic. For gradients, try a node used three times with values whose sum depends on the order, a gradient of a gradient, and an x that the loss reaches only through an i32 cast. Then a file whose size is off by one byte, and an in-place update whose render would be wrong if fused.

Check yourself

Why does the MNIST test check an accuracy threshold instead of every bit?

Is anything random in the program?

Nothing is random: the weights start at zero and the batches are fixed. The run tests check every rule bit for bit. The MNIST test checks that it all adds up to learning.

The update stores W - g into the buffer W was loaded from. Your renderer turns the store into a loop over 7840 elements. What can go wrong?

What does element 5000's gradient read?

The logits, which use every weight. The fix is to materialize the new values first and copy them in after, which is what the spec's semantics require: a store's value comes from the contents before it.

Your render of MNIST takes 60 seconds, but a 2-step version takes 0.1 s. What's the likely cause?

25 times more steps, 600 times more time.

That ratio is roughly quadratic (25² is 625). Typical culprits are a topological sort from each statement, or recomputing "which ranges are open" from scratch for every new node. Memoize, and share one "seen" set across walks.

The MNIST program does about 0.17 GFLOP. If the kernel takes 0.1 s, how many GFLOP/s is that?

Speed is work divided by time.

0.17 / 0.1 = 1.7 GFLOP/s. The oracle does it in about 0.05 s, so about 3.4 GFLOP/s, which is still far below what one CPU core can do. Later weeks close that gap.
