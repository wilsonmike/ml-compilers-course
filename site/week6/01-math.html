exp, log, sqrt and sin from adds and multiplies

By the end of week 6 your compiler trains a small neural network to read handwritten digits. That needs three things your language lacks: math functions like exp and log (this lesson), shorter ways to write common ops (lesson 6.2) and gradients, which tell training what to change (lessons 6.3 and 6.4). Here you build them from adds and multiplies.

Goal

Compute 2 to the power x with only adds and multiplies, and say how log2, sqrt and sin reuse the same two steps.

You'll use

f32 rounding (lesson 2.1), comparing results bit for bit (lesson 2.5) and a loop over a list (P.3)List.fold_left (O.3). For a slow look at a float's bits, see H.4.

The problem: a power with no power op

Your language has add, mul and a handful of others. A neural network needs e to the x. Start with a smaller version of the same puzzle: 20.5, which is 2 to the power one half.

Whole powers are easy. 23 is 2 · 2 · 2 = 8. But you cannot multiply 2 by itself half a time.

20 is 1 and 21 is 2. Guess 20.5 to one decimal place.

Powers add when you multiply, so 20.5 · 20.5 = 21 = 2. Which number times itself is closest to 2?

1.4, because 1.4 · 1.4 = 1.96. The full answer is 1.41421..., the square root of 2. Halfway between 1 and 2 would be 1.5, and that is too big.

You got there by trying numbers. A compiler needs a recipe. Here is one for x between -0.5 and 0.5, made only of adds and multiplies:

2^x ≈ 1 + 0.6931·x + 0.2402·x² + 0.0555·x³

A sum like this, fixed numbers times powers of x, is a polynomial. The fixed numbers are its coefficients. Try it at x = 0.5:

  1. Find the powers. x² = 0.25 and x³ = 0.125.
  2. Multiply. 0.6931 · 0.5 = 0.3466, 0.2402 · 0.25 = 0.0601, 0.0555 · 0.125 = 0.0069.
  3. Add. 1 + 0.3466 + 0.0601 + 0.0069 = 1.4136.

The true value is 1.4142. Each extra term gives more correct digits, and the spec uses eight. Where the coefficients come from is in the reference.

Horner's rule: one multiply and one add per term

Written out as above, the polynomial 1 + a·x + b·x² + c·x³ costs five multiplies: two to build x² and x³, then three more. The same polynomial can be regrouped:

1 + x·(a + x·(b + x·c))

How many multiplies does the regrouped form need?

Count the · signs. No power of x is built on its own.

Three, one per coefficient after the first. Fewer rounded steps also means less rounding error.

This regrouping is Horner's rule. Work from the inside out and keep one running value:

  1. Start. The running value is the coefficient of the highest power.
  2. Repeat. Multiply the running value by x, then add the next coefficient.

With coefficients 2, 3, 4 and x = 10 the running value goes 2, then 2 · 10 + 3 = 23, then 23 · 10 + 4 = 234. Every polynomial in the spec is written this way, as a chain of mul and add.

Repair Horner's rule

horner takes the coefficients, highest power first, and x. The starter forgets one of the two moves, so it only adds the coefficients up. Repair it.

A short polynomial only works close to zero

The four-term polynomial gave 1.4136 at x = 0.5. The true 210 is 1024. What do you think the same polynomial gives at x = 10?

Work it out: 1 + 0.6931 · 10 + 0.2402 · 100 + 0.0555 · 1000.

1 + 6.9 + 24.0 + 55.5 = 87.4. The coefficients fit near zero, and the error grows as x moves away. Even all eight terms only reach 624.

The fix is not a longer polynomial. It is a smaller input. Powers add when you multiply, so any power splits into a whole part and a small part. Take 23.3:

  1. Squeeze the input. The nearest whole number to 3.3 is n = 3. What is left is f = 3.3 - 3 = 0.3. The leftover is always between -0.5 and 0.5.
  2. Use the polynomial. 20.3 ≈ 1.2311. The input is small, so this is accurate.
  3. Put the whole part back. 23 = 8, and 8 · 1.2311 = 9.849. That is 23.3.

Squeezing the input into a small range first is called range reduction. That is the pattern for this lesson: range reduction, then a short polynomial.

The spec finds n as floor(x + 0.5). floor rounds down to a whole number, so floor(3.8) is 3.

For 25.7, what is n?

n = floor(5.7 + 0.5).

floor(6.2) is 6, so f = 5.7 - 6 = -0.3. A negative leftover is fine: 25.7 = 2-0.3 · 64 = 0.81225 · 64 = 51.98.

Watch exp2 run, then write it

The op for 2 to the x is called exp2. Step through the spec's version on 3.3. Each line is rounded to f32.

2 to the x, from the two steps

Write exp2 x. Two helpers are given. small f is the eight-term polynomial for 2f, accurate only for f between -0.5 and 0.5. pow2 n is 2n for a whole number n. Squeeze x into n and f, then combine the two helpers.

2 to a whole power comes straight from the bits

The last step multiplied by 2n. The spec gets that number with no multiplies at all, from the way an f32 is stored. Its 32 bits are a sign bit, an 8-bit exponent field E and a 23-bit mantissa M. The value is 1.M · 2^(E - 127). So 2n is the f32 with exponent field n + 127 and a mantissa of all zeros.

A new op gives you the bits. bitcast x dtype=i32 reads the 32 bits of an f32 as an integer, and bitcast n dtype=f32 goes the other way. Nothing is converted: the same bits are read as the other type. Step through a few numbers.

2^n from its bits

Write pow2 n for -126 ≤ n ≤ 127 by building the f32 bit pattern of 2^n and reading it as a float. No exponentiation allowed.

log2 and sin: the same two steps

Here is what two more functions are for, and how each one squeezes its input.

After that, each one is a short polynomial by Horner's rule. log2 runs exp2 backward: the exponent field hands it e for free. 12 is 1.5 · 2^3, so log2 12 = 3 + log2 1.5. If m is above 1.414 the spec halves it and adds 1 to e, which keeps m near 1.

A network's exp and log use e, about 2.718, in place of 2. Lesson 6.2 gets them from exp2 and log2 with one extra multiply.

For sin 100, the spec subtracts the nearest whole number of turns. 100 / 6.283 is 15.9. How many turns is that?

Nearest, as in exp2: floor(15.9 + 0.5).

16 turns. 100 - 16 · 6.283 is about -0.53, and sin -0.53 is the same as sin 100: about -0.506. The polynomial only ever sees a small input.

sqrt: a guess, then a better guess

sqrt x is the number that times itself gives x. It uses a different trick: start from a rough guess and improve it.

You guess that sqrt 9 is 2. Then 9 / 2 = 4.5. The true answer lies between your guess and that number. What is their average?

(2 + 4.5) / 2.

3.25, much closer to 3 than 2 was. Do it again from 3.25 and you get 3.0096.

If a guess y is too small, x / y is too big, so their average (y + x/y) / 2 is a better guess. This is one step of Newton's method, and each step roughly doubles the number of correct digits. The spec's sqrt is two moves:

  1. Guess. y = exp2(log2(x) / 2). Halving the power is a square root, as 20.5 showed. Two rounded functions leave this guess a few units in the last place off. One unit, an ulp, is the gap between an f32 and the next one.
  2. Improve. One Newton step, (y + x/y) / 2. Perfect squares come out exact: sqrt 16.0 is exactly 4.0.

In .uir all four are ordinary ops on f32 values of any shape: %r = sqrt %s.

The length of a vector

Slot 0 holds six f32. Store sqrt(x0² + ... + x5²) into slot 1. The starter stores the sum of squares.

Close is not equal

C already has expf, logf, sqrtf and sinf. Your compiler prints C. Why not call them?

Two machines run expf from two different C libraries on the same input. What can you count on?

Each library picks its own polynomial and its own range reduction.

Each C library computes these its own way, so the last bit can differ. The grader wants the same 32 bits everywhere.

So the spec gives one definition everyone can match: each math op is a specific program of core ops. Run exactly those steps and your bits match the oracle's on any machine.

Close is not equal

A better polynomial, a different reduction, or C's expf can all be more accurate than the spec, and they still fail the tests. Implement the steps exactly as written, in the order written.

Why build these at all, and the test that catches a compiler one bit off

Besides matching bits, there's a second reason to build the math ops from core ops. A GPU, or a small accelerator, often has no exp instruction at all. Knowing how to build one from multiplies is how compilers for such hardware work.

mismatch_exp2_bits_one_ulp_off asserts a value one ulp away from the right one, and its name says the right outcome is MISMATCH. A compiler that is one ulp off prints MATCH for it, and the test catches it.

Where the coefficients come from, and every coefficient, for when you type them in

Each polynomial is the start of a Taylor series: an endless sum of powers of x that equals the function, cut off after a few terms. For exp2, 2^f = e^(f ln 2) = Σ (f ln 2)^k / k!, so c_k = (ln 2)^k / k!. With |f| ≤ 0.5, eight terms (k = 0 to 7) give more precision than f32 can store. Horner's rule starts from the highest coefficient: c0 + f(c1 + f(c2 + ...)). That's one multiply and one add per term, and it's also more accurate than adding up powers.

The f32 layout in full: the bias, subnormals and bitcast of NaN, for when a tiny number comes out wrong

Every f32 is 32 bits: a sign bit, an 8-bit exponent field E, and a 23-bit mantissa M. For normal numbers the value is (-1)^sign · 1.M · 2^(E - 127). The 127 is a bias, so exponents from -126 to 127 fit in a field from 1 to 254. When the exponent field is 0, the number is subnormal: its value is (-1)^sign · 0.M · 2^-126. These are the tiny numbers below 2^-126, with fewer bits of precision.

There are millions of NaN bit patterns, and different hardware makes different ones (x86 produces a negative NaN for 0 · inf). bitcast of any NaN gives 0x7fc00000, so bitcast never exposes which NaN you had. In C, check isnan first, and read a float's bits with memcpy, not a pointer cast.

exp2 at the edges: NaN, the clamp and why 2^n is two factors, for when exp2 fails on huge or tiny inputs

2^n needs no arithmetic: it's the f32 with exponent field n + 127 and mantissa 0. Build the integer (n + 127) · 2^23 and bitcast it.

Two details make the edges right. First, NaN is caught before anything else, because the answer must be NaN, and casting NaN to i32 would quietly give 0. Second, x is clamped to [-150, 128]. 2^128 is already infinity in f32, and 2^-150 already rounds to 0, so clamping changes no answer and keeps n small. The bit trick (n + 127) · 2^23 only works for n from -126 to 127, and after the clamp n runs from -150 to 128. Below -126 the result is subnormal, and at 128 a single 2^128 would already be infinity even when the final result (say exp2 127.9) is finite. So the spec multiplies by 2^h and then 2^k, with h + k = n and both in [-75, 64], safely normal.

log2 in full: reading m and e from the bits, the series, subnormals and special cases

Bitcast x to an integer b. Its exponent field is b div 2^23, so e = b div 2^23 - 127. Its mantissa bits are b mod 2^23. Adding the bits of 1.0 (1065353216) gives the f32 with that mantissa and exponent 0, which is m, in [1, 2), with x = m · 2^e. So log2 x = e + log2 m.

A series for log2 m converges fastest when m is close to 1, so if m > 1.414 the spec halves it and adds 1 to e. Now m is in [0.707, 1.414]. With s = (m - 1) / (m + 1), |s| ≤ 0.172 and

log2 m = (2 / ln 2) · (s + s³/3 + s⁵/5 + s⁷/7 + s⁹/9 + ...)

Five terms give full f32 precision. A subnormal x has exponent field 0, so it's multiplied by 2^23 first and 23 is subtracted at the end. The special cases are checked at the end: zero gives -inf, a negative gives NaN, and inf and NaN pass through.

sin in full: 2π in two parts, the fold and the clamp, for when sin drifts on large inputs

sin repeats every 2π, so first subtract the nearest whole number of turns: k = floor(x / 2π + 0.5), then r = x - k · 2π. 2π isn't an f32, so the spec subtracts it in two parts: 6.28125, which is exact, and a small correction. Splitting the constant like this is called Cody-Waite reduction. The split keeps r accurate for x up to about 10,000.

Now r is in about [-π, π]. Since sin(π - r) = sin r, folding brings it to [-π/2, π/2], where the Taylor series r - r³/3! + r⁵/5! - ... up to r^13 is accurate. For a huge x, f32 can't even say which turn x is on, so the result is meaningless. The spec still clamps the folded value to [-π/2, π/2], so the result is always a number in [-1, 1].

Check yourself

What does bitcast 2.0 dtype=i32 give?

2.0 is 1.0 · 2^1: mantissa 0, exponent field 1 + 127.

Exponent field 128, shifted into place: 128 · 2^23 = 1073741824, which is 0x40000000.

For exp2 3.3, what are n and f?

n = floor(x + 0.5), the nearest integer.

floor(3.8) = 3, so f = 3.3 - 3, about 0.3 (exactly, the f32 nearest 3.3 minus 3). Then 2^3.3 = 2^0.3 · 8.

The spec's exp2 first limits x to the range [-150, 128]. Why is that safe?

What is 2^1000 in f32?

Every x above 128 gives inf and every x below -150 gives 0, so clamping is free. Without it, exp2 1e30 would cast 1e30 to i32, which saturates at 2147483647, and the bit trick would build nonsense from that.

12.0 is 1.5 · 2^3. After the spec's fold, what are m and e in log2?

Is 1.5 above 1.414?

1.5 is above the fold point, so m is halved to 0.75 and e goes up to 4: 12 = 0.75 · 2^4. Then log2 12 = 4 + log2 0.75, with m close to 1 so the series converges fast.

sqrt's first guess is 2^(log2(x) / 2). Why add a Newton step?

How accurate is a result built from two approximations?

Each of exp2 and log2 is within about 1.5 units, and their errors compound. Newton's method doubles the number of correct digits per step, so one step brings sqrt back to about 1 unit.

What is log2 -0.0?

Is -0.0 below zero? log2 0.0 is -inf, since no power of 2 reaches zero.

cmplt -0.0 0.0 is false: negative zero equals zero. So it isn't treated as negative (which would give nan), and the zero case gives -inf.

What does the grader compare against?

The oracle's result, bit for bit. A more accurate answer is a different answer. The spec defines sin as its program, not as "the true sine".
