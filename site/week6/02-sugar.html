Sugar: ops that are really several ops

By the end of this lesson you can give your language subtract, divide, exp, relu and five more ops by changing only the parser. A training program needs these ops on almost every line. Without them, every formula has to be spelled out the long way, which is slow to write and easy to get wrong.

What a formula costs today

A model gives two scores, a and b. How sure is it of the first one? The usual answer is one line of math:

p = exp(a) / (exp(a) + exp(b))

Here exp(x) means e^x, where e is about 2.718. Your language cannot say that line yet. It has exp2, which is 2^x, and no exp. It has no divide for floats either, only recip from week 2, which is 1/x. So you work around both. Since e^x = 2^(1.442695 · x), you scale first and then use exp2. To divide, you multiply by a recip:

%sa  = mul %a 1.442695
%ea  = exp2 %sa
%sb  = mul %b 1.442695
%eb  = exp2 %sb
%sum = add %ea %eb
%r   = recip %sum
%p   = mul %ea %r

Count the lines. How many lines of .uir did the one line of math take?

Count every line from %sa to %p.

Seven. Three of them, the two scaling multiplies and the recip, are there only because the language is missing an op. And if you type 1.442695 wrong once, the answer is wrong with no error message.

A training program is full of formulas like this one. With four short spellings the same program reads the way the math does:

%ea  = exp %a
%eb  = exp %b
%sum = add %ea %eb
%p   = fdiv %ea %sum

The rest of this lesson makes your compiler accept that version, and every part of it after the parser stays as it is.

Sugar: a short spelling the parser rewrites

Sugar is a short spelling that the parser rewrites, as it reads, into ops the compiler already understands. The name comes from "syntactic sugar": it makes programs sweeter to write and adds nothing new underneath. Week 6 adds nine sugar ops. Start with subtract, spelled sub.

Your parser reads %d = sub %a %b. Which core ops should it build so that %d is a - b?

It is the warm up again, with names in place of 10 and 4.

Flip the sign of b, then add it to a. Option c flips the wrong operand and gives b - a.

Here is what the parser does with that line:

  1. Spot the sugar. The op name is sub, which is on the sugar list.
  2. Build the core nodes. Make the node mul b -1, then the node add a of that. These are the nodes two hand-written lines would have made.
  3. Bind the name. %d now names the add node. No sub node was ever made.

So the type checker, the interpreter, rangeify and the renderer never see a sub. That is the point of sugar: nine new spellings, and no new cases anywhere past the parser. And because a sugar op is its expansion, the result matches the hand-written core ops bit for bit.

Sugar also handles shapes. In lesson 4.1 you wrote expand -1 [4] to subtract vectors. The parser now expands the constant to the operand's shape for you.

Now do the rewrite in code, on a small tree and not on the real parser. An expression is a literal, a name or an op with operands. The function desugar returns the same expression with every sugar op replaced. Float division is spelled fdiv, and fdiv a b means mul a (recip b).

floor: the 12-line program and its edge cases, for when you build it in the lab

floor needs a cast to i32 and back, which truncates toward zero. Below zero, truncation rounds up (-2.5 becomes -2), so a correction subtracts 1. Two edge cases shape the rest. Any f32 with |x| ≥ 2^23 is already a whole number, and casting a big one to i32 saturates at INT_MAX or INT_MIN, which is the wrong whole number, so those go around the cast. So do inf and NaN.

%x   = param [] slot=0 dtype=f32 addrspace=ALU
%nx  = mul %x -1.0
%ax  = max %x %nx
%lt  = cmplt %ax 8388608.0
%big = xor %lt true             # |x| >= 2^23, inf or nan: already an integer
%xc  = where %big 0.0 %x
%ti  = cast %xc dtype=i32       # truncates toward zero
%t   = cast %ti dtype=f32
%up  = cmplt %xc %t             # a negative number was truncated up
%t1  = add %t -1.0
%fl  = where %up %t1 %t
%r   = where %big %x %fl

exp2 and sin use floor internally, so this exact program sits inside both. And it's an example of a function that's defined everywhere and still has a quirk: floor -0.0 is +0.0 by this definition, where IEEE's own floor would keep the sign.

cmpeq, and why it is not defined on f32

Two integers are equal when neither is less than the other: where (cmplt a b) false (where (cmplt b a) false true). For bools, xor (xor a b) true. On f32 that trick breaks. NaN is neither less than nor greater than anything, so the formula would call NaN equal to everything. Rather than pick a rule for that, the spec leaves f32 out. Your parser has to reject cmpeq on f32 itself, because the expansion would pass the type checker. The lab uses cmpeq on integer labels, where it's exactly right.

Write the whole rewrite

Two more sugar ops come from lesson 6.1's math. You met the first in the opening program: exp x means exp2 (mul x 1.442695). The second runs the other way. log x, the logarithm with base e, means mul (log2 x) 0.6931472, a base 2 logarithm scaled by ln 2.

Notice the shape every expansion has had so far. A sugar op turns into a fixed pattern of core ops, with the desugared operands dropped into it. A core op stays what it is and desugars its operands.

Sugar means its expansion, rounding and all

A float op rounds its result to the nearest f32. Real division rounds once: 10 / 3 is the f32 nearest 3.333..., which is 3.3333333.

fdiv 10.0 3.0 means mul 10.0 (recip 3.0). How many times does it round?

Count the float ops in the expansion.

Twice: once for recip 3.0 and once for the multiply. The second rounding starts from a number that is already a little off.

So fdiv 10.0 3.0 lands one step higher, on 3.3333335. That is not a bug to fix. Sugar means its expansion and nothing else, so 3.3333335 is the right answer and the grader expects exactly those bits. The spec defines division this way because a reciprocal is cheaper than a divide on most hardware, and tinygrad does the same. It is also why div stays i32 only: week 2 made div on f32 a rejected program, and that test still has to pass.

The opening formula, with five scores in place of two, is called softmax: it turns scores into probabilities, numbers from 0 to 1 that add up to 1.

Softmax

Slot 0 holds five scores. Store softmax(x) into slot 1, exactly as: e = exp x, s = the sum of e, then fdiv e by s expanded to five elements. The starter stores exp x.

Why the next lesson gets easier

Next lesson your compiler learns to take a gradient: a number that says how much a program's result changes when one input changes a little. Training uses it to decide which way to step each weight. The gradient pass walks the graph and needs one rule for every kind of node it can meet there.

Sugar is expanded in the parser, before the gradient pass runs. How many of the nine sugar ops need a gradient rule of their own?

How many sub nodes are in the graph once the parser is done?

Zero. The pass never meets a sugar node, so it needs no rule for one. A sub is an add and a mul by then, and the rules for those two do the work.

This is what sugar buys you for the rest of the week. Autodiff only has to know the core ops and the four math ops, and sub, fdiv, relu, exp and matmul all get correct gradients for free.

The four math ops are different. They stay as ops until render, because their gradient rules need to see them whole. Taking the gradient of the polynomial inside exp2 would be both slower and less accurate.

Where to expand

Expand sugar in the parser, right where you build nodes. Keep exp2, log2, sqrt and sin as nodes through type checking and gradients, and expand them when you lower to run a program or to render it (or write a C function per op that performs exactly the spec's steps).

How exp and floor get their gradients, for after lesson 6.3

Lessons 6.3 and 6.4 differentiate programs. exp is exp2 of a scaled x, so its gradient is the exp2 rule (d/dx 2^x = 2^x ln 2) times the chain rule through the mul, and no "gradient of exp" rule is needed. The same goes for sub, fdiv, relu and matmul. floor's gradient is zero for |x| < 2^23, and that falls out too: its value goes through a cast to i32, and gradients don't flow through integers. (Bigger values go around the cast unchanged, so there the gradient is 1.)

What is sub -2147483648 1?

What does the expansion do on i32?

What does sugar mean?

Does exp need its own gradient rule?

What does the gradient pass see after parsing?

It only sees core ops and the four math ops. By then an exp is an exp2 and a mul, and the rules for those two do the work.

Why is cmpeq not defined on f32?

What is cmplt nan 1.0? And cmplt 1.0 nan?

Both are false, so "neither is less" holds, and the formula would say NaN equals 1.0. IEEE says NaN equals nothing, not even itself.

What is floor -2.5?

The cast truncates to -2. Is -2.5 < -2?

Truncation gave -2, which is above -2.5, so the correction subtracts 1: -3.0.

Why does floor skip the cast when |x| ≥ 2^23?

How many mantissa bits does an f32 have?

23. From 2^23 up, the spacing between f32s is 1 or more, so there's no fraction left to drop. Sending those around the cast keeps values like 1e10 from saturating to 2147483647.
