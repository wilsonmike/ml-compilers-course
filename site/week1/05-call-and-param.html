call, param, stack and index

You will be able to write a piece of a program once and use it many times, and to keep several values in one table and pick one out. Real models repeat the same work thousands of times, so a compiler needs a way to say "do that again, with these numbers".

Goal

Read, write and run programs that use call, param, stack and index, and say why each one is accepted or rejected.

You'll use

Three ideas from earlier lessons: the same line twice is one node (1.1), an evaluator remembers each node's value (1.2), and bounds say what range a value can be in (1.4).

The two coding exercises use a small type of your own with match (P.4) and a function that calls itself (P.5). If either is new, read that lesson first and come back.

A function is a graph with holes

A function is a piece of a program that you write once and use many times. In .uir a function is not a new kind of thing. It is a graph with a hole in it.

  • param makes a hole. Its slot=0 is the hole's number.
  • The body is the node whose value you want back. Above, the body is %f.
  • call fills the holes and gives back the body's value. Its first source is the body. The rest are the args (short for arguments): the first arg fills slot 0, the next fills slot 1 and so on. Every slot the body uses needs an arg, or the file is rejected.

Follow %r1 = call %f 3 by hand:

  1. Find the body. The first source is %f.
  2. Fill the holes. There is one arg, 3. It goes in slot 0, so %n is 3.
  3. Work out the body. 3 + 1 is 4. 4 × 4 is 16. 16 + 10 is 26.
  4. Hand the answer back. %r1 is 26.

Here is the body by itself, with 3 in the hole. Step through it.

Nothing marks %f as a function. It is an ordinary node that becomes a body when a call uses it as its first source. Every exercise so far worked this way: your %out was a body, and the page was the caller that filled the slots.

This body has two holes. What is %r?

%a = param [] slot=0 dtype=i32 addrspace=ALU
%b = param [] slot=1 dtype=i32 addrspace=ALU
%m = mul %b 10
%f = add %a %m
%r = call %f 4 7

The first arg after the body fills slot 0. The second fills slot 1. Which name is slot 1?

4 fills slot 0, so %a is 4. 7 fills slot 1, so %b is 7. Then 7 × 10 is 70, and 4 + 70 is 74.

A slot number belongs to the call that is running. Inside call %f 3, slot 0 means 3. Inside call %f 5 it means 5. In the next exercise, %x is slot 0 for the tests and %p is slot 0 for the body %f.

Two ways to run a call

The interpreter you have so far stops at %n: a param has no sources to work out and no number written in it. There are two ways to give it one, and they always agree.

Way 1: substitute, then evaluate

To substitute is to swap one thing for another. Build a copy of the body with every hole swapped for its arg. For call %f 3 that is add 3 1, then the mul, then the add of 10. No params are left, so the copy is a program you already know how to run, and it folds down to 26. It is exactly lines 1 to 3 of the long program this lesson started with.

Way 2: evaluate with an environment

In step 2 your interpreter kept an env, a place to look values up. A call gets one too. Its environment says which value each slot holds for this one call. No copy is built.

  1. Work out the args. For call %f 5 there is one, and it is 5.
  2. Make the environment. Slot 0 holds 5.
  3. Evaluate the body. It goes as always, except that a param looks up its slot in the environment.
  4. Drop the environment. The body's value is the call's value. The next call starts with a new one.

Here is the same body with 5 in the environment. The boxes and arrows are the same as before, and every value is different.

Substitution is the way to think about a call. An environment is the way most compilers run one, because it builds no new nodes.

You run call %f 5 with an environment. What happens when the evaluator reaches %n?

Which of the two ways builds new nodes, and which one looks things up?

The environment holds one value per slot for the call that is running. The body is not changed at all, so the next call can use it again with a different number.

The value cache must be per call

In lesson 1.2 your evaluator kept a cache: a table from node to value, so that no node is worked out twice. Now suppose that one cache lives for the whole program, and you run this again:

%r1  = call %f 3
%r2  = call %f 5
%out = add %r1 %r2

The right answer is 72. What does an evaluator with one cache for the whole program give for %out?

The first call works out %f and saves 26 for that node. What does the second call find when it asks for %f?

52. The first call saves "%f is 26". The second call asks for %f, finds 26 in the cache and never looks at the 5. So it adds 26 and 26.

The cache was safe in lesson 1.2 because a node had one value, forever. A node in a body has one value per call. So each call gets two fresh things: its environment and its own empty cache. Inside one call the cache still saves work. When the call ends, both are dropped.

Params are hash consed too

Two param lines with the same slot and dtype are the same node (lesson 1.1), even when they're written for two different functions. That's fine: a param has no value of its own. Its value comes from whichever call is evaluating it right now.

A call inside a body

A body can call another body. Then two calls are running at once, and each has its own slot 0. Guess which one wins here. %inner multiplies its slot 0 by 10. %outer has two slots and hands its slot 1 to %inner.

%p0    = param [] slot=0 dtype=i32 addrspace=ALU
%p1    = param [] slot=1 dtype=i32 addrspace=ALU
%inner = mul %p0 10
%outer = call %inner %p1
%r     = call %outer 3 4

What is %r?

The last line gives %outer slot 0 = 3 and slot 1 = 4. Which of those does %outer pass on as the arg of call %inner?

%outer passes its slot 1, which is 4, into %inner's slot 0. Inside %inner, slot 0 means 4. The 3 belongs to %outer and is never used.

Bodies are closed

Closed means nothing gets in from outside except through the args. Substitution walks the body, but it does not walk into the body (src 0) of a nested call. It does walk into that call's args.

With an environment the rule takes care of itself. The inner call works out its args with the outer environment, then runs its body with a new environment that holds only those args.

Here is the bug the rule prevents. Inner adds 100 to its slot 0, and outer passes its slot 1:

%p0    = param [] slot=0 dtype=i32 addrspace=ALU
%p1    = param [] slot=1 dtype=i32 addrspace=ALU
%inner = add %p0 100
%outer = call %inner %p1      # inner's slot 0 := outer's slot 1
%r     = call %outer 1 2      # outer: slot 0 := 1, slot 1 := 2

Done right, outer substitutes into its args only: call %inner 2, which gives 102. A substitution that wrongly walked into inner's body would turn inner's %p0 into 1 and get 101. The reference traces a nested call one step at a time.

Limits: a promise every call must keep

Lesson 1.4 showed a param with limits, like the [0 5] here:

%k = param [] [0 5] slot=0 dtype=i32 addrspace=ALU
%f = add %k 1

The limits are a promise: every value put in this hole is from 0 to 5. The body's bounds are built on that promise, so somebody has to keep it.

Which call makes the file REJECTED?

The limits include both ends. Which arg is outside 0 to 5?

6 breaks the promise, so the file is rejected before anything runs. 0 and 5 are the two ends of the limits, and the ends are allowed.

The check uses bounds, not the value that happens to arrive: the arg's bounds must sit inside the param's limits. A literal 6 has bounds [6, 6], which is not inside [0, 5]. A param with no limits allows every i32.

When the arg is itself a param of an outer body, its bounds are its own limits. An outer [0, 3] fits an inner [0, 5]. An outer [0, 9] does not, even if the call that runs passes 2.

stack: several values in one

Every value so far has been one number. Suppose a body should give 7, 8 or 9 depending on whether %k is 0, 1 or 2. With cmplt and where, that is a chain that grows with every entry. What you want is a table: write the numbers in a row and pick one by its position.

%s = stack 10 20 30
%r = index %s 1

Positions are counted from 0, so %r is 20. Try each position:

%s = stack 10 20 30, then %r = index %s i
i =
Shape (3,), so the valid indices are 0, 1 and 2. Try -1 and 3.

stack takes scalars of one dtype and adds a new leading axis: stack 10 20 30 has shape (3,), a shape with one axis of size 3. The bracket form [10 20 30] builds the very same node. index x i pops that axis back off and returns one element as a scalar. The elements can be any scalars, not only literals: stack %a %b %c makes a table of three params.

An index has to be proven in range

In the figure, positions -1 and 3 do not exist. With a literal index that is easy to see. Here the index is a param, and the one call in the file passes 1, a position that does exist.

%i = param [] slot=0 dtype=i32 addrspace=ALU
%f = index [10 20 30] %i
%r = call %f 1
%t = assert %r 20

What does ./compile print for this file?

%i has no limits. What are its bounds, and do they fit inside 0 to 2?

REJECTED. The check does not ask "is this call's index fine?". It asks "is every index this node could ever have fine?". %i has no limits, so it could be any i32.

Your compiler promises that a program it accepts can never go wrong while it runs. So, as lesson 1.4 said, the index is checked once, before anything runs: for a stack of n elements, the bounds of the index must sit inside [0, n - 1], or the file is REJECTED.

There are two usual ways to make the proof work. Give the param limits, such as [0 2] for a table of three. Or compute the index with an op whose bounds are narrow: mod %j 3 is always 0, 1 or 2, whatever %j is, and its bounds say so.

Every part of a param line, for when you parse and check one

Writing a param

%x = param [] [0 9] slot=0 dtype=i32 addrspace=ALU
  • The shape, [], is the first source. It means a scalar, and week 1 requires it. Later weeks write things like [3] here.
  • The limits, [0 9], are an optional second source: two literals of the param's dtype, low first. They promise every argument is in [0, 9]. Leave them out and the param is the full range (for a bool, [0, 1]).
  • The attributes: slot=k (a plain decimal number), dtype=i32 or dtype=bool, and addrspace=ALU, which every week 1 value has. All three are required.

The limits are checked at every call, with the bounds from lesson 4. An argument's bounds must fit inside its param's limits. call %body 5 fits [0, 9], and call %body 10 is rejected. When the argument is an outer param, it brings its own limits: an outer [0, 3] fits an inner [0, 5], but an outer [0, 9] doesn't, even if the call that runs passes 2. An outer param with no limits is the full i32 range, so it doesn't fit an inner param with narrower limits.

What a call checks about its args, for when you write the validator 
%x    = param [] slot=0 dtype=i32 addrspace=ALU     # hole number 0, holds an i32
%body = add %x 1              # a graph with a hole: "x + 1"
%r    = call %body 41         # fill hole 0 with 41 and evaluate
%t    = assert %r 42

call's first source is the body. The rest are the args: arg i fills the slot i param reachable from the body. Args are checked statically. A missing arg, or one with the wrong dtype or shape, makes the file REJECTED. Extra args and unused slots are allowed. An extra arg is still a source of the call, so it counts as reachable from the assert.

A body is just an ordinary UOp. Nothing marks %body as "a function". It becomes one when a call uses it as src 0. In the traced graph in this reference, that src 0 edge is drawn dashed. In week 1 the body and every arg are scalars: a call takes numbers and returns a number.

The slots a body uses are the params you can reach from the body without walking into the body of a nested call. That is the closed-body rule again: a nested call's params are filled by its own args.

Every way this lesson's ops get a file rejected, for when a rejected_ test fails

Rejected before anything runs

These are static errors. Each makes the file REJECTED:

  • Two different param nodes for one slot in one body, like add %a %c where %a is a slot 0 i32 param and %c casts a slot 0 bool param. Each slot a body uses has exactly one param node: one dtype, one shape, one set of limits. The same slot can mean different things in different bodies.
  • A param shape other than [], limits written high first like [9 0], or limits of the wrong dtype.
  • A call whose body or args aren't scalars, or whose args don't fit their params' limits.
  • A body nothing calls. Every node must be reachable from the assert, so a function you define and never use is rejected too.

Two more. A param only has a value inside a call, so a param the assert can reach without going through a call body makes the file REJECTED. It's caught before anything runs. And an index is checked by its bounds: every value the index could have must be in [0, n - 1].

What a call costs, for when you add up static cost

Lesson 1.1 said a call costs 1 plus the cost of its body. The body's cost is the same sum you already know, taken over the distinct nodes reachable from the body. Walk into a nested call's args but not into its body, because that call charges for its own body.

%x = param [] slot=0 dtype=i32 addrspace=ALU
%s = add %x %x
%v = call %s 3
%t = assert %v 6

This file costs 3. The call is 1. Its body is the add, which costs 1, plus the param's [], which costs 1. The param and the literals cost 0. Limits like [0 9] are a stack of two elements, so they add 2 more. A stack of n scalars costs n and an index costs 1.

Two different call nodes with the same body each pay for the body. That is how a small file can have a large cost: sharing a body saves lines, not work.

A nested call traced one step at a time, for when your substitution gives the wrong answer

Filling a function's holes with its args has an old name, beta reduction. Here is the spec's nested example, traced one step at a time. %inner doubles its param. %outer passes its own slot 0 param into inner's slot 0. In the picture, the edge from a body into the call that uses it is dashed.

%p0    = param [] slot=0 dtype=i32 addrspace=ALU
%inner = mul %p0 2
%outer = call %inner %p0
%r     = call %outer 5
%t     = assert %r 10
Calls and the simplifier: inlining, for the lab's last simplify tests

A call has no side effects (it's pure): it gives back a value and changes nothing else. So the simplifier can always inline it: replace the call with its body, params substituted, then keep folding. That works whether the args are constants or params. call %body 41 with %body = add %x 1 simplifies all the way to 42.

Where the idea comes from: the lambda calculus (optional)

The lambda calculus in one paragraph

In the 1930s Alonzo Church showed that a language with only three things (variables, function definitions and function application) can express any computation. Evaluation is one move, beta reduction: to apply a function, replace its variable with the argument everywhere it appears. In math notation, λx. x + 1 is "the function taking x to x + 1". Applying it to 41, written (λx. x + 1) 41, becomes 41 + 1. That's exactly what call does to a graph.
