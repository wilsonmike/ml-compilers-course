Week 1 · Lesson 5

call, param, stack and index

Week 1 programs can define functions. A function is just a graph with holes in it: param marks a hole, and call fills the holes and evaluates the graph.

The lambda calculus in one paragraph

In the 1930s Alonzo Church showed that a language with only three things (variables, function definitions and function application) can express any computation. Evaluation is one move, beta reduction: to apply a function, replace its variable with the argument everywhere it appears. In math notation, λx. x + 1 is "the function taking x to x + 1". Applying it to 41, written (λx. x + 1) 41, becomes 41 + 1. That's exactly what call does to a graph.

param and call

%x    = param [] slot=0 dtype=i32 addrspace=ALU     # hole number 0, holds an i32
%body = add %x 1              # a graph with a hole: "x + 1"
%r    = call %body 41         # fill hole 0 with 41 and evaluate
%t    = assert %r 42

call's first source is the body. The rest are the args: arg i fills the slot i param reachable from the body. Args are checked statically. A missing arg, or one with the wrong dtype or shape, makes the file REJECTED. Extra args and unused slots are allowed. An extra arg is still a source of the call, so it counts as reachable from the assert.

A body is just an ordinary UOp. Nothing marks %body as "a function". It becomes one when a call uses it as src 0. In the graphs below, that src 0 edge is drawn dashed. In week 1 the body and every arg are scalars: a call takes numbers and returns a number.

Writing a param

%x = param [] [0 9] slot=0 dtype=i32 addrspace=ALU
  • The shape, [], is the first source. It means a scalar, and week 1 requires it. Later weeks write things like [3] here.
  • The limits, [0 9], are an optional second source: two literals of the param's dtype, low first. They promise every argument is in [0, 9]. Leave them out and the param is the full range (for a bool, [0, 1]).
  • The attributes: slot=k (a plain decimal number), dtype=i32 or dtype=bool, and addrspace=ALU, which every week 1 value has. All three are required.

The limits are checked at every call, with the bounds from lesson 4. An argument's bounds must fit inside its param's limits. call %body 5 fits [0, 9], and call %body 10 is rejected. When the argument is an outer param, it brings its own limits: an outer [0, 3] fits an inner [0, 5], but an outer [0, 9] doesn't, even if the call that runs passes 2. An outer param with no limits is the full i32 range, so it doesn't fit an inner param with narrower limits.

Beta reduction on a graph

The spec's nested example, traced. %inner doubles its param. %outer passes its own slot 0 param into inner's slot 0.

%p0    = param [] slot=0 dtype=i32 addrspace=ALU
%inner = mul %p0 2
%outer = call %inner %p0
%r     = call %outer 5
%t     = assert %r 10
Bodies are closed

Substitution walks the body, but it does not walk into the body (src 0) of a nested call. It does walk into that call's args. A nested function's params belong to that function, and the only way to give them a value is through its args.

Why does this matter? Look at this variant, where inner uses slot 0 and outer passes its slot 1:

%p0    = param [] slot=0 dtype=i32 addrspace=ALU
%p1    = param [] slot=1 dtype=i32 addrspace=ALU
%inner = add %p0 100
%outer = call %inner %p1      # inner's slot 0 := outer's slot 1
%r     = call %outer 1 2      # outer: slot 0 := 1, slot 1 := 2

Done right, outer substitutes into its args only: call %inner 2, which gives 2 + 100 = 102. If your substitution wrongly walked into inner's body too, it would turn inner's %p0 into 1 (outer's slot 0) and get 101.

Substitution with closed bodies

Here is a toy term language with numbers, params, Add, and Call (body, args). Write subst args t: replace every Param i reachable from t with the i-th element of args.

  • A nested Call's body is closed: leave it exactly as it is.
  • Its args are not: substitute inside them.
  • If there is no i-th arg, leave Param i alone.

This is the 101 vs 102 bug from above, on a type small enough to see in one screen. Keep the given show function, because the tests print with it.

Params are hash consed too

%a = param [] slot=0 dtype=i32 addrspace=ALU and %b = param [] slot=0 dtype=i32 addrspace=ALU are the same UOp, even when they're written for two different functions. That's fine: a param doesn't have a value on its own. Its value comes from whichever call is evaluating it right now. So never cache "the value of this node" globally. Cache it per call.

Substitution, as traced above, is the mental model. The usual implementation doesn't build new nodes: it evaluates the body with an environment, a map from slot number to value for the current call, and a fresh cache for that call.

Two more rules. A param only has a value inside a call, so a param the assert can reach without going through a call body makes the file REJECTED. It's caught before anything runs. And a call has no side effects (it's pure), so the simplifier can always inline it: replace the call with its body, params substituted, then keep folding. That works whether the args are constants or params. call %body 41 with %body = add %x 1 simplifies all the way to 42.

stack and index: rank 1

stack takes scalars of one dtype and adds a new leading axis: stack 10 20 30 has shape (3,), a shape with one axis of size 3. The bracket form [10 20 30] builds the very same node. index x i pops that axis back off and returns one element as a scalar. The index is checked before anything runs, by its bounds (lesson 4): every value the index could have must be in [0, n - 1], or the file is REJECTED.

%s = stack 10 20 30, then %r = index %s i
i =
Shape (3,), so the valid indices are 0, 1 and 2. Try -1 and 3.

ALU ops only take rank-0 operands, and in week 1 a call's args and result are scalars too, so a rank-1 value can only be indexed. A typical week 1 use is a small table inside a body, read at a limited index:

%k = param [] [0 2] slot=0 dtype=i32 addrspace=ALU
%f = index [7 8 9] %k
%r = call %f 1             # 8

Params with a shape like [3], vector args and vector asserts arrive in week 2.

Rejected before anything runs

These are static errors. Each makes the file REJECTED:

  • Two different param nodes for one slot in one body, like add %a %c where %a is a slot 0 i32 param and %c casts a slot 0 bool param. Each slot a body uses has exactly one param node: one dtype, one shape, one set of limits. The same slot can mean different things in different bodies.
  • A param shape other than [], limits written high first like [9 0], or limits of the wrong dtype.
  • A call whose body or args aren't scalars, or whose args don't fit their params' limits.
  • A body nothing calls. Every node must be reachable from the assert, so a function you define and never use is rejected too.

Rotate with stack and index

Params a, b, c and i are i32. Stack a b c. Compute j = i + 1 with i32 add (so INT_MAX + 1 wraps to INT_MIN), then return the element at position j mod 3. For example, i = 0 gives b and i = 2 gives a.

The tests include i = 300, i = -2 and i = INT_MAX. Because mod floors, j mod 3 is always 0, 1 or 2, even for a negative j, and its bounds say so. That's what makes the index valid, with no fixing up.

Check yourself

Predict %r.

%p0    = param [] slot=0 dtype=i32 addrspace=ALU
%p1    = param [] slot=1 dtype=i32 addrspace=ALU
%inner = add %p0 100
%outer = call %inner %p1
%r     = call %outer 1 2

Outer's call binds outer's slots: p0 = 1, p1 = 2. Which of those does outer hand to inner's slot 0?

102. Outer's slot 1 (which is 2) fills inner's slot 0. Inner's body is never touched by outer's substitution.

Predict %r. Careful with the closed-body rule.

%p0    = param [] slot=0 dtype=i32 addrspace=ALU
%inc   = add %p0 1
%twice = call %inc %inc
%r     = call %twice 5

%inc appears twice in call %inc %inc: once as the body and once as the arg. Substitution goes into args but never into bodies.

Evaluate the arg first: %inc with p0 = 5. Then run the body %inc on that result.

7. Calling %twice with 5 substitutes into its arg, %inc, giving 6. The body %inc is left alone. Then call %inc 6 gives 7. The same node is used once as a body and once as an arg, and the two roles never mix.

%t    = assert %r 11

The literal 10 has bounds [10, 10]. Do they fit inside the param's limits?

The limits promise every argument is in [0, 9], and 10 breaks the promise. A call whose argument's bounds don't fit is rejected, even though the arithmetic would work.

What does ./compile print for %x = param [] slot=0 dtype=i32 addrspace=ALU followed by %t = assert %x 1?

Is there any call around this param to give slot 0 a value?

There's no call supplying slot 0, so %x has no value. That's visible from the graph alone, so the file is rejected before anything runs.
