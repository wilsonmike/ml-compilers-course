Week 1 · Lesson 6

The week 1 lab

Build a compiler that parses .uir, checks it, runs it and simplifies it. Write it in your own repo, in the language you picked in the sidebar. You're done when every week 1 test passes and you've written 10 tests of your own.

What you're building

  • A parser for the .uir tokens and grammar in spec/uir-week1.md: definitions, names, ops, decimal and hex literals, brackets and key=value attributes.
  • Hash-consed UOps. One constructor that returns the existing node whenever the same (op, src, arg), where dtype and shape are part of the key, was built before. Everything else depends on this.
  • A validator that gives every node a dtype, a shape and bounds, checks index safety, call arguments, limits and the test-file rules, and says REJECTED before anything runs. Around it, the budgets: bytes, nodes and edges, and static cost, each one OVERBUDGET.
  • A memoized interpreter that evaluates the assert, with i32 wrapping, floor div and mod, shifts by y mod 32 and per-call evaluation for call/param.
  • A rewrite-based simplifier: a sources-first rewrite engine run to a fixpoint, with constant folding, canonicalization, identities and bounds-powered rules.

Warm up

Five minutes in .uir before the big build. It makes you use floor div and mod exactly as your interpreter will have to.

C's division from floor division

div floors, so div -7 2 is -4. C's / truncates toward zero, so -7 / 2 is -3 in C. You'll render C in week 2, so it pays to know exactly where they differ. Build C's truncating division as %out for i32 params a and b (b is never 0) from div, mod, cmplt, xor, where and add.

The two only differ when the remainder is nonzero and a and b have opposite signs. Then truncation is one higher.

The command-line contract

The official course runs your compiler as ./compile FILE.... Yours can have any name: the grader takes its path. What the grader reads is your stdout, one line per file. The exit code and stderr aren't graded, so print whatever diagnosis helps you on stderr. A crash is not an answer: an uncaught exception (Fatal error: exception ...a Python traceback) prints no outcome line, and the test fails.

commandresult
./compile FILE...For each file, print one line to stdout: MATCH, MISMATCH, REJECTED or OVERBUDGET, one space, and the path exactly as it was given. Decide in the spec's order and stop at the first outcome: over 4096 bytes, then parse, then 100 nodes or 300 edges, then validation, then a static cost of 1,000,000, then run. The grader runs one test at a time, copied to a file named case.uir.
./compile simplify FILEPrint a valid .uir program to stdout that defines %out with the same dtype and shape, and computes the same value for every input inside the params' limits, then exit 0. It's graded on equivalence (every edge value in every param slot, plus random values) and on an op budget, max_ops, counted on the op bindings you print: duplicate bindings count twice, so hash cons your output.

Running the suite

Stuck on a failing test? The week 1 test guide says what each test checks and which bugs make it fail, and the week 1 study guide has a cheat sheet and a step-by-step way out.

Two tools, two jobs. python tools/serve.py serves these lessons and grades the in-lesson exercises like the one above. tools/test.py grades your compiler against the week's suite. Run these from the root of the course repo:

python tools/test.py --compiler "C:/path/to/your.exe" --week 1
python tools/test.py --compiler "C:/path/to/your.exe" --week 1 -k div     # only tests whose name contains "div"
python tools/test.py --compiler "C:/path/to/your.exe" --week 1 -v         # show what differed
python tools/test.py --compiler "C:/path/to/your.exe" --week 1 --jobs 1   # one test at a time
python _reference/uirc.py --week=1 FILE...                                 # the oracle's outcome for any file

Pass the built executable (for dune, _build/default/bin/main.exe), not dune exec: the suite runs tests in parallel, and parallel dune exec calls fight over dune's build lock.

Pass your wrapper from lesson 0.7: C:/path/to/my-ml-compiler/mlc.cmd on Windows, or the executable mlc script on macOS and Linux. The runner calls it as mlc.cmd FILE and mlc.cmd simplify FILE from the course repo, so the wrapper must find your package from any folder.

Tests live in tests/week1/run/ and tests/week1/simplify/, and you should read them. Each one is a small, readable .uir file whose first comment says what it checks.

Write your 10 tests

The official course has students hand in tests every week, and grades them on how many other students' compilers they catch: a test that every compiler passes earns nothing. Do the same: put 10 in <your compiler repo>/tests/week1/, one .uir file each, following the test-file rules from lesson 2. A test ends with one assert, its expected side is written as a literal, every node is reachable from the assert, and the file name says the outcome. Here's mismatch_div_is_not_c.uir:

%a = div -7 2
%t = assert %a -3

.uir's div -7 2 is -4, so the right answer is MISMATCH. A compiler that divides like C prints MATCH, and your test catches it. A simplify test has no assert, defines %out, and starts with # simplify: max_ops=N. Then check them against the oracle. --check-tests confirms each file name's outcome, and for simplify tests it checks that the oracle's own simplifier reaches your max_ops, so you can't write an impossible target:

python tools/test.py --check-tests <your compiler repo>/tests/week1 --week 1

A good test targets one rule you think someone (maybe you) will get wrong: div INT_MIN -1, mod bounds when both ends have the same quotient, a nested call that reuses slot 0, limits that are one too wide for an index, a file of exactly 4096 bytes.

A build order that works

Start small. Your first goal is the two simplest tests: tests/week1/run/basic_add.uir should print MATCH and mismatch_basic.uir should print MISMATCH. After that, run the whole suite after every step below. Most tests fail at first, and that's expected: each checkpoint says which ones should pass by then.

  1. Set up your repo

    Make a new folder outside the course repo, then git init inside it. Run dune init project mlc there (lesson 0.6 shows dune).Add the mlc package and the wrapper script from lesson 0.7. Copy templates/AGENTS.md from the course repo into your repo's root: it tells an AI assistant to explain and ask questions but never write your compiler code.

    Checkpoint: dune build succeeds and _build/default/bin/main.exe runs.

    Checkpoint: running the wrapper from the course repo's folder prints your usage message and exits 2.

  2. Parse and print

    Split the file into tokens, then group them into bindings with the grammar. Remember that a newline is just whitespace and %x= is one token. Print each binding back in .uir form and check it matches the input, ignoring spacing and comments. Count bytes before you parse, and nodes and edges right after.

    Checkpoint: every file in tests/week1/run/ parses or is REJECTED, none crash, and the overbudget_bytes, overbudget_nodes and overbudget_edges tests pass.

  3. The hash-consed UOp

    One table keyed on (op, src, arg), with dtype and shape as part of the key. Sources are already unique, so compare them by identity. In OCaml, == is physical equality and = is structural.In Python, is is identity, and == on a dataclass compares every field. Know which one you're using. [1 2] and stack 1 2 must come out as one node.

    Checkpoint: building add x 1 twice returns the same physical node.

  4. Types and test-file rules

    dtype and shape for every op, following the table in the spec. No implicit conversions. Then the test-file rules: one final assert, a literal expected side, a scalar left side, every node reachable.

    Checkpoint: the rejected_ tests about dtypes, shapes, attributes and asserts pass.

  5. Interpreter

    Evaluate the assert, with each node computed once. Look up how to do 32-bit wrapping arithmetic in your language (OCaml's native int is 63 bits)(Python ints never overflow), and check your division against the floor table in lesson 2, zero divisors included. A deep chain of nodes will hit Python's recursion limit, so walk it with your own stack or raise the limit.

    Checkpoint: the arithmetic tests pass, and dag_sharing finishes in milliseconds.

  6. call and param

    Evaluate a body with an environment (a map from slot number to value for the current call). Keep the memo per call. Bodies are closed. Check that each used slot has one param node and an arg of the right dtype, and reject a param outside any call.

    Checkpoint: the call_ tests pass, including the ones that reuse slot 0.

  7. Bounds and cost

    Give every node bounds with the rules in spec section 5, exactly as written. Reject an index whose bounds don't fit its axis, and a call whose args don't fit their params' limits. Then add up the static cost.

    Checkpoint: the bounds_, limits_, rejected_bounds_, rejected_limits_ and cost tests pass.

  8. The rewrite engine

    A sources-first pass that tries rules at each node, repeated until nothing changes. Start with constant folding, using the same op semantics as the interpreter, then add canonicalization.

    Checkpoint: the folding simplify tests pass their max_ops.

  9. Symbolic rules and bounds

    i32 identities, call inlining, then the rules that bounds and limits power.

    Checkpoint: every simplify test passes, including the ones designed to catch (x * 2) / 2 and x mod 8 → x with limits that are one too wide.

  10. Your 10 tests

    Write them, and check them with --check-tests. Then try to break your own compiler with them.

Checklist

The AI policy

Your compiler is yours to write. In your repo (my-ml-compiler), the AGENTS.md says an AI assistant may explain concepts, draw diagrams and help you debug by asking questions, but must never write or rewrite compiler code. That's in the spirit of the original course's "slop management" theme. The point is the understanding, and you only get it by typing it yourself.

The reference compiler lives in _reference/ in the course repo. The test runner uses it as the oracle, and running it is fine. Never open it. It's written in Python, not OCaml, so a stray glance hands you less, but it would still spoil the puzzles.It's written in Python, like your compiler, so even a stray glance would hand you answers and spoil the puzzles.

Slop compounds

Every later week builds on this code: loads and stores in week 2, loops in week 3, rangeify in week 4. A sloppy UOp type or a simplifier that is "mostly right" will cost you far more later than it saves now. Keep it small, keep it readable and delete anything you don't understand.

Check yourself

What outcome should your compiler print for this file? Just the outcome word.

%t = assert 2 3

The file is valid and tiny. It runs, and then the two sides are compared.

MISMATCH: a valid program whose values differ. As a course test it would be named mismatch_something.uir.

And this one?

%a = add 1 1.0
%t = assert %a 2

What dtypes does week 1 have?

REJECTED. Week 1 is i32 and bool only, so 1.0 isn't a valid literal yet. Even in week 2, adding an i32 to an f32 is a type error, because there's no implicit conversion.

You wrote a test your compiler should refuse to run. What must its file name start with?

The expected outcome lives in the file name. There's one prefix per outcome except MATCH.

rejected_. The other prefixes are mismatch_ and overbudget_, and a name with none of them expects MATCH.

You're stuck on a failing nested-call test. What can an AI assistant do in your compiler repo?

Look back at the AI policy in your repo's AGENTS.md: explaining is allowed, writing your compiler code is not.

Explaining, drawing and asking questions are all fine. Writing or rewriting compiler code isn't, and neither is copying from the reference.
