Lab: your compiler

You start with a compiler that prints one fixed line and grow it one small, tested step at a time. When the lab is done, your compiler reads a .uir file, refuses a broken one, runs a good one and makes a program smaller without changing what it computes.

Goal

Pass all 282 week 1 tests with a compiler you wrote in your own repository, and write 10 tests of your own.

Warm up

Two questions from this week, from memory. Pulling an idea back out of your head is what makes it stay.

A test file is 5000 bytes long, and one of its lines adds an i32 to a bool. What does your compiler print for it?

Lesson 1.2: which check comes before parsing?

A file over 4096 bytes is refused before it is parsed, so the type error is never seen. Your compiler has to make its checks in that same order.

%x is a param with limits [0 8]. May a simplifier replace mod %x 8 with %x?

Lesson 1.4: try the largest value the limits allow.

8 is allowed, and mod 8 8 is 0, not 8. Limits of [0 7] would make the rule safe. One of the lab's tests checks exactly this.

What you are building

One program with two commands. The course calls it compile.

  • compile FILE judges a test file. It prints one line: MATCH, MISMATCH, REJECTED or OVERBUDGET, then one space, then the path exactly as it was given.
  • compile simplify FILE prints a smaller .uir program that computes the same %out.

Inside are five pieces: a parser, a node table that never builds the same node twice, a validator that says REJECTED before anything runs, an interpreter and a simplifier.

The grader reads only what your program prints on stdout, the normal output. A crash prints no outcome line, so that test fails.

The grader runs compile tests/a.uir, and the assert's two sides are equal. What must your compiler print?

The outcome word comes first, then one space, then the path.

The path is printed back exactly as it came in. The grader copies each test to a file named case.uir first, so the file name tells your compiler nothing.

The full command-line contract, for when the grader and you disagree about output

The official course runs your compiler as ./compile FILE.... Yours can have any name: the grader takes its path. What the grader reads is your stdout, one line per file. The exit code and stderr aren't graded, so print whatever diagnosis helps you on stderr. A crash is not an answer: an uncaught exception (Fatal error: exception ...a Python traceback) prints no outcome line, and the test fails.

The grader runs one test at a time, copied to a file named case.uir.
./compile simplify FILEPrint a valid .uir program to stdout that defines %out with the same dtype and shape, and computes the same value for every input inside the params' limits, then exit 0. It's graded on equivalence (every edge value in every param slot, plus random values) and on an op budget, max_ops, counted on the op bindings you print: duplicate bindings count twice, so hash cons your output.

The language contract is spec/uir-week1.md. If this page and the spec disagree, the spec wins.

A repository and a compile that says MATCH

Set up the folder, the project and git from nothing

A repository is a folder that the tool git watches. Each time you commit, git saves a snapshot of the folder, so you can always get back to a version that worked.

  1. Make the folder. In a terminal, outside the course repo: 
    mkdir my-ml-compiler
cd my-ml-compiler
git init
  2. Make the project. Run dune init project mlc . in that folder. The dot means "right here". You get bin/main.ml, lib/ and test/.
  3. Make the package. Make a folder named mlc inside it, with an empty file mlc/__init__.py.
  4. Write the whole compiler, for now. Replace everything in bin/main.ml with this.Save this as mlc/__main__.py. It prints MATCH and the path for every file it is given, and never opens one. 
    let () =
  for i = 1 to Array.length Sys.argv - 1 do
    print_endline ("MATCH " ^ Sys.argv.(i))
  done
    import sys

for path in sys.argv[1:]:
    print("MATCH", path)
  5. Tell git what to skip. Make a file named .gitignore with one line: _build/__pycache__/.
  6. Copy the AI rules. Copy templates/AGENTS.md from the course repo into your folder. It tells an AI assistant to explain and ask questions but never write your compiler code.
  7. Write the wrapper. On Windows, save these three lines as mlc.cmd in my-ml-compiler, next to the mlc folder: 
    @echo off
set "PYTHONPATH=%~dp0"
python -m mlc %*
    On macOS and Linux, save these two lines as compile in the same place and run chmod +x compile once: 
    #!/bin/sh
PYTHONPATH="$(dirname "$0")" exec python3 -m mlc "$@"

From inside my-ml-compiler, run your compiler by hand (on macOS and Linux, type python3):

dune build

python -m mlc hello.uir

You should see MATCH hello.uir. There is no such file, and that is fine. This compiler never looks.

If the first run does not say 1 / 1 passed
  • expected one line 'MATCH FILE' on stdout, got '' with a stderr line such as [WinError 2] The system cannot find the file specified: the path after --compiler is wrong. Check it letter by letter, and keep the quotes.
  • can't open file ... tools/test.py: you are not in the root of the course repo. cd there first.
  • An old answer: you changed the code but did not run dune build. The runner uses the built file, not your source.
  • No module named mlc: the wrapper is not next to the mlc folder, or you are running the command from a different folder. (The macOS and Linux wrapper can't be named mlc, because a folder with that name is already there.)
  • python is not found: on macOS and Linux the command is python3.
  • git says Please tell me who you are: run the two git config lines it prints, with your own name and email, then commit again.

Read and run a real file

Make MATCH mean something. Write the interpreter from Build the thing that runs it and parse_line from lesson 1.2 again in your own project, and join them.

  1. Read the file and drop each comment, from # to the end of its line.
  2. Split each line into a name, an op and two values. Handle add and mul for now.
  3. Run the lines. Keep each answer under its name, as env did.
  4. Judge. The last line is assert x y. Print MATCH or MISMATCH, then the path.
Checkpoint

-k run/basic gives 2 / 2 passed and -k mismatch_basic gives 1 / 1 passed, the first test your compiler passes by computing something.

Every token, and one table of nodes

The real format has hex numbers, bindings that run over two lines and %x= with no space. Replace the line splitter with a real parser, and make it build nodes.

  1. Cut the text into tokens from the token table in lesson 1.2's reference.
  2. Group tokens into bindings. A name, then an op with its atoms and attributes, or one atom alone. Accept every op in the spec now.
  3. Build every node in one place. One function looks in a table keyed on (op, src, arg) first and returns the node that is already there.
  4. Refuse bad files. For a broken token, an unknown op, or a name used before its line or defined twice, raise your own error, catch it at the top and print REJECTED and the path.
  5. Count. Over 4096 bytes before you parse, or 100 nodes or 300 edges right after, is OVERBUDGET.
Checkpoint

-k hex gives 8 / 8 passed. -k bytes and -k overbudget_nodes each give 2 / 2 passed. Then try -k run/def and -k one_line.

Stuck? Reread hash consing in lesson 1.1 and lesson 1.2's reference.

What to watch for while you write the parser and the node table
  • Print each binding back in .uir form and check it matches the input, ignoring spacing and comments. It is the fastest way to see what your parser understood.
  • The table is keyed on (op, src, arg), with dtype and shape as part of the key. Sources are already unique, so compare them by identity. In OCaml, == is physical equality and = is structural.In Python, is is identity, and == on a dataclass compares every field. Know which one you're using.
  • [1 2] and stack 1 2 must come out as one node. Building add x 1 twice must return the same physical node.
  • The node count is taken after hash consing, with literals and [] included, reachable or not. An edge is one source of one node.
  • Literals: -7, 0xff, 007, true. Every integer must fit in an i32, and hex has no sign.
  • [] alone is the void marker a param uses for its shape.
  • If Python raises RecursionError on a long chain of nodes when you evaluate, walk the graph with your own stack or raise the limit.

Compute like the machine

.uir does arithmetic the way a 32-bit machine does, with one twist for division. Warm up on that twist first.

C's division from floor division

div -7 2 is -4, but C's / truncates toward zero and gives -3. Build C's division as %out for i32 params a and b (b is never 0) from div, mod, cmplt, xor, where and add.

  1. Wrap. After add, mul and shl, keep the low 32 bits and read them as a signed number.
  2. Floor. div and mod round down. div x 0 is -1 and mod x 0 is x.
  3. Shift. shl x y shifts by y mod 32.
  4. Compute each node once with a cache from node to value.
Checkpoint

-k run/div and -k run/mod each give 9 / 9 passed, -k run/shl gives 10 / 10 passed and -k dag_sharing gives 1 / 1 passed. The last one needs the cache: without it, it takes 294 steps.

Stuck? Reread Compute like the machine in lesson 1.2 and check your division against its table.

Types, and files that must be refused

A compiler has to refuse a wrong program before anything is evaluated.

  1. Give every node a dtype when it is built, from its op and its sources: i32, bool or void.
  2. Check each op's inputs. The right number of sources, the right dtypes and the attributes it needs.
  3. Finish the ops. max, xor, cmplt, where, cast, and the bool forms of add, mul, max and xor.
  4. Check the test-file rules. One assert, as the last binding, with a literal of the left side's dtype as its expected side. Every node can be reached from it.
Checkpoint

-k run/cast gives 6 / 6 passed, -k mismatch gives 5 / 5 passed and -k rejected_where gives 2 / 2 passed. -k run/ runs all 245 run tests. 132 of them need nothing from lesson 1.5, so it should say 132 or more.

Stuck? Reread Check types and Judge the run in lesson 1.2, and its reference.

simplify: print the program back

Now the second command. compile simplify FILE reads a program that defines %out, usually over params, with no assert, and prints one that gives the same %out for every input. Each test sets a max_ops, the most op lines you may print. Start with a simplifier that changes nothing.

  1. Read a param line, with optional limits such as [0 9] after the [].
  2. Print the graph. Walk from %out, sources first. Print each node once, under a fresh name, with literals in place and params as they were declared. The last line defines %out.
Checkpoint

-k shared_subexpr gives 1 / 1 passed: hash consing printed two equal mul lines as one. -k simplify/ gives 9 / 37 passed. The other eight are trap_ tests, which have nothing safe to remove. They wait for a tempting rule like (x * 2) / 2 → x.

Stuck? Reread Take inputs in lesson 1.2 and the toggle "How simplify is graded and what to print" in lesson 1.4.

The rewrite engine and folding

Now give the simplifier work.

  1. Write the engine. Visit nodes sources first. At each node try every rule, and try again on the result until none fits. Repeat whole passes until a pass changes nothing.
  2. Fold constants with the interpreter's own functions.
  3. Put constants on the right for add, mul, max and xor.
  4. Add the first rules. add(x, 0) → x, mul(x, 1) → x, mul(x, 0) → 0, xor(x, x) → 0 and add(add(x, c1), c2) → add(x, c1 + c2).
Checkpoint

-k const_fold and -k reassoc each give 1 / 1 passed. Then try -k zero_add and -k xor_self. When one fails, -v shows the program you printed.

Stuck? Reread lesson 1.3. Its reference has every rule and the loop to run on a shared graph.

Safe rules, then bounds

Lesson 1.4 gave you two kinds of rule: some are right for every input, and others only when bounds prove it.

  1. Add the rules that are always safe from the table in lesson 1.4, such as div(x, 1) → x, mod(x, 1) → 0 and where(c, a, a) → a.
  2. Give every node bounds. Follow the bounds column of spec section 5 exactly. A param's bounds are its limits.
  3. Add the rules bounds can prove. A compare that is always true or false, a mod that changes nothing, a div that is always 0, a max whose winner is known.
Checkpoint

-k simplify/bounds gives 6 / 6 passed and -k simplify/limits gives 4 / 4 passed. -k simplify/ gives 34 / 37 passed. The three left need lesson 1.5. If a trap_ test fails now, one of your new rules is wrong for some input, and -v prints that input.

Stuck? Lesson 1.4's toggles have every safe rule and the bounds rule for every op.

call and param

Back to the first command, which now learns to run a function.

  1. Evaluate with an environment. A call maps each slot number to an argument value and evaluates its body with that map. A param looks its slot up.
  2. Keep the value cache per call.
  3. Keep bodies closed. A call inside a body gets only the arguments that call passes.
  4. Check every call before running. Each slot the body uses has one param node and an argument of the same dtype, with bounds inside the param's limits. A param reached without going through a call is refused.
Checkpoint

-k run/call gives 13 / 13 passed and -k limits gives 19 / 19 passed.

Stuck? Reread lesson 1.5 up to "Limits". Its reference lists what a call checks.

stack, index and the cost budget

Three pieces finish the first command.

  1. Type a stack. Its elements share one dtype, and its shape is the number of elements. ALU ops take scalars only.
  2. Prove every index. If the bounds of the index allow any position outside the stack, the file is REJECTED, whatever value the run would use.
  3. Add up the static cost over the distinct nodes the assert can reach. A call costs 1 plus its body. A total of 1,000,000 or more is OVERBUDGET. Check it after validation and before running.
Checkpoint

-k index gives 11 / 11 passed, -k bounds gives 42 / 42 passed, -k cost gives 5 / 5 passed and -k run/ gives 245 / 245 passed.

Stuck? Reread the stack and index sections of lesson 1.5 and its toggle "What a call costs".

Finish simplify

The last three simplify tests need two rules.

  1. Inline a call. Replace call f a0 a1 with a copy of the body in which each param is swapped for its argument: the substitution from lesson 1.5. It stops at a nested call's body, because bodies are closed.
  2. Index a stack by a literal. index(stack(a0, a1, ...), k) → ak.

Predict what %out simplifies to. This is trap_nested_call.

%p0    = param [] slot=0 dtype=i32 addrspace=ALU
%p1    = param [] slot=1 dtype=i32 addrspace=ALU
%inner = add %p0 100
%outer = call %inner %p1
%out   = call %outer %p1 %p0

Work from the outside in. %out puts %p1 in slot 0 and %p0 in slot 1.

%outer hands its slot 1 to %inner, and %out filled slot 1 with %p0. A simplifier that pushes %out's arguments straight into %inner gets add %p1 100, and the grader finds an input where the two differ.

Checkpoint

Write your 10 tests

The official course grades students' own tests on how many other compilers they catch. Put 10 in <your compiler repo>/tests/week1/, one .uir file each, following the test-file rules from lesson 1.2, with the outcome in the file name. Here's mismatch_div_is_not_c.uir:

%a = div -7 2
%t = assert %a -3

div -7 2 is -4, so the right answer is MISMATCH, and a compiler that divides like C is caught. Check your tests against the oracle:

python tools/test.py --check-tests <your compiler repo>/tests/week1 --week 1

With that one file in the folder, it prints 1 / 1 tests agree with the oracle. A good test targets one rule you think someone (maybe you) will get wrong: div INT_MIN -1, a nested call that reuses slot 0, limits one too wide for an index, a file of exactly 4096 bytes.

Simplify tests of your own, and what --check-tests checks

A simplify test has no assert, defines %out, and starts with # simplify: max_ops=N. --check-tests confirms each file name's outcome, and for simplify tests it checks that the oracle's own simplifier reaches your max_ops, so you can't write an impossible target. Another idea for a run test: mod bounds when both ends have the same quotient.

Slop compounds

Every later week builds on this code. A simplifier that is "mostly right" will cost you far more later than it saves now. Keep it small and readable, and delete anything you don't understand.

The AI policy

Your compiler is yours to write. In your repo, the AGENTS.md says an AI assistant may explain concepts, draw diagrams and help you debug by asking questions, but must never write or rewrite compiler code. Running the reference compiler in _reference/ is fine. Never open it.
