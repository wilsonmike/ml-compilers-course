Symbolic simplification

Constant folding needs every input to be known. Symbolic simplification works on values you don't know yet, like a param. It uses algebra and ranges to prove things like "this compare is always true".

Unknowns

Inside a function body, a param (the input in some slot, see lesson 1.2's params box) could be any i32 its limits allow. You can't fold add %x 0 by computing it, but you can still prove it equals %x for every possible x. That's what makes a rule symbolic: it holds for all inputs, so it doesn't need the input.

The simplify subcommand is your compiler's second command, next to plain ./compile FILE from lesson 1.2. It reads a file that defines %out and has no assert, and prints a smaller program that computes the same thing. The grader checks two things. First, your output must give the same value as the original for every input inside the params' limits (more on limits below). It tries edge values in every param slot, nasty ones like INT_MIN, -1 and the ends of each param's limits, plus random values. Second, each test has a max_ops budget, a limit on the op bindings you print. Params, literals and atom bindings like %out = %t3 don't count. So leaving the graph untouched won't pass either.

i32 is a ring

i32 arithmetic is arithmetic mod 232. Wraparound sounds messy, but it makes i32 a ring: addition and multiplication are associative and commutative, and multiplication distributes over addition, exactly like the integers you learned in school. Every identity built only from + and × holds, even when the values overflow. Division is the odd one out: it doesn't undo a multiply that wrapped.

rulei32why

xor(x, x) → 0, xor(x, 0) → xvalidSame for bool: xor(x, x) → false, xor(x, false) → x.

Floats come later

Week 1 has no floats, so every rule here only has to hold for i32 and bool. f32 breaks several of them (x * 0 and x + 0 among them), and week 2 lesson 1 has that version of the table.

Bounds: what range can this value be in?

Some facts don't follow from algebra alone. cmplt (mod %k 8) 8 is always true, but only because you know a remainder by 8 is at most 7. That calls for bounds analysis (also called interval analysis): give every node an interval [lo, hi] that its value is guaranteed to stay inside. Bounds are worked out sources first, just like rewriting.

In the official course, bounds aren't only an optimization. They're part of validation: they decide whether an index is safe and whether a call's arguments fit their params (lesson 5). So every op has one exact rule, and your compiler must compute the same bounds the rules give, no tighter and no looser. Below, x is in [a, b], y is in [c, d], I is the full i32 range, and "fixed" means a single value like [8, 8].

nodebounds
a literal v[v, v]. true is [1, 1] and false is [0, 0].
paramits limits [l, h], or I without limits ([0, 1] for a bool)
add x y[a + c, b + d]
mul x ythe hull (smallest to largest) of ac, ad, bc, bd
max x y[max(a, c), max(b, d)]
div x yy fixed: the hull of a div y and b div y. Otherwise I.
mod x yy fixed at 0: x's bounds. y fixed and nonzero: if a div y and b div y agree, the hull of a mod y and b mod y. If not, [0, y - 1] for y > 0 or [y + 1, 0] for y < 0. y not fixed: I.
xor x yboth fixed: the exact answer. Otherwise I.
shl x ythe hull of a × 2k and b × 2k over every possible k = y mod 32
cmplt x y[1, 1] if b < c, [0, 0] if a ≥ d, otherwise [0, 1]
where p x yp fixed: the chosen side's bounds. Otherwise the hull of both sides.
cast xx's bounds. To bool: [0, 0] if x is always 0, [1, 1] if never, otherwise [0, 1].
stackthe hull of the elements' bounds
index v iv's bounds
callthe body's bounds

One more rule covers every i32 row: if an end of the interval overflows i32, the bounds widen to I. The real value might have wrapped to anywhere.

%x   = param [] slot=0 dtype=i32 addrspace=ALU
%m   = max %x 0
%k   = mod %m 8
%out = cmplt %k 8

Two mod examples

With %x in [10, 13], mod %x 8: both ends have quotient 1 (10 div 8 and 13 div 8), so no multiple of 8 sits in between, and the bounds are the hull of 10 mod 8 and 13 mod 8, which is [2, 5]. With %x in [10, 20] the quotients are 1 and 2, the remainder wraps around past 0 somewhere inside, and all the rule can say is [0, 7]. Because mod floors, that's true even for negative x: mod %x 8 is in [0, 7] for any i32 x.

Is this index safe?

This is the official reference's own example:

%i = param [] [0 2] slot=0 dtype=i32 addrspace=ALU
%v = index [10 20 30] %i
%r = call %v 1
%t = assert %r 20

On this call %i is 1, so the result is 20. But whether the program is valid depends on the bounds of %i across all calls. With limits [0, 2], all three indices exist, so it's safe and the file is a MATCH. Change the limits to [0, 3] and index 3 would be past the end, so the file is REJECTED, whatever this call passes. A constant index works the same way: index [10 20 30] 3 is rejected before anything runs.

The [0 2] after [] is the param's limits, a promise that every argument is in that range (lesson 5 says how calls keep the promise). Without limits a param is I, and index [10 20 30] %i is rejected. To index with an unlimited value, bring it into range first: %k = mod %i 3 is always in [0, 2], so index [10 20 30] %k is safe for every %i.

Deliberately simple

The rules don't try to be clever, so they can miss facts that are true:

  • mul %i %i with %i in [-1, 1] is never negative, but the rule gives the hull of 1, -1, -1, 1: [-1, 1]. Indexing [0 10] with it is rejected.
  • %k = where %c 0 %i with %c = cmplt %i 0 and %i in [-3, 2] clamps negatives to 0, but the condition isn't fixed, so the bounds are the hull of [0, 0] and [-3, 2]: still [-3, 2]. max %i 0 says the same thing in a way the rules can see: [0, 2].

That's on purpose. Every compiler has to agree on which files are REJECTED, so the rules must be simple enough that everyone computes exactly the same intervals. When you write index math, write it in a form the rules can follow.

Inside simplify you have more freedom. There, bounds only justify rewrites, so a tighter interval is fine as long as it's true. A wrong interval, one that leaves out a value the node can really have, is always a bug.

Rules powered by bounds

cmplt(a, b) → true      if a.hi < b.lo
cmplt(a, b) → false     if a.lo ≥ b.hi
max(a, b)   → a         if a.lo ≥ b.hi
mod(x, c)   → x         if 0 ≤ x.lo and x.hi < c
div(x, c)   → 0         if 0 ≤ x.lo and x.hi < c

Limits make these rules stronger. With %x = param [] [0 7] slot=0 dtype=i32 addrspace=ALU, mod %x 8 simplifies to %x, 0 ops. With limits [0 8] it must stay, because 8 mod 8 is 0. These rules matter for real. When week 3 adds loops, every index carries a range, and these rules are how bounds checks and index math disappear.

(x * 2) / 2 is not x

It's tempting to cancel the 2s. In i32, mul wraps and div doesn't undo the wrap:

xx * 2(x * 2) / 2equals x?
363yes
-5-10-5yes
1073741824 (230)-2147483648 (wrapped)-1073741824no

So div(mul(x, c), c) → x is only valid when bounds prove mul(x, c) can't wrap. With limits [0 1000] on %x, or with %x = cast %b dtype=i32 (bounds [0, 1]), it's safe, and the oracle simplifies (x * 2) / 2 down to %x. With a param that has no limits it must stay. The grader's edge-case inputs include 230 precisely to catch this.

Printing your result

simplify prints a .uir program to stdout. Walk sources first from %out and print only the nodes it needs, each once, so every name is defined above its first use. Give each node a fresh name and write constants inline as literals. Print each param exactly as it was declared, limits included. The last binding defines %out. If %out folded to a constant, print it as an atom binding, like %out = 3. Here is one valid output for a file whose %out is ((max x (2 + 1)) + y * 4) + 0:

%t0 = param [] slot=0 dtype=i32 addrspace=ALU
%t1 = max %t0 3
%t2 = param [] slot=1 dtype=i32 addrspace=ALU
%t3 = mul %t2 4
%out = add %t1 %t3

That's 3 ops: the max, the mul and the add. The params and the literal 3 are free. Any names work, because the grader compares values, not text.

Interval arithmetic for i32

Bounds analysis needs two operations on ranges. Write add_range a b and mul_range a b: the tightest range, with fields lo and hi, that contains every x + y (or x * y) with x in a and y in b.

The catch is wraparound. If any value in the result could fall outside the i32 range, the real i32 operation might wrap, so you know nothing: return full.

  • Do the math in OCaml's 63-bit int, then check against int_min and int_max.
  • Do the math in Python's unbounded int, then check against int_min and int_max.
  • For mul, the smallest and largest products can come from any pair of ends: [-3, 2] * [-5, 4] is [-12, 15].
Does 63 bits always hold the product?

Almost. Two i32 values multiply to at most 262, and that one product (INT_MIN * INT_MIN) is one past OCaml's max_int, so it wraps to a negative int. Work out whether that breaks your answer for full * full. There's a test for it.

Check yourself

Which rule is wrong for an i32 %x with no limits?

Try each rule on a value near the edge of the i32 range, like 230.

The multiply can wrap, and dividing doesn't undo the wrap. The other three hold for every i32: zero times anything is zero, addition is associative mod 232, and every remainder by 1 is 0.

What are the bounds of %k? Write them as [lo, hi].

%x = param [] slot=0 dtype=i32 addrspace=ALU
%m = max %x 0
%k = mod %m 8

First find the bounds of %m. Can max %x 0 ever be negative?

Do the two ends of %m have the same quotient by 8? If not, the rule for a positive fixed divisor gives [0, divisor - 1].

%m is [0, INT_MAX]. The ends have quotients 0 and 268435455, which differ, so mod 8 gives [0, 7].

Now drop the max. What does %out simplify to? (x is any i32.)

%x   = param [] slot=0 dtype=i32 addrspace=ALU
%k   = mod %x 8
%out = cmplt %k 8

Without the max, x can be negative. What sign does a floor remainder by a positive number have?

Still true. A floor remainder by 8 is always in [0, 7], even for negative x, so the max never mattered. In C, where % follows the sign of x, it would be [-7, 7].

%x has limits [10 13]. What are the bounds of mod %x 8?

Compare 10 div 8 and 13 div 8. If they agree, no multiple of 8 lies between the ends.

Both quotients are 1, so the bounds are the hull of 10 mod 8 = 2 and 13 mod 8 = 5: [2, 5].

%i has limits [-1 1], and %k = mul %i %i. Is index [0 10] %k valid?

Bounds come from the rule, not from what you know about squares. Take the hull of the four products of the ends.

The products of the ends are 1, -1, -1 and 1, so the bounds are [-1, 1]. The rule doesn't know both sources are the same value, and validation goes by the rule, so the file is rejected.

Predict %out for %x = 1073741824.

%m   = mul %x 2
%out = div %m 2

Work out 1073741824 * 2 first. Does 231 fit in i32?

When a product passes INT_MAX, it wraps to a negative number. Then divide that by 2.

231 doesn't fit in i32, so it wraps to -2147483648. Halving that gives -1073741824, not x.

Why is add(add(x, 3), 4) → add(x, 7) valid in i32, even when x + 3 overflows?

Think about what kind of arithmetic i32 wraparound is. Does regrouping change anything when everything is computed mod 232?

i32 is the ring of integers mod 232. In a ring, grouping doesn't matter. Overflow here is defined wrapping, not undefined behavior like in C.

After simplifying, what's the fewest ops %out can use?

%x   = param [] slot=0 dtype=i32 addrspace=ALU
%a   = add %x 3
%out = add %a 4

Fold the two constants into one. How many adds are left, and would it vanish if the constants summed to 0?

One: add %x 7. (With -3 instead of 4, it would be zero ops, since add %x 0 becomes %x.)

Here %x = param [] [0 1] slot=0 dtype=i32 addrspace=ALU. Can div(mul(%x, 2), 2) simplify to %x?

The grader only checks inputs inside the limits. What bounds does %x * 2 have, and can that wrap?

The rule is valid whenever bounds prove the multiply doesn't wrap. A bool cast to i32 gives the same [0, 1], and the oracle reduces that version to a single cast.
