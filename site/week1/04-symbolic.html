Symbolic simplification

A rewrite rule is only safe if it gives the same answer for every input, including inputs your compiler never sees. Some rules that look obvious are wrong for 32-bit numbers, because those numbers wrap. In this lesson you learn to spot the wrong ones, to test a rule, and to use bounds (the smallest and largest a value can be) to prove the rest.

Goal

Tell a safe rewrite rule from one that breaks a program, and use bounds to prove a rule is safe.

You'll use

Rewrite rules from lesson 1.3, params from lesson 1.2, and numbers that wrap and divide by flooring (H.4 Numbers that behave like C is the slow version).

In the exercises: a list comprehension (P.3), a small class made with @dataclass (P.4) and a function handed to another function (P.5).

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

Your rules from lesson 1.3 run on this program. How many ops does %out use afterward?

%x   = param [] slot=0 dtype=i32 addrspace=ALU
%a   = add %x 0
%out = mul %a 1

Which rule fires on add %x 0? Then look at what the mul is left with.

Zero. add(x, 0) → x removes the add, then mul(x, 1) → x removes the mul. %out is just %x.

The largest i32 is 2147483647. What is add 2147483647 1?

An i32 has 32 bits and no room for a bigger number. Think of a car's odometer rolling over.

It wraps around to the smallest i32, -2147483648. Nothing fails. This one fact causes every problem in this lesson.

Which of these rules would break a program?

Your rules from lesson 1.3 already work on a param, a number the test hands in later. add(x, 0) → x never asks what x is. A rule like that is called symbolic: it treats x as a symbol that stands for any value.

That is a big promise. An i32 has about 4 billion possible values, and the rule must give the same answer as the original for every one of them. If it is wrong for a single value, your compiler quietly changes what somebody's program computes.

Below are two rules that both look true. One is safe and one breaks a program. Predict each before you read on. Two names help: INT_MAX is the largest i32, 2147483647, and INT_MIN is the smallest, -2147483648.

div(mul(x, 2), 2) → x. "Double it, halve it, and you are back where you started."

Try a large x, such as 1073741824. Does twice that fit in an i32?

It breaks. Twice 1073741824 is 2147483648, one more than INT_MAX, so it wraps to -2147483648. Half of that is -1073741824, which is not x.

add(add(x, 3), 4) → add(x, 7). "Adding 3 and then 4 is adding 7."

Try x = 2147483647 on both sides. Both sides wrap. Do they land on the same number?

Safe, even when it wraps. With x = INT_MAX the left side wraps to -2147483646 and then adds 4, which gives -2147483642. The right side wraps straight to -2147483642. The next section says why they always agree.

An input where a rule gives a different answer from the original is called a counterexample. One is enough to throw a rule out. Step through the one you just found, and guess the value of every line. The halving rule is the classic trap, because it works for almost every number you would think to try.

Here is a second rule that looks true: cmplt(x, add(x, 1)) → true, "a number is always less than itself plus one". It breaks for exactly one value.

How to convince yourself a rule is safe

Two questions settle most rules.

  1. Which ops does it use? add and mul keep the low 32 bits of the true answer, and those bits never depend on the bits that were dropped. So it does not matter when the wrap happens, and every school rule made only of + and × stays true. div, mod, cmplt and max are different. They care how big a number is, and a wrap changes that.
  2. What happens at the edges? Rules break where numbers wrap. Try 0, 1, -1, 1073741824, INT_MAX and INT_MIN.

Passing the edge test is good evidence, but it is not a proof. A proof is a reason that covers every value, like question 1, or like the bounds later in this lesson.

Here are both questions on the rule mul(add(x, 1), 2) → add(mul(x, 2), 2):

  1. List the ops. Only add and mul, so it is safe in i32.
  2. Check an edge anyway. Take x = INT_MAX. Left: x + 1 wraps to INT_MIN, and twice that wraps to 0. Right: x * 2 wraps to -2, and adding 2 gives 0. They agree.

Is max(x, add(x, 1)) → add(x, 1) safe? "The larger of x and x + 1 is x + 1."

max cares how big a number is. Try the edge where x + 1 wraps.

At INT_MAX, x + 1 wraps to INT_MIN. The original picks the larger one, INT_MAX. The rule picks INT_MIN.

Next, the edge test as code. It is wrong in the same two ways people get it wrong by hand.

  • The edge values. edges only holds small numbers. Add 1073741824, int_max and int_min.

Why wrapping keeps add and mul rules true: i32 is a ring

i32 arithmetic is arithmetic mod 232. Wraparound sounds messy, but it makes i32 what mathematicians call a ring: addition and multiplication are associative and commutative, and multiplication distributes over addition, exactly like the integers you learned in school. Every identity built only from + and × holds, even when the values overflow. Division is the odd one out: it doesn't undo a multiply that wrapped.

Bounds: how small and how large can it be?

Some true facts are not algebra at all. Predict this one.

%x can be any i32. Can %out ever be false?

%x   = param [] slot=0 dtype=i32 addrspace=ALU
%k   = mod %x 8
%out = cmplt %k 8

mod floors, so a remainder by 8 is never negative: mod -1 8 is 7. List the values a remainder by 8 can be.

A remainder by 8 is one of 0 to 7, even for a negative %x. Every one of those is less than 8, so the whole program can become %out = true.

No rule from the last section says that, and you cannot test 4 billion inputs. What you used was a fact about how small and how large %k can be. A compiler keeps that fact as bounds: a pair [lo, hi] such that every value the node can ever have is from lo to hi, ends included. Bounds are also called an interval or a range.

Bounds are worked out sources first, like rewriting. A literal like 8 has bounds [8, 8]. A param you know nothing about has the full i32 range, [INT_MIN, INT_MAX]. Each op then has a small rule that turns its sources' bounds into its own. Here it is on a program with one more line:

  1. Start at the sources. %x is [INT_MIN, INT_MAX]. The literals are [0, 0] and [8, 8].
  2. Push through max. max %x 0 is never below 0, so %m is [0, INT_MAX].
  3. Push through mod. A remainder by 8 is 0 to 7, so %k is [0, 7].
  4. Ask the question. The largest %k is 7 and the smallest right side is 8. 7 is less than 8, so cmplt %k 8 is always true.
%x   = param [] slot=0 dtype=i32 addrspace=ALU
%m   = max %x 0
%k   = mod %m 8
%out = cmplt %k 8

The rule for add: add the two low ends, and add the two high ends. %k has bounds [0, 7]. What are the bounds of add %k 1? Write them as [lo, hi].

The literal 1 has bounds [1, 1]. Add low to low and high to high.

[0 + 1, 7 + 1] is [1, 8]. The smallest sum uses the two smallest inputs, and the largest sum uses the two largest.

%m has bounds [0, INT_MAX]. What bounds should add %m 1 get?

When %m is INT_MAX, what does the add really produce? Bounds must contain that value.

INT_MAX + 1 wraps to INT_MIN, so the result can be very negative. The only honest bounds are the full range.

That is the rule that keeps bounds honest: if an end does not fit in an i32, give up and say the full range. Bounds that are too wide only cost you a missed simplification. Bounds that leave out a value the node can really have are a bug, because a rule will trust them.

Interval arithmetic for i32

Write add_range a b and mul_range a b: the tightest range, with fields lo and hi, that contains every x + y (or x * y) with x in a and y in b. If any value in the result could fall outside the i32 range, the real operation might wrap, so you know nothing: return full.

The bounds rule for every op, for when you write validation in the lab

In the official course, bounds aren't only an optimization. They're part of validation: they decide whether an index is safe and whether a call's arguments fit their params (lesson 5). So every op has one exact rule, and your compiler must compute the same bounds the rules give, no tighter and no looser. Below, x is in [a, b], y is in [c, d], I is the full i32 range, and "fixed" means a single value like [8, 8]. The hull of some numbers is the interval from the smallest of them to the largest.

nodebounds
a literal v[v, v]. true is [1, 1] and false is [0, 0].
paramits limits [l, h], or I without limits ([0, 1] for a bool)
add x y[a + c, b + d]
mul x ythe hull (smallest to largest) of ac, ad, bc, bd
max x y[max(a, c), max(b, d)]
div x yy fixed: the hull of a div y and b div y (unwrapped, so INT_MIN div -1 overflows i32 and widens to I). Otherwise I.
mod x yy fixed at 0: x's bounds. y fixed and nonzero: if a div y and b div y agree, the hull of a mod y and b mod y. If not, [0, y - 1] for y > 0 or [y + 1, 0] for y < 0. y not fixed: I.
xor x yboth fixed: the exact answer. Otherwise I.
shl x ythe hull of a × 2k and b × 2k over every possible k = y mod 32
cmplt x y[1, 1] if b < c, [0, 0] if a ≥ d, otherwise [0, 1]
where p x yp fixed: the chosen side's bounds. Otherwise the hull of both sides.
cast xx's bounds. To bool: [0, 0] if x is always 0, [1, 1] if never, otherwise [0, 1].
stackthe hull of the elements' bounds
index v iv's bounds
callthe body's bounds

Two extra rules cover the table: for every i32 row, if an end of the interval overflows i32, the bounds widen to I (the real value might have wrapped to anywhere). For bool ops (add, mul, max, xor), the interval is normalized back to [0, 0], [1, 1] or [0, 1].

Two mod examples

With %x in [10, 13], mod %x 8: both ends have quotient 1 (10 div 8 and 13 div 8), so no multiple of 8 sits in between, and the bounds are the hull of 10 mod 8 and 13 mod 8, which is [2, 5]. With %x in [10, 20] the quotients are 1 and 2, the remainder wraps around past 0 somewhere inside, and all the rule can say is [0, 7]. Because mod floors, that's true even for negative x: mod %x 8 is in [0, 7] for any i32 x.

Bounds make more rules safe

The halving rule broke because nothing stopped x * 2 from wrapping. If you know x is small, nothing wraps and the rule is fine. A param can tell you so:

%x = param [] [0 1000] slot=0 dtype=i32 addrspace=ALU

The [0 1000] after [] is the param's limits, a promise that every value handed in is from 0 to 1000. Lesson 5 says how calls keep the promise. With limits, the param's bounds are [0, 1000] and not the full range. Then mul %x 2 has bounds [0, 2000], which fits, so div(mul(x, 2), 2) → x is safe for this %x.

These are the rules that ask bounds for permission. a.hi means the high end of a's bounds and a.lo the low end:

cmplt(a, b) → true      if a.hi < b.lo
cmplt(a, b) → false     if a.lo ≥ b.hi
max(a, b)   → a         if a.lo ≥ b.hi
mod(x, c)   → x         if 0 ≤ x.lo and x.hi < c
div(x, c)   → 0         if 0 ≤ x.lo and x.hi < c

%x has limits [0 8]. Can mod %x 8 be replaced by %x?

The rule needs x.hi < c. Here x.hi is 8 and c is 8. Try that one value.

8 mod 8 is 0, not 8, so 8 is a counterexample. With limits [0 7] the rule fires and the mod disappears.

These rules matter for real. When week 3 adds loops, every index carries a range, and these rules are how bounds checks and index math disappear.

Bounds also decide which files are valid

Your compiler uses bounds for one more job, and this one is not optional. Lesson 5 adds an op that picks an item out of a list: index [10 20 30] %i is item number %i, counting from 0. It only makes sense when %i is 0, 1 or 2. The compiler does not wait to see which value arrives. If the bounds of %i fit inside [0, 2] the file is fine. If they do not, the file is REJECTED before anything runs.

Every compiler has to agree on which files are rejected, so for this job the bounds rules are fixed by the spec. The toggles below have the full example and the true facts the rules miss.

Is this index safe? The full example, for after lesson 5

This is the official reference's own example:

%i = param [] [0 2] slot=0 dtype=i32 addrspace=ALU
%v = index [10 20 30] %i
%r = call %v 1
%t = assert %r 20

On this call %i is 1, so the result is 20. But whether the program is valid depends on the bounds of %i across all calls. With limits [0, 2], all three indices exist, so it's safe and the file is a MATCH. Change the limits to [0, 3] and index 3 would be past the end, so the file is REJECTED, whatever this call passes. A constant index works the same way: index [10 20 30] 3 is rejected before anything runs.

The [0 2] after [] is the param's limits, a promise that every argument is in that range (lesson 5 says how calls keep the promise). Without limits a param is I, and index [10 20 30] %i is rejected. To index with an unlimited value, bring it into range first: %k = mod %i 3 is always in [0, 2], so index [10 20 30] %k is safe for every %i.

Deliberately simple: true facts the bounds rules miss

The rules don't try to be clever, so they can miss facts that are true:

  • mul %i %i with %i in [-1, 1] is never negative, but the rule gives the hull of 1, -1, -1, 1: [-1, 1]. Indexing [0 10] with it is rejected.
  • %k = where %c 0 %i with %c = cmplt %i 0 and %i in [-3, 2] clamps negatives to 0, but the condition isn't fixed, so the bounds are the hull of [0, 0] and [-3, 2]: still [-3, 2]. max %i 0 says the same thing in a way the rules can see: [0, 2].

That's on purpose. Every compiler has to agree on which files are REJECTED, so the rules must be simple enough that everyone computes exactly the same intervals. When you write index math, write it in a form the rules can follow.

Inside simplify you have more freedom. There, bounds only justify rewrites, so a tighter interval is fine as long as it's true. A wrong interval, one that leaves out a value the node can really have, is always a bug.

Where this goes: the simplify command

In the lab your compiler gets a second command, ./compile simplify FILE. It reads a program that defines %out and prints a smaller program that computes the same thing. The grader runs both versions on edge values, like your rule tester, and it counts your ops. A wrong rule fails the first check. A missing rule fails the second.

How simplify is graded and what to print, for the lab

The simplify subcommand is your compiler's second command, next to plain ./compile FILE from lesson 1.2. It reads a file that defines %out and has no assert, and prints a smaller program that computes the same thing. The grader checks two things. First, your output must give the same value as the original for every input inside the params' limits. It tries edge values in every param slot, nasty ones like INT_MIN, -1 and the ends of each param's limits, plus random values. Second, each test has a max_ops budget, a limit on the op bindings you print. Params, literals and atom bindings like %out = %t3 don't count. So leaving the graph untouched won't pass either.

Printing your result

simplify prints a .uir program to stdout. Walk sources first from %out and print only the nodes it needs, each once, so every name is defined above its first use. Give each node a fresh name and write constants inline as literals. Print each param exactly as it was declared, limits included. The last binding defines %out. If %out folded to a constant, print it as an atom binding, like %out = 3. Here is one valid output for a file whose %out is ((max x (2 + 1)) + y * 4) + 0:

%t0 = param [] slot=0 dtype=i32 addrspace=ALU
%t1 = max %t0 3
%t2 = param [] slot=1 dtype=i32 addrspace=ALU
%t3 = mul %t2 4
%out = add %t1 %t3

That's 3 ops: the max, the mul and the add. The params and the literal 3 are free. Any names work, because the grader compares values, not text.
