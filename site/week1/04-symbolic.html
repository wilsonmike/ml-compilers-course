Symbolic simplification

Constant folding needs every input to be known. Symbolic simplification works on values you don't know yet, like a param. It uses algebra and ranges to prove things like "this compare is always true".

Unknowns

Inside a function body, param 0 (the input in slot 0, see lesson 1.2's params box) could be any i32. You can't fold add %x 0 by computing it, but you can still prove it equals %x for every possible x. That's what makes a rule symbolic: it holds for all inputs, so it doesn't need the input.

The simplify subcommand is your compiler's second command, next to run from lesson 1.2. It reads a file that defines %out and prints a smaller program that computes the same thing. It is graded exactly this way. Your output has to compute the same value as the original for every input where the original doesn't error. The grader checks that on every edge value in every param slot (a few hundred cases), including nasty ones like INT_MIN, -0.0 and nan, and it compares f32 results bit for bit, so -0.0 and 0.0 count as different there (all NaNs count as equal). Each test also has a max_ops budget, so leaving the graph untouched won't pass either.

i32 is a ring. f32 is not.

i32 arithmetic is arithmetic mod 232. Wraparound sounds messy, but it makes i32 a ring: addition and multiplication are associative and commutative, and multiplication distributes over addition, exactly like the integers you learned in school. Every identity built only from + and × holds, even when the values overflow.

f32 has none of that. Every op rounds, and the special values inf, -inf, nan and -0.0 break identities you'd expect to hold.

f32 identities

When a rule "obviously" holds, try it on nan, inf, -inf and -0.0 before you trust it on f32. If you're not sure, don't add the rule. A missing rule costs you some ops. A wrong rule costs you correctness.

Bounds: what range can this value be in?

Some facts don't follow from algebra alone. cmplt (mod %k 8) 8 is always true, but only because you know a remainder by 8 is at most 7. That calls for bounds analysis (also called interval analysis): give every i32 node a range [lo, hi] that its value is guaranteed to stay inside. Ranges are worked out sources first, just like rewriting. Below, a.lo and a.hi are the two ends of operand a's range:

  • const c is [c, c]. A param is the full range [INT_MIN, INT_MAX].
  • add: [a.lo + b.lo, a.hi + b.hi], but only if neither end overflows. If one could wrap, fall back to the full range.
  • max: [max(a.lo, b.lo), max(a.hi, b.hi)].
  • mod x c with a const c > 0: [0, c-1] if x.lo ≥ 0, otherwise [-(c-1), c-1], because the sign follows x.
  • cast from bool: [0, 1].

Ranges are conservative. Reporting a range that's too wide is always safe, because it just proves fewer things. Reporting one that's too narrow is a bug.

%x   = param 0 dtype=i32
%m   = max %x 0
%k   = mod %m 8
%out = cmplt %k 8

Rules powered by bounds

cmplt(a, b) → true      if a.hi < b.lo
cmplt(a, b) → false     if a.lo ≥ b.hi
max(a, b)   → a         if a.lo ≥ b.hi
mod(x, c)   → x         if 0 ≤ x.lo and x.hi < c
div(x, c)   → 0         if 0 ≤ x.lo and x.hi < c

These rules matter for real. When week 3 adds loops, every index carries a range, and these rules are how bounds checks and index math disappear.

(x * 2) / 2 is not x

It's tempting to cancel the 2s. In i32, mul wraps and div doesn't undo the wrap:

xx * 2(x * 2) / 2equals x?
363yes
-5-10-5yes
1073741824 (230)-2147483648 (wrapped)-1073741824no

So div(mul(x, c), c) → x is only valid when bounds prove mul(x, c) can't wrap. With %x = cast %b dtype=i32 (range [0, 1]) it's safe, and the oracle simplifies (x * 2) / 2 down to the cast. With a raw param it must stay. The grader's edge-case inputs include 230 precisely to catch this.

Interval arithmetic for i32

Bounds analysis needs two operations on ranges. Write add_range a b and mul_range a b: the tightest range, with fields lo and hi, that contains every x + y (or x * y) with x in a and y in b.

The catch is wraparound. If any value in the result could fall outside the i32 range, the real i32 operation might wrap, so you know nothing: return full.

  • Do the math in OCaml's 63-bit int, then check against int_min and int_max.
  • Do the math in Python's unbounded int, then check against int_min and int_max.
  • For mul, the smallest and largest products can come from any pair of ends: [-3, 2] * [-5, 4] is [-12, 15].
Does 63 bits always hold the product?

Almost. Two i32 values multiply to at most 262, and that one product (INT_MIN * INT_MIN) is one past OCaml's max_int, so it wraps to a negative int. Work out whether that breaks your answer for full * full. There's a test for it.

Check yourself

Which rule is valid for f32?

Try each rule on the awkward floats: nan, inf, and -0.0.

Only multiplying by one is exact for every float. nan × 0 is nan, regrouping changes rounding, and -0.0 + 0.0 is +0.0.

What are the bounds of %k? Write them as [lo, hi].

%x = param 0 dtype=i32
%m = max %x 0
%k = mod %m 8

First find the range of %m. Can max %x 0 ever be negative?

mod by a positive constant on a value that is never negative lands in [0, divisor - 1].

%m is [0, INT_MAX], which is never negative, so mod 8 gives [0, 7].

Now drop the max. What does %out simplify to? (x is any i32.)

%x   = param 0 dtype=i32
%k   = mod %x 8
%out = cmplt %k 8

Without the max, x can be negative, and the sign of mod follows x. Which end of the range moved, and does that end matter for < 8?

Still true. A negative x makes the range [-7, 7], but the top is still 7, and 7 < 8. Only the low end changed.

Predict %out for %x = 1073741824.

%m   = mul %x 2
%out = div %m 2

Work out 1073741824 * 2 first. Does 231 fit in i32?

When a product passes INT_MAX, it wraps to a negative number. Then divide that by 2, truncating toward zero.

231 doesn't fit in i32, so it wraps to -2147483648. Halving that gives -1073741824, not x.

Why is add(add(x, 3), 4) → add(x, 7) valid in i32, even when x + 3 overflows?

Think about what kind of arithmetic i32 wraparound is. Does regrouping change anything when everything is computed mod 232?

i32 is the ring of integers mod 232. In a ring, grouping doesn't matter. Overflow here is defined wrapping, not undefined behavior like in C.

After simplifying, what's the fewest ops %out can use?

%x   = param 0 dtype=i32
%a   = add %x 3
%out = add %a 4

Fold the two constants into one. How many adds are left, and would it vanish if the constants summed to 0?

One: add %x 7. (With -3 instead of 4, it would be zero ops, since add %x 0 becomes %x.)

Here %x = cast %b dtype=i32 with %b a bool param. Can div(mul(%x, 2), 2) simplify to %x?

A bool cast to i32 is always 0 or 1. What range does %x * 2 have, and can that wrap?

The rule is valid whenever bounds prove the multiply doesn't wrap. The oracle reduces this to a single cast.
