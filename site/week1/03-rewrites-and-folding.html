Rewrites and constant folding

By the end of this lesson you can write a simplifier: the part of a compiler that crosses out pointless work, like adding zero, before the program runs. It applies a short list of small rules over and over until none fits. This is the first time your compiler changes a program, so every change has to keep the answer the same.

Goal

Write a function that applies a list of rewrite rules to an expression until no rule fits.

You'll use

match with class patterns on a small tree of dataclasses (P.4) and a function that calls itself on a tree (P.5). Also i32 wraparound from lesson 1.2.

match on a variant type and option (O.3 and O.4). Also i32 wraparound from lesson 1.2.

A rule is a pattern and a replacement

You made four small moves, and each one looked at a single line. Each move is a rewrite rule. Its pattern is the shape to look for. Its replacement is what to build in that place. We write a rule with an arrow between the two:

rulein words
mul(x, 1) → xmultiplying by one changes nothing
add(x, 0) → xadding zero changes nothing
add(c1, c2) → c1 + c2
mul(c1, c2) → c1 * c2		both inputs are known numbers, so compute the answer now
add(add(x, c1), c2) → add(x, c1 + c2)adding 3 and then 10 is adding 13

In a pattern, x matches any node, small or large. A name that starts with c matches only a constant, a plain number written in the program. 0 and 1 match only those exact numbers. When the pattern matches a node, we say the rule fires, and the node is replaced. A rule is only allowed if both sides give the same answer for every input.

Which of these nodes does the rule add(x, 0) → x match?

%t = mul %y 7
%p = add %y 0
%q = add %t 0
%r = add 0 %y

x can stand for any node. The 0 has to be where the pattern says it is.

x matches %y in %p and the whole mul in %q. In %r the 0 is on the left, and the pattern wants it on the right. You'll fix that later in this lesson.

In code, the rules live in one function that looks at a single node and that node's children. The exercises on this page use a small toy tree in place of real UOps: Const is a number, Var is an unknown input, and Add and Mul each have two children. Here are two rules:

def rule(e):
    match e:
        case Add(x, Const(0)):
            return x
        case Mul(x, Const(1)):
            return x
    return None
let rule e =
  match e with
  | Add (x, Const 0) -> Some x
  | Mul (x, Const 1) -> Some x
  | _ -> None

Each casebranch is one rule: the pattern, then the replacement. rule gives back the new node in a Some when a rule fires, and None when no rule matches.

Sources first

rule handles one node. A program has many. Which one do you offer to rule first? Try it on this program.

%x   = param [] slot=0 dtype=i32 addrspace=ALU
%a   = add 3 -3
%out = add %x %a

Nothing has been simplified yet. You offer %out to the rule add(x, 0) → x. Does it fire?

A pattern looks at what a node is right now. It does not compute anything.

The pattern wants the constant 0 as the second source. Right now that source is the node add 3 -3. Fold %a to 0 first, and then the rule fires on %out.

So simplify a node's sources before the node itself. This is called going sources first, or bottom up. Your interpreter evaluates in the same order (lesson 1.2), for the same reason: a node can only be dealt with once its sources are. Each node takes two moves:

  1. Simplify the sources. Do this whole job on each source first.
  2. Rebuild the node. Make the node again from its simplified sources, and offer that to rule.

Repeat until nothing changes

One more thing can go wrong. Watch the last rule from the table, the joining rule, work on (x + 3) + -3:

add(add(x, 3), -3)   →   add(x, 0)

The simplifier offered this node to rule once, the rule fired, and it moved on. What is left in the program?

The replacement is a brand new node. Has any rule looked at it yet?

The rule built add(x, 0), a node no rule has seen. Offer it to rule again and add(x, 0) → x fires.

A rewrite can create a new chance for another rewrite. That adds a third move to the two above:

  1. Try again. While rule returns a new node, offer that new node to rule.

A program where no rule fires anywhere is called a fixpoint (short for fixed point): running the simplifier on it again changes nothing. Here are all three moves on a small program:

%x   = param [] slot=0 dtype=i32 addrspace=ALU
%a   = add 1 2
%b   = add %x %a
%out = add %b -3
  1. Start at the sources. %a is add 1 2. Both inputs are constants, so it becomes 3.
  2. Move up. %b is rebuilt as add %x 3. No rule matches it.
  3. Reach the top. %out is now add(add(x, 3), -3). The joining rule fires and builds add(x, 0).
  4. Try again. add(x, 0) → x fires on the new node.
  5. Stop. No rule matches x. Three ops became none: %out is just %x.

Finish a rewriter

rule is complete, so leave it alone. simplify has two mistakes.

Sources first. The Mul casebranch simplifies both children before it rebuilds the node. The Add casebranch rebuilds the node from children nobody simplified.

Try again. The node is offered to rule one time. It should be offered again and again until rule answers None.

The tests print a tree with parentheses, so Add(Var("y"), Const(5))Add (Var "y", Const 5) shows as (y + 5).

Will it ever stop?

"Keep going until no rule fires" is a loop, and a loop can run forever. A teammate adds this rule, because addition gives the same answer in either order:

add(x, y) → add(y, x)        # always swap

Start with add %a %b and let this one rule fire twice. What do you have?

Write down the node after the first swap. Does the pattern add(x, y) match it?

The first swap gives add %b %a, still an add of two things, so the rule fires again and swaps back. The loop never ends, and your compiler hangs.

The cure: for every rule, name something that the rule makes smaller. All five rules in the table remove at least one op, and a program cannot have fewer than zero ops, so they run out. The swap rule removes nothing, and that is the warning sign. The reference has the full argument.

Constant folding: do the math now, and do it right

The rules add(c1, c2) → c1 + c2 and mul(c1, c2) → c1 * c2 have a name. Constant folding means: every input is a constant, so compute the answer while compiling and put it in the program. There is one such rule for each op that computes on values (the spec calls these ALU ops). It is the easiest place to change a program's answer by accident.

A folder sees mul 65536 65536. It multiplies with Python's *OCaml's * on 63-bit ints, gets 4294967296, and writes that number into the program. Your interpreter runs the original line and gets 0. Which one is right?

65536 × 65536 is 2 to the 32nd. What did the warm up say happens to an i32 that does not fit?

i32 math wraps, so the program's answer is 0. A simplifier may never change an answer. 4294967296 is not even a value an i32 can hold.

So folding has to compute each op exactly as your interpreter does: i32 wraps, division floors, and shl shifts by its amount mod 32. It must not crash either. div 1 0 folds to -1 and mod 7 0 folds to 7. But OCaml's / raises Division_by_zeroPython's // raises ZeroDivisionError, so a folder that calls it directly crashes on a valid program. So don't write the math twice. Share one implementation of each op between folding and interpreting.

One fixed order for operands

Back to the node that got away earlier: %r = add 0 %y. add(x, 0) → x does not match it, because the 0 is on the left.

You want every rule to work whichever side the constant is on. Which fix costs the least?

One of these doubles your rule list. One of them you have already seen loop forever.

One rule that tidies the order first keeps every other rule single. Writing each rule twice works, but the list doubles and it is easy to forget one. The always-swap rule never stops.

add gives the same answer whichever way round its two inputs are. An op like that is called commutative. In week 1 the commutative ops are add, mul, max and xor. For each of them we add one rule:

op(c, x) → op(x, c)      when c is a const and x is not

Picking one agreed way to write a thing, out of several that mean the same, is called canonicalization. The agreed way is the canonical form. Here it is "constant on the right".

This rule swaps, so why does it stop? It only fires when the constant is on the left, and its output has the constant on the right. What it makes smaller is the number of nodes with a constant on the left.

A bonus: to the hash-consing table, add 3 %x and add %x 3 are different nodes. After this rule they are the same node, so the work is shared.

A toy rewriter

Write simplify e. Simplify both children first, then apply these rules to the node, and keep re-applying them to the result until none fires. Integers are i32: fold with 32-bit wraparound.

Add (Const a, Const b)        → Const (a + b)
Mul (Const a, Const b)        → Const (a * b)
Add (Const c, x)              → Add (x, Const c)     (x not a Const)
Mul (Const c, x)              → Mul (x, Const c)     (x not a Const)
Add (x, Const 0)              → x
Mul (x, Const 1)              → x
Mul (x, Const 0)              → Const 0
Add (Add (x, Const a), Const b) → Add (x, Const (a + b))
Mul (Mul (x, Const a), Const b) → Mul (x, Const (a * b))

Leave everything else alone. Add (Const 1, Add (Const 2, Var "y")) becomes (y + 3), which takes three rules in a row.

Key idea

A simplifier is a small set of local, obviously correct rules plus a dumb loop. Every rule has to give exactly the same answer as the interpreter on every input.

What you can do now

  • Read a rewrite rule as a pattern and a replacement, and say which nodes it fires on.
  • Apply rules sources first, and retry each node until no rule fires.
  • Say why a rule set stops, by naming what each rule makes smaller.
  • Fold constants so the answer matches the interpreter, wraparound and division by zero included.
  • Use one ordering rule so that no other rule has to be written twice.

The engine itself is tiny, and you'll write one this week:

  1. Sources first. Visit nodes in topological order, sources before their users. By the time you look at a node, its sources have already been simplified.
  2. Greedy. At each node, try the rules. If one fires, try them all again on the result, until nothing matches.
  3. To a fixpoint. Keep running whole passes until a pass changes nothing. That graph is your answer.
Termination: the full argument that the loop stops, for when you add a rule of your own

"Repeat until nothing changes" only stops if each rule moves the graph toward something smaller or more canonical. A rule like add(x, y) → add(y, x) matches its own output, so the engine swaps forever. The canonicalization rule is safe because it only fires when the const is on the left, and its output has the const on the right, where the rule no longer matches. A good habit: for each rule, name what it shrinks (number of ops, number of non-const sources, constants on the left).

For the nine rules of the toy rewriter, two counts are enough. Write the expression out as a tree. Let N be the number of nodes in it, and let L be the number of add and mul nodes with a const on the left and a non-const on the right.

ruleNL
fold op(c1, c2)down by 2may change
add(x, 0) → x, mul(x, 1) → xdown by 2may change
mul(x, 0) → 0down by at least 2may change
reassociate op(op(x, c1), c2)down by 2may change
op(c, x) → op(x, c), x not a constsamedown by 1
add(x, y) → add(y, x), alwayssamecan go back up. It loops.

Every allowed rule either lowers N, or keeps N the same and lowers L. N cannot go below zero, so it can only drop a limited number of times. Between two drops of N, the swap rule is the only one firing, and each swap lowers L, which is never larger than N. So the rewrites run out. Folding is tried before the swap, so a node with two consts is folded and never swapped.

Two rules can also loop as a pair when each is fine alone, for example one that moves consts right and another that moves them left in some case. When you add a rule, check its output against every other rule's pattern. While developing, give the loop a limit and raise an error past it, so a loop shows up as a message and not as a hang.

Canonical ordering: the exact rule and what it buys, for when two equal programs come out different

add 3 %x and add %x 3 mean the same thing. Without help, every rule would need two versions, one for each side. Instead we add one canonicalization rule for each commutative op (add, mul, max, xor):

op(c, x) → op(x, c)      when c is a const and x is not

On i32 and bool all four really are commutative. When floats arrive in week 2, max stays commutative only because the spec pins down its -0.0 and NaN cases, and that lesson comes back to it.

Now every other rule can assume constants sit on the right. Canonical forms also help hash consing, because two equivalent expressions are more likely to become the same node.

Ops where order matters are never swapped. cmplt a b is a < b, and div, mod and shl also read their two sources differently.

Why hash consing makes rewriting cheap, for when you move from the toy tree to your graph

In a hash-consed graph, building a node that already exists hands you back the existing one. Two statements with the same (op, src, arg), where dtype and shape are part of the key, are a single UOp. Three things follow:

  • Shared work is rewritten once. If add %x 1 appears ten times, it's one node, simplified once.
  • "Did anything change?" is an identity check. If the rule returns the very same object, nothing happened. No deep comparison of trees.
  • Rules like xor(x, x) → 0 are a pointer comparison. Equal expressions are the same node, so "are both sources the same expression?" is just "are they the same object?" (OCaml's physical equality, ==Python's is).

Above: %a = add %x 1 and %b = add %x 1 collapse into one add, and mul %a %b points at it twice. Simplifying %out here leaves exactly 2 ops.

From a tree to a shared graph: the loop your lab simplifier runs, for when the toy version is too slow

The toy works on a tree, so a shared subexpression gets simplified once per path that reaches it. On a hash-consed graph that can be exponential: the doubling chain from lesson 1, 94 lines like %x2 = add %x1 %x1, has 294 paths, and rebuilding it as a tree splits every shared node into copies. Instead, walk the graph sources first (the toposort from lesson 0.3) and keep a memo from each old node to its new node:

simplify root:
  new = empty map, keyed by node identity
  for u in toposort(root):
    n = mk(u.op, [new[s] for s in u.src], u.arg, u.dtype, u.shape)
    while a rule rewrites n to some r that is not n:
      n = r
    new[u] = n
  if new[root] is root: return root
  return simplify(new[root])

mk is your hash-cons constructor, and the rules build their results with it too. Every node is visited once per pass, and two rebuilt nodes that come out equal are the same node again, so xor(x, x) → 0 still sees one object on both sides.
