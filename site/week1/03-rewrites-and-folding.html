Rewrites and constant folding

A compiler pass is mostly a list of small rules like add(x, 0) → x, applied over and over until none of them fire. This lesson shows how that loop works, one rule at a time.

A rule is a pattern and a replacement

A rewrite rule has two halves. The pattern describes a shape of graph to look for. The replacement says what to build instead. We'll write rules like this:

add(x, 0)          → x                  # adding zero does nothing (i32)
mul(x, 1)          → x                  # multiplying by one does nothing
add(c1, c2)        → const(c1 + c2)     # both inputs known: compute it now
mul(c, x)          → mul(x, c)          # move the constant to the right

x and y match any node. Names starting with c (c, c1, c2) match only const nodes. add(x, 0) is shorthand for the .uir node add %x 0, and in the exercise below the same pattern is written Add (x, Const 0)Add(x, Const(0)). A rule fires on a node when the pattern matches it, and then the node is replaced by whatever the right side builds.

The engine itself is tiny, and you'll write one this week:

  1. Sources first. Visit nodes in topological order, sources before their users. By the time you look at a node, its sources have already been simplified.
  2. Greedy. At each node, try the rules. If one fires, try them all again on the result, until nothing matches.
  3. To a fixpoint. Keep running whole passes until a pass changes nothing. That graph is your answer.

Watch it, one rule per step

This is the program being simplified. Use the buttons or the arrow keys. A bold outline means a pattern matched. Green means the rule just built that node. Faded nodes are no longer used by anything.

%x   = param 0 dtype=i32
%a   = add 2 3
%b   = add 4 %a
%c   = mul %b %x
%out = add %c 0

Notice the sources-first order doing its job. add 4 %a can't fold until %a has become the constant 5. Because sources are visited first, that has already happened by the time the engine reaches %b. Visiting results before their sources, you'd need an extra pass for every level of the graph.

Constant folding

Constant folding is the rule family "every input is a const, so compute the answer now." For each arithmetic or logic op (the spec calls these ALU ops) it's one rule, and it evaluates the op with exactly the same semantics as your interpreter: i32 wraps around, f32 rounds to nearest-even, division truncates toward zero.

That last part matters. If your folder computes mul 1073741824 4 with 64-bit integers, it gets 4294967296, which isn't an i32. The interpreter would give 0. A simplifier that changes the answer is a bug, so share one implementation of each op between folding and interpreting.

Don't fold errors into values

div 1 0 has two constant inputs, so the folding rule matches it. But there's no i32 that is "one divided by zero". It's a runtime error, and a program whose asserts depend on it must exit 2. If your folder catches the error and returns something like const 0, the program silently "works". The right move is to not fire: leave div 1 0 in the graph, and let evaluation report it.

Canonicalization: one way to write it

add 3 %x and add %x 3 mean the same thing. Without help, every rule would need two versions, one for each side. Instead we add one canonicalization rule for each commutative op (add, mul, max, xor):

op(c, x) → op(x, c)      when c is a const and x is not

max is only commutative because the spec pins down its two tricky f32 cases: max(-0.0, 0.0) is +0.0 in either order, and a NaN on either side gives NaN. A naive if a > b then a else b returns b in both cases, so swapping the operands changes the answer. That matters, because recip -0.0 is -inf and recip 0.0 is inf.

Now every other rule can assume constants sit on the right. Canonical forms also help hash consing, because two equivalent expressions are more likely to become the same node.

Why hash consing makes this cheap

In a hash-consed graph, building a node that already exists hands you back the existing one. Two statements with the same (op, src, arg), where dtype and shape are part of the key, are a single UOp. Three things follow:

  • Shared work is rewritten once. If add %x 1 appears ten times, it's one node, simplified once.
  • "Did anything change?" is an identity check. If the rule returns the very same object, nothing happened. No deep comparison of trees.
  • Rules like xor(x, x) → 0 are a pointer comparison. Equal expressions are the same node, so "are both sources the same expression?" is just "are they the same object?" (OCaml's physical equality, ==Python's is).

Above: %a = add %x 1 and %b = add %x 1 collapse into one add, and mul %a %b points at it twice. Simplifying %out here leaves exactly 2 ops.

Termination: every rule must make progress

"Repeat until nothing changes" only stops if each rule moves the graph toward something smaller or more canonical. A rule like

add(x, y) → add(y, x)        # always swap

matches its own output, so the engine swaps forever. The canonicalization rule above is safe because it only fires when the const is on the left, and its output has the const on the right, where the rule no longer matches. A good habit: for each rule, name what it shrinks (number of ops, number of non-const sources, constants on the left).

Code it: a toy rewriter

Before rewriting UOps in your own compiler, write the loop on a toy expression type. Same engine: sources first, greedy, to a fixpoint.

A toy rewriter

Write simplify e. Simplify both children first, then apply these rules to the node, and keep re-applying them to the result until none fires. Integers are i32: fold with 32-bit wraparound.

Add (Const a, Const b)        → Const (a + b)
Mul (Const a, Const b)        → Const (a * b)
Add (Const c, x)              → Add (x, Const c)     (x not a Const)
Mul (Const c, x)              → Mul (x, Const c)     (x not a Const)
Add (x, Const 0)              → x
Mul (x, Const 1)              → x
Mul (x, Const 0)              → Const 0
Add (Add (x, Const a), Const b) → Add (x, Const (a + b))
Mul (Mul (x, Const a), Const b) → Mul (x, Const (a * b))

Leave everything else alone. Add (Const 1, Add (Const 2, Var "y")) becomes (y + 3), which takes three rules in a row.

From a tree to a shared DAG

The toy works on a tree, so a shared subexpression gets simplified once per path that reaches it. On a hash-consed graph that can be exponential: a chain of 300 lines like %x2 = add %x1 %x1 has 2300 paths, and rebuilding it as a tree splits every shared node into copies. Instead, walk the graph sources first (the toposort from lesson 0.3) and keep a memo from each old node to its new node:

simplify root:
  new = empty map, keyed by node identity
  for u in toposort(root):
    n = mk(u.op, [new[s] for s in u.src], u.arg, u.dtype, u.shape)
    while a rule rewrites n to some r that is not n:
      n = r
    new[u] = n
  if new[root] is root: return root
  return simplify(new[root])

mk is your hash-cons constructor, and the rules build their results with it too. Every node is visited once per pass, and two rebuilt nodes that come out equal are the same node again, so xor(x, x) → 0 still sees one object on both sides.

Key idea

A simplifier is a small set of local, obviously-correct rules plus a dumb loop. All the cleverness lives in choosing rules, and every rule has to give exactly the same answer as the interpreter on every input.

Your folder sees mul 1073741824 4 (that's 230 × 4). What i32 constant should it produce?

1073741824 is 2 to the 30th, so the product is 2 to the 32nd. Keep only the low 32 bits.

232 wraps around to 0 in 32-bit two's complement. Folding has to wrap exactly like the interpreter does.
