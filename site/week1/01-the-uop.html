Week 1 · Lesson 1

The UOp: one node type for everything

The interpreter you wrote runs a program one line at a time and then forgets it. A compiler has to keep the program, so it can study it and improve it before running it. In this lesson you decide what one piece of that kept program looks like, and you learn the trick that stops the same piece from being built twice.

Goal

Describe any program as a graph of nodes with three fields each, and build those nodes so that the same one is never made twice.

You'll use

The picture of boxes and arrows from Run your first program, and apply, run and env from Build the thing that runs it.

In Python: a dataclass (P.4) and a function that calls itself (P.5).

In OCaml: a record and option (O.4) and let rec (O.2).

Your interpreter forgets the program

Your run loop reads a line, works out a number, saves it in env and moves on. Try it on this program:

%a   = add 2 3
%b   = add 2 3
%out = mul %a %b

Guess first. How many times does your run loop call apply for this program?

The loop calls apply once for each line, whatever the line says.

Three, once per line. Lines 1 and 2 ask for the same sum, but the loop can't tell. When it reads line 2, all it has left of line 1 is the number 5.

A person sees at once that the sum only needs doing once. An interpreter that keeps only numbers never can. So a compiler keeps the whole program, in a form it can look over and improve, and runs it afterward.

That form is the picture from step 1. Press Next and watch what line 2 does.

Line 2 made no new box. This lesson shows how your compiler gets there: first what one box is, then how to never build the same box twice.

One box, three fields

A box in the graph is called a node. Your compiler has one type of node for everything, named UOp (short for micro operation). Every node has the same three fields:

UOp(op, src, arg)
  • op: what the node does, like add or mul.
  • src (sources): the nodes it reads, in order. These are the arrows coming into the box.
  • arg: one piece of data that is not a node. Most nodes have none.

Here is %out = mul %a 4 turned into a node:

  1. Name the op. It is mul.
  2. Find the sources. %a is the node an earlier line made. 4 is a node too: its op is const (a constant, a fixed number), it has no sources and its arg is 4.
  3. Fill the arg. mul needs no extra data, so it has none.

The name %out is not a field. A name is a label the text uses to point at a node.

In the node for the number 7, which field holds the 7?

The 7 is data, not another node, and the op says what kind of node this is.

The op is const, the sources are empty and the arg is 7. In .uir text you never write const. You write the number.

Why three fields are enough

Anything a node needs is either another node, which goes in src, or it isn't, and goes in arg. So every op fits:

Finish value

value works out the number a node stands for. It calls itself on the node's sources. Two places are wrong.

The constant. A const node returns 0. It should return the number kept in its arg.

The multiply. mul returns its first source and ignores the second. It should multiply the two.

The program the official week 1 reference opens with, for when you meet call and assert 
%x = param [] slot=0 dtype=i32 addrspace=ALU
%s = add %x %x
%v = call %s 3
%t = assert %v 6

Each name is defined once and refers to the same value wherever it is used. So the text is just a way to write down a graph: one node per name, plus the literals 3 and 6 and the scalar shape marker [], with arrows from each node to the nodes that read it. The call fills slot 0 with 3, so its body computes 3 + 3 = 6, and the assert checks that. Lessons 2 and 5 explain every piece.

Op names are written in capitals (ADD) when people talk about the compiler and in lowercase (add) in .uir text. They're the same op. Source order matters: CMPLT a b is a < b, not b < a. Other args you'll meet: the target dtype=bool for a CAST. Inside the compiler there are no variables or blocks. A program is one expression, stored as a graph.

One mul. Under it, two copies of add, each with its own x and 3.

Seven: one mul, two add, two x and two 3. Drawn with sharing it is four.

The same program, drawn two ways
The tree has 7 boxes. The graph with sharing has 4.

The copy-everything drawing is a tree. The shared one is a DAG, a directed acyclic graph. Directed means each arrow points one way, from a source to its user. Acyclic means the arrows never loop back, because a line can only use lines above it.

Your compiler stores the DAG. A name used twice in the text is one node with two arrows out. ML compilers work this way because in a model one value often feeds many later ops.

The problem: the same work, over and over

Sharing is not just tidy. In this program from the tests, each line adds the previous value to itself. (%x0 = 1 names the number 1, and # starts a remark that the compiler skips.)

%x0 = 1
%x1 = add %x0 %x0
%x2 = add %x1 %x1
%x3 = add %x2 %x2      # ... keep going to %x94

Guess first. The value function you finished works out both sources of a node from scratch, every time, and never remembers an answer. To get %x3, how many times does it work out %x0?

%x3 needs %x2 twice. Each %x2 needs %x1 twice.

Twice for each level: 2 × 2 × 2 is 8. Every extra line doubles it again. It walks the graph as if it were a tree.

The cure has two halves. Build each node once, so the graph stays at 95 nodes. Then work each node out once: keep its answer the first time, the way env kept an answer for each name, and the run takes 95 steps. The suite's dag_sharing test is this chain at 94 levels, so your compiler needs both.

Hash consing: build each node once

The first half has an odd name. Hash consing means never build the same node twice. Every node you create goes through one table, called a cache. Its key is the node's three fields: (op, src, arg). If the key is already there, you get the existing node back. It is the same object, not an equal copy.

Step through four lines going into the cache.

Structure, not meaning

Hash consing is structural. add 2 3 and add 3 2 are different nodes, even though they're equal as numbers, because the sources are in a different order. Lesson 3 adds rewrite rules that make them meet.

What hash consing gives you for free, for when you write rewrite rules and your evaluator
  • Equality takes one step, however big the expression. "Are these two expressions the same?" becomes "are these the same object?". Rewrite rules like x xor x → 0 need exactly that check, and it doesn't walk any subtrees.
  • Sharing is automatic. Write 2 + 3 a hundred times and you still have one node.
  • Memoization has an easy key. Caching "the value of node n" by node identity means each node is computed at most once. (Once call arrives in lesson 5, this cache has to be per call, because the same param node means different values in different calls.)

In your real compiler each node also carries a dtype and a shape (see the last section), and they are part of the key.

Repair a node table

This make is almost a hash-consing table. Two places are wrong.

The key. It only looks at the op, so two add nodes with different sources would collide. It should be the op plus the ids of the sources.

The hit. When the key is already in the table it builds a copy. It should hand back the node that is stored there.

Write the table yourself

Write create (). It returns a make function with its own private table. make op src must return the same node (the same object: ==is) when it has already built a node with that op and those exact source nodes. Otherwise it builds a new node whose id is the next number: 0, 1, 2 and so on.

Count the sharing

That was the first half of the cure. The second half is to visit each node once when you walk the graph, by remembering which nodes you have already seen. Here you use that to count nodes. Your evaluator will use it to keep answers.

Count distinct nodes

Write dag_size t: the number of physically distinct nodes reachable from t. A node reached twice counts once. dag_size (dbl 3) is 4, and dag_size (dbl 60) has to finish, so walking the tree is out.

Put sharing to work

Sharing also lets you write smaller programs. This one is in .uir, like the programs you wrote in step 1.

x to the 8th in 3 ops

The starter computes x⁸ correctly with 7 muls. Rewrite %out to use at most 3 ops. Sharing is the whole trick: a node can feed both sides of a mul. %x = param [] slot=0 dtype=i32 addrspace=ALU is the input the tests fill in (lesson 2 explains params), and params and literals don't count as ops.

i32 wraps, so 16⁸ is 0. Your program gets that for free.

What else a node knows

Three more facts ride along with every node. The compiler works them out from the node's op and its sources when the node is built.

  • dtype: the kind of value. i32 is a whole number that fits in 32 bits. One past the largest, 2,147,483,647, wraps around to the most negative, -2,147,483,648. bool is true or false. cmplt a b asks "is a less than b?", so its dtype is always bool.
  • shape: how many values the node holds. One value has shape (). stack 1 2 3 packs three values into one node, with shape (3,).
  • cost: how much work the program is, counted before it runs. Each distinct add or mul costs 1. Numbers cost 0.

A node that can't get a valid dtype, such as add 1 true, is refused when it is built. That is the type checker, and you build it in lesson 2.

A test file ends with %t = assert a b, which checks that a equals b. It costs 0.

What is the cost of this program?

%a = add 2 4
%m = mul %a %a

Count each distinct op once, however many arrows leave it.

One add and one mul: 2. The add is used twice but it is one node, so it counts once.

The official reference gives every node one more property, worked out the same way. Bounds are the smallest and largest value a node could ever have. For an i32 param %p with no limits, max %p 0 is in [0, 2³¹-1], and mod of that by 8 is in [0, 7]. They decide whether an index is safe, and lesson 4 covers them.

Static cost in full, for when a test comes back OVERBUDGET

Static cost says how much work a program is before you run it. Add up a cost for each distinct node the assert can reach, once per node however many times it's used. Literals, params and the assert cost 0. [] and index cost 1. Every other op costs its number of result elements, which is 1 for a scalar. A call costs 1 plus the cost of its body (lesson 5).

That makes sharing visible in the number. Here are two programs that both compute 36:

A week 1 test whose cost is 1,000,000 or more is never run: the answer is OVERBUDGET (lesson 2). Cost counts each node once, so a big shared graph can still be cheap. What costs a lot is calling the same body many times, because every call pays for its body again. The doubling chain stops at 94 levels because a week 1 file may hold fewer than 100 nodes.
