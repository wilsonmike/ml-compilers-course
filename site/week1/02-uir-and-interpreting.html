The .uir format, and running it

.uir is the text form of a UOp graph: each binding names one node. Your first milestone is an interpreter (a program that runs another program directly instead of translating it). It reads the file, builds hash-consed nodes, checks them, evaluates the assert and prints one line saying how it went.

Want it slower?

Your interpreter has to compute with 32-bit integers that wrap, and with a division that floors (rounds down, like Python's //, not toward zero like C's /). H.4 Numbers that behave like C goes through both slowly, in your language. Its float sections are a head start on week 2: week 1 has no floats.

The spec is the source of truth

Everything here summarizes spec/uir-week1.md, which follows the official 10-411 week 1 reference. If this page and the spec disagree, the spec wins.

Anatomy of a binding

%flag =definitioncastop%xsourcedtype=boolattribute# commentignored

A .uir file is a list of tokens, not lines. Here they all are:

tokenexamplemeaning
DEF%x=a definition. %x= and %x = are both one token.
REF%x, %0a defined name: % and then letters, digits or underscores
INT-7, 0xff, 007an i32 literal, decimal or hex. Leading zeros are fine: 007 is 7.
BOOLtrue, falsea bool literal
OPadda lowercase op name
ATTRslot=0one key=value token, with no spaces inside
[ ][3 6]brackets around the elements of a stack
file    := binding+ EOF
binding := DEF rhs
rhs     := OP atom* ATTR* | atom
atom    := REF | INT | BOOL | '[' atom* ']'
  • A newline is just whitespace. A binding may span lines, and several may share one. A comment runs from # to the end of the line.
  • Define a name above its first use, and only once. So the file is already in a valid evaluation order.
  • There's no const op in the text. A constant is written as its literal, and a binding can be a single atom: %x = 5, %y = %x, %v = [10 20 30].
  • Attributes come after every source, and each key at most once. cast dtype=bool 1 and cast 1 dtype=bool dtype=i32 are rejected, and so is an attribute the op doesn't take, like add 1 2 dtype=i32.

Params in one paragraph

%x = param [] slot=0 dtype=i32 addrspace=ALU declares an input: a scalar ([]) i32 in slot 0. Every week 1 value lives in the ALU address space, so that part never changes this week. The exercises in lessons 1 to 4 use params: the tests fill slot 0 (and 1, and so on) with numbers and print what your %out computes. Lesson 5 shows how call fills params inside a program. Until then, think of a param as "a number the test hands in". In a test file, nothing fills a param that sits outside any call, so that file is rejected (lesson 5).

No implicit conversion

add 1 true is rejected, not 2. 1 is an i32 and true is a bool, and binary ops need matching dtypes. Write add 1 %b with %b = cast true dtype=i32. C would quietly convert for you. Here, the conversion has to be its own visible node. Floats, f32, arrive in week 2.

The ALU ops, the ones that compute on values, are below. The spec has the full typing rules.

opmeans
add a b, mul a ba + b, a * b

max a bthe larger of a and b
xor a bbitwise exclusive or for i32, logical for bool

where c a ba if the bool c is true, else b. Both branches are evaluated.
cast a dtype=Ta converted to dtype T (rules below)

add, mul, max, xor and cmplt also take two bools. They compute on 0 and 1 and turn the answer back into a bool, so add true true is true (it acts as or) and mul acts as and.

Evaluating: sources first

To evaluate a node, first evaluate its sources. Because names are defined before use, the file order is already a topological order: every node comes after its sources. So the simplest correct evaluator is a recursive eval node that evaluates the sources first and caches each result. Run it on the assert. (Once call arrives in lesson 5, that cache must be per call, because the same param node means different values in different calls.) Step through it:

The assert is the root

A test file ends with exactly one assert, as its last binding, and nothing uses it as an operand. Its left side is the program's return value, a scalar in week 1. Its right side is the expected value: a literal, or a stack of literals, never a computation. And every node must be reachable from the assert, call bodies and unused call arguments included. So this file is rejected. The division is fine (div 1 0 is -1, see below), but nothing reaches it:

%bad = div 1 0     # never needed
%t   = assert 1 1  # the only root

Change the assert to assert %bad -1 and it's a MATCH. Nothing in week 1 can fail at run time: every op gives an answer for every input, and the checks that could fail all happen before anything runs.

Four outcomes

Your compiler is one program, run as ./compile FILE.... For each file it prints one line to stdout: the outcome, one space, and the path exactly as it was given. A second subcommand, simplify, arrives in lessons 3 and 4.

outcomewhenexample
MATCHthe program ran, and the values are equal%t = assert 3 3
MISMATCHthe program ran, and the values differ%t = assert 3 4
REJECTEDinvalid before anything runs: a parse error, a type error, an unsafe index, a broken test-file rule%t = assert 3 true
OVERBUDGETa size or cost limit is hit, so it never runsa file with 100 nodes

The checks happen in a fixed order, and the first one that decides stops the rest:

  1. Over 4096 bytes: OVERBUDGET, without even parsing.
  2. Parse. A file that breaks the grammar: REJECTED.
  3. 100 or more nodes, or 300 or more source edges: OVERBUDGET. Nodes are counted after hash consing, literals and [] included, reachable or not. An edge is one source of one node.
  4. Validate: dtypes, shapes, index safety (lesson 4), call arguments (lesson 5) and the test-file rules. Any failure: REJECTED.
  5. Static cost (lesson 1) of 1,000,000 or more: OVERBUDGET.
  6. Run it: MATCH or MISMATCH.
$ ./compile tests/week1/run/rejected_assert_dtype.uir tests/week1/run/basic_add.uir
REJECTED tests/week1/run/rejected_assert_dtype.uir
MATCH tests/week1/run/basic_add.uir

A test's expected outcome is in its file name: a mismatch_, rejected_ or overbudget_ prefix, and MATCH otherwise. The grader copies each test to a neutral name before your compiler sees it, so the name can't help you.

i32: wrapping, flooring, never failing

Wraparound. add 2147483647 1 is -2147483648. In C, signed overflow is undefined behavior. Here it's defined: the result is reduced mod 2³² into the signed range.

Division floors (like Python's //, unlike C's /, which truncates toward zero). div a b is floor(a / b), and mod a b is a - b * floor(a / b), so a nonzero remainder has the sign of b.

abdiv a bmod a bC a / b, a % b

So neither op can fail. div x 0 is -1 and mod x 0 is x. div INT_MIN -1 is 2³¹, which wraps to INT_MIN, and mod INT_MIN -1 is 0. shl a b shifts by b mod 32, which is always 0 to 31: shl 1 31 and shl 1 -1 are both -2147483648, and shl 1 32 is 1.

div and mod, exactly

Write divmod32 a b for i32 values held in OCaml ints, returning .uir's div and mod as a pair. The quotient is floor(a / b), wrapped to 32 bits, and the remainder is a - b * floor(a / b). When b is 0 the pair is (-1, a). (Lesson 0.6 had the quotient alone. This one adds the remainder.)

Write divmod32(a, b) for i32 values held in Python ints, returning .uir's div and mod as a pair: the floor quotient wrapped to 32 bits, and the remainder a - b * floor(a / b). When b == 0 the pair is (-1, a). (Lesson 0.7 had the quotient alone. This one adds the remainder.)

Check the table above against what your language's own division does. OCaml's / and mod truncate, like C.Python's // and % floor already, but they never wrap, and they raise on zero.

What assert means by "equal"

  • i32 and bool compare exactly, and both sides must have the same dtype: assert 3 true is rejected.
  • The expected side must be written out. %e = 6 then assert %s %e is fine, because %e just names a literal. assert %s %f with %f = add 3 3 is rejected.

Casts. A number to bool means "not zero": cast 5 dtype=bool is true. A bool to i32 gives 0 or 1. A cast to the dtype a value already has changes nothing.

Floats wait for week 2

Week 1 is i32 and bool only. A float literal like 1.5 is rejected. f32, its rounding rules and its odd values (nan, inf, -0.0) are taught in week 2, lesson 1, along with the exercise that rounds to f32.

Check yourself

What is div -7 2?

The exact quotient is -3.5. .uir's division floors: it rounds toward minus infinity, not toward zero.

Floor: -3.5 becomes -4. C's / would give -3, and Python's // agrees with .uir.

What is mod -7 2?

Use a - b * (a div b), with the floored quotient from the previous quiz.

-7 - 2*(-4) = 1. A nonzero remainder has the sign of the divisor, here positive.

What is div 5 0?

Division by zero isn't an error in .uir. The spec picks one fixed answer for every x.

div x 0 is -1, whatever x is. And mod x 0 is x, so mod 5 0 is 5.

What is add 2147483647 1?

i32 addition wraps around. What comes after the largest i32?

i32 wraps: INT_MAX + 1 = INT_MIN.

What does ./compile print for this file?

%a = add 1 true
%t = assert %a 2

Look at the dtypes of the two literals. Does .uir ever convert between them for you?

1 is an i32 literal and true is a bool. There's no implicit conversion, so add rejects mismatched dtypes before anything runs.

Outcome?

%bad = div 1 0
%t   = assert 1 1

The division itself is fine: div 1 0 is -1. Look at the test-file rules instead. Is %bad reachable from the assert?

Every node must be reachable from the assert, and nothing reaches %bad. With assert %bad -1 instead, the file would be a MATCH.

Outcome?

%a = add 2 2
%t = assert %a 5

The program parses and type checks. What does the assert compare?

A valid program whose values differ: 4 is not 5. A test that expects this outcome is named with a mismatch_ prefix.

A 5000-byte file also has a typo on its first line. Outcome?

The checks run in a fixed order. Which one comes before parsing?

The byte limit is checked before the file is parsed, so the typo is never seen. The order is fixed so every compiler gives the same answer.

What is add 0xff 007?

0xff is hex. Leading zeros in a decimal literal change nothing.

0xff is 255 and 007 is 7, so the sum is 262.

What is shl 1 32?

shl shifts by the amount mod 32.

32 mod 32 is 0, so nothing moves: 1. That's also what x86 does with a 32-bit shift, and it's why a shift can never fail.
