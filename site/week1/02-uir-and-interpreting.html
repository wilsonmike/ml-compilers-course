The .uir format, and running it

.uir is the text form of a UOp graph: one node per line. Your first milestone is an interpreter (a program that runs another program directly instead of translating it). It reads the file, builds hash-consed nodes, type-checks them, evaluates what the asserts need, and exits with the right code.

The spec is the source of truth

Everything here summarizes spec/uir-week1.md. The official course hasn't published its grammar yet, so this one is ours and provisional. If this page and the spec disagree, the spec wins.

No implicit conversion

add 1.5 1 is a type error, not 2.5. 1 is an i32 and 1.5 is an f32, and binary ops need matching dtypes. Write add 1.5 1.0, or cast one side. C would quietly convert for you. Here, the conversion has to be its own visible node.

Evaluating: sources first

To evaluate a node, first evaluate its sources. Because names are defined before use, the file order is already a topological order: every node comes after its sources. So the simplest correct evaluator is a recursive eval node that evaluates the sources first and caches each result. Calling it on each assert, in file order, only ever touches what the asserts need. (Once call arrives in lesson 5, that cache must be per call, because the same param node means different values in different calls.) Step through it:

Asserts are the roots

A program's outputs are its asserts. They're checked in file order. A node no assert depends on is never evaluated. That makes this a valid program that exits 0, even though it contains a division by zero:

%bad = div 1 0     # never needed
%t   = assert 1 1  # the only root

Change the assert to assert %bad 0 and now the bad division is needed. That's a runtime error, so exit 2. Type errors are different: they're found while building nodes, so a type error anywhere in the file is exit 2, used or not.

i32: what a C programmer expects, made exact

Wraparound. add 2147483647 1 is -2147483648. In C, signed overflow is undefined behavior. Here it's defined: the result is reduced mod 2³² into the signed range.

Division truncates toward zero (like C, unlike Python's //). mod is whatever makes a = (a div b) * b + (a mod b) true, so its sign follows a.

f32: rounding after every step

An f32 has 24 bits of precision. After every op, the exact result is rounded to the nearest representable f32. A tie goes to the even neighbor, like rounding 2.5 to 2 and 3.5 to 4. If your language computes in 64-bit doubles, round back to 32 bits after each op, not once at the end.

16777216 + 1

2²⁴ = 16777216 is where f32 runs out of integers. add 16777216.0 1.0 is exactly halfway between 16777216 and 16777218, and it rounds to even, giving 16777216.0. The 1 just disappears.

0.1 + 0.2

In 64-bit doubles, 0.1 + 0.2 == 0.3 is famously false. In f32 it happens to be true: %s = add 0.1 0.2 then %t = assert %s 0.3 passes. If your interpreter uses doubles and forgets to round, it gets this wrong.

What assert means by "equal"

  • i32 and bool compare exactly.
  • f32 compares by value, so 0.0 equals -0.0.
  • Two NaNs count as equal, so assert nan nan passes. In IEEE, nan == nan is false. Our rule is chosen so tests can say "this should be NaN".
  • max with a NaN operand is NaN. cmplt with a NaN is false.
cast rules

cast 3.9 dtype=i32 is 3 and cast -3.9 dtype=i32 is -3, because f32 to i32 truncates toward zero. A NaN, or a value outside the i32 range, is a runtime error. bool to a number gives 0 or 1. A number to bool means "not zero".

Round to f32

OCaml's floatPython's float is a 64-bit double. Write f32, which rounds x to the nearest f32 (ties to even, overflow to inf), and add32, which adds two f32 values a and b the way your interpreter must: compute, then round.

The Int32 module can move a float through its 32-bit bit pattern. Look for bits_of_float.

The struct module can move a float through its 32-bit encoding, as in lesson 0.7. Remember what it does on overflow.

Look at the dtypes of the two literals. Does .uir ever convert between them for you?

1 is an i32 literal and 1.5 is f32. There's no implicit conversion, so add rejects mismatched dtypes when the node is built.

No assert depends on %bad, so it's never evaluated. Runtime errors only count when an assert needs the value.

Does this pass?

%s = add 16777216.0 1.0
%t = assert %s 16777216.0

f32 has 24 bits of precision, and 16777216 is 2 to the 24th. Can f32 represent 16777217?

When a value sits exactly halfway between two f32 numbers, the tie goes to the one whose last bit is even.

16777217 isn't representable in f32. It's a tie between 16777216 and 16777218, and ties round to even.

Does assert nan nan pass?

IEEE says NaN never equals NaN, but this course's spec defines assert equality on purpose. Check section 3.

The spec defines assert equality so you can test for NaN. Inside the program, cmplt still follows IEEE: any NaN gives false.

What is cast -3.9 dtype=i32?

Casting f32 to i32 truncates toward zero. Which integer is closer to zero, -3 or -4?

Truncate toward zero, not floor. cast 3000000000.0 dtype=i32 would be a runtime error, because it's out of range.
