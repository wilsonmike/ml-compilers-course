The .uir format, and running it

Your interpreter from the start steps ran programs that were already split into pieces. A real compiler is handed a text file. In this lesson you grow that interpreter one problem at a time, until it can read a .uir file and print one word saying how the run went.

Goal

Follow a .uir test file from its text to the one word your compiler prints for it: MATCH, MISMATCH, REJECTED or OVERBUDGET.

You'll use

The ten-line interpreter from Build the thing that runs it, and the idea from lesson 1 that a program is a graph of nodes, each built once.

In Python: cutting a string into words with .split() (P.3), tuples (P.3) and // and % (P.1).

In OCaml: lists and match (O.3), your own types such as Lit and Name (O.4) and / and mod (O.1).

From text to pieces

In the start steps, the line %out = mul %a 4 reached your run function as ('out', 'mul', 'a', 4)("out", "mul", Name "a", Lit 4). A file gives you only a row of characters, so the first job is to split it yourself.

Turning text into a structure a program can use is called parsing. For one simple line it takes four moves:

  1. Cut at the spaces. %out = mul %a 4 becomes five words.
  2. Take the name. It is the first word with its % removed: out.
  3. Take the op. It is the third word, mul. The second word is the =, and you skip it.
  4. Sort the values. A word that starts with % is an earlier name. Any other word is a number, but it is still text: the character 4, not the number 4. Convert it.

From a line of text to its pieces

parse_line turns one line of text, such as "%out = mul %a 4", into the tuple your interpreter from the start steps ran: ("out", "mul", Name "a", Lit 4). A name loses its % and becomes a Name. A number becomes a Lit.

Cutting the line, the name, the op and the first value are written. Two places still use Lit 0. In atom, a word that is not a name is a number: turn the text into an int. In parse_line, make b from y the same way a is made from x.

Feed each line of a file through parse_line and into the run you wrote in the start steps, and your interpreter reads text.

What a real file adds

Real .uir has a few more kinds of piece. Here is one line with all of them:

%flag =definitioncastop%xsourcedtype=boolattribute# commentignored
  • A binding is one name and what it stands for. So far every line has been one binding.
  • A source is a value the op reads: cast has one, add two and where three.
  • An attribute is extra data for the op, written key=value with no spaces, after the sources.
  • 0xff is 255 written in hex. true and false are values too.

One more thing breaks the cut-at-spaces plan. The format is made of tokens, the smallest pieces that mean something, like words in a sentence. A line break counts as a space and nothing more.

How many bindings does this file hold?

%a = add 2
     3 %t = assert %a 5

Don't count lines. Count the places where a name is followed by =.

Two: %a = add 2 3, spread over two lines, and %t = assert %a 5. %a=add 2 3 with no spaces is legal too, so a real parser reads tokens, not lines.

Every token and the grammar are in the reference.

Build nodes, don't compute yet

One plan changes from the start steps. There, each line's answer was saved under its name as soon as the line was read. Your compiler saves a node under each name, built through the hash-consing table from lesson 1, and computes nothing yet, because the whole program has to be checked before any of it runs.

Compute like the machine

Your interpreter now reads text. Does it get the right answers? Press Next and guess each value with ordinary school arithmetic.

School arithmetic says 65536 × 65536 is 4,294,967,296 and -7 ÷ 2 is -3.5. The program says 0 and -4, and it is right. The language fixes what happens in each case, so that every compiler gives the same result.

Numbers wrap at 32 bits

Whole numbers in .uir are of a kind called i32: an integer stored in 32 bits, which are 32 switches that are each on or off. That is enough for every whole number from -2,147,483,648 to 2,147,483,647 and no others. A result that goes past one end comes back in at the other, like a car's mileage counter rolling over. That is called wrapping.

add 2147483647 1 lands 1 past the largest i32. To come around, subtract 2³², which is 4,294,967,296. The result is -2,147,483,648, the smallest i32. The same rule turns 65536 × 65536 into 0. add and mul wrap. So does shl a b, which shifts a left by b bits, the same as doubling it b times. It only looks at b mod 32, a number from 0 to 31.

Python's numbers never wrapAn OCaml int is 63 bits wide, so your apply wraps the result of every add, mul and shl by hand:

def wrap(x):
    return (x + 2**31) % 2**32 - 2**31
let wrap x = Int32.to_int (Int32.of_int x)

Division rounds down

An i32 can't hold -3.5, so div rounds. It always rounds down, toward the more negative number, which is called flooring. Its partner mod gives the remainder that is left. Take div -7 2 and mod -7 2:

  1. Divide exactly. -7 ÷ 2 is -3.5.
  2. Round down. The next whole number below -3.5 is -4. So div -7 2 is -4, not -3.
  3. Find what is left. mod a b is a - b * (div a b). Here that is -7 - 2 × (-4), which is 1.

Your turn. What is div 7 -2?

Divide exactly first. Then go down to the next whole number, away from zero for a negative result.

7 ÷ -2 is -3.5, and rounding down gives -4. Then mod 7 -2 is 7 - (-2) × (-4), which is -1.

Here are the four sign cases and two odd ones, next to C, which rounds toward zero:

The last row matters most. Dividing by zero is not an error in .uir: div x 0 is -1 and mod x 0 is x. So no op can fail while a program runs. OCaml's / and mod round toward zero, like C.Python's // and % round down already, but they never wrap and they raise an error on zero.

div and mod, exactly

Write divmod32 for i32 values held in your language's own ints. It returns .uir's div and mod as a pair: the floor quotient wrapped to 32 bits, and the remainder a - b * floor(a / b). When b is 0 the pair is (-1, a). Check your answers against the table above.

Check types

Numbers are not the only values. The op cmplt a b (compare, less than) asks "is a less than b?". Its answer is true or false, not a number. So what happens when a program uses that answer as a number?

Guess first. 3 is less than 5, so %c is true. What should a compiler do with the second line?

%c = cmplt 3 5
%s = add %c 1

Two of these answers are guesses about what the writer meant. Which answer makes no guess?

It refuses. Options a and c are both reasonable guesses, and they disagree. A compiler that guesses can turn a slip into a wrong answer that nobody notices.

Every value has a dtype, short for data type: the kind of value it is. Week 1 has two that hold values: i32, a whole number, and bool, true or false. An op with two operands needs both to have the same dtype, so add 1 true is refused.

To mix them, say so with cast, an op that converts a value to the dtype named in its attribute. Here is the program from the quiz, repaired:

%c = cmplt 3 5
%n = cast %c dtype=i32
%s = add %n 1
  1. Find the dtypes. %c is a bool, because cmplt always makes one. 1 is an i32.
  2. Compare them. They differ, so add %c 1 would be refused.
  3. Convert in the open. cast %c dtype=i32 turns true into 1 and false into 0. Now add %n 1 has two i32 operands, and %s is 2.

A bool is what lets a program choose. where c a b gives a when c is true and b when it is false. Its first operand must be a bool, and the other two must share a dtype.

Exactly one of these is refused. Which?

One op needs a bool and was handed a number.

where chooses with a bool, and 1 is an i32. add true false has two operands of the same dtype, and on bools add acts as "or", so it is true. cmplt 4 4 is a legal question whose answer is false.

The check happens when the node is built, because that is when lesson 1 said its dtype is worked out. If no dtype fits, the program is refused before anything is computed. The rule for every op is in the reference.

Finish the type check

result_dtype op a b is given an op and the dtypes of its two operands, each "i32" or "bool". It returns the dtype of the result, or "rejected" when the op does not accept those operands.

The branch for add, mul, max and xor is right. Two branches are too trusting. cmplt needs both operands to have the same dtype, and its result is always "bool". div, mod and shl need both operands to be "i32".

Judge the run

Every test file ends with one assert a b, which compares the program's answer a with the expected value b. Nothing uses the assert and everything leads to it, so it is the root of the graph: the node you start from.

Running starts at the root and works backward. To get a node's value, first get the values of its sources, then apply the op. Each answer is saved under its node, so a node used twice is computed once. (H.2 Walking a graph once is the slow version.) Step through a whole test:

That run ended in MATCH. Had the assert expected 21, it would have ended in MISMATCH. But a file can go wrong before it runs.

Guess first. A test file has add 1 true on its first line. Its last line is an assert that would compare 4 with 5. What should the compiler print?

When is a type error found? Is that before or after the program runs?

The type error is found while the graph is built, so the program never runs and the assert never compares anything. The compiler prints exactly one word for each file, and the first check that fails decides it.

Four outcomes, six checks

For each file your compiler prints one line: the outcome, one space, and the path exactly as it was given. MATCH and MISMATCH are for a program that ran. REJECTED is for a file that breaks a rule. OVERBUDGET is for one too big or too costly to run. A file can break several rules, and every compiler has to print the same word. So the checks run in a fixed order, and the first one that decides stops the rest:

  1. Size. A file over 4096 bytes is OVERBUDGET. It is not even parsed.
  2. Parse. Text that breaks the format is REJECTED.
  3. Count. 100 or more nodes, or 300 or more source edges, is OVERBUDGET. A source edge is one arrow in the graph.
  4. Validate. This checks every other rule the format has. Wrong dtypes, or a broken test-file rule, is REJECTED.
  5. Cost. A static cost (lesson 1) of 1,000,000 or more is OVERBUDGET.
  6. Run. Equal values are a MATCH. Different values are a MISMATCH.

The cheap checks come first, and running comes last, when nothing is left that can go wrong.

Put the checks in order

outcome is handed a record of what the compiler found out about one file: its size in bytes, whether it parses, its nodes and source edges, whether it is valid, its static cost, the value it computes (got) and the value its assert expects (want). It returns the one word the compiler prints.

Every check is here with the right limit, but they run in the wrong order. Put them in the order of the list above. Then repair the last branch: a program that runs is not always a MATCH.

Everything must lead to the assert

One more rule: every node must be reachable from the assert by following arrows backward. A binding that nothing uses breaks the rule, so this file is rejected, though div 1 0 itself is fine:

%bad = div 1 0     # never needed
%t   = assert 1 1  # the only root

Change the assert to assert %bad -1 and it's a MATCH.

A test's file name says which outcome it expects: a mismatch_, rejected_ or overbudget_ prefix, and MATCH otherwise.

Take inputs

You have been copying one long line since the first start step. Now you can read it:

%x = param [] slot=0 dtype=i32 addrspace=ALU
  1. param is the op. It makes an input, a value handed in from outside.
  2. [] is its one source. It says the input is a scalar: a single value and not a list of them.
  3. slot=0 says which input this is. Inputs are numbered from 0.
  4. dtype=i32 says what kind of value comes in.
  5. addrspace=ALU says where the value lives. In week 1 it is always ALU.

A program needs a second input, a yes or no value. Which line declares it?

Two attributes change: which input it is, and what kind of value it holds.

Slots count from 0, so the second input is slot=1. A yes or no value is a bool.

Who fills a param?

In the exercises so far, the tests do: they fill each slot with numbers and check what your %out computes. Inside a program the call op does it (lesson 5). In a test file, nothing fills a param that sits outside any call, so that file is rejected.

The spec is the source of truth

This page summarizes spec/uir-week1.md, which follows the official 10-411 week 1 reference. If they disagree, the spec wins.

Every token and the grammar, for when you write the parser

A .uir file is a list of tokens, not lines. Here they all are:

tokenexamplemeaning
DEF%x=a definition. %x= and %x = are both one token.
REF%x, %0a defined name: % and then letters, digits or underscores
INT-7, 0xff, 007an i32 literal, decimal or hex. Leading zeros are fine: 007 is 7.
BOOLtrue, falsea bool literal
OPadda lowercase op name
ATTRslot=0one key=value token, with no spaces inside
[ ][3 6]brackets around the elements of a stack

The grammar says how tokens may follow each other. Read := as "is made of", | as "or", * as "zero or more" and + as "one or more". An atom is a value written in place: a name, a literal or a bracketed list.

file    := binding+ EOF
binding := DEF rhs
rhs     := OP atom* ATTR* | atom
atom    := REF | INT | BOOL | '[' atom* ']'
  • A newline is just whitespace. A binding may span lines, and several may share one. A comment runs from # to the end of the line.
  • Define a name above its first use, and only once. So the file is already in a valid evaluation order.
  • There's no const op in the text. A constant is written as its literal, and a binding can be a single atom: %x = 5, %y = %x, %v = [10 20 30].
  • Attributes come after every source, and each key at most once. cast dtype=bool 1 and cast 1 dtype=bool dtype=i32 are rejected, and so is an attribute the op doesn't take, like add 1 2 dtype=i32.
  • The text is case-sensitive ASCII. Outside comments, every character is printable ASCII or whitespace (space, tab, carriage return, newline). A comment can't sit between a name and its =.
Every literal, and the ones that are rejected

A literal is a value written out in the text, like 3 or true.

3, -7, 007a constant, dtype i32. It must fit in 32 bits.
0xff, 0x7fffffffhex, also i32. A lowercase 0x and no sign. 0x80000000 doesn't fit, so it's rejected.
true, falsea constant, dtype bool
[1 2 3]the same node as stack 1 2 3, shape (3,) (lesson 5)

Week 1 is i32 and bool only. A float literal like 1.5 is rejected. f32, its rounding rules and its odd values (nan, inf, -0.0) are taught in week 2, lesson 1, along with the exercise that rounds to f32.

The three dtypes, every op and the cast rules, for when you write the type check and apply

There are three dtypes and no implicit conversions. "Implicit" means done for you without being asked.

dtypevalueswatch out
voidnoneOnly [] and assert have it, and neither can be an operand of an ALU op.
booltrue, falseWhat cmplt returns, and what where takes. As a number it's 0 or 1.
i32-2³¹ to 2³¹-1add, mul and shl wrap around.
No implicit conversion

add 1 true is rejected, not 2. 1 is an i32 and true is a bool, and binary ops need matching dtypes. Write add 1 %b with %b = cast true dtype=i32. C would quietly convert for you. Here, the conversion has to be its own visible node. Floats, f32, arrive in week 2.

The ALU ops, the ones that compute on values, are below. The spec has the full typing rules.

opmeans
add a b, mul a ba + b, a * b
div a b, mod a bi32 quotient and remainder, floored (see Compute like the machine)
max a bthe larger of a and b
xor a bbitwise exclusive or for i32, logical for bool
shl a ba shifted left by b mod 32 bits, i32 only
cmplt a ba < b, as a bool
where c a ba if the bool c is true, else b. Both branches are evaluated.
cast a dtype=Ta converted to dtype T (rules below)

add, mul, max, xor and cmplt also take two bools. They compute on 0 and 1 and turn the answer back into a bool, so add true true is true (it acts as or) and mul acts as and.

Casts. A number to bool means "not zero": cast 5 dtype=bool is true. A bool to i32 gives 0 or 1. A cast to the dtype a value already has changes nothing.

Edge cases of wrapping, div, mod and shl, for when a test disagrees with you

Wraparound. add 2147483647 1 is -2147483648. In C, signed overflow is undefined behavior. Here it's defined: the result is reduced mod 2³² into the signed range.

Division floors (like Python's //, unlike C's /, which truncates toward zero). div a b is floor(a / b), and mod a b is a - b * floor(a / b), so a nonzero remainder has the sign of b.

So neither op can fail. div x 0 is -1 and mod x 0 is x. div INT_MIN -1 is 2³¹, which wraps to INT_MIN, and mod INT_MIN -1 is 0. shl a b shifts by b mod 32, which is always 0 to 31: shl 1 31 and shl 1 -1 are both -2147483648, and shl 1 32 is 1.

INT_MIN is the smallest i32, -2147483648, and INT_MAX is the largest, 2147483647.

How to evaluate: sources first, with a cache

To evaluate a node, first evaluate its sources. Because names are defined before use, the file order is already a topological order: every node comes after its sources. So the simplest correct evaluator is a recursive eval node that evaluates the sources first and caches each result. Run it on the assert. H.2 Walking a graph once builds this slowly, with pictures, in your language. (Once call arrives in lesson 5, that cache must be per call, because the same param node means different values in different calls.)

where evaluates both of its branches even though it returns only one. Nothing in week 1 can fail at run time, so that is never visible.

Every rule a test file must follow, and what assert means by "equal"

A test file ends with exactly one assert, as its last binding, and nothing uses it as an operand. Its left side is the program's return value, a scalar in week 1. Its right side is the expected value: a literal, or a stack of literals, never a computation. And every node must be reachable from the assert, call bodies and unused call arguments included.

  • i32 and bool compare exactly, and both sides must have the same dtype: assert 3 true is rejected.
  • The expected side must be written out. %e = 6 then assert %s %e is fine, because %e just names a literal. assert %s %f with %f = add 3 3 is rejected.
  • "Exactly one" counts assert bindings. Two assert lines are two asserts even when they are identical and hash cons to one node.
  • "Last binding" means the last binding names the assert node. %u = %t after %t = assert ... is fine.
  • A file that is all comments has no bindings, so it is rejected.
The complete check order, with every limit and what each step covers

The checks happen in a fixed order, and the first one that decides stops the rest:

  1. Over 4096 bytes: OVERBUDGET, without even parsing.
  2. Parse. A file that breaks the grammar: REJECTED.
  3. 100 or more nodes, or 300 or more source edges: OVERBUDGET. Nodes are counted after hash consing, literals and [] included, reachable or not. An edge is one source of one node.
  4. Validate: dtypes, shapes, index safety (lesson 4), call arguments (lesson 5) and the test-file rules. Any failure: REJECTED.
  5. Static cost (lesson 1) of 1,000,000 or more: OVERBUDGET.
  6. Run it: MATCH or MISMATCH.

Step 2 covers more than the grammar. It also catches a name that is used before it is defined or defined twice, an integer literal that doesn't fit in an i32, an unknown op, and a bad attribute key (one the op doesn't take, or the same key twice). Attribute values, operand counts, dtypes and shapes wait for step 4.
