Moving memory

Your compiler can check and run device loops, but render-cuda does not know them yet. A kernel on device 1 can only read device 1's memory, so the host has to move data there and bring results back. Here you learn the four steps it prints for that, and how the grader counts the bytes.

Goal

Read a device loop and say the lines render-cuda prints for it, and how many bytes they move.

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

A loop over 2 devices reads x (16 elements) at d*8 + e, with e from 0 to 7, and w (2 elements) at the block number b. Where do they live?

A read-only buffer is sharded only when every read of it has the form d*S + e.

Every read of x follows the slice rule with S = 8, and 2 shards of 8 fit in 16. The read of w does not use d, so w is replicated.

In week 8, what did the host function kernel print for a program with one global loop of 2 blocks of 4 threads?

Where were the buffers when kernel was called?

The buffers were already on the GPU, so one launch line was enough. With several devices that is no longer true.

The buffers b0, b1 and b2 are x, w and o. When kernel is called, all three are on device 0.

Device 1 is about to run a kernel that reads x[8] to x[15]. What has to happen first?

Lesson 10.1's one hard fact: what do devices not share?

Devices do not share memory. So the host gets room on device 1 and copies its shard of x in. The hidden lines do that.

The host function is week 8's launch with steps around it, four in all: scatter, launch, wait and gather. The next screens take one step each.

Scatter: room and a copy for every buffer

The loop never reads o. It only stores into it. Yet in the figure, each device's shard of o was copied in too.

Why copy in a buffer the kernel only writes?

Say the kernel skips one element of the shard. What would gather copy back for it?

New memory is not zeroed, and gather copies the whole shard back. Copying o in first means an element the kernel leaves alone comes back unchanged. Every buffer the loop touches is copied in.

The six hidden lines:

    s0_[r6] = (int32_t *)UIR_ALLOC(r6, 8 * sizeof(int32_t));
    UIR_COPY(r6, s0_[r6], 0, b0 + r6 * 8, 8 * sizeof(int32_t));
    s1_[r6] = (int32_t *)UIR_ALLOC(r6, 2 * sizeof(int32_t));
    UIR_COPY(r6, s1_[r6], 0, b1, 2 * sizeof(int32_t));
    s2_[r6] = (int32_t *)UIR_ALLOC(r6, 8 * sizeof(int32_t));
    UIR_COPY(r6, s2_[r6], 0, b2 + r6 * 8, 8 * sizeof(int32_t));
  1. Make room. UIR_ALLOC(d, bytes) gets memory on device d, an allocation. For a sharded buffer it holds S elements, here 8. s0_[r6] keeps one pointer per device.
  2. Copy the shard in. UIR_COPY(dst_dev, dst, src_dev, src, bytes) copies here to device r6 from device 0, starting at b0 + r6 * 8: element d*S, where shard d starts.
  3. Replicated buffers come whole. All of w goes to every device.

Device 0 gets its own allocations too, so the kernel is the same on every device.

Launch: the same line, new arguments

In week 8 the launch was UIR_LAUNCH(k0, 2, 4, b0, b1);. Now it sits in a loop over the devices, and passes s0_[r6] for x.

On device 1, why pass s0_[1] and not b0 + 8, which points at x[8]?

Where does b0 live?

b0 and everything after it is device 0's memory. Device 1's copy of its shard is the allocation s0_[1].

  for (int32_t r6 = 0; r6 < 2; r6++) {
    UIR_DEVICE(r6);
    int32_t v7 = (int32_t)((uint32_t)r6 * (uint32_t)8);
    UIR_LAUNCH(k0, 2, 4, s0_[r6], s1_[r6], s2_[r6], r6, v7);
  }
  1. Select the device. UIR_DEVICE(r6): launches from here on go to device r6.
  2. Compute the host values. %ds = mul %d 8 is in the device loop but outside the kernel, so the host computes it per device: v7.
  3. Launch. 2 blocks of 4 threads, as in week 8, on each device. Then the device's allocations in place of the buffers, the device index r6 and the host values.

A launch does not wait for its kernel, so both devices run at once.

Inside the kernel: element d*S + e is element e

The kernel's parameters b0, b1 and b2 are now the allocations. Three lines of k0 (the whole kernel is in a toggle below):

    int32_t v14 = (int32_t)((uint32_t)v7 + (uint32_t)v13);
    int32_t v17 = b0[(int32_t)((uint32_t)(v14) - (uint32_t)r6 * 8u)];
    b2[(int32_t)((uint32_t)(v14) - (uint32_t)r6 * 8u)] = v18;

v14 is %i, the element's place in the whole buffer. But b0 holds only this device's 8 elements.

On device 1, one thread has v14 = 14. Device 1's allocation holds x[8] to x[15]. At which place in it is x[14]?

Place 0 of the allocation holds x[8].

14 minus 8 is 6. The kernel computes exactly that: v14 - r6 * 8.

The slice rule from lessons 7.4 and 9.1 again: a sharded access is at d*S + e, with e from 0 to S - 1. Shard d starts at element d*S of the buffer and at place 0 of the allocation. So element d*S + e is place e, and the kernel subtracts d*S from every offset into a sharded buffer. That is why it takes the device index. The replicated w is read as b1[r8], unchanged.

Find an element in a device's allocation

Write alloc_offset stride d i: where element i of a buffer sits in device d's allocation. stride is the buffer's S, or 0 when it is replicated. Return -1 when the element is not in that device's allocation at all. alloc_offset 8 1 14 is 6.

Wait, then gather

After the launches, UIR_SYNC() waits until every device has finished its kernels. Only then is it safe to copy results back.

The scatter made six allocations. Which ones should gather copy back to device 0?

Which buffer did the kernels change?

Only o was written. The copies of x and w hold what device 0 already has, so they are just freed.

  UIR_SYNC();
  for (int32_t r6 = 0; r6 < 2; r6++) {
    UIR_FREE(r6, s0_[r6]);
    UIR_FREE(r6, s1_[r6]);
    UIR_COPY(0, b2 + r6 * 8, r6, s2_[r6], 8 * sizeof(int32_t));
    UIR_FREE(r6, s2_[r6]);
  }
  UIR_DEVICE(0);
  1. Copy the written shard back. The scatter's copy turned around: to device 0 at b2 + r6 * 8, from device r6.
  2. Free. UIR_FREE(d, p) gives each allocation back.
  3. Back to device 0. A global loop after the device loop runs on device 0, as in week 8.

Those are the five new names. Like UIR_LAUNCH, they come from the harness, so one file runs on real GPUs and in the emulator.

What the host may compute

Week 8's kernel form put all work inside kernels. Week 10 lets a global loop sit directly inside a top-level device loop, and between them the host may do i32 add and mul on the device index and literals, like v7. The test c_err_load_outside_kernel puts a load of x[d*8] there instead.

What does render-cuda do with the load?

Only two kinds of op may run on the host inside a device loop.

The reference prints invalid: render-cuda: load in a device loop but outside a kernel: only i32 add and mul of the device index may be computed there. ./compile still runs the program.

When memory is in the wrong place

Two things go wrong: a kernel is handed another device's memory, or it uses a place in its own memory that holds nothing useful. The grader's emulator (lesson 8.4) catches both. In it, each allocation is separate memory filled with the byte 0xA5, with 32 more filled bytes on each side.

Your render-cuda forgets the UIR_COPY of x. Everything else is right. What does the grader say for c_shard_scale?

The read is inside the allocation. What is in the allocation?

The kernel reads the fill, 0xA5A5A5A5, and multiplies it by 10. The grader prints buffer 2[0]: expected 10, your kernel left 2021161074 (in the emulator).

The copy budget

The first line of c_shard_scale.uir is # cuda copy: 208. The grader adds up the bytes that every UIR_COPY moves and fails the test above 208. Count them by hand. An i32 is 4 bytes.

How many bytes do the scatter and gather of c_shard_scale move in total?

Each device gets a shard of x, all of w and a shard of o, and sends its shard of o back.

x: 2 copies of 8 elements, 64 bytes. w: 2 copies of 2, 16 bytes. o: 64 bytes in and 64 bytes back. 64 + 16 + 64 + 64 = 208, the number on the test's first line.

A compiler that replicated x would copy all 16 elements to each device. How many bytes would it move?

Only the count for x changes.

x becomes 128 bytes, so 272 in all. The grader prints moved 272 bytes between devices, the budget is 208 (send each device only its shard of a buffer, not all of it).

Both leave the same bits in o, so only the count tells them apart. A replicated buffer costs its whole size per device. A sharded one costs S elements per device, twice if the loop writes it.

Count one buffer's bytes

buffer_bytes devices size elem written stride returns the bytes moved for one buffer: size elements of elem bytes, written if the loop stores to it, stride its S or 0 when replicated. The sharded case has two mistakes. Fix them so that x, w and o of c_shard_scale give 64, 16 and 128.

Count a device loop's bytes

Write loop_bytes devices bufs, where each element of bufs is (size, elem, written, stride) as above. loop_bytes 2 [(16, 4, false, 8); (2, 4, false, 0); (16, 4, true, 8)] is c_shard_scale and gives 208.

    UIR_COPY(r6, s2_[r6], 0, b2 + r6 * 8, 8 * sizeof(int32_t));

    UIR_LAUNCH(k0, 2, 4, s0_[r6], s1_[r6], s2_[r6], r6, v7);

  • The device loop's counter r6 appears in three host loops, one per step, and as a kernel parameter.
  • The kernel takes the allocations under the buffers' names, b0 to b2, then the device index, then the host values it uses.
  • Only the offsets into sharded buffers change inside the kernel: each gets - r6 * 8u, with S as a literal.
  • A device loop with several kernels launches them all on a device, in program order, between one UIR_DEVICE and the next. Lesson 10.4 shows c_two_kernels_per_device.

With real CUDA, device d is GPU d modulo the number of GPUs, so a program with more devices than the machine has GPUs still runs. Lesson 10.5 comes back to this.

Every error the emulator can stop with

The emulator stops with exit code 4, and the grader prints the emulator stopped your kernel: multi-device error: followed by one of these:

  • a kernel was launched on one device with a pointer to another device's memory. Checked for every pointer argument of UIR_LAUNCH. Memory that UIR_ALLOC did not return, like b0, counts as device 0's.
  • UIR_COPY names a device its pointer is not on.
  • UIR_COPY writes past the end of a device allocation, or reads past the end.
  • UIR_FREE names the wrong device.
  • UIR_FREE of memory that UIR_ALLOC did not return.
  • a kernel wrote outside its device's allocation. Found at UIR_FREE, from the 32 filled bytes on each side. A write further away than that is not caught, and a read outside the allocation is never caught. It only gives wrong bits.

Reading memory that was never copied in is not an error. It shows up as a wrong value, because the fill is 0xA5A5A5A5.

Edge cases: one device, and elements no device owns

c_one_device has range 1 axis=device. It still allocates, copies in, launches and copies back, so its budget is 192 bytes: 64 for x and 128 for o.

c_tail_untouched has buffers of 10 elements, 2 devices and S = 4. Elements 8 and 9 belong to no device. They are never copied out or back, so they keep their values on device 0, as spec section 2 requires. Its budget is 96: 32 for x and 64 for o.

Why does UIR_SYNC() come after the launch loop, and not after each launch?

A launch returns before the kernel is done. What would a wait inside the loop hold up?

All devices are started first, then the host waits once. That is what lets two GPUs work at the same time.
