Week 10 · Lesson 4

A GEMM on two GPUs

You have written matrix multiply since week 3. Now you will split one across two devices, count every byte it moves, and add up a result that needs every device. Your compiler's render-cuda has to get all three right in the lab.

Goal

Decide which buffers of a program are sharded and which are replicated, count the bytes its device loop copies, and say why its answer has the same bits on any number of GPUs.

You'll use

The GEMM from lesson 3.3, blocks and phases from 8.2 and 8.3, the memory rule from 10.2, and the four steps and the copy budget from 10.3. The exercises are .uir, the same on both tracks.

Warm up

Two questions from lessons 10.2 and 10.3, from memory. Pulling an idea back out of your head is what makes it stay.

A device loop of 2 only reads the buffer w, at offset %b, the block number. There is no %d in the offset. Where does w live?

Memory a loop only reads may be read anywhere. When is it sharded?

Read-only memory is sharded only when every read is at d·S + e. Here none is.

The buffer x is sharded with S = 8. A kernel on device d loads element 8d + 3 of x. Which element of the device's own allocation is that?

The allocation holds only the shard, which starts at element 8d of the buffer.

Element 3. Element d·S + e of the buffer is element e of the allocation, so the rendered kernel subtracts d·S from the offset.

Decide who needs what

Recall lesson 3.3: row i of C = A @ B is row i of A multiplied by every column of B. Take A with 8 rows and 4 columns, B with 4 rows and 4 columns, and C with 8 rows and 4 columns. Two devices share the work: device 0 makes rows 0 to 3 of C, and device 1 makes rows 4 to 7.

Each device needs a copy of everything it reads. Decide before you read on.

Which of A, B and C can be cut in half, so that each device gets only its half, and which must every device have whole?

Device 0 makes row 2 of C. Which rows of A does that use? Which columns of B?

Row 2 of C uses only row 2 of A, but every column of B. So device 0 needs rows 0 to 3 of A and all of B. In lesson 10.2's words, A and C are sharded and B is replicated.

A row of C and the row of A it comes from land on the same device. B is the price of this split: every device pays for a whole copy.

  1. Split the work. Device d runs 4 blocks. Block b makes row 4d + b of C, and thread t makes column t of that row.
  2. Find the row. %ds is 16d, where the device's rows start. %br is 4b, the block's row within them.
  3. Read A. 16d + 4b + k is row 4d + b, column k. It is d·16 + e with e = 4b + k between 0 and 15, so A follows the slice rule with S = 16. A is sharded.
  4. Read B. 4k + t is row k, column t. It has no d, so B is replicated.
  5. Add up. Thread t adds A[row, k] · B[k, t] into acc[t] for k from 0 to 3, the dot product of lesson 3.3.
  6. Write C. A second phase stores acc[u] at 16d + 4b + u. C is written at d·16 + e, and 2 shards of 16 fit in 32 elements. C is sharded.

Device 1, block 2, k = 3. Which element of A does it load?

16d + 4b + k.

16 + 8 + 3 = 27, which is row 6, column 3. It is inside device 1's shard, elements 16 to 31, so it is element 11 of device 1's allocation of A.

The whole kernel the reference prints, for when you compare it with your own

The load of A, v18, has the shard's start, r6 * 16, subtracted. The load of B, v22, uses its offset as it is, because every device has all of B.

__global__ void k0(float *__restrict__ b0, float *__restrict__ b1, float *__restrict__ b2, int32_t r6, int32_t v7) {
  int32_t r8 = blockIdx.x;
  float a9[1] = {0};
  int32_t v10 = (int32_t)((uint32_t)r8 * (uint32_t)4);
  int32_t v11 = (int32_t)((uint32_t)v7 + (uint32_t)v10);
  {
    int32_t r12 = threadIdx.x;
    for (int32_t r14 = 0; r14 < 4; r14++) {
      float v15 = a9[(int32_t)((uint32_t)(r12) - (uint32_t)r12 * 1u)];
      int32_t v16 = (int32_t)((uint32_t)v11 + (uint32_t)r14);
      float v18 = b0[(int32_t)((uint32_t)(v16) - (uint32_t)r6 * 16u)];
      int32_t v19 = (int32_t)((uint32_t)r14 * (uint32_t)4);
      int32_t v20 = (int32_t)((uint32_t)v19 + (uint32_t)r12);
      float v22 = b1[v20];
      float v23 = (v18 * v22);
      float v24 = (v15 + v23);
      a9[(int32_t)((uint32_t)(r12) - (uint32_t)r12 * 1u)] = v24;
    }
  }
  __syncthreads();
  {
    int32_t r27 = threadIdx.x;
    int32_t v28 = (int32_t)((uint32_t)v11 + (uint32_t)r27);
    float v31 = a9[(int32_t)((uint32_t)(r27) - (uint32_t)r27 * 1u)];

v7 is %ds, computed on the host and passed in. acc is per-thread memory (lesson 9.1), so it became a9[1], one sum for each thread.

Count the bytes it moves

Recall lesson 10.3: the scatter sends each device its shard of a sharded buffer and all of a replicated one, and the gather brings back the shards the loop wrote. Count it by hand.

An f32 is 4 bytes. How many bytes does the device loop copy between devices, out and back, over both devices?

Each device gets 16 floats of each buffer: its shard of A, all of B, its shard of C. Then C's shards come back.

8 copies of 64 bytes is 512, the number in the test's # cuda copy: 512 line. A compiler that moves more fails the test, even with the right bits.

C is copied out as well as back. The rule of lesson 10.3 scatters every buffer the loop touches, because a kernel may leave some elements of its shard unwritten, and those must come back unchanged.

Now suppose every device got a whole copy of A, B and C, and sent back only its own rows of C. A costs 2 × 32 × 4 = 256, B 128, C 256 in and 128 back: 768 bytes. Sharding A and C saved a third. The bigger A and C are, the more it saves. B's copies are what is left to pay.

The host function the reference prints, where you can see each copy

From render-cuda for the same program, with the comment after the first line left out. The last argument of each UIR_COPY is its size in bytes: 8 copies of 64.

void kernel(float *b0, float *b1, float *b2) {
  float *s0_[2];
  float *s1_[2];
  float *s2_[2];
  for (int32_t r6 = 0; r6 < 2; r6++) {
    s0_[r6] = (float *)UIR_ALLOC(r6, 16 * sizeof(float));
    UIR_COPY(r6, s0_[r6], 0, b0 + r6 * 16, 16 * sizeof(float));
    s1_[r6] = (float *)UIR_ALLOC(r6, 16 * sizeof(float));
    UIR_COPY(r6, s1_[r6], 0, b1, 16 * sizeof(float));
    s2_[r6] = (float *)UIR_ALLOC(r6, 16 * sizeof(float));
    UIR_COPY(r6, s2_[r6], 0, b2 + r6 * 16, 16 * sizeof(float));
  }
  for (int32_t r6 = 0; r6 < 2; r6++) {
    UIR_DEVICE(r6);
    int32_t v7 = (int32_t)((uint32_t)r6 * (uint32_t)16);
    UIR_LAUNCH(k0, 4, 4, s0_[r6], s1_[r6], s2_[r6], r6, v7);
  }
  UIR_SYNC();
  for (int32_t r6 = 0; r6 < 2; r6++) {
    UIR_FREE(r6, s0_[r6]);
    UIR_FREE(r6, s1_[r6]);
    UIR_COPY(0, b2 + r6 * 16, r6, s2_[r6], 16 * sizeof(float));
    UIR_FREE(r6, s2_[r6]);
  }
  UIR_DEVICE(0);
}
The count for any size, for when you plan a bigger GEMM

For A with n rows and k columns, B with k rows and m columns, and D devices, with 4-byte floats, the sharded GEMM moves:

  • A: 4nk bytes, each row once, whatever D is.
  • B: 4Dkm bytes, a whole copy for every device.
  • C: 4nm in and 4nm back.

The work is 2nkm float operations. So when n is large, the work per byte is high and more devices help. When B is large and n is small, B's copies take over, and each new device adds a whole B. Cutting B by columns instead does not work in this week's rule: a device's columns of C are not one piece of the buffer at d·S + e, so the stores are rejected.

A result that needs every device

A sum of 16 numbers on two devices has a problem the GEMM did not: no device has all the numbers. The test c_partial_sums.uir solves it in two steps, on 16 i32 numbers.

  1. Partial sums. On each device one thread adds its 8 elements, x[8d + k], into acc, then stores the sum at p[d]. A partial sum is the sum of one shard. p is written at d·1 + 0, so each device's shard of p is one element.
  2. Gather. When the device loop ends, p is whole again on device 0: -15 from device 0 and 11 from device 1.
  3. Total. The last global loop is outside any device loop, so it runs on device 0, as in week 8. It adds p[0] and p[1] into tot: -4.

An i32 is 4 bytes. Count the bytes this program copies between devices. (The device loop never touches tot.)

x is read with S = 8. p is written with S = 1, so it goes out and comes back.

x: 2 × 8 × 4 = 64. p: 2 × 1 × 4 = 8 out and 8 back. 64 + 16 = 80, the test's budget. The total on device 0 needs no copy at all.

The order of a sum is in the program

Now make the same program add f32 numbers: x is 4 floats, each device adds 2 of them, and the last kernel adds the two partial sums. One fact about f32 you need: numbers near 100,000,000 are 8 apart, so 100,000,000 + 1 rounds back to 100,000,000.

x is [100000000, 1, -100000000, 1]. Device 0 adds the first two, device 1 the last two, and device 0 adds the two partial sums. What ends up in tot?

Work out each partial sum with the rounding fact, then add them.

Device 0: 100000000 + 1 rounds to 100000000. Device 1: -100000000 + 1 rounds to -100000000. Their sum is 0. A plain loop that adds left to right gives 1 instead: (100000000 + 1) - 100000000 is 0, then + 1.

With rounding, a different order can give different bits. But the order here is written in the program: each device adds its shard from k = 0 up, then device 0 adds p[0] and p[1]. A device loop means the same as a plain loop, so that order is the same on one GPU, on two, and in the emulator, and the answer is 0 on all of them.

That is why the grader can ask for the oracle's bits exactly. With i32 order never matters: adding with wraparound gives the same bits in any order.

Change the program to 4 devices of 1 element each and it is a different program with a different order. Its bits may differ from the 2-device program's, but the oracle runs that new program too, so your compiler must still match it. Some real multi-GPU libraries choose the order of a sum at run time, from the number of GPUs and how they are wired, so their results can change from machine to machine. This course's design rules that out.

Two kernels on one device

A device loop may hold more than one kernel. Each device launches them in program order. In c_two_kernels_per_device.uir the first kernel writes tmp = x + 1 and the second writes o = tmp · tmp, each on the device's shard of 8 elements. Both global loops sit inside one device loop.

The second kernel reads tmp through %tmp1, the version after the first kernel. Between the two launches tmp stays on the device. The budget is 320: x 64 out, tmp 64 out and 64 back, o 64 out and 64 back.

Split it into two device loops: the first ends after it writes tmp, and the second reads tmp and writes o. Between them all memory is whole on device 0 again. How many bytes do the two loops copy?

Count each loop on its own.

Loop 1: x 64, tmp 64 out and 64 back, 192. Loop 2: tmp 64 out again, o 64 out and 64 back, 192. 384 in all, 64 more than one loop: tmp made a round trip through device 0 for nothing.

On 64 bytes that is nothing. On a model's activations it can turn a speedup into a slowdown, so keep work on the devices as long as you can.
