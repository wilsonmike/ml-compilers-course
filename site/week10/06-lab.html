Week 10 · Lesson 6

Lab: multiple GPUs

In this lab your compiler learns to run one program on several GPUs. It reads a device loop, proves that each device stays inside its shard, and prints CUDA that copies each device its memory, runs its kernels and copies the results back. You need no GPU: the emulator checks every bit and every byte moved.

Goal

Pass all 26 week 10 tests with your own compiler, in the emulator or on GPUs, and write 10 tests of your own.

You'll use

Your compiler from the week 9 lab, and lessons 10.1, 10.2, 10.3, 10.4 and 10.5. The slice check from lesson 7.4 comes back, and so does kernel form from lesson 8.4.

Warm up

Pulling an idea back out of your head is what makes it stay.

A device loop of 2 reads x at 15 - i, back to front, and never writes x. What does the compiler do with x?

Lesson 10.2: memory the loop only reads may be read anywhere.

The reads do not follow d·S + e, so x can't be sharded. Since nothing writes it, a whole copy on each device is safe. A store that broke the rule would be REJECTED.

Two devices. x holds 16 i32 and is sharded. w holds 2 i32 and is replicated. How many bytes does the scatter copy for x and w together?

Lesson 10.3: an i32 is 4 bytes. A shard goes to one device, a replicated buffer to every device.

Two shards of 8 elements are 64 bytes, and two copies of w are 16, so 80. Add o's shards in and back, 64 bytes each way, and you get the 208 that c_shard_scale allows.

What you are building

  • compile FILE reads axis=device and runs a device loop as a plain loop. It rejects a program that breaks lesson 10.2's rules.
  • compile render FILE prints a device loop as a plain for loop.
  • compile render-cuda FILE prints the four steps of lesson 10.3 for each device loop: scatter, launch, wait and gather.

The suite has 26 tests. 16 are run tests: 8 named rejected_, 1 named mismatch_ and 7 that must MATCH. 10 are CUDA tests (c_). Eight of those have a copy budget, and c_err_load_outside_kernel must be refused. There are no CPU render tests and no speed tests this week. The contract is spec/uir-week10.md. rejected_device_bound_17.uir ends in an assert whose values are right for plain loops. Your compiler reads axis=device but has no bound rule yet. What does it print?

Run as a plain loop of 17, does the program compute what the assert says?

It does, so it prints MATCH. Unlike weeks 8 and 9, every week 10 run test ends in an assert, so once your compiler reads the axis, REJECTED shows a rule at work.

Plan it first

Decide the order first.

Which piece is the smallest that makes a week 10 program run?

An axis never changes the bits.

Run as a plain loop, every valid program already gives the right bits.

Your first render-cuda sends a whole copy of every read-only buffer to every device. The bits are right. Which tests fail?

What can the grader see besides the bits?

A whole copy and a shard give the same bits, so only the byte count tells them apart. That makes sharding read-only memory a safe last step.

So: the axis, the rules one at a time, render-cuda, and last, shards for read-only memory.

Keep each device in its shard

This is week 7's slice check with the device range d in place of the thread range.

  1. Find the written memory. Collect every buffer that a store or an mma writes anywhere in the device loop, across all its kernels. Leave out an alloc that is one kernel's shared memory.
  2. Check every access. Each load and store of written memory is at d·S + e, with S a positive literal and 0 ≤ e and e + size ≤ S provable. An mma tile counts with its whole extent.
  3. One stride per buffer. Every access to one buffer uses the same S, in every kernel of the loop.
  4. Try it on read-only memory. Run the same check on buffers the loop only reads. If it fails, do not reject: mark the buffer replicated. Keep S for those that pass, since render-cuda will need it.
Checkpoint 
-k rejected_device_slices_overlap    1 / 1 passed
-k rejected_devices_write_one_place  1 / 1 passed
-k two_strides                       1 / 1 passed
-k run/                              15 or more of 16

Make the shards fit

rejected_device_shards_do_not_fit has 3 shards of 4 in buffers of 10. Every access stays inside, and it is still refused.

  1. Multiply. For a device loop of bound N, a buffer with stride S needs N·S elements.
  2. Compare. If that is more than the buffer's size, a written buffer is REJECTED. A read-only buffer is replicated instead.
  3. Leave the tail alone. Elements past the last shard belong to no device and keep their values.

Print scatter, launch, wait and gather

Start with c_one_device, a device loop of 1. For now, copy every read-only buffer whole to every device.

  1. Accept the new shape. A global loop may sit directly inside a top-level device loop. Its bound is a literal.
  2. Compute on the host. Between kernels, a device loop may hold only i32 add and mul of the device index and literals. Print them in the host loop and pass them to the kernels. Anything else exits 2.
  3. Scatter. For every device and every buffer the loop touches, UIR_ALLOC on that device, then UIR_COPY in its shard of a written buffer, or the whole of a read-only one.
  4. Launch. UIR_DEVICE(d), then each kernel in program order, with the device's allocations in place of the buffers, plus d and any host values.
  5. Index the shard. In the kernel, element d·S + e of a sharded buffer is element e of the allocation, so subtract d·S.
  6. Wait, then gather. UIR_SYNC(). Copy every written shard back to its place on device 0, and UIR_FREE every allocation. Kernels after the loop run on device 0.

What stops a program in the emulator, for when a test ends in "multi-device error"

The emulator gives each allocation its own memory, filled with the byte 0xA5. A kernel that reads what was never copied to its device gets wrong bits. It also stops the program with one of these messages:

  • a kernel was launched on one device with a pointer to another device's memory: you passed a program buffer, or another device's allocation, to a kernel.
  • UIR_COPY names a device its pointer is not on: the device numbers of a copy are swapped or wrong.
  • UIR_COPY writes past the end of a device allocation, or reads past: a copy's size is the whole buffer where the allocation holds a shard.
  • a kernel wrote outside its device's allocation: an index that did not subtract d·S.
  • UIR_FREE names the wrong device.
The host function the reference prints for c_shard_scale, to compare with yours

python _reference/uirc.py render-cuda tests/week10/render/c_shard_scale.uir prints the kernel k0 and then this. x and o are sharded with S = 8, and w is replicated. v7 is the shard's offset, computed on the host.

void kernel(int32_t *b0, int32_t *b1, int32_t *b2) {   /* device pointers; UIR_LAUNCH comes from the harness */
  int32_t *s0_[2];
  int32_t *s1_[2];
  int32_t *s2_[2];
  for (int32_t r6 = 0; r6 < 2; r6++) {
    s0_[r6] = (int32_t *)UIR_ALLOC(r6, 8 * sizeof(int32_t));
    UIR_COPY(r6, s0_[r6], 0, b0 + r6 * 8, 8 * sizeof(int32_t));
    s1_[r6] = (int32_t *)UIR_ALLOC(r6, 2 * sizeof(int32_t));
    UIR_COPY(r6, s1_[r6], 0, b1, 2 * sizeof(int32_t));
    s2_[r6] = (int32_t *)UIR_ALLOC(r6, 8 * sizeof(int32_t));
    UIR_COPY(r6, s2_[r6], 0, b2 + r6 * 8, 8 * sizeof(int32_t));
  }
  for (int32_t r6 = 0; r6 < 2; r6++) {
    UIR_DEVICE(r6);
    int32_t v7 = (int32_t)((uint32_t)r6 * (uint32_t)8);
    UIR_LAUNCH(k0, 2, 4, s0_[r6], s1_[r6], s2_[r6], r6, v7);
  }
  UIR_SYNC();
  for (int32_t r6 = 0; r6 < 2; r6++) {
    UIR_FREE(r6, s0_[r6]);
    UIR_FREE(r6, s1_[r6]);
    UIR_COPY(0, b2 + r6 * 8, r6, s2_[r6], 8 * sizeof(int32_t));
    UIR_FREE(r6, s2_[r6]);
  }
  UIR_DEVICE(0);
}

Send each device only its shard

The bits are right. What is left is waste: a device gets all of a buffer it reads only a shard of.

  1. Use the kept S. A read-only buffer whose reads passed the slice rule and whose shards fit has one.
  2. Scatter a shard. Allocate and copy S elements starting at d·S, as for written memory.
  3. Index it the same way. Subtract d·S in the kernel.
  4. Do not gather it. Nothing wrote it, so only free it.

Write your 10 tests

Put 10 tests in <your compiler repo>/tests/week10/, each aimed at a rule someone will get wrong. The first toggle below holds a whole one, rejected_device_swap_halves.uir. Each device copies the other half of o into its own. As plain loops that gives 9 to 16 twice, which is what the assert says, so only the rule can make it REJECTED: the loop writes o and reads it at 8 - 8d + e.

Good targets for your tests

Good targets: a vector store whose size just fits the end of a shard, and one element more. Shards that fit exactly, N·S equal to the size. A read-only buffer whose shards don't fit, which must be replicated, not rejected. A device loop of 16. A buffer read in one kernel and written in the next, in one device loop.

Check yourself

c_shard_scale fails with moved 272 bytes between devices, the budget is 208. Its x has 16 i32, w has 2 and o has 16, on 2 devices. What did your compiler do?

272 − 208 = 64. Which buffer is 64 bytes more when replicated?

Two whole copies of x are 128 bytes, two halves are 64. Gathering w would add only 16, and a missing copy would move fewer bytes.

The emulator stops a test with a kernel was launched on one device with a pointer to another device's memory. What is the likely bug?

Lesson 10.3: what does a kernel take in place of the buffers?

On device 1, a kernel may only touch device 1's allocations. On device 0 the check can't see it, since the buffers live there too.

The test's name says what it is allowed to do.
