Training on several GPUs

In week 6 your compiler trained a model one batch at a time, on one device. Here the same training step runs on two GPUs: each works out the gradient for half the batch, and device 0 adds the halves and moves the weights. Most large models are trained this way.

Goal

Build one training step that runs on two devices, check that it gives the same weights as one device, and say when more GPUs stop helping.

Weights, loss, gradient and learning rate (6.3, 6.5). The slice rule d*S + e (10.1, 10.2). Scatter and gather (10.3). Partial sums on device 0 (10.4).

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

A weight is 2.0. Its gradient is -4.0 and the learning rate is 0.25. What is the weight after the step?

Lesson 6.5: new weight = old weight minus learning rate times gradient.

2.0 - 0.25 × (-4.0) = 3.0. A negative gradient means raising the weight lowers the loss.

A device loop of 2 writes a buffer of 8 elements at offset 4d + e, with e from 0 to 3. Which elements are device 1's shard?

Lesson 10.2: device d owns elements d·S to d·S + S - 1.

S is 4, so device 1 owns elements 4 to 7. Only that shard travels to it and back.

Split the batch, add the gradients

A week 6 training step worked on a batch: guess, measure the loss, get the gradient, step every weight. A gradient says how much the loss moves when you nudge one weight. With two GPUs, give each half the batch.

A batch of 4 examples, 2 devices. For one weight, device 0 works out the gradient of examples 0 and 1: 1.0. Device 1 does examples 2 and 3: 6.0. The batch's loss is the sum of the 4 examples' losses. What is the weight's gradient for the whole batch?

Nudge the weight. Each example's loss moves a little. How far does their sum move?

7.0. Nudge the weight and the batch's loss moves by all the examples' moves added up. So its gradient is the sum of theirs, and a sum can be split: (g0 + g1) + (g2 + g3). Each device adds its pair, and one device adds the partial sums, as in lesson 10.4.

This plan is called data parallelism: split the data, give every device the whole model. In this week's words:

  1. Shard the batch. Each device gets its own examples and their targets.
  2. Replicate the weights. Every device needs all of them to guess.
  3. Sum per device. Each device adds up its examples' gradients and writes this partial gradient into its shard of a small buffer.
  4. Add and step on device 0. One kernel adds the partial gradients and moves every weight.

Week 6 used the mean loss, the sum times 0.01, which splits the same way. This lesson keeps the plain sum.

A model small enough to see

The model has two weights, w0 and w1. An example is two numbers x0 and x1 and a target t, the answer it should give.

  • guess = w0·x0 + w1·x1
  • error = guess - t
  • loss of one example = half of error × error

A kernel can't use the gradient op, so work it out by hand with lesson 6.3's rules, walking back from the loss to w0:

  1. Loss to error. error × error uses the error twice, and each use gets the other operand as its share. Two shares, then the half: the error.
  2. Error to guess. A nudge to the guess moves the error as much: 1.
  3. Guess to w0. w0·x0 is a mul, so the rule gives x0.
  4. Multiply along the path. error × 1 × x0.

So one example's gradient is error·x0 for w0 and error·x1 for w1. The 4 examples, with both weights at 1.0:

One step, by hand, on two devices

Device 0 gets examples 0 and 1, device 1 gets 2 and 3. Adding their rows of the table, device 0's partial gradient is (1, -1) and device 1's is (6, 0). The learning rate is 0.125, a power of two, so every number here is exact in f32.

Step through the program's memory. Before the last step, work out the new w1.

The batch's gradient for w1 is -1 + 0 = -1. With the learning rate 0.125, what is the new w1?

1.0 - 0.125 × (-1).

1.125. And w0 becomes 1.0 - 0.125 × 7 = 0.125. The batch's loss was 5.0 before the step (half of 1 + 1 + 4 + 4). With the new weights it is about 3.4, so the step helped.

The device loop in .uir

The program has four buffers: %x (8 numbers, slot 0), %t (4 targets), %w (2 weights) and %pg (4 partial gradients), all f32. Example k of device d is example 2d + k, so its numbers start at x[4d + 2k]. The device loop holds one kernel:

  1. The loops. %d = range 2 axis=device, then one block of 2 threads (%j = range 2 axis=local), one per weight. A plain loop %k = range 2 walks the device's 2 examples.
  2. Guess and error. Load x[4d + 2k], x[4d + 2k + 1] and both weights, guess, and subtract t[2d + k].
  3. Add up the gradient. Thread j adds error × x[4d + 2k + j] into acc[j], its own per-thread memory (lesson 9.1), which starts at zero.
  4. Write the partial gradient. After the loop, thread j stores acc[j] into pg[2d + j].

%po   = add %d2 %jb
%pv   = shrink %pg %po []

The weights are loaded at w[b] and w[b + 1], with b always 0. A load at w[0] depends on no loop, so it would sit outside the kernel, which lesson 8.4's kernel form refuses.

void kernel(float *b0, float *b1, float *b2, float *b3) {   /* device pointers; UIR_LAUNCH comes from the harness */
  float *s0_[2];
  float *s1_[2];
  float *s2_[2];
  float *s3_[2];
  for (int32_t r8 = 0; r8 < 2; r8++) {
    s0_[r8] = (float *)UIR_ALLOC(r8, 4 * sizeof(float));
    UIR_COPY(r8, s0_[r8], 0, b0 + r8 * 4, 4 * sizeof(float));
    s1_[r8] = (float *)UIR_ALLOC(r8, 2 * sizeof(float));
    UIR_COPY(r8, s1_[r8], 0, b1 + r8 * 2, 2 * sizeof(float));
    s2_[r8] = (float *)UIR_ALLOC(r8, 2 * sizeof(float));
    UIR_COPY(r8, s2_[r8], 0, b2, 2 * sizeof(float));
    s3_[r8] = (float *)UIR_ALLOC(r8, 2 * sizeof(float));
    UIR_COPY(r8, s3_[r8], 0, b3 + r8 * 2, 2 * sizeof(float));
  }
  for (int32_t r8 = 0; r8 < 2; r8++) {
    UIR_DEVICE(r8);
    int32_t v9 = (int32_t)((uint32_t)r8 * (uint32_t)2);
    int32_t v10 = (int32_t)((uint32_t)r8 * (uint32_t)4);
    UIR_LAUNCH(k0, 1, 2, s0_[r8], s1_[r8], s2_[r8], s3_[r8], r8, v9, v10);
  }
  UIR_SYNC();
  for (int32_t r8 = 0; r8 < 2; r8++) {
    UIR_FREE(r8, s0_[r8]);
    UIR_FREE(r8, s1_[r8]);
    UIR_FREE(r8, s2_[r8]);
    UIR_COPY(0, b3 + r8 * 2, r8, s3_[r8], 2 * sizeof(float));
    UIR_FREE(r8, s3_[r8]);
  }
  UIR_DEVICE(0);
  UIR_LAUNCH(k1, 1, 2, b2, b3);
}

v9 and v10 are 2d and 4d, computed on the host and handed to k0. Only pg is gathered, because it is the only buffer the device loop writes.

One GPU, the same bits

On one device, thread j loops over all 4 examples, then the same update runs (program in the toggle below). It gives w = [0.125 1.125], the same bits.

But the adds come in another order. One device adds ((g0 + g1) + g2) + g3. Two devices add (g0 + g1) + (g2 + g3). With this lesson's numbers every sum is exact, so the order can't show.

Now fill x, t and w with numbers like 0.3 and -1.7. Do the one-device and two-device programs still give the same bits?

Lesson 10.4: who fixes the order of a floating-point sum?

Not always. On 200 inputs of random tenths, 74 gave different bits in a weight, such as 0.69375002 against 0.69374990. Each f32 add rounds, so another order can round differently. Nothing here is random: each program fixes its own order.

The one-device program that always matches is the two-device program with axis=device deleted. %d becomes a plain loop and the adds keep their order. That is the week's promise: an axis never changes a result.

Split a sum across devices

xs is split into n equal shards: with s its length divided by n, device d owns elements d·s to d·s + s - 1. Write split_sum(xs, n)split_sum xs n, the total in this lesson's order. Each device starts at 0.0 and adds its shard left to right. Then device 0 starts from partial sum 0 and adds partial sums 1, 2 and so on. Some tests use huge numbers, where order changes the answer.

Add with a loop and +, not sum(). From Python 3.12, sum() of floats keeps extra precision as it goes, so its answer can differ from adding one float at a time, which is what the hardware and your compiler do.

When more GPUs stop helping

Two parts of the program do not shrink when you add devices.

The part on device 0. The gradient work runs on all devices at once. The add and the step run on device 0 alone, afterward.

A step takes 100 ms on one GPU: 80 ms of gradient work, which splits evenly, and 20 ms of adding and stepping on device 0. Leaving copies out, how many ms does it take on 4 GPUs?

The 80 ms is shared by 4 devices. The 20 ms is not shared.

80 / 4 + 20 = 40 ms. With 8 GPUs it is 30 ms, with 80 GPUs 21 ms. No number of GPUs gets below 20 ms, and device 0 has more partial gradients to add as devices join.

The copies, every step. Lesson 10.1 asked how much work is done per byte moved. Each device gets 4 numbers of x, 2 of t, 2 of w and 2 of pg, and sends 2 of pg back. An f32 is 4 bytes.

How many bytes does UIR_COPY move in all, for both devices?

Per device: 4 + 2 + 2 + 2 numbers out and 2 back.

12 numbers per device, 2 devices, 4 bytes each: 96 bytes, the emulator's budget. 16 of them copy out pg's shards, which the kernels overwrite unread: the scatter copies written buffers too (lesson 10.3).

Those 96 bytes buy about 50 arithmetic operations. Two GPUs would run this tiny step slower than one: it shows the method, not a speedup. Week 6's digit model has 7,840 weights, 31,360 bytes, and they travel to every device on every step.

What real systems do differently

This week's design moves memory the simplest way: everything starts and ends on device 0. Count the cost with 8 devices and week 6's model, where each partial gradient is 31,360 bytes.

How many bytes of partial gradients arrive at device 0 from the other 7 devices, each step?

7 devices, 31,360 bytes each.

7 × 31,360 = 219,520 bytes, all through device 0's link, and then the new weights go out 7 times. Device 0's link becomes the limit.

Real training systems avoid this in three ways:

  1. Keep data on the devices. Each device keeps its own weights from step to step and applies the same update to them, so weights never travel. Each device also loads its own batches.
  2. Send gradients between devices. An all-reduce adds the partial gradients while passing pieces from device to device, so every device ends with the sum. In a ring of 8, each device sends about 2 × 7/8 × 31,360 = 54,880 bytes, and that barely grows with more devices.
  3. Overlap. A device sends one layer's gradient while it computes the next, so copies hide behind work.
How a ring all-reduce gets 2 × 7/8, for the curious

Cut each device's gradient into 8 pieces. In the first 7 rounds, device i sends one piece to device i + 1 (wrapping around), which adds it into its own copy of that piece. After 7 rounds each device holds the full sum of one piece. In the next 7 rounds those finished pieces travel around the ring the same way, so everyone gets every piece. Each round a device sends 1/8 of the gradient, for 14 rounds: 14/8 = 2 × 7/8. With N devices it is 2 × (N - 1)/N, which never reaches 2.

The ring also sets the order of the adds, and it differs from piece to piece. A system that wants the same bits on every run has to keep that order fixed, just as this lesson's program does.

Running it with no GPUs, or too few

You can do this whole week on a laptop. The grader builds your CUDA in lesson 8.4's emulator, with the five UIR_ names defined for several devices:

  • Separate memory. Every UIR_ALLOC is its own block, filled with the byte 0xA5, not zeros. Forget to scatter w to device 1, and its kernel reads that pattern as weights.
  • Wrong-device checks. It stops a kernel launched with another device's pointer, a copy that names the wrong device, and a kernel that writes past its allocation.
  • One after another. Devices run in turn, so UIR_SYNC() has nothing to wait for. The bits are the same, because the program fixes them.

On real GPUs, device d is GPU d modulo the number of GPUs. Each device still gets its own allocations, so the copies and bits match a machine with enough GPUs. Only the speed differs.

A program has 4 devices and the machine has 3 GPUs. Which GPU runs device 3?

3 modulo 3.

GPU 0, which also runs device 0. GPU 0 does twice the work, so the step is no faster than on 2 GPUs, but the weights come out the same.
