The runtime

Your compiler can print C, but nobody has run that C yet. In this lesson you compile it, run it and read the results back, then check them against your interpreter. That check tells you whether your renderer is right, and from week 6 on the compiled C does the real work.

Goal

Turn a rendered kernel into a running program and compare what it leaves in the buffers with your interpreter's answer, bit for bit.

You'll use

The kernel function from lesson 2.4 and f32 with its -0.0 from lesson 2.1. The C here is arrays and printf from lesson 0.1.

In your own language: files, with and exit codes (P.6).

In your own language: calling functions from library modules such as Filename and Sys (O.6).

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

A program has two buffers: slot 0 is f32 and slot 1 is i32. What is the first line of the function your renderer prints?

Lesson 2.4: one pointer per buffer, in slot order. The function returns nothing.

The renderer prints one function, kernel, that takes a pointer to each buffer. It does not print a main. That gap is where this lesson starts.

A program stores into buffer %b twice. The first store makes version %b1 and the second makes %b2. Which version is the program's output?

Lesson 2.2: the output is the version that no after builds on.

%b2, the final version. In C there is only one array, so the final version is simply what the array holds when kernel returns.

How do you know the C is right?

A program adds the first two elements of a buffer and stores the sum in the third. The buffer starts as [10 20 0]. Your interpreter says it ends as [10 20 30]. Your renderer printed this file:

#include <stdint.h>

void kernel(int32_t *b0) {
  int32_t v0 = b0[0];
  int32_t v1 = b0[1];
  int32_t v2 = (int32_t)((uint32_t)v0 + (uint32_t)v1);
  b0[2] = v2;
}

You read the C and it looks right. Which of these could still make the compiled program leave something else in the buffer?

You wrote the interpreter and the renderer. Is either one proven correct yet?

Any of them. Reading cannot rule these out. Running the C can.

You now have two ways to get an answer that share almost no code. The interpreter walks the graph. The C compiler turns your printed text into machine code. If both leave the same bits in every buffer, a bug would have to hit both in the same way. Running one input through two implementations and comparing is called differential testing. A difference proves that at least one side has a bug and hands you a small program that triggers it. It does not say which side is wrong.

The code that runs your C and brings the results back is called a runtime. It does five things, and the rest of this lesson takes them in order:

  1. Render. Print the kernel. You did this in lesson 2.4.
  2. Write a harness. A second C file that fills the buffers, calls the kernel and prints what is left.
  3. Build. Hand both files to a C compiler.
  4. Run. Start the program and collect what it prints.
  5. Read back and compare. Turn the printed text into values and check them against the interpreter.

This week the runtime is optional: ./compile FILE may still interpret, and the grader brings its own harness for render tests. From week 6 on your kernels are timed, so build the plumbing now, while the programs are small enough to check by hand.

A kernel cannot run on its own

Save the file above as kernel.c and ask the C compiler to make a program from it:

clang kernel.c -o prog

What happens?

Where does a C program start running? Is that function in the file?

It does not build. Every C program starts at a function called main, and this file only has kernel. The error says undefined reference to `main', or WinMain on Windows.

The kernel is one function with nobody to call it and no buffers to work on. The file that supplies both is called a harness. Your compiler writes it from the same graph. Here is the harness for this program, main.c:

#include <stdio.h>
#include <stdint.h>

void kernel(int32_t *b0);

int main(void) {
  static int32_t b0[3] = {10, 20, 0};
  kernel(b0);
  printf("0 %d\n", (int)b0[0]);
  printf("0 %d\n", (int)b0[1]);
  printf("0 %d\n", (int)b0[2]);
  return 0;
}
  1. Declare the kernel. The line void kernel(int32_t *b0); says the function exists in another file.
  2. Make the buffers. One array per buffer op, with its size and starting data, or zeros when the op has no data. static keeps a large array off the stack, the small memory area that function calls use.
  3. Call the kernel. Pass the arrays in slot order.
  4. Print every element. One line each: the slot number, a space and the value. This is the format the grader's harness prints.

Finish the harness

harness bufs returns the lines that go inside main, as a list of strings. bufs is a list of (slot, data) pairs for i32 buffers, already in slot order. The array lines are written. Two things are missing:

  • The call passes nothing. Make it pass every array in order, like kernel(b0, b1);.
  • After the call, add one print line per element, buffer by buffer. print_line slot i builds the line for you.

The tests show the lines joined with | .

Build it and run it by hand

Before your compiler runs these commands for you, run them once yourself. Put kernel.c and main.c from the last two sections in an empty folder and open a terminal there.

  1. Build. This is the command the grader uses, with your two files and a name for the program added: 
    clang -std=c11 -O2 -ffp-contract=off -fsanitize=undefined -fsanitize-trap=undefined kernel.c main.c -o prog
    A C compiler that prints nothing has succeeded. The folder now holds prog, or prog.exe on Windows.
  2. Run. Type ./prog, or .\prog in PowerShell. You should see: 
    0 10
0 20
0 30
  3. Ask for the exit code. Every program hands one number back to whoever started it. Zero means it finished normally. Type echo $?, or echo $LASTEXITCODE in PowerShell. You should see 0.

The third line of output is 30, which is what the interpreter said. That is your first check of rendered C against the interpreter.

The -fsanitize flags are the ones from lesson 2.4 that make undefined behavior crash the program. -O2 asks for fast code, and -ffp-contract=off keeps f32 rounding the same as .uir. With gcc, change the last flag to -fsanitize-undefined-trap-on-error.

Break it on purpose. In kernel.c, change the add to plain v0 + v1. In main.c, change the data to {2147483647, 1, 0}. Build with the same command and run. What do you see?

2147483647 is the largest i32. What does C say about a signed add that overflows, and what do the -fsanitize flags do about it?

The build works, because the C is valid. The run crashes inside kernel, before any printf, because signed overflow is undefined behavior and the flags turn it into a crash. A program that exits with anything but 0 means the kernel crashed.

Print the bits, not the decimal

For i32, %d prints every digit, so nothing is lost. Floats are harder. Here are three f32 values that sit next to each other. No f32 lies between them:

0x1.333332p-2f
0x1.333334p-2f
0x1.333336p-2f

A harness prints each of the three with printf("%g\n", x). What comes out?

%g keeps 6 significant digits. These three values first differ in the 8th digit.

0.3 three times. If the interpreter says the middle value and your C leaves the last one, this harness reports a match. The bug stays hidden.

So do not print a decimal. Print the 32 bits themselves, as 8 hex digits. Hex is base 16 (lesson 0.1), so each digit stands for 4 bits. The three values above print as 3e999999, 3e99999a and 3e99999b. Nothing is rounded, so nothing can hide.

The cast (uint32_t)x converts the value, so 1.0f becomes the integer 1. You want the same 4 bytes, read as an integer. memcpy from <string.h> copies bytes from one variable to another without changing them:

static void print_bits(int slot, float x) {
  uint32_t u;
  memcpy(&u, &x, sizeof u);
  printf("%d %08x\n", slot, (unsigned)u);
}
  1. Copy the bytes. After the memcpy, u holds the same 32 bits as x.
  2. Print them in hex. %08x means hex, 8 digits wide, padded with zeros. print_bits(0, 1.0f) prints 0 3f800000.

A float's bits, not its value

Write uint32_t f32_bits(float x), returning the 32 bits that represent x: f32_bits(1.0f) is 0x3f800000. The starter uses the cast, which converts the value. Repair it. No undefined behavior.

Run the C compiler from your compiler

Typing three commands is fine once. The week 2 tests have dozens of programs, so your compiler should do what you just did by hand:

  1. Make a folder. A fresh temporary folder, deleted at the end even after an error.
  2. Write the two files. The rendered kernel and the harness.
  3. Build. Run the C compiler with the same flags and look at its exit code. If it is not 0, print the compiler's message: it points at the line your renderer got wrong.
  4. Run. Start the program with a time limit, then collect its exit code and what it printed. Name it prog.exe: the ending is needed on Windows and does no harm anywhere else.

The build's exit code is 0. The run's exit code is not 0 and the program printed nothing. What is the most likely cause?

A syntax error would stop the build. A wrong value still prints. What did you see when you broke the add on purpose?

The C compiled, so it is valid C. The program died before its first printf, which is what a trap inside kernel looks like. A wrong value would still be printed, with exit code 0.

Read the values back

The program's output is text. For an i32 or bool buffer each line holds a plain whole number, and reading it is one call. An f32 line looks like 0 3f800000, which is slot 0 and the bits of 1.0.

You read 3f800000 as a base 16 whole number and then convert that number to a float. What do you get?

As a whole number, hex 3f800000 is 1065353216. What does converting a whole number to a float keep: its bits or its value?

About a billion. It is the cast mistake again, run backward. Converting keeps the value and changes the bits. You need to keep the bits and change only what they mean.

Reading the bits back takes two moves:

  1. Hex digits to a whole number. int("3f800000", 16) gives 1065353216, a number from 0 to 232 − 1.
  2. The same bits as a float. struct.pack("<I", n) writes the number as 4 bytes, and struct.unpack("<f", data)[0] reads those 4 bytes as an f32. Here that gives 1.0.
  1. Hex digits to an int32. Int32.of_string "0x3f800000" gives 1065353216l. It accepts all 8 digits, even with the top bit set: 0x80000000 becomes Int32.min_int.
  2. The same bits as a float. Int32.float_of_bits reads those 32 bits as an f32. Here that gives 1.0.

No decimal is ever parsed, so nothing is rounded on the way back either.

Eight hex digits back into a float

bits_to_f32 bits gets 8 hex digits, like 3f800000, and must return the float those 32 bits stand for. The starter reads the digits as an int32 and then converts that number's value, so 3f800000 comes back as 1065353216.0 and not 1.0. Repair it so the bits are kept and only their meaning changes.

Now the whole output: split it into lines, split each line at the space and keep the lines for the slot you want.

Read a buffer back from the harness

The output has one line per f32 element, like 0 3f800000. Write read_slot : string -> int -> float listread_slot(out: str, k: int) -> list[float], returning slot k's values in output order. Lines may end in \r\n, blank lines can appear and a slot that never appears gives [].

Compare with the interpreter

You have two lists for each buffer: what the interpreter says and what the C program left. The last step is to compare them.

The interpreter says an element is -0.0. The C program printed 00000000, which is 0.0. Your language says 0.0 equals -0.0. Should the runtime call this a match?

Lesson 2.1: what are recip 0.0 and recip -0.0?

No. -0.0 is 80000000 and 0.0 is 00000000. One recip later they are -inf and inf, so a lost sign is a real bug.

The rule the grader uses for a rendered kernel:

  • i32 and bool: the same number.
  • f32: the same 32 bits. One exception: any NaN matches any NaN, because NaN has many bit patterns and .uir does not pick one.

An assert is different. It compares f32 by value, so there 0.0 does equal -0.0.

Step through the whole loop on one f32 program.

Do the two answers match?

Write same_f32 : float list -> float list -> bool. Both lists hold f32 values: the first from the interpreter, the second read back from the C program. Return true when the lists have the same length and every pair has the same 32 bits. One exception: a NaN matches any NaN. So 0.0 and -0.0 do not match, even though 0.0 = -0.0 is true in OCaml.

Reference for the lab

Open these when you need them.

What the grader's harness does, for when yours must agree with it
  • It declares one static array per buffer, sized from the op, and calls kernel with the arrays in slot order.
  • i32 and bool arrays start from a plain list of numbers. f32 arrays start from raw bits: the harness holds the starting data as uint32_t values and copies them in with memcpy, so -0.0 and NaN start out exact. Hex float literals such as 0x1.99999ap-4f are exact too, but NaN and the infinities then need NAN and INFINITY from <math.h>.
  • It prints i32 and bool elements as slot value with %d, so a bool is 0 or 1. It prints f32 elements as slot bits with %08x.
  • The harness may use loops. Only the kernel must be loopless.
  • It builds with clang -std=c11 -O2 -ffp-contract=off -fsanitize=undefined -fsanitize-trap=undefined, plus -lm for <math.h> functions. With gcc the last flag is -fsanitize-undefined-trap-on-error.
  • kernel.c is compiled as its own file, so it must #include what it uses.
What each decimal format loses, for when you debug by eye
  • %g keeps 6 significant digits. Neighboring floats print the same, and the smallest f32 prints as 1.4013e-45.
  • %f keeps 6 digits after the point. The smallest f32 prints as 0.000000, and -0.0 prints as -0.000000.
  • %.9g prints enough digits to tell any two f32 values apart, but you then have to parse a decimal and round it correctly on the way back.
  • The hex bits need no parsing of decimals at all. They keep the sign of zero, every mantissa bit and the exact NaN.
Why a separate program and not a shared library, for when you think about speed

The fastest-looking design compiles the kernel into a .so or .dll, loads it into your compiler's process and calls it directly. In OCaml that means the ctypes and ctypes-foreign packages, libffi and describing every C type from OCaml.In Python that means the ctypes module, describing every argument's C type and keeping buffers alive while C uses them. It works, but it's a lot of machinery, and a crashing kernel takes your compiler down with it. A separate program costs a few milliseconds of process startup and gives you isolation and plain-text output for free. Start there. You can always switch later.

Build and run from your own code: a full sketch, with timeouts and cleanup, for when you write the runtime 
import os, subprocess, tempfile

FLAGS = ["-std=c11", "-O2", "-ffp-contract=off",
         "-fsanitize=undefined", "-fsanitize-trap=undefined"]

with tempfile.TemporaryDirectory() as d:
    k = os.path.join(d, "kernel.c")
    m = os.path.join(d, "main.c")
    exe = os.path.join(d, "prog.exe")
    with open(k, "w", encoding="utf-8") as f:
        f.write(kernel_text)
    with open(m, "w", encoding="utf-8") as f:
        f.write(main_text)
    c = subprocess.run(["clang", *FLAGS, k, m, "-o", exe],
                       capture_output=True, text=True, timeout=60)
    r = subprocess.run([exe], capture_output=True, text=True, timeout=10)
  1. Make a folder. TemporaryDirectory creates an empty folder and deletes it when the with block ends, even after an error.
  2. Write the two files. kernel_text is what your renderer printed and main_text is the harness.
  3. Build. The command is a list, one item per word you typed by hand. c.returncode is the exit code. If it is not 0, print c.stderr: clang's message points at the line your renderer got wrong.
  4. Run. If r.returncode is 0, r.stdout holds the printed lines as one string. If not, the kernel crashed.
let flags = ["-std=c11"; "-O2"; "-ffp-contract=off";
             "-fsanitize=undefined"; "-fsanitize-trap=undefined"]

let build_and_run kernel_text main_text =
  let dir = Filename.temp_dir "uir" "" in
  let k = Filename.concat dir "kernel.c" in
  let m = Filename.concat dir "main.c" in
  let exe = Filename.concat dir "prog.exe" in
  let out = Filename.concat dir "out.txt" in
  let write path s = Out_channel.with_open_text path (fun oc -> output_string oc s) in
  write k kernel_text;
  write m main_text;
  let build = Sys.command (Filename.quote_command "clang" (flags @ [k; m; "-o"; exe])) in
  let run = Sys.command (Filename.quote_command exe ~stdout:out []) in
  let text = In_channel.with_open_text out In_channel.input_all in
  (build, run, text)
  1. Make a folder. Filename.temp_dir (OCaml 5.1 and later) creates an empty folder and returns its path.
  2. Write the two files. kernel_text is what your renderer printed and main_text is the harness.
  3. Build. Filename.quote_command joins the program name and its arguments into one command line, with quotes that keep a path with spaces in one piece. Sys.command runs it and returns the exit code. If build is not 0, clang has printed a message that points at the line your renderer got wrong.
  4. Run. ~stdout:out sends what the program prints into a file, and In_channel reads that file back. If run is not 0, the kernel crashed.

This sketch runs the program even when the build failed, and it never deletes the folder. Yours should check build first and clean up at the end.

Timeouts and leftovers

Sys.command waits forever. A kernel that faults on Windows and sits in the error reporter will hang your compiler. If you need a timeout, the unix library (add unix to your dune libraries) has Unix.create_process and Unix.waitpid. And delete what you write: Fun.protect ~finally:(fun () -> ...) runs your cleanup even when something in the middle raises.

Without timeout=, subprocess.run waits forever. A kernel that faults on Windows and sits in the error reporter will hang your compiler. With it, a slow program raises subprocess.TimeoutExpired, which you can catch and report.

The library calls one by one, for when you write the runtime
  • tempfile.TemporaryDirectory() creates a fresh, empty directory. Used as with tempfile.TemporaryDirectory() as d:, it deletes the directory and everything in it when the block ends, even if something inside raises. os.path.join(d, "kernel.c") builds paths inside it.
  • subprocess.run runs a command given as a list of arguments, so paths with spaces need no quoting. capture_output=True collects stdout and stderr, text=True decodes them to strings and timeout= stops a program that runs too long.
  • The result's .returncode is the exit code, and .stdout and .stderr hold the output.
  • Filename.temp_dir "uir" "" (OCaml 5.1 and later) creates a fresh, empty directory and returns its path. Filename.concat dir "kernel.c" builds paths inside it.
  • Filename.quote_command builds a command line with every argument quoted correctly for your platform, including paths with spaces. Its ~stdout argument redirects output into a file. On Linux, Filename.quote_command "clang" ~stdout:"out.txt" ["-O2"; "my file.c"; "-o"; "a.out"] is 'clang' '-O2' 'my file.c' '-o' 'a.out' >'out.txt'.
  • Sys.command runs that command line and returns the exit code.

Check yourself

Why print f32 results as hex bits instead of with printf("%g")?

The grader compares f32 results bit for bit. How many digits does %g print, and how many does it take to pin down an f32?

The hex bits are the value, exactly: sign of zero, every mantissa bit, subnormals, NaN. %g rounds to 6 significant digits, and 9 are needed to round-trip an f32.

What are the 32 bits of -0.0f, as 8 hex digits?

Only one bit differs between 0.0f and -0.0f, and it is the first of the 32.

80000000: just the sign bit. 0.0f is 00000000. That one bit is why recip -0.0 is -inf, and why the runtime must keep it.

What does OCaml's Int32.of_string "0xffffffff" return?What does struct.unpack("<i", struct.pack("<I", int("ffffffff", 16)))[0] return? ("<i" is a signed 32-bit int.)

For hex input, Int32.of_string accepts the full 32-bit unsigned range and reinterprets it as a signed int32.int("ffffffff", 16) is 4294967295. Packing it as unsigned and unpacking the same bytes as signed reinterprets the bits.

-1l-1: all 32 bits set is -1 in two's complement. That's what lets Int32.of_string ("0x" ^ bits)the same bytes, unpacked as "<f", read any f32 bit pattern, including ones with the sign bit set.

Sys.command (Filename.quote_command "clang" [...]) returns 1.subprocess.run(["clang", ...]).returncode is 1. What happened?

That number is the command's exit code. What does a nonzero exit code from a compiler mean?

A nonzero exit code from clang means it didn't produce a program, almost always because of an error in the C. Print clang's own message: it points at the line your renderer got wrong.

Your interpreter and your compiled C agree on every test you have. What does that prove?

You wrote both sides. What if you misread one rule and coded it the same way twice?

Agreement between two things you wrote is strong evidence, not proof. If you believed div truncates and built that into both, they would agree and both be wrong. The grader's oracle is the third opinion that catches it.
