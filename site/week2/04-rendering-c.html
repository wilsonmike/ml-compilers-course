Rendering C

So far your compiler has worked out every answer itself. In this lesson it starts writing: it prints a C program that does the same work, and a C compiler turns that into machine code. You learn what to print for each node, in what order, and how to stop C from changing the answer.

Goal

Turn a checked .uir graph into lines of C that give exactly the answers .uir promises.

You'll use

Reading C, undefined behavior and division that truncates, from lesson 0.1. Buffer versions from lesson 2.2 and f32 from lesson 2.1. The slow version of wrapping is H.4.

In the exercises: a dict (P.3), a small class (P.4) and a function that calls itself (P.5).

In the exercises: match on a list (O.3), your own types (O.4) and a ref (O.5).

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

What is %x?

%b  = buffer 2 [10 20] dtype=i32 slot=0
%e  = shrink %b 0 []
%s  = store %e 99
%b1 = after %b %s
%x  = load %e

%e is a view of %b. Which version does the store change: %b or %b1?

10. A store never changes %b. The 99 lives in the new version %b1, and this load reads the old one.

The largest i32 is 2147483647. What is add 2147483647 1 in .uir?

An i32 has no room for a bigger number, so it rolls over like a car's odometer.

It wraps to the smallest i32, -2147483648. Nothing fails. Hold on to this: C does not agree, and that is half of this lesson.

Your compiler writes a C program

A program that runs another program directly is an interpreter. That is what your ./compile has been so far. A compiler does something else: it writes a new program in a lower-level language and lets that program do the work. Yours will write C. Printing that C is called rendering.

Here is a program that doubles the number in a buffer, and next to it the C your renderer will print for it, with one line hidden.

%b  = buffer 1 [21] dtype=i32 slot=0
%e  = shrink %b 0 []
%x  = load %e
%y  = add %x %x
%s  = store %e %y
%b1 = after %b %s
void kernel(int32_t *restrict b0) {
  int32_t v3 = b0[0];
  int32_t v4 = (int32_t)((uint32_t)v3 + (uint32_t)v3);
  ???
}

Which line of C belongs where the ??? is?

The load and the add are printed. The .uir line that still has work to do is the store.

The store writes v4 into element 0 of the buffer. The function returns nothing: its results are whatever it leaves in the buffers.

Read the C against the .uir:

  1. The buffer becomes a parameter. The function is always called kernel. It takes one pointer per buffer, in slot order, so slot 0 is b0.
  2. The load becomes a read. The view %e is b0 at offset 0, so %x is b0[0], saved in a variable.
  3. The add becomes a new variable. It is longer than v3 + v3. A later section shows why.
  4. The store becomes an assignment. shrink and after print no line at all.

The file is compiled on its own, so it starts with #include lines for <stdint.h> (int32_t), <stdbool.h> (bool) and <math.h> (NAN, INFINITY, isnan). restrict is the promise from lesson 0.1, and you may leave it out.

One node, one line

Rendering is three jobs:

  1. Schedule. Pick an order for the lines. Every node comes after its sources.
  2. Name. Give each value node one C variable. The names can be anything unique. The oracle uses v and the node's number.
  3. Print. Write each op as C that means exactly what the .uir op means.

Which line goes first

This program swaps elements 0 and 2. Both loads read the first version, %b.

%b  = buffer 3 [1 2 3] dtype=i32 slot=0
%e0 = shrink %b 0 []
%e2 = shrink %b 2 []
%x  = load %e0
%y  = load %e2
%s0 = store %e0 %y
%b1 = after %b %s0
%f2 = shrink %b1 2 []
%s1 = store %f2 %x
%b2 = after %b1 %s1

Your graph does not remember the order of these lines. It only has source edges. Suppose a renderer prints each store as soon as its value is ready. It could print this:

int32_t v5 = b0[2];
b0[0] = v5;
int32_t v6 = b0[0];
b0[2] = v6;

The buffer starts as 1 2 3. What does it hold after those four lines of C? Write the three numbers.

Run the C one line at a time. What is in b0[0] when the third line reads it?

3 2 3. The 1 was overwritten before it was read, so the swap turned into a copy. The .uir program says 3 2 1.

The graph has two versions of the buffer. C has one array, and a store changes it in place. The moment b0[0] = v5; runs, version %b is gone. So the scheduler follows one extra rule: a store into version V comes after every load of V.

  1. Find the loads of %b. %x and %y.
  2. Hold the store back. %s0 writes into %b, so treat both loads as extra sources of %s0.
  3. Sort as usual. Sources first, as in week 1. The oracle prints:
int32_t v5 = b0[2];
int32_t v6 = b0[0];
b0[0] = v5;
b0[2] = v6;

An order like this always exists. The checker from lesson 2.2 already rejects the one shape where it would not: a load of an old version whose offset depends on a newer version.

Loads before the store

schedule takes toy nodes and returns their names in the order to print them. A node is a tuple (name, kind, version, srcs), and kind is "load", "store" or "op".A node is a record with name, kind, version and srcs, and kind is Load, Store or Op. For a load, version is the buffer version it reads. For a store, it is the version it overwrites.

The sort is written: visit prints a node after everything in needs. Right now needs is only the node's sources, so the swap comes out as a copy. Change needs so that a store also needs every load of the version it overwrites.

Why a + b is the wrong C

Take these two lines, where %x was loaded from a buffer that holds 2147483647, the largest i32. In .uir the add wraps to the smallest i32, so %lt is false.

%y   = add %x 1
%lt  = cmplt %x %y

A renderer that prints add as a plain + would write:

int32_t v7 = v5 + 1;
bool v8 = (v5 < v7);

This is the trap from lesson 0.1. Built with clang -O2, that C stores true: signed overflow is undefined behavior, so the optimizer assumes it never happens and deletes the compare. .uir has no undefined behavior, so your renderer must never print C that has any. The grader compiles with -fsanitize=undefined -fsanitize-trap=undefined, which makes undefined behavior crash the test.

The fix is the one from lesson 0.1. Unsigned math wraps by definition, so convert to uint32_t, add and convert back:

int32_t v7 = (int32_t)((uint32_t)v5 + (uint32_t)1);

mul and shl get the same treatment. shl has one more trap: C does not define a shift by 32 or more, or by a negative amount. .uir shifts by b mod 32, which in C is b & 31.

Make mul and shl wrap

uir_add is done. uir_mul and uir_shl still use the plain C operator, and the runner traps undefined behavior. Fix uir_mul the way uir_add does it. In uir_shl, shift (uint32_t)a by ((uint32_t)b & 31u) and convert the answer back.

Division rounds the other way

A buffer holds -7, and the program computes div %x 2. .uir's div floors, so the answer is -4. A renderer that prints v3 / 2 gets -3, because C truncates toward zero (lesson 0.1).

C's / and % have a second problem: a / 0 and INT_MIN / -1 are undefined behavior, and .uir defines both. So the renderer prints a call to a small helper function, which it defines once above kernel. The oracle prints this for the program above:

int32_t v5 = i32_div(v3, 2);

The helper answers b == 0 and b == -1 without dividing. For everything else it divides the C way, then fixes the result when the remainder is nonzero and its sign differs from b's: that is exactly when C rounded the wrong way. The toggle below has each case.

Floor division in C, without undefined behavior

Write int32_t uir_div(int32_t a, int32_t b) and int32_t uir_mod(int32_t a, int32_t b): .uir's div and mod, in C. The quotient is the floor of a / b, wrapped to 32 bits, so uir_div(-7, 2) is -4 and uir_div(INT_MIN, -1) is INT_MIN. The remainder is a - b * floor(a / b), so uir_mod(-7, 2) is 1 and uir_mod(7, -2) is -1. b = 0 gives -1 and a. No input may hit undefined behavior: the runner traps it.

On Windows, a naive INT_MIN / -1 can hang the test until the runner times it out.

The other ops have no undefined cases, and the oracle prints them directly: i32 max as (a > b ? a : b), cmplt as (a < b), where as (c ? a : b), xor as (a ^ b) for i32 and (a != b) for bool, f32 add and mul as (a + b) and (a * b), and recip as (1.0f / a).

Print each node once

Your graph is hash consed, so a value used five times is one node.

A program doubles a value 30 times: each line is add of the line above with itself. A renderer prints a node's sources again every time it meets them. About how many lines of C does it print?

The top node prints the node below it twice. Each of those prints the next one down twice. Keep doubling for 30 levels.

About 230, which is over a billion. Week 2 has no node budget, so a test can go 300 levels deep. Printing each node once gives 300 lines.

The cure is a table from node to C name:

  1. Look first. If the node is in the table, use its name and stop. Do not walk into its sources.
  2. Print. Otherwise get the text for its sources, then print one line with a fresh name.
  3. Remember. Put the node and its name in the table.

Key the table on which node it is, not on what the node looks like.

Print a shared node once

emit turns a toy expression into C lines and the name of the result. It works, but a node used twice is printed twice: for x * x with x = a + 1 it prints the add two times. The table names exists and nothing uses it. Use it: look the node up before walking into its sources, and save the name after printing the line. Float constants that survive the trip

A constant in your graph is an exact f32. The C file is text, so the constant has to be written as text and read back by the C compiler as the same f32. Suppose the renderer prints floats the default way, with C's %g.

The constant is 16777215.0. %g prints it as 1.67772e+07. What number does the C compiler read back?

e+07 means "times ten million". How many digits did %g keep?

16777200. %g keeps six digits, so the last 15 is gone and the program now computes with a different number.

Nine digits (%.9g) are enough for any f32. There is a cleaner way: a hex float writes the bits themselves. Here is how to read 0x1.8p+1f:

  1. The digits. 0x1.8 is in base 16: 1 plus 8 sixteenths, which is 1.5.
  2. The power. p+1 means times 21. So the value is 3.
  3. The suffix. f makes it a float and not a double.

For mul %x 0.1 the oracle prints (v3 * 0x1.99999a0000000p-4f). Trailing zeros change nothing: 0x1.99999ap-4f is the same number. Three values have no literal, so use NAN, INFINITY and (-INFINITY) from <math.h>. Negative zero keeps its sign: -0x0p+0f, which the oracle writes as -0x0.0p+0f.

An f32 as an exact C literal

Write c_float : float -> stringc_float(x: float) -> str. The input is already an f32 value. Return NAN for any NaN, INFINITY for +inf, (-INFINITY) for -inf, and otherwise what Printf.sprintf "%h" printsthe exact hex float in its shortest form (x.hex() with the trailing zeros of the fraction dropped), followed by f.

Float max is not fmaxf

f32 add and mul are easy: C's float rounds after every operation, exactly like .uir. max looks easy too, because C has a function for it, fmaxf. In .uir, max nan 1.0 is nan.

What does C's fmaxf(NAN, 1.0f) return?

C's rule for the fmax family is to treat a NaN as missing data.

1.0f. C ignores a NaN when the other side is a number. .uir does the opposite, so fmaxf gives the wrong answer.

.uir's max returns NaN if either side is NaN, and returns +0.0 for max(-0.0, 0.0) in either order. So print one more small helper above kernel and call it for every f32 max. The oracle calls its helper f32_max.

Why the grader passes -ffp-contract=off, for when you build your own runtime

One compiler habit can break "round after every operation": contraction. Given a * b + c, the compiler may emit one fused multiply-add instruction that rounds once instead of twice. That's usually more accurate, and it's still the wrong answer for us:

a = 0x1.001p+0f, b = 0x1.001p+0f, c = -0x1.002p+0f
two roundings: (a * b) rounds to 0x1.002p+0, plus c gives 0
one rounding:  fmaf(a, b, c) gives 0x1p-24

-ffp-contract=off forbids that fusion, so the C rounds after every op like the oracle does. The grader passes it for you. If you build your own runtime, pass it too: clang contracts within an expression by default on targets with fused multiply-add, which includes every Apple Silicon Mac.

How vectors, calls, casts and allocs print, for when you reach them in the lab

A rank-1 value becomes a small local array. stack is an array initializer and index is a subscript. Every index has been proven in range, so the subscript never reads past the array. This is the oracle's output for tests/week2/render/stack_index_dynamic.uir, where stack 100 200 300 is indexed by two loaded values mod 3. A loaded value can be negative, so each mod goes through the helper:

void kernel(int32_t *restrict b0, int32_t *restrict b1) {
  int32_t v5[3] = {100, 200, 300};
  int32_t v8 = b0[0];
  int32_t v10 = i32_mod(v8, 3);
  int32_t v11 = v5[v10];
  int32_t v14 = b0[1];
  int32_t v15 = i32_mod(v14, 3);
  int32_t v16 = v5[v15];
  int32_t v17[2] = {v11, v16};
  b1[0 + 0] = v17[0];
  b1[0 + 1] = v17[1];
}

A rank-1 load or store can't use a loop, so it is unrolled one element at a time. In tests/week2/render/rank1_copy.uir, loading shrink %a 2 [3] and storing it into shrink %b 1 [3] prints:

void kernel(float *restrict b0, float *restrict b1) {
  float v6[3] = {b0[2 + 0], b0[2 + 1], b0[2 + 2]};
  b1[1 + 0] = v6[0];
  b1[1 + 1] = v6[1];
  b1[1 + 2] = v6[2];
}

A call doesn't become a C function. It is inlined: the body is printed again for each call, with each param replaced by its arg's name. In tests/week2/render/call_inlined.uir, two calls of p * 10 + q with the args swapped print four lines, two per call.

Most casts are plain C casts. i32 or bool to f32 prints ((float)x), which rounds to nearest-even like .uir. Anything to bool prints (x != 0), which is true for nan, as .uir says. f32 to i32 is the exception: it saturates in .uir and is undefined in C for NaN and out-of-range values, so it calls the saturating helper from the table of safe C.

The C must have no loops and no recursion. It may call <math.h> functions, memcpy from <string.h> and helper functions defined in the same file that do not call themselves, and nothing else.

An alloc whose contents never reach a buffer changes no output, so you may leave it out of the C. Every alloc you do print must start as zeros, because reading memory that was never set is undefined behavior too.

Check yourself

The graph loads b0[2] from version %b, and separately stores into b0[2] to make %b1. Which C order is correct?

The graph has two versions. The C array has only one. What's in b0[2] right after the store runs?

The load. C stores in place, so once b0[2] = ... runs, version %b's value is overwritten. That's why the scheduler makes every store depend on all loads of the version it overwrites.

What does this C expression evaluate to, on every compiler you'll use?

(int32_t)((uint32_t)INT32_MAX + 1u)

Unsigned addition wraps modulo 232. What bit pattern is 231, and what is it as a signed 32-bit number?

-2147483648. The unsigned sum is 231, bit pattern 0x80000000, which converts back to INT_MIN. That's .uir's i32 wraparound, spelled without undefined behavior.

What does the C standard say INT_MIN / -1 evaluates to?

The true quotient is 231. Does that fit in a signed 32-bit int, and what does C say about signed results that don't fit?

Undefined behavior. The quotient doesn't fit, and C doesn't define the result. On x86 it raises a hardware exception. .uir defines it as INT_MIN, so your renderer must handle b == -1 without dividing.

C's -7 / 2 is -3. What must uir_div(-7, 2) return?

.uir's div is the floor of the exact quotient, -3.5. Floor rounds down, toward minus infinity.

-4. C truncated toward zero, the remainder -7 % 2 is -1, nonzero and with a different sign from 2, so the helper subtracts one. uir_mod(-7, 2) is then 1.

What does printf("%g", FLT_MAX) print?

%g uses 6 significant digits by default. FLT_MAX is about 3.4028234663852886 × 1038.

3.40282e+38, and C reads that back as a slightly smaller float (bits 0x7f7fffee, not 0x7f7fffff). Short decimal output loses bits, which is why the renderer prints hex floats.

Why can't the renderer print every f32 max as fmaxf(a, b)?

Look up what C's fmax family does when one argument is NaN, and compare it with the spec's row for max.

C's fmaxf ignores a NaN argument and returns the other one. .uir propagates NaN, and pins max(-0.0, 0.0) to +0.0, which fmaxf doesn't promise. A small helper gets both right.

How many lines of C does an after node produce?

An after is a new version of the same storage. In C, where does that storage live, and did anything need to be copied?

0. The store already changed the array in place. after only tells the scheduler and later loads which version they're reading. In C it's the same pointer.
