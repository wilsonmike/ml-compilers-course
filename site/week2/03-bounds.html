Proving bounds

A program that reads past the end of a buffer gets whatever is stored next door, and nobody is told. In this lesson you prove, before the program runs, that every read and write lands inside its buffer. The tool is one you already have: the bounds from week 1.

Goal

Decide whether a view is provably inside its buffer, and repair one that is not.

You'll use

Bounds, the smallest and largest a value can be, from lesson 1.4. Buffers and shrink views from lesson 2.1. load, store and after from lesson 2.2.

In the exercises: a tuple and unpacking it (P.3).

In the exercises: a tuple taken apart in the function's arguments (O.3).

Warm up

Two questions from lesson 1.4, from memory. Pulling an idea back out of your head is what makes it stay.

%x can be any i32. What are the bounds of mod %x 8? Write them as [lo, hi].

mod floors, so a remainder by 8 is never negative. What is the smallest remainder, and the largest?

[0, 7]. A remainder by 8 is one of 0 to 7, even when %x is negative: mod -1 8 is 7.

%k has bounds [0, 3]. What are the bounds of add %k 4?

The rule for add: add the two low ends, and add the two high ends. The literal 4 has bounds [4, 4].

[0 + 4, 3 + 4] is [4, 7]. You will use both of these answers in this lesson.

A read that misses the buffer

This buffer has 8 elements, numbered 0 to 7. The program asks for element 10.

%b = buffer 8 [5 6 7 8 9 10 11 12] dtype=i32 slot=0
%e = shrink %b 10 []
%x = load %e
element012345678910
holds56789101112???

In lesson 2.4 your compiler turns programs like this into C, and the load becomes int32_t x = b[10];.

What does C do when it runs b[10] on a buffer of 8 elements?

Lesson 0.1: C does not store a buffer's size next to it. b[10] only means "start at b and step 10 elements along".

C does not check. Most of the time it reads whatever is next door: another variable or leftover junk. Now and then the memory is not the program's at all, and it crashes. C calls this undefined behavior, which means anything may happen. The usual result is a wrong number and no error.

A store is worse: it overwrites something that belongs to another part of the program.

So .uir promises that nothing goes wrong at run time. The compiler does not add a check before every read, which would cost time on every access. It proves, before anything runs, that every view is inside its buffer. A program with a view it cannot prove is invalid: ./compile prints REJECTED for the file above, and render refuses it too.

A fixed offset like 10 is easy to check. The hard case is an offset the program computes.

Which of these views are safe?

Predict before you get any rule. %b is a buffer of 8 elements. %i is a number loaded from a second buffer, %ix:

%b  = buffer 8 [5 6 7 8 9 10 11 12] dtype=i32 slot=0
%ix = buffer 1 [2] dtype=i32 slot=1
%i0 = shrink %ix 0 []
%i  = load %i0

A view is safe when it can never reach outside %b, whatever the buffers hold.

Is shrink %b %i [] safe? The file says %ix starts as [2].

A buffer lives outside the program. Who decides what it holds when the compiled code runs?

The data in the file is one possible input. The compiled kernel runs on whatever its caller passes, so %i could be any i32. This view is the read of element 10 again, waiting for the wrong data.

Add one line, %k = mod %i 8. Is shrink %b %k [] safe?

This is the first warm up question.

%k has bounds [0, 7], and the elements of %b are numbered 0 to 7. Whatever %i is, the view lands inside.

In both you asked the same thing: how small and how large can the offset be, and does the window still fit at both ends? That question is the whole proof.

The proof in three steps

Take a view shrink m off [k]. Its parent m has n elements, and the window is k elements wide. A [] view counts as k = 1. The compiler proves the view like this:

  1. Find the offset's bounds. Use the week 1 rules to get [lo, hi] for off. A literal like 6 has bounds [6, 6].
  2. Find the last allowed start. A window of k elements fits when it starts at n - k or earlier.
  3. Compare. The view is proven when lo ≥ 0 and hi ≤ n - k. If either test fails, the program is rejected.

Try it on shrink %b %k [2], with %k = mod %i 8 and the 8 elements of %b:

  1. Find the offset's bounds. %k is [0, 7].
  2. Find the last allowed start. 8 - 2 is 6.
  3. Compare. 0 ≥ 0 holds. 7 ≤ 6 does not. Rejected: a window that starts at 7 would cover elements 7 and 8.

What is the last allowed start for a [3] view on a buffer of 8 elements?

Step 2: n - k.

8 - 3 is 5. A window that starts at 5 covers elements 5, 6 and 7, which is the end of the buffer. So shrink %b 6 [3] is rejected.

Repair the bounds check

view_safe (lo, hi) n k answers one question: is a view of k elements provably inside a parent of n elements, when all you know about its offset is the bounds (lo, hi)? It follows the three steps, and two of them are wrong:

  • Step 2. last_start is only right for a one-element view. Make it right for any k.
  • Step 3. The compare checks the high end only. A negative offset gets through. Check the low end too.
The rule as the spec writes it, and everything it covers, for when you write validation in the lab

The spec states the same test as lo ≥ 0 and hi + k ≤ n. The first part says the window cannot start before the parent. The second says that even at its largest offset the window still ends inside. The allowed offsets are exactly [0, n - k], and the whole range of off has to sit inside it.

  • With a constant offset the bounds are a single point, so this is the plain check from lesson 2.1.
  • Every shrink is checked, whether a load or a store uses it or nothing does.
  • A view of a view is checked against its own parent, not against the buffer underneath.
  • The offset must be an i32 scalar. A loaded bool has bounds [0, 1], but it cannot be an offset until you cast it.
  • The oracle's message names all three numbers: can't prove the view is in bounds: offset in [0, 7], 2 element(s), parent has 8.

A loaded value could be anything

Step 1 needs bounds for the offset. Memory comes from outside the program, so the compiler knows nothing about a number loaded from it. A loaded i32 gets the full range, from INT_MIN (-2147483648) to INT_MAX (2147483647). That is why shrink %b %i [] failed: step 3 compares that huge range with [0, 7].

To make the view valid, you shape the value with ops whose bounds rules give a small answer. The one that does most of the work is mod. It floors, so a nonzero remainder has the sign of the right operand. mod %i 4 is in [0, 3] for every %i, negative ones included: mod -7 4 is 1, not -3.

Step through a 4-element buffer. The green line is the allowed starts, [0, n - k]. The thick line is the offset's bounds.

A guard is not a proof

In C you'd write if (i < 4) x = d[i];. The .uir equivalent, where (cmplt %i 4) %i 0, doesn't help: when the condition isn't fixed, the bounds of a where are the hull of both branches, so the bounds are still everything %i could be. The analysis doesn't look at the condition. The oracle rejects where (cmplt %i 4) (max %i 0) 0 with offset bounds of [0, 2147483647].

Nested forms like shrink %b (mod %i 4) [] are shorthand on this page. In a .uir file each op is its own line. Now repair a program the compiler rejects.

A gather the compiler can prove

Slot 0 is four i32s of data, slot 1 holds one index and slot 2 is a one-element result. Set res[0] = d[i] for the index i in ix[0]: a negative i reads d[0], and any other i reads d[i mod 4]. The starter is the natural first try, and the compiler rejects it.

mod %i 4 on its own is provably in range, but it sends i = -5 to d[3], not d[0]. The negative case needs one more op, before the mod.

Offsets built with arithmetic

An offset can be the result of several ops. The three steps stay the same. Step 1 just pushes bounds through more lines, one rule per op, as in week 1. Here are three offsets for a [] view on a buffer of 8 elements, where the last allowed start is 7. add adds the low ends and the high ends, as long as nothing can wrap.

lineboundsas an offset
%k = mod %i 4[0, 3]proven
%o = add %k 4[4, 7]proven
%p = add %k 5[5, 8]rejected: 8 is past 7

%k has bounds [0, 3] and %b has 8 elements. Is shrink %b (mul %k 2) [2] proven?

Do the three steps. The bounds of mul %k 2 run from 0 × 2 to 3 × 2.

The offset is [0, 6]. The last allowed start is 8 - 2 = 6. 0 ≥ 0 and 6 ≤ 6, so it is proven: a window that starts at 6 covers elements 6 and 7. Nothing here comes near INT_MAX, so nothing wraps.

Now write the lines yourself.

Two reads from one index

Slot 0 is eight i32s of data, d. Slot 1 holds one index, and the starter loads it as %i. Slot 2 is a one-element result. With k = i mod 4, set res[0] = d[k] + d[k + 4]. Both views must be provable for every i, so give each offset its own line and check its bounds with the three steps.

The grader sets the data in slots 0 and 1 for each test and checks the final contents of slot 2.

Two more places the same proof shows up: a view of a view, and index

You can also cut the window first and index inside it: shrink %b 4 [4], then shrink that by %k. The inner view only has to fit the four-element window, and [0, 3] does.

The week 1 rule for index still applies, and it's the same idea. index [7 8 9] %i with a loaded %i is rejected, and index [7 8 9] %k with %k = mod %i 3 is safe. An index into a vector you loaded works the same way: loading a [3] view gives an axis of size 3, just like the stack.

Where mod's bounds come from

Most of your proofs lean on mod. Lesson 1.4 gave its bounds rule in a table, and here you turn it into code. Predict first.

%x has bounds [9, 11]. What are the tightest bounds of mod %x 8?

Work out mod 9 8, mod 10 8 and mod 11 8.

The remainders are 1, 2 and 3. [0, 7] is true but wider than it needs to be. The spec's rule gives [1, 3], and your compiler has to give exactly what the spec gives.

The rule for mod x y, with x in [lo, hi] and y a fixed number:

  1. Handle zero. mod x 0 returns x, so the bounds are [lo, hi].
  2. Compare the two quotients. Floor divide lo and hi by y. If the answers match, no multiple of y gets in the way, and the remainders run from lo mod y to hi mod y. Answer those two, smaller one first.
  3. If they differ, the remainder wraps. It can be any remainder at all: [0, y - 1] for a positive y, and [y + 1, 0] for a negative one.

For [9, 11] and 8, both quotients are 1, so step 2 gives [1, 3]. For [7, 9] the quotients are 0 and 1, so step 3 gives [0, 7].

Bounds of x mod y

Write mod_bounds (lo, hi) ymod_bounds(r, y), with r = (lo, hi): the three steps above, returning the pair (lo, hi) of the answer. So mod_bounds (9, 11) 8mod_bounds((9, 11), 8) is (1, 3), and mod_bounds (7, 9) 8mod_bounds((7, 9), 8) is (0, 7).

C's % truncates instead, so its remainder has the sign of x and can be negative. Lesson 2.4 renders mod with a helper for exactly that reason.

Why your bounds must match the spec exactly, not just be true

Soundness versus exact spec rules. In general, a wrong interval that leaves out a value the offset can really take is dangerous, because your compiler would accept a program that reads outside its memory. In this course, validation uses week 1's exact interval rules (neither tighter nor looser), so every compiler accepts and rejects the same programs in the test suite.

The full table of rules, one per op, is in lesson 1.4.

Check yourself

What are the bounds of %i = load %e, where %e is a view of a buffer whose data is [3 1 2 0]?

Is the data part of the program, or does it come from outside?

Memory is input: the same kernel runs on whatever data the caller passes. The starting data in a test file is just one possible input, so a loaded value gets the full i32 range.

What are the bounds of mod %i 4 when %i is a loaded value? Write it as [lo, hi].

In .uir, mod floors, so a nonzero remainder has the sign of the right operand, not the left.

[0, 3]. Even a negative %i gives a remainder from 0 to 3: mod -7 4 is 1. That's exactly the allowed range for a [] view on 4 elements. C's % would give [-3, 3].

On a buffer of 4 elements, with %i loaded from memory, what's the largest m for which shrink %b (mod %i m) [2] can be proven in bounds?

The allowed offsets are [0, n - k]. What's n - k here?

For a positive m, mod %i m is [0, m - 1].

A two-element window on four elements can start at 0, 1, or 2, so hi must be at most 2. [0, m - 1] fits when m - 1 ≤ 2, so m = 3. With m = 4 the oracle reports offset [0, 3], which doesn't fit.

Why doesn't where (cmplt %i 4) (max %i 0) 0 give a provable index for a 4-element buffer?

What are the bounds of the two branches?

The branches are [0, INT_MAX] and [0, 0], so the hull is [0, INT_MAX]. The bounds analysis learns nothing from the condition. Shape the value itself with mod instead.

On an 8-element buffer, %k is in [0, 3]. Which offset works for a [] view?

Work out each offset's bounds and compare them with [0, 7].

add %k 4 is [4, 7], inside [0, 7]. add %k 5 reaches 8, add %k -1 reaches -1, and mul %k 3 reaches 9.

For a [k] view on a parent of n elements, the offset's bounds must fit inside [0, ?]. What goes in place of the question mark?

The window's last element is at off + k - 1, and that must be at most n - 1.

off + k - 1 ≤ n - 1 means off ≤ n - k, which is the same as the rule hi + k ≤ n.
