Proving bounds

The syllabus says loads and stores are "bounds checked to never be out of range". Our compiler doesn't check at run time. It proves, before anything runs, that every view is inside its memory, using week 1's bounds rules: the same ones that already decide whether an index is safe.

The rule

For shrink m off [k], where the parent m has n elements (k counts as 1 for a [] view), work out the interval [lo, hi] of off, then require:

lo ≥ 0     and     hi + k ≤ n

The first says the window can't start before the parent. The second says that even at its largest offset, the window still ends inside. The allowed offsets are exactly [0, n - k], and the whole interval of off has to sit inside that range.

With a constant offset the interval is a single point, so this is the plain check from lesson 1. It gets interesting when the offset is computed.

Loaded values are unknown

A value loaded from memory could be anything, because memory comes from outside. Its interval is the full i32 range. So this gather, which reads an index from one buffer and uses it on %d, a 4-element buffer, is invalid, even if the data happens to hold a small number:

%i0  = shrink %ix 0 []
%i   = load %i0                 # interval: [INT_MIN, INT_MAX]
%src = shrink %d %i []          # can't prove 0 ≤ %i ≤ 3

To make it valid you shape the interval with ops whose bounds you can compute, using week 1's exact rules (spec section 5). The one that does most of the work is mod. It floors, so a nonzero remainder has the sign of y: mod %i 4 is in [0, 3] for every %i, negative ones included. mod -7 4 is 1, not -3. We write nested forms like shrink %b (mod %i 4) [] as shorthand, but in a .uir file each op is its own binding. Step through: the green line is the allowed range [0, n - k], and the thick line is the offset's interval.

A guard is not a proof

In C you'd write if (i < 4) x = d[i];. The .uir equivalent, where (cmplt %i 4) %i 0, doesn't help: when the condition isn't fixed, the bounds of a where are the hull of both branches, so the interval is still everything %i could be. The analysis doesn't look at the condition. The oracle rejects where (cmplt %i 4) (max %i 0) 0 with an offset interval of [0, 2147483647].

A gather the compiler can prove

Slot 0 is four i32s of data, slot 1 holds one index and slot 2 is a one-element result. Set res[0] = d[i] for the index i in ix[0]: a negative i reads d[0], and any other i reads d[i mod 4]. The starter is the natural first try, and the compiler rejects it.

mod %i 4 on its own is provably in range, but it sends i = -5 to d[3], not d[0]. The negative case needs one more op, before the mod.

Offsets add up, and so do intervals

A view of a view is checked against its own parent. An offset built from arithmetic is checked with the interval rules for that arithmetic: add adds the endpoints when nothing can wrap. With an 8-element buffer:

%k = mod %i 4         # [0, 3]
%o = add %k 4         # [4, 7]: fits a [] view on 8 elements
%p = add %k 5         # [5, 8]: 8 + 1 > 8, invalid

You can also cut the window first and index inside it: shrink %b 4 [4], then shrink that by %k. The inner view only has to fit the four-element window, and [0, 3] does.

The week 1 rule for index still applies, and it's the same idea. index [7 8 9] %i with a loaded %i is rejected, and index [7 8 9] %k with %k = mod %i 3 is safe. An index into a vector you loaded works the same way: loading a [3] view gives an axis of size 3, just like the stack.

Soundness versus exact spec rules

In general, a wrong interval that leaves out a value the offset can really take is dangerous, because your compiler would accept a program that reads outside its memory. In this course, validation uses week 1's exact interval rules (neither tighter nor looser), so every compiler accepts and rejects the same programs in the test suite.

Bounds of x mod y

This is the week 1 rule the oracle uses for mod x y when x is in [lo, hi] and y is fixed. Write mod_bounds (lo, hi) ymod_bounds(r, y), with r = (lo, hi). If y is 0, mod returns x, so the answer is (lo, hi). Otherwise, if lo and hi have the same floor quotient by y, the remainders run from lo mod y to hi mod y, so answer their hull. If the quotients differ, the remainder wraps around: answer (0, y - 1) for a positive y and (y + 1, 0) for a negative one. So mod_bounds (9, 11) 8mod_bounds((9, 11), 8) is (1, 3), and mod_bounds (7, 9) 8mod_bounds((7, 9), 8) is (0, 7).

C's % truncates instead, so its remainder has the sign of x and can be negative. Lesson 4 renders mod with a helper for exactly that reason.

Check yourself

What's the interval of %i = load %e, where %e is a view of a buffer whose data is [3 1 2 0]?

Is the data part of the program, or does it come from outside?

Memory is input: the same kernel runs on whatever data the caller passes. The starting data in a test file is just one possible input, so a loaded value gets the full i32 range.

What's the interval of mod %i 4 when %i is a loaded value? Write it as [lo, hi].

In .uir, mod floors, so a nonzero remainder has the sign of the right operand, not the left.

[0, 3]. Even a negative %i gives a remainder from 0 to 3: mod -7 4 is 1. That's exactly the allowed range for a [] view on 4 elements. C's % would give [-3, 3].

On a buffer of 4 elements, with %i loaded from memory, what's the largest m for which shrink %b (mod %i m) [2] can be proven in bounds?

The allowed offsets are [0, n - k]. What's n - k here?

For a positive m, mod %i m is [0, m - 1].

A two-element window on four elements can start at 0, 1, or 2, so hi must be at most 2. [0, m - 1] fits when m - 1 ≤ 2, so m = 3. With m = 4 the oracle reports offset [0, 3], which doesn't fit.

Why doesn't where (cmplt %i 4) (max %i 0) 0 give a provable index for a 4-element buffer?

What are the intervals of the two branches?

The branches are [0, INT_MAX] and [0, 0], so the hull is [0, INT_MAX]. Interval analysis doesn't learn anything from the condition. Shape the value itself with mod instead.

On an 8-element buffer, %k is in [0, 3]. Which offset works for a [] view?

Work out each interval and compare it with [0, 7].

add %k 4 is [4, 7], inside [0, 7]. add %k 5 reaches 8, add %k -1 reaches -1, and mul %k 3 reaches 9.

For a [k] view on a parent of n elements, the offset's whole interval must fit inside [0, ?]. What goes in place of the question mark?

The window's last element is at off + k - 1, and that must be at most n - 1.

off + k - 1 ≤ n - 1 means off ≤ n - k, which is the same as the rule hi + k ≤ n.
