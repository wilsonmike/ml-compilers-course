What number does %x hold?

How a render test is graded, step by step, for when a kernel fails

A render test is a valid program with a # render header. For each one, the grader:

  1. Runs your.exe render FILE, and fails the test on a nonzero exit.
  2. Removes comments and string literals from your C, and fails the test if for, while, do or goto appears.
  3. Writes its own main: one static array per buffer, filled with each buffer's starting data (f32 copied in from exact bit patterns), then a call to your kernel in slot order, then one line per element (f32 as 8 hex digits of bits).
  4. Compiles both files with clang -std=c11 -O2 -ffp-contract=off -fsanitize=undefined -fsanitize-trap=undefined ... -lm (with gcc, the equivalent trap flag).
  5. Runs the program, and compares every element of every buffer with the oracle: i32 and bool exactly, f32 bit for bit, with any NaN matching any NaN.

A crash in step 5 almost always means undefined behavior that the sanitizer turned into a trap: signed overflow, a division by zero, INT_MIN / -1, a shift by 32 or more, or an f32 to i32 cast of NaN or a huge value. One Windows quirk: a naive INT_MIN / -1 there tends to hang in the system error reporter instead of crashing, so you'll see "didn't finish" rather than "crashed". Check your div and mod first.

Plan it first

Memory has to work in two places: the interpreter behind compile FILE, and the C that render prints. Which comes first?

In lesson 2.2 a version is a value. In lesson 2.4 C has one array, so the order of the lines matters.

In the interpreter each version can be its own copy of the array, so no order is needed. It is the easy one, and it gives you the right answer to hold your C against.

One piece of render can't wait, though: saying no. It needs only code you have, and none of the 54 run tests named rejected_ can pass without it. So the route is a render that refuses, then floats, memory, order and bounds in compile FILE, and C last.

Floats

First the changes that need no memory.

  1. Lift the week 1 limits. No byte, node, edge or cost budget. A param and the left side of an assert may be a vector, such as [3].
  2. Read float literals. 1.5, .5, 2e3, inf, -inf and nan. Read each as a 64-bit float, then round to f32.

Buffers, views and load

Now memory, read only.

  1. Parse the new ops. buffer 3 [1 2 3] dtype=i32 slot=0, alloc 3 dtype=f32 and shrink %b 2 [3]. A list in square brackets is the last operand. A view's shape is [k] or [].
  2. Keep storage apart. Every buffer and alloc line is its own node. Hash consing must never merge two of them.
  3. Mark memory. Buffers, allocs and views have addrspace GLOBAL. Only shrink, load, store and after take them, and never inside a call body.
  4. Check each buffer. A size of 1 or more, a slot no other buffer has, and data of exactly that many literals of its dtype.
  5. Check each view fits. off ≥ 0 and off + k ≤ n, measured against the parent it was cut from, with k = 1 for []. Check every view, even one nothing uses. Literal offsets are enough for now.
  6. Load. A buffer starts as its data, or zeros. load gives a scalar through a [] view, and a vector through a [k] view or a whole buffer.

store, after and the order rules

Next your compiler writes. First fix a program that reads the wrong version.

Rotate three elements

The starter is meant to rotate slot 0 left, so [a b c] becomes [b c a], but one load reads the wrong version. Fix it. Keep it valid: every store sequenced, one store per version.

  1. Type them. store v x needs a value with the view's dtype and shape. after m s needs a store s and a whole version m: a buffer, an alloc or another after.
  2. Make versions values. In the interpreter, after m s is a copy of m's array with the write applied. A load reads the version it names.
  3. Find each store's version. Walk from its view down through the shrinks to a buffer, an alloc or an after.
  4. Check the order. One store per version at most. Every store is the s of exactly one after, and that after names the store's version.
  5. Check an order exists. Every load of version V has to be able to run before the store that overwrites V.

Prove every view

The run tests that are left compute an offset, often from a number read out of memory.

%i is loaded from an i32 buffer, so it could be -5. A buffer has 4 elements. Is the view at offset mod %i 4 safe?

Lesson 2.3: mod floors. What are the bounds of mod x 4 for any x?

Yes. The bounds of mod %i 4 are [0, 3] for every %i. Offset %i alone is rejected, whatever the data is.

  1. Bound a loaded value. It is unknown: the full i32 range for an i32, and [0, 1] for a bool.
  2. Prove with bounds. Run the fit check on the offset's week 1 bounds: lo ≥ 0 and hi + k ≤ n. A view that can't be proven makes the program invalid.

render: the smallest kernel

Now render prints C for a valid program. The runner builds that C, so it needs clang or gcc on your PATH. Start with tests/week2/render/copy_scalar.uir, which copies one element to another buffer. The oracle's kernel for it:

void kernel(int32_t *restrict b0, int32_t *restrict b1) {
  int32_t v5 = b0[0];
  b1[0] = v5;
}
  1. Print the top. Three #include lines, for <stdint.h>, <stdbool.h> and <math.h>. Then kernel, with one pointer per buffer in slot order: int32_t, float or bool.
  2. One node, one line. A load is a new variable. A store is an assignment. A view is its buffer plus the offsets added up. after and assert print nothing.
  3. Order the lines. Sources first. A store into version V goes after every load of V.

render: arithmetic that can't trap

Each i32 and bool op becomes one C expression. The plain spelling is often undefined in C, and the grader's build stops the program there.

  1. Wrap. add and mul go through uint32_t. shl shifts a uint32_t by b & 31.
  2. Floor. div and mod call helper functions that you print above kernel. Each one handles a divisor of 0, a divisor of -1 and the rounding.
  3. Print the easy ops. max, cmplt, xor and where have no undefined cases.
  4. Print each node once. One C variable per node. A node used twice is computed once and named twice.

Write your 10 tests

Same deal as week 1: 10 tests in <your compiler repo>/tests/week2/, each aimed at a rule someone will get wrong. A run test is named as in week 1. A render test starts with a # render line and has no assert. This one catches a mul printed as plain a * b:

# render
%b  = buffer 1 [65536] dtype=i32 slot=0
%e  = shrink %b 0 []
%x  = load %e
%y  = mul %x %x
%s  = store %e %y

Check your tests against the oracle:

python tools/test.py --check-tests <your compiler repo>/tests/week2 --week 2

With that one file in the folder, it prints 1 / 1 tests agree with the oracle.

Good targets for your tests, and what --check-tests does with each kind

A run test says what it expects in its file name: a mismatch_ or rejected_ prefix, or MATCH otherwise. For a render test, --check-tests renders it with the oracle, compiles it with the same harness and checks the buffers.

Good targets: two stores into one version (rejected), a load of an old version after the store (a swap), an offset from a loaded value with and without a mod, a wrapping mul in a render test, a cast of NaN or 3e9 to i32 and max on NaN and -0.0.

Check yourself

Your render output starts every kernel with a for loop that zeroes a scratch array. What happens?

Look at step 2 of "How a render test is graded" near the top of this page.

The grader rejects any for, while, do, or goto outside comments and strings. Zero an alloc with an initializer, = {0}, instead.

What outcome should your compiler print for this file?

%b  = buffer 2 dtype=i32 slot=0
%e  = shrink %b 0 []
%s1 = store %e 1
%s2 = store %e 2
%b1 = after %b %s1
%b2 = after %b1 %s2
%x  = load %b2
%t  = assert %x [2 0]

Which version does %s2 write into? Count the stores into that version.

REJECTED. Both stores write through %e, a view of %b, so version %b has two stores, which is unordered. On top of that, after %b1 %s2 names %b1 while %s2 writes into %b. Either problem alone makes it invalid.

The grader says "your kernel crashed (exit ...)" on a test that only does i32 add and mul. What's the most likely cause?

The grader compiles with -fsanitize-trap=undefined. Which of these is undefined behavior in C?

Signed overflow. A missing include would fail to compile, not crash, and a rounding difference would show up as a wrong value. Wrap through uint32_t.
