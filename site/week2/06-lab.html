Week 2 · Lesson 6

The week 2 lab

Extend your week 1 compiler with floats and memory: the f32 dtype, then buffers, views, loads, stores and versions, checked for order and bounds. Then teach it to print C. You're done when every week 2 test passes, week 1 still passes and you've written 10 new tests of your own.

What you're building

  • f32. Float literals, recip, rounding after every op, the NaN and -0.0 rules for max, cmplt and assert, and saturating casts, from lesson 1. Also rank-1 params and asserts, lists written as bracket operands, like the [3] in shrink %b 2 [3], and no budgets.
  • Memory in the type checker. buffer, alloc, shrink, load, store and after, from spec/uir-week2.md. Memory has addrspace GLOBAL and can't flow into ALU ops, stack, index, call or assert.
  • The ordering checks. One store per version, every store sequenced by exactly one after, and no load of a version that's needed after it was overwritten.
  • Bounds proofs. Every shrink proven in range with your week 1 bounds rules, like every index already is. A view you can't prove makes the program REJECTED.
  • Interpretation with memory, so ./compile FILE can evaluate asserts that read buffers.
  • A renderer: render FILE prints one loopless C function, kernel, with no undefined behavior.
  • Optionally, a runtime that compiles and runs that C. The grader brings its own harness, so you don't need one to pass. You'll want it by week 6, when kernels get timed.

The command-line contract

Week 1's outcome lines and simplify still apply. Week 2 adds floats and memory to the programs you check, and adds render.

commandresult
your.exe FILE...Same as week 1: one line per file, MATCH FILE, MISMATCH FILE or REJECTED FILE, with the path as given. There are no budgets this week, so nothing is OVERBUDGET. Ordering violations, unprovable bounds and memory used as a value are all REJECTED. Nothing fails at run time. You may interpret or compile, and the grader only sees the line.
your.exe render FILEPrint C to stdout that defines void kernel(T0 *b0, T1 *b1, ...), one pointer per buffer in slot order (float, int32_t, bool). Asserts are ignored. For an invalid program, print an invalid: line to stderr and exit 2: the grader also renders each rejected_ run test whose program is itself invalid, and expects that. No for, while, do or goto, and no calls outside the file except <math.h> and memcpy from <string.h> (non-recursive helpers you define in the same file are fine). Include <stdint.h>, <stdbool.h> and <math.h> at the top, because the file is compiled on its own.

How render tests are graded

A render test is a valid program with a # render header. For each one, the grader:

  1. Runs your.exe render FILE, and fails the test on a nonzero exit.
  2. Removes comments and string literals from your C, and fails the test if for, while, do or goto appears.
  3. Writes its own main: one static array per buffer, filled with each buffer's starting data (f32 copied in from exact bit patterns), then a call to your kernel in slot order, then one line per element (f32 as 8 hex digits of bits).
  4. Compiles both files with clang -std=c11 -O2 -ffp-contract=off -fsanitize=undefined -fsanitize-trap=undefined ... -lm (with gcc, the equivalent trap flag).
  5. Runs the program, and compares every element of every buffer with the oracle: i32 and bool exactly, f32 bit for bit, with any NaN matching any NaN.

A crash in step 5 almost always means undefined behavior that the sanitizer turned into a trap: signed overflow, a division by zero, INT_MIN / -1, a shift by 32 or more, or an f32 to i32 cast of NaN or a huge value. One Windows quirk: a naive INT_MIN / -1 there tends to hang in the system error reporter instead of crashing, so you'll see "didn't finish" rather than "crashed". Check your div and mod first.

Write your 10 tests

Same deal as week 1: 10 tests in <your compiler repo>/tests/week2/, each aimed at a rule someone will get wrong. A run test says what it expects in its file name, as in week 1: a mismatch_ or rejected_ prefix, or MATCH otherwise. Render tests start with a # render line. Check them against the oracle:

python tools/test.py --check-tests <your compiler repo>/tests/week2 --week 2

For a render test, --check-tests renders it with the oracle, compiles it with the same harness and checks the buffers. Good targets: two stores into one version (rejected), a load of an old version after the store (a swap), an offset from a loaded value with and without a mod mask, a wrapping mul in a render test, a cast of NaN or 3e9 to i32 and max on NaN and -0.0.

A build order that works

  1. Add f32

    Float literals in the lexer, the f32 dtype in the type checker and recip. In the interpreter, round to f32 after every op, and get the max, cmplt, cast and assert rules exactly right.

    Checkpoint: the f32_, cast_, max_ and literal_ run tests pass, and rejected_type_mix is REJECTED.

  2. Parse the new ops

    buffer and alloc take a size literal. buffer has slot= and an optional data list after the size, like buffer 3 [1 2 3]. shrink takes an offset operand and then a shape, [k] or []. Two allocs of the same size are different storage, so they must not hash cons into one node.

    Checkpoint: every file in tests/week2/run/ parses, or is REJECTED if its name says so.

  3. Type memory

    Give every node an addrspace. Memory can be an operand of shrink, load, store and after, and nothing else.

    Checkpoint: the "memory used as a value" tests, like rejected_mem_alu_operand, are REJECTED.

  4. Bounds

    Reuse your week 1 bounds rules. A loaded value's interval is the full i32 range.

    Checkpoint: the bounds_ tests MATCH and the rejected_bounds_ ones are REJECTED.

  5. Ordering checks

    Find each store's version by walking shrinks down to a buffer, alloc or after. Count stores per version and afters per store. Then try to schedule: if every load of V can't come before the store that overwrites V, the program is invalid.

    Checkpoint: the ordering tests, like rejected_two_stores_one_version, are REJECTED, and the swap tests MATCH.

  6. Interpret memory

    Versions are values: after produces a new array with one write applied. Copying is fine at this size.

    Checkpoint: every week 2 run test prints the outcome its name expects.

  7. Render ALU ops

    One function from op to C expression, with the safe spellings from lesson 4. Test it by rendering week 1 style arithmetic into a buffer.

    Checkpoint: render tests with only i32 math pass, including the wrapping ones and the floor div and mod.

  8. Render memory and the schedule

    Views become pointer plus offset, after prints nothing and loads of a version go before the store that overwrites it. Then f32: hex literals, NaN, infinities, the max helper and the saturating cast to i32.

    Checkpoint: every render test passes, bit for bit.

  9. Your 10 tests

    Write them, check them with --check-tests and use them to break your compiler before the suite does.

Check yourself

Your render output starts every kernel with a for loop that zeroes a scratch array. What happens?

Look at step 2 of how render tests are graded.

The grader rejects any for, while, do, or goto outside comments and strings. Zero an alloc with an initializer, = {0}, instead.

What outcome should your compiler print for this file?

%b  = buffer 2 dtype=i32 slot=0
%e  = shrink %b 0 []
%s1 = store %e 1
%s2 = store %e 2
%b1 = after %b %s1
%b2 = after %b1 %s2
%x  = load %b2
%t  = assert %x [2 0]

Which version does %s2 write into? Count the stores into that version.

REJECTED. Both stores write through %e, a view of %b, so version %b has two stores, which is unordered. On top of that, after %b1 %s2 names %b1 while %s2 writes into %b. Either problem alone makes it invalid.

The grader says "your kernel crashed (exit ...)" on a test that only does i32 add and mul. What's the most likely cause?

The grader compiles with -fsanitize-trap=undefined. Which of these is undefined behavior in C?

Signed overflow. A missing include would fail to compile, not crash, and a rounding difference would show up as a wrong value. Wrap through uint32_t.
