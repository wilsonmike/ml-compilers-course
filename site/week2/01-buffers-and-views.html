Floats, buffers and views

So far your compiler worked one number out of a few inputs, with whole numbers and no memory. Real programs work on big arrays of decimal numbers that sit in memory. This lesson adds both: decimal numbers (the f32 type), rows of numbers in memory (buffers) and windows onto part of a row (views).

Goal

Predict what an f32 op gives after rounding, and say exactly which elements of a buffer a view covers.

You'll use

Memory as a row of numbered boxes, and an array as a base plus an offset (lesson 0.1). Dtypes and i32 wraparound (lesson 1.2). Rewrite rules (lesson 1.3).

For the exercises: the struct module (lesson 0.7), and match on dataclasses with a function that calls itself (P.4 and P.5).

For the exercises: the Int32 module (lesson 0.6), and match on a variant type with a recursive function (O.3 and O.4).

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

In C, int a[6] holds 10, 20, 30, 40, 50 and 60, and p points at a[0] (lesson 0.1). What number is *(p + 2)?

p + 2 moves two elements along, and counting starts at 0.

*(p + 2) is a[2], the third element: 30. A start plus an offset is how every view in this lesson finds its numbers.

Your week 1 simplifier has the rule mul(x, 0) → 0 (lesson 1.3). Is it safe for every i32 x?

Is there any whole number that gives something other than 0 when you multiply it by 0?

It is safe for every i32. Later on this page you test it on decimal numbers, and it does not survive.

A sum with a surprising answer

Week 1 had two dtypes: i32 for whole numbers and bool. Week 2 adds f32, a 32-bit float, which is the type computers use for numbers with a decimal point. You write one with a . in it, so 1.0 is an f32 and 1 is an i32.

%s = add 16777216.0 1.0

Guess first. What is %s?

An f32 has only 32 bits, so it cannot hold every number. Something has to give.

The 1 disappears. An f32 cannot hold 16777217, so the answer moves to a nearby number that it can hold.

An f32 has 32 bits, so it can hold about four billion different numbers and nothing in between. Past 16777216, which is 224, it holds only every second whole number. A dashed box is a number f32 cannot hold:

So every f32 op works in two moves: compute the exact answer, then round it to the nearest number f32 can hold. Here is the sum again:

  1. Compute exactly. 16777216 + 1 is 16777217.
  2. Find the neighbors. The nearest numbers f32 can hold are 16777216 and 16777218.
  3. Pick the nearest. Both are 1 away, so it is a tie. A tie goes to the neighbor whose last stored bit is 0, which here is 16777216. This rule is called ties to even, like rounding 2.5 to 2 and 3.5 to 4.

Rounding happens after each op, so adding 1.0 again gives 16777216.0 again. But add 16777216.0 2.0 is 16777218.0 exactly: in f32, adding 1 twice is not adding 2. The slow version is the floats half of H.4.

Round after every op in your interpreter

Python's floatOCaml's float is a 64-bit double, which holds many more digits than an f32. So compute each op in doubles, then round the result to f32 after each op, not once at the end.

Literals are rounded the same way, so the constant 0.1 is the nearest f32, not exactly 0.1.

Round to f32

Write f32, which rounds a double x to the nearest f32 (ties to even, and a result too big for any f32 becomes inf, infinity, which the next section covers), and add32, which adds two f32 values a and b the way your interpreter must: compute, then round.

The Int32 module can move a float through its 32-bit bit pattern. Look for bits_of_float.

The struct module can move a float through its 32-bit encoding, as in lesson 0.7. Remember what it does on overflow.

Dividing, and three values integers do not have

add, mul, max, cmplt and where take f32 operands too, and so do stack, index and cast. xor, shl, div and mod stay integer only, so floats have no division op. They get one new op: recip a is 1 / a, for an f32 only. To divide a by b, multiply a by recip b.

In week 1, div x 0 was defined as -1 so that nothing fails while running. Floats keep that promise with a value of their own: recip 0.0 is infinity, written inf.

f32 has three special values that show up in the tests all the time:

assert treats 0.0 and -0.0 as equal, and two NaNs as equal, so a test can say "this should be NaN". The reference section has the full rules.

Divide without a divide op

This program should compute a / b on two f32 params, but the starter multiplies them. Repair it with recip, in at most 2 ops. The tests divide by 0.0, -0.0 and inf, and none of those is an error.

Whole numbers and decimals do not mix

%x is an f32 param. A teammate wants to add one to it:

%x = param [] slot=0 dtype=f32 addrspace=ALU
%y = add %x 1

What does the compiler do with this program?

Look at the dtype of each operand. Did week 1 ever let an op take two different dtypes?

1 is an i32 and %x is an f32. An op with two inputs needs both to have the same dtype, and .uir never converts for you.

C would quietly convert the 1. Here a conversion has to be its own visible node. Write add %x 1.0, or convert one side with cast, the only way between f32 and the other dtypes (the reference section has examples):

  • i32 to f32 rounds to the nearest f32, ties to even.
  • f32 to i32 drops the fraction, which is called truncating toward zero: cast 3.9 dtype=i32 is 3. It also saturates: a value past either end of the i32 range stops at that end, and NaN becomes 0.
  • f32 to bool means "not zero", so NaN gives true.

Rewrite rules that break on floats

In the warm up, mul(x, 0) → 0 was safe for every i32. Now try it on an f32 x.

x is nan. What is mul x 0.0?

Look at the nan row of the table of special values.

Arithmetic on a NaN gives NaN. So a simplifier that rewrites mul(x, 0.0) to 0.0 changes the program's answer. The rule is wrong for f32.

Every f32 op rounds, and inf, nan and -0.0 break identities that hold for every i32. The simplify grader compares f32 results bit for bit, so there 0.0 and -0.0 differ (any NaN still matches any NaN). Of the week 1 rules, mul(x, 1) → x survives. mul(x, 0) → 0, add(x, 0) → x and folding two constant adds into one do not. The reference section says why.

The f32 zero trap

%out = (x * 1.0) * 0.0, on an f32 x. Rewrite it with at most one op, computing the same f32 for every x, bit for bit. The tests feed in nan, inf, -inf and negative numbers, and the oracle prints -0.0 as -0.0.

Many numbers need a place to live

That covers floats. Now memory. Here is a job week 1 cannot do: a photo has a million pixel values, and a program should make each one brighter.

With only week 1 tools, where could the million results go?

What does a week 1 program give you when it ends?

Params carry numbers in, and one value comes out. Nothing in week 1 can hold a million numbers.

A buffer is a row of numbered boxes in memory. Each box, called an element, holds one number. A buffer exists before your program runs and after it ends, so it is how big data gets in and how results get out.

%b = buffer 6 [10 20 30 40 50 60] dtype=i32 slot=0
%w = buffer 3 dtype=f32 slot=1
%b: six elements, numbered from 0

Read a buffer line in three parts:

  1. The size. The first operand, an integer literal. %b has 6 elements, numbered 0 to 5.
  2. The starting values. The optional list gives exactly that many. Without it, as in %w, the buffer starts as zeros.
  3. The attributes. dtype is the element type. slot is the buffer's position among the arguments of the C function your compiler writes in lesson 2.4. Two buffers can't share a slot.

An alloc is the same kind of row, but it's scratch space that belongs to the program, like a local float a[3]; in C. It always starts as zeros, and nothing outside sees it.

%a = alloc 3 dtype=f32

Memory is a place, not a number

A teammate wants to compute with those numbers:

%x = add %b 1

What do you think the compiler does?

add takes two numbers. Is a row of elements a number?

%b is not a number. It is the place where numbers are kept. You have to read the numbers out first.

Every week 1 value lived in the ALU address space, the addrspace=ALU on every param: numbers your program computes with. Buffers and allocs live in GLOBAL: they're places, not numbers. You can't add a buffer to 1, compare it, stack it or pass it to a call. You have to load it first, which reads the place and gives you a value:

%r = load %b
%x = index %r 3
%z = add %x 1
  1. Load. %r is the rank-1 value [10 20 30 40 50 60], the kind of value stack builds. A load takes the dtype and shape of what it reads.
  2. Pick. index %r 3 is 40.
  3. Compute. %z is 41. Nothing in %b changed.

A call body can't touch memory either: load first, then pass the value as an argument.

A window onto part of a buffer

You often want a few elements of a big buffer, and the next lesson's writes need a way to say which elements. shrink makes a view: a window that starts some number of elements in and covers a fixed number of them.

%v = shrink %b 2 [3]

Read it as "start 2 elements into %b and cover 3 elements".

%b holds 10, 20, 30, 40, 50 and 60. Which numbers does load %v give?

Skip the first 2 elements, then take 3.

The window covers elements 2, 3 and 4, so the load gives the rank-1 value [30 40 50].

Step through the picture: the window moves over the same six elements. Nothing is copied. A view is just a buffer plus an offset plus a length, like the base plus offset of lesson 0.1.

  • The offset is an i32 operand. It can be a literal or a computed value, and lesson 2.3 shows how computed offsets are checked.
  • The shape comes last. [k] gives a rank-1 window of k elements. [] gives a single element, a rank-0 view, which is what you load and store scalars through.

A view is memory too, so it lives in GLOBAL. A whole buffer counts as a view of all of itself, which is why load %b worked.

The window has to fit

Same buffer, six elements. Someone asks for three elements starting at element 4:

%bad = shrink %b 4 [3]

What do you think happens?

In lesson 0.1, C read whatever was at the address. This compiler promises more than C does.

The window would need an element 6, and there is none. C would read past the end without a word. Your compiler has to refuse the program.

A view of k elements at offset off, cut from a parent of n elements, fits when both of these hold:

off ≥ 0     and     off + k ≤ n

For %bad, 4 + 3 is 7, which is more than 6. A [] view counts as k = 1. Every view must pass before the program runs, because the C your compiler writes checks nothing.

Does the view fit?

The starter gets the rule slightly wrong. Repair fits(n, off, k) in C: return 1 if a view of k elements starting at off fits inside a parent of n elements, else 0. n and k are at least 1, but off can be any int, including INT_MAX and INT_MIN.

Read through a window

Now write the check and the window together. data is a buffer written as a list. Write window data off k: return a list of the k elements that a view starting off elements in covers. If the window does not fit inside data, raise Invalid_argument "out of bounds".

A view of a view

A view can be shrunk again. The new offset counts from the start of the view, not from the start of the buffer.

%b = buffer 6 [10 20 30 40 50 60] dtype=i32 slot=0
%v = shrink %b 2 [3]
%w = shrink %v 2 []
%x = load %w

What does %x hold?

%v covers 30, 40 and 50. Number those three from 0.

Element 2 of %v is 50. Counted from the buffer, that is element 2 + 2 = 4.

Two rules cover every chain of views:

  1. Offsets add up. To find where a view starts in the buffer, add its offset to its parent's start.
  2. Fit inside the parent. The new window has to fit inside the view it was cut from, not just inside the buffer. shrink %v 3 [] is invalid, even though %b has an element 5: %v only has elements 0 to 2.

Resolve a view

Here views are a small type with three cases: a Buffer n, a Shrink (parent, off, k)Buffer(n), a Shrink(parent, off, k) for a [k] view, or an Elem (parent, off)Elem(parent, off) for a [] view. Write resolve vresolve(v), returning (start, len): where the view starts inside its buffer, and how many elements it covers.

Raise Invalid_argument "out of bounds"the "out of bounds" error the starter code describes if any step in the chain doesn't fit inside its parent: a negative offset, or a window that runs past the end of the parent.

Everything week 2 changes from week 1, in one list, for when you update your parser and checker

Everything from week 1 still holds, except for these changes:

  • A new dtype, f32, with float literals and one new op, recip.
  • Rank-1 params and asserts. A param may have a shape like [3], so a call can pass and return vectors, and an assert's left side may be a vector, compared with a stack literal like [1 2 3].
  • Lists are operands. An attribute is still one token with no spaces, as in week 1. So a list, like a view's shape or a buffer's starting data, is written as a bracket operand, last among the operands: shrink %b 2 [3].
  • No memory in a call body. A load inside a body is rejected even when no buffer is passed in. A whole-vector assert on a load works: with %r = load %b on the six-element buffer of this page, %t = assert %r [10 20 30 40 50 60] is a MATCH.
  • No budgets. The week 1 limits (4096 bytes, 100 nodes, 300 edges, cost 1,000,000) are lifted. Week 2 programs are bigger, and nothing is OVERBUDGET.

A vector param in action. In week 2 ALU ops still take scalars, so the body indexes the elements it needs (elementwise vector ALU ops arrive in week 4):

Every way to write an f32 literal, for when you write the tokenizer

A literal with a . or an exponent is an f32. Without either, it's an i32, so 1.0 and 1 are different constants with different dtypes.

1., .5, -.5digits on only one side of the point are fine: 1.0, 0.5 and -0.5

1e39, 1e-50too big rounds to inf, too small rounds to 0.0 (-0.0 for a negative literal)

The exact rule: read the literal as a 64-bit double, then round that to the nearest f32, ties to even. 16777217.0 becomes 16777216.0, because f32 can't hold 16777217.

A test for the rounding: in doubles, 0.1 + 0.2 == 0.3 is famously false. In f32 the rounded sum lands exactly on the rounded 0.3, so %s = add 0.1 0.2 followed by %t = assert %s 0.3 is a MATCH. An interpreter that forgets to round says MISMATCH.

How max, cmplt, assert and cast treat nan, inf and -0.0, for when you write the interpreter
  • max with a NaN operand is NaN, whichever side it's on.
  • max -0.0 0.0 and max 0.0 -0.0 are both +0.0. Python's built-in max gets this wrong: max(-0.0, 0.0) returns -0.0, because it keeps the first of two equal values.OCaml's Stdlib.max gets this wrong: max (-0.0) 0.0 returns -0.0, because it keeps the first of two equal values. Float.max gets both zeros and NaN right.
  • cmplt with a NaN on either side is false. So is cmplt -0.0 0.0: the two zeros are equal.

assert compares f32 by value, with a rule for NaN:

  • 0.0 equals -0.0, so assert -0.0 0.0 is a MATCH. To check the sign of a zero, assert on its recip.
  • Two NaNs count as equal, so assert nan nan is a MATCH. In IEEE, nan == nan is false. The course picks this rule so a test can say "this should be NaN".

An example of each cast rule:

  • i32 to f32 rounds: cast 16777217 dtype=f32 is 16777216.0.
  • f32 to i32 truncates toward zero: cast 3.9 dtype=i32 is 3 and cast -3.9 dtype=i32 is -3.
  • f32 to i32 saturates at or past the ends of the i32 range: cast 3000000000.0 dtype=i32 is 2147483647, and cast -inf dtype=i32 is -2147483648. NaN becomes 0.
  • f32 to bool is "not zero": 0.0 and -0.0 give false, and NaN gives true. bool to f32 gives 0.0 or 1.0.

f32 is IEEE-754 single precision, with 24 bits of precision. That is why whole numbers start to go missing at 224, which is 16777216.

Printing f32 constants, for when your simplify writes a program back out

Printing an f32 constant in your simplify output needs care. Print enough digits to round-trip (%.9g is enough for any f32), and always include a . or an e: %.9g prints 3.0 as 3, which reads back as an i32. Print the specials as inf, -inf and nan.

Check yourself

Is %t = assert nan nan a MATCH?

IEEE says NaN never equals NaN, but the course defines assert equality on purpose. What would a test need in order to say "this should be NaN"?

Assert equality is defined so a test can check for NaN. Inside the program, cmplt still follows IEEE: any NaN gives false.

What is cast -3.9 dtype=i32?

Casting f32 to i32 truncates toward zero. Which integer is closer to zero, -3 or -4?

Truncate toward zero, not floor. Unlike div, which floors, a cast just drops the fraction.

What is cast 3000000000.0 dtype=i32?

3 billion is past the largest i32. f32 to i32 doesn't wrap and doesn't fail.

It saturates to INT_MAX, 2147483647. A value past the bottom of the range gives INT_MIN, and NaN gives 0.

Which rewrite is valid for every f32 x, bit for bit?

Try each rule on the awkward floats: nan, inf and -0.0.

Only multiplying by one is exact for every float. nan × 0.0 is nan, regrouping changes rounding, and -0.0 + 0.0 is +0.0.

What does %x hold?

Offsets add up: where does %v start, and how far into %v is %w?

%v starts at element 2, and %w is one further in: element 3 of %b, which holds 40.

What does load %a give for %a = alloc 3 dtype=f32, before anything is stored?

The spec says what an alloc starts as. And loading a whole 3-element alloc keeps its shape.

Allocs start as zeros, and loading all three elements gives a rank-1 value. In C, a local array starts as garbage, so your renderer will have to initialize it.

Why is shrink %v 3 [] invalid when %v = shrink %b 2 [3] and %b has six elements?

Check the new window against the view it was cut from.

A view must fit inside its parent. %v has three elements, so offset 3 is past its end, even though it would land on element 5 of %b, which does exist.
