Week 2 · Lesson 1

Floats, buffers and views

Week 1 programs computed with i32 and bool, from constants and call arguments. Real kernels compute with floats, and they read and write memory that lives outside the program: model weights, activations, the output you hand back. This lesson adds the f32 dtype first, then starts on memory with the two things you can name: buffers and windows into them.

What's new this week

Everything from week 1 still holds, except for these changes:

  • A new dtype, f32, with float literals and one new op, recip. The first half of this lesson covers it.
  • Rank-1 params and asserts. A param may have a shape like [3], so a call can pass and return vectors, and an assert's left side may be a vector, compared with a stack literal like [1 2 3].
  • Lists are operands. An attribute is still one token with no spaces, as in week 1. So a list, like a view's shape or a buffer's starting data, is written as a bracket operand, last among the operands: shrink %b 2 [3].
  • No budgets. The week 1 limits (4096 bytes, 100 nodes, 300 edges, cost 1,000,000) are lifted. Week 2 programs are bigger, and nothing is OVERBUDGET.

A vector param in action. In week 2 ALU ops still take scalars, so the body indexes the elements it needs (elementwise vector ALU ops arrive in week 4):

%x = param [3] slot=0 dtype=i32 addrspace=ALU
%a = index %x 0
%b = index %x 2
%y = add %a %b
%r = call %y [10 20 30]
%t = assert %r 40

The official week 2 reference isn't out yet, so the week 2 rules in spec/uir-week2.md are the course's own reading. They'll move to the official format when it's published.

f32 literals

A literal with a . or an exponent is an f32. Without either, it's an i32, so 1.0 and 1 are different constants with different dtypes.

1., .5, -.5digits on only one side of the point are fine: 1.0, 0.5 and -0.5

The exact rule: read the literal as a 64-bit double, then round that to the nearest f32, ties to even. 16777217.0 becomes 16777216.0, because f32 can't hold 16777217.

No implicit conversion

add 1.5 1 is REJECTED, not 2.5. 1 is an i32 and 1.5 is an f32, and binary ops need matching dtypes. Write add 1.5 1.0, or cast one side. The same goes for a param: with %x an f32 param, add %x 1 is rejected. C would quietly convert for you. Here, the conversion has to be its own visible node.

Rounding after every step

An f32 is IEEE-754 single precision, with 24 bits of precision. After every op, the exact result is rounded to the nearest representable f32. A tie goes to the even neighbor, like rounding 2.5 to 2 and 3.5 to 4. If your language computes in 64-bit doubles, round back to 32 bits after each op, not once at the end.

add, mul, max, cmplt and where take f32 operands too, and stack, index and cast work on f32 values. Four ops stay integer only: xor, shl, div and mod. There's no float division op. Instead there's recip a, which is 1 / a for an f32 and rejects anything else.

f32 also has special values that integers don't. They show up in the tests all the time:

nanmul inf 0.0"Not a number". Arithmetic on a NaN gives NaN.
-0.0mul -3.0 0.0It equals 0.0, but recip tells them apart: recip -0.0 is -inf, recip 0.0 is inf.
16777216 + 1

2²⁴ = 16777216 is where f32 runs out of integers. add 16777216.0 1.0 is exactly halfway between 16777216 and 16777218, and it rounds to even, giving 16777216.0. The 1 just disappears.

0.1 + 0.2

In 64-bit doubles, 0.1 + 0.2 == 0.3 is famously false. In f32 it happens to be true: %s = add 0.1 0.2 then %t = assert %s 0.3 is a MATCH. If your interpreter uses doubles and forgets to round, it gets this wrong.

Round to f32

OCaml's floatPython's float is a 64-bit double. Write f32, which rounds x to the nearest f32 (ties to even, overflow to inf), and add32, which adds two f32 values a and b the way your interpreter must: compute, then round.

The Int32 module can move a float through its 32-bit bit pattern. Look for bits_of_float.

The struct module can move a float through its 32-bit encoding, as in lesson 0.7. Remember what it does on overflow.

max, cmplt and assert on floats

  • max with a NaN operand is NaN, whichever side it's on.
  • max -0.0 0.0 and max 0.0 -0.0 are both +0.0. Python's built-in max gets this wrong: max(-0.0, 0.0) returns -0.0, because it keeps the first of two equal values.OCaml's Stdlib.max gets this wrong: max (-0.0) 0.0 returns -0.0, because it keeps the first of two equal values. Float.max gets both zeros and NaN right.
  • cmplt with a NaN on either side is false. So is cmplt -0.0 0.0: the two zeros are equal.

assert compares f32 by value, with a rule for NaN:

  • 0.0 equals -0.0, so assert -0.0 0.0 is a MATCH. To check the sign of a zero, assert on its recip.
  • Two NaNs count as equal, so assert nan nan is a MATCH. In IEEE, nan == nan is false. The course picks this rule so a test can say "this should be NaN".

Casts

cast is the only way between f32 and the other dtypes:

  • i32 to f32 rounds to the nearest f32, ties to even. cast 16777217 dtype=f32 is 16777216.0.
  • f32 to i32 truncates toward zero: cast 3.9 dtype=i32 is 3 and cast -3.9 dtype=i32 is -3.
  • f32 to i32 also saturates. Anything at or past the ends of the i32 range clamps: cast 3000000000.0 dtype=i32 is 2147483647, and cast -inf dtype=i32 is -2147483648. NaN becomes 0. Like everything else in the course, a cast never fails at run time.
  • f32 to bool means "not zero": 0.0 and -0.0 give false, and NaN gives true. bool to f32 gives 0.0 or 1.0.

Simplifying floats

i32 arithmetic is arithmetic mod 232, so identities built from + and × hold even when values wrap. f32 has none of that. Every op rounds, and inf, nan and -0.0 break identities you'd expect to hold. The simplify grader compares f32 results bit for bit, so there 0.0 and -0.0 differ (any NaN still matches any NaN).

rulei32f32why
mul(x, 1) → xvalidvalidMultiplying by one is exact, even for nan, inf and -0.0.
mul(x, 0) → 0validwrongnan × 0.0 and inf × 0.0 are nan, and -3.0 × 0.0 is -0.0.
add(x, 0) → xvalidwrong-0.0 + 0.0 = +0.0, so x changes from -0.0 to +0.0. add(x, -0.0) → x is valid: adding -0.0 changes nothing.
add(add(x, c1), c2) → add(x, c1 + c2)validwrongf32 rounds after each add, so regrouping changes the result.

Printing an f32 constant in your simplify output needs care too. Print enough digits to round-trip (%.9g is enough for any f32), and always include a . or an e: %.9g prints 3.0 as 3, which reads back as an i32. Print the specials as inf, -inf and nan.

The f32 zero trap

You are the rewrite engine: %out = (x * 1.0) * 0.0, on an f32 x. Rewrite it with at most one op, computing the same f32 for every x, bit for bit. The tests feed in nan, inf, -inf and negative numbers, and the oracle (the course's reference compiler, which the grader compares you against) prints -0.0 as -0.0.

Memory lives outside the program

That covers floats. The rest of this lesson is about memory. A buffer is a block of n elements that exists before your program runs and after it ends. The program can read it and write it. When your compiler renders C, each buffer becomes one pointer argument of the kernel.

%b = buffer 6 [10 20 30 40 50 60] dtype=i32 slot=0
%w = buffer 3 dtype=f32 slot=1
  • The first operand is the size, an integer literal.
  • dtype is the element type, and slot is the buffer's position in the kernel's argument list. Two buffers can't share a slot.
  • The optional list after the size gives exactly n starting values. Without it the buffer starts as zeros. In real use the data comes from outside, but in tests it's written into the file.

An alloc is the same kind of thing, but it's scratch space that belongs to the program, like a local float a[3]; in C. It always starts as zeros, and nothing outside sees it.

%a = alloc 3 dtype=f32

A view is a window

You rarely want a whole buffer. shrink makes a view: a window that starts some number of elements in and covers a fixed number of them. The offset is an i32 operand. It can be a literal or a computed value, and lesson 3 shows how computed offsets are checked. Nothing is copied. A view is just a buffer plus an offset plus a length.

%v = shrink %b 2 [3]     # elements 2, 3, 4
%e = shrink %b 5 []      # just element 5

The last operand is the view's shape. [k] gives a rank-1 window of k elements. [] gives a single element, a rank-0 view, which is what you load and store scalars through. Step through the picture: the window slides over the same six cells.

Views of views

A view can be shrunk again. The offsets add up, and the new window has to fit inside the view it was cut from, not just inside the buffer.

%v = shrink %b 2 [3]     # elements 2..4 of %b
%w = shrink %v 1 []      # element 1 of %v, which is element 3 of %b

shrink %v 3 [] would be invalid, even though %b has an element 5: %v only has three elements, numbered 0 to 2.

Resolve a view

Here views are a small type with three cases: a Buffer n, a Shrink (parent, off, k)Buffer(n), a Shrink(parent, off, k) for a [k] view, or an Elem (parent, off)Elem(parent, off) for a [] view. Write resolve vresolve(v), returning (start, len): where the view starts inside its buffer, and how many elements it covers.

Raise Invalid_argument "out of bounds"the "out of bounds" error the starter code describes if any step in the chain doesn't fit inside its parent: a negative offset, or a window that runs past the end of the parent.

Memory is not a value

Every week 1 value lived in the ALU address space, the addrspace=ALU on every param: numbers your program computes with. Buffers, allocs and views live in GLOBAL: they're places, not numbers. (GLOBAL here just means "memory", not a C global variable.) You can't add a buffer to 1, compare it, stack it or pass it to a call. You have to load it first. A call body can't touch memory either: a load inside a body is rejected even when no buffer is passed in. Load first, then pass the value as an argument.

%x = add %b 1          # invalid: memory can't be an operand of add
%e = shrink %b 0 []
%y = load %e           # 10, an i32 value
%z = add %y 1          # 11

A load takes the view's dtype and shape. Loading a [] view gives a scalar. Loading a [3] view, or a whole buffer, gives a rank-1 value, the same kind of value stack builds, so you can compare it with assert or pick from it with index.

%r = load %v           # the rank-1 value [30 40 50]
%t = assert %r [30 40 50]

With the buffer above, that file is a MATCH. A week 2 assert may compare a vector, as long as the expected side is a stack of literals.

Why the split matters

Keeping places and values apart is what lets the compiler reason about memory later. A value can be copied, folded and shared freely. A place can't: reading it twice might give two answers if something wrote in between. The next lesson is about exactly that.

Does the view fit?

Write fits(n, off, k) in C: return 1 if a view of k elements starting at off fits inside a parent of n elements, else 0. n and k are at least 1, but off can be any int, including INT_MAX and INT_MIN.

Check yourself

What does the compiler print for this file?

%a = add 1.5 1
%t = assert %a 2.5

Look at the dtypes of the two literals. Does .uir ever convert between them for you?

1 is an i32 literal and 1.5 is f32. There's no implicit conversion, so add rejects mismatched dtypes during validation, before anything runs.

Is this a MATCH?

%s = add 16777216.0 1.0
%t = assert %s 16777216.0

f32 has 24 bits of precision, and 16777216 is 2 to the 24th. Can f32 represent 16777217?

When a value sits exactly halfway between two f32 numbers, the tie goes to the one whose last bit is even.

16777217 isn't representable in f32. It's a tie between 16777216 and 16777218, and ties round to even.

Is %t = assert nan nan a MATCH?

IEEE says NaN never equals NaN, but the course defines assert equality on purpose. Check the section on max, cmplt and assert above.

Assert equality is defined so a test can check for NaN. Inside the program, cmplt still follows IEEE: any NaN gives false.

What is cast -3.9 dtype=i32?

Casting f32 to i32 truncates toward zero. Which integer is closer to zero, -3 or -4?

Truncate toward zero, not floor. Unlike div, which floors, a cast just drops the fraction.

What is cast 3000000000.0 dtype=i32?

3 billion is past the largest i32. f32 to i32 doesn't wrap and doesn't fail.

It saturates to INT_MAX, 2147483647. A value past the bottom of the range gives INT_MIN, and NaN gives 0.

Which rewrite is valid for every f32 x, bit for bit?

Try each rule on the awkward floats: nan, inf and -0.0.

Only multiplying by one is exact for every float. nan × 0.0 is nan, regrouping changes rounding, and -0.0 + 0.0 is +0.0.

Which element indices of %b does shrink %b 2 [3] cover?

It starts at the offset and covers k elements.

Offset 2, three elements: indices 2, 3, and 4.

What does %x hold?

%b = buffer 6 [10 20 30 40 50 60] dtype=i32 slot=0
%v = shrink %b 2 [3]
%w = shrink %v 1 []
%x = load %w

Offsets add up: where does %v start, and how far into %v is %w?

%v starts at element 2, and %w is one further in: element 3 of %b, which holds 40.

On %b = buffer 6 ..., which view is invalid?

A window of k elements starting at off ends at index off + k - 1. The last valid index is 5.

Offset 4 with three elements would cover indices 4, 5, and 6, and there is no index 6. The others end exactly at index 5 or earlier.

What happens with %x = add %b 1, where %b is a buffer?

Is a buffer a value or a place?

A buffer is memory, not a value. ALU ops only take values, so you have to load first. The oracle gives the reason: "memory can't be an operand here (load it first)".

What does load %a give for %a = alloc 3 dtype=f32, before anything is stored?

The spec says what an alloc starts as. And loading a whole 3-element alloc keeps its shape.

Allocs start as zeros, and loading all three elements gives a rank-1 value. In C, a local array starts as garbage, so your renderer will have to initialize it.

Why is shrink %v 3 [] invalid when %v = shrink %b 2 [3] and %b has six elements?

Check the new window against the view it was cut from.

A view must fit inside its parent. %v has three elements, so offset 3 is past its end, even though it would land on element 5 of %b, which does exist.
