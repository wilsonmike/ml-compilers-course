Week 2 · Lesson 2

Load, store, after

By the end of this lesson you can write a program that changes memory and say exactly which reads see the change. Your compiler keeps a program as a graph, and a graph has no "first" and "next". Memory does, so .uir needs a way to put the order into the graph itself.

Goal

Write programs that store into a buffer and load from the right version of it, and tell when a program's stores are fully ordered.

You'll use

Buffers, shrink and load from lesson 2.1, and the idea that a program is a graph where each node points only at its sources, from lesson 1.1.

One exercise uses a loop over a list of tuples. If that is new, do P.3 first.

One exercise uses lists of tuples and the List functions. If those are new, do O.3 first.

Warm up

Two questions from earlier lessons, from memory. Pulling an idea back out of your head is what makes it stay.

shrink makes a window onto part of a buffer (lesson 2.1). What does %x hold?

%b = buffer 4 [10 20 30 40] dtype=i32 slot=0
%e = shrink %b 1 []
%x = load %e

Elements are numbered from 0. Which element does offset 1 point at?

%e is a window onto element 1 alone, and element 1 holds 20.

Two week 1 files hold the same three lines. In the second file the first two lines trade places. Does your compiler build a different graph?

%a   = add 2 3
%c   = mul 4 5
%out = add %a %c

A node records its op and its sources. Does it record which line it was on?

A node only points at its sources. Neither %a nor %c uses the other, so nothing in the graph says which one comes first. For arithmetic that never matters. For memory it does, and that is this lesson.

The problem: read first or write first?

Lesson 2.1 gave you load, which reads elements. Its partner is store: store v x writes the value x into the view v. Here are both, aimed at the same element:

%b = buffer 4 [10 20 30 40] dtype=i32 slot=0
%e = shrink %b 1 []
%s = store %e 99
%x = load %e

Pretend the lines run top to bottom, the way Python or C would run them. What does %x hold?

The store runs first and puts 99 in element 1. Then the load reads element 1.

The write happens first, so the read sees 99.

Now trade the last two lines, so the load comes first. Step through both orders.

Your compiler does not keep the lines. It keeps the graph. What does the graph say about these two nodes?

Look at the operands of each line. Does %x appear in the store, or %s in the load?

The two files build the same graph, and that one graph has two possible answers: 99 and 20. A program with two answers has no meaning. So the program itself has to say which comes first, in a way the graph can hold. (As written, this program is not valid .uir. You'll see why further on.)

A store makes a new version

The fix is to stop thinking of one row of elements that changes. Think of versions: the row as it was before a write, and the row as it is once the write has happened. A store on its own is only an event. Its result is void, which means "no value", so no other line can compute with it. To name the memory once the write has happened, you use after:

%b  = buffer 4 [10 20 30 40] dtype=i32 slot=0
%e  = shrink %b 1 []
%s  = store %e 99
%b1 = after %b %s          # "%b, once %s has happened"
  1. Start with version 0. %b is the row as it began: 10, 20, 30, 40.
  2. Describe the write. %s is the event "99 goes into element 1 of %b".
  3. Name the result. %b1 = after %b %s is version 1: the same row with that one write applied.

%b itself never changes. It is still the name of version 0. Step through a program with two stores and watch the same row at version 0, 1 and 2:

Versions cost no memory. In the C your compiler prints in lesson 2.4, all three versions are one array, written in place. Versions are only how the graph tells time.

In the figure's last step, what does element 2 hold in version 2 (%b2)?

Neither store wrote to element 2. A new version keeps every element that its store did not touch.

A version differs from the one before it only in the elements its store wrote. Element 2 holds 30 in all three versions.

A load says which version it reads

Now the puzzle has an answer. A view is cut from one version, and a load through that view reads that version. %e was cut from %b, so load %e reads version 0, no matter where the line sits in the file. To read the 99, cut a view from %b1:

%x  = load %e
%e1 = shrink %b1 1 []
%y  = load %e1
  1. Find the version. %e is a view of %b, version 0. %e1 is a view of %b1, version 1.
  2. Read that row. Element 1 of version 0 holds 20, so %x is 20. Element 1 of version 1 holds 99, so %y is 99.

The order is now inside the graph. %y points at %e1, which points at %b1, which points at the store. Follow the arrows and the store has to come before that load. Shuffle the lines however you like and the graph stays the same, with one answer.

What does %x hold?

%b  = buffer 2 [5 6] dtype=i32 slot=0
%e  = shrink %b 0 []
%s  = store %e 7
%b1 = after %b %s
%f  = shrink %b1 1 []
%x  = load %f

Which version is %f cut from, and which element? Did the store write that element?

%f is element 1 of version 1. The store only wrote element 0, so element 1 still holds 6.

Running total in place

Slot 0 is a buffer of three i32s. In place, set b[1] = b[0] + b[1], then b[2] = b[1] + b[2] using the new b[1]. The starter has one bug about which version it reads.

Chain the writes

A program with several writes makes a chain of versions. Each store goes into a view of the latest version, and each after names the next one:

%f  = shrink %b1 3 []
%s2 = store %f 7
%b2 = after %b1 %s2

Loads can still reach back. A load through a view of %b reads the starting row even when %b2 exists. That is how a swap works: read both old values first, then write them.

The outputs of a program are the final version of each buffer, the one no after builds on. That is what a caller sees when the program is done, and what the next two exercises are graded on.

Swap two elements in place

Slot 0 is a buffer of four i32s. Swap b[0] and b[1], and leave the other two alone. The starter does half the job.

The grader sets the buffer's data for each test and checks its final contents.

Sum, then clear

Now write one from scratch. Slot 0 is a buffer of three i32s. Set b[2] to b[0] + b[1], using the starting values, and set b[0] to 0. Leave b[1] alone. So [1 2 3] ends as [0 2 3]. Only the buffer line is given.

Two writes with no order

Versions fix the read and write puzzle. The same puzzle comes back with two writes. Both of these stores go into version %b, into the same element:

%b  = buffer 2 dtype=i32 slot=0
%e  = shrink %b 0 []
%s1 = store %e 1
%s2 = store %e 2
%b1 = after %b %s1
%b2 = after %b %s2

What does element 0 hold when this program is done?

Line order is not part of the graph. Does either store, or either after, point at the other?

Whichever store runs last wins, and the graph does not say which that is. There are also two "next versions" of %b, and neither builds on the other, so the program has no final version.

So the language forbids it: a version may be written by at most one store. It does not matter that two stores might touch different elements. To write twice, chain the stores, as you did in the swap.

What "fully ordered" means

The syllabus says loads and stores "must be fully ordered for programs to be valid". That means the graph itself settles which memory operation comes first, every time the order could change a result. Your compiler will print C, where statements run one at a time on one real array, so every order it may pick has to give the same result. Three rules make sure of it:

  1. One store per version. At most one store may write into any given version, through any of its views.
  2. Every store is sequenced. Each store is the s of exactly one after, and that after names the version the store writes into.
  3. Old versions are read before they're overwritten. A load of version V has to be able to run before the store that makes V's successor.

A program that breaks any of them is REJECTED before anything runs.

A store with no after

It's tempting to write store and move on, the way you would in C. That is what the puzzle program at the start of this lesson did. In a graph, a store that no after names is unreachable from the outputs, so nothing could ever observe it. The oracle rejects it: "a store that no after sequences has no effect".

%s1 stores into a view of %b, and %b1 = after %b %s1. Which second store keeps the program valid?

Rule 1 rules out one option. Rule 2 says which version the after must name.

A second store into %b breaks rule 1. A store into %b1 is fine, but its after must name %b1, the version it writes into.

Check rules 1 and 2

Your lab compiler has to check these rules, so practice on a small model. A store is a pair ("s", "b"): the store named s writes into version b. An after is a triple ("b1", "b", "s"), which stands for %b1 = after %b %s.

ordered returns true when rules 1 and 2 both hold. Rule 1 is written. Add rule 2: every store is named by exactly one after, and that after names the version the store writes into.

The old-version trap

Rule 3 is about what happens in C. There, every version of %b is the same array, and a store wipes out the old value for good.

One line loads element 0 of version %b. Another stores into element 0 to make %b1. In the C your compiler prints, where must the load go?

What is in the array's element 0 right after the store has run?

Before. Once the store runs, the old value is gone. So every load of a version must run before the store that overwrites it.

It goes wrong when a load of the old version needs a value that only exists in the new one. Here the index into the old buffer is read from the new buffer. The mod only keeps the index provably in range (lesson 2.3 explains why), so ignore it for now:

%b  = buffer 2 [1 0] dtype=i32 slot=0
%e0 = shrink %b 0 []
%s  = store %e0 0
%b1 = after %b %s
%n0 = shrink %b1 0 []
%i  = load %n0              # reads the NEW b[0]
%k  = mod %i 2
%v  = shrink %b %k []       # ...to index the OLD %b
%y  = load %v
%t  = assert %y 1

The load of old %b must run before the store. But it needs %i, which needs %b1, which needs the store. Step through the chain of "must come before":

No order satisfies every arrow, so the program is REJECTED: "a load of an old buffer version is needed after that version was overwritten". A compiler could save a copy of the old buffer, but that is a hidden allocation, and the course's rule is that the program says what memory it uses.

Every rule for store and after, for when you write the lab
  • store v x: v is a view or a whole buffer, and x is a value of the same dtype and shape. A [] view takes a scalar. A [k] view, or a whole buffer, takes a rank-1 value such as a stack. The result is void.
  • after m s: s must be a store, and m must be the version that store writes into. after %b1 %s is invalid when %s wrote into %b, and so is naming an older version of the right buffer. The result is memory with the same dtype and shape as m.
  • m must be a whole version: a buffer, an alloc or another after. It cannot be a view, so after %e %s is invalid even though %s stored through %e.
  • An alloc has versions in the same way. It is scratch memory, so it is never an output.
  • The outputs are the final version of every buffer: the version no after builds on.
  • In a test file, every line must still be reachable from the assert, as in week 1. A store and its after that the assert never reads make the file REJECTED.

The reasons the oracle gives, which are handy to search for when a test surprises you:

the program hasthe oracle says
a store that no after namesa store that no after sequences has no effect
two stores into one version, with fewer than two after lines on ittwo stores into the same buffer version are unordered
two after lines on the same versiontwo top-level afters on the same buffer version are unordered
an after that names a version its store did not write intoafter: the store must write into the version after names
a load of an old version that depends on a newer onea load of an old buffer version is needed after that version was overwritten

Check yourself

After this runs, what does %x hold?

%b  = buffer 2 dtype=i32 slot=0
%e  = shrink %b 0 []
%s1 = store %e 1
%b1 = after %b %s1
%x  = load %e

Which version is %e a view of?

%e is a view of %b, the version before the store, and the buffer started as zeros. To read the 1, you'd load through shrink %b1 0 [].

Two stores write different elements of %b, and each has its own after %b .... What happens?

Rule 1 counts stores per version, not per element.

The rule is one store per version, through any view. Even when the elements differ, there are now two "next versions" of %b, and neither builds on the other. Chain them instead: the second store goes into a view of the first store's after.

A program has %s = store %e 5 and no after mentions %s. What happens?

Rule 2.

Every store must be sequenced by exactly one after. A store nothing sequences can't affect any version, so the oracle rejects the program rather than guess what you meant.

after m s has to name the version the store wrote into.

%s1 wrote into %b, so only after %b %s1 is right. Loading either version is allowed on its own.

What are the final contents of the buffer?

%b  = buffer 2 [5 6] dtype=i32 slot=0
%e  = shrink %b 0 []
%x  = load %e

%s  = store %f %x

Read b[0], write it into b[1]. Is anything out of order here?

The load reads old %b, which is fine: it runs before the store. b[0] is 5, so b[1] becomes 5 too.

Why is the old-version example above invalid?

mod keeps %k in range, and there's only one store. Follow the arrows in the figure.

It's a cycle: the old load must come before the store (it reads the version the store overwrites), and it also must come after it (its index is read from the new version). Loading a version that has a successor is fine on its own, as the previous question showed.
