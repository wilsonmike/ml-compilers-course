Week 1 study guide

Week 1 builds the core everything else stands on: the hash-consed UOp, a validator, an interpreter and a rewrite engine that simplifies programs. This page recaps it, collects the rules worth memorizing, and walks the lab one step at a time.

The week in one page

1.1 The UOp

A program is a graph of UOp(op, src, arg) nodes, each with a dtype and a shape. Hash consing makes two structurally equal nodes the same node, so equality is one comparison and shared work is computed once. Static cost counts each distinct node once: mul %a %a with one shared add costs 2, and mul %a %b with two distinct adds costs 3.

1.2 .uir and interpreting

A file is tokens, not lines: %name = op atoms attrs, where a newline is just whitespace and a constant is written as its literal. Dtypes are i32 and bool. i32 wraps, division floors, and nothing can fail at run time. Each file gets one outcome, MATCH, MISMATCH, REJECTED or OVERBUDGET, decided in a fixed order.

1.3 Rewrites and folding

A rewrite rule is a pattern and a replacement, like add(x, 0) → x. The engine visits sources first, applies rules until none fire, and repeats passes until nothing changes. Constant folding is the rule family "all inputs are constants, so compute it now", with exactly the interpreter's semantics: div 1 0 folds to -1.

1.4 Symbolic simplification

i32 is a ring mod 232, so reassociation is always safe. Bounds give each node an interval by fixed op-by-op rules, and they're part of validation: an index whose bounds don't fit its axis is rejected. In simplify, bounds and param limits prove rules like cmplt(mod(x, 8), 8) → true.

1.5 call, param, stack and index

A param is param [] [l h] slot=k dtype=t addrspace=ALU, with optional limits. A call binds argument i to slot i in its body, and each argument's bounds must fit the limits. Bodies are closed: substitution stops at a nested call's body but goes into its arguments. A param outside any call is rejected.

Mistakes people make

Most of these are bugs that were planted in the reference compiler to prove the suite catches them. The week 1 test guide lists every test with the bugs known to fail it.

  1. Using your language's native int for i32. Python's ints never overflowOCaml's is 63 bits, so 2147483647 + 1 never wraps. Caught by add_i32_0 and mul_i32_0.
  2. Dividing like C. Truncation gives -7 / 2 = -3, but .uir floors to -4. OCaml's / and mod truncate.Python's // and % already floor. Caught by div_floor_1 and mismatch_div_not_c.
  3. Treating division by zero as an error, or as 0. div x 0 is -1 and mod x 0 is x. Caught by div_zero and bounds_mod_zero.
  4. Shifting by the raw amount. shl x y shifts by y mod 32. Caught by bounds_shl_mod32.
  5. Evaluating without memoization. A tree walk of a shared DAG is exponential. Caught by dag_sharing (it times out).
  6. One global cache across calls. The same body called with 3 and with 4 then returns the same thing twice. Caught by call_memo_per_call.
  7. Substituting into a nested call's body. Bodies are closed. Caught by call_closed_body and the simplify test trap_nested_call.
  8. Bounds that are smarter than the rules. mul %i %i with %i in [-1, 1] is [-1, 1], not [0, 1], and validation must use the rule. Caught by rejected_bounds_mul_square.
  9. Ignoring limits. An argument whose bounds don't fit the param's limits is rejected. Caught by rejected_limits_arg_outside.
  10. Charging a body once. Two different call nodes with the same body each pay for it. Caught by overbudget_cost.
  11. Forgetting the reachability rule. Every node must be reachable from the assert. Caught by rejected_unreachable.
  12. Letting an uncaught exception decide your output. In OCaml, Fatal error: exception Not_foundIn Python, a traceback prints no outcome line, so the test fails whatever the right answer was. Catch your own errors and print REJECTED FILE where the spec says so.

Stuck on the lab?

Build in this order, and don't move on until the check passes. Each check is a tiny program: save it, run it through your compiler and through the oracle (python _reference/uirc.py --week=1 FILE), and compare the outcome lines.

  1. Parse and print. Done when you can print every binding back in .uir form. Check: %a = add 2 3 / %t = assert %a 5 should print MATCH. If a later test is REJECTED when it shouldn't be, look at tokens first: %a=add with no spaces, a binding split across lines, 0xff and 007 are all valid, but +1, -0x10, 0X10 and 1.5 are not.
  2. The hash-consed UOp. Done when building the same node twice gives back the identical node. Check: the suite's dag_sharing runs in milliseconds. If it hangs, your table key hashes or compares whole subtrees instead of child ids or identities.
  3. Interpreter. Done when values come out right. Check: %a = div -7 2 / %t = assert %a -4 prints MATCH. If it prints MISMATCH, your division truncates.
  4. Types. Done when every type error is reported before anything runs. Check: %a = add 1 true / %t = assert %a 2 must print REJECTED.
  5. The rewrite engine. Done when simplify folds constants. Check: %x = param [] slot=0 dtype=i32 addrspace=ALU, %k = mul 3 4, %out = add %k %x should print a program whose %out is add of the param and 12, one op.
  6. Symbolic rules and bounds. Done when cmplt (mod (max %x 0) 10) 10 simplifies to true but cmplt (mod (max %x 0) 10) 9 does not (written as separate bindings). If the second also folds, your comparison is off by one.
  7. call and param. Done when bodies are closed and values are cached per call. Check: %p0 = param [] slot=0 dtype=i32 addrspace=ALU, %p1 = param [] slot=1 dtype=i32 addrspace=ALU, %inner = add %p0 100, %outer = call %inner %p1, %r = call %outer 1 2, %t = assert %r 102 prints MATCH. If you get 101, substitution went into the nested body.
  8. stack and index. Done when unsafe indexes are rejected. Check: %i = param [] [0 3] slot=0 dtype=i32 addrspace=ALU, %v = index [10 20 30] %i, %r = call %v 1, %t = assert %r 20 prints REJECTED, and with limits [0 2] it prints MATCH.
When a test fails and none of this fits

Rerun it alone with -k NAME -v, copy the test file, delete lines as long as it still fails and compare with the oracle on the smallest version. The debugging guide walks through it.

Check yourself

What does %a = shl 3 30 give in .uir (i32)?

3 · 230 = 3,221,225,472, which is more than INT_MAX. Subtract 232.

3221225472 - 4294967296 = -1073741824. shl wraps like add and mul.

What does %a = shl 1 33 give?

The shift amount is taken mod 32 first.

33 mod 32 is 1, so this is shl 1 1, which is 2. A shift amount can never be out of range.

What does %a = mod 2147483647 -2 give?

.uir's mod floors, so a nonzero remainder takes the sign of the divisor.

INT_MAX is odd, so the remainder has size 1, and it takes the sign of -2. The floor quotient is -1073741824, and 2147483647 - (-2)(-1073741824) = -1. C would give 1.

This program has an unused division by zero and an assert that fails. What does ./compile print?

%a = div 1 0
%t = assert 1 2

Division by zero is fine in .uir. Which test-file rule does %a break?

Every node must be reachable from the assert, and nothing reaches %a. Validation comes before running, so the failing assert never gets compared.

What does %r evaluate to?

%p0    = param [] slot=0 dtype=i32 addrspace=ALU
%inner = add %p0 1
%outer = call %inner 10
%r     = call %outer 5

What does %outer's body depend on? Does it use any param of its own?

%outer's body is call %inner 10, which is 11 and uses no param of %outer. The 5 is an extra argument: allowed, and reachable, but nothing uses it.

With hash consing, how many distinct nodes does this program build, counting the constants?

%a = add 1 2
%b = add 1 2
%c = mul %a %b
%d = mul %b %a

Which bindings are the same node? Once %a and %b are one node, what are %c and %d?

The constants 1 and 2 (two nodes), one add, and one mul of that add with itself: %c and %d are the same node. Four in total.

%x has limits [0 8]. Which simplification is wrong?

Try each with x = 8, the top of the limits.

8 mod 8 is 0, not 8. The other three hold for every x in [0, 8], and the grader only tests inputs inside the limits.

Can bounds analysis simplify cmplt (mod (max %x 0) 10) 9?

What interval does mod (max %x 0) 10 have?

The interval is [0, 9]. Values 0 to 8 are less than 9 and 9 is not, so the comparison depends on %x. Against 10 it would fold to true.

Challenges

  1. Tighter bounds for simplify. Validation has to use the spec's bounds rules exactly, but simplify may use any bounds that are true. Find a program where knowing mul %i %i is never negative would let simplify remove one more op, and check your rule never changes a value by running both versions through the oracle with a few params.
  2. A rule the oracle doesn't have. Find a valid i32 identity the reference simplifier misses (for example something with xor or max). Write it as a simplify test with a smaller max_ops and check that python tools/test.py --check-tests DIR --week 1 (the folder holding your test) rejects it, which proves the oracle doesn't reach it yet.
  3. Break the grader. Write a wrong simplification that you think the grader's edge-case inputs won't catch. If you find one, you've found a hole in the course. With one or two params the grader tries every combination of edge values, so think about values that aren't edges.
