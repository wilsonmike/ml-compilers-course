Debugging your compiler

A red test is information. This page is the routine: read what the grader says, find out what the test is for, shrink it until the bug has nowhere to hide, and compare with the oracle.

1. Read the grader's output

Run the suite with -v so every failure prints its details, and -k to run only the tests whose path contains a word:

python tools/test.py --compiler YOUR_COMPILER --week 1 -v
python tools/test.py --compiler YOUR_COMPILER --week 1 -k div -v

YOUR_COMPILER is the command that runs your compiler. For a Python compiler that's the wrapper script from lesson 0.7, such as "C:/path/to/my-ml-compiler/mlc.cmd" on Windows or ~/my-ml-compiler/mlc on macOS and Linux.For an OCaml compiler it's the path to the executable dune built, such as C:/path/to/_build/default/bin/main.exe.

Each failure is a FAIL line with the test's path, then one or more indented lines saying what was wrong. These are real messages from the grader:

FAIL tests/week1/run/i32_div_trunc.uir
    expected exit 0 (pass), got 1
    stderr: assert failed: %t0

Your compiler said an assert failed, but the oracle says every assert passes. So one of your values is wrong, and %t0 is the first assert that saw it.

FAIL tests/week1/run/err_div_zero.uir
    exit 2 is right, but stderr needs a line starting 'invalid:' (an uncaught exception isn't a diagnosis)

Your compiler exited 2, but by crashing. OCaml exits 2 on an uncaught exception, so the grader also requires an invalid: line on stderr. Catch your errors and print the reason. In Python an uncaught exception exits 1 instead, so it shows up as a failed assert with no assert failed: line. The fix is the same: catch it, print invalid: and the reason, and exit 2.

The run contract in one table

2. Find out what the test is for

Every test starts with a comment saying what it checks. The test guides collect all of them, with the plausible bugs known to fail each test: week 1, week 2, week 3, week 4, week 5, week 6. Read the matching section of the spec for that week before changing code: most failures are a rule read differently, not a typo.

3. Shrink the failing test

A test with ten statements has ten places for the bug. Copy it to a scratch file and delete lines until it stops failing, then put back the last thing you removed. What's left is the bug.

Here's i32_div_trunc.uir, which failed above:

%a = div -7 2
%t0 = assert %a -3
%b = div 7 -2
%t1 = assert %b -3
%c = div -7 -2
%t2 = assert %c 3
%d = div 7 2
%t3 = assert %d 3

The failure named %t0, so keep only what %t0 needs:

%a = div -7 2
%t0 = assert %a -3

Ask the oracle what should happen, then try your own guess for the value:

> python _reference/uirc.py run small.uir
(exit 0: -7 div 2 really is -3)

> python _reference/uirc.py run guess.uir      # the same program asserting -4
assert failed: %t0
(exit 1)

Your compiler computes -4: it rounds toward minus infinity, like Python's // or a floor on floats. The spec says division truncates toward zero, like C. Two lines, one rule.

Shrinking tips
  • Delete asserts after the failing one first. They never run.
  • Replace a computed operand with the constant it should be. If the bug disappears, the bug is upstream.
  • For simplify failures, put the grader's args: values in by hand and compare both programs.
  • Keep a folder of shrunk cases. They make good tests for your own suite.

4. Compare with the oracle

The oracle is the reference compiler. Running it is fine and encouraged, but reading its source would hand you the answers.

python _reference/uirc.py run FILE        # exit code and assert line, exactly what the grader expects
python _reference/uirc.py simplify FILE   # one valid simplification of %out (not the only one)
python _reference/uirc.py render FILE     # the oracle's C for a week 2+ program

An example: this program should simplify to its input, and the oracle shows it does.

%x = param 0 dtype=i32
%a = add %x 0
%out = mul %a 1

> python _reference/uirc.py simplify s.uir
%out = param 0 dtype=i32

Your output doesn't have to match the oracle's text. It has to compute the same values and stay within the op limit. For render, compare your C's behavior, not its look: the oracle's C shows one correct schedule, and yours can differ.

5. When render fails

The grader compiles your C with these flags, then runs it on the test's data and compares every buffer bit for bit:

clang -std=c11 -O2 -ffp-contract=off -fsanitize=undefined -fsanitize-trap=undefined

To see exactly which bits differ, print a float's bits in your own test harness:

#include <stdint.h>
#include <string.h>
uint32_t bits_of(float x) { uint32_t u; memcpy(&u, &x, 4); return u; }
/* printf("%08x\n", bits_of(v)); */

3e99999a and 3e99999b differ in the last bit: one rounding step somewhere.

6. Print your IR between passes

Most bugs live between two passes: the graph was right after parsing and wrong after simplifying, or right before rangeify and wrong after. Give your compiler a debug flag that prints the graph as .uir after each pass, then diff the printouts. Printing .uir has a bonus: you can feed any intermediate stage back to the oracle and ask what it computes.

8. Asking for help well

Whoever helps you, a classmate or an AI assistant, needs the same four things:

  1. The smallest program that fails (section 3), not the whole test.
  2. What you expected, what you got, and what the oracle says.
  3. The rule from the spec you think applies.
  4. What you already tried.
An AI assistant in your repo

The AGENTS.md from templates/ sets the rule for your compiler repo: an AI assistant may explain concepts, draw diagrams, run the oracle, and ask you questions that lead to the bug, but it doesn't write or edit your compiler code. Ask "why would this give -4?" rather than "fix my div".

9. When the test itself looks wrong

It happens. The format is provisional and the tests are written by people. Check in this order:

  1. Read the spec section again, slowly. Most "wrong tests" are a rule that says something subtler than it first seemed.
  2. Run the oracle on the test. The grader compares you to the oracle, not to the header, so the oracle's answer is what you're held to.
  3. If the spec and the oracle disagree, that's a real bug in the course. Write it up with the smallest program that shows it, the spec sentence, and what the oracle does, and report it to whoever maintains your copy of the course.
