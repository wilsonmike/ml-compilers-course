Week 10 study guide

Week 10 runs one program on several GPUs. A device loop says which GPU runs which iterations, a rule decides whether each buffer is cut into shards or copied whole, and render-cuda writes the copies out and back. No GPU is needed: the emulator checks every bit and counts every byte moved. This page recaps the week, collects the rules worth memorizing, and walks the lab one step at a time.

The week in one page

10.1 More than one GPU

A device is one GPU, numbered from 0, with its own memory that no other device can see. So anything a device reads is copied to it first. A buffer is sharded (each device gets its own piece) or replicated (each gets a whole copy). The scatter copies out, and the gather copies the results back to device 0. Time on N devices is about work / N + data moved / copy speed, so a job that does little work per byte gets slower on a second GPU.

10.2 Device loops and shards

range N axis=device runs iteration d on device d. N is a literal from 1 to 16, the loop is at the top level, and the parallel loops inside it are global loops. Memory the loop writes follows week 7's slice rule with d in place of r: every access at d·S + e, e inside the shard, one S per buffer, and N·S at most the buffer's size. Memory it only reads is sharded when it passes the same checks, and replicated otherwise. The axis changes no bits.

10.3 Moving memory

For each device loop, render-cuda prints four steps. Scatter: UIR_ALLOC and UIR_COPY for every buffer the loop touches, written ones too, since new memory isn't zeroed. Launch: UIR_DEVICE, then the kernels with the device's allocations. Wait: UIR_SYNC(). Gather: copy written shards back, then UIR_FREE. The kernel subtracts d·S from every offset into a sharded buffer. A # cuda copy: N line fails a test that moves more than N bytes.

10.4 A GEMM on two GPUs

Split C = A @ B by rows: A and C are sharded, B is replicated. c_shard_gemm moves 512 bytes, where whole copies of A, B and C would move 768. A sum that needs every device takes two steps: a partial sum on each device, then a total in a kernel after the loop, on device 0. The program fixes the order of the adds, so the bits are the same on any number of GPUs. Two kernels in one device loop keep their data on the device in between.

10.5 Training on several GPUs

Data parallelism shards the batch and replicates the weights. A batch's gradient is the sum of its examples' gradients, so each device writes a partial gradient, and a kernel on device 0 adds them and steps the weights. A one-device program that loops over the whole batch adds in another order and can differ in the last bits. Deleting axis=device keeps the order. The work on device 0 and the copies on every step don't shrink as devices join, which is why real systems use an all-reduce.

10.6 Lab

The suite has 26 tests: 16 run tests (8 rejected_, 1 mismatch_ and 7 that must MATCH) and 10 c_ tests, eight with a copy budget and c_err_load_outside_kernel, which must be refused. There are no CPU render tests and no speed tests. Weeks 2 to 9 must still pass in full, and week 1 stays at 272 / 282 (the ten programs week 2 made legal).

Mistakes people make

Most of these are bugs that were planted in the reference compiler to prove the suite catches them. The week 10 test guide lists every test and what it checks.

  1. Skipping the slice rule for memory a device loop writes. Caught by rejected_devices_write_one_place and rejected_device_slices_overlap.
  2. Applying it to memory the loop only reads. A failed check there means replicate, not reject. Caught by device_reads_anywhere and c_reads_anywhere.
  3. Missing a shape rule. A bound outside 1 to 16, a device loop inside another loop, a thread loop inside a device loop, two strides for one buffer, or shards that run past the end. Caught by rejected_device_bound_0, rejected_device_bound_17, rejected_device_in_loop, rejected_thread_in_device, rejected_device_two_strides and rejected_device_shards_do_not_fit.
  4. Replicating every read-only buffer. The bits stay right. Caught by the copy budgets: c_shard_scale moves 272 bytes where 208 are allowed.
  5. Not copying a buffer in. The kernel reads the emulator's fill, 0xA5A5A5A5. Caught by c_shard_scale.
  6. Not copying the results back. Caught by c_shard_scale and every other c_ test that writes.
  7. Indexing the whole buffer in the kernel. Without - d·S, device 1 writes past its allocation. Caught by c_shard_scale.
  8. Launching with device 0's pointers. The emulator stops the kernel. Caught by c_shard_scale.
  9. Copying shard 0 to every device. Leaving out + d·S in the copies. Caught by c_shard_scale.

Stuck on the lab?

Build in this order, and don't move on until the check passes.

  1. The axis as a plain loop. Parse axis=device and run it like any loop. Done when this prints MATCH, and still does with all three axes removed:

  2. Where a device loop sits. The bound, the top level, no thread loop inside. Done when -k bound, rejected_device_in_loop and rejected_thread_in_device pass.
  3. Shards. The slice check on written memory, one stride per buffer, and the same check on read-only memory, which marks it replicated when it fails. Done when rejected_device_slices_overlap, rejected_devices_write_one_place and two_strides pass and device_reads_anywhere still prints MATCH.
  4. The shards fit. N·S at most the buffer's size. Done when every run test passes.
  5. render-cuda. Scatter, launch, wait and gather, with every read-only buffer copied whole for now. Done when c_one_device and c_err_load_outside_kernel pass and the tests left fail only on bytes.
  6. Shards of read-only memory. Copy S elements from d·S, subtract d·S in the kernel, and don't gather them. Done when all 26 pass, then weeks 1 to 9 pass as before.

Check yourself

A device loop of 2 stores into a buffer of 16 at 4d + e, with e from 0 to 7. Is it accepted?

Check e + size ≤ S.

7 + 1 ≤ 4 is false, so device 0 writes elements 4 to 7, which are device 1's shard. With 8d + e it is accepted.

Inside a device loop but outside its kernels, which of these may render-cuda compute on the host?

Only two kinds of op may run there.

Only i32 add and mul of the device index and literals. Anything else there makes render-cuda exit 2.

4 devices. x (32 f32) is read at 8d + e, w (4 f32) at the block number, and o (32 f32) is written at 8d + e. How many bytes does the device loop copy?

Sharded: 8 elements per device. Replicated: all of it per device. Written: out and back.

x: 4 · 8 · 4 = 128. w: 4 · 4 · 4 = 64. o: 128 out and 128 back. 448 in all.
