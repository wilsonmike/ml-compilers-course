Reduce and expand

By the end of this lesson you can get one number out of a vector, like its sum or its largest element, and you can stretch one number so it meets every element of a vector. The two ops are reduce and expand. Your compiler needs both, because sums, means and normalization are built from these two moves, and so is almost every layer of a neural network.

Goal

Predict what reduce and expand give, bit for bit, and write .uir programs that use the two together.

You'll use

f32 rounding and recip from lesson 2.1. The accumulator loop from lesson 3.2. Vectors, expand and the rule that shapes must match from lesson 4.1.

Two exercises fold over an OCaml list (O.3).

Warm up

Two questions from earlier weeks, from memory. Pulling an idea back out of your head is what makes it stay.

In f32, what is add 16777216.0 1.0? (16777216 is 224.)

Past 224, an f32 can hold only every second whole number.

A week 3 loop sums a buffer that holds 5 1 2. The accumulator starts at 0. On each pass the loop loads the accumulator, adds the next element and stores the total back. What does the accumulator hold after the second pass?

The first pass adds the 5. What does the second pass add?

0, then 5, then 6, and after the third pass 8. An accumulator loop takes the elements one at a time, from first to last. Today one op will stand for that whole loop.

Two jobs elementwise ops cannot do

In lesson 4.1 every op was elementwise: element i of the result comes from element i of each operand. Two everyday jobs do not fit that mold. Here is the first. A buffer holds four f32s and you want their sum, which is one number.

%x = buffer 4 dtype=f32 slot=0
%v = load %x

%v has shape (4,). You may combine it with itself using any elementwise ops you like: add, mul, max and the rest. What shape can the result have?

What did lesson 4.1 say about the shape of an elementwise result?

An elementwise op gives back the shape it was given. Four numbers in, four numbers out. No chain of them ever arrives at one number.

In week 3 you got a sum with a hand-written loop and an accumulator, about a dozen lines. Vectors were supposed to free you from writing loops, so the sum needs an op of its own.

The second job runs the other way. You have one number, say 1.0, and you want to add it to every element of %v. Lesson 4.1 showed that add %v 1.0 is rejected, because the shapes (4,) and () do not match, and that expand turns the one number into four first.

reduce: one number out of a vector

reduce takes a vector and the name of an op. It folds the vector with that op, which means it combines the elements one after another into a single running value. The result is a scalar.

%x = stack 3 9 2 4
%s = reduce %x op=add
  1. Start with the first element. The running total is 3.
  2. Fold in the next element. 3 + 9 is 12.
  3. Keep going to the end. 12 + 2 is 14, and 14 + 4 is 18.
  4. Hand back the total. %s is 18, with shape ().

That is the accumulator loop from the warm up, written in one line. The op attribute is required and has three choices:

  • op=add gives the sum.
  • op=mul gives the product.
  • op=max keeps the larger value at every step, so it gives the largest element.

The vector must be i32 or f32. A bool vector is rejected. Each step follows the scalar rules you know: i32 wraps and f32 rounds.

What is reduce %x op=max for %x = stack 3 9 2 4?

Start with 3. At each step keep the larger of the running value and the next element.

The running value goes 3, then 9, then 9, then 9. Once the largest element is in, nothing replaces it.

Same numbers, two orders

The worked example added from left to right. Would another order give the same total? For i32 it would: addition that wraps gives the same answer in any order. Now try f32. Add these three numbers in two ways:

left to right:      (16777216.0 + 1.0) + 1.0
small ones first:   16777216.0 + (1.0 + 1.0)

Each + is an f32 add, so it rounds. What do the two orders give?

Use the warm up for the first add of the left to right order. Can f32 hold 16777218?

Left to right, 16777216 + 1 rounds back to 16777216, and then it does so again. Small ones first, 1 + 1 is exactly 2, and 16777216 + 2 is 16777218, which f32 can hold. The same three numbers give two different answers.

The rounding depends on the running total, so the order of the adds changes the result. Here is a second case with four numbers. Near 1e8, which is one hundred million, an f32 holds only every eighth whole number, so 1e8 + 1 rounds straight back to 1e8. Step through both orders.

Both rows hold the same four numbers. Order A ends at 0 and order B ends at 2.

So the order is fixed

If "the sum" could mean any order, two correct compilers could print different answers for the same program. The grader compares f32 results bit for bit, so the spec picks one order and every compiler follows it:

reduce x op=add  =  ((x[0] + x[1]) + x[2]) + ... + x[n-1]
  1. Start from x[0]. Not from 0. A one-element vector reduces to that element, with no op at all.
  2. Go left to right. Fold in x[1], then x[2], up to the last element.
  3. Apply the scalar rule at every step. f32 rounds after each add and i32 wraps.

This order is called a left fold. op=mul and op=max fold the same way. A left fold is the simplest order to state, and it is the order of the accumulator loop, so it is easy to turn into C. A compiler that regroups the adds, for example by summing pairs, gets some f32 programs wrong.

Why not start from 0? Because 0.0 + -0.0 is +0.0, so the sum of [-0.0] would lose its sign.

expand: one number for every element

Now the second job. This program wants to divide every element of x by the sum of x. Floats have no division op, so it multiplies by recip of the sum, which is 1 divided by the sum.

%v = load %x
%s = reduce %v op=add
%r = recip %s
%y = mul %v %r

%v has shape (4,). What happens at %y = mul %v %r?

%r comes from a reduce, so it is a scalar. Does any ALU op stretch a scalar for you?

ALU ops never stretch a scalar on their own. Both operands must have one shape, so the scalar has to become a (4,) vector first.

The repair is the expand you met in lesson 4.1: expand %r [4] is a vector of 4 copies of the scalar %r. It is a broadcast that you write out, and .uir has no other kind. Lesson 4.1 used it to add 1.0 to every element:

%one = expand 1.0 [4]
%z   = add %v %one

Two facts are new here. In week 4, expand takes only a scalar. It never makes a vector longer: a (2,) vector cannot become (3,). And the copies cost nothing. Lesson 4.3 shows that the compiled loop reads the one number again on each pass and never stores four of them.

Add one number to every element

Slot 0 holds five f32s x, and slot 1 holds one f32 b. Slot 2 should get y[i] = x[i] + b. The starter already loads x as the vector %v and b as the scalar %s, but it stores x unchanged. Finish it with one expand and one add.

Reduce, then expand

The two ops are most useful as a pair: boil a vector down to one number, then spread that number back over the vector. Here is the program from the last section, repaired. It computes y = x / sum(x), which is called normalization because the results add up to 1.

%v = load %x                   # (n,)
%s = reduce %v op=add          # ()   the sum
%r = recip %s                  # ()   1 / sum
%e = expand %r [n]       # (n,) 1 / sum, n times
%y = mul %v %e                 # (n,) each x / sum

For x = [1.0 3.0], what is %y? Write the two numbers with a space between them.

Follow the five lines in order. The sum is 4.0, so what is recip of it?

The sum is 4.0 and its recip is 0.25. Expanded, that is [0.25 0.25]. Multiplied elementwise by [1.0 3.0] it gives [0.25 0.75].

A mean works the same way and is even shorter: it is a sum times a constant. For eight elements, reduce and then mul by 0.125. Both operands of that mul are scalars, so it needs no expand.

The mean of eight

Slot 0 holds eight f32s. Store their sum times 0.125 into slot 1. The starter stores just the sum.

Divide by the largest element

Now write the whole pattern yourself. Slot 0 holds six f32s. Store y[i] = x[i] * recip(max(x)) into slot 1. Use recip and mul, as written: the tests check that exact rounding, including what NaN and zero maxima do.

Edge cases of add, mul and max, for when a reduce test is off by one bit

reduce %x op=add takes a vector of shape (n,) and returns a scalar. It starts from x[0], not from 0, and adds the rest left to right, rounding to f32 after every add. op=mul and op=max fold the same way. reduce works on i32 and f32, not bool. i32 wraps at every step, as always.

op=maxmaxany NaN makes the result NaN, and max(-0.0, 0.0) is +0.0

A one-element vector reduces to that element, with no ops at all. bool vectors can't be reduced.

Starting from zero

Seeding the sum with 0.0 looks harmless, and it is for almost every input. But 0.0 + -0.0 is +0.0, so the sum of [-0.0] would come out as +0.0. The spec's fold starts from x[0], so reduce [-0.0] op=add is -0.0. recip tells them apart: -inf versus inf.

Why the order is in the spec

Real-number addition is associative. f32 addition isn't: every add rounds, and the rounding depends on the running total. The grader compares f32 results bit for bit, so "the sum" has to mean one specific sequence of adds. A left fold from the first element is the simplest one to state, and the easiest to render as a loop.

Every rule for expand, for when your type checker has to accept or reject one

expand %s [n] takes a scalar and gives a vector of n copies. The shape is the last operand, a bracket list, and n must be at least 1: a size of 0 is rejected. It's how a scalar meets a vector, since ALU ops never broadcast on their own. Week 4 uses expand on scalars. Week 5 widens it to grow any size-1 axis of a value with the same rank. Growing an axis that isn't size 1 is always rejected: a (2,) vector can't become (3,).

Two rules from the spec apply to both ops of this lesson. A computed vector, which includes the result of expand and the operand of reduce, may not depend on an open range from a hand-written week 3 loop. And bounds analysis (lesson 2.3) treats the result of expand and of reduce as the full range of its dtype.

A value used twice: why normalization reads x twice, for when you reach lesson 4.4

In the normalization program, %v is used twice, by the reduce and by the final mul. That's fine: the generated code reads x twice whatever you do, because the reduce has to finish before the store loop can start. The real question comes when a computed value (not a plain load) has two uses: should the compiler recompute it at each use, or store it once? That's the materialization question of lesson 4.4.

What is reduce %x op=add for %x = stack 100000000.0 -100000000.0 1.0 1.0?

Fold left to right. What's the running total after the first two elements?

1e8 + -1e8 is exactly 0, then 0 + 1 = 1, then 1 + 1 = 2.

And for %x = stack 100000000.0 1.0 1.0 -100000000.0?

In f32 the neighbors of 1e8 are 8 apart. What is 1e8 + 1 after rounding?

1e8 + 1 rounds back to 1e8, twice, and then 1e8 - 1e8 is 0. Same values, different order, different result.

What is reduce %x op=max for %x = stack 1.0 nan 3.0?

reduce folds with week 2's f32 max. What does that do with a NaN operand?

The f32 max returns NaN if either operand is NaN, so once the NaN enters the fold, every later step is NaN too.

What is reduce %x op=mul for the i32 vector %x = stack 65536 65536 3?

65536 is 216. What's 232 in i32?

65536 * 65536 = 232, which wraps to 0 in i32, and 0 * 3 = 0.

What is reduce %x op=add for %x = stack -0.0?

Where does the fold start, and how many adds does a one-element vector need?

The fold starts from x[0] and there's nothing left to add, so the result is -0.0. A sum seeded with 0.0 would give +0.0.

Which axes is expand allowed to grow?
