Rendering vectors

Your render can print loops you wrote by hand, and your interpreter can run whole-vector programs. But render on a vector program has no good answer yet: it fails, or it prints one line of C for every element. In this lesson you make it print a loop, by putting rangeify in front of the renderer you already have.

Goal

Say what C render must print for a vector program, why it has to stay small and which parts of your compiler produce it.

Warm up

In lesson 3.5, a value has no open ranges, like g[0] squared. Where does its line of C go?

Would its value change from one trip through a loop to the next?

Outside. A value's open ranges decide its depth, and with none open it sits in the outer block and runs once.

In lesson 4.3, rangeify lowers a vector program to scalars. Which two things become loops?

Which ops take a whole vector and give back an effect or a single scalar?

One line per element

This week 2 program copies four floats from one buffer to another:

%a  = buffer 4 dtype=f32 slot=0
%c  = buffer 4 dtype=f32 slot=1
%x  = load %a
%st = store %c %x
%c1 = after %c %st

The reference compiler (the grader calls it the oracle) renders it the week 2 way, and so does your compiler. There is no loop. Every element is spelled out, which is called unrolling:

void kernel(float *restrict b0, float *restrict b1) {
  float v2[4] = {b0[0 + 0], b0[0 + 1], b0[0 + 2], b0[0 + 3]};
  b1[0 + 0] = v2[0];
  b1[0 + 1] = v2[1];
  b1[0 + 2] = v2[2];
  b1[0 + 3] = v2[3];
}

Now take a week 4 program that adds two vectors of 1,000 floats:

%a  = buffer 1000 dtype=f32 slot=0
%b  = buffer 1000 dtype=f32 slot=1
%c  = buffer 1000 dtype=f32 slot=2
%x  = load %a
%y  = load %b
%z  = add %x %y
%st = store %c %z
%c1 = after %c %st

Your renderer has no rule for an add of two vectors. The quickest patch is more of the same: one add and one store line for each of the 1,000 elements.

Say you patch it that way, and every value the C computes is right. What does the grader report for this test?

The copy above costs about 38 bytes of C for each element. Multiply by 1,000.

The grader measures your C before it compiles anything, and rejects more than 20,000 bytes. At about 38 bytes for each element, even a plain copy of 1,000 floats unrolls to about 38,000 bytes.

The reference compiler prints this for the same program:

void kernel(float *restrict b0, float *restrict b1, float *restrict b2) {
  for (int32_t r4 = 0; r4 < 1000; r4++) {
    float v7 = b0[r4];
    float v9 = b1[r4];
    float v10 = (v7 + v9);
    b2[r4] = v10;
  }
}

That is eight lines, and the whole file is 1,277 bytes. A thousand lines became one loop with four lines inside.

Why the grader counts bytes

Unrolled C can be correct, so comparing values cannot catch it. Size can. Code that spells out every element grows with the vector. A loop does not: the length appears only as a number in the for line.

The looped kernel above is 8 lines for 1,000 elements. How many lines is it for 2,000 elements?

Which characters of the kernel mention the length?

Still 8. Only 1000 in the for line changes to 2000.

So the limit is a test of one thing: did every vector become a loop? Week 4's big render tests use up to 4,096 elements. A looped kernel for them is about 2,000 bytes, and an unrolled one is far over 20,000. The grader counts your render output in bytes, as UTF-8, right after render exits. Measure it yourself:

C:/path/to/your.exe render tests/week4/render/normalize_4096.uir | wc -c

That is Git Bash, and wc -c counts bytes. On Windows it can count one byte more per line than the grader, which reads a Windows line end as one byte. If the number grows when you double a vector's length, something is still unrolled. The usual causes are a rank-1 value that reaches the printer without going through rangeify, and a vector constant built element by element when it should be an expand.

Small tests can't catch unrolling

A renderer that unrolls passes every test with four-element vectors, and the bits come out right. Only the large render tests hit the 20,000-byte limit. Run them early, not just before you submit.

Will it fit in 20,000 bytes?

Repair int fits(int n, int per_elem, int fixed): 1 if n * per_elem + fixed <= 20000, else 0. The starter is right for small numbers. All three are non-negative ints, but the product may not fit in an int.

Render reuses rangeify

You do not write a new printer for vectors. In lesson 4.3, rangeify asked every vector for its element at index i, and turned each rank-1 store and each reduce into a range, scalar ops and an end. What comes out has no vectors left. It is a week 3 program, the kind your lesson 3.5 renderer already prints. So render is a chain of four steps:

  1. Parse and check. As before, now with week 4's shape rules.
  2. Rangeify. Lower every vector op to scalars at an index. This is the week's new work.
  3. Place. Lesson 3.5's pass gives every value a depth from its open ranges.
  4. Print. Lesson 3.5's printer writes the loops.

The lowered program is also one your interpreter can run, because it ran week 3 programs. That gives you a check on rangeify before any C exists: run the vector program directly, run its lowered form and compare the buffers.

One catch: a week 2 style program, like the four-element copy, must still print with no loops. Send a program through rangeify only when it needs loops. The toggle has the exact rule.

In the looped add above, four lines sit inside the for. Which part of your compiler put them there?

Rangeify produces a graph, not text. Which pass turns open ranges into depths?

Rangeify only builds the graph: a range, two scalar loads, a scalar add, a scalar store and an end. Each of those four values has the new range open, so the week 3 pass places them at depth 1.

The exact rule for when render may print loops, for the lab

render may use for loops when the program has a range, a reduce, an expand or a stage, an elementwise op on a rank-1 value, or any rank-1 value with more than 32 elements. So a plain copy of 4,096 floats is rendered as a loop even though it has no vector math. A program with none of these must render loopless, as in week 2, and the grader fails it if it finds a for. In every case while, do and goto are not allowed.

The grader's order for a render test: run render and fail on a nonzero exit, check the size, check the loop rule, compile, then compare every buffer with the reference.

Two loops and the scalars between them

Here is a program with a reduce in it. It divides every element of x by the sum of x, on 4,096 floats:

%v  = load %x
%s  = reduce %v op=add
%r  = recip %s
%e  = expand %r [4096]
%w  = mul %v %e
%st = store %y %w

How many for loops will its C have?

Use your warm up answer: which ops become loops?

Two: one for the reduce and one for the rank-1 store. The recip is a scalar and the expand makes no loop.

Step through the reference compiler's kernel. The whole file is 1,579 bytes by the grader's count.

Three rules cover almost every week 4 kernel:

  • Every rank-1 store is a loop over the vector's length. Its body computes the element at the loop index, all the way down through the elementwise ops, and stores it.
  • Every reduce is an accumulator loop: seed with the element at 0, fold in elements 1 to n-1. If two reduces read the same vector, that's two loops (lesson 4.4).
  • Scalars live between loops. The reduce's result, its reciprocal, anything computed from scalars alone, has no open range, so week 3's placement puts it in the outer block, once. In the kernel above, 1.0f / v23 runs one time, not 4096 times.
Hoisting comes free

You don't need a separate pass to hoist the reciprocal out of the store loop. It never had the store loop's range in the first place: rangeify asked the expand for its element at i, and the answer was a node with no ranges at all. Placement by open ranges does the rest.

The normalize loop pair

Repair void normalize(const float *x, float *y, int n) (n ≥ 1) so that it computes exactly what the reference kernel computes for store %y (mul %v (expand (recip (reduce %v op=add)))): fold the sum left to right from x[0], compute the reciprocal once as 1.0f / sum, then multiply each element by it. The starter has both loops and gets two of those details wrong. Results are compared bit for bit.

The % 4096 line and the helpers at the top of the file, for when you compare your C with the reference

The reduce loop computes v15 % 4096 before it loads. The reference builds every index as if the value could have several axes, so it adds a % n step. For a vector that step never changes the value, and your C does not need it. Lesson 5.5 shows how a simplifier removes it.

About 1,060 of the 1,579 bytes are the helper functions every rendered file starts with (f32_max, i32_div and the rest from lesson 2.4). They count toward the limit, and they do not grow.

Count the loops before you render

You can predict a kernel's loops from the program, before you run render. A trip is one pass through a loop's body. Go through the program in order:

in the programin the C
a rank-1 store of n elementsone loop, n trips
a reduce of n elementsone loop, n-1 trips, because element 0 is the seed
a stage of n elements (lesson 4.4)one loop that fills the temp, n trips
an expandnothing
a scalar opone line, outside the loops

For the program above that gives 4095 and 4096, which matches the two for lines in the figure. If your C has more loops than your count, or a different bound, look at that op's lowering first.

How many trips does each loop make?

A toy program is an item list in the order the kernel runs: Store n (a rank-1 store of n elements), Reduce n, Stage n, Expand n or Scalar (any scalar op). Write trips prog: the list of trip counts of the for loops the rendered kernel has, in order. A store or a stage loops n times. A reduce loops n - 1 times. An expand or a scalar makes no loop.

Two cases that add or empty a loop, for when a lab test surprises you

A store into the memory it reads prints two loops. When any load in the stored value's graph reads the buffer the store writes, the reference renders the store as if its value were staged: one loop fills a temp, and a second loop copies the temp in. The test r_inplace_scale_by_sum is this case (lesson 4.4).

A reduce of one element still prints a loop. Its bound is n-1, which is 0, so the reference prints for (int32_t r10 = 0; r10 < 0; r10++) and the body never runs. The result is the seed. The test r_reduce_single checks it.
