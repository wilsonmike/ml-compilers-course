Week 4 · Lesson 3

Rangeify

In lessons 4.1 and 4.2 you wrote programs on whole values, with no loops in sight. C has no add for whole vectors, so somebody still has to write the week 3 loop. In this lesson your compiler learns to write it, by asking every value one question: what is your element at index i?

Goal

Turn a program on whole values into week 3 loops by hand, one rule per op, the way your compiler will.

You'll use

Ranges and ends (lesson 3.1), the accumulator loop (3.2), elementwise ops (4.1) and reduce and expand (4.2).

In the exercises: match on your own classes (P.4) and a function that calls itself (P.5).

Warm up

Two questions from lesson 3.1, from memory. Pulling an idea back out of your head is what makes it stay.

What values does %t take, in order?

%i = range 4
%t = mul %i 3

A range counts from 0 and stops before its bound.

%i is 0, 1, 2, 3, so %t is 0, 3, 6, 9. Anything built from a range is computed once for each value of the range.

%s is a store that uses %i. What does %e = end %s %i do?

range makes the counter. Which op says what gets repeated?

end repeats its effects for each value of the range, in order, and closes the range. A loop is a range, some work and an end.

One program, written two ways

Take three buffers of four floats: %a, %b and an empty %y. The job is y = a + b. You can write it the week 4 way, on whole values:

%va = load %a
%vb = load %b
%z  = add %va %vb
%s  = store %y %z

Or the week 3 way, as a loop:

%i  = range 4
%pa = shrink %a %i []
%xa = load %pa
%pb = shrink %b %i []
%xb = load %pb
%z  = add %xa %xb
%py = shrink %y %i []
%s  = store %py %z
%e  = end %s %i

With [1.0 2.0 3.0 4.0] in %a and [10.0 20.0 30.0 40.0] in %b, both put [11.0 22.0 33.0 44.0] in %y. The reference compiler renders both to the same C, character for character. So somewhere inside the compiler, the short program becomes the long one.

You want to turn the short program into the long one with fixed rules, no cleverness. What must you be able to get from a value like %z?

Look at the loop version. What does its %z line compute on each trip?

The numbers are not known until the program runs, and %z is kept in no buffer. The loop body needs a way to compute element i of %z from scalars. In the loop version that is add %xa %xb.

The pass that builds that recipe is called rangeify: it replaces every op on a shaped value with scalar ops inside a range. Replacing an op with simpler ones is called lowering it.

Ask each value for its element at i

Pick an index i. Every vector can answer "what is your element at i?" with a small scalar graph. Two rules cover the program above:

  • An elementwise op at i is the same op on its operands' elements at i.
  • A load of a buffer at i is a scalar load through shrink %buf %i [].

The asking starts at the store, because a store of a whole vector is where the loop comes from:

  1. Open a range. The store writes 4 elements, so make %i = range 4 and aim the store at box i of %y.
  2. Ask the add. Its element at i is a scalar add of two answers it does not have yet.
  3. Ask each load. Each one answers with a scalar load at i. Nothing is left to ask.
  4. Close the range. Wrap the store in end.

Step through it. A box marked ? is a question that has not been answered yet.

The same i went to both operands. That works because the ops are elementwise: element i of the result never needs element i + 1 of anything. One index flows down the graph, and every shape is gone by the time it reaches the bottom.

%w = mul %z %vb, where %z = add %va %vb. What is the element of %w at i, written the way C would show it?

Ask the mul. It asks %z and %vb, with the same index.

The mul asks both operands at i, and %z asks its own operands at i in turn. The answers nest, and the index never changes on the way down.

expand ignores the index

Now y = x * 2.0. A scalar cannot meet a vector directly, so the program broadcasts it first (lesson 4.2):

%v = load %x
%c = expand 2.0 [4]
%z = mul %v %c
%s = store %y %z

The compiler turns this into one loop. How many loads from memory does each trip of the loop do?

What is element i of four copies of 2.0? Does it need memory?

One, for x[i]. Every element of %c is 2.0, so its element at i is the scalar 2.0 itself.

That is the third rule: expand %s [n] at i is %s. The index is thrown away. No four-element copy is ever built, so a broadcast costs nothing in the loop. Here is the loop the reference compiler prints. 0x1.0000000000000p+1f is 2.0 written as a hex float (lesson 2.4):

for (int32_t r4 = 0; r4 < 4; r4++) {
  float v7 = b0[r4];
  float v8 = (v7 * 0x1.0000000000000p+1f);
  b1[r4] = v8;
}

You now have three rules, and each one is a single case of a function that calls itself. Write it on a small model: one type for vector expressions and one for the scalar expressions they turn into.

The element at index i

On a toy type of vector expressions (buffers, broadcasts, adds and multiplies), write at e iat(e, i): the scalar expression for element i of e. The buffer case and the printer are given.

Two things consume a vector and produce a scalar or an effect, and those are where the loops come from:

  • A rank-1 store (a store of a whole vector) becomes a loop: range n, then store element i of the value into element i of the view, then end.
  • A reduce becomes an accumulator loop, exactly week 3's pattern: seed a one-element alloc with the element at 0, loop over 1 to n-1 folding in the element at each index, and load the result after the loop.

A reduce makes its own loop

%t = reduce %v op=add adds up a vector. Its result is one number.

A later op needs %t inside its loop, at index i. What can %t do?

How many elements of %v does one sum need?

One sum needs all of %v, not one element. So the reduce opens its own range and does the asking itself.

The loop it builds is lesson 3.2's accumulator loop, with a one-element alloc holding the running total.

  1. Seed. Store %v's element at 0 into the accumulator.
  2. Fold. Open %r = range n-1. Each trip loads the accumulator, adds %v's element at r + 1 and stores the total back. Close with end.
  3. Read. After the loop, load the accumulator. That scalar is %t.

The reduce asks the same question a store asks, but its index is 0 and then r + 1: an index can be any i32 scalar. And the seed is the first element, not zero, so the fold runs left to right from x[0], as the spec requires. The C exercise below has the one kind of input where a zero seed goes wrong.

The reduce loop in C

Write float sum_left(const float *x, int n) (with n ≥ 1) so that it computes exactly what reduce op=add does: start from x[0], then add x[1] to x[n-1] in order. The starter is right for every input but one kind. The tests compare the 32 bits of your result, printed in hex, so -0.0 (80000000) and 0.0 (00000000) differ.

The reduce loop in full, as .uir and as the oracle's C, for when you compare your renderer's output

This hand-written week 3 program computes the same value as reduce (load %x) op=add on four floats:

%acc  = alloc 1 dtype=f32
%a    = shrink %acc 0 []
%p0   = shrink %x 0 []
%x0   = load %p0
%s0   = store %a %x0
%acc1 = after %acc %s0
%r    = range 3
%a1   = shrink %acc1 0 []
%cur  = load %a1
%j    = add %r 1
%pj   = shrink %x %j []
%xj   = load %pj
%sum  = add %cur %xj
%s    = store %a1 %sum
%e    = end %s %r
%acc2 = after %acc1 %e
%a2   = shrink %acc2 0 []
%t    = load %a2

Here's what the oracle renders for reduce (load %x) op=add on four floats, stored into a one-element buffer. Compare it with lesson 3.2's accumulator:

float a4[1] = {0};
float v7 = b0[0];                /* the element at 0 seeds the fold */
a4[0] = v7;
for (int32_t r14 = 0; r14 < 3; r14++) {
  float v15 = a4[0];             /* loop-carried: reloaded every iteration */
  int32_t v16 = (int32_t)((uint32_t)r14 + (uint32_t)1);
  int32_t v17 = (v16 % 4);       /* decoding the flat counter; always equal to v16 here */
  float v19 = b0[v17];           /* the element at r + 1 */
  float v20 = (v15 + v19);
  a4[0] = v20;
}
float v24 = a4[0];
b1[0] = v24;

The % 4 line is there because the oracle builds every index as if the value could have several axes, so it always adds a % n step. For a vector that step never changes the value. Here r + 1 is always below 4, so it's provably redundant. Lesson 5.5 shows how a simplifier removes lines like this one.

The loop runs n-1 times over indices 1 to n-1, so the fold is left to right from x[0], as the spec requires. The accumulator's load sits inside the loop because of week 3's placement rule: its only use is in the loop, and the loop stores into the version it reads.

Write the reduce rule

The reduce does not care what its operand is. For a sum of squares, reduce (mul %v %v) op=add, it asks the mul for its element at 0 and at r + 1. The mul answers with the rules you already wrote, so no new case is needed.

Lower a reduce

at and show are written. Write lower_reduce e n: the accumulator loop for reduce op=add of the n-element vector expression e, as one line of text. For Vec "x" and 4 it returns acc = x[0]; for r < 3: acc = acc + x[r+1]. Ask e for its element at "0" for the seed and at "r+1" for the step.

A reduce's result is a scalar, so whatever uses it just uses it. Take x / sum(x) from lesson 4.2: reduce, recip, expand, mul, store. The reduce becomes one loop. The recip runs once, between the loops. The store becomes a second loop, and the expand vanishes into it.

Rangeify reuses everything you built

After rangeify, the graph has no vector values left: only scalars, range, end, alloc, loads and stores. That's a week 3 program, and your week 3 renderer already knows how to place each value at the right loop depth and print it. Week 4's new work is entirely in the lowering.

Why the C must be small

When your compiler runs a test it can still evaluate vectors directly. render cannot take that shortcut. Week 4 render tests include vectors of 4096 floats, and the grader rejects rendered C over 20,000 bytes. A renderer that unrolled every elementwise op, one line per element, would print thousands of lines. A rangeified one prints a few loops no matter how big n is. x / sum(x) on 4096 floats renders to 1,579 bytes by the grader's count, most of it helper functions at the top, with two loops: 4095 trips for the reduce, then 4096 for the store.

The first program of this lesson, y = a + b, now on buffers of 4096 floats. How many for loops does it render to?

Which op in that program opens a range?

One. Only the store opens a range. The add and both loads answer inside it, and the size only changes the loop's bound.

Check yourself

What is the element at i of add %a %b, where both are vectors?

What does "elementwise" promise about which elements an op reads?

An elementwise op's element i depends only on its operands' elements i, so the same index flows down to both operands.

What is the element at i of expand %s [4096]?

Does the answer depend on i at all?

Every element of a broadcast is the same scalar, so its element at any index is %s. That's why a broadcast costs nothing in the generated loop.

How many for loops does the oracle render for x / sum(x) (reduce, recip, expand, mul, then a rank-1 store) on 4096 floats?

Which two ops turn into loops?

The reduce becomes one loop and the rank-1 store another. The recip is a scalar, computed once between them, and the expand disappears into the store loop.

In that rendering, how many iterations does the reduce loop run?

Where does the fold start, and what's left to add?

The accumulator is seeded with element 0, so the loop folds in elements 1 to 4095: 4095 iterations.

Why does the grader cap rendered C at 20,000 bytes in week 4?

What does a renderer that doesn't rangeify emit for a 4096-element vector?

Unrolled vector code grows with n, but rangeified code doesn't. The cap is a simple way to check that your renderer really turns shapes into loops. It doesn't force one loop: x / sum(x) needs two.
