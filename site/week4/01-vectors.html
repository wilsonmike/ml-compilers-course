Week 4 · Lesson 1

Vectors and elementwise ops

In week 3 you added and multiplied lists by writing every loop yourself. This week you write what you mean, such as "add these two lists", and your compiler writes the loop. This lesson is the first piece: ops that work on a whole list at once.

What week 4 adds

Writing loops by hand is slow and easy to get wrong. The GEMM in lesson 3.3 took 28 lines, and one wrong offset gave wrong numbers with no error. This week you write whole-list programs, and your compiler turns them into loops. That turning is called rangeify. You build it in lesson 4.3.

Goal

Write programs that add, multiply and compare whole lists with one op, and say why a short list is never stretched for you.

You'll use

Shapes, stack and index from lesson 1.5. Views (shrink) from lesson 2.1, and load, store and after from lesson 2.2. range and end from lesson 3.1.

The same job, two ways

Here is a small job: add two lists of four numbers, pair by pair, into a third list. The first program is the week 3 way. The second is what you would like to write.

%a   = buffer 4 dtype=i32 slot=0
%b   = buffer 4 dtype=i32 slot=1
%out = buffer 4 dtype=i32 slot=2
%i   = range 4
%av  = shrink %a %i []
%x   = load %av
%bv  = shrink %b %i []
%y   = load %bv
%sum = add %x %y
%ov  = shrink %out %i []
%s   = store %ov %sum
%e   = end %s %i
%o1  = after %out %e
%a   = buffer 4 dtype=i32 slot=0
%b   = buffer 4 dtype=i32 slot=1
%out = buffer 4 dtype=i32 slot=2
%va  = load %a
%vb  = load %b
%sum = add %va %vb
%s   = store %out %sum
%o1  = after %out %s

The first program needs a counter, three views, two loads of one number each, a store and an end. Each one is a place to slip. The second has no counter at all. It loads all of a, loads all of b and adds them with one line: add %va %vb.

The second program has no range and no end. The machine still has to do four adds. What do you think your compiler must do with add %va %vb?

Think about the C your compiler prints. What does C need in order to visit four elements?

C has no statement that adds two arrays. So the compiler has to write the loop that you left out.

The reference compiler prints the same C for both programs. Here is the loop, with the wraparound casts trimmed for reading:

for (int32_t r4 = 0; r4 < 4; r4++) {
  int32_t v7 = b0[r4];
  int32_t v9 = b1[r4];
  int32_t v10 = v7 + v9;
  b2[r4] = v10;
}

Until now your compiler rejected the second program, because add only took single numbers. By the end of this week it accepts it and prints that loop.

Values with a shape

Lessons 0.4 and 1.5 gave you these words. Every value has a shape: a list of sizes, one for each axis. A single number is a scalar, with shape (). A row of n numbers of one dtype is a vector, with shape (n,), also called a rank-1 value. This week stops at vectors. Grids arrive in week 5.

You already know three ways to make a vector:

linewhat you getshape

load %v, where %v = shrink %a 1 [3]elements 1, 2 and 3 of the buffer(3,)

And one way to put a vector back: store of a vector into a buffer or view of the same size writes every element.

Weeks 1 to 3 could build vectors but could not compute with them. What is new this week is that the ALU ops (add, mul, max and the rest of the arithmetic from week 1) accept them.

%a is a buffer of 6. What is the shape of %x?

%v = shrink %a 2 [3]
%x = load %v

In shrink %a 2 [3], 2 is where the view starts and [3] is how many elements it holds.

The view holds 3 elements starting at index 2, so the load gives a vector of shape (3,).

Elementwise: one position at a time

So what does an op do with two vectors? Predict before you read on.

What do you think %z is?

%x = stack 1 5 3
%y = stack 4 2 6
%z = max %x %y

Line the two lists up, one above the other, and look at one column at a time.

Each position is decided alone: max(1, 4) = 4, max(5, 2) = 5, max(3, 6) = 6.

The rule is called elementwise: element i of the result is the op applied to element i of each operand. All operands must have the same shape, and the result has that shape too. Here it is on two buffers of floats:

%x = buffer 4 [1.0 2.0 3.0 4.0] dtype=f32 slot=0
%y = buffer 4 [10.0 20.0 30.0 40.0] dtype=f32 slot=1
%vx = load %x                # shape (4,)
%vy = load %y                # shape (4,)
%z  = add %vx %vy            # shape (4,): [11.0 22.0 33.0 44.0]
  1. Check the shapes. Both operands are (4,), so the add is allowed and %z is (4,).
  2. Take one position. Element 0 is 1.0 + 10.0 = 11.0.
  3. Do the same at every position. Step through the rest:

Nothing about the arithmetic changes. Each element is computed with the scalar rules of weeks 1 and 2: i32 wraps, f32 rounds to nearest-even after the op, max propagates NaN. Every ALU op works this way, including cmplt (a vector of bools), where (a vector condition picks per element) and cast. No element needs any other element, which is why the compiler is free to put them all in one loop.

Add two buffers, whole

Slots 0 and 1 hold four i32s each. Store x[i] + y[i] into slot 2. The starter loads only x and stores it unchanged. Load y as a whole value too, add the two and store the sum.

When the shapes differ

Now give add a list of four and a list of two.

What should add of [1 2 3 4] and [10 20] be?

Can you rule out any of the first three from the two lists alone?

All three are sensible, and they give three different lists. Nothing in the program says which one the author meant.

Stretching a smaller value to fit a bigger shape is called broadcasting. A compiler that picked one of those answers for you would hand wrong numbers to everyone who meant another. So .uir never guesses. If the operands of an ALU op do not have the same shape, the program is rejected before it runs.

That holds even when one operand is a scalar. NumPy and PyTorch let you write x + 1.0 and quietly stretch the scalar to x's shape. Here it's a type error, and the program is rejected:

%v = load %x               # shape (4,)
%z = add %v 1.0            # rejected: shapes (4,) and () don't match

Stretching one number looks safe. Here is why it is not. The author of this program wanted to add all of b to all of a, and cut a one-element view by mistake:

%a   = buffer 4 [1 2 3 4] dtype=i32 slot=0
%b   = buffer 4 [10 20 30 40] dtype=i32 slot=1
%va  = load %a
%bv  = shrink %b 0 []
%vb  = load %bv
%sum = add %va %vb
  1. Find the shapes. %va is (4,). %vb is one number, 10, with shape ().
  2. With silent stretching. The program runs and gives [11 12 13 14]. The author wanted [11 22 33 44]. No error, wrong numbers.
  3. With the same-shape rule. The reference compiler stops at the last line: "add: ALU operands must share one shape (no implicit broadcast: use expand)".

A rejected program costs a minute. A silent wrong answer inside a neural network can cost days.

Stretch a value on purpose

When you do want one number in every position, you say so. expand x [n] takes a scalar x and gives a vector of shape (n,) whose every element is x. The shape comes last, in square brackets, and n must be at least 1. To use a scalar with a vector, you expand it first:

%one = expand 1.0 [4]   # [1.0 1.0 1.0 1.0]
%z   = add %v %one            # fine: both (4,)
Why make broadcasts explicit

tinygrad does the same thing: a broadcast is its own node in the graph, never a side effect of an add. That keeps every op's shape rule trivial (all inputs, one shape), and it puts the broadcast where the compiler can see it. When rangeify later asks "what is element i of this value", an expand answers "the scalar, whatever i is", and that's the whole reason a broadcast costs nothing in the generated loop.

Repair: an affine map, elementwise

Slot 0 holds five f32s x, and slot 1 holds two f32s a and b. Store y[i] = a * x[i] + b into slot 2, multiplying first, then adding. The starter forgets b.

Write: clamp at zero

Slot 0 holds five f32s. Store max(x[i], 0.0) into slot 1 for every i, so negative numbers become zero. The starter has only the two buffers. You need a load, a vector of zeros, a max, a store and an after. Neural networks call this op ReLU.

Build an op the language does not have

.uir has no subtract op. You get x - y by multiplying y by -1 and adding. With vectors the -1 has to be a vector too:

%m1 = expand -1 [4]
%ny = mul %vy %m1
%df = add %vx %ny

There is no absolute value op either. The absolute value of a number is its distance from zero: 4 for both 4 and -4.

x is 3 and y is 7. So x - y is -4 and y - x is 4. Which op, given those two results, returns the distance between x and y?

One of the two differences is the answer already. Which op picks it?

One difference is the negative of the other, so the larger one is the distance. max of -4 and 4 is 4.

Absolute difference

Slots 0 and 1 hold four i32s each. Store |x[i] - y[i]| into slot 2, with i32 wraparound (there's no subtract op, and no abs op either).

Vectors don't mix with hand-written loops

A vector may not depend on an open range from a week 3 loop. "The element of a vector at iteration k" is something rangeify will build for you. Mixing the two by hand is rejected.

That rule covers computed vectors: the result of an ALU op on vectors, an expand, lesson 4.2's reduce and lesson 4.4's stage. So expand %i [4] is rejected while %i = range 4 is still open.

How silent broadcasting goes wrong in NumPy, for readers who know NumPy

NumPy stretches any axis of size 1, and adds missing axes on the left. Add an array of shape (3,) to one of shape (3, 1) and you might expect three sums. You get a 3 by 3 grid of nine, with no warning. It is a well-known source of bugs in machine learning code, often found only when a loss value looks odd. With explicit expand, the stretch is a line in the program that a reader and the compiler can both see.

Does any ALU op stretch a scalar for you?

There's no implicit broadcasting. Write %one = expand 1.0 [4] and add that.

%x and %y are i32 vectors of shape (3,). What is cmplt %x %y?

Elementwise means the result has the operands' shape, and cmplt always returns bool.

Each element compares on its own, so you get three bools, shape (3,).

What does %w hold?

%c = stack true false true
%a = stack 1 2 3
%b = stack 9 9 9
%w = where %c %a %b

The condition picks a branch separately for each element.

Element 0 takes a (1), element 1 takes b (9), element 2 takes a (3): [1 9 3].

What does cast %v dtype=i32 give for %v = stack 1.5 -2.5 0.5?

Week 2's cast rule, applied to each element. Which way does f32 to i32 round?

f32 to i32 truncates toward zero, element by element: 1, -2, 0.

Why does the course (like tinygrad) make broadcasting an explicit expand node?

Think about what each op's type rule looks like with and without it.

With explicit broadcasts, "all inputs have one shape" is the whole rule for every ALU op. And the expand node tells rangeify that the element at any index is the same scalar, so it costs nothing in the loop. Implicit broadcasting compiles fine, but it hides that structure inside every op.
