Week 4 · Lesson 4

Fuse or materialize

By the end of this lesson you can spot work that a rangeified program does more than once, and pick between two fixes: do the work again at each use, or do it once and keep the answers in memory. Your compiler needs this choice because lesson 4.3 asks "what is your element at index i?" at every place a value is used, and nothing there stops the same answer from being worked out again.

Goal

Count the arithmetic and the memory traffic of a value that has several uses, and use stage to compute it once.

You'll use

reduce and expand (lesson 4.2), "the element at index i" (lesson 4.3), the depth of a value (lesson 3.5) and the price of a trip to memory (lesson 0.2). One exercise counts with a dict (P.3).One exercise walks a list of pairs (O.3).

Warm up

Two questions from memory. Pulling an idea back out of your head is what makes it stay.

Rangeify asks expand %s [4] for its element at index i (lesson 4.3). What is the answer?

Every element of a broadcast is the same scalar.

The index does not matter, so the answer is %s.

A value is used inside a loop but does not depend on that loop's range (lesson 3.5). Where does the renderer put its C line?

A value is computed inside every loop whose range it depends on, and no deeper.

It sits before the loop and runs once. Lesson 3.5 called this hoisting.

A sum that every element needs

This program adds the total of x to each element of x. Both buffers hold 4 floats.

%v  = load %x
%s  = reduce %v op=add
%e  = expand %s [4]
%w  = add %v %e
%st = store %y %w

Answer lesson 4.3's question by hand, in the most direct way. Element i of %w is x[i] plus element i of %e. Element i of %e is %s. And %s is a reduce, which is a loop. Write each answer down at the place where it is asked for and you get this C:

for (int i = 0; i < 4; i++) {
  float s = x[0];
  for (int j = 1; j < 4; j++) {
    s = s + x[j];
  }
  y[i] = x[i] + s;
}

Guess first. How many times does the line s = s + x[j] run?

The inner loop makes 3 passes each time it starts. How many times does the outer loop start it?

12. The total needs only 3 additions, but the outer loop asks for it 4 times and it is worked out from scratch each time. On 4096 floats that is 16,773,120 additions where 4,095 would do.

The total is the same for every i. So the fix is plain: work it out once before the loop, keep it, and read it back inside the loop. Your compiler already does that, with three pieces you built earlier:

  1. One node. %s is a single node (hash consing, lesson 1.1). Rangeify builds its loop once, however many times it is asked.
  2. Depth 0. The total does not depend on the store loop's range, so the depth rule from the warm up prints it before that loop.
  3. Kept in memory. The reduce leaves its answer in a one-element alloc (lesson 4.3), and one load reads it back.

So the oracle's C has two loops side by side: 3 additions for the total, then 4 for the output. Keeping the answer costs one float of memory, so it is an easy call. The rest of this lesson is about a value where the call is harder.

A vector with two uses

Here is a sum-of-squares normalization: square every element, then divide each square by the total of the squares. The squares, %d, have two uses.

%v  = load %x
%d  = mul %v %v              # the squares
%s  = reduce %d op=add       # use 1: the total
%r  = recip %s
%e  = expand %r [4]
%w  = mul %d %e              # use 2: each square / total
%st = store %y %w

The reduce becomes one loop and the store becomes another (lesson 4.3). Each loop asks %d for its element at the loop's own index.

Guess first. Rangeify does nothing special here. With 4 elements, how many times does the C multiply an element by itself?

How many squares does the reduce need? How many does the store need?

8. The reduce needs all 4 squares, and the store loop needs all 4 again. Nothing in rangeify connects the two questions.

Why don't the pieces from the last screen help? %d is still one node, but its element at i depends on i. Each loop has its own range, so each one asks with its own index and gets its own scalar multiply. And a value that depends on a loop's range has to sit inside that loop. Hoisting cannot move it out.

To compute the squares once, you need somewhere to keep 4 floats, not 1. That is no longer free, so now there is a real choice.

Two answers: fuse or materialize

To fuse a value is to recompute it inside each loop that uses it. The work is repeated, and no extra memory is touched.

To materialize a value is to compute every element once, in a loop of its own, into a temp buffer: scratch memory that exists only while the C runs. Every use then loads from the temp.

The spec lets your compiler do either, and the oracle fuses. The op stage forces the second answer. %q = stage %d is the same value as %d, with one instruction attached: materialize me.

  1. Wrap the value. Add the line %q = stage %d.
  2. Point every use at it. The reduce becomes reduce %q op=add and the multiply becomes mul %q %e.
  3. Rangeify fills a temp. A new loop stores each square into a 4-float temp.
  4. Each use loads. Element i of %q is a load of the temp at i.

fused

s = x[0] * x[0];
for (j = 1; j < 4; j++)
  s = s + x[j] * x[j];
r = 1.0f / s;
for (i = 0; i < 4; i++)
  y[i] = x[i] * x[i] * r;

materialized into the temp t

for (i = 0; i < 4; i++)
  t[i] = x[i] * x[i];
s = t[0];
for (j = 1; j < 4; j++)
  s = s + t[j];
r = 1.0f / s;
for (i = 0; i < 4; i++)
  y[i] = t[i] * r;
Two loops become three. The oracle's exact C for both is in the reference section.
stage wraps a value, not a name

%q = stage %d is a new value. Uses of %q read the temp, and uses of %d still recompute. To share, every use has to go through %q.

Two outputs from one value

Slot 0 is x (4 f32). Write x * x into slot 1 (4 f32) and the sum of x * x into slot 2 (1 f32), using stage so both outputs read one materialized copy of the squares. The starter already writes slot 1.

Count the cost

Neither answer is free. Count what each version does to our 4 floats, leaving out the running total.

fusedmaterialized
multiplies v * v84
floats read from memory812
floats written to a temp04
extra memorynone4 floats

Materializing saved 4 multiplies and paid for them with 4 writes and 4 more reads. Lesson 0.2 says which side costs more. A multiply takes about a nanosecond or less, and a float fetched from main memory takes about 100. A small temp stays in the cache and is far quicker than that, but a write and a read are still not cheaper than the one multiply they replace. For a value as cheap as v * v, fusing wins.

In general, say a value takes ops arithmetic steps per element, has uses uses and n elements:

  • Fused: ops × uses × n arithmetic steps.
  • Materialized: ops × n arithmetic steps, plus n writes and uses × n reads of the temp.

A value takes 10 arithmetic steps per element, and three loops use it. Per element, how many arithmetic steps does materializing save?

Fused, the 10 steps run once per use. Materialized, they run once.

20: fused is 30 steps and materialized is 10. The price is 1 write and 3 reads per element. Now the saving is large, and the temp is likely worth it.

Count both costs

The starter has both formulas and choose, which picks the cheaper answer. mem is the cost of moving one float to or from the temp, counted in arithmetic steps. Each formula leaves something out. Leave choose alone.

Fused. The work repeats once per use.

Staged. Each element is written once, which is there, and read back once per use, which is missing.

When each one wins

The formulas boil down to a few rules of thumb.

  • Cheap value, few uses: fuse. The temp costs more than the arithmetic it saves.
  • Costly value, many uses: materialize. A long chain of ops that feeds several loops is worth one pass over memory.
  • One use: never stage. There is nothing to share.
  • A plain load: never stage. stage (load %x) copies x into a temp and then reads the copy instead of the original. Same reads, plus a write.

How costly a memory move is depends on whether the temp fits in the cache, so nobody settles this by formula alone. Week 6 starts timing the C, and then you measure.

A pass that decides for itself starts by listing the values with more than one use.

Which nodes are worth staging

A graph is a list of (id, srcs) pairs. Return, sorted, every non-leaf id that has two or more distinct consumers. A node read twice by the same consumer (like mul %c %c) is still one use, since rangeify builds that element once per index. That's the candidate list a materialization pass starts from.

The answer is the same either way

You can choose freely because the choice can't change the result. An elementwise op computes the same bits for the same inputs wherever it runs, and every reduce folds its elements in the same order, left to right from the first. So the recomputed square and the stored square are the same float, and both sums add the same floats in the same order.

Materialization is a performance decision

Because results can't change, stage never fixes a wrong answer, and leaving it out never breaks a right one. The grader in week 4 checks only bits and size. Week 6 starts timing kernels, and that's when the choice starts to cost or save you something.

Now write a whole program. Decide for yourself whether anything needs stage.

Variance

Slot 0 is x (8 f32). Write its variance into the one-element buffer in slot 1, computed exactly as

mean = (sum of x) * 0.125
c    = x + expand(-mean)          # -mean is mean * -1.0
var  = (sum of c * c) * 0.125

Both sums are reduce op=add. Results are compared bit for bit.

The oracle's exact C with and without stage, for when you compare your renderer's output

The three versions of the normalization (no stage, stage on one use, stage on both) compile to kernels that, with x = [1.0 2.0 3.0 4.0], leave exactly the same bits in y: 3d088889 3e088889 3e99999a 3f088889, which is 1/30, 4/30, 9/30, 16/30 rounded to f32.

Stage only the store's use and leave the reduce reading %d, and the oracle's C squares in the fill loop and again in the reduce loop: three loops, and the reduce saved nothing.

Two loops become three. Fusion multiplies twice per element. Materializing multiplies once but writes four floats and reads them twice. The % 4 lines are the extra index step from lesson 4.3. Here they never change the value, and lesson 5.5 shows how a simplifier removes them.
Storing into the memory you read: the one store your compiler must stage, for the lab's in-place tests

A program may store a value back into the buffer it was loaded from. The test r_inplace_scale_by_sum multiplies x by its own sum and stores the result into x. The value is defined by the old contents, but a fused store loop overwrites memory while it still reads it. Here that happens to be safe, since iteration i reads only x[i]. In week 5's r_inplace_transpose it isn't: a later iteration would read an element an earlier one already overwrote. So the oracle never fuses such a store. When any load in the stored value's graph reads the memory the store writes (the same buffer or alloc, through any view or after), it stages the value: one loop fills a temp, and a second loop copies the temp in.

Two reduces over one vector: why they need no temp, for when you count loops

Two reduces over one vector already work without a temp: each reduce is its own loop reading x. The oracle even shares the load of x[0] that seeds both folds, because hash consing makes it one node.

Check yourself

Without stage, how many times per element does the oracle's C compute v * v for the sum-of-squares normalization above?

How many loops ask %d for an element?

Twice: once in the reduce loop and once in the store loop. Each loop asks for %d's element at its own index, and without a temp the square is recomputed for each.

With %q = stage %d on both uses, how many for loops does the oracle render?

The reduce and the store are still loops. What does stage add?

Three: the loop that fills the temp with the squares, the reduce loop and the store loop.

Adding stage in front of a value changes which of these?

The temp holds f32 values, and the value was already f32.

Storing an f32 into an f32 buffer and reading it back gives the same bits, and reduces fold in the same order either way. The C changes (an extra loop and a temp) but the result can't.

Which stage is always a loss?

What does the temp contain, and where did those floats come from?

A staged load is a copy of memory you could read directly. It adds a write and a temp without saving any arithmetic.

You write %q = stage %d, use %q in the store, and leave the reduce reading %d. What happens?

%q and %d are two different nodes.

Stage makes a new value. Only its uses read the temp. The reduce still asks %d directly, so the square is computed in the fill loop and again in the reduce loop.

On a typical machine, why does recomputing v * v usually beat materializing it?

Lesson 0.2: compare a cycle with a trip to memory.

Arithmetic is cheap and memory traffic is not. Materializing a value pays only when computing it is expensive enough to outweigh the extra writes and reads. Week 4 doesn't time anything yet, but week 6 does.
